
> 本课以 **SEGGER embOS、Cortex-M、GCC/SEGGER Embedded Studio** 为主线。embOS 是商业 RTOS，具体 API、端口实现、许可范围和交付文件取决于 embOS 版本与授权包。**任务栈初始化、上下文切换、定时器配置和中断接口应以所持授权版本附带的 CPU port、BSP 示例和手册为准**；本课不虚构 embOS 内核源码，也不建议自行重写商业端口。

## 1. 学习目标

### 理解

- 理解 embOS 内核、CPU port、BSP、设备驱动和应用层之间的职责边界。
- 理解 Cortex-M 上任务切换、异常入口、Tick、系统锁和中断安全 API 的关系。
- 理解 embOS 移植包、评估包、目标 CPU port 与编译器 ABI 之间的匹配约束。
- 理解 embOS 与自研内核、FreeRTOS、RT-Thread 在移植工程组织和调度器集成上的差异。

### 掌握

- 能从 SEGGER 提供的目标包中选取对应 CPU、编译器和芯片的 embOS port。
- 能完成 CPU 频率、Tick 源、异常向量、堆栈、初始化顺序和中断优先级配置。
- 能建立最小 embOS 应用，运行多个任务并验证任务调度和延时。
- 能正确使用 embOS 的系统锁和中断服务接口，避免在 ISR 中调用错误 API。

### 精通

- 能通过 map 文件、反汇编、寄存器和栈快照诊断启动失败、上下文损坏、Tick 异常和优先级配置问题。
- 能量化任务切换、Tick、最大中断屏蔽时间、任务栈和同步机制开销。
- 能评估 embOS 端口与芯片安全机制、FPU、Cache、DMA、低功耗和看门狗的协作风险。
- 能定义满足产品实时性和可维护性要求的 embOS BSP 验收测试。

### 能够设计

- 能规划 embOS 在产品中的移植目录、配置管理、驱动层和应用层边界。
- 能设计线程优先级、栈预算、ISR 工作边界和资源同步策略。
- 能为商业 RTOS 建立版本、授权、可复现构建和第三方软件合规流程。
- 能制定量产级故障诊断、升级回归和长期维护方案。

## 3. 技术概述

### 3.1 embOS 的组成

embOS 移植通常由以下部分组成：

```
应用层
  ├── embOS 任务/同步对象 API
  ├── 业务逻辑
  └── 驱动调用

embOS 内核
  ├── 任务调度
  ├── 任务状态管理
  ├── 信号量、事件、邮箱等同步对象
  └── 时间管理

CPU port
  ├── 任务上下文保存和恢复
  ├── 初始任务栈构造
  ├── 临界区/系统锁实现
  └── CPU 特定辅助函数

BSP / 芯片支持层
  ├── 启动文件和向量表
  ├── 时钟树
  ├── Tick 定时器
  ├── UART、DMA、GPIO 等设备
  └── 链接脚本和内存区域

工程与许可
  ├── embOS 版本/授权包
  ├── 编译器与目标 CPU 组合
  ├── 构建配置
  └── 交付范围和许可约束
```

### 3.2 移植的关键边界

对于商业内核，工程师通常不是从零实现调度器，而是：

1. 选取官方支持的 CPU port 和工具链组合。
2. 将内核源码、端口源码、启动文件和芯片 BSP 接入工程。
3. 配置 CPU 频率、Tick 频率、堆栈和中断策略。
4. 按该版本文档完成初始化。
5. 验证调度、ISR、同步机制、性能和故障处理。

**不要将“内核源码可编译”视为移植完成。** 端口与工具链 ABI、异常入口、时钟配置和芯片向量表必须一起验证。

### 3.3 版本与授权边界

实际工程开始前，记录：

|项目|必须记录|
|---|---|
|embOS 版本|发行版、补丁版本或包标识|
|CPU port|架构、核心、端口变体|
|编译器|名称、版本、ABI 选项|
|工程模板|SEGGER Embedded Studio、IDE 或命令行构建配置|
|芯片|型号、硅版本、时钟配置|
|授权|开发、评估、量产和交付范围|
|修改项|本地补丁、修改理由、回归记录|

商业授权条件取决于具体合同和版本，需由项目负责人核对。不要把评估包、授权包中的文件混用，也不要将商业内核文件提交到不符合许可要求的公开仓库。

## 4. 核心特性横向对比

### 4.1 embOS 常见移植路径

|移植路径|适用情况|优点|主要风险|
|---|---|---|---|
|使用 SEGGER 提供的芯片示例工程|芯片和工具链有现成示例|启动、时钟、调试配置通常已打通|示例可能针对旧芯片或旧工具链|
|使用官方 CPU port + 自有 BSP|CPU port 支持，但没有完整板级工程|内核端口风险较低，BSP 可按产品组织|Tick、中断、时钟和启动需要自行整合|
|使用 SEGGER Embedded Studio 项目模板|使用 SES 及对应芯片|工程配置和调试体验较完整|构建脚本可能绑定 IDE|
|使用其他工具链官方 port|编译器有对应官方支持|可融入既有工程|ABI、汇编语法、启动配置需要严格匹配|
|自行编写 CPU port|官方无目标支持或特殊架构|可适配特殊处理器|需要与 SEGGER 协作或获得明确支持；验证风险最高|

### 4.2 CPU 端口需要具备的能力

|能力|说明|Cortex-M 关注点|
|---|---|---|
|任务初始栈构造|让新任务首次恢复时进入任务入口|Thumb 位、PC/LR、栈对齐、FPU 状态|
|任务切换|保存当前任务、恢复目标任务|PendSV 或端口指定异常|
|首次任务启动|无当前任务时启动第一个任务|PSP、异常返回或端口启动函数|
|系统 Tick|推进时间、处理超时|SysTick/定时器源和频率|
|中断服务配合|处理 ISR 中的任务唤醒和调度请求|ISR API 和优先级约束|
|系统锁/临界区|保证内核数据结构原子更新|`BASEPRI`、`PRIMASK` 或端口实现|
|FPU 上下文|保存浮点寄存器状态|lazy stacking、浮点 ABI|
|调试支持|线程列表、栈检查、性能追踪|端口和工具版本匹配|

### 4.3 Cortex-M 端口变体的考虑因素

|条件|影响|
|---|---|
|M0/M0+ 与 M3/M4/M7|可用指令和中断屏蔽机制不同|
|是否有 FPU|影响上下文与编译 ABI|
|是否有 D-Cache|DMA 缓冲区一致性成为系统设计问题|
|使用 `BASEPRI` 还是全局关中断|影响临界区延迟和中断优先级策略|
|TrustZone-M|需要处理安全/非安全状态和栈|
|多核|需要 SMP 调度、跨核同步和 IPI 支持，不能套用单核端口|

## 5. 底层原理与功能特性深度解析

### 5.1 启动和内核初始化顺序

典型 Cortex-M 启动路径：

```
Reset_Handler
  |
  |-- 建立 MSP
  |-- 初始化 .data / .bss
  |-- SystemInit 或厂商时钟初始化
  |-- C 运行库初始化
  |
  |-- main()
        |
        |-- 初始化板级硬件
        |-- 配置 embOS Tick
        |-- 初始化 embOS
        |-- 创建任务
        |-- 启动调度器
```

不同 embOS 版本和工程模板的 API 名称及顺序可能不同。**使用该版本官方示例中的启动接口，不要凭记忆拼接 `OS_Init()`、Tick 配置或调度启动 API。**

推荐移植检查顺序：

```
启动文件与链接脚本
  -> 系统时钟
  -> CPU port 和向量表
  -> embOS 初始化
  -> Tick 配置
  -> 线程/任务创建
  -> 调度器启动
  -> 外设中断启用
```

启动调度器前启用高频外设中断容易出现“ISR 已运行，但内核和同步对象尚未初始化”的竞态。通常先完成内核基础初始化和对象创建，再按产品时序启用业务中断。

### 5.2 Cortex-M 上下文切换原理

典型 Cortex-M 实现中：

- 线程模式使用 PSP。
- 异常处理模式使用 MSP。
- 触发调度请求后，端口将上下文切换安排在合适异常中处理。
- 硬件异常入栈自动保存部分寄存器。
- 端口汇编保存剩余需要保留的寄存器。
- 调度器选择目标任务。
- 端口恢复目标任务上下文，并通过异常返回继续执行。

上下文结构通常涉及：

```
硬件自动保存部分：
R0-R3、R12、LR、PC、xPSR

软件保存部分：
R4-R11，以及端口要求的其他状态

可选状态：
FPU 寄存器、浮点状态控制寄存器、安全状态等
```

具体寄存器集合由 embOS CPU port 决定。不要将其他 RTOS 的 PendSV 汇编复制到 embOS 中；即使架构相同，端口的栈布局和调度器接口也可能不同。

### 5.3 线程初始栈

线程创建后，内核需要构造一个初始上下文，使第一次任务切换能够进入线程入口函数。Cortex-M 栈帧通常涉及：

- 线程入口地址。
- 线程参数。
- 线程退出处理入口。
- xPSR。
- 栈对齐。
- 端口需要的软件保存寄存器。
- 可选 FPU 状态。

**生产代码应使用 embOS 官方线程创建 API 和官方 CPU port 的栈初始化实现。** 不要自行生成栈帧，除非正在开发新 CPU port 且有 SEGGER 提供的架构规范与审核支持。

线程栈大小的单位也要查目标版本文档：可能以字节或栈字为单位。不要从另一个 RTOS 的 API 习惯推断。

### 5.4 Tick 配置

Tick 的职责通常包括：

- 推进系统时间。
- 唤醒超时任务。
- 处理延时和定时事件。
- 支持时间片或调度时基。
- 在需要时触发调度。

配置时应确定：

```
CPU 实际频率
Tick 定时器时钟源
Tick 目标频率
定时器重装值
中断优先级
主频动态变化策略
低功耗期间的计时策略
```

常见误差来源：

- 系统主频改变后没有重设定时器。
- Tick 时钟源并非 `SystemCoreClock`。
- 总线分频导致定时器时钟与 CPU 频率不同。
- 定时器整数分频产生周期量化误差。
- Tick ISR 被较长高优先级 ISR 延迟。
- 低功耗进入和退出时丢失或重复计时。

### 5.5 中断和内核 API

ISR 是否可以调用某个 embOS API、调用前是否必须通知内核进入/退出中断上下文、是否支持从 ISR 请求切换，**都必须以该版本手册和 CPU port 示例为准**。

通用设计原则：

- ISR 不阻塞、不睡眠、不等待资源。
- ISR 执行时间可界定。
- ISR 只采集状态、清除中断、搬运必要数据并通知任务。
- 较复杂解析在任务中执行。
- 高优先级 ISR 不访问未经证明可并发访问的内核对象。
- 若 API 有 ISR 专用版本，必须使用对应 ISR API。
- 不要将“某 API 运行时没有崩溃”当成它可在 ISR 使用的证据。

示意结构：

```
void DMA_IRQHandler(void)
{
    /* 清中断并收集最小必要状态。 */
    dma_acknowledge_irq();

    /* 平台相关：调用 embOS 当前版本规定的 ISR/内核通知接口。 */
    embos_notify_data_available_from_isr();
}
```

此处 `embos_notify_data_available_from_isr()` 是说明性占位符，不是 embOS API 名称。

### 5.6 中断优先级与临界区

Cortex-M 上优先级数值通常越小代表紧急程度越高，但 CMSIS 接口、NVIC 寄存器编码和 RTOS 配置宏可能使用不同编码形式。

移植必须确认：

- 芯片实际实现的优先级位数。
- embOS port 的临界区屏蔽策略。
- 内核可调用 ISR 的优先级范围。
- Tick、PendSV 和外设中断的相对优先级。
- 临界区是否会屏蔽全部中断。
- 是否存在不受临界区屏蔽的高优先级 ISR。

建议建立明确的中断分级：

|中断类别|典型职责|是否访问内核对象|
|---|---|---|
|紧急硬件保护|立即关闭输出、锁存故障|通常不调用 RTOS API|
|高优先级数据采集|采样、DMA 状态处理|只用经端口文档确认的 ISR 接口|
|普通外设中断|唤醒任务、提交事件|使用允许的 ISR API|
|低优先级系统异常|Tick、延迟切换|由 CPU port 管理|

### 5.7 任务和同步对象设计

embOS 应用中的任务通常应围绕功能和时限划分，而不是机械地“一外设一任务”。

示例结构：

```
高优先级：
  安全状态管理
  实时控制

中优先级：
  传感器采集处理
  通信收发

低优先级：
  日志
  诊断 Shell
  非实时维护
```

使用同步对象时应明确：

- 谁是生产者，谁是消费者。
- 对象是否允许多生产者/多消费者。
- 是否会阻塞。
- 超时语义。
- ISR 使用规则。
- 资源所有权。
- 失效和恢复策略。

### 5.8 内存和任务栈

要逐项核算：

```
任务控制块
+ 各任务栈
+ embOS 内核数据
+ 驱动状态
+ 中断栈
+ DMA 缓冲区
+ 日志缓冲区
+ 应用对象
+ 对齐和保留区
```

产品中建议：

- 固定线程优先静态分配。
- 高频、固定大小对象使用内存池。
- 动态分配必须定义失败处理和监测。
- 任务栈用高水位和最大调用路径共同验证。
- 确认中断运行时使用 MSP 还是其他栈，以及中断嵌套的最大栈需求。
- 使用 map 文件确认 RAM 区域没有重叠。

## 6. 性能量化分析

### 6.1 测试环境必须记录

|项目|示例记录|
|---|---|
|MCU|Cortex-M4F，具体芯片型号|
|主频|120 MHz|
|embOS|具体发行版与补丁|
|CPU port|对应核心和编译器目录|
|编译器|GCC/SES 版本与 ABI|
|优化|`-O2` 或项目实际选项|
|Tick|1000 Hz|
|FPU|启用/关闭及 ABI|
|Cache|状态和策略|
|测量方法|DWT、GPIO、J-Link trace|
|测试负载|任务数、ISR 数、队列流量|

### 6.2 计算公式

#### Tick 占用

```
U_tick = C_tick × f_tick / f_cpu
```

#### 上下文切换占用

```
U_switch = C_switch × f_switch / f_cpu
```

#### 任务栈总 RAM

```
RAM_stack = Σ(stack_size_i)
```

前提是 `stack_size_i` 已按实际 API 单位换算成字节。

#### 任务响应时间

简化模型：

```
R =
    最长不可抢占区
  + 更高优先级 ISR 执行时间
  + 调度等待
  + 上下文切换时间
  + 任务自身执行时间
```

完整响应时间分析还要考虑任务阻塞、资源竞争、ISR 嵌套和总线争用。

### 6.3 示例估算

以下仅演示计算，不是 embOS 官方性能数据，也不是特定芯片实测值。

假设：

```
CPU：120 MHz
Tick：1000 Hz
Tick ISR：1000 cycles
任务切换：500 cycles
每秒切换：2000 次
```

Tick 占用：

```
1000 × 1000 / 120,000,000 ≈ 0.83%
```

切换占用：

```
500 × 2000 / 120,000,000 ≈ 0.83%
```

实际开销必须在目标板上测量，且 FPU、Cache、编译器和任务状态会影响结果。

### 6.4 推荐测量方法

#### DWT 周期计数器

```
static void cycle_counter_enable(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->CYCCNT = 0U;
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;
}

static uint32_t cycle_counter_read(void)
{
    return DWT->CYCCNT;
}
```

建议分别测量：

- 空任务循环。
- 任务主动切换。
- Tick 引起的切换。
- ISR 到任务恢复延迟。
- 临界区最长时间。
- 同步对象等待和唤醒路径。
- 带 FPU 任务切换与不带 FPU 任务切换。

#### GPIO 测量

```
外部事件
  -> ISR 拉高 GPIO
  -> ISR 完成
  -> 任务被唤醒后拉高第二个 GPIO
```

逻辑分析仪可以直接观察中断延迟和线程响应延迟，适用于验证真实板级时序。

### 6.5 优化方向

|瓶颈|优化方向|
|---|---|
|Tick ISR 过频|评估更低 Tick 或硬件定时器事件驱动|
|任务切换频繁|合并过细任务，减少无意义唤醒|
|长临界区|缩短共享状态保护范围|
|ISR 过长|DMA、环形缓冲、任务后处理|
|日志阻塞|异步日志和限速|
|任务栈过大|结合高水位和静态调用分析逐项优化|
|高优先级线程占满 CPU|限定批处理长度，设计让出或阻塞点|
|低功耗唤醒开销|使用合适的低功耗时钟和唤醒源|

## 7. 应用场景选型指南

### 决策流程图

```
开始
 |
 |-- embOS 是否有匹配目标 CPU、编译器的官方 port？
 |       |-- 有：使用官方 port 和对应版本示例
 |       |-- 无：联系 SEGGER 确认支持边界，不轻易自写商业内核端口
 |
 |-- 是否有匹配芯片的 BSP 示例？
 |       |-- 有：以示例为基线，审查版本和时钟差异
 |       |-- 无：复用 CPU port，自行移植 BSP 与驱动
 |
 |-- 产品是否要求确定性内存？
 |       |-- 是：静态任务/对象，使用固定缓冲区和内存池
 |       |-- 否：按版本支持方式使用动态分配，并定义失败策略
 |
 |-- 是否使用 FPU、Cache、DMA、TrustZone？
 |       |-- 是：匹配端口和 ABI，额外验证上下文与内存一致性
 |       |-- 否：执行常规切换和中断验证
 |
 |-- 是否要求低功耗或动态调频？
         |-- 是：验证 Tick 补偿、时钟切换和唤醒误差
         |-- 否：固定时钟建立性能基线
```

### 典型场景

|需求|推荐方式|理由|
|---|---|---|
|目标芯片有 SEGGER 示例|从该示例开始|端口、启动和调试设置更容易核对|
|只有 CPU port、没有 BSP|复用官方 port，自建板级初始化|将内核端口风险与硬件适配风险分离|
|RAM 严格受限|静态任务和固定缓冲区|运行时内存边界更可控|
|高速 DMA 通信|DMA + ISR 通知 + 处理任务|ISR 短，减少复制和中断占用|
|FPU 控制算法|官方 FPU 端口 + 统一 ABI|避免任务间 FP 状态污染|
|低功耗传感设备|低功耗计时源 + 唤醒补偿|避免普通 SysTick 阻止深睡眠|
|量产商业产品|固定授权包和可复现构建|控制授权、版本和交付风险|

## 8. 工程最佳实践

### 8.1 设计原则

1. **只使用与 embOS 版本匹配的 CPU port 和示例。**
2. **保留官方端口的原始来源和修改记录。**
3. **业务代码不直接依赖端口内部符号。**
4. **将板级时钟、Tick、驱动和内核初始化分层。**
5. **所有 ISR API 使用规则写入项目规范。**
6. **所有任务栈和 RAM 资源纳入静态预算表。**
7. **启用断言、栈检查、故障快照和看门狗诊断。**
8. **将许可证和第三方软件清单纳入发布流程。**
9. **对编译器升级、主频变化、FPU 配置变化做完整回归。**
10. **用实测最坏值验收实时性，不用平均值代替上界。**

### 8.2 移植验收矩阵

|阶段|验收项|
|---|---|
|编译|内核、CPU port、BSP 无重复符号或 ABI 冲突|
|链接|RAM/Flash 使用与链接脚本预算一致|
|启动|首任务稳定启动，异常入口正确|
|Tick|周期误差和长期漂移符合需求|
|调度|高低优先级抢占行为正确|
|ISR|中断嵌套、优先级和内核 API 使用合法|
|内存|栈、堆、静态对象和 DMA 区域边界正确|
|性能|切换、Tick、ISR 和临界区满足预算|
|稳定性|长时间压力运行、错误注入和恢复路径通过|
|合规|授权包、交付文件和源码修改符合许可|

### 8.3 构建和版本管理规范

- embOS 内核文件与 CPU port 作为固定版本依赖。
- 不将 IDE 自动生成文件与内核源文件混为一个不可追踪目录。
- 保存编译命令、链接脚本、启动文件和工具链版本。
- 对每次 embOS 升级进行：
    - API 差异审查。
    - CPU port 差异审查。
    - 性能回归。
    - 栈和内存回归。
    - 许可范围确认。
- 商业内核文件的分发方式应符合授权合同。
- 本地补丁必须有原因、责任人、测试和回退方式。

## 9. 常见错误与避坑指南

### 错误一：使用了错误 CPU port 或编译器 ABI

错误示例：

```
Cortex-M4F 工程
  + Cortex-M3 port
  + 硬浮点 ABI
```

#### 根因

CPU port 与核心指令集、FPU 配置或编译器 ABI 不匹配。不同目标文件使用不一致的 `-mcpu`、`-mfpu`、`-mfloat-abi` 也可能产生隐蔽问题。

#### 正确实现

- 使用 embOS 包中与 CPU 和编译器对应的端口。
- 统一所有目标文件编译选项。
- 检查 ELF ABI 和 map 文件。
- 使用多个任务并发执行浮点运算，验证上下文隔离。

#### 风险影响

- 链接失败。
- 首次切换异常。
- 只有浮点任务并发时才出现数据污染。
- 随机 HardFault。

### 错误二：SysTick 配置使用错误时钟

错误示例：

```
#define CPU_CLOCK_HZ 16000000U
/* 实际运行时钟为 120 MHz，Tick 仍按旧配置设置。 */
```

#### 根因

将振荡器频率、CPU 频率、总线频率或定时器时钟混为一谈。

#### 正确实现

用芯片时钟树计算 Tick 定时器实际输入频率：

```
f_timer =
    f_source
  / prescaler
  × timer-specific multiplier
```

再计算重装值：

```
reload ≈ f_timer / f_tick - 1
```

具体边界和计数方式依据定时器数据手册及端口实现确认。动态改频后重新配置 Tick。

#### 风险影响

- 延时不准确。
- 超时提前或延后。
- 调度行为随主频切换变化。
- 软件定时器长期漂移。

### 错误三：在 ISR 中使用线程 API

错误示例：

```
void UART_IRQHandler(void)
{
    OS_Delay(1);  /* 错误示意：ISR 中阻塞 */
}
```

#### 根因

ISR 没有可阻塞的任务上下文；阻塞 API 可能修改任务状态并要求切换。

#### 正确实现

- ISR 只接收数据、清状态、更新缓冲区。
- 使用 embOS 手册中明确允许的 ISR 同步接口通知任务。
- 由任务执行解析和阻塞等待。

```
void UART_IRQHandler(void)
{
    uart_drain_fifo_to_ring();
    embos_signal_worker_from_isr(); /* 说明性占位符 */
}
```

#### 风险影响

- 死锁。
- 调度器状态损坏。
- 中断无法退出。
- 系统复位。

### 错误四：向量表仍指向默认异常处理器

错误示例：

```
void PendSV_Handler(void)
{
    for (;;) {
        /* startup 文件默认实现 */
    }
}
```

#### 根因

- 启动文件强符号覆盖了 CPU port。
- 向量表指向旧地址。
- `VTOR` 未指向当前向量表。
- 使用了错误的启动文件。

#### 正确实现

- 检查最终 ELF 中异常符号的地址。
- 检查向量表对应项。
- 运行时检查 `SCB->VTOR`。
- 确认 SVC、PendSV、Tick 中断映射符合该版本端口要求。

#### 风险影响

- 调度器无法启动。
- 首次 Tick 后死机。
- 任务无法切换。

### 错误五：任务栈尺寸单位理解错误

错误示例：

```
OS_TASK task;
uint32_t stack[256];

/* 将 256 理解为 256 字节，实际数组占 1024 字节。 */
```

#### 根因

混淆了 API 使用的字节数、栈元素数和数组实际字节数。

#### 正确实现

- 以目标版本 API 定义为准。
- 使用 `sizeof(stack)` 传递真实数组字节数，前提是 API 需要字节。
- 记录栈深度的单位和对齐要求。
- 用高水位和最坏调用路径测量。

#### 风险影响

- 栈越界覆盖相邻对象。
- RAM 预算错误。
- 难以复现的任务崩溃。

### 错误六：临界区中调用阻塞或慢速 API

错误示例：

```
OS_EnterRegion();

uart_write_blocking(data, length);
OS_Delay(1);

OS_LeaveRegion();
```

#### 根因

临界区可能屏蔽中断或阻止调度，长时间持锁会增加 ISR 延迟，并可能造成死锁。

#### 正确实现

```
OS_EnterRegion();
copy_shared_metadata_to_local();
OS_LeaveRegion();

uart_submit_dma(data, length);
```

具体锁接口和调用限制需查 embOS 对应版本手册。

#### 风险影响

- 高优先级中断延迟超标。
- 系统锁长期占用。
- 优先级反转或死锁。
- 看门狗超时。

### 错误七：DMA 与 Cache 未做一致性处理

#### 根因

DMA 与 CPU Cache 对同一物理内存的可见内容不一致。

#### 正确实现

- TX 前按平台要求 clean cache。
- RX 后按平台要求 invalidate cache。
- 缓冲区按 Cache line 对齐。
- 明确 DMA 和 CPU 的缓冲区所有权。
- 或将缓冲区放在非缓存区。

#### 风险影响

数据错乱、间歇性校验错误和难以复现的通信故障。

## 10. 多机制组合使用方案

### 10.1 架构：DMA + ISR + ISR-safe 通知 + 工作任务

```
DMA
  -> 中断
  -> 更新缓冲区描述符
  -> ISR-safe 通知
  -> 工作任务
  -> 数据解析
  -> 业务队列
```

核心原则：

- ISR 不做协议解析。
- 任务不直接操作 DMA 所有权细节。
- 缓冲区由状态机管理。
- 任务通知机制必须使用 embOS 对应版本允许在 ISR 中使用的接口。
- 队列溢出和 DMA overrun 必须计数并可诊断。

示意代码：

```
typedef struct
{
    uint8_t *data;
    uint16_t length;
    uint8_t index;
} dma_block_t;

static dma_block_t ready_blocks[4];
static volatile uint32_t dma_overrun_count;

void DMA_IRQHandler(void)
{
    dma_block_t block;

    dma_acknowledge_irq();

    block.index = dma_get_completed_index();
    block.data = dma_get_buffer(block.index);
    block.length = dma_get_length();

    dma_prepare_rx_buffer_for_cpu(block.data, block.length);

    if (!dma_ready_ring_push_from_isr(&block)) {
        dma_overrun_count++;
        dma_release_or_drop_block(block.index);
        return;
    }

    /*
     * 替换为所用 embOS 版本文档明确支持的 ISR-safe 通知接口。
     */
    embos_notify_worker_from_isr();
}

static void DataWorker(void)
{
    dma_block_t block;

    for (;;) {
        embos_wait_for_data_event();

        while (dma_ready_ring_pop(&block)) {
            if (!validate_frame(block.data, block.length)) {
                frame_error_count++;
                dma_release_or_drop_block(block.index);
                continue;
            }

            process_frame(block.data, block.length);
            dma_release_block(block.index);
        }
    }
}
```

上述 `embos_*` 函数为说明性占位符，不是 embOS API。产品实现必须替换为所持版本的真实接口。

### 10.2 组合设计检查点

- ISR-safe API 是否被文档明确允许。
- 中断优先级是否满足 port 限制。
- 通知是否可能丢失或合并。
- 事件是否需要计数语义。
- 队列容量是否满足突发数据预算。
- DMA 缓冲区是否可能在处理完成前被重新使用。
- 任务是否能处理峰值数据率。
- 错误计数是否能从诊断接口读取。
- 故障时是否停止 DMA 或进入降级模式。

## 11. 工业级实际案例分析

### 11.1 案例一：高可靠电机控制器

#### 需求

- 电流采样周期 50 us。
- PWM 与 ADC 硬件同步。
- 控制回路最坏执行时间有上界。
- 通信、诊断和日志不得阻塞控制路径。

#### 架构

```
PWM 定时器
  -> ADC 采样
  -> ADC 完成 ISR
  -> 安全限值快速判断
  -> 控制任务或受控实时上下文
  -> 更新 PWM

通信任务
  -> CAN 接收和命令解析

诊断任务
  -> 故障日志和运行统计
```

#### 设计要点

- 硬件紧急关断必须独立于普通线程调度。
- 高频采样使用硬件定时器和 DMA，不依赖 RTOS Tick。
- 中断处理只执行短小、有界的工作。
- 控制任务优先级高，但执行时间必须有上限。
- 日志必须异步且限速。
- 栈预算覆盖最深控制算法路径、浮点库和异常路径。
- 通过 GPIO 和 DWT 测量 ISR、任务响应和控制周期最坏值。

### 11.2 案例二：工业通信网关

#### 需求

- 多通道 UART、CAN、以太网同时运行。
- 支持配置、远程升级、日志和网络协议。
- 需要长期运行，不能依赖定期重启清理资源。

#### 架构

```
UART/CAN/ETH DMA
  -> 各驱动 ISR
  -> 固定缓冲区/描述符池
  -> 通信任务
  -> 协议路由任务
  -> 业务任务

Flash 管理任务
  -> 配置持久化
  -> OTA 镜像写入和校验
```

#### 设计要点

- 网络包、CAN 消息和串口帧使用各自的固定池。
- Flash 写入由单一任务串行管理。
- 不在网络 ISR 中分配内存或打印日志。
- 每个设备定义背压策略、超时和错误恢复状态机。
- OTA 使用镜像校验、回滚和启动确认机制。
- 监控内存池最低余量、队列峰值、丢包和重传。

### 11.3 案例三：低功耗数据记录器

#### 需求

- 大部分时间处于低功耗。
- 每秒采样一次，异常时立即唤醒。
- 需要长时间运行的时间戳和掉电安全存储。

#### 架构

```
RTC/低功耗定时器
  -> 唤醒
  -> 恢复时钟和外设
  -> embOS 时间基准补偿
  -> 采样任务
  -> 非易失存储任务
```

#### 设计要点

- 确认当前 embOS 版本对低功耗 Tick 的支持方式。
- 睡眠时间使用持续工作的低功耗计时源测量。
- 恢复时钟后重新配置周期定时器。
- 存储写入采用日志结构或双区提交，避免掉电破坏最后一份有效数据。
- 量测睡眠电流、唤醒延迟、时间误差和长期漂移。
- 低功耗恢复路径避免使用尚未恢复的 UART 日志。

## 12. 高频问题深度答疑

### Q1：为什么应优先使用官方 CPU port？

CPU port 不只是几段切换汇编。它还定义了栈布局、异常返回、临界区、ISR 协作、浮点上下文和调试能力。自己重写会让这些行为与商业内核内部假设失配。没有官方支持时，应先与 SEGGER 确认支持范围和移植方案。

### Q2：embOS 是否一定使用 SysTick？

不一定。可以使用芯片定时器或其他系统时基。选择时考虑频率稳定性、低功耗行为、与外设的资源冲突、动态调频和中断延迟。实际可用方式由 CPU port 和 embOS 版本支持情况决定。

### Q3：调度器启动后不返回是正常的吗？

一般调度器成功启动后会转入任务执行，不应按普通函数返回路径继续运行。若启动失败或进入异常，检查官方启动顺序、首任务栈帧、CPU port、异常向量、Tick 配置和堆栈边界。

### Q4：为什么不能直接把其他 RTOS 的 PendSV 代码用于 embOS？

上下文切换汇编依赖内核对任务控制块、栈指针存储位置、锁状态和调度请求的约定。即使 Cortex-M 寄存器相同，软件栈帧和端口接口仍可能完全不同。应使用 embOS 对应版本官方端口。

### Q5：ISR 中能否调用 embOS API？

要看具体 API、版本和 CPU port。只有手册明确标注可用于 ISR 的接口才可使用。阻塞、延时、线程控制和普通同步接口通常不能在 ISR 里直接使用；ISR 应短小并通过允许的机制唤醒任务。

### Q6：任务栈的“剩余空间”是否能证明栈绝对安全？

不能。高水位只能代表已覆盖负载下的历史使用情况。未走到的错误路径、递归、异常嵌套、FPU 调用和编译器变化可能增加栈深度。应结合静态调用分析、压力测试和安全余量。

### Q7：商业 RTOS 的工程移植需要额外考虑什么？

除了功能和实时性，还需要：

- 授权包与目标产品范围。
- 源码修改和二次分发边界。
- 内核版本追踪。
- 编译器版本兼容。
- 供应链和漏洞通知流程。
- 发布产物中包含的文件清单。
- 调试包与量产包的授权区别。

这些问题由项目许可和具体合同决定，不能只按技术示例推断。

## 13. 课程核心总结

### 核心结论

- embOS 移植的优先策略是**使用与目标 CPU、编译器和内核版本匹配的官方端口及示例**。
- Cortex-M 重点检查：
    - 初始任务栈。
    - 上下文切换。
    - 异常向量。
    - Tick 时钟。
    - 中断优先级和 ISR API 规则。
- BSP 需明确划分时钟、Tick、设备、内存和启动职责。
- ISR 只处理必要的实时工作，复杂逻辑交给任务。
- FPU、DMA、Cache、低功耗和动态调频都需要专项验证。
- 性能必须在目标硬件和真实负载上测量，估算值不能当成实测值。
- 商业 RTOS 的版本、授权和交付文件管理是工程质量的一部分。

### 通用选型结论

```
有匹配官方示例：
  以官方示例为基线，按产品需求裁剪。

无完整 BSP 但有官方 CPU port：
  复用 CPU port，自建 BSP；不要重写内核端口。

无官方 CPU port：
  先确认 SEGGER 支持范围和授权条件，再评估自定义移植。
```

|中断|ISR API 允许性和优先级范围明确|
|FPU|编译 ABI 与端口一致，任务上下文测试通过|
|DMA|Cache、对齐、缓冲区所有权明确|
|RAM|任务栈、内核对象、驱动缓冲区和 DMA 区域无冲突|
|许可|开发、量产、交付与归档范围确认|
|性能|Tick、切换、ISR 和临界区数据来自目标板测量|

### 场景选型表

|场景|建议|
|---|---|
|官方芯片示例存在|从示例工程开始|
|只有 CPU port|保留端口，自行适配 BSP|

|量产交付|锁定版本、许可清单、构建可复现|

## 16. 实践与进阶路径

### 梯度实战任务

1. **复现官方示例**
    
    - 固定 embOS 包、CPU port、编译器和开发板。
    - 编译、下载、运行官方示例。
    - 保存原始 map 文件和构建配置。
2. **最小板级适配**
    
    - 更换为目标板时钟配置。
    - 配置 Tick 源。
    - 验证 UART 输出和异常向量。
    - 启动两个任务并验证抢占。
3. **中断集成**
    
    - 接入 UART 或 DMA 中断。
    - 通过当前版本允许的 ISR 接口唤醒任务。
    - 测量中断到任务响应延迟。
    - 验证队列或缓冲区溢出策略。
4. **内存和栈测试**
    
    - 对所有任务记录栈大小和高水位。
    - 覆盖最大报文、错误路径、日志和 FPU 运算。
    - 制造内存耗尽和栈边界故障，验证诊断行为。
5. **性能基线**
    
    - 测量 Tick ISR、任务切换、系统锁和 ISR 响应。
    - 在最大负载和中断嵌套下重复测量。
    - 将最大值和高分位值纳入回归报告。
6. **低功耗或动态调频**
    
    - 增加低功耗计时源。
    - 验证 Tick 补偿和长时间漂移。
    - 改变主频并测试时基、通信波特率和任务响应。

### 测试与故障注入

- 反复启动和停止任务。
- 队列满、信号量未释放、设备超时。
- DMA overrun 和 Cache 一致性。
- 高优先级 ISR 持续占用。
- 时钟配置错误。
- 任务栈接近边界。
- 低功耗唤醒竞争。
- 看门狗复位和复位原因保存。
- embOS 版本或编译器升级回归。

### 进阶学习方向

- 阅读所用版本的 embOS 用户手册和 CPU port 文档。
- 对照官方 Cortex-M 端口分析任务栈布局和异常处理。
- 深入研究中断优先级、系统锁和最坏响应时间分析。
- 研究 FPU lazy stacking、Cache 一致性、MPU 和 TrustZone-M。
- 研究低功耗 Tick、动态时钟和外部低功耗定时器协同。
- 建立商业内核版本升级、许可核查、性能回归和构建可复现流程。
