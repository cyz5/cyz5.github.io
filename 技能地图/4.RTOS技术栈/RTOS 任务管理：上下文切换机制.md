
## 1. 学习目标
### 理解

- 解释任务上下文包含哪些 CPU 状态，以及为什么上下文切换不等于“保存全部寄存器”。
- 区分**任务切换、异常/中断切换、调度器选择**三个阶段。
- 说明 Cortex-M 异常入栈、PendSV、任务栈与 MSP/PSP 的关系。

### 掌握

- 根据 Cortex-M 异常栈帧推导任务栈布局。
- 阅读 FreeRTOS Cortex-M 端口中的 PendSV 汇编，跟踪被切换任务的保存与恢复过程。
- 计算上下文切换时间、任务栈最低需求及切换频率带来的 CPU 占用。

### 精通

- 分析 FPU、TrustZone、寄存器扩展、嵌套中断等因素对上下文和栈开销的影响。
- 定位栈溢出、错误返回、任务状态损坏、优先级配置错误等切换相关故障。
- 设计可测量、可追踪、可验证的任务切换机制。

### 能够设计

- 设计 ISR 唤醒高优先级任务后延迟到 PendSV 切换的调度路径。
- 为目标 MCU 建立上下文切换性能基线与栈预算。
- 评估任务切换机制对实时性、能耗和可维护性的影响。

## 2. 前置要求

### 知识要求

- Cortex-M 异常模型：异常入口、异常返回、优先级与尾链。
- RTOS 任务状态：运行态、就绪态、阻塞态、挂起态。
- ARMv7-M/ARMv8-M 基础寄存器：R0-R15、xPSR、CONTROL、MSP、PSP。
- 优先级调度、临界区、抢占和中断安全 API。
- 了解任务栈由谁分配、内核如何保存栈指针。

### 技能要求

- 能阅读 C 与 ARM 汇编混合代码。
- 能使用调试器查看 PSP、MSP、异常栈帧及任务栈高水位。
- 能用 GPIO、DWT cycle counter 或 trace 工具测量延迟。
- 能检查 map 文件、编译器生成代码和链接后的栈布局。

## 3. 技术概述

**上下文切换**是内核将 CPU 的执行状态从当前任务保存起来，并恢复另一个可运行任务状态的过程。恢复后，新任务从上次暂停的位置继续执行，或首次进入任务入口函数。

任务上下文通常包括：

- 通用寄存器：R4-R11 等调用者保存状态。
- 异常硬件栈帧：R0-R3、R12、LR、PC、xPSR。
- 栈指针与控制状态：PSP、CONTROL 等。
- 扩展状态：FPU 浮点寄存器、TrustZone 安全状态、架构扩展寄存器等。
- 内核调度状态：任务状态、优先级、就绪队列、时间片等。它们属于内核对象，不一定都在 CPU 上下文栈中。

Cortex-M 上，典型切换路径是：

1. 中断或系统调用使高优先级任务变为就绪。
2. 内核请求 PendSV。
3. PendSV 以低于普通中断的优先级运行，避免在高优先级 ISR 中执行调度器。
4. PendSV 保存当前任务软件上下文，调用调度器选出下一任务。
5. 恢复新任务上下文，异常返回到线程模式。

主流实现分支：

- **软件完整保存**：异常入口由软件显式保存全部所需寄存器。
- **硬件自动压栈 + 软件补充保存**：Cortex-M 常见方案，硬件压入部分寄存器，端口代码保存其余寄存器。
- **协作式切换**：任务主动让出 CPU，仅在规定位置保存状态。
- **抢占式切换**：时钟节拍或 ISR 触发调度；响应更快，但切换与同步成本更高。
- **架构特定端口**：不同 ISA、编译器 ABI、FPU 与安全扩展使栈帧和汇编实现不同。

## 4. 核心特性横向对比

|方案|触发点|保存责任|响应性|主要成本与风险|
|---|---|---|---|---|
|协作式切换|任务主动 yield/block|端口保存任务切换所需状态|受任务主动让出时机限制|切换少，但任务若不让出可长期占用 CPU|
|抢占式切换|tick、ISR 唤醒高优先级任务|异常硬件与端口共同保存|可满足有界响应要求|增加切换、临界区和同步复杂度|
|Cortex-M PendSV|中断退出后请求调度|硬件异常帧 + 软件 R4-R11 等|通常在当前 ISR 结束后执行|PendSV 优先级配置错误会导致实时性异常|
|直接在 ISR 中切换|ISR 内执行调度或改栈|依端口而异|看似更快|容易破坏嵌套异常语义和内核临界区|
|FPU 延迟保存|仅在需要时保存浮点扩展状态|硬件/端口按使用状态处理|未使用 FPU 的任务开销低|首次浮点使用路径复杂，栈需求易被低估|

## 5. 底层原理与功能特性深度解析

### 5.1 Cortex-M 异常帧与任务栈

Cortex-M 进入异常时，处理器自动压入基本异常帧：

|栈帧字段|大小|
|---|---|
|R0-R3|16 字节|
|R12|4 字节|
|LR|4 字节|
|PC|4 字节|
|xPSR|4 字节|
|合计|**32 字节**|

若启用 FPU 且发生扩展上下文保存，异常帧可能再增加最多 **18 个 32 位字，即 72 字节**，实际行为取决于架构、FP 状态和端口配置。异常入口还可能涉及栈对齐填充。

以常见 Cortex-M FreeRTOS 端口为例，硬件异常帧之外，端口通常保存 R4-R11；启用 FPU 时还可能保存 S16-S31。FreeRTOS 的 TCB 中保存任务栈指针，切换时该指针指向已保存上下文的栈顶。

### 5.2 PendSV 切换路径

以下为结构示意代码，不应直接替代具体芯片和 FreeRTOS 版本的端口汇编。具体寄存器、FPU 与 TrustZone 处理必须以目标端口为准。

```
void PendSV_Handler(void)
{
    uint32_t *saved_sp;

    /* 当前任务的线程栈使用 PSP。 */
    saved_sp = (uint32_t *)__get_PSP();

    /* 软件保存 ABI 下需要跨调用保留的寄存器。 */
    __asm volatile (
        "stmdb %0!, {r4-r11}"
        : "+r"(saved_sp)
        :
        : "memory"
    );

    /* 将当前任务的栈顶写回 TCB。此处为伪接口。 */
    save_current_task_sp(saved_sp);

    /* 选择最高优先级就绪任务，并取得其栈顶。 */
    saved_sp = select_next_task_sp();

    /* 恢复下一任务的 R4-R11。 */
    __asm volatile (
        "ldmia %0!, {r4-r11}"
        : "+r"(saved_sp)
        :
        : "memory"
    );

    __set_PSP((uint32_t)saved_sp);

    /*
     * 异常返回时，处理器从 PSP 恢复硬件异常帧，
     * 并返回线程模式继续运行新任务。
     */
}
```

生产级端口通常直接使用汇编实现入口，避免编译器函数序言、栈使用和 ABI 对现场造成干扰。上述代码用于理解数据流，不是可移植的处理器端口实现。

### 5.3 为什么需要 PendSV

在 ISR 中发现更高优先级任务就绪后，通常只设置 PendSV pending 位，而不直接切换任务：

```
void DMA_IRQHandler(void)
{
    BaseType_t higher_priority_task_woken = pdFALSE;

    clear_dma_interrupt();
    vTaskNotifyGiveFromISR(dma_task_handle,
                           &higher_priority_task_woken);

    /* 只请求延迟到异常退出后进行调度。 */
    portYIELD_FROM_ISR(higher_priority_task_woken);
}
```

设计意义：

- 高优先级硬件中断保持短小、可预测。
- 调度在 ISR 退出路径统一处理。
- PendSV 设为最低异常优先级时，不会抢占尚未完成的普通 ISR。
- 嵌套中断完成后再进行一次切换，减少中间状态复杂度。

### 5.4 新任务首次运行

新任务没有历史上下文可恢复。内核创建任务时会构造一个“伪造的初始栈帧”，令首次异常返回看起来像从异常中恢复：

- PC 指向任务入口包装函数。
- LR 指向任务退出处理函数。
- xPSR 设置 Thumb 状态位。
- 参数放入 R0 对应的栈帧位置。
- 初始栈指针满足架构对齐要求。

```
static void task_entry_wrapper(void (*entry)(void *), void *arg)
{
    entry(arg);

    /* 任务入口返回通常不允许落入未知地址。 */
    vTaskDelete(NULL);
    for (;;) {
        /* 防御性兜底，实际删除后不应到达这里。 */
    }
}
```

### 5.5 切换与调度不是同一件事

调度器负责选择“谁运行”；上下文切换负责让 CPU 转移到该任务。调度策略可在 C 代码中完成，端口汇编则完成寄存器与栈状态迁移。二者边界不清会造成调度锁、临界区和任务栈损坏等问题。

## 6. 性能量化分析

### 6.1 开销模型

一次任务切换的时间可分解为：

Tswitch=Texception+Tsave+Tschedule+Trestore+TreturnTswitch​=Texception​+Tsave​+Tschedule​+Trestore​+Treturn​

其中：

- `T_exception`：异常进入与退出。
- `T_save/restore`：寄存器压栈、出栈。
- `T_schedule`：就绪队列查找、优先级判断。
- 额外项：缓存维护、内存等待状态、FPU 状态处理、安全域转换等。

任务切换 CPU 占比近似为：

Uswitch=Nswitch×TswitchTwindowUswitch​=Twindow​Nswitch​×Tswitch​​

其中 `N_switch` 是统计窗口内的切换次数。

### 6.2 参考估算，不是跨芯片实测承诺

以下是用于预算的 Cortex-M4F 参考量级，实际值必须在目标固件、编译器、优化级别和内存布局下测量：

|指标|假设值|说明|
|---|---|---|
|CPU|Cortex-M4F，80 MHz|目标平台示例|
|基本异常帧|32 字节|8 个 32 位寄存器|
|端口软件保存 R4-R11|32 字节|未计栈对齐等额外空间|
|额外 FPU 扩展帧|最多 72 字节|视 FPU 状态与端口策略|
|基本切换周期预算|约 100-250 cycles|约 1.25-3.13 μs @ 80 MHz，需实测|
|FPU 扩展切换预算|约 150-400 cycles|约 1.88-5.00 μs @ 80 MHz，需实测|

这些数字是设计初期的预算区间，不是对指定芯片的实测结果。队列长度、临界区、Flash wait states、编译器生成的汇编、FPU 使用方式都会改变结果。

### 6.3 推荐测量方法

使用 DWT `CYCCNT` 测量 PendSV 入口到退出的周期；如需端到端调度延迟，则从 ISR 唤醒任务到任务首条可观察指令之间测量。分别测量：

- 普通任务切换。
- ISR 唤醒高优先级任务后的切换。
- 浮点任务与非浮点任务切换。
- Flash 与 SRAM 执行差异。
- 空闲时切换与高队列负载下切换。

```
uint32_t begin = DWT->CYCCNT;

/* 在端口切换路径插桩，生产构建需可关闭。 */
trace_switch_probe();

uint32_t elapsed = DWT->CYCCNT - begin;
```

注意：插桩本身会改变测量结果。建议同时使用 GPIO 示波器测量外部可见延迟，并报告最小值、平均值、最大值和高分位数，而非只报告平均值。

### 6.4 栈预算

单任务最小栈需求至少包含：

Stask≥Scall depth+Sexception frame+Ssoftware context+SFPU+Salignment+SmarginStask​≥Scall depth​+Sexception frame​+Ssoftware context​+SFPU​+Salignment​+Smargin​

- `S_call depth` 取决于最深调用路径和局部变量。
- `S_exception frame` 对 Cortex-M 基本帧为 32 字节，可能增加扩展帧与对齐空间。
- `S_software context` 由端口决定。
- `S_margin` 应依据最坏路径测量和安全要求设定，而非固定经验值。

## 7. 应用场景选型指南

```
需要多个独立执行流吗？
├─ 否
│  └─ 主循环 + 中断通常更简单
└─ 是
   ├─ 任务响应可由各任务主动让出保证吗？
   │  ├─ 是：评估协作式调度，需证明无任务长期占用 CPU
   │  └─ 否：使用抢占式调度
   ├─ 是否有严格 ISR 延迟要求？
   │  ├─ 是：ISR 只做最小处理，PendSV 延迟调度
   │  └─ 否：仍优先采用内核规定的 ISR 通知 API
   └─ 是否使用 FPU/安全扩展？
      ├─ 是：使用对应架构端口并重新测量栈和切换时间
      └─ 否：以基本上下文建立基线
```

|场景需求|建议方案|理由|
|---|---|---|
|电机控制控制环与通信并行|抢占式任务 + 高优先级短控制任务|将响应上界交由优先级与 WCET 预算控制|
|DMA 完成后唤醒处理任务|ISR 通知 + PendSV 切换|ISR 短小，任务在异常退出后运行|
|极小资源、事件驱动系统|主循环或协作式调度|可减少内核状态和切换成本|
|使用大量浮点运算的信号处理|经验证的 FPU 端口，单独测量扩展上下文|FPU 上下文会增加切换与栈开销|
|安全关键系统|经过认证/验证的端口，静态栈分析与运行时监控并用|仅依赖栈高水位不能覆盖全部最坏情况|

## 8. 工程最佳实践

### 设计原则

- 将 ISR、调度器和端口切换的职责分开。
- ISR 中只做必要的确认、数据快照和任务通知。
- 保证 PendSV 使用内核要求的最低优先级；同时确认优先级分组配置符合端口要求。
- 任务栈按最坏调用路径与异常嵌套预算，运行时高水位只作为补充证据。
- 禁止应用代码自行修改 PSP、CONTROL、异常返回码或内核保存的栈指针。
- 使用内核提供的 ISR-safe API，不在 ISR 中调用阻塞 API。
- 发生任务切换时，临界区必须确保调度器对共享状态的假设仍成立。

### 选型决策矩阵

|约束|推荐策略|
|---|---|
|需要有界响应|抢占式调度，明确优先级和 WCET|
|切换开销极敏感|减少无意义唤醒和任务数量，评估协作式模型|
|使用 FPU|按目标端口验证懒惰保存行为与栈需求|
|高安全性|选择成熟端口，启用栈检查、断言和异常追踪|
|多核系统|额外考虑跨核同步、缓存一致性与远程唤醒成本|

### 编码规范

- 每个任务定义明确优先级、栈预算、阻塞策略和最大运行时间。
- ISR 通知只表达事件，不将大型数据结构拷贝到任务栈。
- 禁止在任务入口返回后继续执行未定义代码。
- 构建中启用编译器警告、栈使用分析、静态分析与调度相关断言。
- 版本升级内核、编译器或启动代码后，重新审查汇编端口和性能基线。

## 9. 常见错误与避坑指南

### 错误一：在 ISR 中使用任务上下文 API

```
void UART_IRQHandler(void)
{
    xSemaphoreGive(rx_sem); /* 错误：普通任务 API */
}
```

**根因：** 普通 API 可能访问调度器状态或执行阻塞语义，不满足 ISR 调用约束。

**正确实现：**

```
void UART_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;

    clear_uart_irq();
    xSemaphoreGiveFromISR(rx_sem, &woken);
    portYIELD_FROM_ISR(woken);
}
```

**风险影响：** 内核断言失败、队列状态损坏或难以复现的调度故障。

### 错误二：把任务栈只按局部变量估算

```
static StackType_t stack[128]; /* 未验证是否足够 */
```

**根因：** 忽略调用深度、异常帧、软件保存寄存器、FPU 扩展状态和嵌套中断。

**正确做法：** 在最深调用、错误路径和 FPU 路径下测量并静态分析，再保留经风险评估的余量；启用栈溢出检测与高水位监控。

**风险影响：** 覆盖邻接任务或内核对象，故障可能表现为随机 PC、错误返回或队列损坏。

### 错误三：错误配置 PendSV 优先级

```
NVIC_SetPriority(PendSV_IRQn, 0); /* 通常不符合 Cortex-M RTOS 端口要求 */
```

**根因：** 抢占优先级数字越小通常代表优先级越高；高优先级 PendSV 可能插入普通 ISR 执行期间。

**正确做法：** 按目标端口配置 PendSV 为允许的最低优先级，并使用 FreeRTOS/CMSIS 配置宏统一设置。

**风险影响：** 中断嵌套与调度器假设不一致，出现延迟突增或内核状态损坏。

### 错误四：关闭中断后执行耗时逻辑

```
taskENTER_CRITICAL();
process_large_frame(); /* 错误：耗时不受控 */
taskEXIT_CRITICAL();
```

**根因：** 临界区延长了高优先级中断及切换请求的最坏响应时间。

**正确做法：** 只在临界区内保护共享状态的短暂更新；耗时处理改为任务执行，并通过队列、通知或双缓冲传递数据。

**风险影响：** 实时期限违约、通信 FIFO 溢出、看门狗超时。

## 10. 多机制组合使用方案

### 组合架构

```
外设 ISR
  ├─ 确认中断源
  ├─ 采样必要状态 / 更新 DMA 缓冲索引
  ├─ 通知对应任务
  └─ 请求 PendSV（若唤醒了更高优先级任务）

PendSV
  ├─ 保存当前任务软件上下文
  ├─ 调度器选择下一任务
  ├─ 恢复下一任务软件上下文
  └─ 异常返回：硬件恢复异常帧

高优先级工作任务
  ├─ 取走事件与缓冲区
  ├─ 执行有界处理
  └─ 阻塞等待下一事件
```

### 数据流示例：DMA 完成通知

```
typedef struct {
    uint8_t *buffer;
    size_t length;
    uint32_t sequence;
} dma_event_t;

static TaskHandle_t worker_task;

void DMA_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;

    size_t length = dma_completed_length();
    uint32_t sequence = dma_completed_sequence();

    publish_completed_buffer(length, sequence);
    vTaskNotifyGiveFromISR(worker_task, &woken);
    portYIELD_FROM_ISR(woken);
}

static void worker(void *arg)
{
    (void)arg;

    for (;;) {
        uint32_t pending = ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
        if (pending == 0U) {
            continue;
        }

        dma_event_t event;
        if (!get_next_dma_event(&event)) {
            record_dma_event_overrun();
            continue;
        }

        process_buffer(event.buffer, event.length);
        release_buffer(event.buffer);
    }
}
```

工程要点：

- `publish_completed_buffer()` 必须以适当临界区或单生产者/单消费者协议发布一致状态。
- 若缓冲区由 DMA 写入，需处理目标芯片的数据缓存一致性；Cortex-M7 等带 D-cache 的系统可能需要 cache clean/invalidate。
- 通知计数不能替代队列容量设计。若事件携带多个独立缓冲区描述符，应使用队列或环形缓冲区。
- ISR 中不得进行无界拷贝或等待资源。

## 11. 工业级实际案例分析

### 案例一：电机控制与通信任务并行

**需求：** 控制环周期 1 ms，通信解析可突发运行，控制任务不能因大帧解析而延迟。

**架构：**

- 高优先级控制任务以定时器通知唤醒。
- 通信 ISR 只入队 DMA 缓冲描述符。
- 中低优先级通信任务处理协议帧。
- 通过运行时间监控验证控制任务 WCET 与最坏响应时间。

**核心逻辑：**

```
void control_timer_isr(void)
{
    BaseType_t woken = pdFALSE;

    vTaskNotifyGiveFromISR(control_task_handle, &woken);
    portYIELD_FROM_ISR(woken);
}

void control_task(void *arg)
{
    (void)arg;

    for (;;) {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
        control_step(); /* 必须具备 WCET 预算 */
    }
}
```

**设计要点：** 任务优先级本身不能证明实时性。需结合中断干扰、临界区、切换延迟和控制任务 WCET 计算响应上界。

### 案例二：工业以太网数据采集

**需求：** 多路 DMA 数据持续到达，网络发送和数据处理并行，避免 ISR 中复制大块数据。

**架构：**

- ISR 发布 DMA 缓冲描述符并通知处理任务。
- 处理任务验证数据并生成网络消息。
- 网络发送任务采用独立优先级和流量整形。
- 环形队列满时有明确的丢弃、背压或降采样策略。

**设计要点：** 任务切换开销通常远低于大块数据拷贝和缓存维护成本；应优化数据所有权与零拷贝路径，而不是盲目减少任务数。

### 案例三：低功耗传感器节点

**需求：** 传感器采样间隔长，事件发生时快速处理，平时进入低功耗状态。

**架构：**

- 任务阻塞等待事件，空闲任务进入睡眠。
- 外设中断唤醒内核并通知处理任务。
- 任务处理完成后重新阻塞。
- 使用 tickless idle 时，核对时钟恢复、定时器误差和唤醒路径。

**设计要点：** 上下文切换不是功耗的唯一来源；唤醒频率、外设时钟恢复、睡眠深度和 tickless 配置往往更关键。

## 12. 高频问题深度答疑

### Q1：上下文切换会保存所有 CPU 寄存器吗？

不会。只保存恢复正确执行所必需的状态。Cortex-M 异常机制自动压入一部分寄存器，端口软件保存剩余部分。具体集合取决于 ABI、编译器、FPU 和安全扩展。检查端口源码与反汇编才是可靠答案。

### Q2：为什么 PendSV 通常配置为最低优先级？

这样调度不会抢占仍在执行的高优先级 ISR。内核可以在外设中断处理完成后统一切换任务，保持中断嵌套与内核状态的一致性。代价是调度要等待当前 ISR 链结束，因此 ISR 的最大执行时间仍影响唤醒延迟。

### Q3：从 ISR 唤醒任务后，任务是否立即执行？

不一定。若新任务优先级更高，内核通常请求 PendSV；实际切换要等到当前异常处理完成且允许调度时才发生。若当前屏蔽了相关中断或调度器暂停，延迟还会增加。

### Q4：任务栈中为何还会有异常帧？

线程模式使用 PSP 时，异常入口可以将线程寄存器压入当前线程栈，因此异常帧占用任务栈。若异常发生在 Handler 模式，栈使用与嵌套情况不同。必须按实际异常路径和端口配置核算，而不能只按任务函数调用深度估算。

### Q5：FPU 懒惰保存是否意味着无需额外栈空间？

不是。懒惰保存可能延后浮点寄存器保存，但一旦触发，扩展上下文仍需空间，首次浮点使用路径也可能产生额外时延。栈预算和 WCET 都应覆盖真正发生浮点状态保存的路径。

### Q6：减少任务数量是否一定能降低切换成本？

减少任务可能减少调度事件，但也可能增加单任务状态复杂度、阻塞范围和耦合。更有效的指标是无效唤醒率、切换频率、任务运行时间分布、队列积压和响应时间。对大块数据而言，复制和缓存维护可能比上下文切换更昂贵。

## 13. 课程核心总结

- 上下文切换是“保存当前执行状态 + 调度选择 + 恢复下一执行状态”。
- 在 Cortex-M 上，常见实现由硬件异常帧与端口软件保存共同完成。
- PendSV 用于把调度延迟到适合的异常边界，ISR 应使用 ISR-safe API 请求切换。
- 性能不是单一固定值：CPU、编译器、内存、FPU、就绪队列和临界区都会改变结果。
- **栈预算、优先级配置和异常边界正确性比微优化几十个周期更重要。**
- 通用性能优先级：先减少无意义唤醒和数据拷贝，再优化调度路径；测量确认后才优化汇编。

## 16. 实践与进阶路径

### 梯度实战任务

1. 在 Cortex-M 目标板上创建两个不同优先级任务，记录任务切换顺序与 PSP 变化。
2. 为 PendSV 增加可配置 DWT 插桩，分别测量普通切换和 ISR 唤醒切换。
3. 添加浮点计算任务，对比使用 FPU 前后的栈高水位和切换周期分布。
4. 加入 DMA 通知与双缓冲，验证缓冲区不会在消费者释放前被 DMA 覆盖。
5. 对最坏中断嵌套、最深调用路径和错误路径做栈压力测试。

### 性能测试方法

- 固定 CPU 频率、编译器版本、优化选项和内存布局。
- 清楚记录是否启用 FPU、缓存、TrustZone 与 tickless idle。
- 测量最小、平均、最大值及高分位数，并重复多轮。
- 使用 GPIO/逻辑分析仪验证端到端时序。
- 将性能测试结果纳入构建或发布回归；端口升级后重新测量。

### 进阶方向

- FreeRTOS 对应 Cortex-M 端口源码与异常返回机制。
- ARM Cortex-M 异常优先级、尾链、晚到异常与栈对齐。
- FPU 上下文保存、TrustZone 线程/安全状态切换。
- 固定优先级响应时间分析、WCET 与中断干扰建模。
- Tracealyzer、SystemView、ETM 等运行时调度追踪工具。
