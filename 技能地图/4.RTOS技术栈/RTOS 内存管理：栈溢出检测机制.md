
## 1. 学习目标

### 理解

- 理解任务栈溢出与栈越界的区别，以及溢出如何破坏相邻对象、RTOS 控制结构或返回地址。
- 理解 FreeRTOS 栈溢出检测配置、检测时机和机制边界。
- 理解软件检查、栈哨兵、高水位、MPU guard 和硬件故障检测之间的差异。

### 掌握

- 掌握 FreeRTOS `configCHECK_FOR_STACK_OVERFLOW` 配置与 `vApplicationStackOverflowHook()` 实现。
- 掌握使用任务高水位和栈填充模式进行压力测试。
- 掌握在溢出故障路径中保存诊断信息并进入安全状态。

### 精通

- 能够根据目标端口源码分析栈增长方向、任务栈边界、上下文保存和检测时机。
- 能够识别“溢出发生但未触发钩子”“钩子触发时栈已损坏”等检测盲区。
- 能够设计软件检测、MPU 保护、静态分析和故障注入的组合验证方案。

### 能够设计

- 能为任务栈、主栈和中断栈分别设计溢出保护与诊断机制。
- 能设计不会依赖已损坏任务栈的故障记录和安全处置流程。
- 能将栈边界检测纳入构建配置、测试计划和产品现场监控。

## 2. 前置要求

### 知识要求

- 熟悉 FreeRTOS 任务创建、任务栈和上下文切换。
- 熟悉目标 MCU 的栈指针、异常入口、PSP/MSP 和 MPU 基础。
- 理解 C 函数调用、局部变量、递归、数组越界和调用链。
- 了解链接脚本的 RAM 布局及任务栈存储位置。

### 技能要求

- 能阅读项目使用的 FreeRTOS `tasks.c` 和目标 port 源码。
- 能通过调试器检查任务 SP、栈起止地址和故障现场。
- 能运行任务高水位查询并执行压力测试。
- 能配置栈溢出钩子、硬件 watchpoint 或 MPU 保护区。

## 3. 技术概述

### 栈溢出是什么

栈溢出是执行栈使用超过为其分配的边界。常见原因包括：

- 调用链过深或递归没有上限。
- 局部数组、变长数组或局部结构体过大。
- 格式化输出、文件系统或协议解析等库函数消耗大量栈。
- 中断嵌套、异常上下文或 FPU 上下文保存未纳入预算。
- 编译器、优化级别、LTO 或库版本改变了栈帧布局。
- 缓冲区越界写入，破坏栈上的返回地址或局部变量。

栈溢出可能表现为 HardFault、异常复位、任务状态损坏、随机数据错误、其他任务异常，或在一段时间后才出现故障。

### 检测机制分类

1. **边界/指针检查**：检查任务栈指针是否接近或越过栈边界。
2. **哨兵检查**：检查栈边界预置标记是否被覆盖。
3. **高水位检查**：通过未使用栈区的填充值估算历史最低余量。
4. **MPU guard region**：让栈边界访问触发内存保护异常。
5. **静态分析与编译器报告**：在构建期估算函数栈帧和调用链上界。
6. **硬件故障诊断**：从 fault 状态寄存器和保存的 SP 还原现场。

这些机制互补，不能互相替代。

## 4. 核心特性横向对比

|机制|典型检测时机|优点|主要盲区|运行成本|
|---|---|---|---|---|
|FreeRTOS 检查等级 1|任务切换检查时|检查任务栈指针边界，开销较低|可能在损坏发生后才检查；端口实现相关|低|
|FreeRTOS 检查等级 2|任务切换检查时|额外检查栈边界填充值|只检查特定边界区域，不能发现所有越界模式|低到中|
|高水位 API|查询时|观察测试期间任务栈最低余量|未执行路径不可见；通常不覆盖主栈|查询时扫描开销|
|栈哨兵|检查哨兵时|简单，可用于自定义栈和主栈|可能延迟发现，取决于哨兵位置和检查频率|低|
|MPU guard|越界访问时|可在访问边界时触发保护异常|依赖端口、粒度、对齐和 MPU 配置|区域和配置成本|
|编译器栈分析|构建期|可发现大栈帧和部分深调用链|间接调用、汇编、运行时路径可能不完整|构建分析成本|
|Fault 捕获|异常发生时|可定位异常寄存器和栈指针|现场可能已损坏，处理代码需极简|故障路径成本|

## 5. 底层原理与功能特性深度解析

### 5.1 FreeRTOS 栈溢出检测配置

常见配置：

```
#define configCHECK_FOR_STACK_OVERFLOW  2
```

在不少 FreeRTOS 版本和端口中，等级 1 与等级 2 大致区分为：

- 等级 1：检查任务栈指针是否越过允许边界。
- 等级 2：除栈指针检查外，还检查栈边界附近的填充模式。

**具体检查内容必须查看当前版本的 `tasks.c`、`StackMacros.h` 和 port 实现。** 不同版本或端口可能存在差异，不应仅依据配置值推断所有行为。

开启检测后通常要实现钩子：

```
void vApplicationStackOverflowHook(
    TaskHandle_t task,
    char *task_name)
{
    (void)task;
    (void)task_name;

    system_stack_fault_record(task, task_name);
    system_enter_safe_state();
}
```

钩子名和函数签名应以当前 FreeRTOS 头文件和版本为准。

### 5.2 检测时机：为什么不是“越界瞬间必定捕获”

不少 FreeRTOS 实现会在任务切换相关路径执行检查。因此可能出现：

```
任务写越界
  -> 已破坏相邻内存
  -> 继续执行一段时间
  -> 发生任务切换
  -> 检查发现溢出
```

这意味着：

- 钩子触发时，受害数据可能已经损坏。
- 如果系统没有后续任务切换，检测可能延迟。
- 越界写未覆盖检查区域时，哨兵检查可能不触发。
- 栈指针检查无法识别所有基于错误指针的任意写入。

所以 FreeRTOS 检查主要用于检测和诊断，不能等同于内存隔离。

### 5.3 栈填充与高水位

创建任务时，RTOS 通常将未使用栈区域填充为已知模式。任务运行后，实际使用的栈覆盖这部分填充值。

```
UBaseType_t remaining_words =
    uxTaskGetStackHighWaterMark(task_handle);

size_t remaining_bytes =
    (size_t)remaining_words * sizeof(StackType_t);
```

高水位可以回答：

> 在已执行的路径中，栈最多使用到了什么程度？

它不能回答：

> 所有可能路径和未来输入下，栈是否一定不会溢出？

高水位数据必须结合覆盖率、静态分析和压力测试解释。

### 5.4 Cortex-M 的 PSP、MSP 与任务栈

典型 Cortex-M FreeRTOS 端口常见模式是：

- 任务执行使用 PSP。
- 异常处理使用 MSP。
- 任务切换由 PendSV 等异常完成上下文保存与恢复。

但实际情况由端口汇编、启动代码和配置决定。任务栈溢出检测一般针对任务自己的栈，不一定监测 MSP。

应分别核对：

- 任务栈起止地址和增长方向。
- MSP 初始值及链接脚本保留大小。
- ISR 嵌套规则和最大嵌套深度。
- FPU 上下文保存及 lazy stacking。
- HardFault/NMI 使用的栈和现场保存路径。

### 5.5 MPU guard region

MPU guard 的思路是在栈边界附近设置不可访问区域：

```
可用任务栈 | 不可访问 guard 区 | 其他内存
```

任务访问 guard 区时触发 MemManage 或相应保护异常。它比软件哨兵更接近“访问时捕获”，但需要注意：

- MPU region 尺寸和边界有对齐限制。
- guard 区会占用地址空间或降低可用 RAM。
- 不同 FreeRTOS MPU port 的任务栈布局不同。
- DMA 等总线主设备是否受该 MPU 保护，取决于芯片架构。
- 越界跳过 guard 区的写入或其他内存损坏仍需考虑。

MPU guard 适合高完整性任务，但配置和验证必须针对具体芯片与端口。

### 5.6 栈溢出钩子的故障处理

溢出钩子中不要做依赖当前任务栈或堆的复杂操作：

```
void vApplicationStackOverflowHook(
    TaskHandle_t task,
    char *task_name)
{
    (void)task;
    (void)task_name;

    /* 只写入预先分配的固定故障记录区。 */
    fault_record_stack_overflow_minimal(task);

    disable_nonessential_interrupts();
    system_enter_safe_state();
}
```

避免：

- `printf()` 等格式化输出。
- 动态内存分配。
- 阻塞队列或信号量。
- 复杂文件系统、网络或 Flash 驱动调用。
- 继续运行已知栈损坏的任务。

如果故障记录需要任务名，需确认指针仍有效；更稳妥的做法是记录任务句柄、任务编号或固定长度复制结果。

### 5.7 任务栈哨兵示例

自定义栈或主栈可用哨兵检查。以下是概念示例，边界和增长方向要按目标架构配置：

```
#define STACK_GUARD_WORD  0xA55AA55AU
#define STACK_GUARD_WORDS 4U

static uint32_t s_guard[STACK_GUARD_WORDS];

static void stack_guard_init(void)
{
    for (size_t i = 0U; i < STACK_GUARD_WORDS; ++i) {
        s_guard[i] = STACK_GUARD_WORD;
    }
}

static bool stack_guard_intact(void)
{
    for (size_t i = 0U; i < STACK_GUARD_WORDS; ++i) {
        if (s_guard[i] != STACK_GUARD_WORD) {
            return false;
        }
    }

    return true;
}
```

哨兵必须实际放在需要保护的边界附近，且不能被其他代码覆盖。实际任务栈由 RTOS 管理时，不要未经端口分析就把独立数组当成任务栈保护区。

### 5.8 编译期与静态分析

GCC 可使用 `-fstack-usage` 生成函数栈使用报告。构建期建议：

- 将报告纳入版本控制或 CI 工件。
- 对大栈帧函数设审查阈值。
- 用调用图分析关键任务的最大路径。
- 检查递归、函数指针、回调、汇编和库函数。
- 使用发布优化等级和相同 LTO 设置分析。

静态分析结果是边界推导的一部分，仍需与目标板测量结合。

## 6. 性能量化分析

### 6.1 栈大小和余量计算

栈深字节数：

```
stack_bytes = stack_depth_words × sizeof(StackType_t)
```

剩余字节数：

```
remaining_bytes =
    high_water_words × sizeof(StackType_t)
```

已观测最大使用量：

```
observed_used_bytes =
    configured_stack_bytes - remaining_bytes
```

这只是运行测试观察值。配置栈还要覆盖未执行路径、异常上下文、库函数、编译变化和项目安全裕量。

### 6.2 溢出检测的时间开销

FreeRTOS 边界检查通常发生在调度/切换相关路径，具体成本依端口和配置而异。高水位 API 可能扫描栈填充值，成本与扫描字数相关：

```
T_scan ≈ scanned_words × (load + compare + branch)
```

MPU 检查通常由硬件在访问时完成，正常访问的开销与芯片 MPU 实现和访问路径有关；故障路径成本则包括异常处理。

没有目标 MCU、编译器、配置和栈大小时，不宜给出通用微秒数字。应在目标板使用 DWT 或 GPIO 测量。

### 6.3 性能测量计划

|指标|测量方式|记录项|
|---|---|---|
|高水位查询耗时|DWT 周期计数器|栈容量、扫描字数、优化等级|
|切换路径检查耗时|GPIO 或 Trace|检查等级、任务数、端口|
|溢出检测延迟|故障注入到钩子之间计时|检查触发点和调度行为|
|MSP 峰值|主栈水印或调试器采样|ISR 嵌套和异常配置|
|栈溢出后的诊断完整度|断言/故障注入|记录字段、复位原因|

### 6.4 瓶颈与风险

- **任务切换开销**：启用更严格检查可能增加切换路径操作。
- **高水位扫描**：频繁扫描大量任务栈会消耗 CPU。
- **检测延迟**：软件检查常在栈已被使用后才触发。
- **故障现场不可信**：溢出后栈帧、任务名或局部状态可能已损坏。
- **盲区**：未覆盖路径、主栈溢出、任意指针写、跳过哨兵区域。

## 7. 应用场景选型指南

### 纯文本决策流程图

```
系统是否需要检测栈越界？
├─ 是
│  ├─ 是否使用支持 MPU 的端口并要求访问时保护？
│  │  ├─ 是 -> 配置 MPU guard，并验证故障处理路径
│  │  └─ 否 -> 启用 RTOS 边界检查和哨兵检测
│  ├─ 是否需要发现测试期间余量不足？
│  │  └─ 是 -> 增加高水位监控和阈值告警
│  └─ 是否需要证明最坏路径容量？
│     └─ 是 -> 编译器栈报告 + 调用链分析 + 压力测试
└─ 还要检查哪些栈？
   ├─ 任务栈 -> RTOS 检查 + 高水位
   ├─ MSP/ISR 栈 -> 主栈水印/MPU/嵌套压力测试
   └─ HardFault/NMI -> 预留独立、最小化故障处理路径
```

### 典型场景

|场景|推荐组合|理由|
|---|---|---|
|普通 FreeRTOS 产品|溢出等级 2 + 高水位 + 压力测试|兼顾发现和预算验证|
|硬实时控制器|编译期分析 + 固定栈 + 目标板测试|降低运行期不确定性|
|安全关键任务|MPU guard + 静态分析 + 故障记录|提升隔离和诊断能力|
|多级中断系统|任务栈检测 + MSP 独立水印|任务 API 不覆盖所有异常栈|
|网络解析任务|边界检查 + 最大报文/错误路径测试|输入导致的调用深度和局部缓冲变化大|

## 8. 工程最佳实践

### 设计原则

- 在开发和系统测试构建中启用适当的 RTOS 溢出检查。
- 对关键产品构建依据安全策略决定是否保留检查；不得未经测量直接关闭。
- 任务栈和 MSP/异常栈分别预算、分别监控。
- 对大局部数组、递归、VLA 和深层库调用设置审查规则。
- 使用发布构建、实际 FPU 和实际中断配置验证。
- 高水位阈值通过风险分析制定，不复制其他项目的固定数值。
- 栈溢出处理必须立即转入定义好的安全策略。
- 故障记录使用静态、固定容量空间，并避免在钩子中分配内存。

### 检测方案决策矩阵

|需求|推荐机制|
|---|---|
|尽早发现任务栈边界破坏|RTOS 溢出检查|
|了解已测路径栈余量|高水位 API|
|保护关键任务边界|MPU guard|
|监测 MSP/中断栈|主栈水印或专用 guard|
|估算最坏调用链|编译器报告和静态分析|
|现场定位故障|极简故障记录和 fault 状态采集|

### 工业级编码规范

- 配置宏和钩子签名以项目实际 FreeRTOS 版本为准。
- 栈大小定义明确标注 `WORDS` 或 `BYTES`。
- 监控项保存有效任务句柄，删除任务后及时注销。
- 故障钩子不打印复杂日志，不阻塞，不动态分配。
- 记录任务 ID、SP、栈边界、故障寄存器和软件版本时，避免依赖易损坏指针。
- CI 检查栈使用报告变化、任务栈配置变化和溢出检查配置变化。
- 对溢出钩子进行故障注入，确认最终确实进入安全状态或受控复位。

## 9. 常见错误与避坑指南

### 错误一：认为等级 2 可以保证所有溢出都被捕获

```
#define configCHECK_FOR_STACK_OVERFLOW  2
```

**根因：** 等级 2 是特定实现中的软件检查，不是完整内存保护。检查区域、检测时机和端口实现均有限制。

**正确实现：** 将它与 MPU guard、静态栈分析、高水位和压力测试组合；阅读当前版本检查代码，明确覆盖范围。

**风险影响：** 越界发生后才发现，或越界没有触及被检查位置而漏检。

### 错误二：在溢出钩子中调用 `printf`

```
void vApplicationStackOverflowHook(
    TaskHandle_t task,
    char *name)
{
    printf("overflow: %s\n", name);
}
```

**根因：** 格式化输出可能进一步消耗已损坏的栈、申请堆、阻塞或进入不可恢复的锁状态。

**正确实现：** 只写入静态故障记录，关闭非必要中断，然后进入预定义安全状态或复位。

**风险影响：** 二次故障覆盖原始现场，或系统卡死在错误处理路径。

### 错误三：只监控任务栈，不检查 MSP

```
/* 所有任务高水位正常，因此认定系统栈也正常。 */
```

**根因：** 部分端口的中断和异常使用 MSP，任务高水位 API 不覆盖该栈。

**正确实现：** 查端口和启动代码，单独给 MSP 建立预算、哨兵或保护区，并进行中断嵌套测试。

**风险影响：** ISR 嵌套耗尽主栈，任务栈统计却仍正常。

### 错误四：高水位剩余量接近零仍继续运行

```
if (remaining_bytes < 32U) {
    log_warning();
}
/* 任务仍继续执行复杂逻辑 */
```

**根因：** 告警后继续进入更深调用路径，可能立刻耗尽剩余栈；告警日志本身也会消耗栈。

**正确实现：** 阈值由项目分析确定；低于阈值时执行有限、可证明安全的降级或重启策略，不调用重型日志路径。

**风险影响：** 系统在告警后继续破坏内存，故障更难诊断。

### 错误五：任务删除后继续查询旧句柄

```
vTaskDelete(task_handle);
uxTaskGetStackHighWaterMark(task_handle);
```

**根因：** 任务删除后句柄不再代表有效任务，栈内存可能已释放或复用。

**正确实现：** 删除前停止采样，删除后注销监控项并清空句柄。

**风险影响：** 读取已释放内存或错误任务数据，导致监控误报甚至异常。

## 10. 多机制组合使用方案

### 10.1 组合架构

```
构建期
  ├─ 编译器栈使用报告
  ├─ 静态调用链/递归审查
  └─ 栈预算门禁

运行期
  ├─ FreeRTOS 溢出检查
  ├─ 低频高水位采样
  ├─ MSP/异常栈独立哨兵
  └─ MPU guard（支持时）

故障期
  ├─ 极简钩子/异常处理
  ├─ 写静态故障记录
  ├─ 进入安全状态或受控复位
  └─ 启动后读取故障记录
```

### 10.2 高水位监控框架

```
#include "FreeRTOS.h"
#include "task.h"

typedef struct {
    TaskHandle_t handle;
    const char *name;
    size_t warning_threshold_bytes;
} StackMonitorEntry_t;

static StackMonitorEntry_t s_stack_entries[12U];
static size_t s_stack_entry_count;

static size_t stack_remaining_bytes(TaskHandle_t task)
{
    UBaseType_t words;

    if (task == NULL) {
        return 0U;
    }

    words = uxTaskGetStackHighWaterMark(task);

    return (size_t)words * sizeof(StackType_t);
}

void stack_monitor_sample(void)
{
    for (size_t i = 0U; i < s_stack_entry_count; ++i) {
        const StackMonitorEntry_t *entry = &s_stack_entries[i];
        size_t remaining = stack_remaining_bytes(entry->handle);

        stack_monitor_record(
            entry->name,
            remaining);

        if (remaining < entry->warning_threshold_bytes) {
            stack_monitor_warning(
                entry->name,
                remaining);
        }
    }
}
```

注意事项：

- `uxTaskGetStackHighWaterMark()` 返回单位和类型以项目版本为准。
- 高水位扫描可能访问较多栈内存，采样应低频进行。
- 任务删除、重建和句柄复用时，监控表必须同步更新。
- 阈值告警函数应避免在小栈任务中调用高开销日志。

## 11. 工业级实际案例分析

### 案例一：电机控制任务栈保护

**需求：** 固定周期控制，栈故障必须进入确定的安全状态。

**设计：**

- 静态创建控制任务，限制递归和大局部对象。
- 构建期生成函数栈使用报告。
- 启用目标 FreeRTOS 支持的栈溢出检测。
- 测试中覆盖最高负载、参数切换和错误路径。
- 溢出钩子只记录任务 ID 和故障码，然后关闭功率输出并复位。

**设计要点：**

- 故障钩子不调用控制任务的栈。
- MSP 单独配置，不以任务高水位替代。
- 记录数据写入固定 SRAM 区，启动后由诊断任务读取。

### 案例二：网络协议解析任务

**需求：** 处理最大报文和恶意输入，避免解析调用链耗尽栈。

**设计：**

- 解析器使用固定工作区，不在栈中放最大报文数组。
- 对嵌套协议层数设硬上限。
- 测试最大合法长度、非法长度、截断包和嵌套扩展字段。
- 记录高水位和栈溢出次数，设置低水位告警。
- 解析任务失败后丢弃当前报文，不让不可信输入触发无限递归。

**设计要点：**

- 输入长度先做边界和溢出检查。
- 日志路径也纳入最大调用链评估。
- 不在栈溢出钩子中格式化报文内容。

### 案例三：多中断采集设备

**需求：** 多个中断可嵌套，异常处理需要稳定运行。

**设计：**

- 通过芯片手册、启动文件和 RTOS port 确认异常使用 MSP 的情况。
- 按最大允许嵌套深度估算主栈峰值。
- 在主栈边界设置水印，并在启动后低频检查。
- ISR 只做最少工作，不执行协议解析和动态分配。
- 故障测试中人为增加嵌套压力并检查 MSP 余量。

**设计要点：**

- FreeRTOS 任务栈检查不一定覆盖 MSP。
- HardFault 处理代码需要独立、精简，避免调用常规任务服务。
- 调整中断优先级时重新评估可嵌套组合。

## 12. 高频问题深度答疑

### 1. `configCHECK_FOR_STACK_OVERFLOW = 2` 是否能在越界写发生时立即触发？

不一定。很多实现是在任务切换相关检查点发现边界异常或哨兵被覆盖。越界写可能早已破坏相邻对象。若要求在访问边界时捕获，应评估 MPU guard 或芯片提供的硬件保护机制。

### 2. 高水位为零代表什么？

代表被检查的填充区域已全部被覆盖，或可用余量已非常低；具体含义受端口实现影响。它不是“栈一定刚好溢出”的精确测量。出现零或接近零应视为严重风险，立即复核栈大小和测试路径。

### 3. 栈溢出钩子能安全打印任务名吗？

不应默认安全。任务名指针、当前任务栈和 libc 状态都可能受损。产品级处理宜记录稳定的任务 ID 或预先登记的固定名称索引，避免复杂字符串处理和格式化输出。

### 4. 启用栈溢出检查后，能否减少栈容量？

不能。检测机制不创造栈空间，也不证明所有路径都已测试。栈大小仍应由静态分析、目标板压力测试和安全余量共同确定。

### 5. MPU guard 比软件检查更好吗？

在支持且正确配置时，MPU 可在访问保护区时触发异常，检测更接近故障发生点。但 MPU 有区域粒度、对齐和端口实现限制，也不能覆盖所有任意内存破坏。它是增强手段，不替代栈预算与测试。

### 6. 为什么没有发生任务切换时，栈溢出没有被发现？

如果目标端口的检查运行在任务切换路径，当前任务持续运行时就可能没有执行该检查。定期主动检查不一定安全或被 RTOS 支持，因此应结合 MPU、栈哨兵、静态分析和合理栈余量降低该风险。

## 13. 课程核心总结

- FreeRTOS 栈溢出检查是运行时检测，不是内存隔离或绝对保证。
- 检测等级的具体行为必须查目标版本源码和 port。
- 高水位仅反映已执行路径，不能证明最坏路径不会溢出。
- 任务栈和 MSP/异常栈可能是不同区域，必须分开监控。
- MPU guard 能更早发现边界访问，但依赖芯片、端口和对齐配置。
- 栈溢出钩子必须短小、无阻塞、无动态分配，不能依赖可能已经损坏的栈。
- 工业方案应组合：**静态栈分析、运行时检查、高水位监控、MPU/哨兵和故障注入**。

### 场景选型表

|需求|推荐机制|额外工作|
|---|---|---|
|发现任务栈边界异常|FreeRTOS 检查|验证当前 port 的实际实现|
|获取任务运行余量|高水位 API|覆盖最坏路径并控制扫描频率|

|现场诊断|固定故障记录|故障钩子避免复杂依赖|

### 机制对比表

|机制|发现时机|覆盖对象|核心限制|
|---|---|---|---|
|RTOS 溢出检查|调度/切换检查点等|任务栈|可能不是越界瞬间|

|哨兵|检查时|自定义边界|可能延迟发现|

|静态分析|构建期|可分析代码路径|动态路径和汇编盲区|

## 16. 实践与进阶路径

### 梯度实战任务

1. 在工程中启用适用的 `configCHECK_FOR_STACK_OVERFLOW`，实现极简钩子。
2. 为所有任务采集高水位，并以字节输出剩余量。
3. 构造局部数组或深调用链的测试任务，验证检测机制及其触发时机。
4. 检查 FreeRTOS port、启动文件和链接脚本，确认任务栈与 MSP 的关系。
5. 对主栈添加水印监控，并通过中断嵌套测试验证。
6. 若平台支持 MPU，配置一个任务栈 guard region 并注入越界访问。
7. 将编译器栈报告、栈配置和溢出测试结果纳入 CI。

### 性能测试方法

- 用 DWT 或 GPIO 测量高水位查询与任务切换检查的成本。
- 在不同任务数、栈容量和编译优化级别下重复测试。
- 通过故障注入测量从越界到检测、到安全动作的延迟。
- 记录任务栈与 MSP 的数据，不把它们合并成一个“栈余量”指标。
- 在发布构建、实际 FPU 配置和目标中断优先级下复测。
- 检查故障记录路径在栈已损坏时仍能执行。

### 进阶学习方向

- FreeRTOS `tasks.c`、`StackMacros.h` 和目标 port 的溢出检测路径。
- Cortex-M MemManage、BusFault、HardFault 与栈帧布局。
- MPU region 对齐、子区域和 FreeRTOS MPU port。
- MSP/PSP、异常嵌套及 FPU lazy stacking 的最坏栈预算。
- 编译器静态栈分析与调用图上界推导。
- 安全关键系统中的栈保护诊断覆盖率和故障响应设计。
