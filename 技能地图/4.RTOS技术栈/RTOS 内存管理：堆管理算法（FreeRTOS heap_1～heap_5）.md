
## 1. 学习目标

### 理解

- 理解 FreeRTOS `heap_1`～`heap_5` 的数据结构、分配策略和释放行为。
- 理解堆分配器中的块头、对齐、空闲链表、块拆分与相邻合并。
- 理解不同算法对确定性、碎片、RAM 区域和并发的影响。

### 掌握

- 能根据对象生命周期和实时要求选择 heap 实现。
- 能核对 `configSUPPORT_DYNAMIC_ALLOCATION`、`configTOTAL_HEAP_SIZE` 和 `heap_5` 区域配置。
- 能测量堆总空闲量、最小历史空闲量、最大空闲块及分配延迟。
- 能处理分配失败、堆损坏、对象销毁和多任务并发风险。

### 精通

- 能从目标 FreeRTOS 源码推导实际块布局、对齐粒度、搜索复杂度和合并行为。
- 能分析堆碎片如何由分配尺寸、生命周期和分配释放顺序共同形成。
- 能针对硬实时、多 RAM 区域、网络缓冲区等场景设计堆与内存池组合策略。

### 能够设计

- 能设计适配产品需求的分配器选型矩阵、内存预算和运行时监控。
- 能建立禁止关键路径动态分配、限制分配尺寸、统计失败和验证碎片的工程机制。
- 能为所选分配器设计压力测试、长时间碎片测试和故障注入测试。

## 2. 前置要求

### 知识要求

- 熟悉 C 指针、结构体、对齐、整数溢出和对象生命周期。
- 熟悉 RTOS 任务、临界区、调度器锁、互斥锁和中断上下文。
- 熟悉 MCU RAM 分区、链接脚本、map 文件和堆栈布局。
- 了解 `malloc/free` 与 FreeRTOS `pvPortMalloc/vPortFree` 的用途区别。

### 技能要求

- 能定位实际工程使用的 `heap_n.c`，而不只根据配置宏推测实现。
- 能通过编译器输出或调试器检查 `sizeof(HeapRegion_t)`、堆边界和对齐。
- 能用硬件周期计数器测量分配和释放时间。
- 能运行随机分配、释放和压力测试，并保存堆统计数据。

## 3. 技术概述

### 核心定义

FreeRTOS 将内存分配器实现为可替换的 `heap_n.c` 文件。应用通过 `pvPortMalloc()` 和 `vPortFree()` 使用分配器，内核的动态对象创建 API 也可能调用这些接口。

```
void *pvPortMalloc(size_t size);
void vPortFree(void *ptr);
```

`heap_1`～`heap_5` 不是五种可同时使用的堆策略。通常工程中**只编译其中一个实现文件**，并由该文件决定分配和释放算法。

### 五种实现概览

|实现|释放|堆区域|核心策略|主要取舍|
|---|---|---|---|---|
|`heap_1`|不支持回收|单个连续数组|线性 bump allocator|简单、时间稳定，内存只能单向消耗|
|`heap_2`|支持|单个连续数组|首次适配，不合并相邻空闲块|可重用已释放块，但容易产生外部碎片|
|`heap_3`|支持|C 库管理|包装 `malloc/free`|行为、锁和时间特性依赖 C 库|
|`heap_4`|支持|单个连续数组|地址排序链表、首次适配、相邻合并|通用性较好，搜索时间随链表变化|
|`heap_5`|支持|多个不连续区域|`heap_4` 类算法加多区域初始化|可利用多个 RAM 区域，但不感知区域属性|

具体内部实现会随 FreeRTOS 版本、端口和工程修改而变。**分析和验收必须基于项目实际编译的源码版本。**

### 核心术语

- **内部碎片**：分配块实际占用大于用户请求，差额来自头部、对齐和最小块规则。
- **外部碎片**：空闲内存总量足够，但被分割成不连续小块，无法满足较大的连续申请。
- **首次适配**：沿空闲链表查找第一个足以满足请求的块。
- **块合并**：释放后将物理地址相邻的空闲块合成更大的空闲块。
- **最小历史空闲量**：运行以来可用堆空间的最低点，是容量压力指标，不是碎片指标。

## 4. 核心特性横向对比

|维度|`heap_1`|`heap_2`|`heap_3`|`heap_4`|`heap_5`|
|---|---|---|---|---|---|
|主要接口|`pvPortMalloc`|同左|包装 libc|同左|同左|
|释放后重用|否|是|是|是|是|
|相邻空闲块合并|不适用|否|由 libc 决定|是|是|
|搜索特征|无空闲链表搜索|空闲块搜索|由 libc 决定|首次适配搜索|首次适配、多区域搜索|
|分配延迟上界|接近固定操作路径|依空闲块数量|依 libc|依空闲块数量|依空闲块和区域数量|
|外部碎片|无回收，可能耗尽|高风险|依 libc|仍可能发生|仍可能发生|
|RAM 区域|单块|单块|libc 堆|单块|多块|
|典型用途|启动期一次性分配|受限尺寸集合|需要 libc 集成|通用动态对象|多 RAM bank|
|ISR 使用|不允许|不允许|不允许|不允许|不允许|

**实时性结论：** `heap_1` 的路径最简单，但这不代表动态创建 API 整体恒定时间；`heap_4/5` 的首次适配搜索时间会受堆状态影响。所有分配器都不应未经分析就放入硬实时路径或 ISR。

## 5. 底层原理与功能特性深度解析

### 5.1 共同接口与堆边界

应用通常通过以下 API 使用分配器：

```
void *buffer = pvPortMalloc(size);

if (buffer == NULL) {
    handle_allocation_failure(size);
} else {
    use_buffer(buffer);
    vPortFree(buffer);
}
```

常见 FreeRTOS 配置包括：

```
#define configSUPPORT_DYNAMIC_ALLOCATION  1
#define configTOTAL_HEAP_SIZE             (24U * 1024U)
```

`configTOTAL_HEAP_SIZE` 只对使用静态数组定义堆的实现生效，不能据此认定 libc 堆或所有 `heap_5` 区域的容量。应结合实际 `heap_n.c`、链接脚本和 map 文件确认。

### 5.2 `heap_1`：单向递增分配

`heap_1` 的核心状态通常包括：

- 堆数组。
- 下一个可用地址或当前偏移量。
- 已分配空间累计值。

简化逻辑：

```
void *heap1_alloc(size_t requested)
{
    size_t aligned_size;

    if (requested == 0U ||
        !align_and_check_size(requested, &aligned_size)) {
        return NULL;
    }

    if (aligned_size > heap_remaining()) {
        return NULL;
    }

    void *result = heap_current;
    heap_current += aligned_size;
    heap_remaining -= aligned_size;

    return result;
}
```

实际实现还会维护对齐和统计信息。释放通常不回收：

```
void vPortFree(void *ptr)
{
    (void)ptr;
    /* heap_1 不归还内存。 */
}
```

适用前提是分配对象的生命周期基本等同于系统生命周期，例如启动时创建固定任务和队列。若反复创建销毁对象，`heap_1` 的已用量只增不减，即使调用 `vPortFree()` 也不会恢复容量。

### 5.3 `heap_2`：可释放但不合并

`heap_2` 用空闲块链表记录释放的内存。分配时搜索一个能容纳请求的块，必要时拆分；释放时将块插回空闲链表。

核心限制是：**相邻空闲块不一定被合并。**

```
分配后： [A 已用] [B 已用] [C 已用]
释放 A、B： [A 空闲] [B 空闲] [C 已用]
```

即使 A 与 B 地址相邻，链表中仍可能保留两个独立空闲块。请求的大小超过任何单块时就可能失败。

`heap_2` 更适合分配尺寸种类有限、生命周期模式可预测的系统。对于不同尺寸网络包、临时文件缓存等反复变化的申请，不应把它当成通用抗碎片分配器。

### 5.4 `heap_3`：包装 C 库堆

`heap_3` 将 FreeRTOS 接口映射到 C 库：

```
void *pvPortMalloc(size_t size)
{
    return malloc(size);
}

void vPortFree(void *ptr)
{
    free(ptr);
}
```

真实版本通常会包裹调度器挂起或临界区逻辑，但锁策略和实现细节需读对应版本源码。

必须确认：

- libc 分配器是否支持多任务并发。
- `_sbrk()` 或等效系统调用如何定义堆顶。
- `malloc()` 与任务栈是否可能碰撞。
- `printf()` 或其他库是否会间接申请内存。
- libc 锁是否可被高优先级任务长期阻塞。
- `malloc` 失败时的返回和诊断行为。

**不要假设** `pvPortMalloc()` 返回的指针可以由 libc `free()` 释放，或反之。除非明确验证两者使用同一堆及兼容元数据，否则分别使用配对释放接口。

### 5.5 `heap_4`：地址排序与相邻合并

`heap_4` 的典型策略：

1. 从连续堆数组中初始化一个大空闲块。
2. 申请时按地址排序的空闲链表进行首次适配搜索。
3. 找到可用块后，若剩余空间足以构成最小块则拆分。
4. 释放时按地址插入空闲链表。
5. 与前后物理相邻的空闲块合并。

简化示意：

```
void *heap4_alloc(size_t requested)
{
    size_t total;

    if (!checked_add(requested, block_header_size(), &total)) {
        return NULL;
    }

    total = align_up(total, HEAP_ALIGNMENT);

    enter_heap_lock();

    Block_t *block = first_fit(total);
    if (block != NULL) {
        remove_from_free_list(block);
        split_if_large_enough(block, total);
        mark_allocated(block);
    }

    exit_heap_lock();

    return block != NULL ? block_to_payload(block) : NULL;
}
```

释放与合并示意：

```
void heap4_free(void *ptr)
{
    if (ptr == NULL) {
        return;
    }

    Block_t *block = payload_to_block(ptr);

    enter_heap_lock();

    mark_free(block);
    insert_by_address(block);
    coalesce_with_adjacent_blocks(block);

    exit_heap_lock();
}
```

这些是算法结构示意，不是可替代 FreeRTOS 实现的生产代码。真实实现中的块头布局、标志位、验证逻辑和临界区 API 要以目标源码为准。

**复杂度：** 首次适配可能遍历多个空闲块，通常可描述为 O(n)，其中 `n` 是空闲链表节点数。释放插入和相邻检查也会受到链表长度及实现影响。不能仅凭平均时间宣称存在固定 WCET。

### 5.6 `heap_5`：多个不连续区域

`heap_5` 与 `heap_4` 类似，但可以将多个不连续地址区域交给分配器管理。区域通常在调度器启动前定义：

```
static uint8_t s_internal_heap[12U * 1024U];
static uint8_t s_external_heap[64U * 1024U];

static const HeapRegion_t s_heap_regions[] = {
    { s_internal_heap, sizeof(s_internal_heap) },
    { s_external_heap, sizeof(s_external_heap) },
    { NULL, 0U }
};

void app_define_heap_regions(void)
{
    vPortDefineHeapRegions(s_heap_regions);
}
```

使用前必须确认：

- `vPortDefineHeapRegions()` 调用顺序符合目标版本要求，通常应在首次动态分配之前。
- 区域按实现要求排序，且不重叠。
- 区域起始地址和长度满足对齐要求。
- 区域位于有效 RAM，且没有被栈、DMA、其他堆或外设保留。
- 是否允许调度器启动后调用区域定义函数，必须依据版本源码确认。

`heap_5` 不提供按用途挑选区域的语义。普通分配器可能把某对象放进外部 RAM，但该对象可能要求片上 SRAM、DMA 可达或非缓存区域。需要区域属性时应使用专用分配器或显式分区，不应只靠一个统一 heap。

### 5.7 线程安全与中断

堆元数据在多个任务并发访问时必须受保护。分配器的临界区会影响响应时间，使用互斥锁还可能引入优先级反转。

普通 `pvPortMalloc()` / `vPortFree()` 不应从 ISR 调用。ISR 应：

- 使用静态缓冲区。
- 从预分配固定池获取受控块，且池 API 明确支持 ISR。
- 向任务发送索引、事件或描述符。
- 由任务上下文完成分配与释放。

### 5.8 堆监控接口

常见接口（可用性依 FreeRTOS 版本、配置与实现而定）：

```
size_t free_now = xPortGetFreeHeapSize();
size_t free_min = xPortGetMinimumEverFreeHeapSize();
```

它们通常反映总空闲量，不一定提供最大连续空闲块或真实碎片率。不要把“总空闲量”当作“可满足最大申请尺寸”。

建议额外采集：

```
当前总空闲量
最小历史空闲量
最大连续空闲块
分配失败次数
每个模块的申请和释放统计
最大申请尺寸
分配和释放的 P99 / 最大耗时
```

## 6. 性能量化分析

### 6.1 内存计算

一次申请的实际堆消耗可估算为：

```
实际消耗 =
    用户请求大小
  + 块头部
  + 对齐填充
  + 最小块限制造成的余量
```

若目标 `heap_4` 的对齐粒度为 `A`，块头部为 `H`，用户请求为 `R`，则近似：

```
块大小 = align_up(R + H, A)
内部浪费 = 块大小 - R
```

**A 和 H 必须从目标构建的源码、配置和 `sizeof` 中取得。** 不要把某个 32 位 MCU 上测得的头部尺寸套用到另一个端口。

系统总堆预算：

```
Heap_required =
    Σ(任务栈及 TCB 动态开销)
  + Σ(队列控制结构及队列数据)
  + Σ(信号量、事件组、定时器对象)
  + Σ(应用动态缓冲区)
  + 对齐开销
  + 碎片余量
  + 故障恢复余量
```

动态任务创建时，任务栈和 TCB 也可能从同一堆分配，所以不能只预算应用的 `malloc()` 请求。

### 6.2 碎片指标

```
总空闲量 = Σ(所有空闲块大小)
最大空闲块 = max(每个空闲块大小)

外部碎片率 = 1 - 最大空闲块 / 总空闲量
```

例如，空闲块为 2048、1024、512 字节：

```
总空闲量 = 3584 B
最大空闲块 = 2048 B
外部碎片率 = 1 - 2048 / 3584 ≈ 42.9%
```

该指标是诊断参考，不是标准化的唯一碎片定义。还应记录请求失败时的尺寸和最大空闲块。

### 6.3 性能复杂度和实测

|算法|分配搜索|释放行为|时间变化来源|
|---|---|---|---|
|`heap_1`|无空闲块搜索|不回收|对齐和边界检查|
|`heap_2`|空闲链表搜索|插入空闲链表|空闲块数量|
|`heap_3`|libc 实现决定|libc 实现决定|libc 算法、锁和系统调用|
|`heap_4`|首次适配搜索|排序插入、相邻合并|空闲链表长度、合并路径|
|`heap_5`|空闲搜索加区域布局|类似 `heap_4`|空闲块数量及区域结构|

本课不提供通用“微秒实测值”：没有目标 MCU、时钟、编译器、配置和测试负载时，数字会误导。工程测量应记录：

```
MCU/时钟
编译器版本与优化级别
FreeRTOS 版本与 heap 源码 hash
堆大小和区域布局
堆状态或空闲块数量
平均、P95、P99、最大周期数
中断和任务竞争条件
```

### 6.4 测量方法

在支持 DWT 的 Cortex-M 上，可以用周期计数器测量：

```
uint32_t start = DWT->CYCCNT;
void *ptr = pvPortMalloc(request_size);
uint32_t elapsed = DWT->CYCCNT - start;
```

需处理计数器回绕，并确保测量构建与发布构建一致。建议分别测：

- 空堆、低碎片堆、长期运行碎片堆。
- 小、中、大申请尺寸。
- 单任务与多任务并发。
- 分配成功和失败路径。
- 有无调试检查、哨兵和 Trace。

### 6.5 瓶颈与优化收益

- 链表变长：采用固定池、尺寸分级池或实时分配器可降低搜索抖动。
- 变尺寸生命周期：通过按生命周期分区或启动期冻结减少碎片。
- 锁竞争：关键路径改用静态资源或每模块独立池。
- 外部 RAM 延迟：将控制对象和硬实时数据留在片上 RAM。
- 申请尺寸无上限：增加输入上限和失败策略，避免不可控堆压力。

收益不能只用平均耗时衡量，还要看最大耗时、碎片演化、代码复杂度和可恢复性。

## 7. 应用场景选型指南

### 纯文本决策流程图

```
运行期是否需要释放对象？
├─ 否
│  ├─ 对象仅在启动时创建 -> heap_1 或静态创建
│  └─ 对象数量固定且关键 -> 静态创建
└─ 是
   ├─ 对象大小固定或只有少数尺寸？
   │  ├─ 是 -> 固定块池 / 分级内存池
   │  └─ 否
   │     ├─ 是否为硬实时路径？
   │     │  ├─ 是 -> 重构为预分配、固定池或验证过的实时分配器
   │     │  └─ 否 -> 评估 heap_4
   │     └─ 是否有多个不连续 RAM 区域？
   │        ├─ 是 -> heap_5 或区域专用分配器
   │        └─ 否 -> heap_4
   └─ 是否必须复用 C 库分配器？
      ├─ 是 -> heap_3，并审查 libc、锁和链接脚本
      └─ 否 -> 使用 FreeRTOS heap 或专用池
```

### 典型场景

|需求|推荐方案|理由|
|---|---|---|
|固定任务和队列，仅启动期创建|静态 API 或 `heap_1`|生命周期固定，避免运行期回收问题|
|连接对象可创建销毁、尺寸相近|固定池或尺寸分级池|容量明确，降低碎片和延迟|
|非实时任务中的多种动态对象|`heap_4`|通用性较好，释放时合并相邻块|
|片上 SRAM 加外部 RAM|`heap_5` 或分区分配器|可描述多段内存|
|必须与 libc 统一分配|`heap_3`|复用 C 库，但需验证并发和实时性|
|高实时控制循环|静态对象或固定池|最坏执行时间更易约束|
|DMA 缓冲区|专用静态区或区域池|地址、对齐、Cache 属性可控|

## 8. 工程最佳实践

### 设计原则

- 按**对象生命周期、尺寸分布、实时等级和 RAM 属性**选算法。
- 对所有动态申请规定最大数量、最大尺寸和最大持有时间。
- 关键周期任务不进行未经验证的通用堆分配。
- 对每个对象明确唯一所有者和释放责任。
- 对外部输入驱动的尺寸做上限检查和溢出检查。
- `heap_5` 的区域按地址和对齐要求配置，并防止与链接器段重叠。
- 任何分配失败都要按模块定义降级、丢弃、重试或安全停机策略。
- 不用堆总空闲量替代最大连续块监控。

### 选型矩阵

|需求|首选|不推荐情况|
|---|---|---|
|启动期一次性分配|`heap_1`|对象需要释放|
|小集合尺寸、低频销毁|`heap_2` 可评估|尺寸变化频繁、运行期很长|
|libc 统一管理|`heap_3`|实时上界未知、堆边界不清|
|通用可释放分配|`heap_4`|硬实时路径、碎片不可接受|
|多个不连续 RAM 区域|`heap_5`|内存区域属性需按对象区分|
|固定尺寸消息与数据块|固定块池|尺寸差异过大且池浪费不可接受|

### 工程规范

- 一个工程通常只编译一个 `heap_n.c`，并在构建系统中明确指定。
- 启动时统一初始化内存区域，之后禁止重复初始化。
- 分配失败钩子应记录请求尺寸、任务名、堆统计和调用模块。
- 堆统计接口应与具体 heap 实现能力匹配，不能伪造“最大块”数据。
- 动态 RTOS 对象销毁前，先停止生产者、唤醒等待者并确认无其他引用。
- 对堆管理文件的本地修改必须记录来源、差异和验证测试。

## 9. 常见错误与避坑指南

### 错误一：误以为 `heap_4` 没有碎片

```
/* 频繁申请不同大小，再以不同顺序释放。 */
void *a = pvPortMalloc(80U);
void *b = pvPortMalloc(900U);
void *c = pvPortMalloc(128U);

/* 长时间运行中任意释放和重新申请。 */
```

**根因：** 相邻合并只能合并地址连续且都空闲的块，无法跨越仍在使用的对象。

**正确实现：** 对固定尺寸包使用固定池；对不同生命周期对象分区；对关键申请尺寸设置容量和最大块监控；通过长时间随机测试验证碎片。

**风险影响：** 总空闲量仍较大，但大对象申请失败，现场表现为运行时间越长越容易故障。

### 错误二：只看 `xPortGetFreeHeapSize()`

```
if (xPortGetFreeHeapSize() > 4096U) {
    ptr = pvPortMalloc(4096U);
}
```

**根因：** 总空闲量不等于最大连续可分配块，检查与申请之间还可能发生并发分配。

**正确实现：** 不要用“先查询再申请”代替失败检查；直接检查申请返回值。必要时通过分配器扩展统计最大空闲块，并将统计与实际分配保护机制结合。

**风险影响：** 条件判断通过后分配仍失败，产生竞态和错误降级。

### 错误三：将 `heap_5` 当成按区域属性自动分配

```
/* 错误假设：heap_5 会自动把 DMA 对象放到 DMA 可访问 RAM。 */
void *dma_buffer = pvPortMalloc(DMA_SIZE);
```

**根因：** `heap_5` 管理多个区域，不理解对象用途、DMA 可达性或缓存属性。

**正确实现：** 使用专用 DMA 区域静态对象、区域专用分配器，或在接口中明确指定内存区域。

**风险影响：** DMA 无法访问地址、缓存数据不一致或总线错误。

### 错误四：把 `heap_1` 的 `vPortFree()` 当作真实回收

```
void replace_buffer(void)
{
    void *old = pvPortMalloc(512U);
    vPortFree(old); /* heap_1 下通常不会归还容量 */
    void *next = pvPortMalloc(512U);
    (void)next;
}
```

**根因：** `heap_1` 的设计是单向分配，不支持回收。

**正确实现：** 固定生命周期对象使用 `heap_1`；需要复用时选 `heap_4`、内存池或静态缓冲区。

**风险影响：** 反复替换对象后堆持续消耗，最终申请失败。

### 错误五：把 `malloc/free` 和 `pvPortMalloc/vPortFree` 交叉配对

```
void *ptr = pvPortMalloc(128U);
free(ptr); /* 错误，除非已明确验证堆完全兼容 */
```

**根因：** 两套分配器可能使用不同堆和不同块头格式。

**正确实现：**

```
pvPortMalloc -> vPortFree
malloc       -> free
```

**风险影响：** 堆元数据被错误解释，导致立即损坏或延迟崩溃。

## 10. 多机制组合使用方案

### 组合架构

```
静态对象
  ├─ 控制任务、关键队列、DMA 描述符
  └─ 生命周期固定，不进入通用堆

固定块池
  ├─ 网络包、采集记录、协议帧
  └─ 尺寸固定、运行期可借还

heap_4
  ├─ 非关键且尺寸变化的模块对象
  └─ 监控总空闲量、最大块、失败和延迟

heap_5 / 区域专用分配器
  ├─ 多段 RAM
  └─ 按内存属性区分 DMA、Cache、外部 RAM
```

### 设计模式：固定块优先、通用堆兜底受限

以下是策略框架，需由项目实现池接口和模块统计：

```
typedef enum {
    ALLOC_SOURCE_NONE = 0,
    ALLOC_SOURCE_POOL,
    ALLOC_SOURCE_HEAP
} AllocSource_t;

typedef struct {
    void *ptr;
    size_t capacity;
    AllocSource_t source;
} BufferHandle_t;

bool buffer_acquire(
    size_t requested,
    BufferHandle_t *out)
{
    if ((out == NULL) || (requested == 0U)) {
        return false;
    }

    out->ptr = NULL;
    out->capacity = 0U;
    out->source = ALLOC_SOURCE_NONE;

    if (requested <= SMALL_BLOCK_SIZE) {
        out->ptr = small_pool_take();
        if (out->ptr != NULL) {
            out->capacity = SMALL_BLOCK_SIZE;
            out->source = ALLOC_SOURCE_POOL;
            return true;
        }
    }

    if (requested <= MAX_DYNAMIC_BUFFER_SIZE) {
        out->ptr = pvPortMalloc(requested);
        if (out->ptr != NULL) {
            out->capacity = requested;
            out->source = ALLOC_SOURCE_HEAP;
            return true;
        }
    }

    return false;
}

void buffer_release(BufferHandle_t *handle)
{
    if ((handle == NULL) || (handle->ptr == NULL)) {
        return;
    }

    if (handle->source == ALLOC_SOURCE_POOL) {
        small_pool_give(handle->ptr);
    } else if (handle->source == ALLOC_SOURCE_HEAP) {
        vPortFree(handle->ptr);
    }

    handle->ptr = NULL;
    handle->capacity = 0U;
    handle->source = ALLOC_SOURCE_NONE;
}
```

生产实现还需处理：

- 池块容量和请求尺寸校验。
- 释放来源校验，避免跨分配器释放。
- 并发保护。
- 池耗尽和堆申请失败的策略。
- 统计、哨兵和重复释放检测。

## 11. 工业级实际案例分析

### 案例一：固定任务控制器

**需求：** 任务集合在产品启动前已知，运行期间不增加任务，控制周期要求可预测。

**方案：**

- 首选静态创建。
- 若已有动态创建框架且启动后绝不销毁，可评估 `heap_1`。
- 不在周期控制任务中申请或释放内存。

**关键验证：**

- 所有对象创建失败时系统进入安全状态。
- 任务栈高水位和堆最低水位在最坏负载下记录。
- 链接 map 能证明堆、栈和全局对象没有重叠。

### 案例二：网络连接与包缓冲

**需求：** 连接可动态建立和断开，最多 12 个连接；报文长度变化，但最大 1500 字节。

**方案：**

- 连接控制块：固定 12 个对象池。
- 以太网包：固定 1536 字节块池。
- 非关键协议辅助对象：受控 `heap_4`。
- ISR 只提交 DMA 缓冲区索引，由任务执行协议处理。

**容量核算示例：**

```
包池容量 = 块数 × 块大小
          = 16 × 1536
          = 24576 字节
```

还要加上池元数据、队列和协议栈对象。池块数应根据最大并发持有数、队列峰值和消费者最坏服务延迟确定，不能只按连接数估算。

### 案例三：多 RAM 区域 HMI

**需求：** 片上 SRAM 放关键对象，外部 SDRAM 放图像缓存，DMA 只能访问指定区域。

**方案：**

- 关键任务栈、TCB、DMA 描述符：静态放入指定 RAM 段。
- 外部图像缓存：区域专用分配器，或单独管理的 SDRAM 池。
- 如果使用 `heap_5`，只对允许跨区域分配的普通对象使用。
- 为 DMA 和非缓存区提供独立 API，不让业务模块直接调用通用堆。

**关键验证：**

- 检查 map 文件中的区域边界和对齐。
- 检查外部 RAM 初始化早于首次申请。
- 验证 DMA 对每个返回区域都可达。
- 测量外部 RAM 延迟，不把其当作片上 SRAM。

## 12. 高频问题深度答疑

### 1. 一个工程能同时使用 `heap_1` 和 `heap_4` 吗？

标准集成通常只编译一个 `heap_n.c`，由其实现 `pvPortMalloc()` 和 `vPortFree()`。若业务确实要多种策略，应使用独立命名、独立元数据和独立接口，例如专用固定池加 RTOS heap，而不是链接两份同名实现。

### 2. `heap_4` 合并后是否能避免长期碎片？

不能保证。合并只处理物理相邻且都空闲的块。长期碎片受分配大小分布、释放顺序和对象持有时间影响。应以目标 workload 做长时间测试，监控最大连续块，而不仅是总空闲量。

### 3. `heap_5` 会优先使用哪段 RAM？

取决于目标版本实现、区域顺序和链表管理逻辑。不能仅凭 API 名称推断分配优先级。读实际源码并用可识别的内存区域地址进行测试。若优先级或区域约束是系统要求，应使用显式区域分配接口。

### 4. `heap_3` 是否一定线程安全？

不一定。安全性取决于 C 库是否为多线程环境构建、锁函数是否正确实现，以及 FreeRTOS 包装是否覆盖所有相关调用路径。还要考虑 libc 的 `printf`、文件系统等函数是否使用同一分配器。

### 5. `xPortGetMinimumEverFreeHeapSize()` 能说明没有碎片吗？

不能。它关注历史最低总空闲量，不描述空闲块是否连续。还需最大空闲块或更细粒度的分配器统计，并结合真实申请尺寸分布评估。

### 6. 如何选 `heap_4` 还是固定块池？

若对象尺寸固定或能归入少数尺寸等级，且需要稳定时间和明确容量，优先池。若对象尺寸多变、运行于非关键路径，且需要较高利用率，可评估 `heap_4`。两者也常组合：高频大批量对象走池，低频灵活对象走堆。

## 13. 课程核心总结

- `heap_1`：只分配不回收，适用于启动期单向创建。
- `heap_2`：支持释放但不合并相邻空闲块，碎片风险较高。
- `heap_3`：委托 C 库，实时性、线程安全和堆边界依赖 libc 与工程配置。
- `heap_4`：首次适配并合并相邻空闲块，是通用方案之一，但仍可能碎片化且搜索时间随堆状态变化。
- `heap_5`：支持多个不连续区域，但不自动解决内存属性选择。
- **硬实时路径优先静态对象或固定池。**
- **堆健康不能只看总空闲量；最大连续块和分配失败尺寸同样重要。**
- 测量必须基于目标源码、目标芯片和真实负载，不能把跨平台数字当作 WCET 证明。

## 16. 实践与进阶路径

### 梯度实战任务

1. 在构建系统中确认唯一编译的 `heap_n.c`，记录 FreeRTOS 版本和源码校验信息。
2. 使用 `heap_4` 创建和销毁任务、队列，检查动态对象实际占用。
3. 写随机尺寸分配测试，周期性记录总空闲量、最大空闲块和失败次数。
4. 用相同 workload 对比 `heap_2` 与 `heap_4` 的碎片演化。
5. 配置 `heap_5` 管理两段测试 RAM，并验证区域顺序、对齐和地址范围。
6. 将高频消息缓冲区迁移到固定池，比较最大分配延迟与 RAM 利用率。
7. 为堆耗尽、非法释放和重复释放设计故障注入测试。

### 性能测试方法

- 使用 DWT 或硬件定时器测量分配、释放的平均、P99 和最大耗时。
- 至少测试空闲链表短、中、长三种堆状态。
- 在并发任务和高频中断负载下测最大阻塞时间。
- 通过链接 map 核对堆、栈、静态对象和专用 RAM 区域。
- 记录真实分配请求尺寸和生命周期分布，按产品 workload 长时间运行。
- 将堆最低水位、最大连续块和分配失败次数纳入运行时诊断。

### 进阶学习方向

- 按目标 FreeRTOS 版本逐行阅读 `heap_1.c`～`heap_5.c`。
- 分析块头中的分配标志位、对齐和整数边界检查。
- 研究 TLSF、slab、buddy allocator 和固定块池的时间与空间取舍。
- 研究多核 RTOS 下的堆锁、每核堆和跨核释放。
- 将 MPU、链接器分区、DMA 和 Cache 一致性纳入内存区域设计。
- 建立 CI 中的 RAM 预算、堆压力、碎片和最坏延迟回归测试。
