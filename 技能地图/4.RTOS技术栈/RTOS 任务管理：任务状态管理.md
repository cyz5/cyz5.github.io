
## 1. 学习目标

### 理解

- 区分**任务状态**与任务上下文：状态描述任务能否被调度，上下文描述任务从哪里继续执行。
- 理解就绪、运行、阻塞、挂起、删除等状态的语义，以及状态转换由哪些事件驱动。
- 解释 FreeRTOS 等 RTOS 如何用就绪队列、延时队列和挂起列表实现状态管理。

### 掌握

- 根据任务状态转换图分析任务何时可运行、何时会被唤醒。
- 正确使用任务通知、队列、信号量、延时、挂起与恢复 API。
- 使用任务状态查询、运行时统计和 trace 工具定位任务长期阻塞、饥饿和无效唤醒。

### 精通

- 分析优先级抢占、调度器暂停、中断屏蔽、事件竞态对状态转换的影响。
- 设计超时、取消、故障恢复与任务重启策略。
- 从内核源码追踪 TCB、状态列表和调度器状态更新。

### 能够设计

- 设计符合实时性要求的任务状态模型，明确每个阻塞条件、超时策略和资源所有权。
- 建立可观测性方案，识别任务长期就绪却未运行、长期阻塞和异常挂起。
- 评估任务状态管理对响应时间、内存占用和故障恢复的影响。

### 知识要求

- RTOS 抢占式调度、优先级与时间片基础。
- 队列、信号量、互斥锁、任务通知等同步机制。

- 了解任务控制块（TCB）和任务栈。

- 能阅读 FreeRTOS 任务 API 与对应内核源码。
- 能使用调试器或 trace 工具查看任务列表、优先级和运行状态。
- 能分析任务等待条件、超时时间和资源获取路径。
- 能编写并发测试，覆盖事件先到、超时先到、删除与恢复等边界情况。

## 3. 技术概述

**任务状态管理**是 RTOS 维护任务当前调度资格与等待条件的机制。它决定哪些任务可以参与调度，以及任务因何种事件进入或离开等待状态。

需要区分两类信息：

- **调度状态**：任务当前是否可运行，例如就绪、阻塞、挂起。
- **任务上下文**：寄存器、栈指针等 CPU 状态，用于恢复任务执行。

典型状态包括：

- **运行（Running）** ：当前正在 CPU 上执行。单核系统同一时刻最多一个任务处于运行状态。
- **就绪（Ready）** ：具备运行条件，等待调度器分配 CPU。
- **阻塞（Blocked）** ：等待时间、队列、信号量、通知等有限条件。
- **挂起（Suspended）** ：由显式挂起操作移出调度，通常不会因普通事件自动恢复。
- **删除（Deleted）** ：不再参与调度，相关资源可能立即或延迟回收。

具体状态名称和内部实现依 RTOS 而异。以 FreeRTOS 为例，内部通常通过多个列表表示任务集合；某些 API 的“状态”是对内部列表关系的概括，并非每种状态都对应独立字段。

## 4. 核心特性横向对比

|状态|是否可被调度|常见进入原因|常见离开原因|关键注意点|
|---|---|---|---|---|
|运行|是，正在占用 CPU|调度器选中|被抢占、阻塞、挂起、删除|运行状态不代表正在完成有效工作|
|就绪|是，等待 CPU|新建、等待条件满足、被恢复|调度器选中|长期就绪可能表示优先级饥饿|
|阻塞|否|等待队列、通知、信号量或超时|事件到达或超时|阻塞对象与超时必须可追踪|
|挂起|否|显式 suspend|显式 resume|普通事件通常不会解除挂起|
|删除|否|删除任务 API 或任务入口返回|资源回收或重建|动态对象回收时机与内存管理有关|

|等待方式|条件满足时自动恢复|是否支持超时|适用场景|
|---|---|---|---|
|阻塞等待队列/通知|是|通常支持|事件驱动工作|
|延时等待|到期后恢复|是，延时本身即超时|周期性工作、退避|
|显式挂起|否|通常不适用|管理控制、维护模式|
|忙等轮询|任务仍运行|由代码实现|极少数极短、严格受控场景|

## 5. 底层原理与功能特性深度解析

### 5.1 状态通常由列表关系实现

以 FreeRTOS 为例，TCB 保存任务优先级、栈指针、状态列表项等信息。内核用列表组织任务：

- 每个优先级通常有对应的就绪列表。
- 延时等待任务进入延时列表。
- 等待队列或同步对象的任务进入相应事件等待列表。
- 显式挂起任务进入挂起列表。
- 删除任务进入待清理列表或由调用路径完成回收。

任务状态并不一定由一个 `state` 字段直接决定。状态查询通常根据任务当前挂在哪个列表，以及调度器是否运行等信息推导。

### 5.2 典型状态转换

```
┌──────────────┐
                         │    运行      │
                         └──────┬───────┘
             被抢占 / 时间片到期 │ 阻塞 / 挂起 / 删除
                                ▼
                           ┌────────┐
                           │  就绪  │
                           └───┬────┘
                               │ 等待事件或延时
                               ▼
                         ┌──────────┐
                         │  阻塞    │
                         └────┬─────┘
              事件到达 / 超时 │
                              └──────────> 就绪

就绪或运行 ──显式挂起──> 挂起
挂起 ──显式恢复──> 就绪
```

关键点：

- 任务从阻塞变为就绪，不等于立刻运行；还需等待调度器选择。
- 任务从运行变为就绪，常由更高优先级任务抢占导致。
- 挂起与阻塞语义不同：阻塞有等待条件，条件满足或超时可自动恢复；挂起通常需要显式恢复。
- 删除任务并不是一种等待状态，而是生命周期终止过程。

### 5.3 阻塞等待与事件列表

等待同步对象时，内核需要同时维护两种关系：任务等待哪个事件，以及该任务是否有超时期限。实现上可使用事件列表与延时列表配合，或采用其他内核特定结构。

```
static void sensor_task(void *arg)
{
    (void)arg;

    for (;;) {
        sensor_event_t event;

        /*
         * 任务进入阻塞状态；事件到达或超时后才恢复运行。
         * 超时要有明确定义，不能把等待失败静默吞掉。
         */
        if (xQueueReceive(sensor_queue, &event, pdMS_TO_TICKS(100)) == pdPASS) {
            process_sensor_event(&event);
        } else {
            handle_sensor_timeout();
        }
    }
}
```

这里的状态变化大致是：

1. 任务调用阻塞式接收 API。
2. 内核检查队列；队列为空时，将任务从就绪集合移出。
3. 事件到达后，发送路径解除一个或多个等待任务的阻塞。
4. 被解除阻塞的任务加入就绪集合。
5. 若其优先级高于当前任务，内核请求一次调度。

### 5.4 延时与超时

延时到期由系统节拍或硬件定时器机制驱动。经典 tick 实现中，任务的唤醒时刻会按 tick 粒度量化：

Tdelay≈Nticks×TtickTdelay​≈Nticks​×Ttick​

实际等待时间还取决于调用时刻在 tick 周期中的相位、调度延迟和中断屏蔽时间。因此 `vTaskDelay()` 不适合提供精确周期。

```
static void periodic_task(void *arg)
{
    (void)arg;
    TickType_t last_wake = xTaskGetTickCount();

    for (;;) {
        sample_inputs();
        run_control_step();

        /* 使用绝对节拍，减少循环执行时间造成的周期漂移。 */
        vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(10));
    }
}
```

### 5.5 挂起、阻塞和调度器暂停的区别

- **阻塞任务**：等待某个事件或时间，通常由事件到达或超时自动恢复。
- **挂起任务**：显式从调度中移除，一般要由另一个执行上下文显式恢复。
- **调度器暂停**：调度器暂时不切换任务，但任务状态更新和中断行为仍受内核定义；它不是把所有任务挂起，也不等价于关闭中断。

```
/* 控制任务生命周期的示意代码。 */
void maintenance_enter(void)
{
    vTaskSuspend(acquisition_task_handle);
}

void maintenance_exit(void)
{
    vTaskResume(acquisition_task_handle);
}
```

挂起一个正持有互斥锁的任务会造成资源长期占用，因此任务挂起不应被用作通用同步方案。

### 5.6 删除与资源回收

任务删除后，其任务栈和 TCB 是否立即释放，取决于 RTOS、删除对象和内存分配策略。FreeRTOS 中，自删除任务的清理可能由 Idle 任务完成。因此 Idle 任务必须获得运行机会；若高优先级任务长期不阻塞，待清理资源可能积累。

```
static void worker_task(void *arg)
{
    (void)arg;

    if (!worker_init()) {
        record_worker_init_failure();
        vTaskDelete(NULL);
    }

    for (;;) {
        worker_run_once();
        if (worker_should_stop()) {
            worker_deinit();
            vTaskDelete(NULL);
        }
    }
}
```

### 5.7 状态查询的边界

`eTaskGetState()` 等查询 API 适合诊断，不应作为同步原语。状态在查询返回后可能立即变化；在多核系统中，状态还可能受跨核调度影响。

生产逻辑应使用队列、通知、信号量、互斥锁等同步对象表达条件，而不是轮询任务状态后再采取动作。

## 6. 性能量化分析

### 6.1 状态管理的主要成本

状态管理成本由以下部分组成：

Ttransition=Tcritical+Tlist update+Twakeup selection+Tpreemption decisionTtransition​=Tcritical​+Tlist update​+Twakeup selection​+Tpreemption decision​

总成本受内核数据结构、就绪任务数、优先级数量、临界区实现和 CPU 内存系统影响。

- 采用位图索引优先级的内核，可在固定优先级范围内快速定位最高优先级就绪任务。
- 使用链表遍历的实现，事件唤醒或任务选择成本可能随待处理节点数增长。
- 锁竞争、多核跨核唤醒、缓存一致性会增加额外开销。

### 6.2 量化示例与数据边界

任务状态转换没有跨平台通用的固定耗时。以下公式用于估算，不是实测结果：

Ustate=Ntransition×TtransitionTwindowUstate​=Twindow​Ntransition​×Ttransition​​

例如，假设目标平台实测一次“任务阻塞后被唤醒并加入就绪列表”的内核路径为 1.5 μs，系统每秒发生 10,000 次此类转换，则：

Ustate=10,000×1.5 μs1 s=1.5%Ustate​=1 s10,000×1.5 μs​=1.5%

该数值仅为算例。必须在实际固件中区分状态转换时间与完整调度/上下文切换时间。

### 6.3 内存开销估算

每个任务至少占用：

Mtask=MTCB+Sstack+Mlist itemsMtask​=MTCB​+Sstack​+Mlist items​

- `M_TCB`：与端口、编译选项和内核版本相关。
- `S_stack`：由任务栈预算决定，常远大于状态列表节点开销。
- `M_list items`：状态列表和事件列表节点通常嵌入或关联在 TCB 中，但具体布局因实现而异。

不要用未经目标版本验证的固定 TCB 字节数做产品预算。通过 map 文件、`sizeof()`、静态分配和内存池统计确认实际值。

### 6.4 测量建议

在目标板上采集：

- 状态转换次数与每类转换的时间。
- 任务阻塞、唤醒到真正运行的延迟。
- 长期就绪时间、任务运行时间与阻塞时间。
- 队列满、超时、任务删除和恢复的次数。
- 最坏中断屏蔽时间和调度器暂停时间。

优先使用 RTOS trace hook、DWT 周期计数器或硬件 trace。测量结果需记录 CPU 频率、编译优化、内存位置、tick 频率和中断负载。事件钩子会增加执行时间，应评估插桩对被测系统的扰动。

## 7. 应用场景选型指南

```
任务需要等待条件吗？
├─ 否
│  ├─ 是周期性工作：使用绝对节拍延时或硬件定时器通知
│  └─ 否：检查是否存在忙等或任务划分不合理
└─ 是
   ├─ 条件由队列、信号量、通知表达吗？
   │  ├─ 是：使用阻塞等待，并明确超时行为
   │  └─ 否：先定义事件所有权和同步语义
   ├─ 是否需要管理器强制停止任务？
   │  ├─ 是：评估显式挂起，但先释放锁和外设资源
   │  └─ 否：用阻塞等待表达空闲状态
   └─ 是否需要终止任务？
      ├─ 是：定义清理、资源回收和重建流程
      └─ 否：长期任务通常通过事件循环维持生命周期
```

|典型需求|状态管理方案|理由|
|---|---|---|
|等待 DMA 完成|ISR-safe 通知或队列阻塞等待|事件到达后自动就绪，避免轮询|
|固定周期采样|绝对节拍延时或定时器通知|避免任务执行时间造成周期累计漂移|
|故障后停止模块|明确状态机 + 清理后挂起或删除|资源释放和重启路径可验证|
|暂停维护模式|管理任务协调资源后显式挂起|避免强行挂起时遗留锁或外设状态|
|等待多个事件|队列、事件组或组合等待机制|状态转换对应明确的事件条件|
|低功耗空闲|任务阻塞并由内核进入 Idle/tickless|使内核识别无就绪任务的时间窗口|

## 8. 工程最佳实践

### 设计原则

- 用阻塞等待表达“当前无工作”，避免空转轮询。
- 每个阻塞点都要定义等待对象、超时、取消和错误恢复行为。
- 不把状态查询 API 用作线程间同步。
- 任务状态变更与资源所有权变更应成对设计。
- 删除任务前明确任务栈、TCB、队列、互斥锁、DMA 缓冲区和外设资源的回收责任。
- 任务长期就绪但未运行应视为潜在优先级设计问题，而不是状态查询异常。
- 维护模式优先通过任务内部状态机协作退出，再考虑显式挂起或删除。

### 选型决策矩阵

|需求|首选机制|主要约束|
|---|---|---|
|单个任务等待事件|任务通知|通知值语义需明确，避免覆盖或丢事件|
|携带数据的事件|队列或环形缓冲区|容量、满队列策略、数据所有权|
|多任务互斥访问|互斥锁|锁持有时间、优先级继承与锁顺序|
|等待多个位条件|事件组或对应内核机制|清位语义和竞争条件|
|周期执行|绝对节拍延时或定时器|时间精度、tick 分辨率、超期策略|
|管理任务停止/恢复|明确控制消息与任务状态机|状态转换必须幂等、资源必须可恢复|

### 工业级编码规范

- 为任务规定允许的状态迁移，不允许隐式依赖“它应该已经阻塞”。
- 所有阻塞等待都应检查返回值，并记录超时或错误计数。
- 任务句柄在创建、删除和重建期间要有明确的同步保护。
- 不在高频路径中反复调用任务状态查询进行轮询。
- 若使用动态删除，监控 Idle 任务是否有机会运行以及堆是否稳定。
- 通过 trace 记录状态进入/退出原因，而不只是当前状态快照。

## 9. 常见错误与避坑指南

### 错误一：用忙等等待事件

```
while (!data_ready) {
    /* 持续占用 CPU */
}
```

**根因：** 任务始终处于运行状态，没有进入阻塞状态；低优先级任务可能被饿死，功耗也会上升。

**正确实现：**

```
for (;;) {
    uint32_t notified = ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
    if (notified == 0U) {
        continue;
    }

    consume_ready_data();
}
```

**风险影响：** CPU 占用飙升、系统调度失衡、低功耗失效。若共享标志没有正确同步，还可能出现数据竞争。

### 错误二：将显式挂起误当作事件等待

```
vTaskSuspend(NULL); /* 等待队列数据，错误的抽象 */
```

**根因：** 被挂起任务不会因队列数据到达而自动恢复，除非其他代码显式调用恢复 API。

**正确实现：**

```
message_t message;

if (xQueueReceive(queue, &message, portMAX_DELAY) == pdPASS) {
    process_message(&message);
}
```

**风险影响：** 任务永久不运行，数据积压，系统表面正常但业务停滞。

### 错误三：任务拿着锁时被外部挂起

```
xSemaphoreTake(bus_mutex, portMAX_DELAY);
vTaskSuspend(NULL); /* 错误：挂起时仍持有总线锁 */
```

**根因：** 任务停止运行，但互斥锁所有权仍属于该任务，其他任务无法继续使用总线。

**正确实现：** 任务在受控流程中完成临界操作、释放锁后，再响应管理任务的停止请求。需要取消时，采用可取消的有限等待或任务内部控制消息。

**风险影响：** 死锁、外设永久不可用、超时级联。

### 错误四：把状态查询结果当作稳定事实

```
if (eTaskGetState(worker) == eBlocked) {
    xTaskResume(worker); /* 查询与恢复之间状态可能已变化 */
}
```

**根因：** 查询结果只是瞬时快照。任务可能在检查后被事件唤醒，竞态依赖可能导致恢复操作不符合预期。

**正确实现：** 用队列、通知或受保护的状态协议表达控制意图；需要幂等恢复时使用内核提供的对应 API，并按目标版本确认语义。

**风险影响：** 丢事件、状态不一致、难以复现的任务控制故障。

### 错误五：所有等待都使用无限超时

```
xQueueReceive(queue, &message, portMAX_DELAY);
```

**根因：** 无限等待可能隐藏设备断开、生产者故障或资源耗尽。它并非天然错误，但必须符合系统故障恢复要求。

**正确实现：**

```
if (xQueueReceive(queue, &message, pdMS_TO_TICKS(500)) == pdPASS) {
    process_message(&message);
} else {
    record_receive_timeout();
    attempt_link_recovery();
}
```

**风险影响：** 故障无法检测，任务长期阻塞，系统无法进入降级或恢复流程。

## 10. 多机制组合使用方案

### 架构：事件等待 + 有限超时 + 生命周期控制

```
外设 ISR
  ├─ 清除中断源
  ├─ 发布事件或缓冲区索引
  └─ ISR-safe 通知工作任务

工作任务
  ├─ 阻塞等待事件
  ├─ 收到事件：处理数据
  ├─ 超时：执行链路健康检查
  └─ 收到控制消息：释放资源并进入停止状态

管理任务
  ├─ 发出停止/重启命令
  ├─ 等待工作任务确认资源释放
  └─ 按策略重建或恢复任务
```

```
typedef enum {
    WORKER_CMD_STOP,
    WORKER_CMD_RESTART
} worker_command_t;

static QueueHandle_t worker_event_queue;
static QueueHandle_t worker_command_queue;

static void worker_task(void *arg)
{
    (void)arg;

    for (;;) {
        worker_event_t event;
        worker_command_t command;

        if (xQueueReceive(worker_command_queue,
                          &command,
                          0U) == pdPASS) {
            if (command == WORKER_CMD_STOP) {
                worker_release_resources();
                worker_acknowledge_stopped();
                vTaskSuspend(NULL);
            }

            if (command == WORKER_CMD_RESTART) {
                worker_release_resources();
                if (!worker_acquire_resources()) {
                    record_worker_restart_failure();
                    continue;
                }
            }
        }

        if (xQueueReceive(worker_event_queue,
                          &event,
                          pdMS_TO_TICKS(250)) == pdPASS) {
            worker_process_event(&event);
        } else {
            worker_check_health();
        }
    }
}
```

工程注意事项：

- 停止命令必须能在任务当前阻塞时送达。若事件队列与控制队列分离，需要使用队列集、任务通知、事件组，或将控制事件纳入同一等待路径。
- 示例中的 `xQueueReceive(..., 0)` 只检查控制队列；若控制消息可能在工作任务进入事件队列阻塞后到达，必须设计能唤醒该任务的组合等待方案。
- 实际系统通常将事件与控制命令统一编码进一个队列，或使用任务通知作为唤醒门铃，再由任务读取具体状态。
- 任务确认停止前，应释放锁、外设、DMA 和缓冲区所有权。

## 11. 工业级实际案例分析

### 案例一：传感器采集任务

**需求：** 传感器由数据就绪引脚触发，连续采集时不能忙等，失联后需要在限定时间内发现。

**架构设计：**

- GPIO ISR 清除中断并通知采集任务。
- 采集任务阻塞等待通知，等待带有限超时。
- 超时后检查传感器状态并触发恢复流程。
- 采集数据经队列或环形缓冲区交给处理任务。

**核心代码：**

```
static void acquisition_task(void *arg)
{
    (void)arg;

    for (;;) {
        uint32_t count =
            ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(100));

        if (count == 0U) {
            sensor_check_and_recover();
            continue;
        }

        if (!sensor_read_and_publish()) {
            record_sensor_read_error();
        }
    }
}

void SENSOR_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;

    sensor_clear_irq();
    vTaskNotifyGiveFromISR(acquisition_task_handle, &woken);
    portYIELD_FROM_ISR(woken);
}
```

**设计要点：** 通知是唤醒机制，不应被误认为数据队列。若每次触发都必须保留独立数据，应使用队列或缓冲区记录每个事件。

### 案例二：通信链路故障恢复

**需求：** 链路正常时处理消息，连接断开时按退避间隔重连，恢复后继续工作。

**架构设计：**

- 工作任务在消息队列上阻塞等待。
- 超时触发链路健康检查。
- 断线后进入任务内部的 `DISCONNECTED` 状态，执行有上限的指数退避。
- 链路恢复后回到 `CONNECTED`，不删除并重建任务。

**状态示意：**

```
CONNECTED
  ├─ 收到消息：处理消息
  └─ 健康检查失败：DISCONNECTED

DISCONNECTED
  ├─ 退避计时未到：阻塞等待
  ├─ 重连失败：增加退避时间
  └─ 重连成功：CONNECTED
```

**设计要点：** “任务调度状态”与“业务状态机”是两个维度。任务可以在业务 `DISCONNECTED` 状态下处于阻塞状态，不能用 RTOS 的 `Blocked` 代替业务状态。

### 案例三：设备维护模式

**需求：** 更新固件或维护外设时，停止采集和控制工作，但保留管理通道。

**架构设计：**

- 管理任务发布进入维护命令。
- 业务任务在安全点完成当前事务、释放锁和 DMA。
- 任务确认后进入维护状态或由管理器显式挂起。
- 退出维护时重新初始化外设，再恢复任务处理。

**设计要点：** 不要在任意时刻直接挂起任务。维护切换必须明确处理中事务的完成、缓冲区归属、互斥锁释放和恢复失败处理。

## 12. 高频问题深度答疑

### Q1：任务处于阻塞状态时还会消耗 CPU 吗？

通常不会执行任务代码，因此不消耗该任务的 CPU 时间。但系统仍需处理 tick、外设中断、定时器和调度器维护。若所有任务阻塞，内核可能运行 Idle 任务或进入低功耗状态。

### Q2：就绪任务为什么没有运行？

它可能被更高优先级任务持续抢占，也可能处于调度器暂停、临界区或多核调度限制期间。应观察就绪等待时长、优先级、当前任务和中断负载，而不是只检查任务是否“Ready”。

### Q3：阻塞和挂起有什么本质区别？

阻塞表示等待可描述的条件，通常可由事件或超时自动解除；挂起是显式从调度中移除，通常需要显式恢复。把挂起当作通用等待方式，容易造成永久停顿和资源泄漏。

### Q4：`vTaskDelay()` 后任务进入什么状态？

通常进入延时等待状态，在期限到达后转为就绪，而不是直接变为运行。到期时若有更高优先级任务在运行，延时任务仍要等待调度。

### Q5：任务删除后内存是否立即释放？

取决于 RTOS 实现和删除上下文。某些内核会由 Idle 任务回收自删除任务的 TCB 和栈。应核对所用版本的删除路径，并确保 Idle 任务有机会运行。

### Q6：能否通过查询任务状态决定是否发送事件？

不建议。状态查询是瞬时快照，查询后状态可能改变，存在竞态。发送事件应依据协议本身，并使用有明确定义的队列、通知或同步对象语义。

### Q7：任务的业务状态能否直接等同于 RTOS 状态？

不能。RTOS 状态描述调度资格；业务状态描述模块工作阶段。一个业务上处于“等待连接”的任务，可能是阻塞、就绪或运行。两类状态应分别建模。

## 13. 课程核心总结

- **就绪、运行、阻塞、挂起、删除描述不同的调度与生命周期语义。**
- 任务从阻塞转为就绪后，不保证立刻运行；还需要调度器选中。
- 阻塞用于等待条件，挂起用于显式控制任务参与调度，两者不能混用。
- 状态查询是诊断工具，不是线程间同步机制。
- 用事件、队列、通知等表达工作条件，用任务内部状态机表达业务生命周期。
- 删除、暂停、恢复都必须同时考虑锁、外设、缓冲区和内存回收。
- **工程上最重要的状态指标是：任务为什么进入当前状态、持续多久、由什么事件离开。**

## 16. 实践与进阶路径

### 梯度实战任务

1. 创建一个事件驱动任务，用任务通知阻塞等待，并记录每次阻塞、唤醒和运行时间。
2. 为队列接收增加有限超时，注入生产者故障，验证错误检测与恢复路径。
3. 对比忙等、短周期延时和事件阻塞的 CPU 占用与唤醒延迟。
4. 实现维护模式状态机，验证任务停止时无锁、DMA 或缓冲区泄漏。
5. 使用 trace 工具找出长期就绪、长期运行和异常频繁唤醒的任务。

### 性能与行为测试方法

- 统计状态转换次数、阻塞时间、就绪等待时间和任务运行时间。
- 分别测试正常负载、突发负载、队列满、超时和任务重建路径。
- 记录最长中断关闭时间、调度器暂停时间和事件到任务运行的最大延迟。
- 使用 trace hook 或 GPIO 测量，并考虑插桩开销。
- 将状态迁移覆盖率和异常路径测试纳入回归测试。

- 深入研究优先级反转、优先级继承与任务阻塞时间分析。
- 学习响应时间分析、最坏执行时间（WCET）和实时任务可调度性。
- 研究多核 RTOS 中跨核唤醒、任务迁移与状态同步。
- 使用 SystemView、Tracealyzer 或 ETM 分析任务状态与调度时序。
