
> 本课面向已完成基础移植的系统，覆盖 **FreeRTOS、RT-Thread、embOS、Zephyr**。目标不是证明“能编译、能启动”，而是用可重复的测试证据，证明移植在目标硬件、目标负载和故障条件下满足功能、实时性、内存、安全与可靠性要求。
> 
> 不同 RTOS 的内部接口和测试工具各有差异。本课优先使用各系统的公开 API、目标端口文档和板级测试；embOS 的具体配置与测试接口以对应版本手册和授权包为准。

# 1. 学习目标

## 理解

- 理解移植验证与应用功能测试、系统集成测试、认证测试之间的区别。
- 理解移植验收的五个核心维度：启动与调度、中断与时基、内存与栈、并发与同步、性能与长期可靠性。
- 理解为什么“测试通过一次”不能证明移植正确。
- 理解主机仿真、目标板测试、硬件在环测试和故障注入各自能覆盖的风险。

## 掌握

- 能建立 RTOS 移植测试计划、需求追踪矩阵和验收门槛。
- 能编写启动、线程切换、Tick、ISR、同步对象、栈和内存测试。
- 能使用 DWT、GPIO、逻辑分析仪、map 文件和故障寄存器获取测试证据。
- 能为 FreeRTOS、RT-Thread、embOS、Zephyr 选择合适的测试入口。
- 能区分功能正确、时序满足、内存安全和长稳运行四类测试结果。

## 精通

- 能设计最坏负载、竞争条件、优先级反转、Tick 丢失和内存耗尽等压力场景。
- 能量化中断延迟、任务响应时间、切换开销、栈峰值和内存余量。
- 能构建故障注入和错误恢复测试，验证系统不是只在正常路径工作。
- 能识别测试本身引入的测量开销、扰动和盲区。

## 能够设计

- 能为量产 RTOS 制定可审计、可复现的移植验收规范。
- 能将移植测试纳入持续集成、硬件在环和版本升级回归。
- 能基于系统安全等级设计测试深度、覆盖率和故障恢复要求。
- 能形成可追踪的最终交付证据：源码版本、工具链、配置、测试结果和性能基线。

# 2. 前置要求

## 知识要求

- 目标 RTOS 的线程/任务、调度、Tick、同步对象和中断规则。
- 目标 MCU 的异常模型、NVIC、中断优先级和时钟树。
- 编译器 ABI、链接脚本、map 文件和栈布局。
- 并发基础：竞态、死锁、优先级反转、原子性和内存屏障。
- 性能分析基础：周期计数、响应时间、抖动和分位数。

## 技能要求

- 能构建、下载和调试目标固件。
- 能使用 J-Link、CMSIS-DAP 或厂商调试器。
- 能分析 ELF、map 文件、寄存器和 HardFault 信息。
- 能使用逻辑分析仪或示波器测量 GPIO 时序。
- 能在目标板上运行持续压力测试，并导出日志或统计结果。
- 能在测试固件中注入超时、分配失败、队列满和设备错误。

# 3. 技术概述

## 3.1 移植验证到底验证什么

RTOS 移植验证不是单一的“内核 API 测试”，而是验证以下链路是否闭合：

```
复位和启动
  -> CPU/时钟/内存初始化
  -> 内核初始化
  -> 第一个线程启动
  -> Tick 和超时
  -> 调度和上下文切换
  -> 中断与内核协作
  -> 驱动和设备
  -> 资源边界和错误处理
  -> 长期稳定运行
```

若其中任何一环未验证，系统可能只是在当前测试路径下“看起来正常”。

## 3.2 验证层次

|层次|主要目标|常用方法|
|---|---|---|
|静态检查|配置、符号、内存布局正确|编译检查、map、静态分析|
|单元测试|算法和模块行为正确|主机测试、仿真、测试桩|
|内核集成测试|调度、Tick、同步正确|多线程目标板测试|
|硬件集成测试|时钟、异常、驱动、DMA 正确|目标板和外设测试|
|性能测试|延迟、抖动和资源满足预算|DWT、GPIO、trace|
|稳定性测试|长时间运行和压力下不退化|soak test、资源监控|
|故障注入|错误路径安全且可恢复|超时、内存耗尽、设备故障|
|量产验收|版本和环境可复现|CI、HIL、发布清单|

## 3.3 测试证据的原则

每项测试应记录：

```
测试目的
目标硬件和板卡版本
RTOS 版本/commit
CPU port 和编译器
编译选项
配置文件
输入条件和负载
测量工具和精度
测试步骤
通过标准
结果和日志
异常样本
```

没有这些信息，性能数字和“通过”结论难以复现。

# 4. 核心特性横向对比

## 4.1 四类 RTOS 的验证入口对比

|RTOS|配置证据|内核测试入口|常见资源观测|重点验证|
|---|---|---|---|---|
|FreeRTOS|`FreeRTOSConfig.h`、port|官方 demo、单元测试、应用测试|栈高水位、heap API、trace|port、ISR 优先级、Tick、heap|
|RT-Thread|`rtconfig.h`、BSP、组件配置|内核测试、FinSH/MSH、BSP 测试|线程信息、堆统计、对象状态|BSP 初始化、设备框架、自动初始化|
|embOS|版本手册、CPU port、工程配置|官方示例和授权测试包|版本支持的任务/栈/Trace 工具|CPU port、Tick、授权包和工具链一致性|
|Zephyr|`.config`、最终 DTS、west manifest|`twister`、ztest、sanitycheck|thread analyzer、map、shell stats|Kconfig/Devicetree、设备 ready、模块版本|

## 4.2 测试环境对比

|环境|擅长发现|不擅长发现|
|---|---|---|
|主机单元测试|算法错误、边界条件、状态机逻辑|MCU 异常、真实时序、DMA/Cache|
|QEMU/指令级模拟|部分启动和软件流程|板级时钟、真实中断抖动、电气问题|
|目标板测试|端口、时钟、驱动、内存和时序|大规模自动化成本高|
|硬件在环 HIL|外部接口、负载和故障恢复|测试覆盖设计不当时仍有盲区|
|逻辑分析仪/示波器|硬件边沿和实时延迟|内部调度状态和逻辑原因|
|Trace 工具|线程切换、阻塞、CPU 占用|Trace 本身可能扰动时序|

# 5. 底层原理与功能特性深度解析

## 5.1 建立移植测试基线

测试前先冻结测试基线：

```
硬件：
  MCU、板卡版本、晶振、调试器、外设连接

软件：
  RTOS 版本/commit、CPU port、BSP、驱动版本

工具链：
  编译器、链接器、调试器版本

构建：
  编译选项、链接脚本、RTOS 配置、生成镜像 hash

运行：
  主频、Tick 频率、任务配置、启用组件
```

每次改变以下任一项，都应执行相关回归：

- RTOS 版本。
- CPU port。
- 编译器或优化级别。
- FPU ABI。
- Tick 频率。
- 中断优先级。
- 链接脚本。
- 线程栈。
- DMA 或 Cache 配置。
- 低功耗配置。

## 5.2 启动和异常向量验证

### 测试目标

- 复位向量指向正确入口。
- 向量表基地址正确。
- MSP 和 PSP 初值有效。
- 内核启动函数只执行一次。
- SVC、PendSV、SysTick 或对应异常入口指向正确实现。
- 默认异常处理器未意外接管 RTOS 异常。

### 静态检查

```
arm-none-eabi-nm -n firmware.elf
arm-none-eabi-objdump -h firmware.elf
arm-none-eabi-objdump -d firmware.elf
```

检查：

- 向量表段地址。
- `Reset_Handler` 地址。
- PendSV/SVC/SysTick 最终符号。
- `.data`、`.bss`、堆和栈范围。
- `VTOR` 的运行时值。

### 目标板检查

在启动早期读取并记录：

```
volatile uint32_t debug_vtor;
volatile uint32_t debug_msp;
volatile uint32_t debug_psp;

static void capture_startup_state(void)
{
    debug_vtor = SCB->VTOR;
    __asm volatile ("mrs %0, msp" : "=r"(debug_msp));
    __asm volatile ("mrs %0, psp" : "=r"(debug_psp));
}
```

### 通过标准示例

- 连续冷启动 100 次，无异常启动失败。
- 看门狗复位后可恢复到预期状态。
- 异常入口符号与目标 port 一致。
- `VTOR`、MSP、PSP 均位于有效地址范围。

次数和门槛应根据产品风险等级制定。

## 5.3 首线程和上下文切换验证

### 基本测试

创建：

- 高优先级周期线程。
- 中优先级事件线程。
- 低优先级后台线程。

验证：

- 第一个线程能进入入口函数。
- 阻塞后其他线程获得运行机会。
- 高优先级线程唤醒后能按策略抢占。
- 同优先级时间片行为符合配置。
- 线程退出和删除行为符合 API 约定。
- 线程栈没有越界。

### 线程切换压力测试

```
static volatile uint32_t count_a;
static volatile uint32_t count_b;

static void task_a(void *arg)
{
    ARG_UNUSED(arg);

    for (;;) {
        count_a++;
        k_yield(); /* Zephyr 示例 */
    }
}

static void task_b(void *arg)
{
    ARG_UNUSED(arg);

    for (;;) {
        count_b++;
        k_yield();
    }
}
```

不同 RTOS 的 `yield` API 不同。测试重点不是 API 名称，而是：

- 两个线程都得到运行机会。
- 计数没有异常回退或破坏。
- 长时间切换后状态仍正确。
- 优先级关系符合预期。

不要用上述忙循环作为最终性能测试，因为它会造成最大 CPU 占用并掩盖真实阻塞场景。

### FPU 上下文测试

若启用 FPU：

```
static volatile float fp_result_a;
static volatile float fp_result_b;

static void fp_task_a(void *arg)
{
    float x = 1.0f;

    for (;;) {
        x = x * 1.0001f + 0.003f;
        fp_result_a = x;
        yield_or_sleep();
    }
}
```

另一个线程使用不同数据路径。验证：

- 两个线程浮点状态互不污染。
- 中断嵌套中使用浮点时符合平台策略。
- 优化等级和 ABI 改变后回归通过。

## 5.4 Tick 和超时验证

### Tick 精度测试

设置 GPIO：

```
void tick_test_thread(void *arg)
{
    ARG_UNUSED(arg);

    for (;;) {
        gpio_pin_toggle_dt(&test_pin);
        sleep_for_one_second();
    }
}
```

使用示波器或逻辑分析仪测量：

- 平均周期。
- 最大/最小周期。
- 短期抖动。
- 长期漂移。
- 主频切换前后的变化。

### 时间误差分解

```
观测周期误差 =
    时钟源误差
  + 分频量化误差
  + ISR 延迟
  + 线程调度延迟
  + 测量仪器误差
```

线程周期任务用 `sleep`/`delay` 测量时，测到的不只是 Tick 精度，还包括调度和线程执行时间。要测纯 Tick，应在 Tick ISR 或独立硬件定时器边沿测量。

### 超时边界测试

测试：

- 超时为 0。
- 最小可表示超时。
- 跨 Tick 边界。
- 长超时和计数回绕。
- 线程在超时前后被唤醒。
- 多个线程同时超时。
- Tickless 睡眠前后的超时补偿。

特别关注：

- Tick 计数溢出。
- 取整造成的提前或延后。
- 超时和外部事件同一时刻到达时的竞争语义。

## 5.5 中断与线程协同测试

### 基本 ISR 唤醒测试

```
定时器或 GPIO 外部事件
  -> ISR 记录时间戳
  -> ISR 释放同步对象/提交消息
  -> 高优先级线程被唤醒
  -> 线程记录时间戳
```

记录：

```
t0：硬件事件
t1：ISR 入口
t2：ISR 结束
t3：目标线程开始执行
```

派生指标：

```
中断入口延迟 = t1 - t0
ISR 执行时间 = t2 - t1
中断到线程响应 = t3 - t0
线程调度延迟 = t3 - t2
```

### 中断优先级测试

设计两类 ISR：

- 不允许调用 RTOS API 的高优先级 ISR。
- 允许调用 ISR API 的普通优先级 ISR。

验证：

- 高优先级 ISR 不访问内核对象。
- 普通 ISR API 使用符合端口约束。
- 内核临界区期间，各优先级 ISR 的行为符合预期。
- ISR 嵌套计数和中断退出调度正确。

不同 RTOS 的约束不完全相同，尤其是 FreeRTOS Cortex-M 的 `BASEPRI` 规则、RT-Thread 端口的中断上下文要求、embOS ISR API 限制和 Zephyr 的中断管理策略，必须按目标 port 分别验证。

## 5.6 同步对象和竞争测试

至少覆盖：

- 信号量重复释放。
- 队列满和空。
- 消息长度边界。
- 多生产者、多消费者。
- 线程删除时仍在等待。
- 超时与释放同时发生。
- 互斥锁嵌套。
- 优先级继承。
- 递归锁配置。
- 事件位清除语义。
- ISR 与线程并发读写。

### 优先级反转测试

构造：

```
低优先级 L 持有互斥锁
中优先级 M 持续运行
高优先级 H 请求该锁并阻塞
```

若启用优先级继承，应验证：

- L 临时提升到足够优先级。
- L 能及时释放锁。
- H 随后获得锁。
- M 不会无限期阻塞 H。

测试记录：

```
H 请求锁时间
L 获得/释放锁时间
H 获得锁时间
M 占用 CPU 时间
```

不要只用日志判断优先级继承，应使用 GPIO、Trace 或周期计数。

## 5.7 栈边界和内存测试

### 栈测试

对每个线程记录：

|线程|配置栈|测试峰值|余量|测试负载|
|---|---|---|---|---|
|控制线程||||最大控制路径|
|通信线程||||最大报文和错误路径|
|日志线程||||最大格式化输出|
|空闲线程||||Hook/低功耗路径|

测试应覆盖：

- 最大调用深度。
- 递归或深层协议解析。
- 浮点和 libc 路径。
- 错误处理路径。
- 中断嵌套。
- 日志输出。
- 低功耗进入和恢复。
- 调试和量产编译配置。

### 堆和内存池测试

启用动态内存时验证：

- 最小分配。
- 最大分配。
- 碎片化模式。
- 长时间分配/释放。
- 多线程并发分配。
- 失败注入。
- 内存池耗尽。
- 双重释放和越界检测策略。

故障注入不要在生产固件中保留可被外部触发的任意内存破坏接口。测试钩子应通过专用测试配置控制。

## 5.8 低功耗与动态时钟测试

若系统使用 tickless 或动态调频，测试：

- 进入低功耗前没有待处理设备事务。
- 低功耗期间 Tick 计数补偿正确。
- RTC/LPTIM 误差符合需求。
- 外部唤醒源在睡眠切换边界不会丢失。
- 时钟恢复后 UART、SPI、I2C 和 DMA 正常。
- 看门狗在睡眠期间策略正确。
- 动态主频变化后 Tick 和通信波特率更新。

建议测量：

```
睡眠时间设定值
实际睡眠时间
唤醒延迟
系统时间误差
恢复后首个任务响应时间
睡眠电流和运行电流
```

## 5.9 故障处理和 HardFault 验证

验证系统能记录：

- 复位原因。
- 故障寄存器。
- 堆栈帧中的 PC/LR/xPSR。
- 当前线程 ID/名称。
- 当前中断号。
- MSP 和 PSP。
- 最近错误码和状态机阶段。

Cortex-M 常见寄存器包括：

```
CFSR
HFSR
MMFAR
BFAR
AFSR
ICSR
SHCSR
```

故障记录应避免依赖故障时不可靠的 UART 输出。可采用：

- 预分配 `.noinit` RAM 区域。
- 独立备份寄存器。
- Flash 循环日志。
- 看门狗前短路径记录。
- 上电后由诊断任务导出。

# 6. 性能量化分析

## 6.1 量化数据的报告格式

每份报告至少包含：

```
MCU 和板卡
RTOS 版本/commit
编译器和优化
CPU 频率
Tick 频率
FPU/Cache/MPU 状态
任务和 ISR 配置
日志和 Trace 配置
测量设备和精度
采样次数
平均、最大、P95/P99
测试负载
```

## 6.2 调度和中断指标

### 上下文切换时间

```
T_switch = (cycle_end - cycle_start) / f_cpu
```

若 `f_cpu = 120 MHz`，测得 `600 cycles`：

```
T_switch = 600 / 120,000,000
         = 5 us
```

这只是示例换算，不代表任何 RTOS 的通用性能。

### Tick CPU 占用

```
U_tick = C_tick × f_tick / f_cpu
```

例如：

```
C_tick = 1000 cycles
f_tick = 1000 Hz
f_cpu = 100 MHz

U_tick = 1.0%
```

### 上下文切换 CPU 占用

```
U_switch = C_switch × f_switch / f_cpu
```

### 中断到线程延迟

```
T_irq_to_thread = t_thread_start - t_external_event
```

应分别报告：

- 最小延迟。
- 平均延迟。
- 最大延迟。
- P95/P99。
- 压力负载下最大延迟。

## 6.3 延迟测试方法

### DWT 方法

```
static void dwt_enable(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->CYCCNT = 0U;
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;
}

static uint32_t dwt_read(void)
{
    return DWT->CYCCNT;
}
```

注意：

- 先测量 DWT 读写开销。
- 注意计数器回绕。
- 中断和任务间共享时间戳时要保证读写原子性。
- 测量临界区本身会扰动时序。
- 复杂路径建议用 GPIO 和外部仪器复核。

### GPIO 方法

```
void test_isr(void)
{
    gpio_set(TEST_PIN);
    service_interrupt();
    gpio_clear(TEST_PIN);
}

void test_thread(void)
{
    wake_from_isr();
    gpio_set(RESPONSE_PIN);
    process_event();
}
```

逻辑分析仪可以观察：

- ISR 入口和出口。
- ISR 到任务的延迟。
- 高优先级中断对任务响应的影响。
- 睡眠和唤醒时序。

## 6.4 响应时间分析

简化固定优先级响应时间公式：

```
R_i = C_i + B_i + Σ ceil(R_i / T_j) × C_j
```

其中：

- `R_i`：任务 i 的响应时间。
- `C_i`：任务 i 的执行时间。
- `B_i`：低优先级资源导致的最大阻塞时间。
- `T_j`：高优先级任务 j 的周期。
- `C_j`：高优先级任务 j 的执行时间。

实际系统还应加入：

- ISR 执行时间。
- 最大临界区。
- 调度和上下文切换开销。
- Cache miss。
- 总线争用。
- DMA 访问。
- 系统 Tick。
- 非周期突发事件。

## 6.5 长期稳定性指标

Soak test 应至少监控：

|指标|关注点|
|---|---|
|最小剩余堆|是否持续下降|
|最大连续空闲块|碎片化趋势|
|线程栈最小余量|是否随业务增长恶化|
|队列峰值|峰值是否接近容量|
|丢包/溢出计数|是否逐渐增长|
|看门狗复位|是否发生异常重启|
|Tick 漂移|长期时间基准是否偏离|
|线程运行时间|是否出现异常高 CPU 占用|
|错误恢复次数|是否重复进入降级状态|
|Flash 写入次数|是否超出寿命预算|

## 6.6 测量风险和误差

|风险|影响|处理方式|
|---|---|---|
|测量代码过重|结果被测量开销污染|空测量扣除、GPIO 复核|
|调试器暂停|计时器和线程状态改变|关闭暂停或使用实时 trace|
|日志同步输出|延迟显著增加|单独测有/无日志两组|
|优化等级不同|代码路径变化|记录构建参数|
|Trace buffer 满|丢事件或反向压力|检查溢出计数和采样策略|
|Cache 状态不一致|测量不可比较|固定 Cache 配置|
|只看平均值|隐藏尾部延迟|报告最大值和高分位数|

## 8.3 四类 RTOS 的验证实践

### FreeRTOS

- 检查 `FreeRTOSConfig.h` 和目标 port。
- 启用 `configASSERT`、栈溢出检测和 malloc 失败钩子进行测试。
- 验证 `FromISR` API 和中断优先级边界。
- 使用栈高水位和 heap 统计。
- 根据版本运行官方 Demo/测试套件。
- 对 Tickless、FPU 和动态改频单独测试。

### RT-Thread

- 检查 `rtconfig.h`、BSP 和组件依赖。
- 验证自动初始化阶段及返回值。
- 验证设备注册、`device_is_ready` 等价状态、设备读写和错误恢复。
- 使用 FinSH/MSH 或测试组件采集线程和内存状态。
- 测试中断上下文宏、IPC 和设备框架交互。
- 对关闭组件后的初始化链重新做完整验证。

### embOS

- 以当前版本官方示例和测试工具为基准。
- 按对应手册检查 CPU port、ISR API、Tick 和栈。
- 记录 embOS 版本、工具链和授权包。
- 不以其他版本的内部接口编写测试。
- 用目标版本支持的 Trace/调试功能观察任务和时序。
- 任何端口或配置升级都进行完整回归。

### Zephyr

- 使用 `twister`、`ztest` 和目标板测试支持。
- 检查 `build/zephyr/.config` 和 `build/zephyr/zephyr.dts`。
- 检查设备 `device_is_ready()`。
- 使用 thread analyzer、日志和 tracing 观察栈和调度。
- 对 Board、SoC、overlay 和模块版本做 pristine build。
- 将 host native 测试与真实硬件测试分开记录。

# 9. 常见错误与避坑指南

## 9.1 错误一：只测试 `main()` 能运行

### 错误做法

看到串口输出或 LED 闪烁就宣布移植成功。

### 根因

这只覆盖了启动和单一线程路径，没有验证：

- 多任务切换。
- 中断唤醒。
- Tick 超时。
- 临界区。
- 线程栈。
- 资源耗尽。
- 长时间运行。

### 正确实现

至少完成：

```
启动
  -> 多线程
  -> Tick
  -> ISR 唤醒
  -> IPC 压力
  -> 内存/栈
  -> 设备和 DMA
  -> 长稳
```

### 风险影响

系统可能在实际多任务或高负载时才崩溃，问题已进入产品阶段。

## 9.2 错误二：只看平均延迟

### 错误做法

```
平均线程响应时间 = 20 us，所以满足 100 us 限制。
```

### 根因

平均值隐藏尾部延迟；高优先级中断、临界区、Cache miss 和总线竞争可能形成少量极慢样本。

### 正确实现

报告：

```
最小值
平均值
最大值
P95
P99
P99.9
压力场景最大值
```

同时记录样本数和测试持续时间。

### 风险影响

罕见超时可能触发安全保护或控制失稳。

## 9.3 错误三：用日志测时序

### 错误做法

在 ISR 和线程中调用 `printf()`，根据日志时间戳推断响应时间。

### 根因

格式化、锁、串口发送和缓冲会显著扰动时序；日志可能阻塞或丢失。

### 正确实现

使用：

- DWT 周期计数。
- GPIO 脉冲和逻辑分析仪。
- 硬件 Trace。
- 低开销二进制事件记录。

日志用于解释事件，不应作为高精度时序测量的主要工具。

### 风险影响

测试测到的是日志系统，不是 RTOS 的真实实时性能。

## 9.4 错误四：只在调试优化等级下测试

### 错误做法

仅使用 `-O0` 或调试配置验证后直接发布 `-O2` 固件。

### 根因

优化会改变：

- 内联和调用栈。
- 变量生命周期。
- 时序。
- 汇编代码。
- FPU 使用。
- 栈峰值。
- 竞态窗口。

### 正确实现

至少验证：

```
开发调试配置
量产优化配置
启用/关闭 LTO 的差异（若量产使用 LTO）
目标 FPU ABI
```

### 风险影响

调试版稳定，量产优化版却出现随机异常。

## 9.5 错误五：测试中关闭断言和栈检查

### 错误做法

为了让性能数字更好看，在所有测试配置中都关闭检查。

### 根因

将性能微基准和可靠性测试混为一谈。

### 正确实现

使用两组构建：

```
诊断构建：
  断言、栈检测、Trace、错误日志开启

性能构建：
  与量产配置一致，只保留低扰动测量工具
```

两组结果分别报告，不用性能构建替代可靠性验证。

### 风险影响

测试无法发现配置错误、栈溢出和内核断言问题。

## 9.6 错误六：忽略测试工具和探针的时序扰动

### 错误做法

在所有 ISR 中加入大量 GPIO、日志和 Trace 事件，再将结果当作产品性能。

### 根因

测量点改变了代码路径和总线行为。

### 正确实现

- 使用最小埋点。
- 量测空埋点开销。
- 对比开/关探针结果。
- 用外部仪器复核。
- 单独记录测试构建和量产构建差异。

### 风险影响

测量结果保守过度或虚假乐观，难以用于实时性证明。

## 9.7 错误七：只测正常路径，不测失败路径

### 错误做法

只测试队列有空间、设备正常、内存充足的情况。

### 根因

现场故障通常来自资源耗尽、异常输入和状态竞争。

### 正确实现

主动注入：

- 队列满。
- 堆耗尽。
- DMA timeout。
- UART 溢出。
- 设备未就绪。
- Flash 写入失败。
- Tick 延迟。
- 线程栈接近边界。
- 外部中断风暴。

验证系统进入安全降级，而不是死锁或破坏内核状态。

### 风险影响

系统只能在理想环境运行，实际故障无法恢复。

## 9.8 错误八：测试不同 RTOS 时使用不同负载

### 错误做法

FreeRTOS 测简单 GPIO，Zephyr 测网络满载，然后对比性能。

### 根因

测试负载、优化、日志和设备配置不一致，结果没有可比性。

### 正确实现

统一：

```
硬件
主频
编译器和优化
Tick
任务数量和优先级
同步模式
日志配置
测试输入
采样方法
统计口径
```

并明确哪些差异无法统一，例如驱动框架和内核特性。

### 风险影响

得到错误的 RTOS 性能结论和选型决策。

# 10. 多机制组合使用方案

## 10.1 端到端 ISR 唤醒延迟测试

目标：同时验证硬件中断、ISR、内核通知和线程调度。

```
外部定时器输出脉冲
  -> MCU 外部中断
  -> ISR 记录 t_irq
  -> ISR 通知高优先级线程
  -> ISR 退出
  -> 高优先级线程记录 t_task
  -> GPIO 输出响应脉冲
```

示意代码：

```
static volatile uint32_t irq_cycles;
static volatile uint32_t task_cycles;

void TEST_EXTI_IRQHandler(void)
{
    clear_test_irq();

    irq_cycles = DWT->CYCCNT;

    /*
     * 替换为目标 RTOS 对应的 ISR-safe 通知机制：
     * FreeRTOS: FromISR API
     * RT-Thread: 版本允许的 ISR 语义
     * embOS: 当前版本文档规定的 ISR API
     * Zephyr: ISR 可用的内核 API
     */
    notify_test_thread_from_isr();
}

static void latency_test_thread(void *arg)
{
    ARG_UNUSED(arg);

    for (;;) {
        wait_for_test_event();

        task_cycles = DWT->CYCCNT;
        gpio_set_response_pin();
        record_latency(task_cycles - irq_cycles);
        gpio_clear_response_pin();
    }
}
```

### 10.1.1 测试边界

该方法测量的是 ISR 到线程运行之间的时间，不完全等于外部事件到线程响应。若要测端到端响应，应使用外部脉冲或硬件捕获时间戳。

### 10.1.2 负载组合

分别执行：

- 空载。
- 多个低优先级线程持续运行。
- 高频低优先级中断。
- 最大日志输出。
- 网络/串口突发。
- 临界区压力。
- FPU 任务运行。
- Cache 开启。
- 低功耗唤醒。

## 10.2 故障注入与恢复测试框架

建议把故障注入分为三层：

```
硬件故障：
  外设断线、DMA error、时钟失败

内核/资源故障：
  队列满、内存耗尽、线程超时

应用故障：
  非法消息、状态机异常、升级中断
```

统一记录：

```
struct test_fault_record
{
    uint32_t test_id;
    uint32_t timestamp;
    int32_t error_code;
    uint32_t recovery_state;
    uint32_t reset_reason;
};
```

测试框架应确保：

- 故障注入只在测试配置启用。
- 故障接口不可被量产外部接口意外调用。
- 故障后系统状态可观察。
- 测试重复运行结果一致。
- 复位后可读取故障记录。

# 11. 工业级实际案例分析

## 11.1 案例一：电机控制器的 RTOS 移植验收

### 需求

- 20 kHz 控制环。
- ADC/PWM 硬件同步。
- 安全中断低延迟。
- 通信任务和诊断任务并行。
- 故障时关闭输出并记录原因。

### 验证架构

```
硬件比较器/故障输入
  -> 安全 ISR
  -> PWM 立即关断

定时器/ADC
  -> DMA
  -> 控制处理线程
  -> PWM 更新

通信 ISR
  -> 缓冲区/通知
  -> 通信线程

诊断线程
  -> 状态统计和故障记录
```

### 测试项

- 从外部故障输入到 PWM 关断的硬件延迟。
- ADC DMA 完成到控制计算启动的响应时间。
- 控制线程最大执行时间和最坏抖动。
- 通信突发期间的控制周期。
- 高优先级中断嵌套。
- FPU 上下文隔离。
- 控制线程栈高水位。
- 电机故障和通信故障并发时的状态机行为。

### 验收重点

控制安全路径不能依赖一般日志或普通任务调度。测量最大响应时间，并对故障关断路径做硬件级验证。

## 11.2 案例二：工业网关长期运行验证

### 需求

- 以太网、CAN、多个 UART 同时工作。
- 网络突发和 OTA。
- 设备运行数月。
- 不能因短期内存压力导致复位。

### 测试负载

- 以太网持续吞吐。
- CAN 高总线负载。
- UART 连续收发。
- 文件系统周期写入。
- OTA 下载中断和恢复。
- 日志高峰。
- 设备热插拔或线路断开。
- 网络抖动和远端无响应。

### 监控指标

- 最小 heap 和最大连续空闲块。
- 网络 pool 最小余量。
- 各队列最大深度。
- DMA 错误和丢包。
- 看门狗复位计数。
- 线程运行时间。
- Flash 写入失败。
- 文件系统错误恢复次数。

### 验收重点

运行期间不仅要求没有复位，还应确认资源指标没有单调恶化。每隔固定时间保存统计，观察堆、队列和栈趋势。

## 11.3 案例三：低功耗传感节点的唤醒验证

### 需求

- 深睡眠时功耗低。
- RTC 每 30 秒唤醒。
- GPIO 告警可异步唤醒。
- 唤醒后采样、存储并继续睡眠。

### 测试项

- 设定睡眠时间与实际睡眠时间差。
- RTC 时间长期漂移。
- GPIO 在睡眠切换窗口触发时是否丢失。
- 外设时钟恢复时间。
- 首个线程运行延迟。
- 唤醒后第一次 SPI/I2C/DMA 是否成功。
- 看门狗和复位原因。
- 电池低压时的时钟和唤醒稳定性。

### 验收重点

低功耗测试不仅是测电流，还要验证时间基准和所有唤醒路径。睡眠电流合格但唤醒丢事件，仍属于移植失败。

# 12. 高频问题深度答疑

## Q1：移植验证最少要测哪些内容？

最低集合应包括：

```
启动和首线程
多线程切换
Tick 和超时
ISR 唤醒线程
同步对象并发
任务栈边界
内存失败路径（若启用动态内存）
目标设备初始化
目标编译配置下的实时性
长时间压力运行
```

如果使用 FPU、DMA、Cache、MPU、低功耗或 TrustZone，还需单独验证对应机制。

## Q2：主机单元测试通过，能否说明 RTOS 移植正确？

不能。主机测试适合验证应用算法、状态机和协议逻辑，但不能替代：

- 异常入口。
- Cortex-M 栈布局。
- NVIC 优先级。
- 实际 Tick 时钟。
- DMA 和 Cache。
- 硬件中断延迟。
- 低功耗时钟。

需要目标板测试或可证明覆盖这些机制的硬件仿真。

## Q3：如何选取压力测试时长？

由风险和运行场景决定。短时压力适合发现启动、死锁和高频竞态；长稳测试用于发现：

- 内存泄漏。
- 堆碎片。
- 计数溢出。
- 长期时钟漂移。
- 文件系统累积错误。
- 低概率调度竞态。

对网关、记录仪、工业控制器，建议至少覆盖远长于正常单次运行周期的测试，并结合历史故障率和发布要求设定时长。

## Q4：最大延迟是否可信？

只有在输入场景覆盖充分、测量点可靠、采样数量足够且测试条件明确时，最大值才有意义。最大值是已观察到的样本最大值，不自动等价于数学意义上的最坏执行时间。

要进一步提高可信度：

- 静态分析任务执行时间。
- 计算最高优先级干扰。
- 覆盖所有 ISR 嵌套组合。
- 测试 Cache 冷/热状态。
- 测试总线和 DMA 争用。
- 对测量误差留出余量。

## Q5：为什么测试中通过，量产后仍然出现栈溢出？

常见原因：

- 测试输入没有覆盖深调用路径。
- 量产优化不同。
- 量产打开浮点或格式化路径。
- 量产线程优先级不同。
- 中断嵌套层次更深。
- 量产日志或错误路径不同。
- 芯片批次、时钟或温度使行为变化。
- 栈水位测试只在短时间内进行。

应使用量产编译配置完成栈压力测试，并保留明确安全余量。

## Q6：如何测试优先级反转？

构造低优先级线程持有锁，中优先级线程持续运行，高优先级线程等待锁。比较：

- 开启/关闭优先级继承。
- 高优先级线程等待时间。
- 低优先级线程释放锁时间。
- 中优先级线程 CPU 占用。

不要只依赖线程状态文本，要用时间戳、GPIO 或 Trace 测量。

## Q7：配置升级后需要全部重测吗？

不能只做编译检查。升级 RTOS、编译器、CPU port 或 Board 配置后，至少应重测受影响链路：

- 端口或异常变更：启动、切换、中断、栈。
- 时钟变更：Tick、超时、低功耗。
- 内存配置变更：堆、栈、失败注入。
- 驱动变更：设备初始化、DMA、Cache。
- 网络组件变更：吞吐、buffer、长期稳定性。
- 编译器变更：ABI、FPU、栈和性能。

产品级升级应执行完整回归。

## Q8：四类 RTOS 怎么做公平性能比较？

固定以下条件：

- 同一 MCU 和主频。
- 同一编译器及版本。
- 同一优化等级。
- 同一 FPU、Cache、MPU 配置。
- 同一 Tick。
- 同一任务数量和优先级。
- 同一 IPC 类型和数据量。
- 同一测量点。
- 同一统计方法。
- 同一日志和 Trace 设置。

同时明确比较对象是“裸内核”，还是“包含设备框架和组件的完整系统”。两种结果代表不同问题。

# 13. 课程核心总结

## 核心要点

1. 移植验证必须从启动覆盖到长期运行，不能止于“任务能跑”。
2. 必须分别验证功能、时序、资源、错误处理和长期稳定性。
3. 目标板测试不可由主机单元测试替代。
4. 平均延迟不足以证明实时性，应报告最大值和高分位值。
5. 测量本身会扰动系统，必须评估探针、日志和 Trace 的开销。
6. 错误路径必须主动注入，不能依赖偶然发生。
7. 量产编译配置本身必须被测试，不能只测试 `-O0` 调试版本。
8. 四类 RTOS 共用测试目标，但具体接口和中断规则必须按各自版本和 port 验证。
9. 长稳测试必须监控资源趋势，而不是只看是否复位。
10. 移植验收结果应可复现、可追踪、可审计。

## 性能排序说明

不存在固定的“哪个 RTOS 切换最快”结论。性能排序取决于：

```
CPU port
编译器和优化
Tick 频率
是否使用 FPU
临界区实现
内存模型
日志和 Trace
任务切换场景
测量方法
```

因此应在同一目标硬件和同一测试条件下测量，并将“内核切换测试”和“完整产品场景测试”分开报告。

# 16. 实践与进阶路径

## 16.1 梯度实战任务

### 任务一：移植 Smoke Test

完成：

- 冷启动。
- 首线程运行。
- Tick 计数递增。
- UART/调试接口输出测试状态。
- 看门狗不会误复位。

### 任务二：内核行为测试

创建多个线程验证：

- 高优先级抢占。
- 同优先级时间片。
- 阻塞和唤醒。
- 线程退出和恢复。
- 信号量、队列和互斥锁。
- ISR 唤醒线程。

### 任务三：性能测量

测量：

- Tick ISR 周期。
- 上下文切换周期。
- 中断入口延迟。
- ISR 执行时间。
- 高优先级线程响应延迟。
- 临界区最大长度。

使用 DWT 与 GPIO 两种方法交叉验证。

### 任务四：内存压力

测试：

- 最大线程数。
- 最大队列长度。
- 堆碎片。
- 内存池耗尽。
- 任务栈峰值。
- malloc 失败。
- 运行 24 小时以上的资源趋势。

### 任务五：故障注入

注入：

- 中断风暴。
- Tick 延迟。
- 队列满。
- DMA timeout。
- 设备初始化失败。
- 通信断线。
- Flash 写入失败。
- 低功耗唤醒失败。
- 看门狗复位。

每种故障都要验证诊断记录和恢复状态。

### 任务六：版本升级回归

分别升级：

- RTOS 版本。
- 编译器。
- CPU port。
- 芯片 SDK。
- Board 配置。

对比：

```
Flash/RAM
线程栈
Tick
切换时间
ISR 延迟
设备初始化
长稳结果
故障恢复
```

## 16.2 性能测试方法

推荐报告：


对严格实时系统，还应执行响应时间分析和最坏干扰组合分析，不能只依赖统计测试。
