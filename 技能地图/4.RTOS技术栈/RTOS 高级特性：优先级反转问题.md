- **理解**：理解优先级反转的定义、形成条件，以及它与普通任务阻塞、死锁的区别。
- **掌握**：掌握优先级继承、优先级天花板两种主要协议的工作机制、适用边界和常见实现差异。

- **能够设计**：能够为实时任务设计锁策略、锁顺序、超时与故障恢复方案，并通过压力测试验证截止时间。

## 3. 技术概述

**优先级反转**是指高优先级任务因等待低优先级任务持有的资源而阻塞，同时中优先级任务持续抢占低优先级任务，使高优先级任务的等待时间远超资源临界区本身的执行时间。

典型条件：

1. 低优先级任务 `L` 获得互斥资源 `R`。
2. 高优先级任务 `H` 请求 `R`，因此阻塞。
3. 中优先级任务 `M` 就绪并抢占 `L`。
4. `L` 无法运行并释放 `R`，导致 `H` 间接被 `M` 延迟。

这不是简单的“高优先级任务被低优先级任务挡住”。关键在于**第三个任务可以不断延长等待时间**。

需要区分：

- **有界阻塞**：低优先级任务在有限临界区内持锁，高优先级任务等待有上界。
- **无界反转**：中优先级任务可反复抢占持锁者，导致高优先级任务等待无可用上界。
- **死锁**：任务形成循环等待，通常即使没有中优先级任务也无法前进。
- **优先级反转**：存在资源等待和调度干扰，不一定形成循环等待，任务可能最终恢复。

主要解决方案：

- **优先级继承（PIP）** ：持锁任务临时继承最高等待者的优先级。
- **优先级天花板（PCP / Immediate Ceiling）** ：根据资源使用者优先级，提升持锁任务优先级，限制系统进入可能导致阻塞链的状态。
- **缩短临界区、分离资源、消息传递**：从架构上减少共享和持锁执行时间。
- **超时、故障恢复、监控**：限制故障或异常路径中的无限等待；它们不能代替正确的锁协议。

## 5. 底层原理与功能特性深度解析

### 5.1 经典反转时序

设优先级数值越大表示优先级越高：

```
时间  ───────────────────────────────────────────────────────────>

H:                 请求 R ─────── 阻塞等待 ─────────────── 获得 R
M:                             运行运行运行运行运行
L:   获得 R ────── 被 M 抢占 ─────────────── 恢复 ─ 释放 R
```

不使用继承时，`H` 被 `L` 阻塞；而 `L` 又被 `M` 抢占。若 `M` 的执行可持续到任意长，`H` 的响应时间便不再由 `L` 的临界区决定。

### 5.2 优先级继承的运行过程

PI mutex 的核心状态通常包括：

- mutex 当前所有者；
- 等待该 mutex 的任务集合或优先级有序队列；
- 所有者的基础优先级；
- 所有者因其他 mutex 继承的有效优先级；
- 锁释放时的重新计算和调度请求。

当 `H` 等待 `L` 持有的 mutex：

```
effective_priority(L) = max(base_priority(L), highest_waiter_priority)
```

调度器随后把 `L` 放入新的优先级就绪队列，或者更新其优先级索引。`L` 以继承后的优先级运行，尽快完成临界区并释放 mutex。释放后，内核通常根据 `L` 仍持有的其他 mutex 及其等待者重新计算有效优先级，而非无条件恢复基础优先级。

一个简化的源码级伪代码如下：

```
void mutex_lock(struct mutex *m)
{
    task_t *self = current_task();

    scheduler_lock();
    if (m->owner == NULL) {
        m->owner = self;
        self->held_mutex_count++;
        scheduler_unlock();
        return;
    }

    wait_queue_insert_by_priority(&m->waiters, self);
    self->state = TASK_BLOCKED;

    task_t *owner = m->owner;
    if (owner->effective_priority < self->effective_priority) {
        scheduler_requeue_with_priority(owner, self->effective_priority);
    }

    scheduler_unlock();
    schedule();
}

void mutex_unlock(struct mutex *m)
{
    task_t *self = current_task();

    scheduler_lock();
    assert(m->owner == self);

    if (!wait_queue_empty(&m->waiters)) {
        task_t *next = wait_queue_pop_highest(&m->waiters);
        m->owner = next;
        next->held_mutex_count++;
        next->state = TASK_READY;
        ready_queue_insert(next);
    } else {
        m->owner = NULL;
    }

    /* 按其余持有锁及等待链重新计算有效优先级。 */
    recompute_effective_priority(self);
    scheduler_unlock();
    schedule_if_higher_priority_ready();
}
```

这是用于解释的伪实现，不是可直接移植的内核代码。真实内核还必须处理超时撤销等待节点、任务删除、递归锁计数、锁释放顺序、嵌套继承链和中断安全。

### 5.3 嵌套锁与继承传播

若 `L` 持有 `A`，随后等待 `B`，而 `B` 由另一个任务持有，优先级继承可能沿等待链传播：

```
H 等待 A -> A.owner = L -> L 等待 B -> B.owner = X
```

为避免 `H` 被链中间的任务长期延迟，内核可能把高优先级一路传播到 `X`。这要求内核具备等待关系追踪和优先级重算逻辑。部分小型 RTOS 实现的继承能力只覆盖有限情况，使用前要核查实现和版本文档，尤其是多 mutex、超时和任务删除路径。

### 5.4 递归锁、二值信号量与 mutex 的差别

- **Mutex** 通常包含所有者身份，并可能具备优先级继承。
- **二值信号量**通常表达事件或计数，不保证所有者语义，也不一定支持继承。
- **递归 mutex**允许同一任务重复上锁，但必须按相同次数解锁。它不能解决跨任务死锁。
- **关调度器或关中断**不是 mutex 替代品。它们影响的是整个系统调度或中断响应。

### 5.5 Cortex-M 上的实现注意点

常见 RTOS 在 Cortex-M 上由 PendSV 完成任务上下文切换，SysTick 或其他定时器推进时间片与超时。mutex 获取通常在任务上下文中执行；ISR 不应阻塞等待 mutex。部分内核在调度器临界区内使用 `BASEPRI` 屏蔽一组可配置优先级的中断，但这与优先级继承是两套不同机制：

- `BASEPRI` 保护内核共享数据结构，控制哪些中断可以打断内核操作。
- PI 调整的是任务有效优先级，影响任务调度顺序。
- 不能因为内核使用了 `BASEPRI`，就认为应用层资源已避免优先级反转。

## 6. 性能量化分析

### 6.1 阻塞时间模型

对固定优先级、抢占式任务集，任务 `i` 的响应时间常用迭代式估算：

Ri=Ci+Bi+∑j∈hp(i)⌈RiTj⌉CjRi​=Ci​+Bi​+j∈hp(i)∑​⌈Tj​Ri​​⌉Cj​

其中：

- CiCi​：任务执行时间；
- BiBi​：任务因低优先级任务持锁产生的最大阻塞；
- hp(i)hp(i)：比任务 `i` 优先级高的任务集合；
- TjTj​、CjCj​：高优先级干扰任务的周期和执行时间。

如果最高优先级任务能被一个低优先级临界区阻塞，且该临界区长度为 LcsLcs​，则该锁产生的阻塞上界至少需要覆盖 LcsLcs​ 加锁释放及调度开销。若没有有效的继承/天花板协议，**不能简单把 BiBi​ 设为临界区长度**，因为中优先级干扰可能反复延长它。

### 6.2 可复核的示例计算

假设 MCU 上测得：

- 低优先级任务临界区 Lcs=120 μsLcs​=120 μs；
- mutex 获取、释放与唤醒合计开销约 8 μs8 μs；
- 中优先级任务周期 TM=1 msTM​=1 ms，执行时间 CM=300 μsCM​=300 μs；
- 高优先级任务本身执行时间 CH=80 μsCH​=80 μs。

若无 PI，`M` 在 `L` 持锁后就绪并执行 300 µs，则高优先级任务可能至少增加这段干扰；若中优先级任务以 1 ms 周期持续到达，最大延迟还取决于 `L` 能否在任务释放间隙运行，不能仅用 120 µs 估算。

使用正确 PI 后，`L` 临时升到 `H` 的优先级，经典三任务场景下 `M` 不再能抢占它。此时 `H` 的资源阻塞上界近似为：

BH≤Lcs+Cunlock/wakeup≈120+8=128 μsBH​≤Lcs​+Cunlock/wakeup​≈120+8=128 μs

该数字是基于上述假设的计算示例，不是某款 RTOS 的实测结果。实际值应在目标 MCU、编译器优化级别、时钟和 RTOS 版本上测量。

### 6.3 内存与 CPU 开销

- mutex 通常需要所有者指针、等待队列头、递归计数或协议标志；具体大小受 ABI 和 RTOS 结构影响。
- 等待队列采用链表时，每个等待任务通常需要一个等待节点或复用任务控制块中的事件节点。
- 优先级继承可能增加优先级变更、等待链传播和队列重排开销。
- 若按优先级数组维护就绪队列，重排代价可能是常数或与优先级数相关；若使用通用有序链表，则可能是 O(n)O(n)。
- 不能把“mutex 占用几十字节”当作通用常数；应以目标 RTOS 的 `sizeof`、映射文件和运行时高水位为准。

建议在目标平台测量：

1. 无竞争 mutex 的 lock/unlock 周期数。
2. 一任务等待、另一任务释放时的唤醒到运行延迟。
3. 继承、降级、嵌套锁传播的最坏路径时间。
4. 临界区内中断最大延迟及任务截止时间抖动。
5. 锁等待超时和任务删除路径的开销。

### 决策流程图

    |

    |   |

    |   |

    |       +-- RTOS 原生 mutex 是否确认支持优先级继承？

### 典型场景

|场景|推荐方案|理由|
|---|---|---|
|高频采集任务与低频配置任务共享寄存器影子|PI mutex 或单一所有者|避免高优先级采集任务被低优先级配置任务长期挡住|
|多任务访问日志串口|日志服务任务 + 有界队列|消除各业务任务对串口互斥的直接竞争，需设计队列满处理|

|ISR 与任务共享数据|原子操作、短临界区或双缓冲|ISR 不可阻塞等待 mutex；PI 不解决 ISR 与任务间的所有一致性问题|
|多把锁、资源依赖复杂的控制任务|限定锁顺序、资源 ceiling 或所有权重构|PI 可以缓解反转，但复杂锁图仍可能死锁或难以证明上界|
|文件系统或闪存擦写路径|专用存储任务 + 请求队列|擦写时间长且不可预知，避免高优先级实时任务直接持锁等待|

## 8. 工程最佳实践

### 设计原则

- 用 RTOS 的 **mutex** 保护任务间互斥资源，确认其是否实现 PI，以及哪些路径受支持。
- 临界区内只做必要的状态更新；不做阻塞 I/O、等待事件、动态内存分配或长时间轮询。
- 为每把锁定义所有者、保护对象、最大持有时间、获取超时和锁顺序。
- 多锁场景统一规定全局获取顺序，避免 `A -> B` 与 `B -> A` 并存。
- 驱动层负责资源同步，不要让上层业务代码自行拼接寄存器访问与解锁逻辑。
- 对长耗时硬件操作使用状态机或异步请求，不把硬件忙等待放进共享锁内。
- mutex 只能在任务上下文使用；中断服务程序不得阻塞获取 mutex。

### 选型决策矩阵

|条件|首选|补充检查|
|---|---|---|
|共享临界区短，任务优先级跨度大|PI mutex|测量最坏持锁时间和继承路径|
|共享资源长时间被占用|单一所有者任务/消息队列|队列容量、背压、取消和超时|
|多资源关系复杂且需严格阻塞上界|PCP/ceiling 或重构|RTOS 协议语义及证明模型|
|仅 ISR 与任务间共享少量状态|原子操作或短临界区|对齐、内存序、中断屏蔽窗口|
|访问失败必须快速返回|带超时 mutex|超时后的状态恢复与重试策略|

### 编码规范

- 使用封装函数成对管理 lock/unlock；所有错误和提前返回路径均须释放已获取锁。
- 断言 mutex 所有权或状态转换的前置条件。
- 将锁超时记录到可追踪日志或诊断计数器，但避免在持锁期间执行阻塞日志。
- 诊断数据应包含任务名、mutex 名、等待时长、持有者和调用点。
- 不通过手工修改任务优先级“模拟 PI”；这种做法容易在超时、异常和嵌套锁路径下无法恢复。

## 9. 常见错误与避坑指南

### 错误一：用普通二值信号量做互斥

错误代码：

```
if (xSemaphoreTake(binary_sem, portMAX_DELAY) == pdTRUE) {
    update_shared_state();
    xSemaphoreGive(binary_sem);
}
```

根因：二值信号量通常没有 mutex 所有者语义，也可能不支持优先级继承。

正确实现：若目标 FreeRTOS 配置和版本支持 PI，使用原生 mutex API；其他 RTOS 也应使用其 mutex 类型。

```
if (xSemaphoreTake(state_mutex, pdMS_TO_TICKS(20)) == pdTRUE) {
    update_shared_state();
    xSemaphoreGive(state_mutex);
} else {
    record_lock_timeout();
}
```

风险：高优先级任务可能被低优先级任务持锁造成的中优先级干扰长期延迟；误释放信号量还可能破坏同步语义。

### 错误二：在 mutex 临界区中执行阻塞 I/O

错误代码：

```
lock(bus_mutex);
spi_transfer_blocking(tx, rx, length);
unlock(bus_mutex);
```

根因：传输时长与外设状态、总线竞争或超时策略相关，锁持有时间可能远超设计预期。

正确实现：尽可能缩短锁内的总线配置和状态更新；对长事务使用总线管理器任务，或拆分为有明确最大时长的操作。若硬件传输必须独占总线，则制定事务最大长度和超时，并纳入响应时间分析。

风险：所有等待同一资源的高优先级任务都被阻塞；看门狗、控制环和通信超时可能连锁触发。

### 错误三：持锁后执行可能失败的早退路径未解锁

错误代码：

```
lock(mutex);
if (!device_ready()) {
    return ERROR_NOT_READY;
}
update_device_state();
unlock(mutex);
```

根因：错误路径遗漏释放，后续任务永久阻塞，常被误诊为优先级反转。

正确实现：

```
status_t update_device(void)
{
    status_t result = STATUS_OK;

    if (mutex_lock_timeout(&device_mutex, DEVICE_LOCK_TIMEOUT) != STATUS_OK) {
        return STATUS_TIMEOUT;
    }

    if (!device_ready()) {
        result = STATUS_NOT_READY;
        goto out;
    }

    update_device_state();

out:
    mutex_unlock(&device_mutex);
    return result;
}
```

风险：永久锁死资源；PI 只能提升仍能运行的持锁任务，无法修复丢失解锁导致的永久占用。

### 错误四：在 ISR 中等待 mutex

错误代码：

```
void DMA_IRQHandler(void)
{
    mutex_lock(&buffer_mutex);
    process_dma_buffer();
    mutex_unlock(&buffer_mutex);
}
```

根因：ISR 不能阻塞等待任务调度；若持锁者正等待该 ISR 完成，还可能形成不可恢复的依赖环。

正确实现：ISR 仅确认硬件状态并投递通知/缓冲区索引；任务上下文获取 mutex 并处理数据。若必须共享短状态，使用平台允许的短临界区或原子变量。

风险：内核断言、调度器状态损坏、丢失中断或死锁。

### 错误五：认为 PI 能解决死锁

错误代码：

```
Task A: lock(X); lock(Y)
Task B: lock(Y); lock(X)
```

根因：两个任务形成循环等待；提升优先级不会释放对方持有的锁。

正确实现：统一锁顺序，例如所有路径固定为 `X -> Y`；无法统一时采用避免嵌套锁的所有权设计。

风险：系统永久阻塞，且高优先级任务可能最终也被卷入等待链。

## 10. 多机制组合使用方案

### 协同架构

推荐的资源访问路径：

```
高优先级控制任务 ----+
                     +--> PI mutex --> 短状态更新区 --> 共享状态
低优先级配置任务 ----+

多个业务任务 --> 有界请求队列 --> 资源所有者任务 --> SPI/UART/Flash
                                  |
                                  +--> 超时、错误恢复、执行统计
```

- 对**短、确定、必须共享内存的临界区**：PI mutex。
- 对**长时、硬件依赖、吞吐量敏感的资源操作**：资源所有者任务和消息传递。
- 对**ISR 数据交接**：通知、无锁单生产者/单消费者队列或短临界区。
- 对所有路径：锁顺序、超时策略、持锁时间统计和故障诊断。

### 可复用的 C 框架

下面是与 RTOS 无关的接口框架，具体函数映射到目标 RTOS API。接口契约要求 `lock_timeout()` 对互斥资源使用具备 PI 的 mutex。

```
typedef enum {
    STATUS_OK = 0,
    STATUS_TIMEOUT,
    STATUS_IO_ERROR,
    STATUS_INVALID
} status_t;

typedef struct {
    mutex_t mutex;                 /* 必须使用具备 PI 的 RTOS mutex */
    uint32_t lock_timeout_ticks;
    atomic_uint timeout_count;
    atomic_uint io_error_count;
} shared_device_t;

status_t shared_device_update(shared_device_t *dev,
                              const update_request_t *request)
{
    status_t result;

    if ((dev == NULL) || (request == NULL)) {
        return STATUS_INVALID;
    }

    if (mutex_lock_timeout(&dev->mutex, dev->lock_timeout_ticks) != STATUS_OK) {
        atomic_fetch_add(&dev->timeout_count, 1U);
        return STATUS_TIMEOUT;
    }

    /* 临界区只更新内存状态，不等待外设，不执行阻塞日志。 */
    result = validate_request(request);
    if (result == STATUS_OK) {
        apply_request_to_shadow_state(request);
    }

    mutex_unlock(&dev->mutex);

    if (result != STATUS_OK) {
        return result;
    }

    /* 外设 I/O 通过资源所有者任务异步执行。 */
    if (device_request_submit(request) != STATUS_OK) {
        atomic_fetch_add(&dev->io_error_count, 1U);
        return STATUS_IO_ERROR;
    }

    return STATUS_OK;
}
```

关键边界：

- 队列提交失败后，不应假设外设操作已发生。
- 请求队列必须有容量上限和满队列策略。
- 如果 shadow state 已更新但提交失败，需要定义回滚、重试或“期望状态与实际状态分离”的语义。
- 原子计数器是否 lock-free 取决于目标 CPU 和编译器；要求硬实时的 ISR 路径需核验汇编与库实现。

## 11. 工业级实际案例分析

以下为典型工程模式，不代表某一特定厂商的内部实现。

### 案例一：电机控制器共享配置与控制参数

**需求**：1 kHz 电流环读取控制参数；低优先级通信任务更新目标值和限幅配置。

**架构**：控制参数采用双缓冲或版本化快照。通信任务写入非活动缓冲区，完成后原子切换索引；若必须保护少量共享元数据，使用短 PI mutex。

**核心代码思路**：

```
void control_config_publish(const config_t *cfg)
{
    uint32_t next = active_index ^ 1U;
    config_buffer[next] = *cfg;
    memory_barrier();
    atomic_store_explicit(&active_index, next, memory_order_release);
}

void current_loop_step(void)
{
    uint32_t index = atomic_load_explicit(&active_index, memory_order_acquire);
    config_t local = config_buffer[index];
    run_current_controller(&local);
}
```

**设计要点**：需确认平台原子操作和内存屏障语义；若配置结构较大或可能多写者并发，应使用序列锁、禁抢占短区或专用同步机制。不要让 1 kHz 控制环等待慢速通信任务持有的长锁。

### 案例二：共享 SPI 总线访问传感器与非易失存储

**需求**：高优先级传感器采样与低优先级参数持久化共享 SPI 控制器。

**架构**：SPI 总线由总线管理器任务独占。传感器任务提交带截止时间的高优先级请求；存储写入拆成有界片段，并在片段之间让出总线。

**设计要点**：PI mutex 只能保护总线寄存器配置和短事务，不能让长时间 Flash 擦写成为高优先级任务的阻塞源。为每个请求定义最大线缆占用时间、超时和取消行为；高优先级请求的队列优先策略也要避免低优先级请求饥饿。

### 案例三：工业通信设备的诊断日志

**需求**：多个任务记录日志，共享 UART；通信任务不能因日志输出卡住。

**架构**：业务任务将结构化日志写入有界无锁/短临界区队列，UART 日志任务统一串行化输出。队列满时丢弃低等级日志并增加计数，高等级故障记录使用独立保留槽或备用存储。

**设计要点**：不要在业务任务持有全局日志锁时等待 UART DMA 完成。日志队列的写入临界区必须有明确上界，日志任务优先级和带宽应避免反过来影响控制任务。

## 12. 高频问题深度答疑

### 1. 使用了优先级继承，就能保证高优先级任务实时吗？

不能。PI 只限制一种由低优先级持锁者和中优先级干扰构成的反转。任务仍会受到更高优先级任务、ISR、关中断区、多个锁链、非抢占内核区和硬件等待影响。必须把阻塞时间、执行时间、干扰项一起纳入响应时间分析。

### 2. PI 是否能完全消除优先级反转？

它能消除经典三任务场景中的无界延长，但不意味着阻塞为零。高优先级任务仍要等待持锁者完成临界区。复杂锁链、多 mutex 和超时撤销的行为取决于内核实现；需要查阅源码和配置。

### 3. 为什么不直接给低优先级任务设置最高优先级？

静态抬高整个任务优先级会让它在不持锁时也抢占其他任务，扩大干扰范围。PI 是有条件、随资源竞争变化的动态提升，并在适当时机恢复有效优先级。手动调整很容易在异常路径、嵌套锁和超时下泄漏优先级。

### 4. PI mutex 可以在中断中使用吗？

通常不可以。ISR 不能阻塞等待；而 mutex 的优先级继承依赖任务调度和任务所有者。ISR 与任务共享数据应使用适合中断上下文的原子操作、通知、无锁队列或短临界区。

### 5. PI 能解决死锁吗？

不能。PI 调整调度优先级，不改变资源依赖图。循环等待仍然存在。应通过全局锁顺序、禁止嵌套锁、资源所有者任务或锁依赖检查消除死锁。

### 6. 一定要加获取超时吗？

对于可恢复业务路径，通常应有超时或故障监控，但超时并非越短越好。过短会产生误报和重试风暴；过长会超出任务截止时间。依据锁的最坏持有时间、任务截止时间和故障策略确定。超时返回后必须保证状态一致，不能继续访问未保护的数据。

### 7. 如何证明某个 RTOS 的 mutex 真的支持 PI？

查对应版本源码和文档，检查：等待者是否按优先级排序；持锁者是否提升有效优先级；解锁时如何恢复；多 mutex 时是否重新计算；超时撤销等待者时是否重新计算；任务删除和递归锁路径如何处理。最后在目标板通过竞争测试和调度追踪验证。

## 13. 课程核心总结

- 优先级反转的核心是：**高优先级任务等待低优先级持锁者，而中优先级任务延迟持锁者运行**。
- PI mutex 能限制经典场景中的无界反转，但不会消除临界区本身造成的阻塞。
- PI 不能解决死锁、过长临界区、ISR 阻塞或任务截止时间设计错误。
- 长时间硬件操作优先采用资源所有者任务和消息传递，避免业务任务直接竞争慢资源。
- 实时性评估必须包含 `C`、`B`、高优先级干扰、ISR 延迟及内核临界区，并在目标板测量关键路径。
- 通用方案排序：**单一所有者/消息传递（减少共享） > 短临界区 + PI mutex（受控共享） > 无继承普通互斥（不适合高优先级实时竞争）** 。具体优劣仍取决于吞吐、延迟和证明要求。

## 16. 实践与进阶路径

### 梯度实战任务

1. 编写三个任务复现经典反转：低优先级持锁，高优先级请求，中优先级周期性抢占；比较普通信号量和 PI mutex。
2. 在目标板记录高优先级任务从请求锁到运行的延迟分布，输出平均值、最大值和高分位值。
3. 加入两把嵌套 mutex、等待超时和任务删除测试，核查有效优先级恢复。
4. 将共享 SPI 操作改造成资源所有者任务，比较端到端延迟、抖动、CPU 占用和队列满行为。
5. 对实际任务集建立响应时间表，验证最坏阻塞和截止时间是否满足。

### 性能测试方法

- 使用 DWT `CYCCNT`、硬件定时器或外部逻辑分析仪测量关键路径。
- 在锁前、锁后、任务唤醒和临界区结束处打点；避免用阻塞日志作为计时工具。
- 在高优先级任务、周期 ISR 和中优先级压力任务并发下重复测试。
- 覆盖正常、超时、错误返回、队列满、任务重启和异常解锁路径。
- 报告 MCU、主频、编译器与优化选项、RTOS 版本、任务优先级、临界区内容和测量次数；没有这些信息，数字不可复现。

### 进阶方向

- 固定优先级响应时间分析与阻塞项建模。
- Priority Ceiling Protocol 与 Immediate Ceiling Protocol 的形式化比较。
- 多核 RTOS 下的跨核锁、优先级传播和缓存一致性问题。
- 无锁数据结构的内存序、ABA 问题与可证明的有界执行时间。
- RTOS 调度追踪、时序验证和基于模型的并发测试。
