## 3. 技术概述

裸机驱动通常假定“只有主循环和中断”在访问硬件，主循环中不会被另一个线程抢占。RTOS 引入多个可并发执行的线程后，原有隐含假设不再成立：

```
裸机常见模型：
主循环 -> 驱动
ISR     -> 驱动（通常有限）

RTOS 常见模型：
线程 A -> 驱动
线程 B -> 驱动
ISR    -> 驱动/通知
DMA 回调 -> 驱动/通知
```

迁移的核心任务是重建驱动的并发和生命周期契约：

- **执行上下文**：线程、ISR、定时器回调、DMA 回调分别允许哪些操作。
- **资源所有权**：谁可以访问外设寄存器、总线、DMA 缓冲区和驱动状态。
- **同步策略**：如何保护设备状态和事务原子性。
- **时间语义**：忙等、延时、超时和周期任务如何映射到 RTOS。
- **错误与恢复**：等待超时、总线故障、设备掉线时如何退出和恢复。

### 主流迁移模式

1. **最小适配**：保留同步驱动接口，在关键路径增加锁和超时。
2. **ISR 通知 + 线程处理**：ISR 执行有界操作，工作线程完成阻塞 I/O 和协议处理。
3. **专用驱动服务线程**：所有设备请求排队给单一线程串行化。
4. **异步状态机**：用中断、DMA 和事件驱动状态转换，减少线程阻塞。
5. **子系统适配**：接入 RTOS 的设备模型或类别 API，统一应用访问方式。

## 4. 核心特性横向对比

|维度|裸机直接调用|加锁同步适配|服务线程串行化|异步状态机|

## 5. 底层原理与功能特性深度解析

### 5.1 先建立调用上下文清单

对每个公开函数和回调记录调用来源、是否可能阻塞、是否可重入，以及允许访问的资源。

|函数/回调|可能上下文|可阻塞？|典型职责|
|---|---|---|---|
|`device_read()`|线程|可以|等待数据、执行事务|
|`device_isr()`|ISR|不可以|清中断、记录状态、通知线程|
|`dma_complete()`|ISR 或中断延迟上下文|通常不可以|标记完成、释放缓冲所有权、通知|
|`timer_callback()`|依 RTOS 定时器实现而定|通常不建议|触发短工作或投递消息|
|`worker()`|线程|可以|协议处理、恢复、重试|

在调用上下文不明确之前，不要给驱动函数简单地“全部加锁”。锁本身可能只能在线程上下文使用。

### 5.2 将忙等转换为超时等待

裸机常见代码：

```
while ((REG_STATUS & READY_BIT) == 0U)
{
    /* 等待硬件 */
}
```

问题：无超时时可能永久卡死；在 RTOS 线程中忙等会占用 CPU，影响其他任务。

改造为有界轮询：

```
static int wait_ready(uint32_t timeout_ms)
{
    const uint32_t start = platform_uptime_ms();

    while ((REG_STATUS & READY_BIT) == 0U)
    {
        if ((platform_uptime_ms() - start) >= timeout_ms)
        {
            return -ETIMEDOUT;
        }

        rtos_delay_ms(1);
    }

    return 0;
}
```

此模式适合低频、短时间且没有硬件中断通知的状态等待。要求：

- `platform_uptime_ms()` 在回绕时差值计算正确。
- `rtos_delay_ms()` 只在允许阻塞的线程上下文调用。
- 超时时间覆盖器件最大响应时间和总线延迟。
- 高精度或低延迟场景优先用中断/信号量，而不是固定粒度轮询。

### 5.3 ISR 与线程分工

中断处理程序应尽量短：确认中断源、读取必要状态、通知线程。不能在 ISR 中等待互斥量、做阻塞总线访问或执行无界协议解析。

```
static void peripheral_isr(void)
{
    uint32_t status = PERIPH->STATUS;

    /* 尽快清除已处理的中断源，避免重复进入。 */
    PERIPH->STATUS = status;

    if ((status & RX_READY_BIT) != 0U)
    {
        /* ISR-safe API；具体名称和是否可调用取决于 RTOS。 */
        rtos_sem_give_from_isr(&g_rx_sem);
    }
}

static void rx_worker(void *argument)
{
    RTOS_UNUSED(argument);

    for (;;)
    {
        if (rtos_sem_take(&g_rx_sem, RTOS_WAIT_FOREVER) != 0)
        {
            continue;
        }

        /* 在线程上下文做可阻塞处理。 */
        process_received_data();
    }
}
```

注意：

- ISR-safe API 的名称和调度行为依 RTOS 而异。
- 部分 RTOS 需要在 ISR 退出前显式请求调度。
- 若硬件 FIFO 很浅，ISR 可能仍需搬运数据，但工作量必须有界。
- 不要从 ISR 获取普通互斥量。

### 5.4 共享外设访问与锁粒度

同一外设被多个线程调用时，需要定义锁保护的是**设备状态**还是**完整硬件事务**。通常需要让不可分割的事务整体受保护：

```
int sensor_read(struct sensor *dev, int16_t *value)
{
    int rc;

    if ((dev == NULL) || (value == NULL))
    {
        return -EINVAL;
    }

    rc = rtos_mutex_lock(&dev->lock, 20);
    if (rc != 0)
    {
        return rc;
    }

    rc = bus_read_registers(dev->bus, dev->address,
                            SENSOR_DATA_REG, dev->raw, sizeof(dev->raw));
    if (rc == 0)
    {
        *value = decode_sample(dev->raw);
    }

    rtos_mutex_unlock(&dev->lock);
    return rc;
}
```

锁设计要点：

- 不在持锁期间执行长延时、日志输出或无界等待。
- 总线控制器锁与设备状态锁各司其职，避免重复粗锁。
- 明确全局锁顺序，避免线程 A 持锁顺序为 `device -> bus`，线程 B 却是 `bus -> device`。
- 对多任务高优先级路径评估优先级继承和最大锁持有时间。
- 若驱动 API 会被 ISR 调用，则不能在该路径上使用线程互斥量。

### 5.5 处理启动顺序与静态初始化

裸机驱动可能在 `main()` 前通过全局初始化或固定启动顺序访问外设。RTOS 下还要确认：

- 时钟、GPIO、Pinmux、总线控制器先于外设驱动就绪。
- 中断在驱动状态和同步对象初始化后再使能。
- 线程启动前，驱动配置和设备对象已构造完成。
- 失败初始化能清理已申请资源，不能留下半初始化设备。
- 设备被多线程访问时，单纯的 `init_done` 标志需要同步保护；`volatile` 不能替代互斥或原子操作。

### 5.6 DMA 与缓存一致性

裸机代码常假设 DMA 完成后 CPU 立刻看到数据。带缓存 MCU 上，RTOS 不会自动解决 Cache 一致性：

- DMA 发送前：按平台要求 clean cache。
- DMA 接收后：按平台要求 invalidate cache。
- 缓冲区满足 DMA 地址和长度对齐要求。
- DMA 工作期间，CPU 不读写由 DMA 所有的缓冲区。
- 完成事件与缓冲区所有权转移要有清晰同步关系。

### 5.7 多调用者下的取消与超时

线程等待驱动结果时，超时并不一定代表硬件操作停止。必须定义：

- 超时后事务是否仍在后台运行。
- 是否可以取消硬件操作。
- 缓冲区是否仍被 DMA 使用。
- 后续请求是否可以启动。
- 发生超时时设备是否需复位或进入故障态。

“调用者超时返回”与“硬件事务已终止”是两件不同的事。

## 6. 性能量化分析

### 6.1 迁移前后需要测什么

没有指定 MCU、RTOS、时钟、总线速率和编译参数时，不应给出所谓通用实测值。应在目标板上对同一驱动路径进行基准测试，记录：

|指标|测量方法|关注点|
|---|---|---|
|API 调用开销|DWT/硬件定时器包围调用|分离纯函数、锁和总线时间|
|最大锁等待时间|记录锁请求与获取时间|发现优先级反转和长临界区|
|ISR 执行时间|GPIO 翻转或周期计数器|确认中断服务有界|
|ISR 到线程响应延迟|ISR 时间戳与线程入口时间戳|调度延迟和优先级影响|
|最坏 I/O 完成时间|硬件时间戳或逻辑分析仪|验证截止时间|
|CPU 占用|RTOS 统计或空闲任务计数|发现忙等和过量轮询|
|RAM/栈使用|map 文件、栈水位|服务线程和队列开销|
|超时与错误率|计数器和故障注入|验证恢复策略|

### 6.2 性能计算

对同步事务：

Tcomplete=Tqueue+Tlock+Tbus+Tdevice+Tschedule+TdecodeTcomplete​=Tqueue​+Tlock​+Tbus​+Tdevice​+Tschedule​+Tdecode​

其中：

- `T_queue`：请求排队等待。
- `T_lock`：锁竞争等待。
- `T_bus`：总线传输时间。
- `T_device`：器件内部转换或处理时间。
- `T_schedule`：中断退出到线程运行的调度延迟。
- `T_decode`：数据转换与校验。

RTOS 适配后增加的主要不一定是 API 调用开销，通常是**调度等待、锁等待、队列等待和线程切换**。

对轮询驱动的 CPU 成本，可粗略估算：

Upoll≈TbusyTperiodUpoll​≈Tperiod​Tbusy​​

例如每 10 ms 忙等 1 ms，单此轮询就占用约 10% CPU；改为事件等待后，CPU 可在等待期间执行其他任务，但会引入唤醒和调度延迟。

### 6.3 瓶颈分析与优化

- **高 CPU 占用**：定位无延时轮询和忙等，优先改为事件等待或有界轮询。
- **尾延迟上升**：检查锁等待、线程优先级、队列积压和中断屏蔽时长。
- **吞吐下降**：评估是否逐字节加锁、频繁任务切换或总线事务未批量化。
- **响应时间不可控**：避免在高优先级线程中调用无界同步 I/O。
- **RAM 增长**：检查新增服务线程栈、队列、DMA 缓冲区与重复缓存。
- **收益验证**：一次只改变一个因素，比较最大响应时间和高分位数，而不只看平均值。

```

|

|   |
|   +-- 是：加超时并确认调用处于线程上下文
|   +-- 否：保留简单同步路径，验证启动顺序
|
+-- 是：设备事务是否短且可由调用线程执行？
|   |
|   +-- 是：用互斥量保护完整事务，定义超时和锁顺序

|
+-- 是否由 ISR/DMA 事件驱动？
|   |
|   +-- 是：ISR 只做有界操作并通知线程，明确缓冲区所有权

|

```

|场景|推荐方案|理由|
|---|---|---|
|低频配置寄存器访问|同步接口 + 设备互斥量|简单，事务边界清晰|
|多线程共享慢速 I2C 外设|专用服务线程或设备锁|控制并发，避免复杂调用方互锁|
|高速 UART/SPI 接收|DMA/中断 + 环形缓冲区 + 消费线程|解耦硬件吞吐和业务处理|
|ISR 触发短处理|ISR 通知工作线程|避免 ISR 内阻塞和长时间处理|
|硬实时控制环|明确高优先级路径和最大阻塞时间|降低不可预测的调度和锁延迟|
|多外设共用总线|总线层统一仲裁，设备层管理状态|避免各驱动绕过总线锁|
|容易永久卡死的旧驱动|有界等待、取消和恢复状态机|将无界故障转为可控错误|

## 8. 工程最佳实践

### 设计原则

- 迁移前先定义所有驱动入口、调用上下文和资源所有权。
- 将硬件访问封装成可测试的底层事务函数，业务状态机不直接操作寄存器。
- 每个等待都必须有上限或明确证明不会永久等待。
- ISR 只做有界工作；复杂处理进入线程上下文。
- 使用 RTOS 原语保护共享状态，不能用 `volatile` 代替同步。
- 以事务为单位确定锁边界，避免过粗锁长期占用 CPU。
- 设备错误应向上传播；恢复行为要区分可重试和不可恢复故障。
- 对 DMA 设计缓冲区所有权状态，不允许 CPU 与 DMA 无协调地同时访问。

### 选型决策矩阵

|需求|推荐方案|主要代价|
|---|---|---|
|单线程、低速、简单外设|加超时的同步接口|调用线程阻塞|
|多线程并发、事务较短|互斥量保护事务|锁等待和死锁风险|
|多客户端访问、设备慢|服务线程 + 请求队列|队列和线程资源、请求排队|
|高吞吐或中断驱动|DMA/中断 + 缓冲区|状态和生命周期管理复杂|
|硬实时控制|受控的无阻塞路径或专用高优先级线程|资源预留与严格验证|

### 工业级编码规范

- 每个 API 文档说明是否可从 ISR 调用、是否阻塞、超时单位和返回码。
- 所有共享状态明确由哪把锁或原子操作保护。
- 不持有互斥量执行 `sleep`、长延时、无界轮询和日志输出。
- 建立统一锁顺序，必要时采用优先级继承互斥量。
- 处理初始化失败和部分资源申请成功后的逆序清理。
- 对等待和重试设置期限、次数上限和退避策略。
- 用计数器暴露超时、总线错误、队列溢出、设备复位次数。
- 禁止将线程上下文 API 从 ISR、硬件定时器回调或高优先级中断路径调用。
- 在代码评审中检查 DMA 缓冲区对齐和 Cache 维护。

## 9. 常见错误与避坑指南

### 错误一：把 `volatile` 当成线程同步

错误代码：

```
static volatile int transfer_done;

void dma_isr(void)
{
    transfer_done = 1;
}

int wait_transfer(void)
{
    while (transfer_done == 0)
    {
    }
    return 0;
}
```

根因：`volatile` 只约束编译器对访问的优化，不提供线程唤醒、互斥或完整内存顺序保证；循环还会忙占 CPU。

正确实现：ISR-safe 信号量、事件或原子变量配合等待机制；若共享 DMA 数据，还需遵循内存屏障和 Cache 维护要求。

风险影响：高 CPU 占用、任务无法及时调度、数据可见性问题。

### 错误二：在 ISR 中获取互斥量或阻塞等待

错误代码：

```
void peripheral_isr(void)
{
    rtos_mutex_lock(&device_lock, WAIT_FOREVER);
    read_device_over_bus();
    rtos_mutex_unlock(&device_lock);
}
```

根因：互斥量可能阻塞，ISR 无法等待线程运行；总线访问也可能需要等待。

正确实现：ISR 清中断并通知线程，由线程获取锁并执行事务。

风险影响：死锁、断言、长时间关中断或系统调度失效。

### 错误三：无超时轮询硬件状态

错误代码：

```
while ((STATUS_REG & DONE) == 0U)
{
}
```

根因：硬件故障、时钟未开或中断丢失时，循环永不结束。

正确实现：使用中断/信号量等待，或使用单调时间源进行有界轮询并返回 `-ETIMEDOUT`。

风险影响：线程永久占用、看门狗复位、系统功能整体失效。

### 错误四：所有驱动函数都用同一把全局锁

错误代码：

```
int driver_read(void)
{
    lock(&global_driver_lock);
    int rc = read_device();
    unlock(&global_driver_lock);
    return rc;
}
```

根因：锁保护范围过宽，多个独立设备互相阻塞；若读操作有延时，临界区会很长。

正确实现：按设备状态和总线事务分别划分锁，明确锁顺序，只在需要原子性的区段持锁。

风险影响：尾延迟增加、优先级反转、无关设备相互阻塞。

### 错误五：线程超时后立即复用 DMA 缓冲区

错误代码：

```
if (wait_dma_done(timeout) != 0)
{
    reuse_buffer();
}
```

根因：等待超时不一定取消了硬件 DMA，DMA 可能仍在访问该缓冲区。

正确实现：停止 DMA 并确认硬件已停，或保留缓冲区直到完成/复位确认；之后再释放所有权。

风险影响：内存破坏、数据污染、随机故障。

### 错误六：线程优先级设置不当导致间接优先级反转

错误代码：

```
/* 高优先级控制线程和低优先级日志线程使用同一设备锁；
 * 中优先级任务持续运行。 */
```

根因：低优先级线程持锁时被中优先级任务抢占，高优先级线程因此等待更久。

正确实现：采用优先级继承互斥量、缩短临界区、调整服务线程优先级，并测量最大锁持有和等待时间。

风险影响：控制回路错过截止时间、延迟长尾恶化。

## 10. 多机制组合使用方案

### 协同架构

```
调用线程
  |
  | 请求/响应或队列消息
  v
驱动服务线程
  |-- 设备状态锁
  |-- 总线访问
  |-- DMA 缓冲区管理
  |
  +<-- ISR：清中断、记录状态、通知服务线程
  |
  +<-- DMA 完成：交接缓冲区所有权、通知服务线程
```

适用条件：设备事务可能阻塞、多个客户端共享、需要统一恢复，且系统可接受服务线程和队列的资源成本。

### 组合设计要点

- 请求对象携带操作类型、参数、超时和完成通知。
- 请求入队前校验参数，队列满时返回明确错误或施加背压。
- 服务线程串行执行设备事务，集中处理总线错误和恢复。
- 客户端超时后需标记请求状态；不能假设硬件操作自动取消。
- ISR 和 DMA 回调仅更新最少状态并通知服务线程。
- 记录请求排队时间、执行时间、超时数和队列峰值。

### 代码框架

```
enum driver_op
{
    DRIVER_OP_READ,
    DRIVER_OP_WRITE,
};

struct driver_request
{
    enum driver_op op;
    uint8_t reg;
    uint8_t *buffer;
    size_t length;
    int result;
    rtos_sem_t completion;
};

static void driver_service_thread(void *argument)
{
    RTOS_UNUSED(argument);

    for (;;)
    {
        struct driver_request *req = NULL;

        if (rtos_queue_receive(&request_queue,
                               &req,
                               RTOS_WAIT_FOREVER) != 0)
        {
            continue;
        }

        if (req == NULL)
        {
            continue;
        }

        req->result = rtos_mutex_lock(&device_lock, REQUEST_LOCK_TIMEOUT);
        if (req->result == 0)
        {
            if (req->op == DRIVER_OP_READ)
            {
                req->result = bus_read(req->reg,
                                       req->buffer,
                                       req->length);
            }
            else if (req->op == DRIVER_OP_WRITE)
            {
                req->result = bus_write(req->reg,
                                        req->buffer,
                                        req->length);
            }
            else
            {
                req->result = -EINVAL;
            }

            rtos_mutex_unlock(&device_lock);
        }

        rtos_sem_give(&req->completion);
    }
}
```

生产实现还必须明确请求对象和缓冲区的所有权：请求完成前，客户端不得释放或复用服务线程仍在使用的内存。若请求允许超时取消，应增加请求状态和取消确认协议。

## 11. 工业级实际案例分析

### 案例一：裸机 I2C 传感器驱动迁移

**需求：** 旧驱动在主循环中轮询数据就绪位，RTOS 下由采集线程周期读取，配置线程可以修改量程。

**架构设计：**

- 传感器状态由设备锁保护。
- 采集线程按固定周期读取，或由 DRDY 中断通知。
- 配置接口校验量程，配置和采样读共享锁。
- 总线驱动管理 I2C 控制器并提供事务超时。
- 超时、NACK、ID 错误分别记录并定义恢复策略。

**核心代码：**

```
int sensor_set_range(struct sensor *sensor, uint8_t range)
{
    int rc;

    if (!range_is_valid(range))
    {
        return -EINVAL;
    }

    rc = rtos_mutex_lock(&sensor->lock, 10);
    if (rc != 0)
    {
        return rc;
    }

    rc = i2c_write_reg(sensor->bus, sensor->address,
                       REG_RANGE, range);
    if (rc == 0)
    {
        sensor->range = range;
    }

    rtos_mutex_unlock(&sensor->lock);
    return rc;
}
```

**设计要点：** 软件记录的量程只在硬件写成功后更新；采样值转换必须使用与该样本一致的量程配置。

### 案例二：裸机 UART 环形缓冲区迁移

**需求：** 旧工程在 UART ISR 中写环形缓冲区，主循环解析。RTOS 下多个线程消费协议数据并发送命令。

**架构设计：**

- ISR 只搬运 FIFO 数据并更新环形缓冲区。
- ISR 通过信号量或事件唤醒协议线程。
- 协议线程负责拆包、校验和派发。
- TX 接口由 mutex 或 TX 服务线程串行化，避免多线程交错发送。
- 明确环形缓冲区满时丢弃策略和计数方式。

**设计要点：** 单生产者/单消费者队列适合 ISR 写、线程读；若多个生产者或消费者，必须使用支持多方并发的同步结构，或在访问索引时进行保护。

### 案例三：DMA 采样驱动迁移

**需求：** 裸机 DMA 采集 ADC 数据，主循环检查完成标志。RTOS 下采集结果需要交给多个处理线程，且支持休眠恢复。

**架构设计：**

- DMA 完成 ISR 只识别通道、确认中断并通知采集线程。
- 采集线程执行 Cache invalidate、校验样本并将缓冲区交给下游。
- 缓冲区有明确的 `FREE -> DMA_OWNED -> READY -> CPU_OWNED -> FREE` 状态。
- suspend 前停止 DMA 并确认停止，resume 后重新配置并校验时钟与 ADC 状态。

**设计要点：** 通知不能替代缓冲区所有权；在 DMA 仍运行时不能复用缓冲区。电源管理流程必须和 DMA 状态机协同。

## 12. 高频问题深度答疑

### Q1：裸机驱动迁移后，是否只需给 API 加互斥量？

不一定。若驱动包含 ISR、DMA、回调、长时间忙等或线程间等待，加锁远远不够。先列出所有共享状态和调用上下文，再决定是设备锁、服务线程、事件驱动还是状态机。

### Q2：`volatile` 能否解决 ISR 和线程之间的数据竞争？

不能。它不能提供互斥、线程唤醒或完整的跨核/内存顺序保证。简单标志可使用 RTOS 原子 API；事件通知使用信号量或事件；复合数据通常需要同步对象或临界区。

### Q3：什么时候应该用专用服务线程？

当设备访问可能阻塞、多个客户端需要串行、故障恢复需要统一管理，或客户端不应直接掌握硬件事务时，服务线程通常有价值。代价是额外线程栈、队列等待和请求生命周期管理。

### Q4：所有轮询都要改成中断吗？

不需要。短、确定、低频的轮询有时更简单。应优先去掉无超时的长时间忙等；若硬件支持事件通知且响应要求较高，改为中断/信号量通常更合适。选择依据是 CPU 占用、延迟和实现复杂度。

### Q5：线程超时后，驱动是否应该立即复位外设？

不总是。要区分单次调用超时、器件忙、总线故障和硬件失效。立即复位可能影响其他客户端或破坏正在进行的事务。恢复应由设备状态机统一决策，并与事务取消、DMA 状态和共享用户协同。

### Q6：如何确定锁粒度？

保护必须保持原子性的最小事务，而不是机械地按函数加锁。若配置写入和随后的数据读取依赖一致状态，应覆盖两者相关状态更新；纯数据转换和日志通常可放到锁外。用最大锁持有时间和阻塞时间验证设计。

### Q7：如何控制优先级反转？

优先使用支持优先级继承的互斥量，缩短锁持有时间，避免持锁等待 I/O 或休眠，并合理配置服务线程优先级。还应测量高优先级调用的最大锁等待时间，而不仅看平均值。

### Q8：迁移时是否应顺便改成 RTOS 设备模型？

取决于工程架构和复用需求。若应用需要统一的设备发现、类别接口和生命周期管理，接入设备模型有价值；若目标只是把单一驱动安全地运行在线程中，先建立正确的并发与上下文契约更重要，不必为了抽象而扩大改动范围。

## 13. 课程核心总结

- **迁移的关键是改造执行模型和资源契约，不是替换 API 名称。**
- 每个驱动入口都应声明允许的调用上下文、阻塞行为和线程安全语义。
- ISR 做有界工作；阻塞事务、协议解析和恢复放到线程上下文。
- 所有等待必须有期限或有明确的硬件完成保证。
- `volatile` 不是线程同步机制；共享状态必须使用合适的 RTOS 同步原语。
- DMA 迁移必须管理缓存一致性和缓冲区所有权。
- 锁、队列、服务线程和异步状态机各有代价，应按实时性和复杂度选型。
- 所有性能结论都应在目标板上测量最大延迟、尾延迟、CPU 占用和资源水位。

## 14. 快速参考速查表

### 场景选型表

|场景|推荐方案|
|---|---|
|低频、短事务、线程调用|同步 API + 设备互斥量|
|长时间等待硬件|中断/信号量，或有界轮询|
|ISR 触发复杂处理|ISR 通知线程或工作队列|
|多客户端共享慢速外设|服务线程 + 请求队列|
|高速接收或采集|DMA/中断 + 环形缓冲区 + 消费线程|
|高优先级硬实时控制|缩短临界区，避免无界阻塞并测最坏延迟|
|DMA 接收数据|明确缓冲区所有权并处理 Cache 一致性|

### 迁移核查表

|项目|核查问题|
|---|---|
|调用上下文|是否可能从 ISR、定时器回调或多个线程调用？|
|等待行为|所有轮询和等待是否有超时？|
|共享状态|哪些字段被多个上下文访问，由什么保护？|
|锁策略|锁是否可能在 ISR 获取？是否有统一锁顺序？|
|DMA|缓冲区由谁拥有？是否做 Cache 维护？|
|生命周期|初始化、失败回滚、休眠恢复和关闭如何处理？|
|错误语义|超时、总线错误和设备异常是否可区分？|
|实时性能|是否测量最大锁等待、ISR 延迟和 I/O 完成时间？|
