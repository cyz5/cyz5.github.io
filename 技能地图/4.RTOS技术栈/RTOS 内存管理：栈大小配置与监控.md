
## 1. 学习目标

### 理解

- 理解 RTOS 任务栈的用途、增长方向、上下文切换保存内容，以及任务栈与中断栈的边界。
- 理解栈溢出、栈余量不足、栈高水位统计和静态栈分析各自能发现什么、不能证明什么。
- 理解 FreeRTOS 栈深通常以 `StackType_t` 个数表示，而不是字节数。

### 掌握

- 掌握基于调用链、编译器栈使用报告和目标板压力测试配置任务栈的方法。
- 掌握 FreeRTOS 栈溢出检测、高水位查询和任务运行统计的使用方式。
- 掌握启动期栈预算、运行时采样、告警阈值和故障处置策略。

### 精通

- 能够分析任务调用链、局部对象、编译器生成代码、中断嵌套和上下文保存对栈的影响。
- 能够识别高水位“看起来充足”但测试未覆盖关键路径的风险。
- 能够设计栈使用监控、异常定位、构建期预算和产品现场诊断体系。

### 能够设计

- 能够为每个任务制定可审计的栈大小依据和安全余量。
- 能够区分任务栈、异常栈、中断栈和 FPU 上下文，并为各自配置容量。
- 能够设计基于静态分析、编译器报告、运行时高水位和故障注入的组合验证方案。

## 2. 前置要求

### 知识要求

- 熟悉 C 函数调用、局部变量、递归、函数指针和中断处理。
- 熟悉 MCU 栈指针、异常入口、上下文切换和 ABI 基本约定。
- 熟悉 RTOS 任务创建、优先级、任务切换和中断优先级配置。
- 熟悉链接脚本中的 RAM、`.bss`、`.data`、堆和栈段。

### 技能要求

- 能查看编译器栈使用报告和链接器 map 文件。
- 能读取任务高水位、任务状态和栈溢出回调信息。
- 能在目标板上构造最坏负载并记录任务栈余量。
- 能使用调试器查看 SP、任务栈边界和故障现场寄存器。

## 3. 技术概述

### 栈是什么

任务栈保存任务执行时需要保留的上下文，包括：

- 函数返回地址和保存寄存器。
- 局部变量、临时变量和部分参数。
- 嵌套函数调用所需的栈帧。
- RTOS 切换任务时保存的寄存器上下文。
- 某些端口下的浮点寄存器上下文。
- 中断或异常处理过程中使用的上下文，具体取决于硬件和端口设计。

栈配置是**容量预算问题**，不是只看源码中局部变量大小。编译器优化、调用深度、异常嵌套、FPU、库函数和目标 ABI 都会改变实际使用量。

### 栈的种类

|栈类型|典型用途|常见配置位置|
|---|---|---|
|任务栈|每个 RTOS 任务的执行上下文|任务创建参数或静态栈数组|
|主栈/MSP|异常入口、启动代码、部分中断上下文|链接脚本或启动文件|
|进程栈/PSP|Cortex-M 线程态任务执行栈|RTOS 端口上下文|
|中断栈|某些 RTOS/CPU 为 ISR 单独提供|端口或链接脚本|
|异常栈|HardFault、NMI、异常入口等|启动代码或系统栈|

**不能默认“所有中断都使用当前任务栈”。** Cortex-M FreeRTOS 通常由线程态任务使用 PSP，异常处理使用 MSP，但切换和嵌套细节必须核对端口汇编及具体异常路径。

### FreeRTOS 中的栈深单位

FreeRTOS `xTaskCreate()` / `xTaskCreateStatic()` 的栈深参数通常以 `StackType_t` 个数表示：

```
#define CONTROL_STACK_WORDS  512U
```

若：

```
sizeof(StackType_t) == 4U
```

则栈数组占用：

```
512 × 4 = 2048 字节
```

应在目标工程中核对 `sizeof(StackType_t)`，不要把栈深直接当字节传入。

### 监控手段分类

- **编译期分析**：编译器栈使用报告、静态调用图、递归检查。
- **运行期观测**：栈高水位、哨兵/填充模式、SP 边界检查。
- **溢出检测**：RTOS 栈溢出检查、MPU guard region、硬件栈限制。
- **故障诊断**：保存任务名、SP、栈边界、故障寄存器和调用栈。
- **测试覆盖**：最大负载、最深调用链、错误路径、中断嵌套和库函数路径。

## 4. 核心特性横向对比

|方案|能发现的问题|不能保证什么|额外成本|建议用途|
|---|---|---|---|---|
|编译器栈使用报告|单函数静态栈帧大小、部分调用关系|动态调用、间接调用、全部运行时路径|构建和分析成本|预算基线与回归检查|
|FreeRTOS 高水位 API|运行期间触及过的最小余量|未覆盖路径的最大栈需求|扫描填充模式的 CPU 成本|运行时诊断和压力测试|
|FreeRTOS 溢出检查|特定边界被破坏|所有越界都能及时捕获|少量运行开销|开发、测试和部分产品构建|
|MPU guard region|越界访问触发保护异常|所有端口/区域配置都能覆盖全部问题|MPU 区域、对齐和空间成本|高完整性系统|
|栈哨兵/水印|栈内容触及边界的迹象|立即检测、精确故障路径|初始化和扫描成本|现场监控与测试|
|静态数组固定栈|栈容量确定、易审计|栈使用一定不越界|固定 RAM 预留|关键任务和固定任务集|

## 5. 底层原理与功能特性深度解析

### 5.1 函数调用如何消耗栈

在常见 ABI 下，函数调用可能将部分寄存器保存到栈上，并为局部变量分配栈帧。示例：

```
static int process_packet(const uint8_t *data, size_t length)
{
    uint8_t scratch[192];
    int result = 0;

    if ((data == NULL) || (length == 0U)) {
        return -1;
    }

    parse_header(data, length, scratch, sizeof(scratch));
    result = validate_payload(scratch, sizeof(scratch));

    return result;
}
```

该函数至少引入 192 字节局部数组，但实际栈帧可能更大，还包含：

- 保存寄存器。
- 对齐填充。
- 编译器临时值。
- 调用子函数的参数和保存状态。
- 错误路径与优化配置差异。

若 `parse_header()` 再调用 `decode()`，栈峰值一般来自调用链上同时存活的栈帧，而不是所有函数栈帧大小的简单全局总和。

简化估算：

```
调用链栈峰值 ≈
    当前函数栈帧
  + 最深子调用链栈帧
  + ABI/编译器临时空间
  + RTOS/异常上下文相关空间
```

### 5.2 任务栈和上下文切换

任务被切出时，端口层会保存恢复执行所需的寄存器。以 Cortex-M 为例，硬件异常入口和 FreeRTOS 汇编端口会共同参与上下文保存。具体哪些寄存器由硬件自动压栈、哪些由端口软件保存，取决于：

- Cortex-M 型号和异常机制。
- 使用 MSP 还是 PSP。
- FPU 是否启用及是否发生浮点上下文保存。
- lazy stacking 配置。
- FreeRTOS port 汇编实现。

因此任务栈预算必须从**目标端口代码**核对上下文大小，而不能只按 C 调用栈估算。

### 5.3 FreeRTOS 栈高水位

FreeRTOS 通常用创建任务时初始化的已知填充值填充栈空间。任务运行后，部分栈区域被覆盖。高水位查询据此扫描仍未改变的区域，估算历史最低剩余栈。

```
UBaseType_t words =
    uxTaskGetStackHighWaterMark(task_handle);
```

部分版本或端口还提供 `uxTaskGetStackHighWaterMark2()`，返回类型为 `configSTACK_DEPTH_TYPE`。应使用项目头文件中的实际声明，避免类型不匹配。

剩余字节数估算：

```
size_t remaining_bytes =
    (size_t)words * sizeof(StackType_t);
```

**高水位是历史观测值，不是静态证明。** 如果某个错误路径、日志路径或最大中断嵌套没有在测试中发生，它不会反映在高水位中。

### 5.4 高水位填充法的限制

填充法通常只能判断仍保持初始模式的连续区域。以下情况可能影响结果：

- 栈底附近初始化或端口使用的数据被误认为栈使用。
- 栈从高地址向低地址增长，扫描方向依赖端口实现。
- 未经过的路径没有压栈。
- 某些编译器或运行库可能写入栈区域。
- 栈溢出已破坏相邻对象后才被监测到。
- 高频读取需要扫描大量内存，产生 CPU 开销。

对产品系统，应限制采样频率，例如低优先级监控任务周期采样，而不是在控制循环每次迭代中扫描全部任务栈。

### 5.5 FreeRTOS 栈溢出检查

FreeRTOS 配置中常见选项：

```
#define configCHECK_FOR_STACK_OVERFLOW  2
```

不同检测等级和具体实现会随版本变化。常见机制包括：

- 检查任务栈指针是否越过边界。
- 检查栈边界附近的填充值是否被覆盖。

需要实现相应钩子：

```
void vApplicationStackOverflowHook(
    TaskHandle_t task,
    char *task_name)
{
    (void)task;
    (void)task_name;

    disable_nonessential_interrupts();
    system_enter_safe_state();
}
```

生产代码中的钩子应尽量短，不宜调用普通日志、动态分配、阻塞 API 或复杂驱动。栈溢出发生时，当前任务栈本身已不可信，应优先把必要信息写入预留静态故障区，再进入安全状态或复位。

### 5.6 静态任务栈配置

```
#include "FreeRTOS.h"
#include "task.h"

#define WORKER_STACK_WORDS  640U

static StaticTask_t s_worker_tcb;
static StackType_t s_worker_stack[WORKER_STACK_WORDS];
static TaskHandle_t s_worker_handle;

static void worker_task(void *argument)
{
    (void)argument;

    for (;;) {
        worker_process();
        vTaskDelay(pdMS_TO_TICKS(20U));
    }
}

BaseType_t worker_task_create(void)
{
    s_worker_handle = xTaskCreateStatic(
        worker_task,
        "worker",
        WORKER_STACK_WORDS,
        NULL,
        tskIDLE_PRIORITY + 2U,
        s_worker_stack,
        &s_worker_tcb);

    return (s_worker_handle != NULL) ? pdPASS : pdFAIL;
}
```

静态任务使栈地址和容量显式可见，但不自动保证容量正确。建议将栈尺寸、单位和用途写入配置表，并在构建期输出字节数。

### 5.7 动态任务栈配置

```
#define WORKER_STACK_WORDS  640U

BaseType_t worker_task_create(void)
{
    TaskHandle_t handle = NULL;

    BaseType_t result = xTaskCreate(
        worker_task,
        "worker",
        WORKER_STACK_WORDS,
        NULL,
        tskIDLE_PRIORITY + 2U,
        &handle);

    if (result != pdPASS) {
        return pdFAIL;
    }

    return pdPASS;
}
```

动态创建的任务栈通常来自 FreeRTOS 堆，具体实现以目标版本和配置为准。增加栈深会同时增加 RAM 预算和堆压力；删除任务是否回收相关内存，也需结合对应 API 和 heap 实现确认。

### 5.8 中断栈与主栈

在 Cortex-M FreeRTOS 的典型配置中：

- 线程态任务常使用 PSP。
- 异常处理常使用 MSP。
- 启动代码、NMI、HardFault 及部分中断路径可能使用主栈。

但不能将这一概括直接视为工程事实。需要检查：

- 启动文件设置的 MSP 初值。
- 链接脚本保留的主栈大小。
- FreeRTOS port 的任务栈切换汇编。
- 中断优先级和嵌套配置。
- ISR 是否调用了会增加栈使用的库函数。
- FPU 上下文和异常嵌套行为。

若多个中断嵌套使用 MSP，其最坏需求与嵌套深度、各 ISR 栈帧和硬件压栈内容有关。任务高水位 API 通常不监控这段主栈。

### 5.9 FPU 对栈的影响

启用 FPU 后，任务或异常路径可能需要保存额外浮点上下文。是否发生、保存多少、何时保存，取决于芯片、编译选项、RTOS port 和 lazy stacking 配置。应使用目标芯片参考手册与端口代码核算，并在实际启用 FPU 的发布构建中测量。

### 5.10 编译器栈使用报告

GCC 可通过选项输出每个函数的栈使用报告，例如：

```
-fstack-usage
```

生成的报告可用于：

- 找出大栈帧函数。
- 发现局部大数组。
- 对比不同版本函数栈需求变化。
- 与静态调用图组合估算最长路径。

局限包括：

- 间接调用目标可能不完整。
- 函数指针和回调关系需要人工补充。
- 递归可能使栈深无界。
- 汇编代码、ISR 和库函数报告可能不完整。
- 最终栈使用还受链接版本、优化级别、LTO 和 ABI 影响。

## 6. 性能量化分析

### 6.1 任务栈 RAM 预算

单个任务栈字节数：

```
任务栈字节数 = 栈深（StackType_t 数量）× sizeof(StackType_t)
```

系统任务栈总量：

```
M_task_stacks =
    Σ(task_stack_depth_i × sizeof(StackType_t))
```

再加上：

```
M_stack_system =
    M_task_stacks
  + M_main_stack
  + M_interrupt_stack（若独立）
  + 保护区/对齐开销
```

示例：若 `StackType_t` 为 4 字节，任务栈深 640：

```
640 × 4 = 2560 字节
```

这只是任务栈数组大小，不包括任务 TCB，也不表示实际峰值使用量。

### 6.2 栈余量和安全系数

若压力测试测得最小剩余栈为 `R_test`，可以将其作为观测余量，但不能直接把它当作设计余量。一个工程化预算可写为：

```
配置栈深 =
    静态分析最大需求
  + 未覆盖路径余量
  + 上下文/异常余量
  + 项目安全裕量
```

若只有实测数据：

```
配置栈深 >= 实测最大使用量 × 安全系数
```

安全系数应根据安全等级、测试覆盖、库调用确定性和平台要求制定，而不是统一套用一个比例。更可靠的做法是对静态分析、目标板压力测试和异常路径分别留出可说明的余量。

### 6.3 监控成本

高水位扫描成本约与栈容量相关：

```
扫描时间 ≈ 扫描字数 × 单字读取和比较成本
```

如果每个任务栈都在高频周期扫描，CPU 成本会随任务数量和栈总容量增长。建议：

- 低优先级监控任务定期采样。
- 只在开发或诊断构建中提高采样频率。
- 对关键任务记录最小余量，不要每个周期完整扫描全部栈。
- 评估 RTOS API 扫描实现是否会影响实时响应。

### 6.4 量化数据的正确获取方式

本课不提供跨平台固定“每个任务要多少字节”或“溢出检查耗时多少微秒”的数字。可靠数据应来自目标工程：

|指标|方法|必须记录|
|---|---|---|
|函数栈帧|编译器 `-fstack-usage` 或对应工具|编译器、优化级别、LTO|
|调用链峰值|静态调用图、人工路径分析|函数指针和递归假设|
|任务运行峰值|高水位 API|测试负载和覆盖路径|
|主栈峰值|哨兵或调试器 SP 采样|ISR 嵌套和异常场景|
|溢出检测延迟|故障注入、GPIO/周期计数器|检测等级和端口|
|RAM 总预算|map 文件和链接符号|发布构建与链接脚本版本|

## 7. 应用场景选型指南

### 纯文本决策流程图

```
该执行上下文是否有独立栈？
├─ 否 -> 确认当前 RTOS/端口的实际栈模型
└─ 是
   ├─ 是否为中断、异常或主栈？
   │  ├─ 是 -> 依据嵌套深度、硬件压栈和 ISR 调用链单独预算
   │  └─ 否 -> 作为任务栈预算
   └─ 任务是否包含递归、大局部数组、格式化或复杂库调用？
      ├─ 是 -> 消除无界因素或单独进行静态分析和压力测试
      └─ 否 -> 用调用链报告 + 运行高水位建立容量
         ├─ 关键任务 -> 静态分析、运行测试、溢出保护三重验证
         └─ 普通任务 -> 报告基线 + 高水位监控 + 失败诊断
```

### 典型场景

|场景|配置策略|重点|
|---|---|---|
|电机控制周期任务|固定静态栈、严格调用链控制|禁止递归和大局部对象|
|网络协议任务|按最深解析路径配置，并压测最大报文|解析器嵌套、错误路径、日志|
|日志任务|使用固定格式化缓冲区或受控栈预算|`printf` 等函数可能有较大栈需求|
|文件系统任务|专门测试最深目录/错误路径|第三方库栈帧和回调路径|
|ISR/异常处理|单独预算 MSP/ISR 栈|嵌套深度和硬件上下文|
|浮点任务|在目标 FPU/port 配置下测量|浮点上下文保存|

## 8. 工程最佳实践

### 设计原则

- 每个任务栈都应有配置依据、单位、字节数和责任模块。
- 任务栈与 MSP/异常栈分开预算、分开监控。
- 禁止递归，除非最大深度可证明且纳入预算。
- 避免大数组作为局部变量；优先静态缓冲区、固定池或专用工作区。
- 栈预算使用发布构建配置验证，不能只使用调试构建。
- 关键任务采用静态分析、运行高水位和溢出保护组合验证。
- 将栈高水位低于阈值定义为可诊断事件，阈值需由项目风险分析确定。
- 栈溢出钩子不调用可能依赖任务栈或堆的复杂服务。

### 选型决策矩阵

|方法|适用对象|优点|局限|
|---|---|---|---|
|编译器栈报告|可构建源码中的 C 函数|发现大栈帧，便于版本比较|不自动覆盖所有运行时路径|
|高水位监测|FreeRTOS 任务|反映实际测试峰值|未执行路径不可见|
|栈边界检查|开发和测试构建|发现部分溢出|可能在破坏发生后才发现|
|MPU 保护|高完整性任务|越界可触发保护异常|需要端口支持和区域规划|
|主栈哨兵|MSP/中断栈|发现主栈水印变化|需要自行实现并验证|

### 工业级编码规范

- 使用带 `_WORDS` 或 `_BYTES` 后缀的宏，避免单位混淆。
- 记录 `sizeof(StackType_t)`，并将字节数输出到构建报告。
- 禁止在任务栈中使用尺寸由外部输入决定的变长数组。
- 禁止未经评估的递归和大局部缓冲区。
- 栈溢出钩子只执行最小化、无阻塞、无分配的安全操作。
- 对每个任务配置“最小剩余栈阈值”和告警策略。
- 对任务删除和重建路径重新监控栈数据，避免使用旧句柄采样。
- 构建门禁对栈使用报告变化设置审查阈值。

## 9. 常见错误与避坑指南

### 错误一：把栈深参数当作字节

```
/* 错误：预期 2048 字节，却传入 2048 个 StackType_t。 */
xTaskCreate(worker_task, "worker", 2048U,
            NULL, 2U, NULL);
```

**根因：** FreeRTOS 栈深参数通常以 `StackType_t` 个数为单位。

**正确实现：**

```
#define WORKER_STACK_BYTES  2048U
#define WORKER_STACK_WORDS \
    (WORKER_STACK_BYTES / sizeof(StackType_t))

_Static_assert(
    (WORKER_STACK_BYTES % sizeof(StackType_t)) == 0U,
    "Stack size must align to StackType_t");

xTaskCreate(worker_task, "worker", WORKER_STACK_WORDS,
            NULL, 2U, NULL);
```

**风险影响：** 可能过度占用 RAM，也可能因反向误算导致栈不足。

### 错误二：仅凭一次高水位测试缩小栈

```
/* 错误做法：一次演示流程余量很多，就直接大幅减小栈。 */
size_t remaining = uxTaskGetStackHighWaterMark(task) *
                   sizeof(StackType_t);
```

**根因：** 高水位只记录已执行路径的历史最低余量。故障路径、异常输入、日志路径和最大中断嵌套可能未覆盖。

**正确实现：** 结合静态调用链分析、压力测试、错误路径测试和合理余量；使用发布优化构建复测。

**风险影响：** 产品现场特定条件下才发生溢出，复现困难。

### 错误三：任务栈高水位代表所有栈都安全

```
/* 错误推断：所有任务高水位充足，所以中断栈一定安全。 */
```

**根因：** 高水位 API 监控的是任务栈，不一定监控 MSP、异常栈或独立 ISR 栈。

**正确实现：** 按目标端口确认栈模型；为主栈或 ISR 栈单独设置哨兵、边界监控和测试。

**风险影响：** 中断嵌套耗尽 MSP 后，任务栈指标仍显示正常。

### 错误四：在任务栈里放大数组

```
void parser_task(void *argument)
{
    uint8_t frame_buffer[4096];
    /* 处理报文 */
}
```

**根因：** 局部数组随任务栈占用，编译器还可能额外生成临时空间。

**正确实现：** 使用固定池、静态工作区或受控共享缓冲区，并定义所有权和并发保护。

**风险影响：** 任务创建时栈预算显著增加，或深调用路径下溢出。

### 错误五：溢出钩子里打印复杂日志

```
void vApplicationStackOverflowHook(
    TaskHandle_t task,
    char *name)
{
    printf("stack overflow: %s\n", name);
}
```

**根因：** 格式化输出可能消耗更多栈、申请堆、阻塞或依赖已损坏的调度状态。

**正确实现：** 将必要的任务 ID、SP 和错误码写入预分配故障记录区，然后进入安全态或触发受控复位。

**风险影响：** 二次溢出、死锁、故障信息丢失或复位行为不可预测。

## 10. 多机制组合使用方案

### 10.1 栈预算闭环

```
架构阶段
  -> 列出任务、优先级、调用链和栈类型
构建阶段
  -> 编译器栈报告 + 静态调用图 + map 文件
测试阶段
  -> 最大负载、错误路径、FPU、ISR 嵌套
运行阶段
  -> 高水位采样 + 阈值告警 + 故障记录
发布阶段
  -> 发布配置复测 + RAM 预算审核 + 版本留档
```

### 10.2 运行时监控框架

```
#include "FreeRTOS.h"
#include "task.h"

typedef struct {
    const char *name;
    TaskHandle_t handle;
    UBaseType_t minimum_remaining_words;
} TaskStackMonitor_t;

static TaskStackMonitor_t s_monitors[8U];
static size_t s_monitor_count;

static size_t task_stack_remaining_bytes(TaskHandle_t task)
{
    UBaseType_t remaining_words;

    if (task == NULL) {
        return 0U;
    }

    remaining_words = uxTaskGetStackHighWaterMark(task);

    return (size_t)remaining_words * sizeof(StackType_t);
}

void stack_monitor_sample(void)
{
    for (size_t i = 0U; i < s_monitor_count; ++i) {
        size_t remaining =
            task_stack_remaining_bytes(s_monitors[i].handle);

        stack_monitor_record(
            s_monitors[i].name,
            remaining);
    }
}
```

实际实现应注意：

- `uxTaskGetStackHighWaterMark()` 的返回类型和句柄有效性。
- 任务删除后应注销监控项。
- 阈值判断应使用字节或 words，并统一单位。
- API 是否可在指定调用上下文使用，以目标 FreeRTOS 版本为准。
- 采样频率要评估扫描开销。

## 11. 工业级实际案例分析

### 案例一：电机控制任务

**需求：** 固定周期控制，任务执行时间和栈需求都需可审核。

**设计：**

- 静态创建控制任务。
- 禁止递归、VLA 和大局部缓冲区。
- 控制算法栈由编译器报告和静态调用图建立基线。
- 在最大负载、故障注入和发布优化构建中测高水位。
- 栈溢出钩子写入静态故障记录并进入安全态。

**设计要点：**

- 不能只测正常控制周期。
- 诊断上报、异常处理和参数切换路径也要测。
- 中断和主栈单独预算。

### 案例二：网络协议解析任务

**需求：** 处理最大长度报文，解析流程包含多层协议和错误分支。

**设计：**

- 解析工作缓冲区从固定池获取，不放在任务栈。
- 使用最大报文、非法长度、嵌套扩展头和错误恢复流程做压力测试。
- 编译器栈报告锁定协议解析函数的栈帧变化。
- 对递归解析采用显式深度上限，或改为迭代状态机。

**设计要点：**

- 外部输入不能影响递归深度和 VLA 尺寸。
- `printf`、格式化和第三方库的调用路径需单独检查。
- 高水位不足告警要包含任务名、剩余字节和软件版本。

### 案例三：多中断采集设备

**需求：** 多个优先级中断可嵌套，任务使用 PSP，异常使用 MSP。

**设计：**

- 通过端口汇编和启动文件确认 PSP/MSP 使用方式。
- 根据允许的最大中断嵌套和各 ISR 栈帧评估 MSP。
- 在 MSP 预留区设置水印，并在低风险时段读取。
- 禁止 ISR 调用深层解析、格式化输出和动态分配。
- 通过中断嵌套压力测试验证异常栈余量。

**设计要点：**

- FreeRTOS 任务高水位不覆盖 MSP。
- ISR 优先级配置和可屏蔽规则会改变最大嵌套深度。
- HardFault 现场保存不能依赖已溢出的任务栈。

## 12. 高频问题深度答疑

### 1. 高水位还剩 100 字节，任务就安全吗？

不能仅凭一个数字判断。需要知道：

- 是否覆盖最深调用路径。
- 是否包含错误处理和日志路径。
- 是否覆盖 FPU 和中断场景。
- 测试与发布构建是否一致。
- 该端口高水位 API 的单位和实现方式。

阈值应基于平台上下文开销和安全分析确定，不能跨项目照搬固定字节数。

### 2. 配置栈大小时还需要把中断栈算到每个任务里吗？

取决于端口。如果中断使用独立 MSP，则 ISR 需求应计入主栈预算，而非简单叠加到每个任务栈。如果中断使用当前任务栈，则相关 ISR 嵌套可能影响被打断任务栈。必须根据目标处理器、RTOS 端口和异常入口代码确认。

### 3. 高水位 API 的返回单位是什么？

FreeRTOS API 通常以 `StackType_t` 数量返回，不是字节。乘以 `sizeof(StackType_t)` 才能换算字节。部分版本提供 `...HighWaterMark2` 以适配不同栈深类型，使用前应查看工程头文件和版本。

### 4. 栈溢出检测等级 2 是否能保证不越界？

不能。它是检测机制，不是硬件内存隔离证明。越界可能在检测前破坏邻近对象，也可能以不覆盖检测区域的方式发生。高完整性需求还应考虑 MPU guard、静态分析、边界哨兵和压力测试。

### 5. 为什么使用 `printf` 后才发生栈溢出？

格式化输出可能调用多层 libc 函数、使用较大的局部状态，浮点格式化尤其可能增加栈需求。调试构建还可能启用额外检查。应使用目标 libc 的栈使用报告或实测，并避免在小栈任务和错误钩子中调用复杂格式化函数。

### 6. 任务栈高水位会不会因任务删除而失效？

句柄指向的任务删除后不再有效，不能继续查询。任务销毁后应从监控表注销句柄；重建任务时记录新的句柄和栈区。静态栈数组若复用，也应明确已无任务引用后才能重置或重新创建。

## 13. 课程核心总结

- 栈大小是基于调用链、上下文保存、库函数和异常模型的容量预算。
- FreeRTOS 栈深参数通常以 `StackType_t` 数量表示，必须转换成字节核算。
- 高水位表示测试期间观测到的最低余量，不覆盖未执行路径。
- 任务栈、MSP/异常栈和独立中断栈必须按目标端口分别确认与监控。
- 栈溢出钩子应短小、无阻塞、无动态分配，不依赖已损坏栈。
- 最可靠的策略是组合**编译器栈报告、静态调用链分析、目标板压力测试、运行时高水位和边界保护**。
- 发布配置、编译器优化、FPU 和链接脚本改变后，应重新验证栈预算。

## 16. 实践与进阶路径

### 梯度实战任务

1. 为工程所有任务建立清单，记录栈深、字节数、调用模块和实时等级。
2. 为 GCC 工程启用 `-fstack-usage`，比较控制构建与发布构建的函数栈帧变化。
3. 为任务周期采集高水位，输出最低剩余字节数并设置项目级告警阈值。
4. 构造网络最大报文、错误处理和日志输出压力测试，验证栈峰值。
5. 检查 Cortex-M 启动代码、FreeRTOS port 汇编和链接脚本，确认 PSP/MSP 使用关系。
6. 对主栈增加水印监测，执行最大中断嵌套故障注入。
7. 将任务栈报告和 RAM 预算接入 CI，栈需求显著增长时要求审查。

### 性能测试方法

- 在目标板记录高水位扫描的执行时间和采样周期。
- 使用发布构建、真实主频、实际 FPU 和中断配置。
- 覆盖最大输入、错误路径、任务切换、异常嵌套和低内存状态。
- 在调试器中检查任务 SP、栈起止地址和溢出钩子现场。
- 将任务栈和主栈数据分别记录，避免指标混淆。
- 对版本升级、编译器升级、LTO、优化等级和 libc 变化触发重新测试。

### 进阶学习方向

- Cortex-M 异常压栈、MSP/PSP 与 FreeRTOS 上下文切换汇编。
- FPU lazy stacking 对异常栈和任务栈的影响。
- 编译器静态调用图、栈使用分析和递归上界证明。
- MPU guard region、栈隔离和故障现场恢复。
- 高完整性系统中的栈预算、覆盖率和安全论证。
- 多核 RTOS 中每核异常栈、任务迁移与栈保护设计。
