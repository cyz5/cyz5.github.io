## 1. 学习目标

### 理解

- 解释任务的 Ready、Running、Blocked、Suspended 等状态及状态转换。
- 理解固定优先级抢占式调度、同优先级时间片调度和优先级反转。
- 理解 RTOS 优先级数值与“高优先级”的对应关系因内核而异。

### 掌握

- 按任务截止期、周期和执行时间划分任务优先级。
- 使用静态任务创建、周期任务、任务通知、队列及互斥锁。
- 测量任务切换、唤醒延迟、任务栈余量和 CPU 占用率。

### 精通

- 基于响应时间分析识别不可调度任务集。
- 评估优先级继承、互斥锁持有时间和阻塞时间对实时性的影响。
- 从内核调度路径和 MCU 异常上下文切换路径定位抖动与延迟。

### 能够设计

- 设计可做响应时间分析的任务集合和优先级表。
- 设计任务间通信、共享资源访问及过载退化策略。
- 建立可复测的调度性能基准和在线任务健康监控机制。

## 3. 技术概述

### 3.1 定义

**任务**是 RTOS 的调度实体，通常拥有独立栈、任务控制块（TCB）、优先级和运行状态。调度器根据就绪任务及调度策略，决定哪个任务获得 CPU。

**优先级管理**是为任务分配调度等级，并通过调度规则、阻塞关系、继承机制等，控制任务获得 CPU 的顺序与时机。

### 3.2 技术价值

任务和优先级管理解决的不是“代码怎么并行执行”，而是：

- 如何满足任务的响应时间与截止期。
- 如何限制低重要性工作对实时工作的干扰。
- 如何让事件驱动任务在无工作时阻塞，降低 CPU 和功耗开销。
- 如何控制共享资源竞争导致的时序不确定性。
- 如何在系统过载时，保证关键功能优先运行并让非关键功能可控退化。

### 3.3 主流实现分支

1. **固定优先级抢占式调度**：工程上最常见，FreeRTOS、ThreadX、Zephyr 均支持。
2. **协作式调度**：任务主动让出 CPU；对任务行为约束较强。
3. **同优先级轮转调度**：多个同优先级就绪任务按时间片轮转。
4. **动态优先级调度**：运行中改变任务优先级，常见于优先级继承或特定调度算法。
5. **EDF（Earliest Deadline First）** ：按绝对截止期动态调度，常用于需要更高处理器利用率或特定实时分析的系统。

## 4. 核心特性横向对比

### 4.1 调度策略对比

|方案|调度依据|抢占能力|优点|风险与代价|适用场景|
|---|---|---|---|---|---|
|固定优先级抢占|任务静态优先级|强|行为可预测、易于审查|优先级分配不当会饥饿或错过截止期|控制、仪器、工业设备|
|固定优先级协作|任务主动让出|弱|调度开销低|一个任务不让出就会阻塞全系统|极小型、行为完全受控的系统|
|同优先级时间片|优先级相同后轮转|中|避免同级任务长期独占|时间片通常依赖系统 tick，增加切换开销|多个同级后台任务|
|EDF|绝对截止期|强|在经典假设下处理器利用率高|动态维护开销与分析复杂度更高|任务集动态、截止期驱动明显的系统|

### 4.2 常见 RTOS 优先级约定对比

|RTOS / 接口|数值方向|说明|
|---|---|---|
|FreeRTOS 原生 API|数值越大，优先级越高|`0` 通常为最低优先级；有效范围通常为 `0 ... configMAX_PRIORITIES-1`|
|Zephyr|数值越小，优先级越高|线程优先级和调度类别还受配置影响|
|ThreadX|数值越小，优先级越高|`0` 通常为最高优先级|
|CMSIS-RTOS2|使用 `osPriority...` 枚举|映射到具体底层内核时需核对适配层|

**工程规则：** 不要仅凭“优先级 5 比优先级 3 高”推断行为；必须核对所用 RTOS 的数值约定和配置。

### 4.3 优先级反转处理机制

|机制|行为|优点|局限|
|---|---|---|---|
|无继承互斥锁|高优先级任务等待低优先级持锁任务|实现简单|中优先级任务可能持续抢占低优先级持锁者|
|优先级继承（PI）|持锁者临时提升至等待者中的高优先级|缩短经典优先级反转|需要分析嵌套锁和持锁时长|
|优先级上限（PCP/Ceiling）|进入资源区时提升到预设上限|可限制阻塞链长度|资源访问关系和上限配置更复杂|
|直接禁抢占/关中断|临界区内阻止调度或中断|短小临界区开销低|延长中断延迟，不能作为长资源保护方案|

## 5. 底层原理与功能特性深度解析

### 5.1 FreeRTOS 任务状态及数据结构

常见任务状态包括：

- **Running**：当前正在 CPU 上执行。单核系统同一时刻只有一个任务处于运行状态。
- **Ready**：任务可运行，但 CPU 当前分配给了其他任务。
- **Blocked**：等待时间、队列、信号量、通知等事件。
- **Suspended**：由应用显式挂起，不会因为超时自动恢复。
- **Deleted**：已请求删除；动态分配任务所占资源通常由 Idle 任务清理。

在 FreeRTOS 中，任务控制块 `TCB_t` 保存栈顶指针、状态链表节点、事件链表节点、优先级、栈起始地址、任务名等信息。就绪任务通常按优先级组织在多个就绪链表中；延时任务和等待事件的任务也通过链表管理。

**要点：** 状态是内核内部调度状态，不应由应用代码自行推断或修改。需要诊断时，优先使用 trace hook、运行时统计和任务列表接口。

### 5.2 调度路径：从任务变为就绪到获得 CPU

FreeRTOS 的典型路径可以概括为：

1. 任务等待事件或调用延时 API，进入 Blocked。
2. tick 中断或事件发生，内核将该任务从等待链表移入 Ready 链表。
3. 内核判断新任务是否比当前任务优先级更高。
4. 若需要切换，设置 PendSV 等待挂起异常。
5. PendSV 保存当前任务上下文、选择下一个任务、恢复新任务上下文。

核心逻辑分布在 `tasks.c` 的调度和 tick 处理路径，以及具体端口的 `port.c` 上下文切换代码中。对于 Cortex-M，**PendSV 通常设为最低系统异常优先级**，以便不会打断高优先级中断处理。

> 源码符号和优化路径会随 FreeRTOS 版本、编译宏和端口变化。分析时应查阅项目实际使用的 `tasks.c`、`port.c`，不要只依据 API 手册推断执行开销。

### 5.3 就绪任务选择与复杂度

内核需要从 Ready 任务中选择最高优先级任务。

- 通用实现可能遍历优先级，选择过程开销随优先级数量增长。
- Cortex-M 等端口可启用优化选择，通过优先级位图和位扫描快速找到最高优先级。
- 同优先级时间片轮转通常通过轮换该优先级就绪链表中的任务实现。

是否启用优化选择、最大优先级数限制及位图实现方式，取决于 FreeRTOS 版本和端口配置。应核对 `configUSE_PORT_OPTIMISED_TASK_SELECTION` 及相关端口实现。

### 5.4 优先级和抢占

FreeRTOS 固定优先级抢占模式下，较高优先级 Ready 任务通常可抢占较低优先级 Running 任务。以下情况会推迟切换：

- 调度器暂停期间。
- 内核临界区或端口临界区期间。
- 更高优先级中断仍在执行期间。
- 当前任务或平台配置不允许立即进行相应切换时。

**任务优先级不等于业务重要性。** 分配优先级的核心依据应是截止期、执行时间、阻塞时间和干扰，而不是模块名称或代码“看起来重要”。

### 5.5 任务创建与栈的单位

FreeRTOS `xTaskCreateStatic()` 的栈深度单位是 **`StackType_t` 元素数量**，不是字节数。

```
#define CONTROL_STACK_WORDS    320U

static StackType_t control_stack[CONTROL_STACK_WORDS];
static StaticTask_t control_tcb;

static void control_task(void *arg)
{
    (void)arg;

    for (;;)
    {
        /* 执行控制计算；完成后等待下一周期或事件。 */
        vTaskDelay(pdMS_TO_TICKS(10U));
    }
}

static TaskHandle_t create_control_task(void)
{
    return xTaskCreateStatic(
        control_task,
        "control",
        CONTROL_STACK_WORDS,     /* 单位：StackType_t 个数 */
        NULL,
        4U,
        control_stack,
        &control_tcb);
}
```

栈大小需要结合编译器、调用深度、局部变量、浮点上下文保存方式、异常嵌套和库函数使用情况确定，不能只按经验给一个“通用值”。

可使用 `uxTaskGetStackHighWaterMark()` 观察任务运行期间的最小剩余栈水位。该接口在常见 FreeRTOS 配置中返回以 `StackType_t` 为单位的水位，但需要核对所用端口和 API 版本。

### 5.6 周期任务：固定周期而非相对延时

如果使用 `vTaskDelay()`，执行时间会累积到周期中，形成周期漂移。固定周期任务一般优先使用 `vTaskDelayUntil()`：

```
static void periodic_task(void *arg)
{
    const TickType_t period = pdMS_TO_TICKS(5U);
    TickType_t last_wake = xTaskGetTickCount();

    (void)arg;
    configASSERT(period > 0U);

    for (;;)
    {
        /* 执行时间需纳入周期和截止期分析。 */
        run_control_step();

        /*
         * 按上一次计划唤醒时刻推进，降低任务执行时间造成的周期漂移。
         * 若执行超时，调用可能立即返回；仍需另外记录 deadline miss。
         */
        vTaskDelayUntil(&last_wake, period);
    }
}
```

如果任务超期，`vTaskDelayUntil()` 并不能自动消除超期，只是保持计划时间基准。应用必须定义超期策略：记录、丢弃过期工作、降级运行、触发安全状态或复位。

### 5.7 优先级继承与 FreeRTOS 的工程限制

典型优先级反转：

1. 低优先级任务持有共享资源。
2. 高优先级任务等待该资源。
3. 中优先级任务抢占低优先级任务。
4. 高优先级任务因低优先级任务迟迟不能释放资源而被间接阻塞。

FreeRTOS 的**互斥锁（mutex）** 支持优先级继承；二值信号量一般不提供互斥锁语义，也不应替代互斥锁来保护需要继承优先级的资源。FreeRTOS 的继承实现属于简化实现，涉及多个互斥锁时，反转恢复行为可能不如完整协议精细；应根据所用版本源码和项目锁关系验证。

设计原则：

- 临界区尽量短，禁止持锁期间执行阻塞 I/O、长计算或无界等待。
- 明确锁的获取顺序，避免锁顺序反转造成死锁。
- 不要依赖“提升优先级”解决错误的锁粒度或阻塞设计。
- 实时关键路径优先采用消息传递和单一资源所有者模式，减少共享状态。

## 6. 性能量化分析

### 6.1 栈与任务内存公式

对静态任务，RAM 预算至少要包含：

Mtasks=∑i=1N(Wi×sizeof(StackTypet)+sizeof(StaticTaskt))+Mqueues+Mtimers+Midle+MotherMtasks​=i=1∑N​(Wi​×sizeof(StackTypet​)+sizeof(StaticTaskt​))+Mqueues​+Mtimers​+Midle​+Mother​

其中：

- WiWi​：任务栈深度，单位为 `StackType_t` 个数。
- `sizeof(StaticTask_t)`：依 RTOS 版本、配置和 ABI 而变，不应硬编码。
- 队列存储空间需单独计算。
- Timer service task、Idle task 等也需要栈和 TCB。

例如 Cortex-M 上 `StackType_t` 常为 4 字节；320 个栈元素约为 **1280 字节栈空间**，但这不含 TCB。

### 6.2 CPU 占用和 tick 开销

若 tick 频率为 ftickftick​，每次 tick 处理耗时为 CtickCtick​ 个 CPU 周期，CPU 频率为 fCPUfCPU​，则：

Utick≈ftick×CtickfCPUUtick​≈fCPU​ftick​×Ctick​​

示例：假设 ftick=1000ftick​=1000 Hz、fCPU=400fCPU​=400 MHz，测得 tick 路径平均消耗 600 个周期：

Utick=1000×600400×106=0.15%Utick​=400×1061000×600​=0.15%

这仅统计 tick 处理本身，不包括 tick 中触发的任务切换、其他中断和驱动工作。

### 6.3 固定优先级响应时间分析

对于单核、固定优先级抢占式任务集，常用响应时间迭代公式：

Ri=Ci+Bi+∑j∈hp(i)⌈RiTj⌉CjRi​=Ci​+Bi​+j∈hp(i)∑​⌈Tj​Ri​​⌉Cj​

- CiCi​：任务 ii 的最坏执行时间。
- BiBi​：低优先级任务或资源造成的最大阻塞时间。
- TjTj​：高优先级任务 jj 的周期或最小到达间隔。
- hp(i)hp(i)：所有高于任务 ii 的任务集合。
- 可调度条件通常要求 Ri≤DiRi​≤Di​，其中 DiDi​ 是相对截止期。

示例（假设单核、忽略中断干扰和阻塞）：

|任务|周期 TT|执行时间 CC|截止期 DD|优先级|
|---|---|---|---|---|
|A|5 ms|0.3 ms|5 ms|最高|
|B|10 ms|0.8 ms|10 ms|中|
|C|20 ms|2.0 ms|20 ms|低|

利用率：

U=0.3/5+0.8/10+2.0/20=24%U=0.3/5+0.8/10+2.0/20=24%

按从高到低计算：

- RA=0.3RA​=0.3 ms
- RB=0.8+⌈0.8/5⌉×0.3=1.1RB​=0.8+⌈0.8/5⌉×0.3=1.1 ms
- RCRC​ 迭代：先得到 2.0+0.3+0.8=3.12.0+0.3+0.8=3.1 ms；再计算干扰项，仍为 3.13.1 ms

此示例全部满足截止期，但实际分析还必须加入中断干扰、最长临界区、调度器暂停和测量误差。

### 6.4 性能测量方法与数据边界

用户尚未指定 MCU、时钟、FreeRTOS 版本、编译器和优化选项，因此**无法诚实地给出可称为“实测”的通用任务切换数据**。不同端口、FPU 使用、缓存、编译选项和临界区都会显著改变结果。

建议在目标板上建立以下基准：

|指标|测量方式|关注因素|
|---|---|---|
|任务切换周期数|PendSV 入口/出口或 trace hook 读取 DWT|上下文保存、FPU、调度器优化|
|中断到任务响应时间|ISR 置 GPIO，任务运行后清 GPIO|中断优先级、PendSV、临界区|
|tick 路径周期数|SysTick 入口/出口读取 DWT|tick 频率、延时链表活动量|
|任务栈余量|栈水位 API 加压力测试|最大调用深度、异常嵌套、库函数|
|运行时 CPU 占用|FreeRTOS runtime stats 或周期计数|统计时钟精度、测量窗口|

测量时同时记录芯片型号、频率、Flash wait states、缓存设置、编译器版本、优化等级、RTOS 版本和配置宏。**平均值不能替代 WCET；实时性决策应看上界和最坏干扰条件。**

## 7. 应用场景选型指南

### 7.1 纯文本决策流程图

```
任务是否有明确截止期或严格响应时间要求？
├─ 是
│  ├─ 是否需要中断级响应？
│  │  ├─ 是：ISR 中只做最短采集/确认，必要时用 DMA；
│  │  │      将后续工作通知给高优先级任务。
│  │  └─ 否：采用固定优先级抢占调度，做响应时间分析。
│  └─ 是否涉及共享资源？
│     ├─ 是：优先改成消息传递/单一资源所有者；
│     │      必须共享时使用互斥锁并限制持锁时间。
│     └─ 否：事件通知或队列阻塞等待。
└─ 否
   ├─ 是否属于周期性工作？
   │  ├─ 是：使用 vTaskDelayUntil，监控周期超期。
   │  └─ 否：使用队列、任务通知或工作队列等待事件。
   └─ 是否为可丢弃/可降级工作？
      ├─ 是：放在较低优先级，设计过载丢弃策略。
      └─ 否：重新评估截止期和资源预算。
```

### 7.2 典型场景

|需求|推荐方案|理由|
|---|---|---|
|电机电流环，数十微秒级更新|PWM/ADC 同步中断或 DMA，任务负责较慢控制与配置|超短且硬件同步的闭环不宜依赖普通任务调度|
|传感器异步采样后处理|ISR 采集/入队，较高优先级任务处理|ISR 轻量，处理逻辑可分析、可扩展|
|网络协议与日志|中低优先级任务、队列、有限队列深度|避免非实时工作干扰控制任务|
|多任务访问同一外设|单一驱动任务作为资源所有者，其他任务发请求|降低锁竞争、死锁和时序耦合|
|低功耗周期采样|阻塞等待定时器/通知，合理配置 tickless idle|避免空转和过度唤醒|

## 8. 工程最佳实践

### 8.1 设计原则

1. **先定义截止期，再分配优先级。** 优先级反映调度需求，不代表代码重要性或开发团队级别。
2. **优先级数量保持可管理。** 用清晰的优先级带表示实时等级，避免每个任务都拥有唯一优先级。
3. **事件驱动任务必须阻塞。** 没有工作时调用队列、通知或延时 API，不允许无限轮询。
4. **高优先级任务应短且可阻塞。** 不要让高优先级任务持续计算并长期占用 CPU。
5. **任务间尽量传递消息，不共享可变状态。** 共享资源越多，锁与阻塞分析越困难。
6. **每个任务都应有过载策略。** 例如队列满时计数、丢弃、合并请求或进入安全状态。
7. **栈大小与 WCET 都必须验证。** 压力测试覆盖最长路径、错误路径、浮点和深层调用。

### 8.2 选型决策矩阵

|条件|推荐决策|
|---|---|
|关键任务周期固定、截止期清晰|固定优先级 + 响应时间分析|
|事件不可丢失且需有界排队|有界队列，并定义队列满处理策略|
|单生产者向单消费者发事件|任务通知可减少数据结构和拷贝开销|
|多任务保护共享资源|互斥锁；审查锁顺序和持锁时间|
|设备驱动访问串行且耗时|单一驱动任务拥有设备，使用请求队列|
|系统无动态创建需求|静态任务/队列创建，便于 RAM 预算和审查|

### 8.3 工业级编码与配置规范

- 任务栈、TCB、队列深度、任务优先级集中定义并审查。
- 任务名具备模块语义；日志中记录任务名、优先级、堆栈余量和超期计数。
- 确认 `configMAX_PRIORITIES`、`configUSE_PREEMPTION`、`configUSE_TIME_SLICING`、栈溢出检查和运行时统计配置。
- Cortex-M 上确认 RTOS 可调用中断的 NVIC 优先级范围，遵守 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 等约束。
- 使用 `configASSERT()` 检查创建失败、周期换算为零、非法优先级和资源初始化失败。
- 关键任务不要依赖动态优先级调整来“修补”架构问题。
- 在 CI 或启动自检中验证任务数、栈预算、优先级表和配置文件的一致性。

## 9. 常见错误与避坑指南

### 错误一：高优先级任务无限轮询，导致其他任务饥饿

**错误代码**

```
static void event_task(void *arg)
{
    for (;;)
    {
        if (event_is_ready())
        {
            process_event();
        }
    }
}
```

**根因分析：** 任务始终 Ready，优先级高于其他任务时会持续占用 CPU。

**正确实现：**

```
static void event_task(void *arg)
{
    for (;;)
    {
        /* 阻塞直到事件到达。 */
        (void)ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
        process_pending_events();
    }
}
```

**风险影响：** 低优先级任务饥饿、Idle 任务无法运行、看门狗或低功耗策略失效。

---

### 错误二：把字节数当作 FreeRTOS 栈深度

**错误代码**

```
xTaskCreate(task_fn, "task", 1024U, NULL, 2U, NULL); /* 常见错误：误认为 1024 字节 */
```

**根因分析：** FreeRTOS 常见 API 的栈深度参数以 `StackType_t` 个数计，不是字节。

**正确实现：**

```
#define TASK_STACK_BYTES  1024U
#define TASK_STACK_WORDS  (TASK_STACK_BYTES / sizeof(StackType_t))

configASSERT((TASK_STACK_BYTES % sizeof(StackType_t)) == 0U);
```

**风险影响：** 实际分配的栈比预期大或小，导致 RAM 预算错误或栈溢出。

---

### 错误三：用相对延时实现固定周期，造成周期漂移

**错误代码**

```
for (;;)
{
    do_work();
    vTaskDelay(pdMS_TO_TICKS(10U));
}
```

**根因分析：** 实际周期等于工作时间加延时时间。

**正确实现：**

```
TickType_t last_wake = xTaskGetTickCount();

for (;;)
{
    do_work();
    vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(10U));
}
```

**风险影响：** 采样周期漂移、控制算法时基误差、不同任务逐渐失去相位关系。

---

### 错误四：用二值信号量代替互斥锁保护需要 PI 的资源

**错误代码**

```
SemaphoreHandle_t lock = xSemaphoreCreateBinary();
/* 多任务通过该信号量互斥访问长时间资源 */
```

**根因分析：** 二值信号量和互斥锁语义不同；不应假设二值信号量具有互斥锁的优先级继承行为。

**正确实现：**

```
SemaphoreHandle_t lock = xSemaphoreCreateMutex();

if (lock == NULL)
{
    enter_safe_failure_state();
}
```

**风险影响：** 优先级反转延长关键任务阻塞时间；若错误地由 ISR 操作，还会引入不可预测行为。

---

### 错误五：把 RTOS 任务优先级和 NVIC 中断优先级混为一谈

**错误表现：** 给某个任务设置高优先级后，认为它可以抢占正在运行的高优先级中断。

**根因分析：** RTOS 任务调度发生在可进行上下文切换的时机；正在执行的中断优先级与任务优先级属于不同调度层级。

**正确做法：**

- ISR 只完成短小、确定的工作。
- 通过 `...FromISR()` API 通知任务。
- 检查中断优先级是否满足 RTOS 可调用 API 的约束。

**风险影响：** 错误的中断 API 调用可能破坏内核状态；过长 ISR 会增加所有任务响应延迟。

---

### 错误六：锁内执行无界等待或长计算

**错误代码**

```
xSemaphoreTake(device_mutex, portMAX_DELAY);
wait_for_device_forever();
xSemaphoreGive(device_mutex);
```

**根因分析：** 锁持有时间无界，其他任务的阻塞时间也无界。

**正确做法：**

- 将设备访问集中到驱动任务，由队列串行化请求。
- 若必须持锁，设置有限超时，锁外等待设备完成。
- 记录最大持锁时长，并将其纳入响应时间分析。

**风险影响：** 关键任务错过截止期、死锁、系统看门狗复位。

---

## 10. 多机制组合使用方案

### 10.1 推荐架构

```
硬件 ISR / DMA
     │  FromISR 通知或队列投递
     ▼
高优先级事件处理任务
     │  消息队列
     ├──────────────► 控制任务
     │
     └──────────────► 通信/日志任务（低优先级）
                              │
                         资源所有者任务
                         （单独访问外设）
```

组合原则：

- **静态创建**：固定数量任务和队列，启动时完整检查资源。
- **任务通知**：轻量唤醒单个任务；需要携带多条数据时使用队列。
- **有界队列**：明确队列满时的丢弃、覆盖或降级行为。
- **互斥锁**：只用于不可避免的短临界区，不作为默认通信手段。
- **优先级继承**：缓解部分资源阻塞，不能替代锁粒度和架构分析。

### 10.2 FreeRTOS 框架示例

以下代码展示静态队列、静态任务和 ISR 入队框架。具体传感器读取和输出驱动由项目实现。

```
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

#include <stdint.h>
#include <stdbool.h>

#define SAMPLE_QUEUE_DEPTH      16U
#define ACQ_TASK_STACK_WORDS    320U
#define PROC_TASK_STACK_WORDS   384U

#if (configMAX_PRIORITIES < 5)
#error "该示例要求 configMAX_PRIORITIES 至少为 5"
#endif

typedef struct
{
    uint32_t timestamp;
    int32_t  value;
} sample_t;

static StaticQueue_t g_sample_queue_ctrl;
static sample_t g_sample_queue_storage[SAMPLE_QUEUE_DEPTH];
static QueueHandle_t g_sample_queue;

static StaticTask_t g_process_tcb;
static StackType_t g_process_stack[PROC_TASK_STACK_WORDS];
static TaskHandle_t g_process_task;

static StaticTask_t g_logger_tcb;
static StackType_t g_logger_stack[ACQ_TASK_STACK_WORDS];
static TaskHandle_t g_logger_task;

/* 由 BSP/驱动层实现：不得在 ISR 中执行无界工作。 */
extern void process_sample(const sample_t *sample);
extern void log_drop_count(uint32_t count);
extern uint32_t get_and_clear_isr_drop_count(void);
extern void enter_safe_failure_state(void);

static void process_task(void *arg)
{
    sample_t sample;

    (void)arg;

    for (;;)
    {
        /*
         * 阻塞等待，避免空转。
         * 队列深度和最坏消费时间必须经过负载验证。
         */
        if (xQueueReceive(g_sample_queue, &sample, portMAX_DELAY) == pdPASS)
        {
            process_sample(&sample);
        }
    }
}

static void logger_task(void *arg)
{
    (void)arg;

    for (;;)
    {
        const uint32_t drops = get_and_clear_isr_drop_count();

        if (drops != 0U)
        {
            log_drop_count(drops);
        }

        vTaskDelay(pdMS_TO_TICKS(1000U));
    }
}

/*
 * 在具有适当中断优先级配置的 ISR 中调用。
 * 任务队列满时采取“丢弃并计数”策略；是否适合项目，需由需求决定。
 */
void sensor_data_ready_isr(uint32_t timestamp, int32_t value)
{
    BaseType_t higher_priority_woken = pdFALSE;
    const sample_t sample = {
        .timestamp = timestamp,
        .value = value
    };

    if (xQueueSendFromISR(
            g_sample_queue,
            &sample,
            &higher_priority_woken) != pdPASS)
    {
        /* 实际项目应使用适合 ISR 的计数方式并处理计数回绕。 */
        record_isr_drop();
    }

    portYIELD_FROM_ISR(higher_priority_woken);
}

bool app_tasks_init(void)
{
    g_sample_queue = xQueueCreateStatic(
        SAMPLE_QUEUE_DEPTH,
        sizeof(sample_t),
        (uint8_t *)g_sample_queue_storage,
        &g_sample_queue_ctrl);

    if (g_sample_queue == NULL)
    {
        enter_safe_failure_state();
        return false;
    }

    /*
     * FreeRTOS：优先级数值越大，优先级越高。
     * 示例设定：事件处理任务高于低优先级日志任务。
     */
    g_process_task = xTaskCreateStatic(
        process_task,
        "sample_proc",
        PROC_TASK_STACK_WORDS,
        NULL,
        4U,
        g_process_stack,
        &g_process_tcb);

    if (g_process_task == NULL)
    {
        enter_safe_failure_state();
        return false;
    }

    g_logger_task = xTaskCreateStatic(
        logger_task,
        "logger",
        ACQ_TASK_STACK_WORDS,
        NULL,
        1U,
        g_logger_stack,
        &g_logger_tcb);

    if (g_logger_task == NULL)
    {
        enter_safe_failure_state();
        return false;
    }

    return true;
}
```

工程化补充：

- `record_isr_drop()` 必须是 ISR 安全实现；如果由任务读取计数，应采用原子操作或受控临界区，避免读改写竞态。
- 若每个采样都不可丢失，应改用 DMA 环形缓冲区、硬件 FIFO 或足够容量的缓冲策略，而不是简单丢弃。
- 高优先级任务必须有实际阻塞点，否则低优先级日志任务无法运行。
- 任务、队列创建失败时，进入安全故障路径；若使用动态创建，还要明确资源回收责任。

## 11. 工业级实际案例分析

### 案例一：电机驱动控制器

**需求**

- PWM 与 ADC 由硬件定时同步。
- 电流环更新具有微秒到数十微秒级时序要求。
- 通信和日志不能干扰控制闭环。

**架构设计**

```
PWM/ADC 触发
  └─ ADC DMA / 短中断：记录样本、确认状态
       └─ 电流环快速处理：硬件同步路径
            ├─ 较慢速度环任务：固定周期
            └─ 通信/日志任务：低优先级、队列传递
```

**核心设计要点**

- 对严格同步的电流环，通常由 PWM/ADC/DMA/中断链路保证时序；不能仅因任务优先级高，就假设其满足严格闭环时间。
- 速度环和状态机可用 `vTaskDelayUntil()`。
- 高频测量数据采用环形缓冲区，避免每个中断样本都创建一个任务事件。
- 通信任务处理不完时允许丢弃低价值遥测，不允许阻塞控制路径。
- 用 GPIO 标记 PWM 事件、ISR 起止和控制输出更新时间，实测最大延迟与抖动。

### 案例二：工业网关

**需求**

- 多路串口或 CAN 数据进入系统。
- 协议解析、转发、日志和远程管理并发运行。
- 通信突发时系统不能因日志阻塞丢失控制消息。

**架构设计**

- ISR/DMA 将数据写入环形缓冲区。
- 高优先级通信收取任务负责搬运和快速分类。
- 协议处理任务通过有界队列接收消息。
- 日志任务低优先级运行，设置独立缓冲容量和丢弃策略。
- 外设由单一驱动任务拥有，其他任务以消息请求访问。

**设计要点**

- 各队列都要有容量依据：依据最大突发速率、最坏消费延迟和可接受积压量估算，而不是拍脑袋设置。
- 协议解析避免长时间持有锁；复杂数据处理放在任务上下文完成。
- 在总线过载时进行优先级分类、过滤、合并或丢弃低优先级消息。
- 统计队列高水位、溢出次数和最久等待时间，作为现场诊断指标。

### 案例三：安全监测设备

**需求**

- 高优先级报警事件必须快速响应。
- 状态记录和远程上传可以延迟。
- 关键事件需要可审计且不能被普通日志流量挤掉。

**架构设计**

- 报警检测采用独立高优先级任务，或由短 ISR 通知任务处理。
- 安全状态切换由专门任务或确定的状态机负责。
- 普通日志和远程上传放在低优先级任务。
- 报警事件使用独立高优先级队列或专用锁存标志，避免被普通消息队列淹没。

**设计要点**

- 不能只通过“调高报警任务优先级”保证安全：还应分析中断延迟、临界区、资源阻塞及报警路径 WCET。
- 过载时允许降低遥测、日志和非关键维护任务服务质量，但应保留安全事件处理能力。
- 定义报警处理失败、任务未按期运行、栈余量不足时的安全状态和 watchdog 策略。

## 12. 高频问题深度答疑

### Q1：优先级是不是越多、分得越细越好？

不是。优先级过多会提高评审、验证和重构成本。若两个任务截止期、阻塞关系和实时等级相近，通常可以分配在同一优先级，并验证同级轮转和最大响应时间。真正重要的是任务集可分析，而不是优先级编号“精细”。

### Q2：高优先级任务能不能永远不阻塞？

通常不能。持续 Ready 的高优先级任务会压制低优先级任务；即使高优先级任务本身没有错过截止期，也可能导致 Idle、日志、管理任务甚至看门狗维护任务无法运行。高优先级任务应只在必须快速处理时运行，完成工作后阻塞等待下一事件或周期。

### Q3：任务优先级继承能彻底消除优先级反转吗？

不能简单这样认为。PI 可以减轻经典反转，但不能消除锁顺序错误、无界持锁、长时间等待外设、死锁或中断引入的延迟。多个锁、嵌套锁和递归锁还会增加分析难度。优先级继承是缓解机制，不是资源管理架构的替代品。

### Q4：任务数越少，系统就越实时吗？

不一定。任务过多会增加栈、TCB 和调度管理成本；但把所有工作合并成单个任务，也可能导致长执行路径、职责耦合和响应时间难以界定。任务边界应基于独立的周期、截止期、事件源和资源所有权划分。

### Q5：同优先级任务会自动轮转吗？

取决于 RTOS 和配置。FreeRTOS 的时间片行为受内核配置和调度路径影响；不要假设所有 RTOS 都按固定 tick 自动轮转。若同级任务长期计算且不阻塞，验证其调度公平性，并考虑拆分工作、设置明确阻塞点或重新评估优先级。

### Q6：任务优先级和中断优先级怎么配合？

它们属于不同层级。正在执行的中断能否打断其他代码由 NVIC 优先级控制；任务间调度由 RTOS 优先级控制。ISR 通常应短小，把耗时处理交给任务。Cortex-M 上还必须正确配置 RTOS 可调用的中断优先级范围，否则 ISR 调用内核 API 可能破坏内核状态。

## 13. 课程核心总结

### 核心要点

- 任务管理的核心是状态转换、阻塞关系、上下文切换和资源预算。
- 优先级应由截止期、执行时间、阻塞时间和干扰共同决定。
- 高优先级任务不能长期空转；空闲时应阻塞等待事件。
- 优先级继承只对特定互斥资源场景有帮助，不能代替资源架构设计。
- 必须测量目标板上的切换延迟、最大响应时间、栈余量和队列高水位。

### 性能排序

从减少任务调度和通信开销角度，通常可以粗略理解为：

1. **ISR/DMA 直接完成极短硬件动作**：延迟低，但受 ISR 最小化和中断安全约束。
2. **任务通知等轻量唤醒机制**：适合单任务事件通知。
3. **有界队列传递消息**：适合携带数据和多生产者/消费者场景，需考虑拷贝和队列管理。
4. **互斥锁共享资源**：同步和阻塞成本较高，且需要分析优先级反转。

实际排序受 CPU、端口、消息大小、临界区和缓存影响，必须通过目标板测量确认。

### 通用选型结论

- 时间极紧且硬件同步的路径：优先使用外设、DMA 和最短 ISR。
- 周期性任务：优先使用固定优先级和 `vTaskDelayUntil()`。
- 异步事件：用通知或队列阻塞等待。
- 共享资源：优先改为单一资源所有者；必须共享时使用正确的互斥机制。
- 关键任务：做响应时间分析并定义超期处置策略。

## 14. 快速参考速查表

### 场景选型表

|场景|优先级策略|通信/同步|重点检查|
|---|---|---|---|
|固定周期控制|截止期驱动的固定优先级|周期唤醒、必要时通知|WCET、抖动、超期计数|
|ISR 触发处理|ISR 唤醒高优先级任务|通知或 FromISR 队列|NVIC API 优先级约束|
|共享外设|独立驱动任务优先|请求队列|队列满策略、最大排队时延|
|日志与遥测|低优先级|缓冲区/队列|过载丢弃、对关键任务的干扰|
|多任务共享短临界区|按截止期安排优先级|互斥锁|持锁时间、锁顺序、PI 行为|

### 特性对比表

|机制|适合用途|主要优势|主要风险|
|---|---|---|---|
|固定优先级抢占|实时任务集|行为可分析、实现普遍|优先级配置错误会饥饿|
|时间片轮转|同级任务公平运行|避免同级长期独占|tick 带来额外切换和抖动|
|任务通知|单任务事件通知|轻量、直接|不能直接替代所有多数据队列场景|
|队列|消息传递和缓存|边界明确、可解耦|队列满和拷贝成本需设计|
|互斥锁|共享资源互斥|有所有权语义，常支持 PI|阻塞、死锁及持锁时延|
|静态任务创建|固定任务集合|内存确定、启动行为清晰|需要提前规划静态 RAM|

## 16. 实践与进阶路径

### 阶段一：任务状态与调度验证

- 创建三个不同优先级任务，分别使用周期延时、队列阻塞和无限轮询。
- 观察任务列表、CPU 占用和 Idle 任务运行情况。
- 修复高优先级空转造成的低优先级饥饿。

### 阶段二：优先级反转复现

- 设计低优先级持锁、高优先级等待、中优先级持续运行的实验。
- 比较普通信号量、互斥锁和不共享资源的单一所有者模式。
- 测量高优先级任务最大阻塞时间，而不仅观察平均值。

### 阶段三：响应时间分析

- 构造 3～5 个周期任务，测量或估算 WCET。
- 加入 ISR 干扰和最长临界区，计算响应时间。
- 故意提高任务利用率或延长临界区，验证何时出现 deadline miss。

### 阶段四：建立性能基准

- 用 DWT `CYCCNT` 测量任务切换、ISR 到任务响应和 tick 路径。
- 用 GPIO 和示波器验证外部可见延迟与抖动。
- 对每项结果记录硬件、工具链、配置和测试条件，并使用压力负载测量最坏值。
- 对所有任务进行栈压力测试，覆盖异常路径、日志路径、浮点路径和最大调用深度。

### 进阶方向

- 深入阅读目标 FreeRTOS 版本中的 `tasks.c`、`queue.c` 和 Cortex-M `port.c`。
- 学习响应时间分析、优先级天花板协议、WCET 分析和实时系统过载处理。
- 研究 Zephyr 的调度器、线程优先级及工作队列模型，并对比其与 FreeRTOS 的资源管理方式。
- 建立 CI 静态检查：任务优先级表、栈预算、配置宏、队列容量和实时需求之间的一致性。
