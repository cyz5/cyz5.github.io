
## 1. 学习目标

### 理解

- 理解任务状态机、优先级调度、抢占、阻塞和唤醒之间的关系。
- 区分任务执行时间、调度等待时间、阻塞时间和端到端响应时间。
- 理解任务行为分析需要结合内核事件、同步对象、业务事件和硬件时序，单看 CPU 使用率不足以定位根因。

### 掌握

- 使用 Tracealyzer 或 SystemView 分析任务切换、状态转换、任务优先级和同步对象事件。
- 通过任务状态快照、运行时间统计、队列水位和任务栈高水位建立行为证据。
- 为关键任务定义释放、开始运行、阻塞、完成和超时等业务边界事件。

### 精通

- 定位任务饥饿、优先级反转、忙等、过度抢占、周期漂移和唤醒延迟。
- 分析任务与 ISR、队列、信号量、互斥锁和定时器服务任务之间的因果关系。
- 识别跟踪缺失、时间戳错误和采集扰动造成的误判。

### 能够设计

- 能设计可观测、可诊断的任务模型和事件规范。
- 能为关键实时任务建立可验证的时序预算及告警条件。
- 能将开发阶段的时间线分析转化为现场低开销监控指标。

## 2. 前置要求

### 知识要求

- 熟悉目标 RTOS 的任务状态、优先级调度和任务切换机制。
- 理解 ISR 上下文、关中断区间、临界区和调度器锁定。
- 熟悉队列、二值/计数信号量、互斥锁、事件组和软件定时器。
- 理解 CPU 运行时间、任务响应时间和截止时间的定义。

### 技能要求

- 能使用 SystemView、Tracealyzer 或目标平台的任务跟踪工具。
- 能读取任务快照、运行时间统计、栈高水位和队列水位。
- 能使用 DWT、硬件定时器或 GPIO 校验关键时序。
- 能构造可重复的负载，并关联固件版本、配置与跟踪文件。

## 3. 技术概述

任务行为分析是对任务在运行过程中的**状态、时序、调度关系和资源交互**进行观察与解释。核心问题不是“任务运行了多久”，而是：

- 任务何时具备运行条件？
- 任务何时实际获得 CPU？
- 任务为什么阻塞或被抢占？
- 它等待的资源何时可用？
- 任务是否满足端到端截止时间？
- ISR、其他任务或临界区对它造成了什么影响？

典型任务时间组成：

```
端到端响应时间
= 释放延迟
+ Ready 等待时间
+ 实际执行时间
+ 阻塞等待时间
+ 其他系统与外设延迟
```

任务行为分析常用数据源：

- **内核跟踪**：任务切换、阻塞、唤醒、优先级变化。
- **用户事件**：业务请求开始、处理阶段、完成和错误。
- **运行时统计**：任务 CPU 时间和窗口占用。
- **对象统计**：队列深度、信号量等待、互斥锁持有。
- **硬件测量**：周期计数器、GPIO、逻辑分析仪、ETM。
- **故障数据**：断言、看门狗原因、任务栈与寄存器快照。

## 4. 核心特性横向对比

|分析方法|可回答的问题|优点|局限|
|---|---|---|---|
|任务状态快照|采样时任务处于什么状态|开销低、易量产|不提供完整时间线|
|运行时间统计|哪些任务占用了 CPU|适合负载归因|无法单独解释等待和抢占原因|
|SystemView/Tracealyzer|何时切换、阻塞、唤醒及被抢占|时间关系和因果链清晰|依赖端口和事件完整性，有采集开销|
|用户事件埋点|业务阶段耗时和端到端时间|业务语义明确|插桩边界需要设计，遗漏路径会误导|
|GPIO/硬件计时|外部边沿和关键路径时间|可独立验证硬件时序|软件语义较少|
|日志|错误码和业务状态|易读、实现简单|高频日志扰动大，时间精度和顺序可能不可靠|

分析任务行为时，通常组合使用：**内核事件解释调度，业务事件解释功能阶段，硬件计时校验关键时限**。

## 5. 底层原理与功能特性深度解析

### 5.1 任务状态与调度关系

常见状态可概括为：

- **Running**：当前占用 CPU。
- **Ready**：可以运行，但等待调度。
- **Blocked**：等待时间、资源或事件。
- **Suspended**：被显式挂起，通常不参与正常调度。

状态变化的解释必须结合事件：

```
Blocked -> Ready：等待条件满足或超时
Ready -> Running：调度器选择了该任务
Running -> Ready：被更高优先级任务抢占，或时间片切换
Running -> Blocked：任务主动等待资源或延时
```

任务长时间没有运行，不一定是“卡死”。它可能一直处于 Blocked，也可能处于 Ready 却被更高优先级任务持续占用 CPU。应查看状态转换和时间线，而不是只看一次快照。

### 5.2 定义关键时序指标

对周期任务，建议定义：

- **释放时刻**：任务应开始工作的时间点。
- **实际开始时刻**：代码真正开始执行的时间点。
- **完成时刻**：该周期业务完成的时间点。
- **截止时间**：完成任务的最晚允许时刻。

由此计算：

```
调度等待时间 = 实际开始时刻 - 释放时刻
执行时间     = 完成时刻 - 实际开始时刻
响应时间     = 完成时刻 - 释放时刻
抖动         = 实际开始时刻相对预期释放时刻的偏差
```

代码中应明确这些边界，而不是把任务运行时间统计直接叫作“响应时间”。

```
enum {
    EVT_CONTROL_RELEASE = 0x201,
    EVT_CONTROL_BEGIN   = 0x202,
    EVT_CONTROL_END     = 0x203,
    EVT_CONTROL_LATE    = 0x204
};

void control_task(void *arg)
{
    (void)arg;

    TickType_t wake_time = xTaskGetTickCount();

    for (;;) {
        vTaskDelayUntil(&wake_time, CONTROL_PERIOD_TICKS);

        const uint32_t start = platform_cycle_count();
        trace_user_event(EVT_CONTROL_BEGIN, start);

        control_step();

        const uint32_t end = platform_cycle_count();
        trace_user_event(EVT_CONTROL_END, end);

        const uint32_t runtime = end - start;
        if (runtime > CONTROL_BUDGET_CYCLES) {
            trace_user_event(EVT_CONTROL_LATE, runtime);
            diagnostic_increment(DIAG_CONTROL_OVERRUN);
        }
    }
}
```

这是结构示例。`trace_user_event()` 应映射到项目当前 Tracealyzer、SystemView 或其他跟踪接口，并确认其任务/ISR 安全性。

### 5.3 分析任务阻塞原因

任务进入 Blocked 状态时，应识别阻塞源：

- 延时或周期等待；
- 队列为空或已满；
- 信号量不可用；
- 互斥锁被其他任务持有；
- 事件组条件未满足；
- 外设驱动等待完成；
- 软件定时器或任务通知等待。

对于同步对象，时间线应尽可能关联：

```
请求等待 -> 对象可用/事件到达 -> 任务 Ready -> 任务 Running
```

如果看到任务阻塞较久，但没有对象事件，可能是事件未插桩、事件丢失、等待的是外设状态，或调度器端口未记录该类对象。

### 5.4 Ready 等待与任务饥饿

**Ready 等待**表示任务具备运行条件，但调度器没有选择它。常见原因：

- 更高优先级任务持续 Ready；
- 同优先级任务使用时间片或持续占用；
- 长临界区、调度器锁定或关中断；
- 高频 ISR 持续打断任务；
- 任务优先级配置错误；
- SMP 系统中核心亲和性或锁竞争。

判断任务饥饿，需要统计 Ready 状态持续时间或通过时间线重建，而不是只看任务累计 CPU 时间。任务 CPU 占用低可能正是饥饿的表现。

### 5.5 任务优先级反转分析

经典优先级反转：

```
低优先级 L 持有互斥锁
高优先级 H 等待该锁
中优先级 M 抢占 L
L 无法运行并释放锁
H 长时间等待
```

检查要点：

- 资源是否使用互斥锁，而非普通二值信号量；
- 是否启用了优先级继承；
- 临界区是否包含阻塞调用或长时间计算；
- 锁是否存在嵌套与反向获取；
- 任务时间线是否能标记锁获取、释放和等待。

优先级继承可以缓解特定反转，但不能修复死锁、锁顺序错误或持锁期间进行慢速 I/O。

### 5.6 任务切换频繁与忙等

高切换率可能来自：

- 任务周期过短；
- 任务反复 `yield`；
- 队列/信号量来回唤醒；
- 短延时形成高频轮询；
- 任务运行时间过短，系统调度开销占比变大。

错误的轮询模式：

```
void sensor_task(void *arg)
{
    for (;;) {
        if (sensor_data_ready()) {
            process_sensor_data();
        }
        taskYIELD(); /* 仍然是持续轮询 */
    }
}
```

更合适的事件驱动模式：

```
void sensor_task(void *arg)
{
    for (;;) {
        if (ulTaskNotifyTake(pdTRUE, portMAX_DELAY) == 0U) {
            continue;
        }

        process_sensor_data();
    }
}
```

通知应在数据就绪的 ISR 或生产者任务中发送。若使用 ISR 通知，必须调用当前 RTOS 端口对应的 ISR-safe API，并正确处理是否需要切换任务的返回状态。

### 5.7 周期漂移与相对延时

周期任务若使用相对延时：

```
for (;;) {
    do_work();
    vTaskDelay(period);
}
```

周期实际长度近似为：

```
周期 = 执行时间 + 延时时间 + 调度延迟
```

执行时间变化会累计造成漂移。固定周期任务通常应使用 `vTaskDelayUntil()`，但仍需处理过载、tick 精度和任务错过周期的策略。

对高精度控制环，RTOS tick 可能不够精细，应使用硬件定时器或高分辨率释放机制。

## 6. 性能量化分析

### 6.1 必须采集的量

|指标|计算/来源|解释|
|---|---|---|
|执行时间|任务开始到结束的计数差|任务实际占用 CPU 的时间|
|调度等待|Ready 到 Running 的时间差|任务获得 CPU 前的延迟|
|阻塞时间|Blocked 状态持续时间|等待资源或事件的时间|
|响应时间|释放到完成|端到端实时性指标|
|抢占次数|跟踪事件计数|调度干扰和切换频率|
|CPU 占比|窗口运行时间 / 窗口总时间|负载归因|
|最坏抖动|实际开始与预期释放的最大偏差|周期稳定性|

### 6.2 周期任务时序预算

周期任务响应时间可用以下分解进行诊断：

```
R = J_release + W_ready + C_execution + B_resource + I_ISR
```

其中：

- `J_release`：释放时刻误差或定时器抖动；
- `W_ready`：Ready 后等待 CPU 的时间；
- `C_execution`：自身执行时间；
- `B_resource`：锁或其他资源阻塞；
- `I_ISR`：执行期间受中断干扰的时间。

这是分析分解，不是所有 RTOS 下都能直接从单一 API 获取各项。应通过事件边界、内核跟踪和硬件时间戳分别估算。

### 6.3 计数器换算

若计数器频率为 `f`，两次读数差为 `Δc`：

```
时间秒数 = Δc / f
时间微秒 = Δc × 1,000,000 / f
```

32 位计数器应采用无符号差值处理一次回绕：

```
uint32_t elapsed = end_counter - start_counter;
```

采样间隔必须短于计数器回绕周期，或者将硬件计数器扩展为更宽的时间基准。

### 6.4 测量扰动与实测

没有固定的“任务跟踪开销”数值。需要在目标硬件上测量：

1. 关闭跟踪时的关键任务响应时间。
2. 开启内核事件跟踪时的响应时间。
3. 加入用户事件后的响应时间。
4. 输出通道满载或主机断开时的行为。
5. 任务切换频率和中断率变化后的开销。

推荐记录最小、平均、P99 和最大响应时间，而非只记录平均值。用户事件插桩也要测量，避免在高频路径中形成显著扰动。

## 7. 应用场景选型指南

### 纯文本决策流程图

```
问题表现是什么？
├─ 任务运行时间很高
│  └─ 运行时间统计 + 热点事件/采样分析
├─ 任务响应慢，但 CPU 总使用率不高
│  └─ Ready 等待、资源阻塞和 ISR 时间线
├─ 任务长时间不运行
│  └─ 区分 Blocked 与 Ready；检查优先级和事件来源
├─ 周期逐渐漂移
│  └─ 检查相对延时，改用绝对周期释放并测量抖动
├─ 偶发超时
│  └─ 保存超时前跟踪快照 + 释放/开始/结束用户事件
├─ 队列积压
│  └─ 关联生产者、消费者、队列水位和阻塞事件
└─ 硬件外部时序异常
   └─ GPIO/逻辑分析仪与任务跟踪结合
```

### 典型场景

|需求|方案|理由|
|---|---|---|
|控制任务抖动|周期边界事件 + 内核切换跟踪|区分释放误差、调度等待和执行时间|
|任务饥饿|Ready 状态持续时间 + 优先级和 ISR 事件|找出高优先级任务或中断占用|
|互斥锁等待|锁事件 + 任务切换时间线|识别持锁者和优先级反转|
|通信处理延迟|DMA、队列投递、消费者开始/完成事件|建立数据从硬件到应用的因果链|
|高频切换|任务切换计数和周期窗口|找到轮询、短延时或通知风暴|
|现场偶发死锁|快照模式/异常触发记录|保留故障前状态和同步对象活动|

## 8. 工程最佳实践

### 设计原则

- **为关键任务定义释放、开始、完成和截止时间**，明确测量边界。
- **Ready 等待和 Blocked 等待必须分开分析**。
- 对任务名称、优先级、功能和截止时间建立一张稳定的任务表。
- 内核事件与用户业务事件采用统一时基，并记录时间戳频率。
- 事件数据应包含丢失检测；有事件缺口时不应给出确定性根因结论。
- 将现场长期指标做成低成本计数、直方图和最大值；详细跟踪仅在问题定位时启用。
- 对每个结论保留固件版本、调度配置、输入负载和采集配置。

### 任务分析决策矩阵

|观察结果|优先检查|
|---|---|
|高 CPU、执行时间高|算法热点、循环边界、格式化、复制和浮点运算|
|低 CPU、响应时间高|阻塞对象、资源竞争、低优先级、外设等待|
|Ready 时间长|更高优先级任务、ISR、关中断和调度锁|
|Blocked 时间长|等待对象、超时值、事件来源和生产者状态|
|切换频率高|轮询、短延时、频繁通知和过小工作批次|
|任务周期漂移|相对延时、tick 分辨率和执行时间变化|
|偶发任务不再运行|死锁、任务删除、栈损坏、调度器状态和断言|

### 工业级编码规范

- 任务名应能反映职责，避免重名或截断后无法区分。
- 关键任务的周期、截止时间、优先级和栈预算应在配置表中统一管理。
- 任务状态和统计数据不得直接访问 RTOS 私有 TCB 字段。
- 不在高优先级任务或 ISR 中做阻塞式日志输出。
- 用户事件参数使用稳定 ID 和明确单位，避免传递指针或敏感业务数据。
- 任务进入错误或降级状态时，应记录明确的状态码和计数。
- 对任务创建、删除、优先级修改和资源持有建立可追溯事件。

## 9. 常见错误与避坑指南

### 错误一：把任务 CPU 时间当成任务响应时间

```
任务运行 100 us，所以响应时间是 100 us。
```

**根因**：任务可能先等待调度 500 us，再运行 100 us；也可能在执行中被 ISR 或高优先级任务打断。

**正确实现**：定义释放、开始和完成事件，分别计算调度等待、执行时间和端到端响应时间。

**风险影响**：任务 CPU 占用正常，但仍错过截止时间。

### 错误二：看到任务没有运行就判定任务阻塞

```
任务时间线没有运行段 -> 任务处于 Blocked
```

**根因**：任务可能处于 Ready 等待 CPU，也可能事件丢失或处于被跟踪工具未显示的上下文。

**正确实现**：检查状态转换、优先级、空闲任务、ISR 和跟踪完整性，区分 Ready 与 Blocked。

**风险影响**：误调队列、超时或任务优先级，掩盖真正的 CPU 饥饿原因。

### 错误三：周期任务使用相对延时

```
for (;;) {
    control_step();
    vTaskDelay(period_ticks);
}
```

**根因**：每轮执行时间和调度延迟都会累积到周期中。

**正确实现**：使用 `vTaskDelayUntil()` 或硬件定时器释放，并制定错过周期后的处理策略。

**风险影响**：周期漂移、控制环相位变化和长期同步偏差。

### 错误四：在 ISR 中执行复杂业务处理

```
void DMA_IRQHandler(void)
{
    parse_full_protocol_frame();
    update_application_state();
    send_text_log();
}
```

**根因**：ISR 占用直接延迟其他中断和任务，且某些业务 API 不允许在中断上下文使用。

**正确实现**：ISR 清标志、搬运必要数据并通知任务；复杂解析放到专用任务。

**风险影响**：高优先级任务被中断延迟，出现 ISR 嵌套过深、队列溢出或系统失去响应。

### 错误五：通过提高任务优先级解决所有延迟

```
任务反应慢 -> 一律提升优先级
```

**根因**：延迟可能来自锁等待、外设、长临界区、死锁或上游生产者未运行。提升优先级无法解决这些原因。

**正确实现**：先确认任务是 Ready 还是 Blocked，再分析等待对象、持锁者、ISR 和调度竞争。

**风险影响**：高优先级任务进一步压制系统其他任务，造成新的饥饿或优先级反转。

### 错误六：在时间线上忽略跟踪丢失和测量扰动

```
观察到一次长空洞 -> 认定 CPU 卡死
```

**根因**：传输堵塞、缓冲区溢出、跟踪停止或用户事件过密都可能制造空洞；跟踪插桩也会改变时序。

**正确实现**：检查丢失计数和 Recorder 状态，做开启/关闭跟踪的对照，并用硬件计时器或 GPIO 校验。

**风险影响**：错误根因分析，或因为过度插桩而掩盖原始问题。

## 10. 多机制组合使用方案

建议把任务行为分析分为三个层级：

```
内核调度层
├─ 任务创建、切换、阻塞和唤醒
├─ ISR 进入和退出
└─ 队列、信号量和互斥锁事件

业务时序层
├─ 请求释放
├─ 任务开始处理
├─ 子阶段完成
└─ 完成、超时或错误

长期监控层
├─ 最大响应时间和执行时间
├─ Ready 等待/阻塞时间分布
├─ 超时次数和队列高水位
└─ 任务栈余量
```

### 组合代码框架

```
typedef struct {
    uint32_t max_runtime_cycles;
    uint32_t max_response_cycles;
    uint32_t deadline_miss_count;
} task_behavior_metrics_t;

static task_behavior_metrics_t g_control_metrics;

void control_task(void *arg)
{
    (void)arg;

    TickType_t wake_time = xTaskGetTickCount();

    for (;;) {
        vTaskDelayUntil(&wake_time, CONTROL_PERIOD_TICKS);

        const uint32_t release_cycle =
            platform_expected_release_cycle();
        const uint32_t start_cycle =
            platform_cycle_count();

        const uint32_t wait_cycles =
            start_cycle - release_cycle;

        trace_task_event(TASK_EVT_CONTROL_START, wait_cycles);

        control_step();

        const uint32_t end_cycle = platform_cycle_count();
        const uint32_t runtime_cycles = end_cycle - start_cycle;
        const uint32_t response_cycles = end_cycle - release_cycle;

        if (runtime_cycles > g_control_metrics.max_runtime_cycles) {
            g_control_metrics.max_runtime_cycles = runtime_cycles;
        }

        if (response_cycles > g_control_metrics.max_response_cycles) {
            g_control_metrics.max_response_cycles = response_cycles;
        }

        if (response_cycles > CONTROL_DEADLINE_CYCLES) {
            ++g_control_metrics.deadline_miss_count;
            trace_task_event(TASK_EVT_CONTROL_DEADLINE_MISS,
                             response_cycles);
        }

        trace_task_event(TASK_EVT_CONTROL_END, runtime_cycles);
    }
}
```

`platform_expected_release_cycle()` 必须有可靠实现。如果释放时刻来自 RTOS tick，应考虑 tick 分辨率和换算误差；若截止时间严格，应在硬件定时器或高分辨率时基上定义释放点。统计字段若由多个上下文读写，需要同步保护。

### 组合设计要点

- 内核事件用于恢复调度状态机。
- 用户事件用于标记业务阶段。
- 运行时间统计用于长期任务负载排名。
- 硬件时间戳用于校验关键路径。
- 队列水位、超时和错误码用于说明行为后果。
- 异常触发快照保存关键任务状态、资源状态和最近事件。

## 11. 工业级实际案例分析

### 案例一：控制任务偶发错过截止时间

**需求**：1 ms 控制周期中偶发超期，平均 CPU 使用率正常。

**架构设计**

- 在周期释放、任务开始和任务结束位置记录用户事件。
- 启用任务切换与 ISR 跟踪。
- 周期性保存最大调度等待、最大执行时间和超时次数。
- 使用 GPIO 或 DWT 验证最坏响应时间。

**分析方式**

- `Ready` 等待长：检查高优先级任务、ISR 或关中断区间。
- 执行时间长：检查算法分支、资源等待和缓存/总线影响。
- 周期释放偏移：检查 tick 定时、相对延时和释放源抖动。

**设计要点**

平均 CPU 使用率不能证明周期任务满足截止时间。验收应基于最坏或高分位响应时间，并覆盖峰值输入。

### 案例二：通信消费者任务偶发饥饿

**需求**：DMA 已收到数据，但应用处理延迟并发生队列溢出。

**架构设计**

- ISR 记录 DMA 完成时间和通知结果。
- 生产者记录队列投递成功或失败。
- 消费者记录开始处理时间、完成时间和队列深度。
- 任务时间线展示消费者是否处于 Ready、Blocked 或 Running。

**根因区分**

- 消费者 Blocked：检查通知丢失、等待对象和超时配置。
- 消费者 Ready 但未运行：检查优先级和高优先级任务占用。
- 消费者运行但吞吐不足：优化处理批次、算法或任务分配。
- 队列持续增长：根据生产消费速率重新设计容量和背压策略。

**设计要点**

队列满时不能只记录错误日志。应保存水位、丢弃计数和时间窗口，才能区分突发峰值与长期吞吐不足。

### 案例三：低优先级维护任务长期得不到运行

**需求**：维护任务负责清理资源和更新状态，但在高负载时长期不运行。

**架构设计**

- 记录维护任务状态、优先级和 Ready 等待时间。
- 统计所有高优先级任务运行时间及周期。
- 记录 ISR 总占用和最长连续中断负载。
- 对维护工作设置预算和分片处理。

**分析方式**

如果任务始终 Ready 且无运行片段，说明调度饥饿；若任务运行后又长期 Blocked，则应分析它等待的资源或事件。

**设计要点**

不应简单提高维护任务优先级。可以为维护任务设置明确运行预算、将清理工作拆分成有限批次，或调整高优先级任务阻塞行为。

## 12. 高频问题深度答疑

### Q1：任务时间线中的执行段是否等于任务代码执行时间？

不一定。不同工具的事件钩子位置、ISR 归属和时钟基准会影响边界。有些统计把 ISR 时间归入被打断任务，有些单独显示 ISR。应查明端口语义，并通过硬件计时器校准关键路径。

### Q2：为什么任务 CPU 占用低，却出现响应超时？

任务可能长时间 Ready 等待 CPU，或者阻塞在互斥锁、队列、外设等待上。CPU 占用只统计实际运行时间，不能说明等待时间。需要同时测量释放到开始、开始到完成以及资源等待时间。

### Q3：长时间 Blocked 就一定是故障吗？

不一定。周期任务正常延时、等待事件或等待低速外设都可能长期 Blocked。应将实际阻塞时间与设计的周期、超时值和业务截止时间比较，并确认等待源是否符合预期。

### Q4：优先级反转是否总能通过优先级继承解决？

不能。优先级继承可以降低特定互斥锁场景的反转影响，但不能解决死锁、锁顺序错误、持锁期间阻塞 I/O、普通信号量误当互斥锁或资源访问设计不合理。还需分析锁获取顺序和最长持锁时间。

### Q5：任务开始事件应该放在循环顶部还是等待操作之后？

如果要测量任务从释放到开始的调度等待，事件应尽量贴近实际任务释放与第一次执行边界；循环顶部只能代表代码到达该位置。若任务周期通过 `vTaskDelayUntil()` 释放，需要明确预期释放时刻，避免把等待 API 的时间误算成业务执行时间。

### Q6：任务行为分析应该采集多久？

取决于问题发生概率和扰动预算。确定性问题可用短时间窗口；稀有现场问题需要较长覆盖，通常采用低成本统计常驻、详细跟踪按需触发。采集窗口必须覆盖完整业务周期、输入峰值和异常触发前后的上下文。

## 13. 课程核心总结

- 任务行为分析的重点是**状态转换、时序和因果关系**，不只是 CPU 占用。
- 对关键任务，明确释放、开始、完成和截止时间，分别计算等待、执行和响应。
- `Ready` 长时间等待通常指向调度竞争；`Blocked` 长时间等待通常指向资源或事件链路。
- 同步对象、ISR 和业务阶段事件需要关联分析。
- 跟踪存在扰动和丢失可能，关键时序应使用硬件方法交叉验证。
- 低开销运行时指标用于长期监控，事件时间线用于深入定位。

## 16. 实践与进阶路径

### 梯度实战任务

1. **建立任务清单**  
    为每个任务登记职责、优先级、周期、截止时间、栈预算和等待对象。
    
2. **采集任务时间线**  
    使用 SystemView 或 Tracealyzer 记录任务切换、阻塞、唤醒和 ISR，确认任务状态转换与设计一致。
    
3. **加入业务边界事件**  
    给一个周期控制任务加入释放、开始、完成和超时事件，计算调度等待、执行和响应时间。
    
4. **注入调度竞争**  
    增加高优先级负载任务，观察低优先级任务 Ready 等待和饥饿；再验证分片处理或负载整形效果。
    
5. **注入资源等待**  
    构造互斥锁争用和队列积压，观察持有者、等待者、阻塞时间及优先级继承行为。
    
6. **验证测量扰动**  
    比较关闭跟踪、内核事件跟踪和加入用户事件后的响应时间、ISR 延迟和 CPU 占用。
    

### 性能测试方法

测试报告至少包括：

```
固件版本和构建配置
任务优先级与周期
任务执行时间：平均、P99、最大
调度等待时间：平均、P99、最大
端到端响应时间：平均、P99、最大
Blocked 时间及等待对象
ISR 执行时间和调用频率
队列最大水位和丢弃次数
任务栈高水位
跟踪事件丢失和缓冲区状态
```

### 进阶学习方向

- FreeRTOS 调度器的 Ready 列表、延时列表和任务切换源码。
- 优先级反转、优先级继承、优先级天花板和锁顺序分析。
- 固定优先级响应时间分析与最坏执行时间估算。
- ISR 延迟、关中断时间和嵌套中断预算。
- SystemView/Tracealyzer 用户事件设计和自动化轨迹分析。
- 多核 RTOS 的任务迁移、核亲和性和跨核同步行为。
