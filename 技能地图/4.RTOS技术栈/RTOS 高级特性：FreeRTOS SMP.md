我会按课程结构讲解 FreeRTOS SMP，并把版本边界说清楚：FreeRTOS 的 SMP 支持与单核内核、官方 SMP 移植及厂商扩展并不完全相同，调度语义和 API 不能一概而论。性能数值会标明是公式估算、示例测量还是必须在目标板验证的量。

## 3. 技术概述

### 3.1 SMP 的定义

在 SMP 系统中，多个 CPU 核运行同一个操作系统内核，并共享一个全局任务集合与共享内存。任务通常可以运行在任一允许的核上，具体由调度器和任务亲和性决定。

```
FreeRTOS SMP Kernel
          +-------------------------+
          | shared ready state      |
          | shared task objects     |
          | shared IPC objects      |
          +------------+------------+
                       |
             +---------+---------+
             |                   |
           Core 0              Core 1
```

与单核 FreeRTOS 相比，SMP 并不只是“多开一个核”。它改变了：

- 调度器的数据并发访问；
- 临界区的保护范围；
- 任务是否可能同时运行；
- 中断和任务的共享方式；
- 内存访问和缓存行为；
- 最坏执行时间分析方法。

### 3.2 FreeRTOS SMP 的版本与移植边界

**不要仅凭“工程使用 FreeRTOS”就假设它是 SMP 内核。**

FreeRTOS 内核和各厂商移植的支持形态可能不同：

- 某些 FreeRTOS 版本或官方内核配置提供 SMP 支持。
- 某些芯片使用厂商维护的 FreeRTOS SMP 分支或补丁。
- 某些双核芯片默认采用 AMP：每个核运行独立内核或由一个核运行 RTOS、另一个核运行专用固件。
- 有的移植提供 `vTaskCoreAffinitySet()` 或类似接口；接口名称和语义可能因版本或厂商不同。
- 调度策略、抢占点、任务迁移规则及 SMP 配置项必须以目标工程的内核源码和官方文档为准。

开始设计前应确认：

```
FreeRTOS Kernel 版本和提交
+ port 层实现
+ 芯片 SDK/BSP 版本
+ SMP 相关配置项
+ 任务亲和性 API
+ 每核中断与 tick 实现
```

本文讲解通用 SMP 设计原则，并用 FreeRTOS 风格接口举例；示例 API 需适配具体目标版本。

### 3.3 SMP、AMP 与单核对比

|特性|单核 FreeRTOS|FreeRTOS SMP|AMP|
|---|---|---|---|
|内核实例|一个|所有核共享一个内核实例|通常每核独立固件或内核|
|任务并行|否|是|通过核间协议协作|
|调度状态|单一 CPU 的调度器状态|共享调度状态并协调多个 CPU|各核分别调度|
|任务迁移|不适用|通常可迁移，受亲和性约束|通常不迁移|
|共享内存同步|单核临界区即可覆盖任务并发|需跨核同步和内存顺序|需处理跨核共享和协议|
|故障隔离|较弱|共享内核和地址空间|可有更强核间隔离|
|适用场景|资源受限、负载较低|多任务并行、共享资源较多|异构核、安全隔离或独立子系统|

### 3.4 SMP 不是自动获得两倍性能

两个核能提高吞吐量的前提是：

- 有足够的可并行工作；
- 关键路径不存在串行瓶颈；
- 共享锁竞争不严重；
- 内存和外设带宽足够；
- 任务调度、核间通信和 cache 维护开销可控。

如果所有任务都抢同一把全局锁，或者都依赖一个单核外设服务任务，增加核心数可能只增加同步成本和时延。

## 4. 核心特性横向对比

### 4.1 FreeRTOS SMP 常用调度模式

不同 FreeRTOS SMP 移植的实现可能有差异，下表描述常见设计维度，不代表所有版本都采用完全相同的策略。

|维度|单核模式|SMP 模式|工程影响|
|---|---|---|---|
|运行任务数|同一时刻最多 1 个任务|最多与在线核数相同|共享状态必须按真正并发处理|
|就绪任务选择|单个最高优先级 Ready task|需给多个核分配可运行任务|同优先级和亲和性可能影响选择|
|任务切换|当前核本地切换|本地切换，也可能触发核间调度|跨核抢占和 IPI 增加开销|
|任务迁移|不存在|可能发生|cache 热度、栈所在内存和延迟变化|
|亲和性|不适用|可允许或限制任务运行核|限制迁移，但可能导致负载不均|
|临界区|常通过关中断或调度锁保护|通常需跨核互斥机制|单核关中断不足以保护共享数据|
|ISR|当前核处理|需考虑中断归属和核间通知|外设 IRQ 路由影响实时性|
|Tick|单一时基|可能由每核 tick 或协调机制实现|必须查看 port 实现|
|内存带宽|单核访问|多核并发访问|可能受 SRAM、cache、总线瓶颈限制|

### 4.2 同步机制对比

|机制|跨核适用性|阻塞特性|适合用途|主要限制|
|---|---|---|---|---|
|FreeRTOS mutex|取决于 SMP 移植实现|可阻塞|任务间互斥|需确认 PI、跨核安全和 ISR 限制|
|Binary semaphore|取决于内核实现|可阻塞|事件同步|不等同于 mutex，无所有权语义|
|Task notification|通常用于唤醒目标任务|可阻塞等待|单任务事件通知|具体 SMP 语义和核间唤醒需核查|
|Critical section API|依 port 实现|通常短暂屏蔽或锁定|极短共享状态更新|不能假定等价于单核关中断|
|Spinlock|依移植或 SoC 提供|自旋等待|极短跨核临界区|不能持有期间阻塞或执行长操作|
|C11 原子操作|依编译器和平台支持|通常不阻塞|计数、标志、索引发布|原子不保证整体算法正确|
|原子指针/邮箱|依实现|不一定阻塞|小型跨核交接|生命周期和内存顺序需严谨|
|IPC 队列/共享队列|需具体实现|可阻塞或非阻塞|跨核消息传递|多核缓存、队列容量和唤醒开销|

### 4.3 任务放置策略对比

|策略|优点|缺点|适用情况|
|---|---|---|---|
|全部可迁移|调度器有较大负载均衡空间|cache 命中和时延可能变化|通用工作任务|
|固定亲和单核|时延和资源归属更稳定|易形成单核过载|硬实时任务、核专属外设|
|软亲和|优先运行指定核，必要时可迁移|实际行为依实现|兼顾 cache 热度与负载均衡|
|分核固定分配|任务拓扑明确|负载无法动态均衡|固定功能分区、通信核与控制核分离|

## 5. 底层原理与功能特性深度解析

### 5.1 SMP 调度的核心问题

单核调度器每次选择一个任务运行；SMP 调度器必须决定：

1. 哪些任务处于 Ready 状态？
2. 哪些核当前空闲或可抢占？
3. 哪些任务允许在某个核运行？
4. 一个任务是否已经被另一个核选中？
5. 是否需要让另一个核停止当前任务并重新调度？
6. 如何避免两个核同时运行同一个任务？

常见实现会维护共享任务状态，并在任务选中、阻塞、唤醒和迁移时进行同步。具体数据结构可能包含：

- 全局 Ready list 或按优先级组织的 Ready list；
- 每核当前任务指针；
- 任务运行核标识；
- 任务亲和性掩码；
- 每核调度锁或全局调度锁；
- 跨核中断/调度通知状态。

若共享 Ready list 需要全局锁，调度路径可能在高核数下成为瓶颈。

### 5.2 调度器锁与任务临界区

要区分三种经常被混为一谈的操作：

1. **禁止本核中断**：阻止当前核响应特定中断。
2. **调度器锁定**：阻止当前核发生任务切换或延迟调度。
3. **跨核锁定共享数据**：阻止其他核并发访问共享对象。

在单核系统中，关中断或调度器锁常能间接阻止任务并发访问。但在 SMP 上，其他核仍可能继续执行。因此：

> **仅关本核中断，通常不能保护被其他 CPU 核访问的共享数据。**

要保护跨核共享状态，必须使用目标 port 定义的 SMP critical section、spinlock、mutex 或正确的原子操作。

### 5.3 SMP 临界区的典型伪实现

不同 port 实现可能采用不同方案。概念上常见的 SMP 临界区类似：

```
void enter_smp_critical(void)
{
    local_irq_state_t irq_state = local_irq_save();

    spinlock_acquire(&kernel_lock);
    local_irq_state_store(irq_state);
}

void exit_smp_critical(void)
{
    spinlock_release(&kernel_lock);
    local_irq_restore(local_irq_state_load());
}
```

真实实现必须处理：

- 嵌套进入计数；
- 当前核身份；
- 递归或非递归锁语义；
- 内存屏障；
- 是否允许高优先级 ISR 抢占；
- ISR 和任务上下文的不同路径；
- 临界区中的调度器状态；
- 自旋锁等待期间是否关闭本地中断。

**不能把此伪代码直接当作应用代码使用。** 应用应使用对应 FreeRTOS port 提供的临界区宏或同步 API。

### 5.4 Spinlock 与 mutex 的选择

Spinlock：

```
如果锁被其他核持有：
    当前核忙等，直到锁释放
```

mutex：

```
如果锁不可用：
    当前任务阻塞，调度其他任务运行
```

适用边界：

- spinlock 仅适合非常短、执行时间有明确上界的跨核临界区。
- mutex 适合可能需要等待的任务间互斥。
- ISR 通常不能阻塞等待 mutex；spinlock 是否可在 ISR 中使用，必须查看 port 和具体接口契约。
- 持有 spinlock 时禁止阻塞、等待任务事件、访问慢速外设或执行复杂日志。
- 自旋等待期间当前核仍消耗 CPU，不能把它当作“没有成本的锁”。

### 5.5 优先级继承与跨核等待

单核中的优先级继承主要缓解低优先级持锁任务被中优先级任务抢占的问题。在 SMP 上还会出现：

- 高优先级任务在核 0 等待核 1 上的低优先级持锁任务；
- 持锁任务是否能被调度到空闲核；
- mutex 的优先级继承是否跨核传播；
- 多核同时等待同一个 mutex；
- 继承后任务迁移是否改变调度行为。

因此不能默认单核 FreeRTOS mutex 的 PI 语义在 SMP port 中完全相同。应检查目标实现的 mutex 和调度器源码，并在目标平台实测。

### 5.6 任务亲和性

亲和性用于限制任务可以在哪些核运行。它通常可表达为：

```
Core 0 only
Core 1 only
Core 0 or Core 1
```

是否提供 API、API 名称和软硬亲和语义取决于 FreeRTOS 版本和 port。FreeRTOS 风格示例：

```
/* API 名称和参数需按目标 FreeRTOS SMP 版本确认。 */
BaseType_t result =
    vTaskCoreAffinitySet(task_handle, CORE_0_MASK);
```

亲和性适用于：

- 任务使用核专属外设；
- 需要稳定 cache locality；
- 中断和任务需要同核处理；
- 某些硬实时任务需要固定执行核；
- 需要隔离控制负载和通信负载。

亲和性过度使用会造成：

- 某核 Ready list 堆积；
- 另一个核空闲；
- 高优先级任务无法使用空闲核；
- 任务固定核上发生局部过载。

### 5.7 任务迁移的代价

任务迁移通常不搬动任务栈本身，但会改变：

- 运行上下文所在的核；
- 该核的寄存器和 cache 状态；
- 任务本地数据和 cache 热度；
- 任务可能访问的核本地资源；
- 任务运行时的中断和调度竞争情况。

迁移的影响可能包括：

- 冷 cache 导致执行时间增加；
- 共享 L2 或 SRAM 总线竞争变化；
- 核间调度通知开销；
- 任务局部变量仍在线程栈上，但线程本地或核本地状态不一定可迁移；
- 测量到的 WCET 和抖动增大。

### 5.8 共享变量、原子操作和内存顺序

在 SMP 上，即使对齐后的 32 位读写在硬件上原子，也不表示整个数据结构更新是原子的。

错误示例：

```
shared->length = length;
shared->ready = 1U;
```

另一个核可能观察到 `ready == 1`，却仍读到旧 `length`。正确做法需要发布/获取语义：

```
shared->length = length;

atomic_store_explicit(&shared->ready,
                      1U,
                      memory_order_release);
```

消费者：

```
if (atomic_load_explicit(&shared->ready,
                         memory_order_acquire) != 0U) {
    uint32_t length = shared->length;
    process_data(length);
}
```

这仍要求：

- `shared->length` 在生产者发布后不被并发修改；
- 原子操作在目标平台上符合要求；
- 若涉及 DMA，还需执行 cache 维护；
- 若消息有多个生产者，还需更多同步机制。

### 5.9 伪共享与缓存行

如果两个核频繁修改位于同一 cache line 的不同变量，cache line 可能不断在核之间迁移。这叫**伪共享**。

```
struct counters {
    atomic_uint core0_count;
    atomic_uint core1_count;
};
```

即使两个计数器逻辑上独立，如果它们位于同一 cache line，更新可能引发 cache line ping-pong。

优化方向：

```
typedef struct {
    alignas(CACHE_LINE_SIZE) atomic_uint value;
    uint8_t padding[CACHE_LINE_SIZE - sizeof(atomic_uint)];
} per_core_counter_t;
```

对齐尺寸应根据目标平台 cache line 大小确定，不能假设所有 MCU 都是 32 或 64 字节。部分芯片没有数据 cache，此时伪共享的 cache 代价不存在，但仍可能存在共享总线和互连竞争。

### 5.10 每核资源与全局资源

适合按核拆分的资源：

- 统计计数器；
- 临时解析状态；
- 日志 staging buffer；
- 任务唤醒计数；
- 核本地 trace buffer。

适合全局共享的资源：

- 同一个 DMA 通道；
- 同一个 SPI 控制器；
- 网络接口；
- 全局内存池；
- 跨核命令队列。

把高频写入的状态按核分片，常能减少共享锁竞争；但汇总时仍需定义一致性和时间语义。

## 6. 性能量化分析

### 6.1 性能数据的解释边界

FreeRTOS SMP 的性能强烈依赖：

- MCU/SoC 型号和核间互连；
- cache 是否一致；
- FreeRTOS 版本与 SMP port；
- 临界区实现；
- 编译器和优化等级；
- 核频、总线频率和内存区域；
- 任务亲和性；
- ISR 负载和核间竞争。

因此以下项目应在目标板测量，不能视为固定常数。对很多 MCU，跨核锁和 IPI 的成本可能从亚微秒到数微秒或更高；具体值必须由实际 port 和硬件决定。

### 6.2 Amdahl 定律与并行收益

若程序中可并行部分比例为 PP，使用 NN 个核的理想加速比为：

S(N)=1(1−P)+PNS(N)=(1−P)+NP​1​

例如，可并行比例 P=0.8P=0.8，双核理想加速比：

S(2)=10.2+0.8/2=1.67S(2)=0.2+0.8/21​=1.67

实际速度还需扣除：

- 锁和队列同步；
- 核间中断；
- 任务迁移；
- cache miss；
- 内存总线竞争；
- 串行外设和串行代码。

若串行部分占比大，增加核数的收益有限。

### 6.3 临界区与锁竞争成本

一段跨核临界区的平均占用可能为：

Tcritical=Tlock+Twork+TunlockTcritical​=Tlock​+Twork​+Tunlock​

若两个核的任务以频率 f0f0​、f1f1​ 访问同一锁，且每次锁持有时间为 TcTc​，粗略竞争概率随访问频率和持锁时间增加。锁越长、访问越集中，spin 等待和核间 cache 迁移越明显。

优化顺序通常是：

1. 缩短临界区；
2. 取消不必要共享；
3. 按核拆分状态；
4. 将外设交给所有者任务；
5. 最后才考虑更复杂的无锁算法。

### 6.4 任务负载和核利用率

每核利用率可初步估算为：

Uk=∑i∈CorekCiTi+UISR,k+Usync,kUk​=i∈Corek​∑​Ti​Ci​​+UISR,k​+Usync,k​

其中：

- CiCi​：任务最坏执行时间；
- TiTi​：任务周期；
- UISR,kUISR,k​：该核中断占用率；
- Usync,kUsync,k​：锁等待、核间通信和调度协调开销。

总 CPU 利用率低，并不保证每核实时性良好。亲和性可能导致一核过载、另一核空闲。

### 6.5 建议的实测项目

|测试项目|测量方法|
|---|---|
|本地任务唤醒延迟|任务通知前后记录周期计数|
|跨核任务唤醒延迟|生产核与消费核分别打点|
|Mutex 无竞争开销|单任务重复 lock/unlock|
|Mutex 跨核竞争开销|两核持续竞争并记录最大等待|
|Spinlock 最大等待|控制持锁时间，测量竞争核等待|
|任务迁移成本|固定亲和和允许迁移对比 WCET|
|跨核消息吞吐|序列号和时间戳统计|
|IPI 开销|GPIO、trace 或硬件计数器|
|Cache 影响|预热与冷 cache、同核与跨核对比|
|伪共享影响|相邻计数器与 cache-line 分隔计数器对比|

### 6.6 内存开销

SMP 相关内存通常增加在：

- 每核 ISR 栈或异常栈；
- 每核调度状态；
- 每核中断和 trace 状态；
- 核间通信队列或 mailbox；
- 对齐后的 per-core 数据；
- cache 维护缓冲区；
- 多核任务同步结构。

具体大小取决于 port，建议用 `sizeof()`、map 文件和运行时栈高水位实测。不能仅按“增加一个核”推断 RAM 只增加一个任务栈。

### 7.1 纯文本决策流程图

```
目标芯片是否提供可用的 FreeRTOS SMP port？
|
+-- 否 --> 使用 AMP 或单核 FreeRTOS
|
+-- 是
    |
    +-- 任务负载是否有足够并行性？
    |   |
    |   +-- 否 --> SMP 收益有限；优先优化单核路径
    |   |
    |   +-- 是
    |       |
    |       +-- 是否大量访问同一外设/全局锁？
    |       |   |
    |       |   +-- 是 --> 先拆分资源所有权或按核分片
    |       |   +-- 否 --> 继续进行 SMP 负载建模
    |       |
    |       +-- 是否有硬实时任务？
    |           |
    |           +-- 是 --> 评估固定亲和、最坏迁移延迟和中断路由

    |

```

### 7.2 典型场景

|场景|推荐方案|理由|
|---|---|---|
|网络栈和应用任务有大量并行处理|SMP|可并行处理接收、协议和应用工作|
|高频控制任务要求确定时延|固定亲和或 AMP 分核|降低迁移和跨核共享的不确定性|
|两核共享同一 SPI 控制器|单一 SPI owner task 或专用核|避免多个核频繁争抢同一外设|
|任务负载动态变化|SMP 可迁移任务|调度器有机会均衡负载|
|安全域和非安全域隔离要求高|AMP/安全分区|核间边界更清晰|
|两核分别处理不同外设子系统|固定核分区|本地状态简单，跨核通信有限|
|共享状态更新频繁|按核分片或消息传递|减少全局锁和 cache line 竞争|

## 8. 工程最佳实践

### 8.1 架构原则

- 先评估并行性，再决定采用 SMP。
- 高实时任务优先评估固定亲和或明确核分区，不要把迁移当作免费的负载均衡。
- 高频共享数据按核分片，降低全局锁和 cache line 迁移。
- SPI、UART、Flash、网络控制器等独占资源优先使用资源所有者任务。
- 共享数据优先采用消息传递或单写者模型，减少任意任务读写同一结构。
- 核间通信接口应明确消息顺序、所有权、超时和失败行为。
- SMP 临界区内不得阻塞、等待其他任务或执行慢速硬件访问。
- 所有原子操作都必须确认目标平台实现和内存序。
- 对每个核独立测量负载和中断占用，而不只看系统总 CPU 使用率。

### 8.2 设计决策矩阵

|条件|推荐策略|检查项|
|---|---|---|
|高并行、低共享|SMP 任务可迁移|核负载均衡和迁移成本|
|高并行、部分共享|分片 + 消息传递|共享边界和队列延迟|
|强实时控制|固定亲和或 AMP|核上 WCET、IRQ 归属|
|共享外设频繁访问|Owner task|排队延迟和请求优先级|
|多核高频更新全局计数|per-core 计数|汇总周期和一致性|
|短小共享状态|原子变量或 SMP 临界区|原子宽度与内存屏障|
|多字段事务状态|mutex 或快照|一致性、PI、锁顺序|
|需要严格故障隔离|AMP 或核间隔离|IPC 协议和故障边界|

### 8.3 工程编码规范

- 明确每个任务的允许运行核和迁移策略。
- 所有共享对象标注所有者、访问核、同步方式和生命周期。
- ISR、任务和跨核访问分别说明其并发上下文。
- 不能用 `volatile` 代替原子操作或锁。
- 不能只关本核中断来保护跨核共享数据。
- 多核临界区保持短小，避免调用日志、内存分配和阻塞 API。
- 核本地统计数据尽量按 cache line 隔离。
- mutex 锁顺序应全局统一，避免跨核死锁。
- 任务创建和亲和性设置失败必须处理，不可继续启动依赖任务。
- 启动阶段必须定义核 0、其他核、共享内存和调度器的启动顺序。
- 记录每核 CPU 利用率、任务迁移次数、跨核唤醒次数和锁等待时间。

## 9. 常见错误与避坑指南

### 错误一：把单核关中断临界区当成跨核互斥

错误代码：

```
taskENTER_CRITICAL();
shared_counter++;
taskEXIT_CRITICAL();
```

问题根因：如果目标 SMP port 的临界区只屏蔽本核中断，另一个核仍可能同时执行同一段代码。

正确做法：

- 使用目标 SMP port 明确提供的跨核临界区；
- 或使用 C11 原子操作；
- 或使用任务级 mutex 保护复合共享状态。

```
atomic_fetch_add_explicit(&shared_counter,
                          1U,
                          memory_order_relaxed);
```

适用限制：原子计数适用于独立计数器，不适合保护多字段事务。

风险：数据丢失、计数错误、共享链表损坏和随机崩溃。

### 错误二：认为任务不会在两个核上同时访问共享结构

错误代码：

```
if (queue_count > 0U) {
    queue_count--;
    process_item();
}
```

根因：两个核上的任务可能真正并行执行，检查和更新不是原子事务。

正确实现：

```
if (mutex_lock(&queue_mutex) != STATUS_OK) {
    return STATUS_ERROR;
}

if (queue_count > 0U) {
    queue_count--;
    have_item = true;
}

mutex_unlock(&queue_mutex);

if (have_item) {
    process_item();
}
```

若使用 RTOS 原生队列，应优先使用其队列 API，不要重复实现已有的同步语义。

风险：重复消费、丢失项目、队列索引损坏。

### 错误三：持有 Spinlock 时执行长操作

错误代码：

```
spinlock_acquire(&shared_lock);
memcpy(large_buffer, source, LARGE_SIZE);
spi_transfer_blocking(data, length);
spinlock_release(&shared_lock);
```

根因：另一个核在整个操作期间持续自旋，消耗 CPU 并扩大实时延迟。

正确实现：

```
spinlock_acquire(&shared_lock);
copy_shared_metadata(&local_metadata);
spinlock_release(&shared_lock);

/* 慢速操作放在锁外。 */
spi_transfer_blocking(data, length);
```

风险：另一核空转、任务延迟暴涨、系统吞吐下降。

### 错误四：过度固定任务亲和性造成一核过载

错误配置：

```
所有实时任务固定在 Core 0
通信任务固定在 Core 1
```

实际可能是 Core 0 任务和 ISR 负载已超过可调度能力，而 Core 1 长期空闲。

正确做法：

- 统计每核任务、ISR 和同步负载；
- 仅对确有确定性或硬件绑定需求的任务固定亲和；
- 允许普通工作任务迁移；
- 将关键路径的 WCET 和最坏干扰纳入每核响应时间分析。

风险：系统总 CPU 利用率不高，但关键核已过载并错过截止时间。

### 错误五：共享变量只加 `volatile`

错误代码：

```
volatile uint32_t ready;
volatile uint32_t length;
```

根因：`volatile` 不保证两字段的一致性，也不提供完整跨核内存顺序。

正确实现：用原子发布标志或锁保护整个结构，并确保发布/获取关系。

```
shared->length = length;
atomic_store_explicit(&shared->ready,
                      1U,
                      memory_order_release);
```

风险：消费者看到 ready 标志，却读到旧数据或部分更新的数据。

### 错误六：假设 FreeRTOS 所有 SMP 版本的 API 一样

错误做法：

```
vTaskCoreAffinitySet(task, mask);
```

直接复制到不同芯片 SDK、FreeRTOS 版本或厂商分支。

根因：亲和性 API、SMP 配置、调度语义和 port 实现可能不同。

正确做法：

- 检查目标工程 FreeRTOS 版本和提交；
- 检查头文件与 port 源码；
- 确认 API 是否支持动态修改亲和性；
- 验证任务创建和亲和性失败路径；
- 对任务迁移行为做实际 trace。

风险：编译失败、任务运行核不符合预期，或应用代码建立在错误调度假设上。

### 错误七：两核同时初始化共享外设或全局对象

错误代码：

```
void app_init(void)
{
    global_driver_init();
    create_application_tasks();
}
```

如果两个核都可能调用 `app_init()`，就可能并发初始化共享硬件。

正确做法：

- 设计明确的单核启动协调；
- 使用原子一次性初始化状态机；
- 其他核等待初始化完成；
- 共享对象在使用前发布，并具有正确内存顺序。

状态机示意：

```
UNINITIALIZED
    -> INITIALIZING
    -> READY
    -> FAILED
```

风险：外设寄存器配置互相覆盖、队列重复创建、静态对象被重置。

### 错误八：忽略核间中断和缓存成本

错误假设：

```
唤醒另一个核上的任务等同于本核任务通知
```

根因：跨核唤醒可能需要更新共享调度状态、发送 IPI、执行缓存一致性操作或等待目标核进入调度点。

正确做法：

- 分别测量本核唤醒和跨核唤醒；
- 降低不必要的跨核通知频率；
- 批量传递数据；
- 让高频生产者和消费者尽量位于同核，或明确接受跨核成本。

风险：平均值看似正常，但跨核路径尾延迟超过实时预算。

## 10. 多机制组合使用方案

### 10.1 通信核与控制核分区

一种常见架构：

```
Core 0：实时控制
    - 高频采样任务
    - 控制算法任务
    - 相关外设 ISR

Core 1：通信与服务
    - 网络协议任务
    - 日志任务
    - 配置和诊断任务

Core 0 <---- bounded IPC ----> Core 1
```

设计要点：

- 控制核只接收必要、结构稳定的命令和参数快照。
- 通信核不直接写控制核正在使用的多个状态字段。
- 控制参数通过双缓冲、版本化快照或专用队列交接。
- 日志和诊断流不能阻塞控制核。
- 两核时钟、tick 和时间戳必须有可比较的定义。

### 10.2 核间消息队列

跨核消息应携带：

```
typedef struct {
    uint16_t type;
    uint16_t length;
    uint32_t sequence;
    uint32_t timestamp;
    uint8_t payload[IPC_PAYLOAD_MAX];
} ipc_message_t;
```

契约应说明：

- 是否按值拷贝还是传递指针；
- 队列满时如何处理；
- 是否保证跨核消息顺序；
- 超时基于哪个核的时钟；
- 任务或核重启后如何清理旧消息；
- 消息版本和长度校验方式。

### 10.3 每核本地统计与周期汇总

高频计数不要全部争用同一个全局原子变量：

```
typedef struct {
    alignas(CACHE_LINE_SIZE) atomic_uint irq_count;
    uint8_t padding[CACHE_LINE_SIZE - sizeof(atomic_uint)];
} core_counter_t;

static core_counter_t per_core_counters[NUM_CORES];
```

各核更新自己的计数器，低频诊断任务周期性汇总。此方案减少 cache line 在核间迁移，但需要接受汇总值不是瞬时强一致的事实。

### 10.4 生产级跨核交接框架

```
typedef struct {
    uint32_t sequence;
    uint32_t timestamp;
    uint16_t type;
    uint16_t length;
    uint8_t payload[IPC_MAX_PAYLOAD];
} ipc_message_t;

status_t ipc_send_to_control(const ipc_message_t *message)
{
    if (message == NULL) {
        return STATUS_INVALID;
    }

    if (message->length > IPC_MAX_PAYLOAD) {
        return STATUS_TOO_LARGE;
    }

    if (message->type >= IPC_TYPE_MAX) {
        return STATUS_INVALID;
    }

    if (ipc_queue_send(&control_queue,
                       message,
                       IPC_SEND_TIMEOUT) != STATUS_OK) {
        ipc_queue_overflow_count++;
        return STATUS_BUSY;
    }

    return STATUS_OK;
}

void control_task(void *arg)
{
    ipc_message_t message;

    for (;;) {
        if (ipc_queue_receive(&control_queue,
                              &message,
                              WAIT_FOREVER) != STATUS_OK) {
            continue;
        }

        if ((message.length > IPC_MAX_PAYLOAD) ||
            (message.type >= IPC_TYPE_MAX)) {
            ipc_invalid_message_count++;
            continue;
        }

        control_handle_message(&message);
    }
}
```

实际实现还需确认：

- 队列是否跨核安全；
- 是否触发核间中断；
- 消息数据是否 cache coherent；
- 队列是否为静态分配；
- 接收任务的亲和性；
- 队列满后的业务降级行为。

## 11. 工业级实际案例分析

以下是典型架构模式，不代表特定厂商产品实现。

### 案例一：双核电机控制与网络通信

#### 需求

- 控制环周期为 1 ms；
- 网络配置和遥测处理有突发负载；
- 控制任务不能受网络解析和日志影响。

#### 架构

```
Core 0：
    ADC/DMA ISR
    控制任务
    故障快速处理任务

Core 1：
    Ethernet/Wi-Fi 任务
    协议解析
    日志与诊断

Core 1 -> Core 0：
    有界命令队列 + 配置快照
Core 0 -> Core 1：
    低频状态快照 + 统计数据
```

#### 设计要点

- 控制任务固定到 Core 0，或使用经验证的硬亲和策略。
- 网络任务不直接修改控制状态结构。
- 配置消息带版本号，控制任务在周期边界读取一致快照。
- 故障快速关断由硬件或高优先级本地 ISR 完成，不依赖跨核消息。
- 监控 Core 0 的最坏周期执行时间和跨核消息造成的等待。

### 案例二：双核网络网关与共享 SPI Flash

#### 需求

- 两核分别处理网络和协议任务；
- Flash 存储设备只有一个 SPI 控制器；
- 多个任务需要保存配置、日志和升级数据。

#### 原始问题

```
Core 0：持有配置锁 -> 请求 SPI
Core 1：持有日志锁 -> 请求 SPI
升级任务：持有升级锁 -> 等待配置锁
```

跨核增加了锁竞争和锁顺序复杂度。

#### 改进架构

```
所有任务
    -> SPI 请求队列
        -> 固定在 Core 1 的 SPI Owner Task
            -> SPI DMA
            -> 请求完成通知
```

#### 设计要点

- SPI 硬件只有一个所有者。
- 擦除和编程等待拆为异步阶段，不长时间持有总线锁。
- 请求含有优先级、截止时间和取消语义。
- Flash 写入和日志流量使用不同队列或配额，避免日志挤占升级写入。
- 统计每类请求的队列等待时间和最坏事务时间。

### 案例三：双核数据采集和分析

#### 需求

- Core 0 采集高速传感器数据；
- Core 1 执行滤波和特征提取；
- 数据速率高，按值复制会造成 CPU 和内存带宽压力。

#### 架构

```
DMA Buffer Pool
    -> Core 0 ISR 发布完成块索引
    -> 跨核有界描述符队列
    -> Core 1 批量处理
    -> 归还 Buffer Pool
```

#### 设计要点

- 传递块索引或指针，不复制整个数据块。
- 明确 DMA 与 CPU 的 cache 维护边界。
- Core 0 发布块后不能重用，直到 Core 1 明确归还。
- 队列满时必须决定丢弃最新块、最旧块或降采样。
- 块大小应平衡 ISR 频率、批处理延迟和内存占用。
- 测量跨核队列吞吐和缓冲块周转时间。

## 12. 高频问题深度答疑

### 1. FreeRTOS SMP 是否意味着每个任务都能在任意核运行？

不一定。任务可能受亲和性、port 调度策略、核状态和当前运行状态限制。部分实现支持可迁移任务，部分任务可能固定在某核。必须查看目标版本的亲和性 API 和调度器实现。

### 2. 任务迁移会不会导致栈损坏？

正常的任务迁移不应搬动或破坏任务栈；任务栈通常属于任务控制块，任务换核后仍使用自己的栈。但若应用错误依赖核本地栈、核本地寄存器状态、无效 TLS 状态或未同步的局部静态数据，迁移可能暴露问题。要区分“任务栈本身”与“核本地状态”。

### 3. FreeRTOS mutex 在 SMP 上是否自动跨核安全？

只有当目标 FreeRTOS SMP port 明确提供并验证了该语义时才成立。要检查：

- mutex 内部访问是否跨核同步；
- PI 是否支持跨核等待；
- ISR 是否允许给出信号；
- 任务删除时等待链如何处理；
- 临界区是否覆盖共享内核数据。

不要将单核移植的使用经验直接套用到不同厂商 SMP 分支。

### 4. 单核关中断为什么不能保护共享数据？

关中断通常只影响当前 CPU 核。另一个核仍然可以并行读取或写入共享内存。跨核共享数据必须使用跨核锁、SMP 临界区、原子操作或消息传递。

### 5. 两核都调用队列 API安全吗？

如果目标 FreeRTOS SMP 内核明确支持跨核并发访问同一队列，且队列对象生命周期正确，通常可以由内核提供同步。但必须确认该队列 API 对 ISR、核间并发和对象删除的具体约束。应用不能绕过队列 API，直接读写队列内部结构。

### 6. 亲和性越固定，实时性越好？

不一定。固定亲和减少迁移抖动，但可能让单核过载，同时浪费另一核资源。应结合每核响应时间、ISR 归属、资源访问和任务负载测量后决定。

### 7. SMP 的任务通知是否可能触发跨核中断？

可能。若通知目标任务当前不在本核，内核可能通过核间中断或其他同步机制通知目标核。具体行为取决于 port。跨核唤醒成本应单独测量，不要以同核通知性能代替。

### 8. 两核时间戳能直接比较吗？

不一定。需要确认：

- 两核是否使用同步时钟源；
- 计数器是否同频、同相位；
- 计数器是否会在低功耗状态停止；
- 时间戳读取是否需要同步；
- tick 是否全局一致。

端到端测量最好使用共享硬件计时器或具备明确同步语义的时钟源。

### 9. `volatile` 能解决 SMP 可见性问题吗？

不能。`volatile` 不保证原子性、内存顺序、复合结构一致性或 cache 一致性。应使用原子操作、锁、消息传递和平台定义的内存屏障；DMA 还需 cache 维护。

### 10. 双核是否一定能提升实时性？

不一定。双核增加并行能力，但也增加核间同步、缓存和调度交互。若关键任务受共享锁、串行外设或内存带宽限制，SMP 可能提高平均吞吐但恶化最坏时延。

### 11. SMP 和 AMP 应如何选择？

选择 SMP 的倾向：

- 任务能够有效并行；
- 需要共享统一任务和 IPC 模型；
- 同一系统中任务负载动态变化；
- 芯片和 FreeRTOS port 的 SMP 支持成熟。

选择 AMP 的倾向：

- 核之间需要故障隔离；
- 核具有不同功能或实时需求；
- 核间共享很少；
- 每核独立复位或安全分区很重要；
- SMP port 不成熟或不支持目标功能。

## 13. 课程核心总结

### 核心结论

- SMP 增加真正的任务并行，也引入真正的并发数据竞争。
- 单核中的“关中断保护共享状态”通常不能覆盖其他核。
- FreeRTOS SMP 的 API、亲和性和调度语义必须以目标版本和 port 源码为准。
- 任务迁移可能改善负载均衡，也可能增加 cache 和尾延迟。
- Spinlock 只适合短临界区；等待可能较长的任务互斥应使用适当的阻塞同步机制。
- 高频共享数据应尽量按核分片，或改成单写者和消息传递。
- 外设资源通常适合单一所有者任务，而不是由多个核直接竞争。
- SMP 性能不能只看总 CPU 利用率，应单独分析每核负载、跨核唤醒和锁等待。
- SMP 不能保证线性加速；串行比例、共享锁和内存带宽决定实际收益。

### 通用选型结论

```
并行度高、共享少、SMP port 成熟
    -> SMP，允许普通任务灵活调度

有硬实时任务、核本地外设或稳定时延要求
    -> 固定亲和或明确核分区

大量跨核共享状态
    -> 优先做数据分片、快照或消息传递

独占外设跨核访问
    -> 资源所有者任务

需要强故障隔离或 SMP 支持不成熟
    -> AMP 或单核 RTOS
```

## 14. 快速参考速查表

### 场景选型表

|场景|首选方案|必查事项|
|---|---|---|
|可并行的普通工作任务|SMP 可迁移|负载均衡和迁移抖动|
|硬实时控制任务|固定亲和/核分区|每核 WCET 和 IRQ 归属|
|高频跨核数据|批量描述符或共享缓冲区|cache 和所有权|
|多核共享全局计数|per-core counters|汇总一致性|
|共享 SPI/UART/Flash|Owner task|队列延迟和请求优先级|
|共享结构体多字段更新|mutex、SMP 临界区或快照|跨核同步能力|
|短原子状态更新|C11 atomics|原子实现和内存序|
|安全隔离需求|AMP/分区|核间协议和复位边界|

### 关键概念对比表

|概念|保护范围|是否允许阻塞|典型用途|
|---|---|---|---|
|本核关中断|当前核中断上下文|否|极短的本核中断保护|
|调度器锁|当前调度器/port 定义范围|通常否|防止特定调度切换|
|SMP 临界区|依 port，可能保护跨核内核状态|否或受限|内核短临界区|
|Spinlock|所有参与核|否|极短跨核共享访问|
|Mutex|任务级共享资源|是|可能等待的任务互斥|
|Atomic|特定变量或原子操作|通常否|计数器、标志、发布状态|
|任务亲和性|限制任务运行核|不适用|控制迁移和核负载|

## 16. 实践与进阶路径

### 16.1 梯度实战任务

1. 在目标工程中确认 FreeRTOS 版本、SMP port、配置宏和任务亲和性 API。
2. 创建双核任务并通过 trace 确认任务实际运行核。
3. 比较任务固定到单核和允许迁移时的执行时间分布。
4. 在两核上竞争同一 mutex，测量平均和最大等待时间。
5. 用只关本核中断的方式保护共享计数器，复现竞态，再用原子操作修复。
6. 构造跨核任务通知，测量通知提交到目标任务开始运行的延迟。
7. 实现 per-core 计数器，与单个全局原子计数器对比吞吐量。
8. 构造 cache line 相邻计数器和分离计数器，测量伪共享影响。
9. 将共享 SPI 驱动改造成资源所有者任务，比较锁等待和请求排队时延。
10. 运行高优先级 ISR、控制任务和通信负载，评估每核截止时间。

### 16.2 性能测试方法

测试报告至少记录：

- MCU/SoC 型号、核数、核频和总线频率；
- FreeRTOS 版本、port、SMP 配置和厂商补丁；
- 编译器、优化级别和 cache 配置；
- 每个任务的优先级和亲和性；
- 每核 ISR 频率和最大执行时间；
- 同核与跨核任务唤醒延迟；
- mutex/spinlock 平均和最大等待；
- 每核 CPU 利用率；
- 任务迁移次数；
- 共享队列吞吐和积压；
- D-cache、共享 SRAM、DMA 和核间一致性配置；
- 平均、P99 和最大响应时间。

测量时应区分：

```
API 返回时间
目标任务进入 Ready 时间
目标任务开始运行时间
业务处理完成时间
```

仅测量发送 API 的耗时，不能代表端到端通信延迟。

### 16.3 进阶学习方向

- 目标 FreeRTOS SMP port 的调度器和临界区源码。
- `vTaskCoreAffinitySet()` 等亲和 API 的具体实现与限制。
- Cortex-M 多核、RISC-V SMP 或目标 SoC 的核间中断机制。
- Spinlock、MCS lock、ticket lock 和短临界区性能比较。
- Cache coherence、伪共享、内存屏障和 DMA 缓存维护。
- SMP 固定优先级调度与每核可调度性分析。
- AMP 核间 mailbox、共享内存协议和故障恢复。
- SMP 系统的任务迁移、核隔离、功耗管理和低功耗唤醒。
- 多核 trace、跨核时间同步和最坏响应时间测量。
