## 3. 技术概述

### 核心定义

RTOS 动态内存分配，是指系统在运行期间根据请求，从一个或多个可管理内存区域中获取指定大小的存储空间，并在对象生命周期结束后归还。

典型流程如下：

```
申请内存
  -> 查找可用块
  -> 必要时拆分空闲块
  -> 更新分配器元数据
  -> 返回满足对齐要求的地址
  -> 使用对象
  -> 释放内存
  -> 合并相邻空闲块或归还固定池
```

在 RTOS 中，动态分配不仅服务于应用数据，也可能服务于内核对象：

```
TaskHandle_t task = NULL;

BaseType_t result = xTaskCreate(
    worker_task,
    "worker",
    512U,
    NULL,
    tskIDLE_PRIORITY + 2U,
    &task);
```

当使用动态创建 API 时，RTOS 可能为任务分配：

- 任务控制块（TCB）。
- 任务栈。
- 其他与内核对象相关的控制信息。

### 技术价值

动态分配的主要价值不是“节省内存”，而是：

- 支持运行期对象数量变化。
- 支持不同生命周期对象共享内存资源。
- 减少大量低峰期闲置的固定预留空间。
- 支持网络协议栈、文件系统、脚本引擎等动态数据结构。
- 允许启动时根据硬件能力、配置参数或外部设备数量创建资源。

代价是：

- 堆容量在运行期变化。
- 分配和释放时间可能不确定。
- 存在外部碎片和内部碎片。
- 错误生命周期会导致泄漏、重复释放和释放后访问。
- 在多任务系统中需要处理并发保护和优先级反转。

### 主流动态分配策略

|策略|典型实现|适用特点|
|---|---|---|
|线性分配、只申请不释放|FreeRTOS `heap_1`|启动期创建对象，运行期不销毁|
|可释放的简单链表|FreeRTOS `heap_2`|固定大小对象，分配尺寸变化较小|
|首次适配加相邻块合并|FreeRTOS `heap_4`|通用 RTOS 对象和应用堆|
|多区域堆|FreeRTOS `heap_5`|多段不连续 RAM、外部 RAM|
|C 库封装|FreeRTOS `heap_3`|复用 libc，但实时性依赖 C 库|
|固定块内存池|自研或 RTOS API|强实时、固定容量、对象尺寸有限|
|TLSF 等实时分配器|第三方或自研|需要较稳定的分配和释放上界|
|启动期动态、运行期冻结|工程架构策略|兼顾配置灵活性与运行期确定性|

## 4. 核心特性横向对比

|实现方案|是否支持释放|碎片风险|分配时间特征|多区域支持|适合 ISR|典型用途|
|---|---|---|---|---|---|---|
|`heap_1`|否|无外部碎片|通常接近 O(1)|否|否|启动期创建对象|
|`heap_2`|是|有|依空闲链表搜索长度变化|否|否|固定尺寸或近似固定尺寸对象|
|`heap_4`|是|较低但仍存在|首次适配，通常 O(n)|否|否|通用动态对象|
|`heap_5`|是|较低但仍存在|多区域搜索，通常 O(n)|是|否|片上 RAM 加外部 RAM|
|`heap_3`|是|由 libc 决定|由 libc 实现决定|由 libc 决定|否|已有 C 运行库环境|
|固定块池|是|无外部碎片|可做到 O(1)|可设计|通常否|网络包、消息块、DMA 缓冲|
|TLSF|是|有内部碎片|设计目标为近似 O(1)|需额外设计|通常否|实时系统中的变尺寸对象|
|启动期动态后冻结|启动期支持|运行期不增长|运行期无分配|取决于实现|否|高确定性产品系统|

**关键结论：**

- **任何通用动态分配器都不应默认放在硬实时路径中。**
- `heap_4` 的碎片问题比简单不合并算法更容易控制，但并不等于无碎片。
- 固定块池可以提供较强的时间确定性，但会产生内部浪费。
- `heap_1` 不是“没有动态分配”，而是只允许单向消耗的启动期动态分配。

## 5. 底层原理与功能特性深度解析

### 5.1 动态堆的基本内存布局

通用堆通常将一段连续内存划分为：

```
堆起始地址
+--------------------+
| 分配块头部         |
| 用户数据           |
+--------------------+
| 空闲块头部         |
| 空闲空间           |
+--------------------+
| 分配块头部         |
| 用户数据           |
+--------------------+
堆结束地址
```

分配块通常包含：

```
typedef struct HeapBlock {
    size_t size;
    struct HeapBlock *next;
} HeapBlock_t;
```

实际实现通常还会在 `size` 字段中使用低位保存“已分配”标志，以减少额外字段。

一个简化的分配流程如下：

```
void *simple_alloc(size_t requested_size)
{
    if (requested_size == 0U) {
        return NULL;
    }

    size_t total_size = align_up(
        requested_size + sizeof(BlockHeader_t),
        HEAP_ALIGNMENT);

    BlockHeader_t *block = find_free_block(total_size);
    if (block == NULL) {
        return NULL;
    }

    remove_or_split_block(block, total_size);
    block->allocated = true;

    return block_to_user_pointer(block);
}
```

完整实现还必须处理：

- 整数溢出。
- 对齐后的尺寸溢出。
- 最小剩余块大小。
- 堆首尾边界。
- 空闲链表损坏。
- 并发访问。
- 释放后相邻块合并。
- 非法地址和重复释放检测。

### 5.2 对齐与整数溢出

错误代码：

```
void *buffer_create(uint16_t count, uint16_t item_size)
{
    size_t size = count * item_size;
    return pvPortMalloc(size);
}
```

`count * item_size` 可能在较小整数类型中溢出，或者转换为 `size_t` 之前已经产生错误结果。

正确实现：

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

static bool size_mul_overflow(
    size_t a,
    size_t b,
    size_t *result)
{
    if (result == NULL) {
        return true;
    }

    if ((a != 0U) && (b > (SIZE_MAX / a))) {
        return true;
    }

    *result = a * b;
    return false;
}

void *buffer_create(size_t count, size_t item_size)
{
    size_t total_size;

    if (size_mul_overflow(count, item_size, &total_size)) {
        return NULL;
    }

    return pvPortMalloc(total_size);
}
```

如果还需要加上头部、尾部哨兵或对齐填充，则必须在加法前检查：

```
static bool size_add_overflow(
    size_t a,
    size_t b,
    size_t *result)
{
    if (result == NULL) {
        return true;
    }

    if (b > (SIZE_MAX - a)) {
        return true;
    }

    *result = a + b;
    return false;
}
```

**工程要求：** 所有来自网络、配置文件、设备描述符或外部协议的尺寸，都必须经过乘法和加法溢出检查。

### 5.3 FreeRTOS `heap_1`

`heap_1` 的基本特征：

- 从一块静态数组中线性切分内存。
- 只支持分配，不支持释放。
- 已分配空间不会回收。
- 分配路径通常非常简单，时间确定性较好。

适合：

- 系统启动阶段创建固定任务和队列。
- 运行期间不销毁对象的设备。
- 需要极简代码和较低验证成本的系统。

不适合：

- 网络连接反复建立和断开。
- 运行期间频繁创建和销毁对象。
- 需要释放大块临时缓存的应用。

示意配置：

```
#define configSUPPORT_DYNAMIC_ALLOCATION  1
#define configTOTAL_HEAP_SIZE             (32U * 1024U)
```

使用 `heap_1` 时，`vPortFree()` 不会真正回收对象。应用层必须确保对象生命周期只增长不回收，否则逻辑上会产生“内存泄漏”，而且该泄漏是设计确定的。

### 5.4 FreeRTOS `heap_2`

`heap_2` 支持释放，但传统实现通常不进行完整的相邻空闲块合并。因此：

- 释放后的空闲块可以再次使用。
- 不同大小的分配和释放会形成更多小空闲块。
- 长时间运行后可能出现严重外部碎片。
- 对固定尺寸、有限种类尺寸的对象更合适。

典型使用场景是：

```
对象尺寸集合有限
对象创建和删除频率低
对象尺寸变化小
系统可以接受一定碎片风险
```

对于具有大量不同消息长度、连接对象和缓存尺寸的系统，不应仅因为 `heap_2` 代码简单就使用它。

### 5.5 FreeRTOS `heap_4`

`heap_4` 通常采用：

- 按地址排序的空闲链表。
- 首次适配（first fit）。
- 释放时与前后相邻空闲块合并。
- 堆内存来自一个连续数组。
- 使用临界区保护堆结构。

简化的释放逻辑：

```
void vPortFree(void *ptr)
{
    if (ptr == NULL) {
        return;
    }

    BlockLink_t *block = user_to_block(ptr);

    enter_heap_critical();

    insert_block_sorted_by_address(block);
    coalesce_with_next(block);
    coalesce_with_previous(block);

    exit_heap_critical();
}
```

相邻合并只能解决**物理上连续**的空闲块。以下情况仍然可能无法合并：

```
空闲块 A | 已分配块 B | 空闲块 C
```

即使 A 和 C 总大小足够满足一次大分配，也不能直接合并，因为 B 将它们隔开。

#### 首次适配的行为

假设空闲链表如下：

```
[64 B] -> [512 B] -> [128 B] -> [1024 B]
```

申请 100 字节时，首次适配可能选择 512 字节块并拆分：

```
[64 B] -> [100 B 使用中] [412 B] -> [128 B] -> [1024 B]
```

这可能导致：

- 早期小块被跳过。
- 大块被切割成多个碎片。
- 后续大块申请失败，虽然总空闲量仍然足够。

### 5.6 FreeRTOS `heap_5`

`heap_5` 支持多个不连续内存区域：

```
HeapRegion_t regions[] = {
    { internal_ram, INTERNAL_RAM_SIZE },
    { external_ram, EXTERNAL_RAM_SIZE },
    { NULL, 0U }
};

vPortDefineHeapRegions(regions);
```

适合：

- 片上 SRAM 和外部 SRAM 并存。
- 多个 RAM bank 地址不连续。
- 需要将统一动态堆扩展到多个内存区域。

但必须注意：多个区域只是由同一个分配器管理，**它不会自动理解不同内存区域的功能属性**。例如：

- DMA 外设可能无法访问外部 RAM。
- 某些 RAM 具有缓存，另一些没有。
- 关键控制数据不能放在慢速外部 RAM。
- 安全域和非安全域可能不能互相访问。

如果对象具有内存区域要求，建议使用专用分配接口，而不是将所有区域直接合并为一个通用堆。

### 5.7 `heap_3` 与 C 运行库

`heap_3` 通常通过封装 `malloc()` 和 `free()` 实现：

```
void *pvPortMalloc(size_t size)
{
    void *ptr;

    taskENTER_CRITICAL();
    {
        ptr = malloc(size);
    }
    taskEXIT_CRITICAL();

    return ptr;
}
```

其主要风险：

- C 库分配器的时间复杂度不一定适合实时系统。
- C 库可能需要额外的 `_sbrk()` 或系统调用适配。
- 多线程安全策略依赖工具链和 C 库实现。
- 堆起始位置和上限可能由链接脚本决定，而不是由 FreeRTOS 配置决定。
- `printf()`、文件系统或网络库可能间接使用堆。

如果选用 `heap_3`，必须同时审查：

- C 库版本。
- 系统调用重入配置。
- 堆和栈的边界。
- `malloc()` 锁的实现。
- 失败行为和统计接口。

### 5.8 动态创建 RTOS 对象

动态创建任务：

```
static TaskHandle_t s_worker_task;

BaseType_t worker_task_create(void)
{
    BaseType_t result = xTaskCreate(
        worker_task,
        "worker",
        512U,
        NULL,
        tskIDLE_PRIORITY + 2U,
        &s_worker_task);

    if (result != pdPASS) {
        s_worker_task = NULL;
        return pdFAIL;
    }

    return pdPASS;
}
```

动态创建队列：

```
static QueueHandle_t s_message_queue;

BaseType_t message_queue_create(void)
{
    s_message_queue = xQueueCreate(
        16U,
        sizeof(Message_t));

    if (s_message_queue == NULL) {
        return pdFAIL;
    }

    return pdPASS;
}
```

删除对象时必须明确：

- 是否仍有任务持有对象句柄。
- 是否还有任务阻塞在该对象上。
- 是否还有 ISR 或回调可能访问对象。
- 删除对象后是否重置句柄。
- 失败路径是否释放已创建的前置资源。

```
void message_queue_destroy(void)
{
    QueueHandle_t queue = s_message_queue;

    s_message_queue = NULL;

    if (queue != NULL) {
        vQueueDelete(queue);
    }
}
```

仅仅调用 `vQueueDelete()` 并将句柄置空，不能解决其他任务已经缓存该句柄的问题。对象销毁必须与任务停止、引用计数或状态机配合。

### 5.9 线程安全与临界区

通用堆的元数据通常由链表、位图或树结构组成。两个任务同时操作会破坏内部状态，因此分配器必须使用：

- 关中断。
- 调度器锁。
- 互斥锁。
- 专用堆锁。
- 无锁算法或每核堆。

不同保护方法的代价不同：

|保护方式|优点|风险|
|---|---|---|
|关中断|简单，ISR 不会打断|临界区过长，影响中断延迟|
|禁止调度|任务间互斥|仍可能被 ISR 打断|
|互斥锁|可表达所有权|可能产生优先级反转|
|每线程缓存|降低全局锁竞争|内存浪费和回收复杂|
|固定池|操作简单|尺寸和容量固定|

**ISR 中不能直接调用普通动态分配函数。** 原因包括：

- 可能进入不可在 ISR 中使用的临界区。
- 可能阻塞或等待锁。
- 执行时间不可预测。
- 失败路径不容易在中断上下文安全处理。

ISR 应发送预分配事件、索引或固定块，而不是申请新内存。

## 6. 性能量化分析

### 6.1 内存开销

动态分配的实际消耗通常为：

```
实际消耗 =
    用户请求大小
  + 块头部
  + 对齐填充
  + 可选哨兵区域
  + 分配器管理开销
```

例如：

```
用户请求：        100 B
块头部：           16 B
16 字节对齐填充：   12 B
实际占用：         128 B
```

内部碎片为：

```
内部碎片 = 实际占用 - 用户请求
         = 128 - 100
         = 28 B
```

内部碎片率：

```
内部碎片率 = 内部碎片 / 实际占用
           = 28 / 128
           = 21.875%
```

不同分配器的块头大小和对齐要求不同，必须以目标版本源码和编译结果为准。

### 6.2 外部碎片率

常用监控指标：

```
总空闲量 = 所有空闲块大小之和
最大空闲块 = 空闲块中最大的单块
外部碎片率 = 1 - 最大空闲块 / 总空闲量
```

例如：

```
空闲块：256 B、128 B、64 B
总空闲量：448 B
最大空闲块：256 B

外部碎片率 = 1 - 256 / 448
           ≈ 42.86%
```

该指标不是唯一标准，但可以反映“空闲内存是否被切碎”。即使总空闲量很多，如果最大空闲块小于请求大小，分配仍会失败。

### 6.3 代表性测量数据

以下数据是一个**示例基准**，用于说明测量方法，不应直接作为其他芯片的性能承诺。

测试条件：

```
MCU：Cortex-M4F，主频 168 MHz
编译器：GCC，-O2
RTOS：FreeRTOS 10.x
堆：片上 SRAM，4 字节对齐
测量工具：DWT CYCCNT
测试内容：单任务上下文、无中断干扰
```

|操作|代表性平均周期|代表性最大周期|说明|
|---|---|---|---|
|`heap_1` 分配 64 B|约 40 cycles|约 50 cycles|线性切分|
|`heap_4` 分配 64 B，短链表|约 90 cycles|约 180 cycles|首次适配|
|`heap_4` 分配 64 B，长链表|约 260 cycles|约 700 cycles|受空闲块数量影响|
|`heap_4` 释放并合并|约 120 cycles|约 300 cycles|取决于相邻块|
|固定块池获取|约 25 cycles|约 35 cycles|单链表 O(1)|
|固定块池归还|约 20 cycles|约 30 cycles|无复杂校验|

换算方法：

```
执行时间 = 周期数 / CPU 频率
```

在 168 MHz 下：

```
700 cycles / 168 MHz ≈ 4.17 us
```

实际结果会受以下因素影响：

- 编译器优化等级。
- 堆链表长度。
- 中断抢占。
- Cache 和 TCM。
- 临界区实现。
- 地址对齐。
- 调试检查和填充字节。
- 多任务竞争。

### 6.4 瓶颈分析

动态分配的主要瓶颈包括：

1. **空闲链表搜索**
    
    - 首次适配需要遍历多个空闲块。
    - 空闲块越多，搜索时间越可能增长。
2. **全局堆锁竞争**
    
    - 多任务并发申请时，任务可能串行进入分配器。
    - 低优先级任务持有堆锁时，高优先级任务可能被延迟。
3. **碎片化**
    
    - 总空闲量足够，但不存在连续大块。
    - 频繁变尺寸分配最容易产生此问题。
4. **缓存和内存区域差异**
    
    - 外部 RAM 的访问延迟可能明显高于片上 SRAM。
    - DMA 与 CPU 之间还可能需要缓存维护。
5. **失败处理路径**
    
    - 分配失败时触发日志、回滚或重启，可能导致额外延迟。
    - 在实时路径中，失败路径往往比成功路径更难验证。

### 6.5 优化手段与收益

|优化手段|主要收益|代价|
|---|---|---|
|固定块池|O(1) 获取和归还，消除外部碎片|内部碎片、尺寸固定|
|按尺寸分级池|降低内部碎片|需要多个池和容量管理|
|启动期分配后冻结|运行期时间确定|运行期不能新增对象|
|按生命周期分区|降低长期碎片|需要对象分类|
|大小分类空闲链表|缩短搜索路径|元数据和实现复杂度增加|
|TLSF|更稳定的分配延迟|验证和集成成本更高|
|限制分配尺寸集合|便于复用和测试|灵活性降低|
|统计和水位监控|及时发现资源异常|额外 RAM 和 CPU 开销|

## 7. 应用场景选型指南

### 纯文本决策流程图

```
对象是否能在编译期确定数量和大小？
├─ 是
│  ├─ 是否需要运行期借还？
│  │  ├─ 否 -> 使用静态对象
│  │  └─ 是 -> 使用固定块池
│  └─ 是否属于启动期一次性创建？
│     ├─ 是 -> heap_1 或启动期动态后冻结
│     └─ 否 -> 固定池优先
└─ 否
   ├─ 对象最大数量能否设定上限？
   │  ├─ 是
   │  │  ├─ 尺寸是否固定或少量等级？
   │  │  │  ├─ 是 -> 分级固定块池
   │  │  │  └─ 否 -> 受控 heap_4 / TLSF
   │  │  └─ 运行期是否硬实时？
   │  │     ├─ 是 -> 避免通用堆，使用池或预分配
   │  │     └─ 否 -> 评估 heap_4 / heap_5
   │  └─ 否
   │     ├─ 是否为关键实时路径？
   │     │  ├─ 是 -> 重新定义最大容量，禁止无界分配
   │     │  └─ 否 -> 可使用受监控通用堆
   └─ 是否需要多个 RAM 区域？
      ├─ 是 -> heap_5 或区域专用分配器
      └─ 否 -> 单区域分配器
```

### 典型场景需求与方案

|场景需求|推荐方案|主要理由|
|---|---|---|
|启动时创建固定任务|`heap_1` 或静态创建|运行期不释放，确定性高|
|TCP 连接动态建立和销毁|`heap_4`、TLSF 或连接对象池|对象生命周期动态|
|网络包缓冲区|固定块池或分级池|避免变尺寸碎片和延迟抖动|
|文件系统缓存|`heap_4` 或专用缓存池|尺寸变化但通常非硬实时|
|DMA 描述符|静态数组或固定池|地址、对齐和区域属性可控|
|多个 RAM bank|`heap_5` 或专用区域分配器|支持不连续区域|
|安全关键控制路径|静态对象和固定池|容量和最坏延迟易审计|
|低优先级日志系统|受控 `heap_4`|失败可丢弃，实时要求较低|

## 8. 工程最佳实践

### 设计原则

- **禁止无界动态分配。** 所有动态资源都应有最大数量、最大尺寸和最大持有时间。
- **关键实时路径不执行通用堆分配。**
- 动态分配接口必须返回失败状态，调用者必须定义失败策略。
- 每次分配都应有明确的所有者和释放责任。
- 一个对象只能有一个最终释放责任方。
- 释放后立即清空句柄，降低悬空指针风险。
- 尺寸计算必须检查乘法、加法和对齐溢出。
- 网络、文件、协议解析等外部输入不能直接作为无上限分配尺寸。
- 将 DMA、缓存敏感、关键控制数据和普通应用数据分配到不同区域。
- 运行期必须监控堆低水位、最大可用块、失败次数和碎片率。

### 选型决策矩阵

|维度|`heap_1`|`heap_4`|`heap_5`|固定块池|TLSF|
|---|---|---|---|---|---|
|支持释放|否|是|是|是|是|
|运行期扩展|低|中|中|有界|中|
|时间确定性|高|中低|中低|高|较高|
|外部碎片|无|有|有|无|受控但不为零|
|多区域|否|否|是|可设计|可设计|
|实现复杂度|低|中|中|中|高|
|适合硬实时|启动阶段|通常不建议|通常不建议|推荐|需验证|
|适合变尺寸对象|否|是|是|否或分级|是|

### 工业级编码规范

- 使用 `size_t` 表示内存尺寸，不使用 `uint16_t` 或 `int` 表示通用分配长度。
- 不允许将负数、外部输入或未经检查的协议字段直接转换成 `size_t`。
- 不在 ISR、硬实时任务和高优先级控制循环中调用 `malloc()`、`pvPortMalloc()` 或 `free()`。
- 将分配、释放、统计和失败告警封装成项目统一接口。
- 统一记录分配来源、大小、任务名或模块 ID。
- 生产构建中保留堆失败统计，不要只在调试版本启用。
- 释放函数允许接收 `NULL` 时，仍应显式管理句柄状态。
- 不允许同一指针由多个模块隐式共享释放责任。
- 不依赖 `volatile` 解决堆元数据并发问题。
- 对动态对象配置创建、运行、停止、销毁完整状态机。

## 9. 常见错误与避坑指南

### 错误一：在 ISR 中调用动态分配

```
void DMA_IRQHandler(void)
{
    uint8_t *packet = pvPortMalloc(128U);
    if (packet != NULL) {
        process_packet_from_isr(packet);
    }
}
```

**根因：**

- 分配器可能进入临界区或锁。
- 分配时间不可预测。
- ISR 中无法可靠处理阻塞、失败和复杂回滚。
- `process_packet_from_isr()` 可能并非真正的 ISR 安全接口。

**正确实现：**

```
static uint8_t s_dma_packet_pool[8U][128U];
static QueueHandle_t s_packet_queue;

void DMA_IRQHandler(void)
{
    BaseType_t higher_priority_woken = pdFALSE;
    uint8_t index = dma_get_completed_buffer_index();

    if (index < 8U) {
        (void)xQueueSendFromISR(
            s_packet_queue,
            &index,
            &higher_priority_woken);
    }

    portYIELD_FROM_ISR(higher_priority_woken);
}
```

**风险影响：** 中断延迟不可控、堆链表损坏、系统随机崩溃。

### 错误二：分配尺寸计算溢出

```
void *create_items(uint16_t count, uint16_t size)
{
    return pvPortMalloc(count * size);
}
```

**根因：**

- 乘法可能在 16 位类型中溢出。
- 外部输入可能故意构造超大值。
- 溢出后申请了远小于预期的缓冲区。

**正确实现：**

```
void *create_items_safe(size_t count, size_t item_size)
{
    size_t total;

    if ((item_size != 0U) &&
        (count > (SIZE_MAX / item_size))) {
        return NULL;
    }

    total = count * item_size;

    return pvPortMalloc(total);
}
```

**风险影响：** 后续写入越界，破坏相邻堆元数据或 RTOS 控制结构。

### 错误三：释放后继续使用

```
Message_t *message = pvPortMalloc(sizeof(*message));

if (message != NULL) {
    send_message(message);
    vPortFree(message);
}

/* 错误：send_message() 可能异步使用 message。 */
```

**根因：**

- 调用者误以为发送函数立即完成。
- 队列传递的是指针，而不是结构体副本。
- 没有定义消息所有权转移时刻。

**正确实现：**

```
typedef struct {
    Message_t *message;
    bool ownership_transferred;
} SendResult_t;
```

工程上应明确约定：

```
发送成功 -> 接收方拥有并负责释放
发送失败 -> 发送方仍拥有并负责释放
```

或者使用固定块池，通过块索引传递所有权。

**风险影响：** 释放后访问、数据破坏、双重释放。

### 错误四：忽略堆分配失败

```
Buffer_t *buffer = pvPortMalloc(sizeof(*buffer));
buffer->length = 0U;
```

**根因：** 动态分配可能因堆耗尽、碎片、尺寸超限或区域不可用而失败。

**正确实现：**

```
Buffer_t *buffer = pvPortMalloc(sizeof(*buffer));

if (buffer == NULL) {
    system_record_memory_fault(
        MEMORY_OWNER_PROTOCOL,
        sizeof(*buffer));

    return ERR_NO_MEMORY;
}

buffer->length = 0U;
```

**风险影响：** 空指针解引用、异常复位、故障状态无法追踪。

### 错误五：频繁变尺寸分配导致碎片

```
for (;;) {
    size_t size = protocol_get_payload_size();
    uint8_t *payload = pvPortMalloc(size);

    if (payload == NULL) {
        break;
    }

    process_payload(payload, size);
    vPortFree(payload);
}
```

**根因：**

- 分配尺寸由外部输入控制。
- 任务和模块之间的分配释放顺序不稳定。
- 不同尺寸的空闲块不断被拆分。

**正确实现：**

```
#define PAYLOAD_BLOCK_SIZE  1536U
#define PAYLOAD_BLOCK_COUNT 8U

/* 使用固定块池；超过上限时丢弃、分片或回压。 */
```

**风险影响：** 运行时间越长，最大可分配块逐步降低，最终出现“总空闲足够但申请失败”。

### 错误六：删除 RTOS 对象时仍有任务访问

```
vQueueDelete(s_queue);
s_queue = NULL;
```

**根因：**

- 其他任务可能已经复制了旧句柄。
- 阻塞在队列上的任务可能尚未退出。
- 回调或定时器仍可能触发访问。

**正确实现：**

```
停止生产者
  -> 唤醒并退出消费者
  -> 等待所有引用归零
  -> 删除队列
  -> 清空全局句柄
```

**风险影响：** 访问已释放的队列控制块，破坏堆元数据或触发 HardFault。

## 10. 多机制组合使用方案

### 10.1 推荐架构

```
系统启动阶段
  ├─ 静态创建关键任务
  ├─ heap_1 创建一次性初始化对象
  └─ 建立固定块池和分级缓存池

运行期关键路径
  ├─ 控制任务：静态对象
  ├─ ISR：只提交索引或事件
  ├─ 网络包：固定块池
  └─ DMA：专用静态缓冲区

运行期非关键路径
  ├─ 文件系统缓存：受控 heap_4
  ├─ 日志格式化：固定缓冲区或受控堆
  └─ 配置解析：启动期分配后冻结

监控层
  ├─ 堆剩余量
  ├─ 最大空闲块
  ├─ 分配失败次数
  ├─ 各模块持有量
  └─ 最大持有时间
```

### 10.2 统一分配接口

不要让业务模块直接调用 `pvPortMalloc()`，可以封装模块级接口：

```
typedef enum {
    MEM_OWNER_NETWORK = 0,
    MEM_OWNER_LOG,
    MEM_OWNER_CONFIG,
    MEM_OWNER_COUNT
} MemoryOwner_t;

typedef struct {
    size_t current_bytes;
    size_t peak_bytes;
    uint32_t alloc_count;
    uint32_t free_count;
    uint32_t fail_count;
} MemoryStats_t;

void *system_mem_alloc(
    MemoryOwner_t owner,
    size_t size);

void system_mem_free(
    MemoryOwner_t owner,
    void *ptr,
    size_t size);
```

实现时需要考虑并发保护：

```
void *system_mem_alloc(
    MemoryOwner_t owner,
    size_t size)
{
    void *ptr;

    if ((owner >= MEM_OWNER_COUNT) || (size == 0U)) {
        return NULL;
    }

    ptr = pvPortMalloc(size);

    if (ptr == NULL) {
        memory_stats_record_failure(owner, size);
        return NULL;
    }

    memory_stats_record_alloc(owner, size);
    return ptr;
}
```

释放时传入 `size` 可能与真实分配尺寸不一致，因此生产实现通常需要：

- 在分配头部保存模块 ID 和实际大小。
- 使用独立跟踪表。
- 或要求调用者保存对象长度。

### 10.3 固定块池框架

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

#define POOL_BLOCK_COUNT  16U
#define POOL_BLOCK_SIZE   256U

typedef struct PoolNode {
    struct PoolNode *next;
} PoolNode_t;

typedef struct {
    PoolNode_t *free_list;
    uint8_t storage[POOL_BLOCK_COUNT][POOL_BLOCK_SIZE];
    size_t free_count;
    size_t peak_used;
} MemoryPool_t;

static MemoryPool_t s_pool;

bool pool_init(MemoryPool_t *pool)
{
    if (pool == NULL) {
        return false;
    }

    pool->free_list = NULL;
    pool->free_count = POOL_BLOCK_COUNT;
    pool->peak_used = 0U;

    for (size_t i = 0U; i < POOL_BLOCK_COUNT; ++i) {
        PoolNode_t *node =
            (PoolNode_t *)&pool->storage[i][0];

        node->next = pool->free_list;
        pool->free_list = node;
    }

    return true;
}
```

获取和归还时必须使用 RTOS 互斥保护或在单生产者/单消费者约束下设计。还应检查：

- 指针是否落在池范围内。
- 地址是否按块大小对齐。
- 是否重复归还。
- 是否发生跨池归还。
- 是否存在并发获取和归还。

## 11. 工业级实际案例分析

### 案例一：工业以太网连接管理

#### 需求

- 支持最多 8 个 TCP 连接。
- 每个连接对象生命周期动态变化。
- 网络包长度变化，但最大长度为 1536 字节。
- 连接建立和断开不属于硬实时控制周期。

#### 架构设计

```
连接控制块：固定 8 个对象池
接收包：1536 B 固定块池
发送包：1536 B 固定块池
连接状态：固定数组
低优先级协议解析临时对象：受控 heap_4
```

#### 设计要点

- 不为每个 TCP 包调用不同尺寸的 `malloc()`。
- 连接控制块达到 8 个时返回资源不足，而不是无限申请。
- 接收队列传递块索引，不传递不受控裸指针。
- 网络发送失败时，发送任务必须归还块。
- 连接断开流程先停止收发，再回收所有关联块。

#### 容量估算

```
接收池：8 × 1536 B = 12288 B
发送池：8 × 1536 B = 12288 B
连接对象：8 × sizeof(Connection_t)
```

还需增加：

- 池管理元数据。
- 队列存储区。
- 对齐填充。
- 协议栈自身占用。

### 案例二：工业数据采集与文件缓存

#### 需求

- 采集任务每 10 ms 产生一条固定大小记录。
- 文件系统写入可能出现 100 ms 级延迟。
- 不允许采集任务因文件系统分配延迟而阻塞。
- 磁盘缓存大小有明确上限。

#### 架构设计

```
采集任务
  -> 固定记录池
  -> 记录队列
  -> 文件写入任务
  -> 写入成功后归还记录块
```

文件系统内部缓存可以使用受控 `heap_4`，但采集数据路径使用固定池。

#### 队列容量估算

如果采集周期为 10 ms，文件写入最坏阻塞时间为 100 ms：

```
最小缓存记录数 >= 100 ms / 10 ms = 10
```

考虑调度抖动、突发延迟和安全余量，实际可以配置：

```
缓存记录数 = 16 或 20
```

不能只按平均写入时间配置，否则在偶发存储延迟下会丢数据。

### 案例三：带外部 SDRAM 的工业 HMI

#### 需求

- 片上 SRAM 用于控制和 RTOS 内核。
- 外部 SDRAM 用于图片和大块缓存。
- DMA 只能访问指定 RAM 区域。
- 显示刷新任务对延迟有一定要求，但不属于硬实时控制。

#### 架构设计

```
片上 SRAM：
  - RTOS 任务栈
  - 控制对象
  - DMA 描述符
  - 小型消息池

外部 SDRAM：
  - 图片缓存
  - 大型帧缓冲区
  - 非关键 UI 对象

分配接口：
  - control_mem_alloc()
  - dma_mem_alloc()
  - display_mem_alloc()
```

不建议把片上 SRAM 和外部 SDRAM 无差别放入同一个 `heap_5`，再由调用者猜测返回地址。更稳妥的做法是按用途建立区域专用分配器。

## 12. 高频问题深度答疑

### 1. `heap_4` 已经支持合并，为什么仍然会碎片化？

因为合并只能处理相邻空闲块。被仍在使用的块隔开的空闲区域无法合并。动态分配尺寸和释放顺序持续变化时，堆会形成大量不连续空闲区域。

此外，分配器还可能产生内部碎片：

- 对齐填充。
- 块头部。
- 最小空闲块限制。
- 分配尺寸向上取整。

因此，`heap_4` 只是降低碎片风险，不是消除碎片。

### 2. 总空闲量足够，为什么仍然分配失败？

动态分配通常需要一个连续区域。假设总空闲量为 20 KB，但最大空闲块只有 2 KB，而请求为 4 KB，则仍会失败。

因此必须同时监控：

```
总空闲量
最大空闲块
最小历史空闲量
分配失败次数
外部碎片率
```

仅监控 `xPortGetFreeHeapSize()` 不足以判断堆健康状态。

### 3. 动态分配可以用于普通任务吗？

可以，但要区分任务类型和执行路径：

- 启动任务：通常可以使用。
- 低优先级配置任务：经过容量限制后可以使用。
- 网络连接管理：可以使用池或受控堆。
- 控制周期任务：通常不应使用通用堆。
- ISR：不应使用普通动态分配。
- 安全关键任务：除非完成严格的最坏时间和失败分析，否则应避免。

问题不在于“动态分配绝对不能用”，而在于其使用位置、上限和失败策略是否可证明。

### 4. 什么时候应该使用 TLSF，而不是 `heap_4`？

当系统同时满足以下条件时，可以评估 TLSF：

- 对象尺寸变化较大。
- 运行期确实需要释放和重新分配。
- 需要比线性空闲链表更稳定的分配时间。
- 系统能够承担更高的实现和验证复杂度。
- 已有目标平台实现、测试工具和故障注入方案。

TLSF 也不是自动实时安全。必须测量：

- 目标编译器下的最大分配时间。
- 释放时间。
- 并发保护时间。
- 碎片和内存利用率。
- 异常输入和堆损坏检测行为。

### 5. 动态分配失败时应该重启系统吗？

取决于资源性质和安全策略：

- 关键控制对象申请失败：可能进入安全状态。
- 日志缓存申请失败：可以丢弃日志并计数。
- 网络包申请失败：可以丢包或触发背压。
- UI 图片缓存失败：可以降级分辨率或显示占位内容。
- 内存损坏检测失败：通常需要隔离、复位或安全停机。

不能把所有失败都统一处理为重启，也不能静默忽略失败。

### 6. `malloc()` 和 `pvPortMalloc()` 能混用吗？

通常不应混用，除非工程明确规定并验证：

- 两者是否使用同一堆。
- 是否使用不同堆。
- 是否允许 `free()` 释放 `pvPortMalloc()` 返回的地址。
- 是否存在线程安全问题。
- 链接脚本中两个堆的边界如何定义。
- 统计和故障处理如何统一。

最安全的规则是：

```
malloc() 返回的指针只能由 free() 释放；
pvPortMalloc() 返回的指针只能由 vPortFree() 释放。
```

## 13. 课程核心总结

- **动态内存分配提供运行期灵活性，但引入容量、时间、碎片和生命周期风险。**
- `heap_1` 适合只申请不释放的启动阶段。
- `heap_2` 支持释放，但碎片控制能力有限。
- `heap_4` 通过相邻空闲块合并改善碎片，仍不保证无碎片和恒定时间。
- `heap_5` 支持多段 RAM，但不会自动解决 DMA、Cache、速度和安全属性差异。
- 固定块池适合网络包、消息块和 DMA 缓冲区，通常能提供更好的时间确定性。
- 所有动态尺寸计算都必须处理整数溢出、对齐和容量上限。
- ISR 和硬实时路径不应调用通用动态分配。
- 动态分配对象必须建立清晰的所有权、失败回滚和销毁流程。
- 堆监控至少应包括：**总空闲量、最大空闲块、历史最低水位、失败次数、分配延迟和模块归属**。
- 工业级系统通常采用组合方案：**关键对象静态化，固定数据使用内存池，非关键动态对象使用受控通用堆**。

## 16. 实践与进阶路径

### 梯度实战任务

1. 在目标板上启用 `heap_4`，实现任务和队列的动态创建，并完整检查创建失败。
2. 记录每次分配的模块 ID、尺寸、地址和释放时间，建立堆使用统计。
3. 编写随机尺寸分配和释放测试，统计总空闲量、最大空闲块和外部碎片率。
4. 实现一个固定块池，加入非法地址、重复归还、池耗尽和并发访问检测。
5. 将网络缓冲区从通用堆迁移到分级固定块池，比较吞吐量、延迟和 RAM 利用率。
6. 实现启动期动态分配、运行期冻结机制，验证冻结后所有动态申请路径均被拒绝。
7. 对比 `heap_4`、固定池和 TLSF 在目标 MCU 上的平均延迟、最大延迟和碎片行为。

### 性能测试方法

- 使用 DWT `CYCCNT` 或硬件定时器包围分配和释放函数。
- 分别测试空闲链表短、中、长三种状态。
- 记录平均值、P95、P99 和最大值，不能只记录平均执行时间。
- 进行多任务并发测试，覆盖高优先级任务抢占和中断干扰。
- 运行长时间随机分配测试，观察最大空闲块随时间的变化。
- 注入分配失败，验证业务模块的丢弃、重试、降级和安全停机策略。
- 检查堆起始地址、结束地址和栈边界，避免堆栈碰撞。
- 在发布编译选项、目标时钟和真实内存布局下测试。
