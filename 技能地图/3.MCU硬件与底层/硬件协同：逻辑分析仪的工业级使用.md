
## 1. 学习目标

### 理解

- 理解逻辑分析仪从输入探头、阈值比较器、采样器、触发器、采集存储器到协议解码器的完整数据链路。
- 理解**定时采集、状态采集、同步采样、异步采样、毛刺捕获、协议触发**的本质差异。
- 理解逻辑分析仪只记录数字判决结果，无法直接反映过冲、振铃、慢边沿和逻辑电平裕量。
- 理解采样率、存储深度、通道数、压缩方式与可观测时间窗之间的约束。
- 理解 MCU 软件事件、数字总线事务与系统状态机之间的时间关联。

### 掌握

- 掌握 UART、SPI、I²C、CAN、LIN、1-Wire 等常用协议的采集、解码和触发方法。
- 掌握数字输入阈值、采样率、存储深度、预触发比例和触发条件配置。
- 掌握通过 GPIO、定时器、DMA 和 RTOS 事件构建固件可观测点。
- 掌握建立保持时间、总线占用率、事务延迟、中断响应和任务抖动的测量方法。
- 掌握逻辑分析仪与示波器、协议分析仪、DWT、ETM/SWO 的协同使用。

### 精通

- 精通采样量化误差、亚稳态、异步采样、通道偏斜和输入负载对测量结果的影响。
- 精通偶发协议故障、竞争条件、丢中断、异常片选、总线锁死和实时性长尾问题的定位。
- 能判断异常来自**协议实现、软件调度、电气完整性、采样设置或解码配置**。
- 能通过分层触发和状态编码，在长时间运行系统中捕获低概率故障。
- 能对测量结果给出误差边界，而不是只读取软件自动生成的时间值。

### 能够设计

- 能设计面向逻辑分析的 PCB 测试点、调试连接器和低负载探测接口。
- 能设计低侵入固件追踪总线和状态编码机制。
- 能设计跨 MCU、FPGA、传感器、通信模块的统一时间关联方案。
- 能建立基于命令行解码、波形文件和自动判据的硬件在环回归体系。

## 3. 技术概述

### 3.1 核心定义

逻辑分析仪将多个输入节点的连续电压与设定阈值比较，再按照采样时钟把判决结果记录为离散逻辑状态。

```
被测数字节点
    │
    ├─ 探头与连接线
    │
    ├─ 输入保护和高阻缓冲
    │
    ├─ 阈值比较器
    │      ├─ 电压 >= VIH -> 逻辑 1
    │      ├─ 电压 <= VIL -> 逻辑 0
    │      └─ 中间区域    -> 结果不确定
    │
    ├─ 定时采样或状态采样
    │
    ├─ 触发逻辑
    │
    ├─ 采集存储器/流式传输
    │
    └─ 波形显示、测量和协议解码
```

逻辑分析仪最终保存的是：

D[n]∈{0,1}D[n]∈{0,1}

而示波器保存的是量化后的电压：

V[n]∈RV[n]∈R

因此，逻辑分析仪擅长回答：

- 哪个事件先发生？
- 某帧发送了什么数据？
- 任务和中断之间间隔多久？
- 哪个状态组合触发了故障？
- 总线在长时间运行中何时出现异常？

它不能独立可靠回答：

- 高电平实际是多少伏？
- 边沿是否存在过冲和振铃？
- 输入是否有足够噪声裕量？
- 某个错误位是软件发错，还是电气波形跨阈值多次？
- 电源跌落是否导致数字状态异常？

### 3.2 技术价值

- 以较多通道同时观察 CPU、FPGA、外设和通信模块。
- 长时间记录低概率协议异常及其前后上下文。
- 将软件状态、中断、DMA、总线和外设行为映射到统一时间轴。
- 验证接口协议、状态机顺序和芯片时序约束。
- 量化总线利用率、事务延迟、任务抖动和响应长尾。
- 通过自动解码和脚本分析建立可重复的回归测试。

### 3.3 主流技术分支

#### 按采样机制分类

- **定时分析 Timing Analysis**：使用逻辑分析仪内部时钟异步采样。
- **状态分析 State Analysis**：使用被测系统时钟同步采样数据。
- **过渡存储 Transition Storage**：只记录边沿或状态变化时间。
- **流式采集 Streaming Capture**：持续将数据传送到主机。
- **深存储采集 Deep Memory**：使用本地高速存储捕获高数据率事件。

#### 按设备形态分类

- USB 便携式逻辑分析仪。
- 台式高性能逻辑分析仪。
- 示波器内置 MSO 数字通道。
- FPGA 内嵌逻辑分析仪，如 Xilinx ILA、Intel Signal Tap。
- 专用协议分析仪，如 USB、PCIe、CAN 和 Ethernet 分析仪。

#### 按分析目标分类

- 数字时序分析。
- 协议事务分析。
- 软件执行路径关联。
- FPGA 内部信号分析。
- 总线性能与占用率分析。
- 长时间异常事件捕获。

## 5. 底层原理与功能特性深度解析

### 5.1 数字阈值判决

逻辑分析仪通过比较器将模拟电压转换为数字状态：

D(t)={0,V(t)≤VTH1,V(t)>VTHD(t)={0,1,​V(t)≤VTH​V(t)>VTH​​

真实数字输入通常还定义：

- `VIL(max)`：保证识别为低电平的最大输入电压。
- `VIH(min)`：保证识别为高电平的最小输入电压。
- `VIL(max) < V < VIH(min)`：不确定区域。

逻辑分析仪显示稳定的 0 或 1，**不代表被测芯片拥有足够逻辑裕量**。分析仪阈值与芯片阈值可能不同。

例如，1.8 V CMOS 输入要求：

```
VIL(max) = 0.35 × VDD = 0.63 V
VIH(min) = 0.65 × VDD = 1.17 V
```

若分析仪阈值固定为 1.4 V，则一个 1.25 V 高电平：

- 对被测芯片可能是合法高电平。
- 对分析仪可能被判为低电平。

反之，分析仪也可能将芯片处于不确定区的电压判为稳定逻辑值。

### 5.2 异步采样和时间量化误差

定时分析使用内部采样时钟：

tn=nTs,Ts=1fstn​=nTs​,Ts​=fs​1​

被测边沿通常不与采样时钟对齐。一个边沿被记录到相邻采样点，其单边沿时间误差约为：

0≤ϵedge<Ts0≤ϵedge​<Ts​

两个独立边沿之间的时间差测量误差最坏约为：

∣ϵΔt∣<2Ts∣ϵΔt​∣<2Ts​

在均匀独立相位假设下，单边沿量化误差标准差近似为：

σedge=Ts12σedge​=12​Ts​​

例如 `f_s = 100 MS/s`：

Ts=10nsTs​=10ns

那么：

- 单边沿误差小于 10 ns。
- 两边沿间隔最坏误差接近 20 ns。
- 单边沿标准差约 2.89 ns。

因此，用 100 MS/s 分析仪声称测得 `5.2 ns` 时序差没有工程意义。

### 5.3 采样率选择

Nyquist 条件只适合带限模拟信号重建，不能直接作为可靠数字时序捕获准则。

工程上可采用：

fs≥K×feventfs​≥K×fevent​

其中：

- 只需协议解码：`K` 通常取 4~10。
- 需要脉宽和边沿间隔分析：`K` 通常取 10~20。
- 需要发现窄毛刺：采样周期必须显著小于毛刺宽度。
- UART 解码：通常至少每位 4~8 点，复杂抖动分析需要更多。
- SPI 解码：至少稳定采到每个有效边沿及边沿间数据。

对最小脉宽 `Tmin`，若要求至少采到 `N` 个点：

fs≥NTminfs​≥Tmin​N​

要让 50 ns 脉冲至少包含 5 个采样点：

fs≥550ns=100MS/sfs​≥50ns5​=100MS/s

需要注意，通道数增加时部分设备会降低每通道最大采样率。

### 5.4 存储深度与捕获时间

未压缩连续采集时：

Tcapture=MemoryDepthSampleRateTcapture​=SampleRateMemoryDepth​

若设备有 100 M samples 存储深度，以 500 MS/s 采集：

Tcapture=100M500M=0.2sTcapture​=500M100M​=0.2s

原始数据量近似为：

DataSize=SampleRate×ChannelCount×TDataSize=SampleRate×ChannelCount×T

16 通道、100 MS/s、每通道按 1 bit 紧凑保存 10 s：

100M×16×10/8=2GB100M×16×10/8=2GB

实际文件还包含时间戳、索引和元数据，容量通常更大。

### 5.5 跳变压缩

对于长时间保持不变的信号，逐点存储非常浪费。跳变压缩只保存：

```
时间戳 t0：状态 0x0001
时间戳 t1：状态 0x0003
时间戳 t2：状态 0x0002
```

近似压缩收益取决于：

CompressionRatio≈SampleRateTransitionRateCompressionRatio≈TransitionRateSampleRate​

若以 100 MS/s 观察平均每秒变化 1000 次的状态 GPIO，理论数量级压缩比可达：

100×1061000=1000001000100×106​=100000

但对持续高速翻转的并行总线，跳变率接近采样率，压缩收益趋近于 1，甚至因时间戳开销而变差。

### 5.6 状态采集

状态采集由目标时钟驱动，典型连接如下：

```
目标系统 CLK  ─────────> 分析仪采样时钟输入
目标系统 DATA[15:0] ───> 分析仪数据输入
目标系统 VALID ────────> 分析仪采样资格信号
```

在每个目标时钟有效边沿，分析仪保存总线状态：

State[n]=DATA(tCLK,n)State[n]=DATA(tCLK,n​)

其优点是只记录系统认为有效的状态，适合：

- FPGA 内部或外部并行接口。
- 地址总线和数据总线。
- 同步 FIFO。
- 摄像头并行接口。
- 存储器控制总线。

局限是时钟边沿之间出现又消失的毛刺可能完全不可见，因此状态分析不能替代定时分析和示波器。

### 5.7 亚稳态与采样不确定性

被测边沿落在逻辑分析仪采样触发器的建立保持窗口内时，内部触发器可能进入亚稳态。设备通常通过高速前端、同步链或编码逻辑降低影响，但无法从物理上彻底消除。

表现包括：

- 同一周期信号重复采集时，边沿偶尔落在相邻采样点。
- 多个同时翻转的位看起来不是同时变化。
- 总线短暂显示不存在的中间码。
- 协议解码器偶发报告非法状态。

这不一定表示目标系统有错误，可能只是异步观测产生的采样不确定性。

对二进制计数器：

```
0111 -> 1000
```

四个位不会在物理上绝对同时变化。异步分析仪可能捕获：

```
0111 -> 0100 -> 1100 -> 1000
```

若需要跨时钟域传递计数值，应使用 Gray Code，而不是依赖普通二进制位同时翻转。

### 5.8 通道偏斜

不同探头线长度、输入缓冲和采样通路产生通道间偏斜：

tmeasured,i=tactual,i+tprobe,i+tchannel,itmeasured,i​=tactual,i​+tprobe,i​+tchannel,i​

两个通道的相对误差：

Δterror=(tprobe,1−tprobe,2)+(tchannel,1−tchannel,2)Δterror​=(tprobe,1​−tprobe,2​)+(tchannel,1​−tchannel,2​)

在低速 UART 上，1 ns 偏斜可忽略；在 100 MHz 并行接口上，1 ns 已占 10% 周期。

工程措施：

- 同组信号使用等长探头线。
- 使用厂家规定的高带宽数字探头。
- 通过同一边沿分配到多个通道进行偏斜校准。
- 高速建立保持分析优先使用示波器或专用时序分析设备。

### 5.9 输入负载与接地

逻辑分析仪输入通常可近似为：

```
被测节点 ── Rin || Cin ── GND
```

即使 `Rin = 1 MΩ`，在高频下仍由输入电容主导：

∣XC∣=12πfC∣XC​∣=2πfC1​

假设 `Cin = 10 pF`：

|频率|容抗|
|---|---|
|1 MHz|15.9 kΩ|
|10 MHz|1.59 kΩ|
|100 MHz|159 Ω|
|500 MHz|31.8 Ω|

多通道同时连接会加重局部地回流、电容负载和串扰。连接时应：

- 每组高速信号配置邻近地线。
- 避免所有通道仅共用一根很长的地线。
- 不将飞线跨过开关电源电感或高 `dv/dt` 节点。
- 未使用通道不要悬挂在敏感信号上。
- 先关闭目标板电源，再连接高密度探头。

### 5.10 协议解码不是原始事实

协议解码器根据配置参数解释采样数据：

```
原始边沿
  + 通道映射
  + 阈值
  + 波特率/时钟极性/相位
  + 位序
  + 片选极性
  = 解码事务
```

任一参数错误都会生成“合理但错误”的结果。例如 SPI 配置错误：

- CPOL 错误导致空闲电平解释错误。
- CPHA 错误导致在变化边沿采样。
- MSB/LSB 位序错误导致字节反转。
- 字长错误导致帧边界漂移。
- CS 极性错误导致事务无法分帧。

协议解码失败时，应回到原始波形逐层检查，而不是立即判定固件错误。

### 5.11 软件事件硬件化

为逻辑分析预留诊断 GPIO，将软件事件映射为外部波形。

```
#include <stdint.h>
#include "stm32h7xx.h"

#define TRACE_PORT              GPIOB
#define TRACE_ISR_PIN           (1U << 0)
#define TRACE_TASK_PIN          (1U << 1)
#define TRACE_DMA_PIN           (1U << 2)
#define TRACE_FAULT_PIN         (1U << 3)

static inline void trace_set(uint32_t pin)
{
    TRACE_PORT->BSRR = pin;
}

static inline void trace_clear(uint32_t pin)
{
    TRACE_PORT->BSRR = pin << 16U;
}

void DMA1_Stream0_IRQHandler(void)
{
    trace_set(TRACE_DMA_PIN);

    uint32_t status = DMA1->LISR;

    if ((status & DMA_LISR_TEIF0) != 0U) {
        DMA1->LIFCR = DMA_LIFCR_CTEIF0;
        trace_set(TRACE_FAULT_PIN); /* 锁存故障，便于触发 */
    }

    if ((status & DMA_LISR_TCIF0) != 0U) {
        DMA1->LIFCR = DMA_LIFCR_CTCIF0;
        adc_dma_complete_from_isr();
    }

    trace_clear(TRACE_DMA_PIN);
}
```

设计要求：

- 使用 `BSRR` 原子置位/清零，避免 `ODR` 读改写竞争。
- 故障标记宜锁存，而非生成极窄脉冲。
- 对准确外部可见边界，可选择性加入 `__DSB()`，但必须量化侵入开销。
- 对亚微秒执行路径，优先结合 DWT、ETM 或硬件定时器输出。
- 禁止在硬实时路径中通过 `printf` 代替追踪信号。

### 5.12 多位状态编码

GPIO 数量有限时，可输出状态码：

```
#define TRACE_STATE_MASK  (0x0FU << 4U)
#define TRACE_STATE_SHIFT 4U

typedef enum {
    TRACE_STATE_IDLE       = 0x0U,
    TRACE_STATE_ACQUIRE    = 0x1U,
    TRACE_STATE_FILTER     = 0x2U,
    TRACE_STATE_CONTROL    = 0x3U,
    TRACE_STATE_TRANSMIT   = 0x4U,
    TRACE_STATE_FAULT      = 0xFU
} trace_state_t;

static inline void trace_state_write(trace_state_t state)
{
    uint32_t value = ((uint32_t)state & 0x0FU) << TRACE_STATE_SHIFT;
    uint32_t clear = TRACE_STATE_MASK << 16U;

    /*
     * BSRR 同次写入完成位清除和置位，避免 ODR 读改写竞争。
     * 仍需考虑不同 GPIO 引脚物理传播延迟。
     */
    GPIOB->BSRR = clear | value;
}
```

必须保证所有状态位位于同一 GPIO 端口，否则跨端口写入不能原子完成，分析仪可能看到短暂中间状态。

更稳健的方案是增加一个 `TRACE_VALID`：

```
static inline void trace_state_commit(trace_state_t state)
{
    GPIOB->BSRR = TRACE_VALID_PIN << 16U;
    GPIOB->BSRR = (TRACE_STATE_MASK << 16U)
                | (((uint32_t)state & 0x0FU) << TRACE_STATE_SHIFT);
    GPIOB->BSRR = TRACE_VALID_PIN;
}
```

逻辑分析仪仅在 `TRACE_VALID` 上升沿读取状态总线。

## 8. 工程最佳实践

### 8.1 设计原则

1. **先明确问题属于数字语义还是模拟电气，再选择仪器。**
2. 逻辑分析仪的“1”或“0”不代表电压裕量合格。
3. 采样率应根据最小事件宽度选择，而不是仅根据总线基频选择。
4. 关键测量必须记录实际采样率、输入阈值、探头和通道配置。
5. 优先使用故障锁存和预触发，避免只看到故障发生后的结果。
6. 协议解码结论必须能回溯到原始边沿。
7. 软件追踪点应低侵入、原子化、语义稳定。
8. 时序边界结论必须考虑采样量化误差和通道偏斜。
9. 电气异常必须通过示波器复核。
10. 自动化测试必须保存原始采集文件，而不能只保存截图。

### 8.2 选型决策矩阵

评分范围：1 为较弱，5 为较强。

|方案|多通道|时间精度|长时间采集|电气分析|协议深度|成本效率|
|---|---|---|---|---|---|---|
|低成本 USB 逻辑分析仪|3|2|4|1|3|5|
|高速 USB 逻辑分析仪|4|4|4|1|4|4|
|台式逻辑分析仪|5|5|5|1|4|1|
|MSO|3|4|2|5|3|2|
|FPGA 内嵌 ILA|5|4|2|1|2|4|
|专用协议分析仪|2|4|5|2|5|1|
|ETM/SWO|2|5|3|1|5，限软件执行|3|

### 8.3 PCB 可测性规范

- 关键总线至少预留 `CLK`、`DATA`、`CS/VALID` 和邻近地测试点。
- 测试点支路应尽可能短，高速网络避免永久长 stub。
- 高密度接口使用带交错地的调试连接器，例如 `GND-SIG-GND-SIG`。
- 多电压域测试点应明确丝印标注电平，不允许仅依赖原理图猜测。
- 复位、电源良好、看门狗输出和故障信号应可访问。
- 预留 4~8 位追踪端口时，应尽可能安排在同一 GPIO 端口。
- 追踪引脚不得影响 Boot Strap、安全输出或功率器件默认状态。
- 量产板无法保留测试点时，可通过零欧姆电阻或专用测试焊盘隔离 stub。
- FPGA 调试设计应预留 ILA 资源预算和调试时钟。
- 对高可靠设备，保留只读诊断接口，不应为调试绕过安全控制。

### 8.4 工业级固件追踪规范

```
#include <stdbool.h>
#include <stdint.h>
#include "stm32h7xx.h"

typedef enum {
    TRACE_EVT_ADC_IRQ = 0U,
    TRACE_EVT_CONTROL_TASK,
    TRACE_EVT_COMMS_TASK,
    TRACE_EVT_DMA_COMPLETE,
    TRACE_EVT_FAULT,
    TRACE_EVT_COUNT
} trace_event_t;

static const uint16_t g_trace_pins[TRACE_EVT_COUNT] = {
    [TRACE_EVT_ADC_IRQ]       = 1U << 0,
    [TRACE_EVT_CONTROL_TASK]  = 1U << 1,
    [TRACE_EVT_COMMS_TASK]    = 1U << 2,
    [TRACE_EVT_DMA_COMPLETE]  = 1U << 3,
    [TRACE_EVT_FAULT]         = 1U << 4
};

static inline bool trace_event_is_valid(trace_event_t event)
{
    return (uint32_t)event < (uint32_t)TRACE_EVT_COUNT;
}

static inline void trace_event_begin(trace_event_t event)
{
#if defined(ENABLE_HW_TRACE)
    if (trace_event_is_valid(event)) {
        GPIOB->BSRR = g_trace_pins[event];
    }
#else
    (void)event;
#endif
}

static inline void trace_event_end(trace_event_t event)
{
#if defined(ENABLE_HW_TRACE)
    if (trace_event_is_valid(event)) {
        GPIOB->BSRR = (uint32_t)g_trace_pins[event] << 16U;
    }
#else
    (void)event;
#endif
}
```

编码规范：

- 追踪宏关闭后不得产生参数未使用告警。
- 追踪接口不得动态分配内存。
- 禁止从追踪代码调用阻塞 API。
- 一个信号只能表达一种稳定语义。
- 高电平起止边界必须在接口文档中定义。
- 故障信号应保持到主机读取或显式清除。
- 追踪版本、引脚映射和固件提交号必须关联保存。

## 9. 常见错误与避坑指南

### 9.1 错误一：采样率只设置为总线频率的两倍

#### 错误配置

```
SPI 时钟：20 MHz
逻辑分析仪采样率：40 MS/s
```

#### 根因分析

每个 SPI 周期仅有两个采样点。采样相位稍有变化，就可能丢失时钟边沿、错误估计占空比或在错误时刻读取数据。

#### 正确实现

```
仅协议解码：建议至少 100~200 MS/s
时序分析：根据最小边沿间隔进一步提高采样率
电气质量：使用示波器复核
```

#### 风险影响

- SPI 字节随机解码错误。
- 错判 CPHA 或位序。
- 无法识别异常窄时钟脉冲。
- 建立保持时间结论无效。

### 9.2 错误二：将解码错误直接归因于固件

#### 错误判断

```
协议解码器显示 0xA5 为 0x4B，因此 MCU 发送错误。
```

#### 根因分析

可能的真实原因包括：

- CPOL/CPHA 配置错误。
- 位序设置错误。
- 采样率不足。
- 数字阈值不匹配。
- 信号振铃多次跨越阈值。
- 探头地线导致干扰。
- 解码器字长配置错误。

#### 正确实现

1. 检查原始 CLK、DATA 和 CS 边沿。
2. 根据器件数据手册确认采样边沿。
3. 提升采样率并缩短探头连接。
4. 用示波器检查边沿和阈值。
5. 再与发送缓冲区和寄存器配置核对。

#### 风险影响

- 修改正确的驱动代码。
- 掩盖真实信号完整性问题。
- 引入新的协议兼容性缺陷。

### 9.3 错误三：使用 GPIO ODR 读改写生成追踪状态

#### 错误代码

```
void trace_toggle(uint32_t pin)
{
    GPIOB->ODR ^= pin;
}
```

#### 根因分析

该操作不是原子的。任务和 ISR 同时修改同一端口时会丢失更新；编译器生成的读改写过程也增加了不确定延迟。

#### 正确实现

```
static inline void trace_high(uint32_t pin)
{
    GPIOB->BSRR = pin;
}

static inline void trace_low(uint32_t pin)
{
    GPIOB->BSRR = pin << 16U;
}
```

#### 风险影响

- 追踪脉冲缺失或极性错误。
- 同端口业务 GPIO 被意外覆盖。
- 根据错误波形误判任务执行顺序。

### 9.4 错误四：忽略输入阈值和电压兼容性

#### 错误操作

```
将固定 TTL 阈值的分析仪直接用于 1.2 V CMOS 总线。
```

#### 根因分析

分析仪阈值可能高于被测总线高电平，导致全部或部分高电平被判为低电平。另一些低成本设备可能不具备 5 V 容限，直接连接会损坏输入。

#### 正确实现

- 查阅分析仪输入绝对最大额定值。
- 设置适合目标电压域的阈值。
- 必要时使用专用低压数字探头或电平转换缓冲。
- 用示波器验证目标节点实际电平。

#### 风险影响

- 错误解码。
- 输入保护二极管导通并加载总线。
- 损坏逻辑分析仪或目标板。

### 9.5 错误五：用短脉冲标记低概率故障

#### 错误代码

```
if (crc_error) {
    GPIOB->BSRR = TRACE_FAULT_PIN;
    GPIOB->BSRR = TRACE_FAULT_PIN << 16U;
}
```

#### 根因分析

脉冲可能短于分析仪采样周期，且主机流式采集可能因缓冲间隙漏掉事件。

#### 正确实现

```
static volatile uint32_t g_fault_flags;

void fault_latch(uint32_t fault)
{
    g_fault_flags |= fault;
    GPIOB->BSRR = TRACE_FAULT_PIN;
}

void fault_clear_after_capture(void)
{
    g_fault_flags = 0U;
    GPIOB->BSRR = TRACE_FAULT_PIN << 16U;
}
```

#### 风险影响

- 故障实际发生但无法触发。
- 团队错误认为问题不可复现。
- 缺失故障发生前的上下文。

### 9.6 错误六：多位状态码跨 GPIO 端口写入

#### 错误代码

```
GPIOA->BSRR = state_low_bits;
GPIOC->BSRR = state_high_bits;
```

#### 根因分析

两个总线写操作不可能同时到达不同 GPIO 外设。分析仪可能看到中间状态，尤其在总线争用或中断抢占时。

#### 正确实现

优先把状态位放在同一 GPIO 端口。若硬件无法调整，则增加 VALID 信号：

```
GPIOB->BSRR = TRACE_VALID_PIN << 16U;

GPIOA->BSRR = GPIOA_STATE_CLEAR | gpioa_state_value;
GPIOC->BSRR = GPIOC_STATE_CLEAR | gpioc_state_value;

__DSB();
GPIOB->BSRR = TRACE_VALID_PIN;
```

分析软件仅在 VALID 上升沿采样状态。

#### 风险影响

- 状态机出现不存在的非法状态。
- 错误推断任务切换或故障路径。
- 自动分析脚本产生假告警。

### 9.7 错误七：使用逻辑分析仪判定电气时序合规

#### 错误做法

```
逻辑分析仪显示数据在时钟前 6 ns 改变，因此满足 5 ns 建立时间。
```

#### 根因分析

该结论忽略：

- 采样时间量化。
- 通道间偏斜。
- 不同输入阈值。
- 慢边沿导致的阈值交叉时间差。
- 探头负载。

#### 正确实现

- 逻辑分析仪用于筛查和统计。
- 示波器按接收芯片规定的阈值测量建立保持时间。
- 对通道偏斜进行校正。
- 评估温度、电压和工艺角落。

#### 风险影响

- 将边界设计错误判定为合格。
- 产品在高温、低压或批量差异下失效。

## 10. 多机制组合使用方案

### 10.1 技术协同架构

```
外部传感器/总线
       │
       ├────────────> 示波器：电压、边沿、电源和模拟异常
       │
       v
MCU 外设 -> DMA -> ISR -> RTOS 任务 -> 驱动输出
   │        │      │         │             │
   │        │      │         │             └─ 逻辑通道：输出/片选
   │        │      │         └─ TRACE_TASK
   │        │      └─ TRACE_ISR
   │        └─ TRACE_DMA
   ├─ TRACE_STATE[3:0] + VALID
   ├─ TRACE_FAULT 锁存
   ├─ DWT：周期与计数
   └─ ETM/SWO：指令和软件事件

逻辑分析仪：长时间、多通道、协议和事件顺序
示波器：模拟电气根因和精确边沿
DWT：片上周期量化
ETM/SWO：代码路径
专用协议分析仪：复杂标准协议语义
```

### 10.2 组合设计模式

#### 模式一：故障锁存 + 大比例预触发

```
采集窗口：
[故障前 90% 历史] [触发点] [故障后 10%]

触发源：
TRACE_FAULT 上升沿

适用：
看门狗复位、CRC 错误、DMA 溢出、协议超时
```

#### 模式二：事务边界 + 软件状态

```
CH0：CS
CH1：CLK
CH2：MOSI
CH3：MISO
CH4~CH7：TRACE_STATE
CH8：TRACE_VALID
CH9：TRACE_FAULT
```

可同时回答“线上发生了什么”和“软件当时处于哪个状态”。

#### 模式三：示波器和逻辑分析仪共用触发

```
MCU TRACE_FAULT
    ├─ 逻辑分析仪外部触发
    └─ 示波器外部触发
```

两台仪器必须考虑各自触发延迟。若需要精确跨仪器时间关联，应额外输出周期同步脉冲，并在两个采集文件中校正时间轴。

### 10.3 完整代码框架

```
#include <stdbool.h>
#include <stdint.h>
#include "stm32h7xx.h"

#define TRACE_ISR_PIN       (1U << 0)
#define TRACE_TASK_PIN      (1U << 1)
#define TRACE_DMA_PIN       (1U << 2)
#define TRACE_FAULT_PIN     (1U << 3)
#define TRACE_VALID_PIN     (1U << 4)
#define TRACE_STATE_SHIFT   5U
#define TRACE_STATE_MASK    (0x07U << TRACE_STATE_SHIFT)

typedef enum {
    SYS_STATE_IDLE = 0U,
    SYS_STATE_ACQUIRE,
    SYS_STATE_PROCESS,
    SYS_STATE_TRANSMIT,
    SYS_STATE_RECOVERY,
    SYS_STATE_FAULT
} system_state_t;

typedef enum {
    FAULT_NONE          = 0U,
    FAULT_ADC_OVERRUN   = 1U << 0,
    FAULT_DMA_ERROR     = 1U << 1,
    FAULT_SPI_TIMEOUT   = 1U << 2,
    FAULT_CONTROL_LATE  = 1U << 3
} fault_flag_t;

typedef struct {
    volatile uint32_t fault_flags;
    volatile uint32_t fault_cycles;
    volatile uint32_t dma_irq_count;
    volatile uint32_t max_dma_to_task_cycles;
    volatile uint16_t latest_sample;
    volatile bool sample_ready;
} trace_diagnostics_t;

static trace_diagnostics_t g_trace_diag;
static volatile uint32_t g_dma_complete_cycles;

static inline uint32_t cycles_now(void)
{
    return DWT->CYCCNT;
}

static inline void trace_set(uint32_t pin)
{
    GPIOB->BSRR = pin;
}

static inline void trace_clear(uint32_t pin)
{
    GPIOB->BSRR = pin << 16U;
}

static void trace_state_commit(system_state_t state)
{
    uint32_t encoded;

    if ((uint32_t)state > (uint32_t)SYS_STATE_FAULT) {
        state = SYS_STATE_FAULT;
    }

    encoded = ((uint32_t)state << TRACE_STATE_SHIFT) & TRACE_STATE_MASK;

    trace_clear(TRACE_VALID_PIN);
    GPIOB->BSRR = (TRACE_STATE_MASK << 16U) | encoded;
    __DSB();
    trace_set(TRACE_VALID_PIN);
}

static void trace_fault_latch(fault_flag_t fault)
{
    uint32_t primask = __get_PRIMASK();

    __disable_irq();
    g_trace_diag.fault_flags |= (uint32_t)fault;

    if (g_trace_diag.fault_cycles == 0U) {
        g_trace_diag.fault_cycles = cycles_now();
    }

    trace_set(TRACE_FAULT_PIN);
    __DSB();

    if (primask == 0U) {
        __enable_irq();
    }
}

bool trace_diagnostics_init(void)
{
    RCC->AHB4ENR |= RCC_AHB4ENR_GPIOBEN;
    (void)RCC->AHB4ENR;

    GPIOB->MODER &= ~0x0000FFFFU;
    GPIOB->MODER |=  0x00005555U;
    GPIOB->BSRR = 0x00FFU << 16U;

    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->CYCCNT = 0U;
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;

    trace_state_commit(SYS_STATE_IDLE);

    return (DWT->CTRL & DWT_CTRL_CYCCNTENA_Msk) != 0U;
}

void DMA1_Stream0_IRQHandler(void)
{
    uint32_t status;

    trace_set(TRACE_DMA_PIN);
    status = DMA1->LISR;

    if ((status & DMA_LISR_TEIF0) != 0U) {
        DMA1->LIFCR = DMA_LIFCR_CTEIF0;
        trace_fault_latch(FAULT_DMA_ERROR);
    }

    if ((status & DMA_LISR_TCIF0) != 0U) {
        DMA1->LIFCR = DMA_LIFCR_CTCIF0;

        g_trace_diag.latest_sample = adc_dma_buffer_get_latest();
        g_trace_diag.sample_ready = true;
        g_trace_diag.dma_irq_count++;
        g_dma_complete_cycles = cycles_now();
    }

    trace_clear(TRACE_DMA_PIN);
}

void control_task_step(void)
{
    uint16_t sample;
    uint32_t latency;
    uint32_t primask;

    if (!g_trace_diag.sample_ready) {
        return;
    }

    primask = __get_PRIMASK();
    __disable_irq();
    sample = g_trace_diag.latest_sample;
    g_trace_diag.sample_ready = false;
    if (primask == 0U) {
        __enable_irq();
    }

    latency = cycles_now() - g_dma_complete_cycles;
    if (latency > g_trace_diag.max_dma_to_task_cycles) {
        g_trace_diag.max_dma_to_task_cycles = latency;
    }

    trace_set(TRACE_TASK_PIN);
    trace_state_commit(SYS_STATE_PROCESS);

    if (!control_update(sample)) {
        trace_fault_latch(FAULT_CONTROL_LATE);
        trace_state_commit(SYS_STATE_FAULT);
    } else {
        trace_state_commit(SYS_STATE_IDLE);
    }

    trace_clear(TRACE_TASK_PIN);
}

void trace_fault_clear_after_capture(void)
{
    uint32_t primask = __get_PRIMASK();

    __disable_irq();
    g_trace_diag.fault_flags = FAULT_NONE;
    g_trace_diag.fault_cycles = 0U;
    trace_clear(TRACE_FAULT_PIN);

    if (primask == 0U) {
        __enable_irq();
    }
}
```

### 10.4 框架设计要点

- GPIO 追踪负责外部事件关联，DWT 负责内部周期量化。
- 故障引脚保持有效，直到采集完成后显式清除。
- 状态总线通过 VALID 信号提交，避免中间状态被误读。
- ISR 不执行格式化日志、阻塞调用或动态分配。
- 周期计数采用无符号减法，可正确处理一次计数器回绕。
- 正式项目应将寄存器映射、端口宽度和中断清除方式适配到具体 MCU。
- 对 SMP、多核或复杂 Cache 系统，需要增加核标识、内存屏障和跨核事件设计。

## 11. 工业级实际案例分析

### 11.1 案例一：SPI Flash 偶发 CRC 错误

#### 需求

工业控制器连续运行数小时后偶发配置区 CRC 错误。驱动重试通常成功，传统日志只能记录“CRC mismatch”，无法确定是发送、接收、片选还是调度问题。

#### 架构设计

```
CH0：SPI_CS
CH1：SPI_CLK
CH2：SPI_MOSI
CH3：SPI_MISO
CH4：DMA_COMPLETE
CH5：FLASH_TASK
CH6：CRC_FAULT，锁存
CH7~CH9：软件状态码

触发：
CRC_FAULT 上升沿

预触发：
95%

采集：
250 MS/s，跳变压缩，SPI 协议解码
```

#### 核心代码

```
typedef struct {
    uint32_t address;
    uint32_t expected_crc;
    uint32_t actual_crc;
    uint32_t spi_status;
    uint32_t timestamp;
} flash_fault_snapshot_t;

static flash_fault_snapshot_t g_flash_fault;

static void flash_latch_crc_fault(uint32_t address,
                                  uint32_t expected,
                                  uint32_t actual)
{
    uint32_t primask = __get_PRIMASK();

    __disable_irq();

    if ((g_trace_diag.fault_flags & FAULT_SPI_TIMEOUT) == 0U) {
        g_flash_fault.address = address;
        g_flash_fault.expected_crc = expected;
        g_flash_fault.actual_crc = actual;
        g_flash_fault.spi_status = SPI1->SR;
        g_flash_fault.timestamp = DWT->CYCCNT;
    }

    g_trace_diag.fault_flags |= FAULT_SPI_TIMEOUT;
    GPIOB->BSRR = TRACE_FAULT_PIN;
    __DSB();

    if (primask == 0U) {
        __enable_irq();
    }
}
```

#### 捕获结果

- 错误事务中 `CS` 在第 173 个字节后短暂释放约 1.1 µs。
- `CLK` 和数据本身无缺失。
- 片选由任务级软件控制，而 DMA 完成回调释放了一个共享 SPI 锁。
- 高优先级任务在事务中间抢占并启动另一设备事务。
- CRC 错误是**总线所有权竞争**，不是 Flash 器件可靠性问题。

#### 修复方案

- 将 CS 生命周期与总线互斥锁绑定到同一事务对象。
- DMA 完成只通知事务状态机，不直接释放总线所有权。
- 事务结束必须满足 `DMA complete + SPI not busy + CS deasserted`。
- 增加运行期所有权断言。

```
typedef struct {
    volatile bool owned;
    volatile bool dma_done;
    GPIO_TypeDef *cs_port;
    uint32_t cs_pin;
} spi_transaction_t;

bool spi_transaction_finish(spi_transaction_t *transaction)
{
    if ((transaction == NULL) || !transaction->owned) {
        return false;
    }

    if (!transaction->dma_done ||
        ((SPI1->SR & SPI_SR_BSY) != 0U)) {
        return false;
    }

    transaction->cs_port->BSRR = transaction->cs_pin;
    transaction->owned = false;
    spi_bus_unlock();
    return true;
}
```

#### 设计要点

- 逻辑分析仪揭示的是跨任务事务边界，而不是单个 API 的局部行为。
- 协议解码需与任务追踪信号共同分析。
- 修复后应运行高负载回归并统计至少数百万个事务。

### 11.2 案例二：I²C 总线低温锁死

#### 需求

室外传感节点在低温启动时偶发卡死。SDA 持续为低，驱动超时后重复初始化仍无法恢复。

#### 架构设计

```
CH0：SCL
CH1：SDA
CH2：传感器 RESET
CH3：传感器电源使能
CH4：MCU I²C ISR
CH5：I²C_RECOVERY
CH6：FAULT_LATCH
CH7：系统状态 VALID

示波器：
同步测量传感器 VDD 和 SDA 模拟电平
```

#### 核心恢复代码

```
#define I2C_RECOVERY_CLOCKS 9U

static bool i2c_wait_line_high(GPIO_TypeDef *port,
                               uint32_t pin,
                               uint32_t timeout_cycles)
{
    uint32_t start = DWT->CYCCNT;

    while ((port->IDR & pin) == 0U) {
        if ((DWT->CYCCNT - start) >= timeout_cycles) {
            return false;
        }
    }

    return true;
}

bool i2c_bus_recover(void)
{
    trace_set(TRACE_TASK_PIN);

    i2c_peripheral_disable();
    i2c_pins_configure_open_drain_gpio();

    gpio_release_sda();
    gpio_release_scl();

    if (!i2c_wait_line_high(SCL_PORT, SCL_PIN, RECOVERY_TIMEOUT_CYCLES)) {
        trace_fault_latch(FAULT_SPI_TIMEOUT);
        trace_clear(TRACE_TASK_PIN);
        return false;
    }

    for (uint32_t i = 0U; i < I2C_RECOVERY_CLOCKS; ++i) {
        if ((SDA_PORT->IDR & SDA_PIN) != 0U) {
            break;
        }

        gpio_drive_scl_low();
        delay_cycles(I2C_RECOVERY_LOW_CYCLES);
        gpio_release_scl();

        if (!i2c_wait_line_high(SCL_PORT,
                                SCL_PIN,
                                RECOVERY_TIMEOUT_CYCLES)) {
            trace_fault_latch(FAULT_SPI_TIMEOUT);
            trace_clear(TRACE_TASK_PIN);
            return false;
        }

        delay_cycles(I2C_RECOVERY_HIGH_CYCLES);
    }

    /* 生成 STOP：SDA 低期间释放 SCL，随后释放 SDA。 */
    gpio_drive_sda_low();
    delay_cycles(I2C_RECOVERY_LOW_CYCLES);
    gpio_release_scl();

    if (!i2c_wait_line_high(SCL_PORT, SCL_PIN, RECOVERY_TIMEOUT_CYCLES)) {
        trace_fault_latch(FAULT_SPI_TIMEOUT);
        trace_clear(TRACE_TASK_PIN);
        return false;
    }

    delay_cycles(I2C_RECOVERY_HIGH_CYCLES);
    gpio_release_sda();

    bool recovered = ((SDA_PORT->IDR & SDA_PIN) != 0U);
    i2c_pins_restore_alternate_function();
    i2c_peripheral_reinitialize();

    trace_clear(TRACE_TASK_PIN);
    return recovered;
}
```

#### 捕获结果

- 传感器上电后 VDD 上升缓慢。
- MCU 在传感器复位释放后 210 µs 即发送首个 START。
- 数据手册要求电源稳定后等待至少 1 ms。
- 传感器在地址应答后复位，SDA 保持低电平。
- 9 个恢复时钟可释放总线，但根因是上电时序违规。

#### 修复方案

- 使用传感器电源良好条件或保守延迟控制初始化。
- 将 RESET 保持时间与 VDD 有效状态绑定。
- 启动后先检查 SCL/SDA 是否均为高。
- 保留总线恢复机制，但不将其作为上电时序错误的替代方案。

#### 设计要点

- 逻辑分析仪确定协议和控制时序。
- 示波器确定 VDD 何时真正达到有效电压。
- 单独使用任何一种仪器都不足以完整闭环。

### 11.3 案例三：电机控制任务周期性超期

#### 需求

20 kHz 电流环要求每 50 µs 完成一次控制计算，偶发超期导致 PWM 更新缺失。平均执行时间只有 12 µs，软件统计未发现明显异常。

#### 架构设计

```
CH0：PWM 更新事件
CH1：ADC DMA 完成
CH2：控制 ISR
CH3：控制任务
CH4：通信 ISR
CH5：日志任务
CH6：DEADLINE_FAULT
CH7~CH9：系统状态码

采集：
500 MS/s，分段采集 10,000 段

触发：
DEADLINE_FAULT 上升沿
```

#### 核心监测代码

```
#define CPU_CLOCK_HZ          400000000UL
#define CONTROL_DEADLINE_US   50UL
#define CONTROL_DEADLINE_CYCLES \
    ((CPU_CLOCK_HZ / 1000000UL) * CONTROL_DEADLINE_US)

static volatile uint32_t g_control_release_cycles;

void adc_dma_complete_from_isr(void)
{
    g_control_release_cycles = DWT->CYCCNT;
    trace_set(TRACE_DMA_PIN);
    control_task_notify_from_isr();
    trace_clear(TRACE_DMA_PIN);
}

void control_task_run_once(void)
{
    uint32_t start = DWT->CYCCNT;

    trace_set(TRACE_TASK_PIN);
    trace_state_commit(SYS_STATE_PROCESS);

    control_execute();
    pwm_commit();

    uint32_t elapsed = DWT->CYCCNT - g_control_release_cycles;

    if (elapsed > CONTROL_DEADLINE_CYCLES) {
        trace_fault_latch(FAULT_CONTROL_LATE);
        trace_state_commit(SYS_STATE_FAULT);
    } else {
        trace_state_commit(SYS_STATE_IDLE);
    }

    trace_clear(TRACE_TASK_PIN);

    /*
     * start 可用于区分纯执行时间和从 DMA 发布到完成的端到端时间。
     */
    control_stats_update(DWT->CYCCNT - start, elapsed);
}
```

#### 捕获结果

- 超期前通信 ISR 连续运行约 31 µs。
- 通信 ISR 内执行了 Cache 维护和大型环形缓冲区扫描。
- 控制任务自身执行时间仍为约 12 µs，但释放到完成延迟达到约 57 µs。
- 平均执行时间无法暴露高优先级中断造成的长尾阻塞。

#### 修复方案

- ISR 只确认硬件事件并提交描述符。
- 缓冲区扫描移至任务上下文。
- 限制单次接收批处理数量。
- 调整中断优先级，确保控制链路不被非关键通信长期阻塞。
- 使用 P99.99 和最大值，而不是平均值作为实时性验收指标。

#### 设计要点

- 实时系统必须测量**端到端响应时间**，不仅是函数执行时间。
- 逻辑分析仪适合揭示多个异步执行实体的相对顺序。
- DWT 提供更精确的周期数据，两者共同形成证据链。

## 12. 高频问题深度答疑

### 12.1 逻辑分析仪采样率应该是信号频率的多少倍？

没有统一倍数，取决于最小事件宽度和测量目标。

- 只做稳定协议解码：通常 4~10 倍总线时钟。
- 测量脉宽和相对时序：通常 10~20 倍。
- 捕获毛刺：采样周期必须显著短于毛刺宽度。
- 判定纳秒级建立保持裕量：通用逻辑分析仪通常不够，应使用示波器或专用设备。

必须同时检查多通道开启后的**实际每通道采样率**。

### 12.2 为什么逻辑分析仪能解码，但设备仍通信失败？

分析仪与接收芯片的阈值、输入迟滞和采样位置不同。可能出现：

- 分析仪判决正确，目标芯片因慢边沿或噪声错误采样。
- 分析仪探头电容抑制振铃，使故障暂时消失。
- 协议数据正确，但电气时序不满足建立保持要求。
- 通信成功，但上层状态机超时。
- 总线事务正确，电源或复位在事务后异常。

解码成功只能证明分析仪按当前配置得到了合理数字序列，不代表整个电气和软件链路合格。

### 12.3 什么时候使用定时采集，什么时候使用状态采集？

使用定时采集：

- 需要测量事件间隔、脉宽和毛刺。
- 被测信号来自不同异步时钟域。
- 分析串行协议和中断时序。
- 需要看到目标时钟边沿之间的行为。

使用状态采集：

- 分析同步并行总线。
- 只关心被测系统时钟边沿上的有效数据。
- 需要提高存储效率。
- 目标提供可靠的采样时钟和资格信号。

复杂问题常同时使用两种模式进行交叉验证。

### 12.4 为什么同一边沿在多次采集中会移动一个采样点？

这是异步采样量化的正常结果。目标边沿与分析仪采样时钟没有固定相位，边沿可能落在相邻两个采样点之间。若边沿接近采样器建立保持窗口，还会出现额外不确定性。

应将结果表达为误差范围：

t=tmeasured±Tst=tmeasured​±Ts​

而不是把屏幕游标显示的所有小数位都当作有效精度。

### 12.5 逻辑分析仪能否替代示波器？

不能。两者关注层次不同：

```
逻辑分析仪：
状态、顺序、协议、长时间、多通道

示波器：
电压、噪声、边沿、过冲、振铃、电源、模拟时序
```

推荐先用逻辑分析仪定位“哪次事务、哪个状态、哪个时刻”异常，再用示波器聚焦观察对应节点的电气行为。

### 12.6 如何捕获一天只出现一次的故障？

核心不是盲目增加存储深度，而是降低需要保存的数据量：

1. 固件将故障条件锁存到 GPIO。
2. 使用跳变压缩或低速流式采集。
3. 设置 90%~99% 预触发，保留故障前因。
4. 将高速原始总线采集限定到故障附近。
5. 同步保存固件内部故障快照和时间戳。
6. 必要时使用两级触发：事务开始后等待特定异常。
7. 自动保存采集文件，避免人工值守。

### 12.7 GPIO 追踪会不会改变实时行为？

会。GPIO 写入会占用 CPU 指令、总线和外设桥资源，还可能改变 Cache、流水线和中断时序。`__DSB()` 可使边界更确定，但侵入更大。

工程上应：

- 单独测量空追踪开销。
- 使用直接寄存器写而非 HAL。
- 只保留关键事件。
- 使用同一端口批量编码状态。
- 通过 DWT 交叉验证。
- 对极低扰动需求使用 ETM 或硬件定时器输出。

## 13. 课程核心总结

### 13.1 核心要点

- **逻辑分析仪记录的是阈值判决后的数字状态，不是实际电压。**
- 采样率必须由最小脉宽和时间精度要求决定。
- 异步采样存在至少一个采样周期量级的边沿量化误差。
- 多通道时序分析必须考虑探头负载和通道偏斜。
- 协议解码器是解释层，原始边沿才是第一层证据。
- 低概率故障应使用故障锁存、大比例预触发、分段采集和跳变压缩。
- GPIO 追踪适合建立软硬件时间关联，但必须量化侵入开销。
- 电气问题必须通过示波器复核。
- 实时系统应关注最大值和长尾分布，不应只关注平均执行时间。
- 原始采集、配置、固件版本和环境条件共同构成可复现证据。

### 13.2 性能排序

#### 多通道长时间数字观测能力

```
台式深存储逻辑分析仪
> 高速流式 USB 逻辑分析仪
> 专用协议分析仪
> MSO 数字通道
> 示波器模拟通道
```

#### 电气根因分析能力

```
高带宽示波器 + 合适探头
> MSO 模拟通道
> 带模拟通道的混合采集设备
> 逻辑分析仪
```

#### 软件追踪侵入性，由低到高

```
ETM
< 定时器硬件输出
< DWT
< 直接 GPIO 寄存器写
< HAL GPIO
< 串口格式化日志
```

#### 偶发故障捕获效率

```
故障锁存 + 预触发 + 跳变压缩
> 协议条件触发 + 分段存储
> 长时间流式采集
> 普通边沿单次触发
> 人工观察
```

### 13.3 通用选型结论

- UART、SPI、I²C 和软件状态关联优先使用逻辑分析仪。
- 电源、复位模拟电平、边沿完整性和建立保持裕量使用示波器。
- 并行同步总线优先考虑状态采集。
- 高速标准总线的深层事务分析使用专用协议分析仪。
- FPGA 内部信号优先使用 ILA 或 Signal Tap。
- MCU 执行路径使用 ETM/SWO，外部事件关联使用 GPIO。
- 对关键故障，至少采用两种独立测量机制交叉验证。

## 16. 实践与进阶路径

### 16.1 梯度实战任务

#### 任务一：采样率与量化误差实验

- 生成 1 MHz、10 MHz 和 25 MHz 方波。
- 分别使用 24、100、250 和 500 MS/s 采集。
- 测量周期、高低脉宽和边沿位置分布。
- 计算理论量化误差并与实测离散结果比较。
- 确认何种采样率只够解码，何种采样率可用于时序分析。

#### 任务二：UART 长时间可靠性分析

- 配置 115200 baud、1 Mbaud 和 3 Mbaud。
- 连续传输带序号和 CRC 的测试帧。
- 注入波特率偏差、任务延迟和接收缓冲区溢出。
- 统计帧错误、丢帧、重帧和最大帧间隔。
- 用示波器复核高波特率下的实际位宽和电平。

#### 任务三：SPI 事务效率分析

- 同时采集 CLK、MOSI、MISO、CS、DMA 和任务 GPIO。
- 分别测试轮询、中断和 DMA 三种传输方式。
- 计算线速、有效吞吐率和片选间空闲时间。
- 分离硬件传输时间、驱动开销和 RTOS 调度延迟。
- 对不同块大小绘制吞吐率曲线。

#### 任务四：I²C 故障注入与恢复

- 人工让从设备在第 3、5、8 个数据位后保持 SDA 为低。
- 验证超时检测、9 时钟恢复和 STOP 生成。
- 使用跳变压缩连续运行至少 8 小时。
- 统计恢复成功率和恢复时间。
- 使用示波器测量上拉电阻变化对上升时间的影响。

#### 任务五：RTOS 实时性长尾分析

- 设计 20 kHz 或 1 kHz 周期控制任务。
- 输出任务释放、开始、结束、ISR 和故障信号。
- 注入网络中断、Flash 擦写、Cache miss 和临界区负载。
- 采集至少 100 万个周期。
- 输出最小值、平均值、P99、P99.9、P99.99 和最大值。
- 区分执行时间、阻塞时间、调度延迟和端到端延迟。

#### 任务六：多位状态追踪总线

- 使用 3~~4 个 GPIO 编码 8~~16 个系统状态。
- 增加 VALID 提交信号。
- 故意将状态拆到不同端口，观察中间码。
- 改为同端口 BSRR 或 VALID 方案并验证修复效果。
- 编写解析器把状态波形转换为状态迁移日志。

#### 任务七：逻辑分析仪与示波器联合触发

- 将故障锁存 GPIO同时连接两台仪器。
- 逻辑分析仪采集协议和软件状态。
- 示波器采集电源、复位和关键数据线模拟波形。
- 输出同步脉冲并校正两套时间轴。
- 建立同一故障的数字语义与模拟根因证据链。

#### 任务八：自动化硬件在环回归

- 使用设备 SDK、CLI 或 sigrok 控制采集。
- 自动配置采样率、阈值、通道和触发条件。
- 导出 VCD、CSV、SR 或设备原生文件。
- 自动检查事务顺序、最大延迟、超时和非法状态。
- 将测试结果关联硬件版本与固件提交。
- CI 失败时保留原始波形作为构建产物。
