## 5. 底层原理与功能特性深度解析

## 5.1 Flash 写入为什么慢

Flash 写入通常包含：

```
数据装载
    ↓
Page Program
    ↓
状态轮询
    ↓
ECC 校验
    ↓
映射表更新
```

擦除则通常为：

```
Block Erase
    ↓
整块电荷释放
    ↓
状态轮询
    ↓
坏块 / ECC 状态检查
```

NOR Flash 典型特征：

- 读取可以接近随机访问；
- 写入前通常必须擦除；
- 擦除粒度远大于写入粒度；
- 同一扇区频繁更新会导致寿命快速下降。

典型参数：

```
页编程时间：0.2~3 ms
4 KB 扇区擦除：20~100 ms
64 KB 块擦除：100~500 ms
```

因此，下面的策略非常危险：

```
/* 错误：每次更新一个字段都擦除整个扇区 */
void update_counter(uint32_t value)
{
    flash_erase_sector(CONFIG_ADDR);
    flash_program(CONFIG_ADDR, &value, sizeof(value));
}
```

更合理的做法是：

- RAM 中聚合修改；
- 定时批量提交；
- 使用追加日志；
- 使用双备份；
- 对频繁更新字段单独分配存储区域。

## 5.2 写放大

写放大定义为：

WA=实际写入介质的数据量应用层请求写入的数据量WA=应用层请求写入的数据量实际写入介质的数据量​

例如应用写入 1 KB，但文件系统因擦除、GC、元数据更新实际写入 8 KB：

WA=8KB1KB=8WA=1KB8KB​=8

Flash 寿命近似为：

Life=Nerase×CusableWdaily×WA×365Life=Wdaily​×WA×365Nerase​×Cusable​​

其中：

- NeraseNerase​：擦除寿命；
- CusableCusable​：可用容量；
- WdailyWdaily​：每天应用写入量；
- WAWA：写放大系数。

假设：

```
容量：1 GB
擦除寿命：3000 次
每天写入：2 GB
写放大：3
```

则理论寿命：

Life=3000×1GB2GB×3×365≈1.37年Life=2GB×3×3653000×1GB​≈1.37年

**写放大是工业设备寿命设计的核心指标，而不是附属指标。**

## 5.3 FAT 文件系统中的目录和 FAT 表开销

FAT 文件系统访问文件时通常需要：

1. 定位根目录或子目录；
2. 扫描目录项；
3. 查询 FAT 链；
4. 找到数据簇；
5. 读取或更新目录项；
6. 必要时更新 FAT 表。

对于大量小文件：

```
文件创建频率高
目录项数量大
FAT 链较长
文件删除频繁
```

可能出现：

- 目录扫描耗时随文件数线性增长；
- FAT 表随机访问增加；
- 簇碎片造成额外寻道和读操作；
- 断电时目录和 FAT 状态不一致。

对于 FATFS，建议：

- 使用固定目录层级；
- 控制单目录文件数量；
- 使用连续大文件；
- 使用 `f_lseek()` 预分配；
- 采用日志文件追加，而不是大量小文件；
- 关闭不必要的 `f_sync()`。

## 5.4 批量写和缓存

错误模式：

```
for (size_t i = 0; i < sample_count; ++i) {
    fwrite(&samples[i], sizeof(samples[i]), 1, fp);
    fflush(fp);
}
```

这会产生：

```
用户态调用 × N
文件系统路径 × N
块设备请求 × N
元数据更新 × N
同步等待 × N
```

更合理：

```
size_t bytes = sample_count * sizeof(samples[0]);

if (fwrite(samples, 1, bytes, fp) != bytes) {
    /* 错误处理 */
}
```

批量写的吞吐收益来自：

Ttotal=N×(Tsubmit+Tmedia)Ttotal​=N×(Tsubmit​+Tmedia​)

当单次写入块增大后：

Ttotal≈DB×Tsubmit+TmediaTtotal​≈BD​×Tsubmit​+Tmedia​

其中：

- DD：总数据量；
- BB：单次写入块大小。

通常建议：

- 小型 MCU：4 KB~32 KB；
- Linux eMMC：64 KB~1 MB；
- 高吞吐媒体：1 MB~4 MB；
- 具体值必须以目标硬件实测为准。

## 5.5 Linux 文件写入语义

### `write()`

数据可能仅进入页缓存，并未真正写入介质。

```
ssize_t n = write(fd, buf, len);
```

成功只说明数据已被内核接受，不代表掉电安全。

### `fsync()`

要求文件相关数据和必要元数据提交到稳定介质。

```
if (fsync(fd) < 0) {
    perror("fsync");
}
```

### `fdatasync()`

通常只保证数据及必要元数据，比 `fsync()` 开销更低。

### `O_SYNC`

每次写调用都接近同步写，可靠性高但吞吐和延迟通常较差。

### `O_DIRECT`

绕过页缓存，但有对齐限制：

- Buffer 地址对齐；
- 长度对齐；
- 文件偏移对齐。

示例：

```
int fd = open("/data/log.bin", O_WRONLY | O_CREAT | O_DIRECT, 0644);
if (fd < 0) {
    return -1;
}

void *buf = NULL;
if (posix_memalign(&buf, 4096, 4096) != 0) {
    close(fd);
    return -1;
}

memset(buf, 0xA5, 4096);

ssize_t ret = write(fd, buf, 4096);
if (ret != 4096) {
    /* 处理短写、EIO、ENOSPC 等异常 */
}

free(buf);
close(fd);
```

**注意：`O_DIRECT` 并不自动等价于掉电安全，仍可能需要 `fsync()`。**

## 5.6 工业级追加日志实现

下面是适用于 MCU/RTOS 的固定块日志框架。核心思想：

- 固定长度记录；
- 单调递增序号；
- CRC 校验；
- 环形覆盖；
- 启动时扫描恢复；
- 不依赖复杂目录操作。

```
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define LOG_MAGIC       0x4C4F4731u
#define LOG_RECORD_SIZE 64u

typedef struct {
    uint32_t magic;
    uint32_t sequence;
    uint32_t timestamp;
    uint16_t payload_len;
    uint16_t reserved;
    uint8_t  payload[48];
    uint32_t crc32;
} log_record_t;

_Static_assert(sizeof(log_record_t) == LOG_RECORD_SIZE,
               "log record size must be fixed");

static uint32_t crc32_calc(const void *data, size_t len);

bool log_record_build(log_record_t *rec,
                      uint32_t sequence,
                      uint32_t timestamp,
                      const void *payload,
                      uint16_t payload_len)
{
    if (rec == NULL || payload == NULL ||
        payload_len > sizeof(rec->payload)) {
        return false;
    }

    memset(rec, 0xFF, sizeof(*rec));
    rec->magic = LOG_MAGIC;
    rec->sequence = sequence;
    rec->timestamp = timestamp;
    rec->payload_len = payload_len;
    memcpy(rec->payload, payload, payload_len);

    rec->crc32 = crc32_calc(rec, offsetof(log_record_t, crc32));
    return true;
}

bool log_record_valid(const log_record_t *rec)
{
    if (rec == NULL || rec->magic != LOG_MAGIC) {
        return false;
    }

    if (rec->payload_len > sizeof(rec->payload)) {
        return false;
    }

    uint32_t crc = crc32_calc(rec, offsetof(log_record_t, crc32));
    return crc == rec->crc32;
}
```

### 关键设计点

- `magic` 用于判断记录类型；
- `sequence` 用于恢复最新记录；
- `payload_len` 用于检查边界；
- `CRC` 用于检测掉电或介质错误；
- 固定记录长度简化索引和回收；
- 记录写入顺序应避免出现“有效标志已写但数据未写完”。

更严格的提交顺序可以是：

```
1. 写入 Header + Payload
2. 计算并写入 CRC
3. 最后写入 Commit Marker
```

这样可避免部分写入被误判为完整记录。

## 5.7 双备份参数提交

参数更新通常采用：

```
区域 A：版本号 + 参数 + CRC
区域 B：版本号 + 参数 + CRC
```

启动时：

1. 验证 A；
2. 验证 B；
3. 选择版本号更大的有效副本；
4. 更新时写入较旧副本；
5. 写入完成后再更新有效标志。

```
typedef struct {
    uint32_t magic;
    uint32_t version;
    device_config_t config;
    uint32_t crc;
    uint32_t commit;
} config_slot_t;

bool config_slot_valid(const config_slot_t *slot)
{
    if (slot == NULL ||
        slot->magic != CONFIG_MAGIC ||
        slot->commit != CONFIG_COMMIT) {
        return false;
    }

    uint32_t crc = crc32_calc(slot, offsetof(config_slot_t, crc));
    return crc == slot->crc;
}
```

该方案的优点：

- 掉电不会同时破坏两个副本；
- 读取路径简单；
- 不需要完整文件系统；
- 适合 MCU 参数区。

## 6.3 性能模型

Efficiency=TmediaTapp+Tfs+Tdriver+Tbus+TmediaEfficiency=Tapp​+Tfs​+Tdriver​+Tbus​+Tmedia​Tmedia​​

```

```

## 8. 工程最佳实践

## 8.1 设计原则

### 原则一：实时任务不直接访问慢速介质

错误架构：

```
ADC 采集任务
    ↓
直接 fwrite()
    ↓
SD 卡
```

推荐架构：

```
ADC 采集任务
    ↓
无锁/低锁环形缓冲
    ↓
存储任务
    ↓
批量写入文件系统
```

### 原则二：把同步边界设计成业务事务

不要无条件每次写都 `fsync()`。应根据业务定义提交点：

```
采样数据：允许丢失最近 1 秒
配置数据：必须立即持久化
升级状态：每个阶段必须持久化
故障事件：必须优先写入
```

### 原则三：顺序写优先于随机写

优先级通常为：

```
连续大块顺序写
    >
连续小块顺序写
    >
随机大块写
    >
随机小块写
```

### 原则四：容量预留

不要让存储介质长期运行在 95% 以上容量。建议：

- 普通文件系统：保留 10%~20%；
- Flash 写密集系统：保留 20%~30%；
- 环形日志：根据寿命和恢复需求设计。

### 原则五：性能测试必须关注尾延迟

平均延迟可能很好，但 P99/P999 极差。工业系统至少应记录：

```
平均值
最大值
P95
P99
P999
超时次数
错误次数
```

## 8.3 工业级编码规范

- 所有 IO 返回值必须检查。
- 处理短读、短写、`EINTR`、`EIO`、`ENOSPC`。
- 文件路径、文件名、记录长度必须进行边界校验。
- 不在中断中执行文件系统操作。

    - CRC；
    - 显式序列化。
- 文件格式必须支持版本升级。
- 写入日志必须能够在任意位置掉电后恢复。
- 存储任务必须有超时和故障隔离机制。

## 9. 常见错误与避坑指南

## 9.1 错误一：每条记录都同步写

### 错误代码

```
for (;;) {
    write(fd, &record, sizeof(record));
    fsync(fd);
}
```

### 根因

- 把“系统调用完成”误认为“必须立即持久化”；
- 没有定义业务提交周期；
- 忽略了介质内部擦除和垃圾回收。

### 正确实现

```
buffer_append(&cache, &record, sizeof(record));

if (cache_size(&cache) >= 32 * 1024 ||
    elapsed_ms_since_flush() >= 1000) {
    write_all(fd, cache_data(&cache), cache_size(&cache));
    fdatasync(fd);
    cache_reset(&cache);
}
```

### 风险影响

- 吞吐下降；
- 任务阻塞；
- P99 延迟不可控；
- SD/eMMC 写放大增加。

---

## 9.2 错误二：DMA 与 Cache 不一致

### 错误代码

```
memcpy(tx_buf, source, length);
sdmmc_dma_write(tx_buf, length);
```

### 根因

CPU 修改的数据仍停留在 D-Cache，DMA 从 RAM 读取到旧数据。

### 正确实现

```
memcpy(tx_buf, source, length);

/* DMA 发送前清理 D-Cache */
SCB_CleanDCache_by_Addr((uint32_t *)tx_buf,
                        ALIGN_UP(length, 32));

sdmmc_dma_write(tx_buf, length);
```

DMA 接收后：

```
sdmmc_dma_read(rx_buf, length);

/* DMA 完成后使 Cache 失效 */
SCB_InvalidateDCache_by_Addr((uint32_t *)rx_buf,
                              ALIGN_UP(length, 32));
```

### 风险影响

- 文件数据偶发损坏；
- CRC 错误；
- 问题只在开启 Cache 或高负载时出现；
- 难以复现。

---

## 9.3 错误三：使用结构体直接持久化

### 错误代码

```
fwrite(&config, sizeof(config), 1, fp);
```

### 根因

- 编译器可能插入 Padding；
- 字节序不明确；
- 结构体字段扩展后格式不兼容；
- 指针成员不能持久化；
- 浮点格式可能不一致。

### 正确实现

```
typedef struct {
    uint32_t version;
    uint32_t baudrate;
    uint16_t timeout_ms;
    uint8_t  mode;
} config_wire_t;

void config_serialize(config_wire_t *out,
                      const device_config_t *in)
{
    memset(out, 0, sizeof(*out));
    out->version = to_le32(in->version);
    out->baudrate = to_le32(in->baudrate);
    out->timeout_ms = to_le16(in->timeout_ms);
    out->mode = in->mode;
}
```

### 风险影响

- 固件升级后无法读取旧配置；
- 跨平台解析错误；
- 隐蔽数据损坏。

---

## 9.4 错误四：文件名和目录无限增长

### 错误代码

```
snprintf(path, sizeof(path), "/log/%08u.bin", sequence++);
create_file(path);
```

### 根因

- 创建大量小文件；
- 目录扫描和 FAT 更新成本线性增加；
- 删除旧文件产生碎片。

### 正确实现

```
/log/2025/03/08/segment_0000.bin
/log/2025/03/08/segment_0001.bin
/log/2025/03/08/segment_0002.bin
```

同时设置：

- 单文件最大容量；
- 单目录最大文件数；
- 按时间或大小滚动；
- 定期回收旧文件；
- 预分配文件容量。

### 风险影响

- 启动扫描变慢；
- 空间碎片增多；
- 目录操作延迟抖动。

---

## 9.5 错误五：没有容量和短写检查

### 错误代码

```
write(fd, buf, length);
```

### 根因

- 假设 `write()` 必然写完；
- 忽略 `ENOSPC`、`EIO`、`EINTR`；
- 没有磁盘空间阈值管理。

### 正确实现

```
ssize_t write_all(int fd, const void *buf, size_t len)
{
    const uint8_t *p = buf;
    size_t done = 0;

    while (done < len) {
        ssize_t n = write(fd, p + done, len - done);

        if (n > 0) {
            done += (size_t)n;
            continue;
        }

        if (n < 0 && errno == EINTR) {
            continue;
        }

        return -1;
    }

    return (ssize_t)done;
}
```

### 风险影响

- 文件尾部缺失；
- 日志记录截断；
- 文件系统认为文件已存在但内容不完整。

## 10. 多机制组合使用方案

## 10.1 推荐架构

```
实时采集任务
    ↓
SPSC Ring Buffer
    ↓
存储服务任务
    ├─ 批量聚合
    ├─ CRC
    ├─ 文件滚动
    ├─ 水位监控
    ├─ 异步写
    └─ 周期同步
        ↓
文件系统适配层
        ↓
块设备驱动
        ↓
DMA
        ↓
SD/eMMC/NOR
```

### 组合机制

- 环形缓冲：隔离实时任务与慢速介质；
- 批量写：降低固定开销；
- CRC：检测数据损坏；
- 文件滚动：限制单文件大小；
- 双备份：保护关键配置；
- 异步提交：减少阻塞；
- 高低水位：防止缓冲溢出；
- 看门狗监测：检测存储任务卡死。

## 10.2 存储服务框架

```
typedef struct {
    uint8_t *data;
    size_t capacity;
    size_t head;
    size_t tail;
} ring_buffer_t;

typedef struct {
    int fd;
    ring_buffer_t ring;
    uint64_t bytes_written;
    uint32_t dropped_records;
    uint32_t sync_period_ms;
    uint32_t last_sync_ms;
} storage_service_t;

static bool storage_flush(storage_service_t *svc)
{
    uint8_t block[32 * 1024];
    size_t n = ring_read(&svc->ring, block, sizeof(block));

    if (n == 0) {
        return true;
    }

    if (write_all(svc->fd, block, n) != (ssize_t)n) {
        return false;
    }

    svc->bytes_written += n;
    return true;
}

void storage_task(void *arg)
{
    storage_service_t *svc = arg;

    for (;;) {
        wait_for_data_or_timeout();

        while (ring_size(&svc->ring) >= 32 * 1024) {
            if (!storage_flush(svc)) {
                storage_mark_fault();
                break;
            }
        }

        if (time_elapsed(svc->last_sync_ms) >= svc->sync_period_ms) {
            if (!storage_flush(svc) ||
                fdatasync(svc->fd) < 0) {
                storage_mark_fault();
            } else {
                svc->last_sync_ms = system_time_ms();
            }
        }

        if (ring_free(&svc->ring) < 4 * 1024) {
            storage_raise_high_watermark();
        }
    }
}
```

### 设计要点

- 采集任务只负责入队；
- 存储任务负责所有文件系统操作；
- 队列满时必须定义策略：
    - 丢最旧；
    - 丢最新；
    - 阻塞采集；
    - 降采样；
    - 切换到备用介质。
- 关键事件不能和普通日志共用同一优先级。

## 11. 工业级实际案例分析

## 11.1 案例一：电机控制器参数存储

### 需求

- 参数量：8 KB；
- 更新频率：每天几十次；
- 断电不能损坏；
- 启动读取时间小于 10 ms；
- 支持固件版本升级。

### 架构

```
内部 NOR Flash
    ├─ Slot A
    ├─ Slot B
    └─ 版本信息
```

### 核心逻辑

```
启动：
1. 校验 Slot A
2. 校验 Slot B
3. 选择版本号最大且 CRC 正确者
4. 无有效副本则加载默认参数

更新：
1. 修改 RAM 参数
2. 写入较旧 Slot
3. 写入 CRC
4. 写入 Commit Marker
5. 重新读取校验
6. 切换当前 Slot
```

### 设计要点

- 不在运行控制循环中擦除 Flash；
- 更新操作放到低优先级任务；
- 写入期间禁止同时修改同一参数；
- 关键参数按字段范围校验；
- 每次升级需要兼容旧版本格式。

## 11.2 案例二：工业采集终端高频日志

### 需求

- 采样频率：1000 Hz；
- 每条记录：64 B；
- 原始数据率：64 KB/s；
- 允许掉电丢失最多 1 秒；
- 控制任务不能被存储阻塞。

### 架构

```
采样 ISR / DMA
    ↓
双缓冲
    ↓
RAM 环形队列，容量 2 MB
    ↓
存储任务，32 KB 批量写
    ↓
预分配日志文件
    ↓

```

若允许缓存 1 秒：

64KB/s×1s=64KB64KB/s×1s=64KB

但工业系统应考虑抖动，建议容量至少：

Cbuffer=Rdata×Tworst−case×SafetyFactorCbuffer​=Rdata​×Tworst−case​×SafetyFactor


- DMA 双缓冲减少 CPU 搬运；

- 每秒提交一次；
- 日志记录带序列号；
- 启动时检测序列号断点；
- 存储故障时切换到降采样模式。

## 11.3 案例三：Linux 网关设备根文件系统

### 需求

- 系统区只读；
- 应用配置可更新；
- 掉电后系统必须可启动；
- 支持远程升级；
- 减少 eMMC 写放大。

### 架构

```
eMMC
├─ Boot A
├─ Boot B
├─ RootFS A：SquashFS，只读
├─ RootFS B：SquashFS，只读
├─ Data：ext4/f2fs，可写
└─ Recovery：最小恢复系统
```

### 升级策略

```
当前运行 RootFS A
    ↓
下载升级包到 Data 临时区
    ↓

    ↓

    ↓

    ↓

    ├─ 成功 → 标记 B 成功

```

### 设计要点

- 系统区不直接覆盖；
- 升级采用 A/B 分区；
- 配置数据与系统镜像分离；
- 使用 `fsync()` 确保升级状态提交；
- Bootloader 必须支持失败回滚；
- 不依赖单一配置文件判断升级完成。

## 12. 高频问题深度答疑

### 问题一：为什么文件系统已经有缓存，还需要应用层缓存？

文件系统缓存通常服务于通用访问模式，未必理解业务语义。应用层缓存可以：

- 聚合固定格式记录；
- 根据优先级丢弃数据；
- 对关键事件单独提交；
- 控制掉电允许丢失窗口；
- 避免实时任务进入文件系统。

因此两者职责不同：

```
文件系统缓存：通用 IO 优化
应用层缓存：业务时序和可靠性控制
```

### 问题二：`fsync()` 是否等于数据已经安全写入 Flash？

不一定。它通常表示内核已经要求块设备完成持久化，但实际安全性还取决于：

- 存储控制器；
- eMMC/SD 内部缓存；
- 设备是否正确实现 Flush；
- 供电是否在写入期间稳定；
- 文件系统日志语义。

高可靠系统还需要：

- 存储器支持可靠写；
- 使用事务记录；
- 增加 CRC；
- 设计掉电测试；
- 必要时使用超级电容或掉电检测。

### 问题三：为什么顺序写也会出现长尾延迟？

因为介质内部可能执行：

- 垃圾回收；
- 块擦除；
- 坏块替换；
- FTL 映射表更新；
- ECC 重试；
- 内部缓存刷写。

所以平均吞吐不能代表实时性。必须测量 P99/P999。

### 问题四：FATFS 适合工业设备吗？

取决于使用方式。

适合：

- SD 卡数据交换；
- 固件升级包；
- 用户可读文件；
- 日志导出。

不适合直接承担：

- 高频小块同步写；
- 强实时持久化；
- 复杂掉电事务；
- 高并发文件访问。

对于关键参数和高频日志，建议使用独立原始分区或专用日志格式。

### 问题五：LittleFS 和 FATFS 应该怎么选？

选择 LittleFS 的条件：

- 介质为 NOR 或 Raw Flash；
- 文件数量不多；
- 强调掉电恢复；
- 不要求 PC 直接读取。

选择 FATFS 的条件：

- SD/eMMC 等块设备；
- 需要与 PC 交换；
- 需要通用文件格式；
- 介质控制器已经完成坏块和磨损管理。

### 问题六：什么时候应该放弃文件系统，使用原始日志？

当以下条件成立时，可以考虑原始格式：

- 数据格式固定；
- 访问路径可控；
- 不需要用户浏览文件；
- 需要极低延迟；
- 需要确定性；
- 能够自行实现 CRC、索引、回收和掉电恢复。

但原始格式会把以下责任转移给应用：

```
空间管理
版本管理
错误恢复
磨损均衡
垃圾回收
掉电一致性
工具支持
```

## 13. 课程核心总结

### 核心要点

1. **存储性能是端到端问题**，不能只优化文件系统 API。
2. **小块随机写是最危险的访问模式**。
3. **批量顺序写通常是最有效的通用优化手段**。
4. **实时任务不应直接访问 SD、eMMC 或文件系统**。
5. **平均吞吐不足以描述工业存储性能，必须关注 P99/P999 延迟**。
6. **掉电一致性需要 CRC、事务、双备份或日志提交协议**。
7. **写放大直接决定 Flash 寿命**。
8. **关键参数、高频日志、大文件和系统根文件系统应采用不同架构**。
9. **文件格式必须具备版本、长度、CRC 和恢复机制**。
10. **DMA + Cache 一致性是 MCU 存储系统中最常见的隐蔽问题之一**。

### 通用性能排序

一般情况下：

```
SRAM / TCM
    >
FRAM
    >
NOR 顺序读取
    >
eMMC 顺序访问
    >
SD 卡顺序访问
    >
小块文件系统随机写
    >
频繁同步写 + Flash 擦除
```

### 通用选型结论

- **实时数据**：RAM/TCM + 环形缓冲；
- **高频持久化**：FRAM 或顺序日志；
- **少量关键配置**：NOR + 双备份；
- **可移动存储**：FATFS；
- **Linux NAND 系统**：F2FS 或 UBIFS；
- **只读固件系统**：SquashFS；
- **强一致数据**：事务日志 + CRC + 明确提交点。
