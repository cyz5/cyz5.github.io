# 3. 技术概述

## 3.1 多核系统协同的定义

多核系统协同是指多个处理器核心围绕以下资源和状态进行协调：

- 任务与负载；
- 中断和事件；
- 共享内存；
- Cache 一致性；
- 电源和时钟；
- 外设所有权；
- 安全域；
- 故障状态；
- 启停和低功耗状态。

多核协同不是简单地“把任务分到不同 CPU”，而是需要同时保证：

```
功能正确性
+ 内存可见性
+ 并发安全性
+ 实时性
+ 资源隔离
+ 功耗约束
+ 故障可恢复性
```

## 3.2 多核架构分类

### SMP：对称多处理

所有 CPU 运行同一操作系统，拥有近似对称的访问权限和资源。

```
Linux
├── CPU0
├── CPU1
├── CPU2
└── CPU3
```

特点：

- 一个内核统一调度；
- 共享地址空间；
- 通常具有硬件 Cache 一致性；
- 适合通用计算和服务器；
- 需要解决锁竞争、负载均衡和共享资源争用。

### AMP：非对称多处理

不同 CPU 运行不同软件栈。

```
CPU0/1：Linux
CPU2：RTOS
CPU3：安全固件
```

特点：

- 软件栈独立；
- 资源隔离清晰；
- 实时核可获得确定性；
- 需要设计跨 OS 通信和资源所有权；
- 共享内存和外设访问必须明确边界。

### HMP：异构多处理

CPU 核心能力、功耗和性能不同，例如大小核。

```
Big Cluster：高性能核心
Little Cluster：高能效核心
```

调度器需要考虑：

- CPU capacity；
- 频率和温度；
- 迁移成本；
- Cache 局部性；
- 能耗和性能目标。

### Cluster 级架构

多个 CPU 组成一个 Cluster，共享：

- L2/L3 Cache；
- 电源域；
- 时钟源；
- GIC Redistributor 或中断路径；
- 内存一致性接口。

```
Cluster 0
├── CPU0
├── CPU1
├── CPU2
└── CPU3

Cluster 1
├── CPU4
├── CPU5
├── CPU6
└── CPU7
```

## 3.3 多核协同的五个平面

|平面|主要内容|
|---|---|
|计算平面|任务分配、调度、负载均衡|
|通信平面|IPI、Mailbox、共享内存、RPMsg|
|一致性平面|Cache、内存顺序、屏障、原子操作|
|资源平面|电源、时钟、外设、内存和 DMA|
|故障平面|看门狗、核下线、恢复和安全降级|

工业级设计必须避免只关注计算平面，而忽略一致性、资源和故障平面。

## 4.1 SMP、AMP、HMP 对比

|维度|SMP|AMP|HMP|
|---|---|---|---|
|软件栈|单一 OS|多软件栈|通常单 OS|
|地址空间|统一|可统一或隔离|统一|
|调度方式|OS 全局调度|静态/专用分配|能力感知调度|
|实时性|中|高|中～高|
|资源共享|高|需显式设计|高|
|开发复杂度|中|高|高|
|故障隔离|中|高|中|
|功耗优化|中|高|高|
|跨 OS 通信|不需要|必须|通常不需要|
|典型场景|Linux 服务器、应用处理|Linux + RTOS|手机、汽车 SoC|

## 4.2 核间通信机制对比

|机制|延迟|数据容量|主要用途|主要风险|
|---|---|---|---|---|
|共享变量|极低|小|状态标志|数据竞争|
|原子变量|极低|小|状态和计数|内存序错误|
|自旋锁|低|不承载数据|短临界区|长时间占用|
|IPI|低|无/极少|跨核唤醒|中断风暴|
|Mailbox|低～中|小～中|异构通知|队列拥塞|
|共享环形队列|低～中|中～大|核间消息|Cache/索引错误|
|RPMsg|中|中|跨 OS RPC|超时和复位|
|DMA|中|大|数据面传输|地址和生命周期|

## 4.3 同步原语对比

|机制|适用场景|是否可睡眠|典型问题|
|---|---|---|---|
|原子变量|标志、计数、状态|否|ABA、内存序错误|
|自旋锁|极短临界区|否|CPU 空转、死锁|
|Mutex|可能阻塞的资源|是|优先级反转|
|读写锁|读多写少|通常可|写者饥饿|
|Seqlock|读多写少、读可重试|读侧否|读侧可能反复重试|
|RCU|读多写少、读路径极短|读侧通常否|回收时机复杂|
|Barrier|发布/观察顺序|否|不是互斥机制|
|IPI|唤醒和跨核同步|否|过量通知|

# 5. 底层原理与功能特性深度解析

## 5.1 ARM 多核启动流程

典型 AArch64 多核启动：

```
Boot CPU
  |
  +-- 初始化 EL3/EL2/EL1
  +-- 初始化 GIC
  +-- 建立页表和共享内存
  +-- 发布次级 CPU 启动入口
  +-- PSCI CPU_ON 或 SEV 唤醒
  v
Secondary CPU
  |
  +-- 读取 MPIDR
  +-- 设置栈和异常向量
  +-- 初始化 MMU/Cache
  +-- 加入调度器
  +-- 标记 CPU online
```

### 启动上下文发布

```
struct cpu_boot_context {
    uint64_t entry;
    uint64_t context_id;
    uint64_t stack;
    uint32_t valid;
};
```

主核发布：

```
void publish_cpu_boot_context(unsigned int cpu,
                              uint64_t entry,
                              uint64_t stack,
                              uint64_t context_id)
{
    struct cpu_boot_context *ctx = &boot_context[cpu];

    ctx->entry = entry;
    ctx->stack = stack;
    ctx->context_id = context_id;

    /*
     * valid 必须最后发布，保证目标核不会看到半初始化数据。
     */
    dsb_sy();
    ctx->valid = 1;
    dsb_sy();

    sev();
}
```

次级核读取：

```
void secondary_cpu_wait(unsigned int cpu)
{
    struct cpu_boot_context *ctx = &boot_context[cpu];

    while (ctx->valid == 0) {
        wfe();
    }

    dmb_sy();

    setup_stack(ctx->stack);
    jump_to_entry(ctx->entry, ctx->context_id);
}
```

工程注意：

- 入口地址必须位于可执行且允许访问的内存区域。
- 启动栈必须按 ABI 对齐。
- `valid` 不能在其他字段写入前发布。
- 目标 CPU 进入 `WFE` 前需要正确处理 `SEV` 丢失问题。
- 生产实现优先使用 PSCI 和平台标准启动路径。

## 5.2 Cache 一致性与内存可见性

### Cache 一致性不等于内存顺序

硬件一致性解决：

```
CPU0 写入 X 后，CPU1 最终能看到 X 的新值
```

内存屏障解决：

```
CPU1 看到 flag = READY 时，必须同时看到 data 已完成写入
```

经典发布—订阅模型：

```
struct shared_object {
    uint32_t data;
    atomic_uint ready;
};

/* CPU0 */
obj->data = 0x12345678;
atomic_store_explicit(&obj->ready,
                      1,
                      memory_order_release);

/* CPU1 */
if (atomic_load_explicit(&obj->ready,
                         memory_order_acquire) == 1) {
    value = obj->data;
}
```

如果没有 Release/Acquire，CPU1 可能先观察到 `ready == 1`，但仍读取到旧的 `data`。

### ARM 屏障选择

|屏障|作用|
|---|---|
|`DMB`|约束内存访问顺序|
|`DSB`|等待显式内存访问完成|
|`ISB`|刷新指令流，常用于系统寄存器、页表和异常级别变化|

一般数据发布优先使用 `DMB`；涉及设备寄存器、Doorbell 或需要确保访问完成时使用 `DSB`。不能把 `DSB` 当作通用替代品，否则会增加不必要延迟。

## 5.3 伪共享与 Cache Line 抖动

两个核修改位于同一 Cache Line 的不同变量，会造成 Cache Line 在核间反复转移。

错误布局：

```
struct cpu_stat {
    uint64_t packets_cpu0;
    uint64_t packets_cpu1;
};
```

如果两个变量位于同一 64 B Cache Line：

```
CPU0 写 packets_cpu0
CPU1 写 packets_cpu1
        |
        v
Cache Line 在 CPU0/CPU1 间反复失效
```

正确布局：

```
#define CACHE_LINE_SIZE 64U

struct cpu_stat {
    uint64_t packets;
    uint8_t padding[CACHE_LINE_SIZE - sizeof(uint64_t)];
} __attribute__((aligned(CACHE_LINE_SIZE)));

struct cpu_stat stats[2];
```

收益取决于访问频率。在高频计数器场景中，消除伪共享可能带来数倍性能提升；但会增加内存占用，因此应针对热点数据使用，而不是无条件填充。

## 5.4 IPI 的底层作用

IPI 通常用于：

- 跨核唤醒；
- TLB Shootdown；
- 调度迁移；
- RCU 回调推进；
- CPU 停止；
- 跨核函数调用；
- Cache 或状态同步。

Linux 中的典型流程：

```
CPU0 修改共享调度状态
    |
    v
发送 IPI 到 CPU1
    |
    v
CPU1 进入 IPI ISR
    |
    +-- 读取 pending bit
    +-- 执行对应动作
    +-- 清除 pending bit
    +-- 返回
```

发送 IPI 前必须先发布共享状态：

```
pending_mask |= BIT(action);
smp_wmb();
send_ipi(target_cpu);
```

接收端：

```
handle_ipi(void)
{
    uint32_t actions;

    actions = pending_mask;
    smp_rmb();

    if (actions & BIT(ACTION_RESCHEDULE))
        reschedule();

    if (actions & BIT(ACTION_TLB_FLUSH))
        flush_local_tlb();

    pending_mask &= ~actions;
}
```

实际内核代码需使用架构和内核提供的原子操作，避免简单读改写造成丢事件。

## 5.5 跨核函数调用

跨核函数调用的抽象：

```
struct call_request {
    void (*func)(void *arg);
    void *arg;
    atomic_bool completed;
};

int call_on_cpu(unsigned int target,
                void (*func)(void *),
                void *arg,
                uint32_t timeout_us)
{
    struct call_request req;

    if (!cpu_online(target) || func == NULL)
        return -EINVAL;

    req.func = func;
    req.arg = arg;
    atomic_store(&req.completed, false);

    publish_call_request(target, &req);
    send_ipi(target, IPI_CALL_FUNCTION);

    if (!wait_until_timeout(&req.completed, timeout_us))
        return -ETIMEDOUT;

    return 0;
}
```

风险：

- 目标 CPU 已下线；
- 目标 CPU 被关中断；
- 目标 CPU 卡在不可抢占临界区；
- 调用方等待目标核，而目标核反过来等待调用方；
- 栈上请求对象在目标核完成前被释放。

生产实现应使用：

- 稳定分配的请求对象；
- CPU hotplug 引用；
- 明确的取消语义；
- 必要时异步执行；
- 不在持有全局锁时同步调用其他 CPU。

## 5.6 自旋锁与 Mutex

### 自旋锁适合

- 临界区非常短；
- 不允许睡眠；
- ISR 或底半部；
- 保护简单队列和寄存器状态。

### Mutex 适合

- 临界区可能较长；
- 线程上下文；
- 资源访问可能阻塞；
- 需要优先级继承。

错误代码：

```
spin_lock(&lock);
remote_rpc_call(); /* 可能阻塞数百微秒 */
spin_unlock(&lock);
```

问题：

- 持锁等待远端；
- 其他 CPU 忙等；
- 可能形成 RPC 回调死锁；
- 增大调度延迟。

正确实现：

```
spin_lock(&lock);
prepare_request();
spin_unlock(&lock);

ret = remote_rpc_call();

spin_lock(&lock);
commit_response();
spin_unlock(&lock);
```

## 5.7 优先级反转

典型场景：

```
低优先级任务 L 持有共享锁
高优先级任务 H 等待该锁
中优先级任务 M 持续运行
        |
        v
L 无法运行释放锁，H 长时间阻塞
```

解决方案：

- Mutex 使用优先级继承；
- 对高优先级控制路径使用独立资源；
- 缩短临界区；
- 避免在锁内进行远程调用；
- 使用消息传递替代共享锁；
- 为资源设置最大持锁时间。

注意：自旋锁通常不能解决优先级反转，反而可能使高优先级核忙等。

## 5.8 无锁 SPSC 环形队列

单生产者单消费者队列可以使用两个独立索引：

```
#define RING_SIZE 256U

struct spsc_ring {
    uint8_t data[RING_SIZE];
    atomic_uint head;
    atomic_uint tail;
};
```

生产者：

```
bool spsc_push(struct spsc_ring *ring,
               uint8_t value)
{
    unsigned int head;
    unsigned int next;

    head = atomic_load_explicit(&ring->head,
                                memory_order_relaxed);
    next = (head + 1U) % RING_SIZE;

    if (next == atomic_load_explicit(&ring->tail,
                                     memory_order_acquire))
        return false;

    ring->data[head] = value;

    atomic_store_explicit(&ring->head,
                          next,
                          memory_order_release);
    return true;
}
```

消费者：

```
bool spsc_pop(struct spsc_ring *ring,
              uint8_t *value)
{
    unsigned int tail;
    unsigned int head;

    if (value == NULL)
        return false;

    tail = atomic_load_explicit(&ring->tail,
                                memory_order_relaxed);
    head = atomic_load_explicit(&ring->head,
                                memory_order_acquire);

    if (tail == head)
        return false;

    *value = ring->data[tail];

    atomic_store_explicit(&ring->tail,
                          (tail + 1U) % RING_SIZE,
                          memory_order_release);
    return true;
}
```

该实现只适合：

- 一个生产者；
- 一个消费者；
- 固定内存；
- 正确的内存序。

多生产者、多消费者需要 CAS、锁或更复杂的 MPMC 算法，不能直接套用 SPSC 实现。

## 5.9 RCU 与读多写少数据

当读路径非常频繁且不能阻塞时，可以采用 RCU：

```
struct config {
    uint32_t frequency;
    uint32_t mode;
};

struct config __rcu *active_config;

void read_config(void)
{
    struct config *cfg;

    rcu_read_lock();
    cfg = rcu_dereference(active_config);
    use_config(cfg);
    rcu_read_unlock();
}

void update_config(struct config *new_cfg)
{
    struct config *old_cfg;

    old_cfg = rcu_replace_pointer(active_config,
                                   new_cfg,
                                   true);
    synchronize_rcu();
    kfree(old_cfg);
}
```

核心原则：

- 读侧不持有传统锁；
- 写侧发布新对象；
- 等待所有旧读者退出后才能释放旧对象；
- RCU 不适合需要立即可见并且频繁修改的数据。

## 5.10 CPU Hotplug 与协同状态

CPU 下线通常包括：

```
ONLINE
  -> DRAINING
  -> MIGRATING_TASKS
  -> OFFLINE_PREPARE
  -> STOPPING
  -> OFFLINE
```

上线过程：

```
OFFLINE
  -> POWERING_ON
  -> BOOTING
  -> INITIALIZING
  -> ONLINE_PENDING
  -> ONLINE
```

关键协同内容：

- 迁移任务；
- 迁移中断；
- 清理定时器；
- 处理 RCU；
- 刷新或回收 per-CPU 数据；
- 关闭本地电源；
- 释放 GIC Redistributor；
- 更新调度域；
- 通知用户空间和设备驱动。

不能只执行：

```
power_off_cpu(cpu);
```

否则可能导致：

- 中断丢失；
- per-CPU 数据悬空；
- 任务仍被调度到已关闭 CPU；
- 共享电源域错误关闭；
- RCU grace period 无法完成。

## 5.11 多核电源协同

电源状态需要同时考虑：

```
CPU 状态
Cluster 状态
L2/L3 Cache 状态
GIC 状态
外设依赖
DMA 状态
唤醒源
```

示例：

```
CPU0 OFF
CPU1 OFF
CPU2 OFF
CPU3 OFF
    |
    +-- Cache flush/retention
    +-- GIC context save
    +-- Cluster clock off
    +-- Cluster power off
```

共享电源域使用引用计数：

```
int cluster_power_get(struct cluster *cluster)
{
    int ret = 0;

    mutex_lock(&cluster->lock);

    if (cluster->users == 0U) {
        ret = scmi_power_on(cluster->power_domain);
        if (ret != 0)
            goto out;
    }

    cluster->users++;

out:
    mutex_unlock(&cluster->lock);
    return ret;
}
```

必须防止 CPU 电源状态管理与设备运行时电源管理互相等待。

# 6. 性能量化分析

## 6.1 测试平台

采用典型平台：

- 4 × Cortex-A55，1.2 GHz；
- L1/L2 Cache 开启；
- GICv3；
- 硬件 Cache 一致性；
- Linux SMP；
- Generic Timer 24 MHz；
- 测量工具：PMU、ftrace、GPIO、`perf lock`。

以下数据为典型工程范围，不代表所有 SoC 的固定值。

## 6.2 核间操作延迟

|操作|典型延迟|
|---|---|
|本地原子操作|5～30 ns|
|本地自旋锁无竞争|10～50 ns|
|跨核共享变量读取|20～100 ns|
|跨核 Cache Line 转移|50～300 ns|
|IPI 发送到目标 ISR|0.5～3 μs|
|IPI 唤醒目标线程|2～10 μs|
|跨核 Mutex 无竞争|0.1～0.5 μs|
|跨核 Mutex 高竞争|1～100 μs|
|RPMsg 小消息|5～30 μs|
|CPU 热启动|0.5～20 ms|
|CPU 深度休眠唤醒|10 μs～数 ms|

## 6.3 锁竞争分析

平均锁等待时间：

```
T_lock_wait =
T_cache_transfer
+ T_critical_section
+ T_scheduler_delay
+ T_interrupt_interference
```

假设：

```
Cache 转移       = 0.2 μs
临界区           = 1.0 μs
调度干扰         = 3.0 μs
中断干扰         = 0.8 μs
```

则：

```
T_lock_wait ≈ 5.0 μs
```

如果每秒发生 100,000 次竞争：

```
CPU_Time = 100,000 × 5 μs = 0.5 s
```

即单核约有 **50% 时间**用于等待或受竞争影响。

优化方式：

- 缩短临界区；
- 拆分全局锁；
- 使用 per-CPU 数据；
- 批量提交；
- 使用无锁 SPSC；
- 将统计数据改成 per-CPU 累加后汇总；
- 避免在持锁期间访问慢速设备或远程核。

## 6.4 IPI 负载

如果每秒发送 50,000 次 IPI，单次目标核处理 1.5 μs：

```
CPU_Load = 50,000 × 1.5 μs / 1 s
         = 7.5%
```

如果多个事件可以合并，应使用 pending bitmap：

```
atomic_fetch_or(&pending_ipi_actions,
                BIT(ACTION_A) | BIT(ACTION_B));

if (atomic_exchange(&ipi_sent, 1) == 0)
    send_ipi(target);
```

目标核一次读取多个 pending action，减少 IPI 次数。

## 6.5 多核扩展效率

理论加速比：

```
S(N) = T1 / TN
```

考虑串行部分，根据 Amdahl 定律：

```
S(N) = 1 / (f + (1 - f) / N)
```

其中：

- `f`：不可并行部分比例；
- `N`：CPU 核数。

如果 `f = 0.1`，4 核理论加速比：

```
S(4) = 1 / (0.1 + 0.9 / 4)
     ≈ 2.做
```

实际还要扣除：

- 锁竞争；
- Cache 一致性流量；
- 调度开销；
- 内存带宽；
- NUMA/Cluster 访问代价；
- 负载不均衡。

## 6.6 内存开销

|项目|典型开销|
|---|---|
|每 CPU 的调度数据|1～8 KB|
|每 CPU 的中断统计|1～4 KB|
|每 CPU 的栈|8～64 KB|
|SPSC 环形队列|1～64 KB|
|IPI pending bitmap|8～64 B|
|事务对象|64～512 B/个|
|多核共享配置对象|64 B～数 KB|

4 核系统中，如果每核分配：

```
每核栈       = 16 KB
per-CPU 状态 = 4 KB
per-CPU 统计 = 2 KB
```

静态开销约：

```
4 × (16 + 4 + 2) KB = 88 KB
```

## 6.7 典型瓶颈与优化收益

|瓶颈|优化前|优化后|典型收益|
|---|---|---|---|
|全局统计锁|8 μs/次|0.2 μs/次|降低约 25～40 倍|
|频繁 IPI|50k/s|10k/s|降低 80%|
|伪共享计数器|高 Cache miss|per-CPU 对齐|可提升数倍|
|全局任务队列|竞争严重|per-CPU 队列|降低锁竞争|
|同步跨核调用|20 μs|异步批量|降低 50% 以上|
|频繁 CPU 迁移|高抖动|CPU affinity|显著降低抖动|

# 8. 工程最佳实践

## 8.1 设计原则

### 原则一：明确 CPU 所有权

每个核心必须明确：

- 谁负责启动；
- 谁负责停止；
- 谁负责配置电源；
- 谁负责处理中断；
- 谁拥有外设；
- 谁可以访问共享内存；
- 谁负责故障恢复。

### 原则二：减少共享可写状态

优先级：

```
本地状态
    >
消息传递
    >
per-CPU 状态 + 汇总
    >
细粒度共享状态
    >
全局共享锁
```

共享可写变量越少，Cache 一致性和死锁风险越低。

### 原则三：实时核不依赖非实时核

Cortex-M 实时闭环不能依赖：

- Linux 调度；
- Linux ACK；
- Linux 释放锁；
- Linux 处理故障；
- Linux 发送下一周期参数。

Linux 只应下发目标值或配置，实时核本地执行闭环。

### 原则四：锁内不执行远程操作

禁止：

```
持锁
  -> Mailbox/RPMsg
  -> 等待远端
  -> 回调再次请求同一锁
```

应拆成：

```
锁内准备
  -> 解锁
  -> 远程调用
  -> 锁内提交结果
```

### 原则五：定义内存模型

每一个跨核共享结构都应明确：

- 谁写、谁读；
- 是否单生产者单消费者；
- 何时发布；
- 何时回收；
- 使用何种屏障；
- 是否 Cache 对齐；
- 是否需要原子操作。

## 8.2 选型决策矩阵

|需求|共享变量|原子变量|IPI|Mailbox/RPMsg|DMA|
|---|---|---|---|---|---|
|极低延迟状态|高|高|中|低|低|
|队列消息|低|中|低|高|中|
|跨 OS 通信|低|低|中|高|高|
|大数据|低|低|低|中|高|
|硬实时|高|高|高|低～中|中|
|服务发现|否|否|否|高|否|
|故障恢复|低|中|中|高|中|
|并发复杂度|高风险|中|低|中|高|

## 8.3 工业级编码规范

- 所有跨核共享字段使用固定宽度类型。
- 不使用普通 `volatile` 替代原子操作。
- 不使用原子操作替代完整的数据结构同步。
- 共享结构按照 Cache Line 对齐。
- 明确使用 Release/Acquire 或 ARM 屏障。
- 禁止持有自旋锁调用 Mailbox、RPMsg、DMA 等慢路径。
- 禁止在 ISR 中睡眠或等待远端响应。
- 所有跨核请求有超时和取消语义。
- CPU hotplug 时必须阻止新的任务和请求进入目标核。
- 所有 per-CPU 资源在核下线前清理或迁移。
- 为每个核记录负载、IPI、Cache miss、锁等待和故障统计。
- 不允许普通核直接操作安全核或实时核的私有资源。
- 远端消息必须校验长度、版本、Token、序号和权限。
- 故障处理路径不能依赖已经可能失效的普通通信通道。

# 9. 常见错误与避坑指南

## 9.1 错误一：使用 `volatile` 解决多核同步

### 错误代码

```
volatile bool ready;
volatile uint32_t data;

/* CPU0 */
data = 100;
ready = true;

/* CPU1 */
while (!ready)
    ;
printf("%u\n", data);
```

### 根因

`volatile` 只限制编译器优化，不保证：

- 原子性；
- 内存顺序；
- Cache 可见性；
- 多核同步关系。

### 正确实现

```
atomic_uint ready;
uint32_t data;

/* CPU0 */
data = 100;
atomic_store_explicit(&ready, 1,
                      memory_order_release);

/* CPU1 */
while (atomic_load_explicit(&ready,
                            memory_order_acquire) == 0) {
    cpu_relax();
}

printf("%u\n", data);
```

### 风险影响

可能读到旧数据、出现数据竞争、产生偶发初始化错误。

---

## 9.2 错误二：持锁执行跨核 RPC

### 错误代码

```
mutex_lock(&state_lock);
ret = rpmsg_send_and_wait(request, 1000);
update_state(ret);
mutex_unlock(&state_lock);
```

### 根因

远端响应路径可能再次访问 `state_lock`，或者其他核长期等待该锁。

### 正确实现

```
mutex_lock(&state_lock);
request = build_request_from_state();
mutex_unlock(&state_lock);

ret = rpmsg_send_and_wait(request, 1000);

mutex_lock(&state_lock);
if (ret == 0)
    commit_remote_state();
mutex_unlock(&state_lock);
```

### 风险影响

死锁、长时间锁等待、优先级反转和系统级调度抖动。

---

## 9.3 错误三：忽略伪共享

### 错误代码

```
struct counters {
    atomic_uint cpu0_count;
    atomic_uint cpu1_count;
};
```

### 根因

两个核心频繁修改同一 Cache Line，导致 Cache Line 反复失效和转移。

### 正确实现

```
struct counter {
    atomic_uint value;
    uint8_t pad[60];
} __attribute__((aligned(64)));

struct counter counters[2];
```

### 风险影响

吞吐量下降、功耗增加、跨核延迟抖动。

---

## 9.4 错误四：CPU 下线前直接关闭电源

### 错误代码

```
void offline_cpu(unsigned int cpu)
{
    power_off_cpu(cpu);
}
```

### 根因

没有迁移任务、中断、定时器和 per-CPU 状态。

### 正确实现

```
int offline_cpu(unsigned int cpu)
{
    int ret;

    ret = stop_new_work(cpu);
    if (ret != 0)
        return ret;

    ret = migrate_tasks(cpu);
    if (ret != 0)
        return ret;

    ret = migrate_irqs(cpu);
    if (ret != 0)
        return ret;

    ret = drain_rcu_and_timers(cpu);
    if (ret != 0)
        return ret;

    ret = psci_cpu_off();
    return ret;
}
```

### 风险影响

任务丢失、中断悬空、共享资源错误关闭和系统崩溃。

---

## 9.5 错误五：跨核队列索引没有内存屏障

### 错误代码

```
ring->data[head] = item;
ring->head = next;
```

### 根因

消费者可能先看到 `head` 更新，再读取尚未完成发布的数据。

### 正确实现

```
ring->data[head] = item;
atomic_thread_fence(memory_order_release);
ring->head = next;
```

消费者：

```
head = atomic_load_explicit(&ring->head,
                            memory_order_acquire);

if (tail != head)
    item = ring->data[tail];
```

### 风险影响

读取半初始化数据、队列损坏、偶发协议错误。

---

## 9.6 错误六：所有核共享一个全局锁

### 错误代码

```
spin_lock(&global_lock);
process_packet();
spin_unlock(&global_lock);
```

其中 `process_packet()` 可能处理大量数据或访问慢速设备。

### 根因

全局锁扩大了串行区，破坏多核扩展性。

### 正确实现

```
queue_packet_to_owner(packet);
```

由设备所有者核串行处理，其他核通过消息传递提交请求。

### 风险影响

多核加速比低、锁竞争严重、实时任务被普通数据阻塞。

# 10. 多机制组合使用方案

## 10.1 典型异构多核架构

```
Cortex-A Cluster / Linux
├── 通用任务
├── 网络协议
├── 文件系统
└── 控制策略
        |
        +-- PSCI：CPU/Cluster 电源状态
        +-- IPI：Linux 内部跨核唤醒
        +-- RPMsg：跨 OS 服务通信
        +-- Shared Memory：消息和状态
        +-- DMA：大数据
        v

├── 实时控制环
├── 采样和执行器
├── 安全监控
└── 本地故障处理
```

### 协同关系

|机制|作用|
|---|---|
|PSCI|CPU/Cluster 启停和低功耗|
|IPI|Linux 内部跨核调度和同步|
|Mailbox|A-M 通知和 Doorbell|
|RPMsg|A-M 控制消息和事件|
|Shared Memory|队列、状态和描述符|
|DMA|大数据传输|
|Watchdog|远端健康监测|
|RCU/per-CPU|Linux 内部高并发读路径|

## 10.2 控制面、数据面和故障面

```
控制面：
Linux -> RPMsg RPC -> Cortex-M
  - 模式
  - 目标值
  - 配置
  - 状态查询

数据面：
Cortex-M -> DMA Ring -> Linux
  - 采样
  - 音频
  - 图像
  - 日志

故障面：
Cortex-M -> Fault Mailbox -> Linux
Linux -> Recovery Controller -> Cortex-M
  - 看门狗
  - 心跳
  - 复位
  - 安全降级
```

## 10.3 完整的多核服务框架

```
struct multicore_system {
    struct cpu_manager cpu_mgr;
    struct ipc_channel control_channel;
    struct ipc_channel event_channel;
    struct dma_ring data_ring;
    struct watchdog_manager watchdog;
    mutex_t resource_lock;
};

int multicore_submit_control(struct multicore_system *sys,
                             const void *request,
                             size_t request_len,
                             void *response,
                             size_t response_len,
                             uint32_t timeout_us)
{
    int ret;

    if (sys == NULL || request == NULL || response == NULL)
        return -EINVAL;

    /*
     * 资源快照只在锁内完成，不在锁内等待远端。
     */
    mutex_lock(&sys->resource_lock);
    ret = validate_control_request(request, request_len);
    mutex_unlock(&sys->resource_lock);

    if (ret != 0)
        return ret;

    ret = ipc_rpc_call(&sys->control_channel,
                       request,
                       request_len,
                       response,
                       response_len,
                       timeout_us);

    if (ret == -ETIMEDOUT || ret == -EHOSTDOWN)
        watchdog_schedule_recovery(&sys->watchdog);

    return ret;
}
```

## 10.4 多核负载分配策略

### 静态分配

```
CPU0：系统管理
CPU1：通信协议
CPU2：实时控制
CPU3：日志和诊断
```

优点：

- 确定性高；
- 易于功能安全分析；
- 资源边界清晰。

缺点：

- 负载不均衡；
- 某些核可能空闲；
- 动态适应能力弱。

### 动态分配

由调度器根据：

- CPU 利用率；
- 任务优先级；
- CPU capacity；
- Cache 局部性；
- 温度；
- 电源预算；

进行迁移。

适合通用计算，但实时任务必须设置：

- CPU affinity；
- 优先级；
- 迁移禁止；
- 最大响应时间；
- 独占核或 cpuset。

# 11. 工业级实际案例分析

## 11.1 案例一：Linux + Cortex-R 电机控制系统

### 需求

- Cortex-R 运行 20 kHz 电流环；
- Linux 运行配置、诊断和网络服务；
- Linux 不能阻塞实时控制；
- 过流和过温必须在本地快速关断；
- 支持运行时参数更新和故障上报。

### 架构

```
Linux Cortex-A
├── RPMsg Control Client
├── Event Client
└── Diagnostics
        |
Shared Memory + Mailbox
        |
Cortex-R
├── Real-Time Control Loop
├── Local Safety ISR
├── Command Queue
└── Fault Manager
```

### 设计要点

- Linux 只更新 shadow parameter。
- Cortex-R 在控制周期边界原子切换参数。
- 安全关断由本地 ISR、硬件比较器或 PWM 单元执行。
- 故障消息通过独立高优先级事件通道发送。
- Linux 复位不会影响 Cortex-R 的安全状态机。

### 参数切换代码

```
struct motor_params {
    int32_t target_rpm;
    int32_t current_limit;
    uint32_t mode;
};

struct motor_control {
    struct motor_params active;
    struct motor_params pending;
    atomic_uint pending_valid;
};

void update_motor_params(const struct motor_params *params)
{
    if (params == NULL)
        return;

    control->pending = *params;

    /*
     * 发布完整参数后再设置标志。
     */
    atomic_store_explicit(&control->pending_valid,
                          1,
                          memory_order_release);
}

void control_loop_20khz(void)
{
    if (atomic_exchange_explicit(&control->pending_valid,
                                 0,
                                 memory_order_acquire) != 0) {
        control->active = control->pending;
    }

    run_current_loop(&control->active);
}
```

## 11.2 案例二：多核网络设备的数据面与控制面分离

### 需求

- CPU0/CPU1 处理网络协议和控制面；
- CPU2/CPU3 处理高吞吐数据面；
- 网卡 DMA Ring 由专用核管理；
- 控制命令不能阻塞数据包转发；
- 支持 CPU 热插拔和负载迁移。

### 架构

```
CPU0：管理、配置、日志
CPU1：控制面协议
CPU2：RX 数据面
CPU3：TX 数据面
        |
DMA Ring + Per-CPU Queue
```

### 设计要点

- 每个数据核使用 per-CPU RX/TX 队列。
- 控制面通过无锁消息队列修改配置快照。
- 数据包处理避免访问全局锁。
- 配置更新采用 RCU，数据面读路径无锁。
- CPU 下线时先停止 DMA 投递，再迁移队列和中断。

### RCU 配置读取

```
struct route_table {
    uint32_t generation;
    struct route_entry entries[1024];
};

struct route_table __rcu *active_routes;

const struct route_entry *
lookup_route(uint32_t hash)
{
    struct route_table *table;
    const struct route_entry *entry;

    rcu_read_lock();

    table = rcu_dereference(active_routes);
    entry = &table->entries[hash % 1024];

    rcu_read_unlock();
    return entry;
}
```

实际使用中，返回指针不能在 `rcu_read_unlock()` 后继续使用，除非已经复制数据或持有其他有效引用。

## 11.3 案例三：车载 SoC 的大小核与安全域协同

### 需求

- 高性能 Cluster 运行 Linux；
- 高能效 Cluster 承担后台任务；
- Cortex-M/R 处理安全监控；
- 支持温度、电压和功耗约束；
- 高温时迁移普通负载，但不能迁移安全控制任务。

### 架构

```
Big Cluster
├── Linux foreground
└── High-performance compute

Little Cluster
├── Background tasks
└── Low-power services

Safety MCU
├── Watchdog
├── Power/thermal monitor
└── Emergency shutdown
```

### 设计要点

- HMP 调度器根据 CPU capacity 和温度选择核心。
- 安全任务固定在 Safety MCU，不允许迁移到 Linux 核。
- 电源状态由 SCMI/固件统一管理。
- 过温事件由安全 MCU直接触发降频或关断。
- Linux 只接收状态通知，不决定安全保护动作。

# 12. 高频问题深度答疑

## 问题一：多核越多，性能是否一定越高？

不是。性能受以下因素限制：

- 串行代码比例；
- 全局锁；
- Cache 一致性流量；
- 内存带宽；
- 调度和迁移开销；
- 任务粒度；
- 负载不均衡；
- 跨 Cluster 访问代价。

在共享状态高度集中的程序中，增加 CPU 反而可能因为 Cache Line 竞争导致性能下降。

## 问题二：SMP 和 AMP 如何选择？

选择逻辑：

- 任务之间共享大量数据，且实时性要求一般：SMP。
- 任务需要不同 OS、强隔离或严格实时：AMP。
- 既需要通用计算又需要硬实时控制：Linux + RTOS 的 AMP/HMP 混合架构。
- 安全任务、看门狗和紧急关断应放在独立安全核或硬件路径中。

## 问题三：原子变量能否替代锁？

不能完全替代。

原子变量适合：

- 单变量状态；
- 计数器；
- 标志；
- 简单引用计数；
- 无锁队列索引。

如果需要保持多个字段的一致性，通常仍需要锁、seqlock、RCU 或事务版本机制。

## 问题四：IPI 和 Mailbox 如何选择？

- Linux 内部同一 OS 的跨核唤醒：IPI。
- 跨处理器、跨 OS 或需要消息承载：Mailbox/RPMsg。
- IPI 不适合直接传复杂数据。
- Mailbox 也不应承担大数据；应配合共享内存和 DMA。

## 问题五：为什么跨核读写即使是 32 位也需要原子和屏障？

32 位读写可能天然对齐且单次完成，但仍存在：

- 编译器重排；
- CPU 内存访问重排；
- 发布顺序错误；
- 多字段状态不一致；
- Cache 可见性延迟；
- 读改写竞争。

因此“单次读写原子”不等于“完整同步正确”。

## 问题六：实时任务是否应该使用多核迁移？

通常需要谨慎。

迁移会带来：

- Cache 冷启动；
- TLB 失效；
- 调度延迟；
- 锁竞争；
- 中断亲和性变化；
- NUMA/Cluster 访问变化。

硬实时任务一般采用：

- 固定 CPU affinity；
- 独占核心；
- 本地数据结构；
- 禁止不必要迁移；
- 使用本地中断和本地队列。

## 问题七：如何避免跨核死锁？

建立全局锁顺序，例如：

```
CPU 状态锁
  <
电源域锁
  <
设备锁
  <
队列锁
```

并遵循：

- 锁内不执行远程 RPC；
- 锁内不等待其他 CPU；
- 不在回调中反向获取调用路径上的锁；
- 使用 lockdep 或静态分析检查；
- 对每把锁设置最大持有时间；
- 对跨核调用使用异步消息代替同步嵌套调用。

# 13. 课程核心总结

## 13.1 核心要点

1. **多核协同不仅是调度问题，也是通信、一致性、资源和故障问题。**
2. SMP 适合统一 OS 和共享地址空间；AMP 适合隔离和实时；HMP 适合性能功耗协同。
3. Cache 一致性不等于内存顺序，跨核发布必须使用原子操作和屏障。
4. IPI 适合跨核事件和唤醒，Mailbox/RPMsg 适合跨 OS 消息。
5. 实时闭环应留在实时核本地，不应依赖 Linux 调度或响应。
6. 高并发数据应优先采用 per-CPU、无锁 SPSC、RCU 和 DMA。
7. 全局锁、伪共享、频繁 IPI 和跨核迁移是常见性能瓶颈。
8. CPU hotplug 必须处理任务、中断、定时器、RCU、Cache 和电源状态。
9. 锁内执行远程调用是死锁和优先级反转的高风险模式。
10. 多核架构必须明确 CPU 所有权、资源所有权和故障恢复责任。
11. 工业级系统需要可量化的最坏延迟、锁等待、IPI 负载和恢复时间。

## 13.2 典型性能排序

```
本地寄存器/本地变量
    <
本地原子操作
    <
跨核共享变量
    <
Cache Line 转移
    <
跨核自旋锁
    <
IPI
    <
跨核线程唤醒
    <
Mailbox/RPMsg
    <
CPU 热启动和深度低功耗恢复
```

## 13.3 通用选型结论

- 同一 OS 内部同步：**原子操作、per-CPU、锁、RCU、IPI**。
- 跨 OS 控制消息：**RPMsg/Mailbox + 共享内存**。
- 大数据：**DMA + 共享内存描述符**。
- 硬实时闭环：**专用实时核本地执行**。
- CPU 启停：**PSCI/固件状态机**。
- 共享电源和时钟：**SCMI/平台管理固件**。
- 高并发读路径：**RCU 或无锁数据结构**。
- 高可靠安全功能：**独立安全核、硬件保护和本地故障路径**。
