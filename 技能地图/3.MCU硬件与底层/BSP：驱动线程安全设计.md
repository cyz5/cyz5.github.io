## 3. 技术概述

### 3.1 BSP 的定位

BSP 是把**具体板卡差异**封装起来的硬件适配层，通常包括：

```
Boot ROM
   ↓
启动文件 / 向量表 / 链接脚本
   ↓
芯片级支持包 CMSIS / SoC HAL
   ↓
BSP：时钟、PinMux、电源、板载器件、板级总线
   ↓
设备驱动：UART、SPI、I2C、ADC、Flash、Sensor
   ↓
OS 适配层 / 服务层
   ↓
应用
```

**BSP 不应承载业务逻辑，也不应把所有驱动代码写进 `main.c`。**

### 3.2 主流实现分支

|分支|典型实现|优势|风险|
|---|---|---|---|
|裸机 BSP|启动代码 + 外设驱动|延迟低、资源小|并发模型弱、扩展困难|
|RTOS BSP|驱动对象 + OS 原语|多任务、模块化|锁和优先级问题|
|Linux BSP|Boot、Device Tree、驱动、rootfs|生态完整|启动和资源开销较大|
|厂商 HAL BSP|SDK/HAL + 板级初始化|开发快|HAL 隐藏时序和错误|
|自研寄存器 BSP|直接寄存器控制|可控、性能稳定|维护成本高|

## 4. 核心特性横向对比

|机制|可用于 ISR|是否阻塞|适合保护|典型延迟|主要风险|
|---|---|---|---|---|---|
|临界区|是，但应极短|否|极短共享数据|数十 ns～数 µs|拉长中断关闭时间|
|自旋锁|视 RTOS 实现|通常不睡眠|SMP/极短临界区|低～中|单核上忙等浪费 CPU|
|互斥锁|否|是|设备寄存器和状态|1～数十 µs|死锁、优先级反转|
|二进制信号量|ISR 可释放|是|ISR 通知任务|2～数十 µs|不表达所有权|
|计数信号量|ISR 可释放|是|资源计数、事件累计|2～数十 µs|计数溢出/语义混乱|
|事件组|通常 ISR 仅置位|是|多条件同步|数 µs～数十 µs|位定义失控|
|原子操作|是|否|标志、计数器、状态|1～数十 ns|不能保护复合事务|
|环形缓冲区|ISR/任务均可|否|单生产者单消费者|O(1)|多生产者需额外同步|

## 5. 底层原理与功能特性深度解析

### 5.1 BSP 分层与设备对象

推荐将“硬件资源”“设备状态”“同步对象”“操作接口”集中到实例对象中，而不是使用大量全局变量。

```
#include <stdint.h>
#include <stdbool.h>
#include "FreeRTOS.h"
#include "semphr.h"
#include "task.h"

typedef enum {
    DEV_CLOSED = 0,
    DEV_READY,
    DEV_ERROR
} dev_state_t;

typedef struct {
    uint32_t base;
    uint8_t  irq;
    uint8_t  instance;
    dev_state_t state;
    SemaphoreHandle_t lock;       /* 保护寄存器和软件状态 */
    SemaphoreHandle_t tx_done;    /* ISR -> 任务 */
    TaskHandle_t owner;           /* 可选：记录当前调试上下文 */
} uart_dev_t;

static uart_dev_t g_uart1;

static bool uart_valid(const uart_dev_t *d)
{
    return d != NULL && d->lock != NULL && d->tx_done != NULL &&
           d->state == DEV_READY;
}

int uart_write(uart_dev_t *d, const uint8_t *buf, size_t len,
               TickType_t timeout)
{
    if (!uart_valid(d) || buf == NULL || len == 0U) {
        return -1;
    }
    if (xSemaphoreTake(d->lock, timeout) != pdTRUE) {
        return -2; /* 明确区分资源超时 */
    }

    d->owner = xTaskGetCurrentTaskHandle();
    /* 配置 DMA/FIFO；不得在锁内执行不可控的长时间等待 */
    bool started = uart_start_tx_dma(d->base, buf, len);
    if (!started) {
        d->owner = NULL;
        xSemaphoreGive(d->lock);
        return -3;
    }

    BaseType_t ok = xSemaphoreTake(d->tx_done, timeout);
    if (ok != pdTRUE) {
        uart_abort_tx(d->base);
        d->state = DEV_ERROR;
        d->owner = NULL;
        xSemaphoreGive(d->lock);
        return -4;
    }
    d->owner = NULL;
    xSemaphoreGive(d->lock);
    return 0;
}

void UART1_IRQHandler(void)
{
    BaseType_t higher = pdFALSE;
    if (uart_irq_tx_done(g_uart1.base)) {
        uart_clear_irq(g_uart1.base);
        xSemaphoreGiveFromISR(g_uart1.tx_done, &higher);
    }
    portYIELD_FROM_ISR(higher);
}
```

**注意：** `volatile` 只能保证编译器每次访问内存，不保证复合操作原子性，也不替代互斥锁或内存屏障。

### 5.2 线程安全的三个层次

1. **可重入**：函数不依赖可变共享状态，或状态由调用者提供。
2. **线程安全**：共享状态由正确同步机制保护。
3. **时序安全**：不仅数据正确，而且设备状态转换、超时和 DMA 生命周期正确。

例如，以下代码不是线程安全的：

```
/* 错误：两个任务可能同时修改同一个静态发送缓冲区 */
static uint8_t tx_buf[256];
void log_write(const char *s)
{
    strcpy((char *)tx_buf, s);
    uart_send(tx_buf, strlen((char *)tx_buf));
}
```

应改为调用者缓冲区、实例私有缓冲区加锁，或使用消息队列把数据复制到专属日志任务。

### 5.3 ISR 与任务同步

ISR 只做三件事：**读取/清除硬件状态、保存最小必要数据、通知任务**。不得在 ISR 中申请互斥锁、打印日志、执行阻塞 API 或进行复杂协议解析。

### 5.4 DMA、Cache 与内存生命周期

DMA 访问的是物理内存，而 CPU 可能访问 Cache。非一致性 Cache 平台必须执行：

```
/* 伪代码：发送前清 Cache，接收后失效 Cache */
cache_clean_by_addr(tx_buf, len);
dma_start_tx(tx_buf, len);

wait_dma_done();
cache_invalidate_by_addr(rx_buf, len);
```

同时必须保证 DMA 完成前缓冲区仍然有效；禁止把栈上临时数组交给异步 DMA。

## 6. 性能量化分析

以下为典型 Cortex-M7@400 MHz、FreeRTOS、D-Cache 开启平台的工程基线示例，实际值需以目标板实测为准。

|项目|典型值|
|---|---|
|互斥锁无竞争获取/释放|0.8～2.5 µs|
|互斥锁竞争切换|3～15 µs|
|ISR 置位信号量并唤醒高优先级任务|2～8 µs|
|临界区进入/退出|50～180 ns|
|任务栈基础占用|512～2048 B|
|驱动对象及同步对象|100～500 B/实例|
|256 字节 DMA 传输 CPU 参与时间|通常 < 5 µs|

基本公式：

```
锁占用率 = 锁持有总时间 / 测量窗口时间
最坏响应时间 R = C + B + Σ((R/Ti) × Ci)
```

其中 `C` 为本任务执行时间，`B` 为阻塞时间，`Ci/Ti` 为高优先级任务干扰。

优化顺序：

1. 把等待 DMA、FIFO 空闲、总线完成等操作移出锁。
2. 从“每字节锁”改为“每事务锁”。
3. 使用 DMA 和消息队列降低 CPU 介入。
4. 对 SPSC 数据流使用无锁环形缓冲区。
5. 采集锁持有时间、最大阻塞时间和调度延迟，而非只测平均值。

## 7. 应用场景选型指南

```
是否涉及多个任务访问同一硬件？
├─ 否 → 无锁或局部临界区
└─ 是
   ├─ 是否需要设备所有权和优先级继承？
   │  ├─ 是 → 互斥锁
   │  └─ 否
   ├─ 是否为 ISR 通知任务？
   │  ├─ 是 → ISR-safe 信号量/任务通知
   │  └─ 否
   ├─ 是否需要缓存多个事件？
   │  ├─ 是 → 计数信号量/消息队列
   │  └─ 否 → 二进制信号量/事件组
```

|场景|方案|理由|
|---|---|---|
|多任务共享 SPI 总线|总线互斥锁 + 事务接口|保证片选、配置和传输原子性|
|UART 接收中断|ISR 写环形队列，任务解析|缩短 ISR，避免丢字节|
|I2C 设备访问|总线锁 + 超时 + 总线恢复|I2C 可能被从设备拉死|
|高速采样|DMA 双缓冲 + 任务通知|降低 CPU 和锁开销|
|日志输出|多生产者队列 + 单消费者 UART 任务|消除并发输出交错|

## 8. 工程最佳实践

### 8.1 设计原则

- **一个硬件资源一个仲裁点**：SPI 总线锁不能只保护某个设备。
- 锁保护的是完整事务，而不是单次寄存器写。
- 所有可能阻塞的 API 必须带超时；禁止无限等待。
- ISR、任务、初始化和错误恢复使用不同 API 契约。
- 驱动状态机必须显式建模：`RESETTING/READY/BUSY/ERROR/RECOVERING`。
- 对每个驱动定义锁顺序，例如：`电源锁 → 总线锁 → 设备锁`。

### 8.2 选型决策矩阵

|条件|首选|
|---|---|
|共享硬件且有所有权概念|互斥锁|
|单生产者单消费者|无锁环形缓冲区|
|ISR 唤醒一个任务|直接任务通知|
|多个条件组合|事件组|
|固定数量资源|计数信号量|
|跨核共享|原子变量 + 内存屏障/自旋锁|

### 8.3 编码规范

- 使用 `enum` 表示状态和错误码，禁止用魔数。
- 驱动入口统一检查参数、状态、上下文和超时。
- 锁获取失败必须记录原因和统计计数。
- 不在锁内调用未知回调，避免回调重入和锁环。
- 用静态分析检查 ISR API、栈使用、整数溢出和空指针。

## 9. 常见错误与避坑指南

### 错误一：ISR 中获取互斥锁

```
void SPI_IRQHandler(void)
{
    xSemaphoreTake(spi_mutex, portMAX_DELAY); /* 错误 */
}
```

根因：ISR 无法阻塞，且可能打断持锁任务。正确实现是 ISR 清状态并发送任务通知。风险是系统崩溃、死锁或实时性失控。

### 错误二：只保护数据，不保护设备事务

```
lock();
spi_write_reg(REG, value);
unlock();
spi_read_status(); /* 锁外，可能被其他任务改变片选/配置 */
```

正确做法是把“选片—配置—传输—读状态—释放片选”作为一个事务整体保护。否则会产生设备状态错乱。

### 错误三：锁顺序不一致

```
TaskA: take(bus_lock); take(dev_lock);
TaskB: take(dev_lock); take(bus_lock); /* 锁死 */
```

统一全局锁顺序，或使用单一设备服务任务串行化访问。

### 错误四：DMA 使用栈变量

```
void send(void)
{
    uint8_t tmp[64];
    dma_start(tmp, sizeof(tmp)); /* 函数返回后 DMA 仍在访问 */
}
```

正确做法是使用静态、专属或内存池缓冲区，并以 DMA 完成事件作为生命周期结束标志。风险包括数据损坏、HardFault 和偶发现场问题。

### 错误五：用 `volatile` 代替同步

```
volatile uint32_t count;
count++; /* 读-改-写仍可能丢失更新 */
```

使用原子加、临界区或锁。`volatile` 不能提供互斥和跨核内存可见性。

## 10. 多机制组合使用方案

推荐的高速串口架构：

```
ISR ──> DMA 半满/完成 ──> 无锁环形缓冲区 ──> RX 任务
TX 生产者 ──> 消息队列 ──> TX 任务 ──> DMA
                         ↑
                  设备互斥锁/状态机
```

```
typedef struct {
    const uint8_t *data;
    size_t len;
} tx_msg_t;

static QueueHandle_t tx_queue;
static SemaphoreHandle_t uart_lock;

int uart_async_send(const uint8_t *data, size_t len, TickType_t to)
{
    if (!data || len == 0U || len > UART_MAX_TX) return -1;
    tx_msg_t msg = { data, len };
    return xQueueSend(tx_queue, &msg, to) == pdTRUE ? 0 : -2;
}

static void uart_tx_task(void *arg)
{
    tx_msg_t msg;
    for (;;) {
        if (xQueueReceive(tx_queue, &msg, portMAX_DELAY) != pdTRUE) continue;
        if (xSemaphoreTake(uart_lock, pdMS_TO_TICKS(100)) != pdTRUE) continue;
        /* 生产实现应复制到 DMA 所有权缓冲区，避免调用者提前释放 */
        if (!uart_dma_send_owned(msg.data, msg.len, pdMS_TO_TICKS(100))) {
            uart_recover();
        }
        xSemaphoreGive(uart_lock);
    }
}
```

关键点：队列只传递指针时，必须明确**所有权、生命周期和释放责任**；否则应传递数据副本或使用引用计数内存池。

## 11. 工业级实际案例分析

### 案例一：多传感器共享 SPI

**需求：** 4 个传感器、3 个任务访问同一 SPI，总线速率 20 MHz，要求单次事务超时小于 2 ms。

**架构：** SPI 总线互斥锁 + 每设备配置缓存 + 事务超时 + 错误后重新初始化。

**设计要点：** 锁覆盖片选和完整事务；禁止设备驱动直接修改全局 SPI 配置；超时后释放片选并恢复总线。

### 案例二：工业网关 UART 高速接收

**需求：** 921600 bps，突发 4 KB，不能因协议解析阻塞接收。

**架构：** DMA 环形接收 + 空闲线中断 + SPSC 环形缓冲区 + 协议解析任务。

**设计要点：** 接收 ISR 只计算 DMA 写指针并通知任务；解析任务按帧校验和长度处理；溢出时记录计数并丢弃当前帧，而不是覆盖未知数据。

### 案例三：掉电保护 Flash 驱动

**需求：** 多任务提交参数，掉电时保证最后一个已确认版本可恢复。

**架构：** 参数服务任务串行化写入，Flash 锁保护擦写，双区日志 + CRC + 序号提交。

```
写数据 → 写 CRC → 写序号/提交标志 → 校验回读
恢复时扫描两个区 → 选择 CRC 正确且序号最大的记录
```

**设计要点：** Flash 擦写期间禁止直接持有锁等待整个擦除；可由服务任务管理状态，并让其他调用者获得明确的忙状态或超时错误。

## 12. 高频问题深度答疑

### 1. 互斥锁和二进制信号量有什么本质区别？

互斥锁表达**所有权**，通常支持优先级继承；二进制信号量表达**事件或资源令牌**，不应用于递归释放或所有权管理。保护共享设备优先用互斥锁，ISR 通知任务用信号量或任务通知。

### 2. 为什么锁内等待 DMA 会导致实时性差？

DMA 等待时间受总线竞争、设备响应和异常状态影响，属于不可控延迟。其他高优先级任务会被阻塞，低优先级持锁任务还可能引发优先级反转。应采用“启动事务—释放/分离锁—完成通知—状态收敛”的架构，或让专属驱动任务独占设备。

### 3. 单核 MCU 还需要内存屏障吗？

需要考虑编译器重排、写缓冲、DMA 和 Cache。普通任务间依靠 RTOS 同步原语通常已包含必要屏障；ISR/DMA 共享数据、设备寄存器和 Cache 管理则必须遵循架构屏障和 Cache 维护要求。

### 4. 什么时候用临界区而不用锁？

只保护几条指令、且临界区上界可证明很短时使用临界区。若包含循环、总线访问、日志、等待或函数回调，不应关闭中断。

### 5. 驱动是否应允许多个任务同时打开？

应区分“打开句柄”和“硬件所有权”。可以允许多个逻辑句柄，但对独占资源、配置修改和异步 DMA 必须建立明确的仲裁策略；不能简单依赖全局布尔变量。

### 6. 线程安全是否意味着一定高性能？

不是。粗粒度锁易实现但并发度低；细粒度锁提高并行度却增加锁顺序和死锁复杂度。嵌入式系统通常优先选择**可证明的粗粒度事务锁**，再用队列、DMA和专属任务优化吞吐。

## 13. 课程核心总结

- **BSP 负责板级差异，驱动负责设备抽象，业务不得下沉到硬件层。**
- 线程安全必须同时覆盖数据、设备状态和时序。
- ISR 只做最小工作；阻塞、解析和恢复交给任务。
- 共享总线保护的是完整事务，不是单个寄存器访问。
- DMA 设计必须同时考虑 Cache、一致性和缓冲区生命周期。
- 性能排序通常为：原子/无锁结构 > 短临界区 > 无竞争互斥锁 > 竞争锁 > 锁内同步等待。
- 通用结论：**低并发、强确定性优先事务锁；高吞吐优先 DMA+队列；ISR 通知优先任务通知；复杂设备优先专属服务任务。**

## 16. 实践与进阶路径

### 梯度实战任务

1. **基础工程：** 为 UART 建立 BSP 初始化、阻塞收发和错误码体系。
2. **并发改造：** 增加 DMA、任务通知、接收环形缓冲区和超时恢复。
3. **总线工程：** 实现多设备 SPI 总线锁、锁顺序检查和事务统计。
4. **可靠性工程：** 注入 ISR 丢包、DMA 超时、I2C SDA 被拉低、Flash 掉电。
5. **性能工程：** 采集 P50/P95/P99 延迟、最大锁占用、CPU 占用和栈余量。

### 性能测试方法

- 使用 GPIO 打点测量 ISR 入口到任务响应的延迟。
- 使用 DWT Cycle Counter 测量锁、寄存器访问和 DMA 回调耗时。
- 记录最坏值，不只看平均值。
- 用高优先级周期任务、突发总线流量和随机超时构造压力场景。
- 在 CI 中执行静态检查、竞态测试、接口契约测试和故障恢复测试。

### 进阶方向

- 设备树与 Linux platform driver 的 BSP 迁移。
- 多核 AMP/SMP 下的共享内存、IPI 和缓存一致性。
- MPU 隔离、驱动沙箱和安全启动。
- 形式化状态机验证、模型检测和实时调度分析。
- 面向可观测性的驱动指标、trace 事件和现场诊断数据设计。

**最终工程判断标准：一个驱动不仅要“正常路径能工作”，还必须能在并发、超时、复位、DMA异常、总线卡死和掉电恢复条件下给出确定、可观测且可恢复的行为。**
