## 3. 技术概述

## 3.1 存储介质分类

嵌入式系统中的存储介质可按以下维度分类：

|介质|典型接口|擦除粒度|编程粒度|是否需要 FTL|典型用途|
|---|---|---|---|---|---|
|NOR Flash|SPI/QSPI/OSPI|4 KB～256 KB|1～256 B|通常不需要|Bootloader、参数、代码、少量日志|
|SLC NAND|SPI NAND、Raw NAND|128 KB～4 MB|2～16 KB|Raw NAND 通常需要上层管理|大容量数据、日志、镜像|
|eMMC|MMC/SDIO|内部管理|512 B 逻辑扇区|内置|Linux 根文件系统、升级包|
|SD 卡|SDMMC/SPI|内部管理|512 B 逻辑扇区|内置|可移动媒体、数据导出|
|EEPROM|I²C/SPI|页或字节|1～页|不需要|小容量参数、校准值|
|FRAM|I²C/SPI|无需擦除|字节级|不需要|高频更新计数器、关键状态|
|SRAM|并行/片上|无|字节级|不需要|RAM Disk、缓存、临时文件|
|UFS|M-PHY|内部管理|逻辑块|内置|高端 Linux、工业计算平台|

## 3.3 Block 设备与 MTD 设备

### Block 设备

Block 设备向上提供固定大小逻辑块，通常为 512 B 或 4 KB。

特点：

- 支持逻辑块读写。
- 设备内部可能隐藏物理擦除、坏块和磨损均衡。
- 常见于 SD、eMMC、SSD。
- 上层通常使用 FAT、ext4、LittleFS Block Backend 等。

### MTD 设备

MTD，Memory Technology Device，直接暴露 Flash 的物理约束：

- 读取粒度通常较小。
- 编程只能将 bit 从 `1` 写为 `0`。
- 擦除后才能将 bit 从 `0` 恢复为 `1`。
- 擦除粒度远大于写入粒度。
- 需要处理坏块、ECC、擦写寿命和掉电一致性。

## 5. 底层原理与功能特性深度解析

## 5.1 NOR Flash 的写入约束

NOR Flash 的基本状态转换：

```
擦除：
0 → 1

编程：
1 → 0

错误操作：
0 → 1，必须先擦除
```

因此不能直接用普通内存语义覆盖写入：

```
/* 错误：不能保证覆盖写入 */
flash_write(addr, &new_value, sizeof(new_value));
```

生产级写入通常需要：

1. 读取原扇区。
2. 判断目标 bit 是否存在 `0 → 1`。
3. 若不存在，直接编程。
4. 若存在，执行整扇区擦除。
5. 修改内存副本。
6. 写回整个扇区。
7. 进行 CRC 校验和提交标志写入。

```
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define FLASH_SECTOR_SIZE 4096U

typedef enum {
    FLASH_OK = 0,
    FLASH_ERR_PARAM = -1,
    FLASH_ERR_IO = -2,
    FLASH_ERR_VERIFY = -3
} flash_status_t;

static int flash_read(uint32_t addr, void *buf, size_t len);
static int flash_program(uint32_t addr, const void *buf, size_t len);
static int flash_erase_sector(uint32_t addr);
static uint32_t crc32(const void *data, size_t len);

flash_status_t flash_update(uint32_t addr,
                            const void *data,
                            size_t len)
{
    if (data == NULL || len == 0U ||
        len > FLASH_SECTOR_SIZE ||
        (addr % FLASH_SECTOR_SIZE) + len > FLASH_SECTOR_SIZE) {
        return FLASH_ERR_PARAM;
    }

    uint8_t sector[FLASH_SECTOR_SIZE];

    if (flash_read(addr - (addr % FLASH_SECTOR_SIZE),
                   sector,
                   sizeof(sector)) != 0) {
        return FLASH_ERR_IO;
    }

    uint32_t offset = addr % FLASH_SECTOR_SIZE;
    bool need_erase = false;

    for (size_t i = 0; i < len; ++i) {
        uint8_t oldv = sector[offset + i];
        uint8_t newv = ((const uint8_t *)data)[i];

        /*
         * 若存在 old=0、new=1，则必须擦除。
         */
        if ((uint8_t)(~oldv & newv) != 0U) {
            need_erase = true;
        }
    }

    if (!need_erase) {
        if (flash_program(addr, data, len) != 0) {
            return FLASH_ERR_IO;
        }
    } else {
        memcpy(&sector[offset], data, len);

        uint32_t sector_addr = addr - (addr % FLASH_SECTOR_SIZE);

        if (flash_erase_sector(sector_addr) != 0) {
            return FLASH_ERR_IO;
        }

        if (flash_program(sector_addr,
                          sector,
                          sizeof(sector)) != 0) {
            return FLASH_ERR_IO;
        }
    }

    uint8_t verify[FLASH_SECTOR_SIZE];

    if (flash_read(addr, verify, len) != 0 ||
        memcmp(verify, data, len) != 0) {
        return FLASH_ERR_VERIFY;
    }

    return FLASH_OK;
}
```

### 工程风险

- 栈空间不足：4 KB 临时缓冲区不能无条件放在任务栈。
- 擦除期间长时间阻塞：典型 4 KB 擦除可能为 20～200 ms。
- 断电导致扇区内容处于不确定状态。
- 多任务并发更新导致数据覆盖，必须使用存储锁。

## 5.2 双槽提交实现掉电一致性

对配置、校准值、启动参数等关键数据，不应直接覆盖单份文件。推荐双槽或日志记录方案：

```
Slot A: magic | version | length | payload | crc | commit
Slot B: magic | version | length | payload | crc | commit

启动时：
1. 检查 magic
2. 检查 length
3. 检查 CRC
4. 检查 commit 标志
5. 选择 version 最大且有效的槽
```

```
#define RECORD_MAGIC 0x53434647U /* "SCFG" */
#define COMMIT_DONE  0xA5A5A5A5U

typedef struct {
    uint32_t magic;
    uint32_t version;
    uint32_t length;
    uint32_t crc;
    uint32_t commit;
} record_header_t;

typedef struct {
    uint32_t sample_rate;
    uint32_t device_id;
    int32_t  calibration_offset;
} device_config_t;

static bool config_record_valid(const uint8_t *raw,
                                size_t area_size,
                                record_header_t *hdr_out)
{
    if (raw == NULL || area_size < sizeof(record_header_t)) {
        return false;
    }

    record_header_t hdr;
    memcpy(&hdr, raw, sizeof(hdr));

    if (hdr.magic != RECORD_MAGIC ||
        hdr.commit != COMMIT_DONE ||
        hdr.length != sizeof(device_config_t) ||
        sizeof(record_header_t) + hdr.length > area_size) {
        return false;
    }

    const uint8_t *payload = raw + sizeof(record_header_t);

    if (crc32(payload, hdr.length) != hdr.crc) {
        return false;
    }

    if (hdr_out != NULL) {
        *hdr_out = hdr;
    }

    return true;
}
```

### 提交顺序

正确顺序：

```
1. 擦除目标槽
2. 写入 header，但 commit 保持擦除态
3. 写入 payload
4. 读取校验 payload
5. 最后单独写入 commit 标志
```

不能先写 `commit`，否则掉电时可能出现“看似有效、实际数据不完整”的记录。

## 5.3 NAND Flash、ECC 与坏块管理

NAND 的可靠性问题主要包括：

- 出厂坏块。
- 使用过程中新增坏块。
- Read disturb。
- Program disturb。
- 位翻转。
- 写入失败。
- 擦除失败。
- ECC 可纠正位数超过上限。

典型数据路径：

```
应用数据
  ↓
文件系统
  ↓
UBI / YAFFS / NAND FTL
  ↓
ECC 编码
  ↓
NAND 控制器
  ↓
Flash Cell
```

读取时：

```
Flash Cell
  ↓
NAND 控制器读取
  ↓
ECC 解码与纠错
  ↓
返回数据 + 纠错计数
```

工程上必须记录：

- 每块 ECC correction count。
- 不可纠正错误次数。
- 擦除失败次数。
- 重新映射次数。
- 坏块增长趋势。

不要将 Raw NAND 直接当成普通数组使用：

```
/* 错误：跳过坏块、ECC 和擦除约束 */
raw_nand_write(physical_address, buf, len);
```

## 5.4 FTL 与 eMMC/SD 的隐藏行为

eMMC 和 SD 卡内部通常包含：

```
逻辑块地址
  ↓
FTL 映射表
  ↓
磨损均衡
  ↓
坏块重映射
  ↓
ECC
  ↓
NAND Flash
```

因此：

- 主机看到的是逻辑扇区，不是物理块。
- 覆盖写可能触发内部读-改-写。
- 小块随机写会增加内部写放大。
- `fsync()` 只表示主机向设备提交了同步请求，具体持久化语义取决于控制器和介质。
- 断电时可能出现映射表更新和数据更新不同步。

### 建议

- 使用 4 KB 或更大对齐的写入。
- 对日志采用顺序追加。
- 对大文件预分配。
- 避免频繁更新 FAT 目录项。
- 升级数据与运行日志分区隔离。
- 对关键数据使用双副本和版本号。
- 量产设备优先选择工业级 eMMC/SD，并验证掉电行为。

## 5.5 文件系统挂载流程

通用挂载流程：

```
检测设备
  ↓
读取识别信息
  ↓
验证分区表
  ↓
识别文件系统
  ↓
执行 mount
  ↓
校验关键目录
  ↓
加载元数据
  ↓
发布存储就绪事件
```

工程代码应区分：

- 设备不存在。
- 设备存在但未格式化。
- 文件系统损坏。
- 挂载超时。
- 介质只读。
- 容量不足。
- 文件系统版本不兼容。

```
typedef enum {
    STORAGE_MOUNT_OK = 0,
    STORAGE_MOUNT_NO_DEVICE,
    STORAGE_MOUNT_UNFORMATTED,
    STORAGE_MOUNT_CORRUPTED,
    STORAGE_MOUNT_READONLY,
    STORAGE_MOUNT_TIMEOUT,
    STORAGE_MOUNT_FAILED
} storage_mount_result_t;

storage_mount_result_t storage_mount_with_recovery(void)
{
    if (!blockdev_present()) {
        return STORAGE_MOUNT_NO_DEVICE;
    }

    if (fs_mount("/data") == 0) {
        if (fs_check_required_dirs("/data") != 0) {
            return STORAGE_MOUNT_CORRUPTED;
        }
        return STORAGE_MOUNT_OK;
    }

    if (fs_is_unformatted()) {
        /*
         * 生产系统中不能无条件格式化，必须满足：
         * 1. 用户明确允许；
         * 2. 数据确实不需要保留；
         * 3. 设备处于恢复模式；
         */
        if (recovery_format_allowed()) {
            if (fs_format("/data") == 0 &&
                fs_mount("/data") == 0) {
                return STORAGE_MOUNT_OK;
            }
        }

        return STORAGE_MOUNT_UNFORMATTED;
    }

    if (fs_is_readonly()) {
        return STORAGE_MOUNT_READONLY;
    }

    if (fs_repair() == 0 && fs_mount("/data") == 0) {
        return STORAGE_MOUNT_OK;
    }

    return STORAGE_MOUNT_FAILED;
}
```

## 5.6 多介质统一抽象

推荐定义统一的存储设备描述：

```
typedef enum {
    STORAGE_MEDIA_NOR,
    STORAGE_MEDIA_SPI_NAND,
    STORAGE_MEDIA_EMMC,
    STORAGE_MEDIA_SD,
    STORAGE_MEDIA_FRAM,
    STORAGE_MEDIA_RAM
} storage_media_type_t;

typedef enum {
    STORAGE_CAP_CONFIG      = 1U << 0,
    STORAGE_CAP_LOG         = 1U << 1,
    STORAGE_CAP_UPDATE      = 1U << 2,
    STORAGE_CAP_MEDIA       = 1U << 3,
    STORAGE_CAP_REMOVABLE   = 1U << 4,
    STORAGE_CAP_HOTPLUG     = 1U << 5
} storage_capability_t;

typedef struct storage_device storage_device_t;

typedef struct {
    int (*read)(storage_device_t *dev,
                uint64_t offset,
                void *buf,
                size_t len);

    int (*write)(storage_device_t *dev,
                 uint64_t offset,
                 const void *buf,
                 size_t len);

    int (*erase)(storage_device_t *dev,
                 uint64_t offset,
                 size_t len);

    int (*sync)(storage_device_t *dev);
    int (*ioctl)(storage_device_t *dev, uint32_t cmd, void *arg);
} storage_ops_t;

struct storage_device {
    const char *name;
    storage_media_type_t type;
    uint32_t capabilities;
    uint32_t block_size;
    uint64_t capacity;
    bool present;
    bool readonly;
    const storage_ops_t *ops;
    void *private_data;
};
```

上层不应直接判断具体硬件型号，而应面向能力：

```
storage_device_t *storage_select(uint32_t required_caps,
                                 uint64_t min_capacity,
                                 bool removable_allowed);
```

例如：

```
配置：
  required_caps = STORAGE_CAP_CONFIG
  removable_allowed = false

用户媒体：
  required_caps = STORAGE_CAP_MEDIA
  removable_allowed = true

升级镜像：
  required_caps = STORAGE_CAP_UPDATE
  min_capacity = image_size * 2
```

## 6.2 写放大

写放大定义：

WA=BytesphysicalByteshostWA=Byteshost​Bytesphysical​​

例如，应用每次写入 100 B，但文件系统需要更新：

- 4 KB 数据块；
- 4 KB 元数据块；
- 4 KB 日志块；
- 4 KB 垃圾回收搬移块。

则物理写入约为：

Bytesphysical=16KBBytesphysical​=16KBWA=16KB100B≈163.84WA=100B16KB​≈163.84

这会显著降低 NOR、NAND 和 SD 卡寿命。

### 优化方式

- 采用批量写入。
- 使用顺序日志代替随机覆盖。
- 参数变化后延迟合并提交。
- 预分配文件。
- 采用固定大小记录。
- 将高频计数器放到 FRAM。
- 使用独立日志分区，避免污染主文件系统。

## 6.3 寿命估算

对于 NOR Flash：

Life=Nerase×BlockSizeDailyWriteLife=DailyWriteNerase​×BlockSize​

假设：

- 单块寿命：100,000 次擦除；
- 擦除块大小：4 KB；
- 每天写入：1 MB；
- 没有磨损均衡。

Life=100000×40961024×1024≈390.6 daysLife=1024×1024100000×4096​≈390.6 days

如果使用 64 个块进行均匀磨损：

Life≈390.6×64≈25,000 daysLife≈390.6×64≈25,000 days

理论上约 68 年，但实际还要考虑：

- 温度降额。
- 文件系统元数据额外写入。
- 写放大。
- 局部热点。
- 擦除失败。
- 数据保持时间。

更合理的估算为：

其中 `Derating` 可按 1.5～3 估算。

## 8. 工程最佳实践

## 8.1 设计原则

### 原则一：按数据属性分区，而不是按硬件介质分区

推荐：

```
Boot Partition
  ├── bootloader_a
  ├── bootloader_b
  └── boot_metadata

Config Partition
  ├── device_config
  ├── calibration
  └── factory_data

Log Partition
  ├── runtime_log
  └── crash_dump

Update Partition
  ├── image_a
  ├── image_b
  └── update_state

User Data Partition
  └── media files
```

### 原则二：高频小写与大文件顺序写必须隔离

不能将以下数据放在同一文件系统中：

- 每秒更新的运行状态。
- 数 GB 的升级包。
- 用户媒体文件。
- 系统配置文件。

因为它们会产生完全不同的元数据和写入模式。

### 原则三：存储锁必须统一

```
static SemaphoreHandle_t g_storage_mutex;

int storage_safe_write(const char *path,
                       const void *data,
                       size_t len)
{
    if (path == NULL || data == NULL || len == 0U) {
        return -1;
    }

    if (xSemaphoreTake(g_storage_mutex,
                       pdMS_TO_TICKS(5000)) != pdTRUE) {
        return -2;
    }

    int ret = fs_write_file_atomic(path, data, len);

    xSemaphoreGive(g_storage_mutex);
    return ret;
}
```

不要允许每个业务模块自行创建文件系统锁，否则容易形成锁顺序反转。

### 原则四：所有关键写入都必须有可验证提交点

关键记录应包含：

- Magic。
- 版本号。
- 长度。
- CRC。
- 序列号。
- 提交标志。
- 可选的时间戳。
- 可选的签名或认证标签。

### 原则五：不要在实时路径中执行不可预测的擦除或垃圾回收

错误设计：

```
void control_loop_task(void *arg)
{
    for (;;) {
        control_step();

        /* 可能触发 100 ms 擦除或垃圾回收 */
        log_append("/data/log.bin", sample, sizeof(sample));

        vTaskDelay(pdMS_TO_TICKS(1));
    }
}
```

正确设计：

```
控制任务
  ↓ 非阻塞发送
内存日志队列
  ↓
低优先级存储任务
  ↓ 批量顺序写入
Flash/SD
```

## 8.2 选型决策矩阵

评分范围：1～5 分。

|方案|掉电可靠性|PC 兼容性|高频小写|大容量|实时性|开发复杂度|
|---|---|---|---|---|---|---|
|NOR + LittleFS|5|1|4|2|4|3|
|NOR + FATFS|2|3|1|2|2|2|
|SD + FATFS|3|5|2|5|2|2|
|eMMC + FATFS|4|4|3|5|3|3|
|NAND + UBIFS|5|1|4|5|3|5|
|FRAM + KV|5|1|5|1|5|2|
|RAM Disk|1|1|5|2|5|1|

## 8.3 工业级编码规范

- 所有路径长度、文件名长度和目录深度必须有限制。
- 所有 `open`、`read`、`write`、`sync`、`close` 返回值必须检查。
- 写入后不默认认为数据已持久化，关键数据必须 `fsync` 或调用介质同步接口。
- 禁止在中断服务函数中访问文件系统。
- 禁止在持有存储锁时调用可能阻塞数百毫秒的外部服务。
- 文件名使用 ASCII 或统一 UTF-8 策略，避免跨平台编码问题。
- 对外部 SD 卡文件必须进行大小、格式和签名校验。
- 文件删除采用“先关闭、再校验、后删除”的流程。
- 对所有文件操作增加超时、重试次数和错误统计。
- 文件系统错误码必须转换为系统级诊断码，不能直接丢弃。

## 9. 常见错误与避坑指南

## 9.1 错误一：直接覆盖 NOR Flash

### 错误代码

```
uint32_t value = 0x12345678;
flash_program(CONFIG_ADDR, &value, sizeof(value));
```

### 根因

新数据可能需要将某些 bit 从 `0` 改为 `1`，而 NOR 编程只能执行 `1 → 0`。

### 正确实现

使用扇区读-改-擦-写，或使用双槽日志记录。

### 风险影响

- 配置数据损坏。
- 部分字段更新、部分字段未更新。
- 设备重启后进入默认配置。
- 现场表现为偶发且难以复现。

---

## 9.2 错误二：高频调用 `fsync`

### 错误代码

```
for (uint32_t i = 0; i < 1000; ++i) {
    fs_write(fd, &sample, sizeof(sample));
    fsync(fd);
}
```

### 根因

每条记录都触发文件系统元数据提交和底层设备同步，导致：

- 写放大。
- 延迟抖动。
- SD 卡内部垃圾回收频繁触发。
- 文件系统寿命下降。

### 正确实现

内存队列聚合后批量写入：

```
#define LOG_BATCH_SIZE 4096U

static uint8_t log_batch[LOG_BATCH_SIZE];
static size_t log_batch_used;

int log_append_batch(int fd, const void *data, size_t len)
{
    if (data == NULL || len == 0U ||
        len > LOG_BATCH_SIZE - log_batch_used) {
        return -1;
    }

    memcpy(&log_batch[log_batch_used], data, len);
    log_batch_used += len;

    if (log_batch_used == LOG_BATCH_SIZE) {
        if (fs_write(fd, log_batch, log_batch_used) !=
            (int)log_batch_used) {
            return -2;
        }

        if (fsync(fd) != 0) {
            return -3;
        }

        log_batch_used = 0U;
    }

    return 0;
}
```

### 风险影响

- 任务周期超时。
- 控制回路抖动。
- 存储介质寿命缩短。
- 异常掉电时丢失更多数据，需结合周期提交和容量策略平衡。

---

## 9.3 错误三：忽略 DMA 与 Cache 一致性

### 错误代码

```
static uint8_t rx_buffer[4096];

sdmmc_read_dma(block, rx_buffer, sizeof(rx_buffer));
process_data(rx_buffer);
```

### 根因

DMA 直接写内存，但 CPU 可能从 D-Cache 读取旧数据。

### 正确实现

```
#include <stdint.h>

#define CACHE_LINE_SIZE 32U

static uint8_t rx_buffer[4096]
    __attribute__((aligned(CACHE_LINE_SIZE)));

static void cache_invalidate(void *addr, size_t len);

int storage_dma_read(uint32_t block)
{
    cache_invalidate(rx_buffer, sizeof(rx_buffer));

    if (sdmmc_read_dma(block, rx_buffer, sizeof(rx_buffer)) != 0) {
        return -1;
    }

    cache_invalidate(rx_buffer, sizeof(rx_buffer));

    process_data(rx_buffer);
    return 0;
}
```

实际平台中还需要：

- 确认 DMA 完成中断或信号。
- 保证 Buffer 不被其他任务同时访问。
- 发送前执行 Clean，接收后执行 Invalidate。
- 避免 Cache Line 与其他变量共享导致误刷缓存。

### 风险影响

- 文件头偶发错误。
- CRC 校验随机失败。
- 数据错乱但硬件逻辑分析仪显示总线正常。
- 只在启用 Cache 或高负载时出现。

---

## 9.4 错误四：多个任务直接访问同一文件系统

### 错误代码

```
void task_a(void *arg)
{
    for (;;) {
        fs_write(fd, buffer_a, sizeof(buffer_a));
    }
}

void task_b(void *arg)
{
    for (;;) {
        fs_close(fd);
        fs_open("/data/log", &fd);
    }
}
```

### 根因

- 文件句柄生命周期未统一。
- 文件系统库可能不是线程安全的。
- 读写和关闭操作发生竞态。
- 底层驱动可能不支持并发访问。

### 正确实现

推荐单一存储服务任务：

```
业务任务
  ↓ Storage Request Queue
存储服务任务
  ├── open
  ├── read
  ├── write
  ├── sync
  ├── rotate
  └── close
```

### 风险影响

- 文件系统内部状态损坏。
- 任务随机崩溃。
- 目录项丢失。
- 设备运行数天后才出现错误。

---

## 9.5 错误五：检测到挂载失败就自动格式化

### 错误代码

```
if (fs_mount("/data") != 0) {
    fs_format("/data");
    fs_mount("/data");
}
```

### 根因

挂载失败可能由以下因素造成：

- 设备尚未就绪。
- 供电不稳定。
- 文件系统临时锁定。
- 目录损坏但数据仍可修复。
- 驱动初始化超时。
- 文件系统版本不兼容。

### 正确实现

```
第一次挂载失败
  ↓
读取设备状态和错误码
  ↓
若设备未就绪 → 重试
若只读 → 以只读模式挂载
若可修复 → 执行检查与修复
若明确为未格式化 → 进入恢复策略
若确认数据不可保留 → 允许格式化
```

### 风险影响

- 用户数据不可逆丢失。
- 升级包被删除。
- 设备现场恢复证据消失。
- 形成“设备一出问题就自动清空数据”的严重产品缺陷。

## 10.3 存储请求框架

```
typedef enum {
    STORAGE_REQ_READ,
    STORAGE_REQ_WRITE,
    STORAGE_REQ_SYNC,
    STORAGE_REQ_DELETE,
    STORAGE_REQ_FORMAT
} storage_req_type_t;

typedef struct {
    storage_req_type_t type;
    char path[96];
    void *buffer;
    size_t length;
    uint32_t timeout_ms;
    int result;
    SemaphoreHandle_t completion;
} storage_request_t;

static QueueHandle_t g_storage_queue;

int storage_submit(storage_request_t *req)
{
    if (req == NULL || g_storage_queue == NULL) {
        return -1;
    }

    req->result = -100;

    if (xQueueSend(g_storage_queue,
                   req,
                   pdMS_TO_TICKS(req->timeout_ms)) != pdTRUE) {
        return -2;
    }

    if (xSemaphoreTake(req->completion,
                       pdMS_TO_TICKS(req->timeout_ms)) != pdTRUE) {
        return -3;
    }

    return req->result;
}

static void storage_task(void *arg)
{
    storage_request_t req;

    for (;;) {
        if (xQueueReceive(g_storage_queue,
                          &req,
                          portMAX_DELAY) != pdTRUE) {
            continue;
        }

        switch (req.type) {
        case STORAGE_REQ_READ:
            req.result = fs_read_file(req.path,
                                      req.buffer,
                                      req.length);
            break;

        case STORAGE_REQ_WRITE:
            req.result = fs_write_file_atomic(req.path,
                                              req.buffer,
                                              req.length);
            break;

        case STORAGE_REQ_SYNC:
            req.result = fs_sync_all();
            break;

        case STORAGE_REQ_DELETE:
            req.result = fs_delete(req.path);
            break;

        case STORAGE_REQ_FORMAT:
            req.result = recovery_format_allowed()
                       ? fs_format(req.path)
                       : -10;
            break;

        default:
            req.result = -11;
            break;
        }

        xSemaphoreGive(req.completion);
    }
}
```

该架构的核心价值：

- 文件系统只在单一任务中访问。
- 业务任务不会直接触发不可预测的底层操作。
- 可统一加入超时、统计、优先级和故障恢复。
- 未来切换存储介质时，上层接口不变。

## 11. 工业级实际案例分析

## 11.1 案例一：工业控制器运行日志

### 需求

- 采样周期：1 ms。
- 日志速率：约 2 KB/s。
- 设备连续运行 10 年。
- 断电时保留最近 5 分钟关键日志。
- 不能阻塞控制任务。

### 架构

```
控制任务
  ↓ 无锁环形缓冲区
日志任务
  ↓ 每 4 KB 批量提交
NOR Flash 环形日志
  ↓
记录头 + 序列号 + 时间戳 + CRC
```

### 核心设计

单条记录：

```
typedef struct {
    uint32_t magic;
    uint32_t sequence;
    uint32_t timestamp_ms;
    uint16_t type;
    uint16_t length;
    uint8_t  payload[48];
    uint32_t crc;
} log_record_t;
```

设计要点：

- 记录固定大小，避免文件碎片。
- 每个擦除块增加块序号。
- 启动时扫描最新有效块。
- 发现 CRC 错误时跳过当前记录，继续扫描下一块。
- 采用环形回收，始终保留最近数据。
- 日志任务优先级低于控制任务。

### 可靠性

若每条记录 64 B，日志速率 2 KB/s：

DailyWrite=2×86400=172800KBDailyWrite=2×86400=172800KB

若使用 8 MB NOR 日志区，并且擦除块 4 KB，写放大控制到 1.5，平均磨损均衡：

DailyErase≈172800×1.58192≈31.6 次/块总平均DailyErase≈8192172800×1.5​≈31.6 次/块总平均

需要根据 Flash 擦除寿命、目标年限和热区分布进一步验证。

eMMC
├── Bootloader

  ↓ 重启

  ├── 启动成功 → CONFIRMED

typedef enum {

## 12. 高频问题深度答疑

## 问题一：为什么 FATFS 不适合直接运行在裸 NOR Flash 上？

FAT 文件系统按逻辑扇区覆盖写设计，而 NOR 受限于：

- 擦除粒度大。
- 不能直接执行 `0 → 1`。
- FAT 表和目录项会成为热点。
- 掉电时 FAT、目录和数据可能不同步。

可以在 NOR 上使用 FATFS，但通常需要：

- FTL。
- 扇区映射。
- 写缓存。
- 磨损均衡。
- 掉电保护。

否则应优先使用 LittleFS 或 KV Store。

## 问题二：LittleFS 是否可以替代 FATFS？

不能简单替代。

LittleFS 优势：

- 适合裸 Flash。
- 日志式更新。
- 掉电恢复能力较强。
- 磨损均衡。
- 资源占用适合 MCU。

FATFS 优势：

- PC 兼容性好。
- SD/eMMC 生态成熟。
- 大文件与用户交换方便。

如果设备需要 SD 卡拔出后直接插 PC 读取，仍应使用 FATFS。

## 问题三：`fsync()` 是否等于数据已经安全写入 Flash？

不一定。

它通常表示：

- 文件系统缓存已提交。
- 块设备收到了同步请求。

但真正的持久化还可能受以下因素影响：

- SD/eMMC 内部缓存。
- 控制器 FTL 映射更新。
- 设备是否支持可靠写。
- 电源是否在完成内部提交前消失。

关键数据应结合：

- 双副本。
- 提交标志。
- CRC。
- 设备可靠写命令。
- 掉电保护电容。
- 启动恢复扫描。

## 问题四：为什么顺序写也会出现几十毫秒甚至几百毫秒卡顿？

常见原因：

- SD 卡内部垃圾回收。
- FTL 映射表更新。
- 擦除延迟。
- 文件系统扩展文件或更新目录。
- Cache Flush。
- 温度升高导致介质降速。
- 介质接近满容量。
- 写入没有对齐到物理块。

实时系统中必须把“平均延迟”和“最大延迟”分开统计。

## 问题五：日志应该写文件还是写环形 Flash 记录？

取决于需求：

|需求|方案|
|---|---|
|用户需要 PC 直接读取|FATFS 文件|
|追求长期可靠性|固定记录环形日志|
|高频小记录|内存队列 + 批量写|
|断电保留最后几条|双提交记录|
|大容量历史数据|eMMC/SD 顺序文件|
|关键故障证据|独立分区 + CRC/签名|

实际系统常采用“两级日志”：

```
高速短期日志：内部 NOR 环形区
长期完整日志：SD/eMMC 文件
```

## 问题六：如何判断文件系统损坏还是硬件故障？

建议按层次诊断：

```
1. 设备识别是否成功？
2. 块设备原始读是否成功？
3. 固定扇区读写是否稳定？
4. CRC 是否一致？
5. 文件系统元数据是否损坏？
6. 是否存在新增坏块或 ECC 超限？
7. 是否出现供电跌落？
8. 是否存在 Cache/DMA 一致性问题？
```

不能看到 `mount failed` 就直接判定文件系统损坏。

## 13. 课程核心总结

## 13.1 核心要点

1. **NOR/NAND 是受物理擦除约束的非易失存储，不是普通 RAM。**
2. **SD/eMMC 虽然对外表现为块设备，但内部 FTL 行为仍会带来写放大和延迟抖动。**
3. **FATFS 解决兼容性，LittleFS 解决裸 Flash 可靠性，UBIFS 解决大容量 Raw NAND。**
4. **配置、日志、升级镜像和用户媒体必须按访问模式拆分。**
5. **掉电一致性必须通过版本、CRC、双副本和提交标志共同实现。**
6. **文件系统访问应集中到存储服务中，避免多任务直接并发访问。**
7. **性能评价必须同时关注平均吞吐、P99/P999 延迟、写放大、RAM 占用和寿命。**
8. **任何自动格式化策略都必须受到严格条件控制。**

## 13.2 性能排序

### 随机小写延迟

```
FRAM > NOR KV > LittleFS NOR > eMMC > SD FATFS
```

这里的“>`”表示更优。

### 大文件顺序吞吐

```
UFS/eMMC HS200 > 高速 SDMMC > SPI NAND > QSPI NOR > I²C FRAM
```

### 掉电可控性

```
FRAM + 双副本 > LittleFS > UBIFS/YAFFS2 > eMMC + 可靠写 > FATFS + 普通 SD
```

实际结果取决于实现和硬件掉电保护。

## 13.3 通用选型结论

- **小数据、高可靠、高频更新：FRAM 或 KV Store。**
- **裸 NOR：优先 LittleFS 或专用日志结构。**
- **大容量 Raw NAND：Linux 平台优先 UBI + UBIFS。**
- **需要 PC 兼容：SD/eMMC + FATFS。**
- **升级：双镜像、签名校验、启动确认和自动回滚缺一不可。**
- **实时控制：存储操作异步化、批量化、预分配，禁止将擦除放入硬实时路径。**

## 3.3 Block 设备与 MTD 设备

### Block 设备

Block 设备向上提供固定大小逻辑块，通常为 512 B 或 4 KB。

特点：

- 支持逻辑块读写。
- 设备内部可能隐藏物理擦除、坏块和磨损均衡。
- 常见于 SD、eMMC、SSD。
- 上层通常使用 FAT、ext4、LittleFS Block Backend 等。

### MTD 设备

MTD，Memory Technology Device，直接暴露 Flash 的物理约束：

- 读取粒度通常较小。
- 编程只能将 bit 从 `1` 写为 `0`。
- 擦除后才能将 bit 从 `0` 恢复为 `1`。
- 擦除粒度远大于写入粒度。
- 需要处理坏块、ECC、擦写寿命和掉电一致性。

## 5. 底层原理与功能特性深度解析

## 5.1 NOR Flash 的写入约束

NOR Flash 的基本状态转换：

```
擦除：
0 → 1

编程：
1 → 0

错误操作：
0 → 1，必须先擦除
```

因此不能直接用普通内存语义覆盖写入：

```
/* 错误：不能保证覆盖写入 */
flash_write(addr, &new_value, sizeof(new_value));
```

生产级写入通常需要：

1. 读取原扇区。
2. 判断目标 bit 是否存在 `0 → 1`。
3. 若不存在，直接编程。
4. 若存在，执行整扇区擦除。
5. 修改内存副本。
6. 写回整个扇区。
7. 进行 CRC 校验和提交标志写入。

```
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define FLASH_SECTOR_SIZE 4096U

typedef enum {
    FLASH_OK = 0,
    FLASH_ERR_PARAM = -1,
    FLASH_ERR_IO = -2,
    FLASH_ERR_VERIFY = -3
} flash_status_t;

static int flash_read(uint32_t addr, void *buf, size_t len);
static int flash_program(uint32_t addr, const void *buf, size_t len);
static int flash_erase_sector(uint32_t addr);
static uint32_t crc32(const void *data, size_t len);

flash_status_t flash_update(uint32_t addr,
                            const void *data,
                            size_t len)
{
    if (data == NULL || len == 0U ||
        len > FLASH_SECTOR_SIZE ||
        (addr % FLASH_SECTOR_SIZE) + len > FLASH_SECTOR_SIZE) {
        return FLASH_ERR_PARAM;
    }

    uint8_t sector[FLASH_SECTOR_SIZE];

    if (flash_read(addr - (addr % FLASH_SECTOR_SIZE),
                   sector,
                   sizeof(sector)) != 0) {
        return FLASH_ERR_IO;
    }

    uint32_t offset = addr % FLASH_SECTOR_SIZE;
    bool need_erase = false;

    for (size_t i = 0; i < len; ++i) {
        uint8_t oldv = sector[offset + i];
        uint8_t newv = ((const uint8_t *)data)[i];

        /*
         * 若存在 old=0、new=1，则必须擦除。
         */
        if ((uint8_t)(~oldv & newv) != 0U) {
            need_erase = true;
        }
    }

    if (!need_erase) {
        if (flash_program(addr, data, len) != 0) {
            return FLASH_ERR_IO;
        }
    } else {
        memcpy(&sector[offset], data, len);

        uint32_t sector_addr = addr - (addr % FLASH_SECTOR_SIZE);

        if (flash_erase_sector(sector_addr) != 0) {
            return FLASH_ERR_IO;
        }

        if (flash_program(sector_addr,
                          sector,
                          sizeof(sector)) != 0) {
            return FLASH_ERR_IO;
        }
    }

    uint8_t verify[FLASH_SECTOR_SIZE];

    if (flash_read(addr, verify, len) != 0 ||
        memcmp(verify, data, len) != 0) {
        return FLASH_ERR_VERIFY;
    }

    return FLASH_OK;
}
```

### 工程风险

- 栈空间不足：4 KB 临时缓冲区不能无条件放在任务栈。
- 擦除期间长时间阻塞：典型 4 KB 擦除可能为 20～200 ms。
- 断电导致扇区内容处于不确定状态。
- 多任务并发更新导致数据覆盖，必须使用存储锁。

## 5.2 双槽提交实现掉电一致性

对配置、校准值、启动参数等关键数据，不应直接覆盖单份文件。推荐双槽或日志记录方案：

```
Slot A: magic | version | length | payload | crc | commit
Slot B: magic | version | length | payload | crc | commit

启动时：
1. 检查 magic
2. 检查 length
3. 检查 CRC
4. 检查 commit 标志
5. 选择 version 最大且有效的槽
```

```
#define RECORD_MAGIC 0x53434647U /* "SCFG" */
#define COMMIT_DONE  0xA5A5A5A5U

typedef struct {
    uint32_t magic;
    uint32_t version;
    uint32_t length;
    uint32_t crc;
    uint32_t commit;
} record_header_t;

typedef struct {
    uint32_t sample_rate;
    uint32_t device_id;
    int32_t  calibration_offset;
} device_config_t;

static bool config_record_valid(const uint8_t *raw,
                                size_t area_size,
                                record_header_t *hdr_out)
{
    if (raw == NULL || area_size < sizeof(record_header_t)) {
        return false;
    }

    record_header_t hdr;
    memcpy(&hdr, raw, sizeof(hdr));

    if (hdr.magic != RECORD_MAGIC ||
        hdr.commit != COMMIT_DONE ||
        hdr.length != sizeof(device_config_t) ||
        sizeof(record_header_t) + hdr.length > area_size) {
        return false;
    }

    const uint8_t *payload = raw + sizeof(record_header_t);

    if (crc32(payload, hdr.length) != hdr.crc) {
        return false;
    }

    if (hdr_out != NULL) {
        *hdr_out = hdr;
    }

    return true;
}
```

### 提交顺序

正确顺序：

```
1. 擦除目标槽
2. 写入 header，但 commit 保持擦除态
3. 写入 payload
4. 读取校验 payload
5. 最后单独写入 commit 标志
```

不能先写 `commit`，否则掉电时可能出现“看似有效、实际数据不完整”的记录。

## 5.3 NAND Flash、ECC 与坏块管理

NAND 的可靠性问题主要包括：

- 出厂坏块。
- 使用过程中新增坏块。
- Read disturb。
- Program disturb。
- 位翻转。
- 写入失败。
- 擦除失败。
- ECC 可纠正位数超过上限。

典型数据路径：

```
应用数据
  ↓
文件系统
  ↓
UBI / YAFFS / NAND FTL
  ↓
ECC 编码
  ↓
NAND 控制器
  ↓
Flash Cell
```

读取时：

```
Flash Cell
  ↓
NAND 控制器读取
  ↓
ECC 解码与纠错
  ↓
返回数据 + 纠错计数
```

工程上必须记录：

- 每块 ECC correction count。
- 不可纠正错误次数。
- 擦除失败次数。
- 重新映射次数。
- 坏块增长趋势。

不要将 Raw NAND 直接当成普通数组使用：

```
/* 错误：跳过坏块、ECC 和擦除约束 */
raw_nand_write(physical_address, buf, len);
```

## 5.4 FTL 与 eMMC/SD 的隐藏行为

eMMC 和 SD 卡内部通常包含：

```
逻辑块地址
  ↓
FTL 映射表
  ↓
磨损均衡
  ↓
坏块重映射
  ↓
ECC
  ↓
NAND Flash
```

因此：

- 主机看到的是逻辑扇区，不是物理块。
- 覆盖写可能触发内部读-改-写。
- 小块随机写会增加内部写放大。
- `fsync()` 只表示主机向设备提交了同步请求，具体持久化语义取决于控制器和介质。
- 断电时可能出现映射表更新和数据更新不同步。

### 建议

- 使用 4 KB 或更大对齐的写入。
- 对日志采用顺序追加。
- 对大文件预分配。
- 避免频繁更新 FAT 目录项。
- 升级数据与运行日志分区隔离。
- 对关键数据使用双副本和版本号。
- 量产设备优先选择工业级 eMMC/SD，并验证掉电行为。

## 5.5 文件系统挂载流程

通用挂载流程：

```
检测设备
  ↓
读取识别信息
  ↓
验证分区表
  ↓
识别文件系统
  ↓
执行 mount
  ↓
校验关键目录
  ↓
加载元数据
  ↓
发布存储就绪事件
```

工程代码应区分：

- 设备不存在。
- 设备存在但未格式化。
- 文件系统损坏。
- 挂载超时。
- 介质只读。
- 容量不足。
- 文件系统版本不兼容。

```
typedef enum {
    STORAGE_MOUNT_OK = 0,
    STORAGE_MOUNT_NO_DEVICE,
    STORAGE_MOUNT_UNFORMATTED,
    STORAGE_MOUNT_CORRUPTED,
    STORAGE_MOUNT_READONLY,
    STORAGE_MOUNT_TIMEOUT,
    STORAGE_MOUNT_FAILED
} storage_mount_result_t;

storage_mount_result_t storage_mount_with_recovery(void)
{
    if (!blockdev_present()) {
        return STORAGE_MOUNT_NO_DEVICE;
    }

    if (fs_mount("/data") == 0) {
        if (fs_check_required_dirs("/data") != 0) {
            return STORAGE_MOUNT_CORRUPTED;
        }
        return STORAGE_MOUNT_OK;
    }

    if (fs_is_unformatted()) {
        /*
         * 生产系统中不能无条件格式化，必须满足：
         * 1. 用户明确允许；
         * 2. 数据确实不需要保留；
         * 3. 设备处于恢复模式；
         */
        if (recovery_format_allowed()) {
            if (fs_format("/data") == 0 &&
                fs_mount("/data") == 0) {
                return STORAGE_MOUNT_OK;
            }
        }

        return STORAGE_MOUNT_UNFORMATTED;
    }

    if (fs_is_readonly()) {
        return STORAGE_MOUNT_READONLY;
    }

    if (fs_repair() == 0 && fs_mount("/data") == 0) {
        return STORAGE_MOUNT_OK;
    }

    return STORAGE_MOUNT_FAILED;
}
```

## 6.2 写放大

写放大定义：

例如，应用每次写入 100 B，但文件系统需要更新：

- 4 KB 数据块；
- 4 KB 元数据块；
- 4 KB 日志块；
- 4 KB 垃圾回收搬移块。

### 优化方式

- 采用批量写入。
- 使用顺序日志代替随机覆盖。
- 参数变化后延迟合并提交。
- 预分配文件。
- 采用固定大小记录。
- 将高频计数器放到 FRAM。
- 使用独立日志分区，避免污染主文件系统。

典型文件系统 RAM 开销：

|项目|典型大小|

- 文件系统缓存放在静态内存。

- 对文件句柄设置上限。
- 对目录递归深度设置上限，防止异常文件系统造成栈溢出。

## 8. 工程最佳实践

## 8.1 设计原则

### 原则一：按数据属性分区，而不是按硬件介质分区

推荐：

```
Boot Partition
  ├── bootloader_a
  ├── bootloader_b
  └── boot_metadata

Config Partition
  ├── device_config
  ├── calibration
  └── factory_data

Log Partition
  ├── runtime_log
  └── crash_dump

Update Partition
  ├── image_a
  ├── image_b
  └── update_state

User Data Partition
  └── media files
```

### 原则二：高频小写与大文件顺序写必须隔离

不能将以下数据放在同一文件系统中：

- 每秒更新的运行状态。
- 数 GB 的升级包。
- 用户媒体文件。
- 系统配置文件。

因为它们会产生完全不同的元数据和写入模式。

### 原则三：存储锁必须统一

```
static SemaphoreHandle_t g_storage_mutex;

int storage_safe_write(const char *path,
                       const void *data,
                       size_t len)
{
    if (path == NULL || data == NULL || len == 0U) {
        return -1;
    }

    if (xSemaphoreTake(g_storage_mutex,
                       pdMS_TO_TICKS(5000)) != pdTRUE) {
        return -2;
    }

    int ret = fs_write_file_atomic(path, data, len);

    xSemaphoreGive(g_storage_mutex);
    return ret;
}
```

不要允许每个业务模块自行创建文件系统锁，否则容易形成锁顺序反转。

### 原则四：所有关键写入都必须有可验证提交点

关键记录应包含：

- Magic。
- 版本号。
- 长度。
- CRC。
- 序列号。
- 提交标志。
- 可选的时间戳。
- 可选的签名或认证标签。

### 原则五：不要在实时路径中执行不可预测的擦除或垃圾回收

错误设计：

```
void control_loop_task(void *arg)
{
    for (;;) {
        control_step();

        /* 可能触发 100 ms 擦除或垃圾回收 */
        log_append("/data/log.bin", sample, sizeof(sample));

        vTaskDelay(pdMS_TO_TICKS(1));
    }
}
```

正确设计：

```
控制任务
  ↓ 非阻塞发送
内存日志队列
  ↓
低优先级存储任务
  ↓ 批量顺序写入
Flash/SD
```

## 8.2 选型决策矩阵

评分范围：1～5 分。

|方案|掉电可靠性|PC 兼容性|高频小写|大容量|实时性|开发复杂度|
|---|---|---|---|---|---|---|
|NOR + LittleFS|5|1|4|2|4|3|
|NOR + FATFS|2|3|1|2|2|2|
|SD + FATFS|3|5|2|5|2|2|
|eMMC + FATFS|4|4|3|5|3|3|
|NAND + UBIFS|5|1|4|5|3|5|
|FRAM + KV|5|1|5|1|5|2|
|RAM Disk|1|1|5|2|5|1|

## 8.3 工业级编码规范

- 所有路径长度、文件名长度和目录深度必须有限制。
- 所有 `open`、`read`、`write`、`sync`、`close` 返回值必须检查。
- 写入后不默认认为数据已持久化，关键数据必须 `fsync` 或调用介质同步接口。
- 禁止在中断服务函数中访问文件系统。
- 禁止在持有存储锁时调用可能阻塞数百毫秒的外部服务。
- 文件名使用 ASCII 或统一 UTF-8 策略，避免跨平台编码问题。
- 对外部 SD 卡文件必须进行大小、格式和签名校验。
- 文件删除采用“先关闭、再校验、后删除”的流程。
- 对所有文件操作增加超时、重试次数和错误统计。
- 文件系统错误码必须转换为系统级诊断码，不能直接丢弃。

## 9. 常见错误与避坑指南

## 9.1 错误一：直接覆盖 NOR Flash

### 错误代码

```
uint32_t value = 0x12345678;
flash_program(CONFIG_ADDR, &value, sizeof(value));
```

### 根因

新数据可能需要将某些 bit 从 `0` 改为 `1`，而 NOR 编程只能执行 `1 → 0`。

### 正确实现

使用扇区读-改-擦-写，或使用双槽日志记录。

### 风险影响

- 配置数据损坏。
- 部分字段更新、部分字段未更新。
- 设备重启后进入默认配置。
- 现场表现为偶发且难以复现。

---

## 9.2 错误二：高频调用 `fsync`

### 错误代码

```
for (uint32_t i = 0; i < 1000; ++i) {
    fs_write(fd, &sample, sizeof(sample));
    fsync(fd);
}
```

### 根因

每条记录都触发文件系统元数据提交和底层设备同步，导致：

- 写放大。
- 延迟抖动。
- SD 卡内部垃圾回收频繁触发。
- 文件系统寿命下降。

### 正确实现

内存队列聚合后批量写入：

```
#define LOG_BATCH_SIZE 4096U

static uint8_t log_batch[LOG_BATCH_SIZE];
static size_t log_batch_used;

int log_append_batch(int fd, const void *data, size_t len)
{
    if (data == NULL || len == 0U ||
        len > LOG_BATCH_SIZE - log_batch_used) {
        return -1;
    }

    memcpy(&log_batch[log_batch_used], data, len);
    log_batch_used += len;

    if (log_batch_used == LOG_BATCH_SIZE) {
        if (fs_write(fd, log_batch, log_batch_used) !=
            (int)log_batch_used) {
            return -2;
        }

        if (fsync(fd) != 0) {
            return -3;
        }

        log_batch_used = 0U;
    }

    return 0;
}
```

### 风险影响

- 任务周期超时。
- 控制回路抖动。
- 存储介质寿命缩短。
- 异常掉电时丢失更多数据，需结合周期提交和容量策略平衡。

---

## 9.3 错误三：忽略 DMA 与 Cache 一致性

### 错误代码

```
static uint8_t rx_buffer[4096];

sdmmc_read_dma(block, rx_buffer, sizeof(rx_buffer));
process_data(rx_buffer);
```

### 根因

DMA 直接写内存，但 CPU 可能从 D-Cache 读取旧数据。

### 正确实现

```
#include <stdint.h>

#define CACHE_LINE_SIZE 32U

static uint8_t rx_buffer[4096]
    __attribute__((aligned(CACHE_LINE_SIZE)));

static void cache_invalidate(void *addr, size_t len);

int storage_dma_read(uint32_t block)
{
    cache_invalidate(rx_buffer, sizeof(rx_buffer));

    if (sdmmc_read_dma(block, rx_buffer, sizeof(rx_buffer)) != 0) {
        return -1;
    }

    cache_invalidate(rx_buffer, sizeof(rx_buffer));

    process_data(rx_buffer);
    return 0;
}
```

实际平台中还需要：

- 确认 DMA 完成中断或信号。
- 保证 Buffer 不被其他任务同时访问。
- 发送前执行 Clean，接收后执行 Invalidate。
- 避免 Cache Line 与其他变量共享导致误刷缓存。

### 风险影响

- 文件头偶发错误。
- CRC 校验随机失败。
- 数据错乱但硬件逻辑分析仪显示总线正常。
- 只在启用 Cache 或高负载时出现。

---

## 9.4 错误四：多个任务直接访问同一文件系统

### 错误代码

```
void task_a(void *arg)
{
    for (;;) {
        fs_write(fd, buffer_a, sizeof(buffer_a));
    }
}

void task_b(void *arg)
{
    for (;;) {
        fs_close(fd);
        fs_open("/data/log", &fd);
    }
}
```

### 根因

- 文件句柄生命周期未统一。
- 文件系统库可能不是线程安全的。
- 读写和关闭操作发生竞态。
- 底层驱动可能不支持并发访问。

### 正确实现

推荐单一存储服务任务：

```
业务任务
  ↓ Storage Request Queue
存储服务任务
  ├── open
  ├── read
  ├── write
  ├── sync
  ├── rotate
  └── close
```

### 风险影响

- 文件系统内部状态损坏。
- 任务随机崩溃。
- 目录项丢失。
- 设备运行数天后才出现错误。

---

## 9.5 错误五：检测到挂载失败就自动格式化

### 错误代码

```
if (fs_mount("/data") != 0) {
    fs_format("/data");
    fs_mount("/data");
}
```

### 根因

挂载失败可能由以下因素造成：

- 设备尚未就绪。
- 供电不稳定。
- 文件系统临时锁定。
- 目录损坏但数据仍可修复。
- 驱动初始化超时。
- 文件系统版本不兼容。

### 正确实现

```
第一次挂载失败
  ↓
读取设备状态和错误码
  ↓
若设备未就绪 → 重试
若只读 → 以只读模式挂载
若可修复 → 执行检查与修复
若明确为未格式化 → 进入恢复策略
若确认数据不可保留 → 允许格式化
```

### 风险影响

- 用户数据不可逆丢失。
- 升级包被删除。
- 设备现场恢复证据消失。
- 形成“设备一出问题就自动清空数据”的严重产品缺陷。

## 10.3 存储请求框架

```
typedef enum {
    STORAGE_REQ_READ,
    STORAGE_REQ_WRITE,
    STORAGE_REQ_SYNC,
    STORAGE_REQ_DELETE,
    STORAGE_REQ_FORMAT
} storage_req_type_t;

typedef struct {
    storage_req_type_t type;
    char path[96];
    void *buffer;
    size_t length;
    uint32_t timeout_ms;
    int result;
    SemaphoreHandle_t completion;
} storage_request_t;

static QueueHandle_t g_storage_queue;

int storage_submit(storage_request_t *req)
{
    if (req == NULL || g_storage_queue == NULL) {
        return -1;
    }

    req->result = -100;

    if (xQueueSend(g_storage_queue,
                   req,
                   pdMS_TO_TICKS(req->timeout_ms)) != pdTRUE) {
        return -2;
    }

    if (xSemaphoreTake(req->completion,
                       pdMS_TO_TICKS(req->timeout_ms)) != pdTRUE) {
        return -3;
    }

    return req->result;
}

static void storage_task(void *arg)
{
    storage_request_t req;

    for (;;) {
        if (xQueueReceive(g_storage_queue,
                          &req,
                          portMAX_DELAY) != pdTRUE) {
            continue;
        }

        switch (req.type) {
        case STORAGE_REQ_READ:
            req.result = fs_read_file(req.path,
                                      req.buffer,
                                      req.length);
            break;

        case STORAGE_REQ_WRITE:
            req.result = fs_write_file_atomic(req.path,
                                              req.buffer,
                                              req.length);
            break;

        case STORAGE_REQ_SYNC:
            req.result = fs_sync_all();
            break;

        case STORAGE_REQ_DELETE:
            req.result = fs_delete(req.path);
            break;

        case STORAGE_REQ_FORMAT:
            req.result = recovery_format_allowed()
                       ? fs_format(req.path)
                       : -10;
            break;

        default:
            req.result = -11;
            break;
        }

        xSemaphoreGive(req.completion);
    }
}
```

该架构的核心价值：

- 文件系统只在单一任务中访问。
- 业务任务不会直接触发不可预测的底层操作。
- 可统一加入超时、统计、优先级和故障恢复。
- 未来切换存储介质时，上层接口不变。

## 11. 工业级实际案例分析

## 11.1 案例一：工业控制器运行日志

### 需求

- 采样周期：1 ms。
- 日志速率：约 2 KB/s。
- 设备连续运行 10 年。
- 断电时保留最近 5 分钟关键日志。
- 不能阻塞控制任务。

### 架构

```
控制任务
  ↓ 无锁环形缓冲区
日志任务
  ↓ 每 4 KB 批量提交
NOR Flash 环形日志
  ↓
记录头 + 序列号 + 时间戳 + CRC
```

### 核心设计

单条记录：

```
typedef struct {
    uint32_t magic;
    uint32_t sequence;
    uint32_t timestamp_ms;
    uint16_t type;
    uint16_t length;
    uint8_t  payload[48];
    uint32_t crc;
} log_record_t;
```

设计要点：

- 记录固定大小，避免文件碎片。
- 每个擦除块增加块序号。
- 启动时扫描最新有效块。
- 发现 CRC 错误时跳过当前记录，继续扫描下一块。
- 采用环形回收，始终保留最近数据。
- 日志任务优先级低于控制任务。

### 可靠性

若每条记录 64 B，日志速率 2 KB/s：

DailyWrite=2×86400=172800KBDailyWrite=2×86400=172800KB

若使用 8 MB NOR 日志区，并且擦除块 4 KB，写放大控制到 1.5，平均磨损均衡：

DailyErase≈172800×1.58192≈31.6 次/块总平均DailyErase≈8192172800×1.5​≈31.6 次/块总平均

需要根据 Flash 擦除寿命、目标年限和热区分布进一步验证。

## 11.2 案例二：支持 OTA 的工业网关

### 需求

- 固件镜像大小：32 MB。
- 支持断点下载。
- 升级断电后设备必须自动恢复。
- 固件必须进行签名校验。
- 失败后回滚到旧版本。

### 分区设计

```
eMMC
├── Bootloader
├── Boot Metadata
├── RootFS_A
├── RootFS_B
├── Update Download
└── User Data
```

### 升级状态机

```
IDLE
  ↓ 下载
DOWNLOADING
  ↓ SHA-256 校验
DOWNLOADED
  ↓ 签名校验
VERIFIED
  ↓ 写入目标槽
PENDING_BOOT
  ↓ 重启
TRIAL_BOOT
  ├── 启动成功 → CONFIRMED
  └── 启动失败 → ROLLBACK
```

### 启动元数据

```
typedef enum {
    BOOT_SLOT_A = 0,
    BOOT_SLOT_B = 1
} boot_slot_t;

typedef enum {
    UPDATE_IDLE,
    UPDATE_DOWNLOADING,
    UPDATE_VERIFIED,
    UPDATE_PENDING,
    UPDATE_CONFIRMED,
    UPDATE_ROLLBACK
} update_state_t;

typedef struct {
    uint32_t magic;
    uint32_t version;
    boot_slot_t active_slot;
    boot_slot_t trial_slot;
    update_state_t state;
    uint32_t boot_attempts;
    uint8_t image_hash[32];
    uint32_t crc;
} boot_metadata_t;
```

设计要点：

- 元数据采用双副本。
- `boot_attempts` 防止无限重启。
- 新镜像必须完成哈希和签名验证后才能标记 `PENDING`。
- 第一次启动新镜像处于试运行状态。
- 系统关键服务全部启动并完成健康检查后，才写入 `CONFIRMED`。
- 任何失败都不允许覆盖旧镜像。

## 11.3 案例三：可移动 SD 卡数据导出设备

### 需求

- 用户插拔 SD 卡。
- 设备持续记录数据。
- 拔卡时不能损坏主配置。
- 文件可在 Windows/Linux 上读取。
- SD 卡异常时设备继续运行。

### 架构

```
传感器数据
  ↓
RAM 缓冲区
  ↓
Storage Service
  ↓
SD/FATFS
  ├── /data/current.bin
  ├── /data/archive/
  └── /system/status
```

### 热插拔流程

```
检测卡插入
  ↓
电源稳定等待
  ↓
初始化 SDMMC
  ↓
挂载文件系统
  ↓
创建并校验目录
  ↓
发布 MEDIA_READY

检测卡移除
  ↓
停止新写入
  ↓
关闭文件
  ↓
同步缓存
  ↓
卸载文件系统
  ↓
关闭电源
  ↓
发布 MEDIA_REMOVED
```

设计要点：

- 不依赖文件系统访问作为卡移除检测。
- 卡移除后，数据暂存于 RAM 或内部 NOR。
- 写入失败必须区分“临时介质错误”和“永久设备故障”。
- 用户文件和系统关键配置分离。
- 对导出文件写入临时名，完成后执行原子重命名：

```
current.tmp → fsync → rename current.bin
```

## 12. 高频问题深度答疑

## 问题一：为什么 FATFS 不适合直接运行在裸 NOR Flash 上？

FAT 文件系统按逻辑扇区覆盖写设计，而 NOR 受限于：

- 擦除粒度大。
- 不能直接执行 `0 → 1`。
- FAT 表和目录项会成为热点。
- 掉电时 FAT、目录和数据可能不同步。

可以在 NOR 上使用 FATFS，但通常需要：

- FTL。
- 扇区映射。
- 写缓存。
- 磨损均衡。
- 掉电保护。

否则应优先使用 LittleFS 或 KV Store。

## 问题二：LittleFS 是否可以替代 FATFS？

不能简单替代。

LittleFS 优势：

- 适合裸 Flash。
- 日志式更新。
- 掉电恢复能力较强。
- 磨损均衡。
- 资源占用适合 MCU。

FATFS 优势：

- PC 兼容性好。
- SD/eMMC 生态成熟。
- 大文件与用户交换方便。

如果设备需要 SD 卡拔出后直接插 PC 读取，仍应使用 FATFS。

## 问题三：`fsync()` 是否等于数据已经安全写入 Flash？

不一定。

它通常表示：

- 文件系统缓存已提交。
- 块设备收到了同步请求。

但真正的持久化还可能受以下因素影响：

- SD/eMMC 内部缓存。
- 控制器 FTL 映射更新。
- 设备是否支持可靠写。
- 电源是否在完成内部提交前消失。

关键数据应结合：

- 双副本。
- 提交标志。
- CRC。
- 设备可靠写命令。
- 掉电保护电容。
- 启动恢复扫描。

## 问题四：为什么顺序写也会出现几十毫秒甚至几百毫秒卡顿？

常见原因：

- SD 卡内部垃圾回收。
- FTL 映射表更新。
- 擦除延迟。
- 文件系统扩展文件或更新目录。
- Cache Flush。
- 温度升高导致介质降速。
- 介质接近满容量。
- 写入没有对齐到物理块。

实时系统中必须把“平均延迟”和“最大延迟”分开统计。

## 问题五：日志应该写文件还是写环形 Flash 记录？

取决于需求：

|需求|方案|
|---|---|
|用户需要 PC 直接读取|FATFS 文件|
|追求长期可靠性|固定记录环形日志|
|高频小记录|内存队列 + 批量写|
|断电保留最后几条|双提交记录|
|大容量历史数据|eMMC/SD 顺序文件|
|关键故障证据|独立分区 + CRC/签名|

实际系统常采用“两级日志”：

```
高速短期日志：内部 NOR 环形区
长期完整日志：SD/eMMC 文件
```

## 问题六：如何判断文件系统损坏还是硬件故障？

建议按层次诊断：

```
1. 设备识别是否成功？
2. 块设备原始读是否成功？
3. 固定扇区读写是否稳定？
4. CRC 是否一致？
5. 文件系统元数据是否损坏？
6. 是否存在新增坏块或 ECC 超限？
7. 是否出现供电跌落？
8. 是否存在 Cache/DMA 一致性问题？
```

不能看到 `mount failed` 就直接判定文件系统损坏。

## 13. 课程核心总结

## 13.1 核心要点

1. **NOR/NAND 是受物理擦除约束的非易失存储，不是普通 RAM。**
2. **SD/eMMC 虽然对外表现为块设备，但内部 FTL 行为仍会带来写放大和延迟抖动。**
3. **FATFS 解决兼容性，LittleFS 解决裸 Flash 可靠性，UBIFS 解决大容量 Raw NAND。**
4. **配置、日志、升级镜像和用户媒体必须按访问模式拆分。**
5. **掉电一致性必须通过版本、CRC、双副本和提交标志共同实现。**
6. **文件系统访问应集中到存储服务中，避免多任务直接并发访问。**
7. **性能评价必须同时关注平均吞吐、P99/P999 延迟、写放大、RAM 占用和寿命。**
8. **任何自动格式化策略都必须受到严格条件控制。**

## 13.2 性能排序

### 随机小写延迟

```
FRAM > NOR KV > LittleFS NOR > eMMC > SD FATFS
```

这里的“>`”表示更优。

### 大文件顺序吞吐

```
UFS/eMMC HS200 > 高速 SDMMC > SPI NAND > QSPI NOR > I²C FRAM
```

### 掉电可控性

```
FRAM + 双副本 > LittleFS > UBIFS/YAFFS2 > eMMC + 可靠写 > FATFS + 普通 SD
```

实际结果取决于实现和硬件掉电保护。

## 13.3 通用选型结论

- **小数据、高可靠、高频更新：FRAM 或 KV Store。**
- **裸 NOR：优先 LittleFS 或专用日志结构。**
- **大容量 Raw NAND：Linux 平台优先 UBI + UBIFS。**
- **需要 PC 兼容：SD/eMMC + FATFS。**
- **升级：双镜像、签名校验、启动确认和自动回滚缺一不可。**
- **实时控制：存储操作异步化、批量化、预分配，禁止将擦除放入硬实时路径。**
