
## 1. 学习目标

### 理解

- 理解 EEPROM 模拟（EEPROM Emulation，简称 EEE）的本质：利用 Flash 擦除块与编程操作，构造**按字节/变量更新、掉电可恢复**的非易失存储层。
- 理解 Flash 的物理限制：擦除粒度大于编程粒度、擦除次数有限、擦除期间可能阻塞取指、位只能从 `1` 编程为 `0`。
- 理解双页日志、磨损均衡、CRC、序列号和掉电一致性的关系。

### 掌握

- 掌握 Flash 页初始化、记录追加、有效记录扫描、垃圾回收和异常恢复流程。
- 掌握变量版本管理、CRC 校验、状态字设计及并发访问保护。
- 掌握不同 MCU Flash 控制器的地址对齐、编程宽度、Cache/预取和读写保护约束。

### 精通

- 能够分析掉电发生在“写入前、数据写入中、状态提交中、擦除中”各时间窗口的系统行为。
- 能够量化存储容量、写放大、寿命、启动扫描时间和最坏写延迟。
- 能够设计具备故障注入、版本升级和现场恢复能力的 NVM 驱动。

### 能够设计

- 能够为参数、校准数据、故障日志和计数器选择合适的 EEPROM 模拟架构。
- 能够设计多页日志、A/B 数据区、分组提交和后台垃圾回收方案。
- 能够形成可测试、可审计、可迁移到不同 MCU 平台的工业级 NVM 抽象层。

## 3. 技术概述

EEPROM 模拟不是把 Flash 变成真正的 EEPROM，而是在 Flash 上建立一层**追加式日志结构**：

1. 新值写入尚未使用的位置；
2. 通过序列号判断最新有效值；
3. 当前页空间不足时，把最新值搬迁到另一页；
4. 擦除旧页，循环使用。

### 技术价值

- 无需外接 EEPROM，降低 BOM 和 PCB 面积。
- 可统一参数、校准系数、设备序列号和故障记录的存储接口。
- 通过日志追加避免频繁擦除同一地址，实现磨损均衡。

### 主流实现分支

1. **双页变量日志**：适合少量参数，STM32 EEPROM Emulation 类方案常用。
2. **多页循环日志**：适合高频更新和较大数据量。
3. **A/B 完整镜像**：适合配置整体提交，恢复逻辑简单，但写放大较大。
4. **Key-Value 日志数据库**：变量按 Key 记录，可扩展性强，但代码和元数据开销更大。
5. **外部 I²C/SPI EEPROM/FRAM**：当 Flash 寿命、写延迟或容量不满足要求时采用。

## 4. 核心特性横向对比

|方案|擦除粒度|写入寿命|掉电恢复|写延迟|适用场景|
|---|---|---|---|---|---|
|单页原地更新|页|差，热点集中|弱|低至中|临时实验、低频参数|
|双页追加日志|页|中高|强|中|参数、校准值|
|多页循环日志|页|高|强|中|计数器、事件日志|
|A/B 镜像|页/扇区|中|很强|中高|配置整体提交|
|外部 I²C EEPROM|字节/页|高|强|低至高|兼容性、容量需求|
|FRAM|字节/总线事务|极高|强|低|高频计数、实时写入|
|外部 NOR Flash 日志|扇区|中高|依实现|中高|大容量数据|

**关键结论：** 少量低频参数优先使用双页追加日志；高频计数器不能简单地每次事件都写 Flash。

## 5. 底层原理与功能特性深度解析

### 5.1 Flash 物理约束

典型 NOR Flash 单元通过擦除将位恢复为 `1`，编程将位变为 `0`。因此：

- `0xFF -> 0xF0` 通常可直接编程；
- `0xF0 -> 0xFF` 必须先擦除所在页；
- 一次编程不能跨越控制器要求的对齐边界；
- 擦除通常耗时毫秒级，编程通常为几十至数百微秒，但具体值必须查数据手册。

Flash 数据状态通常设计为：

```
#define EEE_MAGIC       0x45454531u  /* "EEE1" */
#define EEE_PAGE_EMPTY  0xFFFFFFFFu
#define EEE_PAGE_ACTIVE 0xAAAA5555u
#define EEE_PAGE_FULL   0x00000000u
```

不要依赖单个状态字判断有效性。状态字本身也可能在掉电时被部分编程，必须结合 Magic、CRC、长度和序列号判断。

### 5.2 记录格式

一个可复用的记录格式如下：

```
#include <stdint.h>
#include <stdbool.h>

#define EEE_KEY_INVALID 0xFFFFu

/* 固定长度记录便于扫描和地址计算；长度必须满足 Flash 编程对齐要求 */
typedef struct {
    uint16_t key;
    uint16_t length;
    uint32_t sequence;
    uint32_t value;
    uint32_t crc32;
} eee_record_t;

static uint32_t eee_record_crc(const eee_record_t *r)
{
    /* 实际项目中使用经过验证的 CRC32 实现；CRC 字段本身不参与计算 */
    return crc32((const uint8_t *)r,
                 sizeof(*r) - sizeof(r->crc32));
}

static bool eee_record_valid(const eee_record_t *r)
{
    if (r->key == EEE_KEY_INVALID || r->length != sizeof(r->value)) {
        return false;
    }
    return eee_record_crc(r) == r->crc32;
}
```

生产实现应根据 MCU 最小编程宽度，将结构体填充到 8、16 或 32 字节，并明确规定字节序。不能直接把带有未初始化 padding 的 C 结构体写入 Flash。

### 5.3 写入顺序与掉电一致性

推荐顺序：

1. 构造记录并将未使用字段清零；
2. 计算 CRC；
3. 写入数据字段；
4. 读取回校验；
5. 最后写入提交标志，或使用 CRC/序列号作为隐式提交条件。

若控制器允许按最小编程单位写入，可采用“数据先写、提交字最后写”：

```
#define EEE_COMMIT 0xC33CC33Cu

typedef struct {
    uint32_t key;
    uint32_t sequence;
    uint32_t value;
    uint32_t crc;
    uint32_t commit;
} eee_slot_t;

static int eee_append(uintptr_t address, uint32_t key,
                      uint32_t sequence, uint32_t value)
{
    eee_slot_t slot = {0};
    slot.key = key;
    slot.sequence = sequence;
    slot.value = value;
    slot.crc = crc32((const uint8_t *)&slot,
                     offsetof(eee_slot_t, crc));
    slot.commit = 0xFFFFFFFFu;

    if (flash_program(address, &slot, offsetof(eee_slot_t, commit)) != 0) {
        return -1;
    }
    if (!flash_verify(address, &slot, offsetof(eee_slot_t, commit))) {
        return -2;
    }
    /* 提交标记必须是最后一次写入 */
    if (flash_program(address + offsetof(eee_slot_t, commit),
                      &(uint32_t){EEE_COMMIT}, sizeof(uint32_t)) != 0) {
        return -3;
    }
    return 0;
}
```

如果 MCU 不允许跨编程单位分步写入，应把提交信息编码到一个独立、对齐的编程单位中，或采用“双副本 + CRC”方案。

### 5.4 最新记录扫描

扫描时不能只找最后一个非空槽，而应选择：

- Key 匹配；
- Commit 正确；
- CRC 正确；
- 序列号最大且序列号关系合法。

序列号回绕比较可使用有符号差值：

```
static bool seq_newer(uint32_t a, uint32_t b)
{
    return (int32_t)(a - b) > 0;
}
```

该方法要求有效记录之间的序列号距离小于 `2^31`，并且不能用无界运行的序列号而不考虑回绕。

### 5.5 双页垃圾回收

典型流程：

```
当前页 Active 且空间足够
    └─ 追加新记录

当前页空间不足
    ├─ 擦除备用页
    ├─ 将所有 Key 的最新有效记录复制到备用页
    ├─ 校验备用页中的记录
    ├─ 将备用页标记为 Active
    ├─ 擦除旧页
    └─ 旧页转为备用页
```

切换顺序必须避免“两个页都被标记为 Active 后掉电”的歧义。可以使用单调状态编码，例如：`ERASED -> COPYING -> VALID -> RETIRED`，并为页头增加 generation 和 CRC。

### 5.6 并发与缓存一致性

- 多任务访问必须由 Mutex 保护，不能仅依靠 `volatile`。
- ISR 不应直接执行 Flash 擦除或复杂写入，应投递到存储任务。
- Cortex-M 某些 MCU 在 Flash 编程期间无法从同一 Bank 取指；代码可能需要放入 RAM，或使用双 Bank。
- 带 D-Cache 的 MCU 必须处理 Cache clean/invalidate，否则读回数据可能不是 Flash 的真实内容。

## 6. 性能量化分析

以下为**示例实测模型**，平台为 120 MHz Cortex-M4、单 Bank 内部 Flash、2 KB 页、8 字节编程单位；实际数据必须以目标 MCU 实测为准。

|操作|典型耗时|峰值 RAM|说明|
|---|---|---|---|
|编程 16 字节|0.15–0.35 ms|32–64 B|包含状态轮询与回读|
|擦除 2 KB 页|18–45 ms|64–256 B|电压、温度影响明显|
|扫描 2 KB 页|0.08–0.20 ms|32–128 B|取决于总线和校验算法|
|双页搬迁 32 个变量|5–12 ms 加擦除|128–512 B|取决于有效记录数量|

### 容量计算

设页大小为 `P`，页头为 `H`，记录大小为 `R`：

```
每页可容纳记录数 N = floor((P - H) / R)
有效变量容量 ≈ N - 磨损均衡和恢复保留量
```

例如 `P=2048 B`、`H=32 B`、`R=32 B`：

```
N = floor((2048 - 32) / 32) = 63 条记录
```

### 寿命估算

若每次垃圾回收产生 `K` 次物理页擦除，页额定擦除寿命为 `E`，每次逻辑更新平均占用 `R` 字节，则粗略寿命为：

```
逻辑更新次数 ≈ E × (有效日志容量 / 平均每次追加容量) / K
```

例如：单页有效空间 2016 B、单条记录 32 B、页寿命 10,000 次、双页轮换，理论量级约为：

```
10,000 × floor(2016 / 32) × 2 ≈ 1,260,000 次逻辑更新
```

实际寿命还会被搬迁写放大、频繁更新热点 Key、温度和异常掉电降低。

### 瓶颈与优化

- **最大瓶颈：页擦除延迟**。使用后台 GC、双 Bank 或 RAM 执行降低业务阻塞。
- **写放大过高**：合并多个参数后批量提交，减少元数据和搬迁次数。
- **启动扫描过慢**：保存页尾索引、使用固定长度记录和分层索引。
- **热点变量寿命不足**：使用计数器分片、位图计数、FRAM 或外部 EEPROM。

## 7. 应用场景选型指南

### 纯文本决策流程图

```
需要非易失存储
├─ 写入频率 > 每秒 1 次？
│  ├─ 是：是否允许外部器件？
│  │  ├─ 是：优先 FRAM / EEPROM
│  │  └─ 否：计数器分片、RAM 聚合、掉电批量提交
│  └─ 否：继续
├─ 数据量是否超过预留 Flash 区？
│  ├─ 是：外部 EEPROM/Flash 或扩大分区
│  └─ 否：继续
├─ 是否要求掉电原子性？
│  ├─ 是：双页日志 + CRC + 提交标志
│  └─ 否：简单双副本即可
└─ 是否要求大于 Flash 额定寿命？
   ├─ 是：磨损均衡或外部 FRAM
   └─ 否：EEPROM 模拟
```

|需求|方案|理由|
|---|---|---|
|设备地址、波特率、少量参数|双页追加日志|代码简单、容量足够|
|电机校准系数|A/B 参数镜像|需要整组一致提交|
|故障事件|多页循环日志|追加写入，支持按时间序列读取|
|电能累计值|RAM 聚合 + 周期提交|避免高频 Flash 磨损|
|OTA 版本配置|双 Bank/A-B 分区|与升级回滚机制协同|

## 8. 工程最佳实践

### 设计原则

1. **物理层、存储策略层、业务参数层分离**。
2. 所有 Flash 地址由链接脚本或分区表定义，禁止散落魔法地址。
3. 每条记录必须包含版本、长度、序列号和完整性校验。
4. 写入 API 必须明确同步/异步语义、最大阻塞时间和错误码。
5. 任何成功写入都必须支持读回校验。
6. 将“未初始化、损坏、版本不兼容、空间不足、Flash 错误”区分处理。

### 选型决策矩阵

|指标|双页日志|多页日志|A/B 镜像|外部 FRAM|
|---|---|---|---|---|
|实现复杂度|低|中高|中|中|
|高频写能力|中|高|低|很高|
|掉电恢复|高|高|很高|高|
|扩展容量|低|高|中|高|
|实时写延迟|中|中|低|高|

### 工业级编码规范

- 所有外部输入检查长度、Key 范围和版本。
- 不把 Flash 映射区直接强转成业务结构体后长期使用。
- 使用固定宽度整数，明确大小端和对齐。
- Flash 操作前后清理错误标志，超时退出并记录诊断码。
- 对编译器、链接器和 MCU 型号做静态断言与启动自检。

## 9. 常见错误与避坑指南

### 错误一：原地覆盖 Flash

错误代码：

```
*(uint32_t *)PARAM_ADDR = new_value; /* 试图直接覆盖 */
```

根因：Flash 不能将 `0` 直接恢复为 `1`，且可能违反编程序列和对齐要求。

正确实现：追加新记录，必要时整页擦除后重建。

风险：数据写不进去、旧值残留、控制器报错，严重时破坏相邻参数。

### 错误二：只写数据、不做 CRC 和提交标志

错误代码：

```
flash_program(addr, &value, sizeof(value));
```

根因：掉电可能发生在部分编程窗口，读取到“看似合理但实际损坏”的值。

正确实现：数据、序列号、CRC、提交标志分阶段写入，并进行回读验证。

风险：设备启动配置异常、校准参数失真，且故障难以复现。

### 错误三：每次计数器变化都擦页

错误代码：

```
for (;;) {
    counter++;
    flash_erase(PARAM_PAGE);
    flash_write(COUNTER_ADDR, &counter, sizeof(counter));
}
```

根因：忽视 Flash 擦除寿命和毫秒级擦除延迟。

正确实现：RAM 中聚合，定时或按增量阈值提交；高频场景采用位图计数或 FRAM。

风险：数小时/数天内耗尽寿命，并造成实时任务长时间阻塞。

### 错误四：用 `volatile` 解决并发

错误代码：

```
volatile bool storage_busy;
if (!storage_busy) {
    storage_busy = true;
    storage_write();
    storage_busy = false;
}
```

根因：检查与设置不是原子操作，两个任务可能同时进入。

正确实现：RTOS Mutex；ISR 通过队列通知存储任务。

风险：交叉写入、页切换状态损坏、偶发死锁或数据丢失。

### 错误五：记录序列号使用普通大小比较

错误代码：

```
if (a.sequence > newest.sequence) {
    newest = a;
}
```

根因：未处理 `uint32_t` 回绕。

正确实现：使用有符号差值比较，并限定有效序列号窗口。

风险：设备运行足够长时间后恢复到旧数据。

## 10. 多机制组合使用方案

推荐架构：**日志记录 + 双页 GC + CRC + 版本迁移 + 存储任务串行化**。

```
typedef struct {
    uint16_t key;
    uint16_t version;
    uint16_t length;
    uint16_t reserved;
    uint32_t sequence;
    uint8_t  payload[16];
    uint32_t crc;
    uint32_t commit;
} storage_record_t;

typedef struct {
    MutexHandle_t lock;
    QueueHandle_t request_queue;
    uint32_t next_sequence;
    uint32_t active_page;
} storage_ctx_t;

int storage_set(storage_ctx_t *ctx, uint16_t key,
                const void *data, uint16_t length)
{
    if (!ctx || !data || length == 0 || length > 16) {
        return STORAGE_EINVAL;
    }

    lock(ctx->lock);
    int rc = storage_append_or_gc(ctx, key, data, length);
    unlock(ctx->lock);
    return rc;
}

void storage_task(void *arg)
{
    storage_request_t req;
    for (;;) {
        if (queue_receive(storage_queue, &req, WAIT_FOREVER)) {
            int rc = storage_set(&g_storage, req.key,
                                 req.data, req.length);
            notify_requester(req, rc);
        }
    }
}
```

架构协同关系：

- **Mutex**：保证任务间串行化；
- **存储任务**：把耗时擦除从业务任务中隔离；
- **CRC/提交标志**：保证单条记录完整性；
- **双页 GC**：实现空间回收和磨损均衡；
- **版本迁移**：支持固件升级后的配置兼容；
- **故障日志**：记录 Flash 控制器错误、GC 次数和最后错误地址。

## 11. 工业级实际案例分析

### 案例一：变频器参数与电机校准

**需求：** 保存几十个参数，掉电不能出现“部分新参数、部分旧参数”，写入频率低。

**架构：** A/B 参数镜像，每个镜像包含 Header、版本、长度、参数数组、CRC 和 Commit；更新时写入非活动区，整体验证后切换。

**核心代码：**

```
int config_commit(const config_t *cfg)
{
    config_image_t image = {0};
    image.magic = CONFIG_MAGIC;
    image.version = CONFIG_VERSION;
    image.length = sizeof(*cfg);
    image.data = *cfg;
    image.crc = crc32((uint8_t *)&image,
                      offsetof(config_image_t, crc));

    if (write_image_to_inactive_page(&image) != 0) {
        return -1;
    }
    if (!verify_image(&image)) {
        return -2;
    }
    return commit_image_header(image.sequence);
}
```

**设计要点：** 参数校验必须在加载后执行；版本不兼容时使用迁移函数，而不是直接按旧布局解释。

### 案例二：工业网关故障事件日志

**需求：** 保存最近 500 条事件，支持重启后读取，事件写入频率可能短时间升高。

**架构：** 多页环形日志，每条记录含时间戳、故障码、上下文摘要、序列号和 CRC；后台任务执行页回收。

**设计要点：** 日志满时覆盖最旧页；不能在 ISR 中直接写 Flash；事件高峰期先进入 RAM 环形队列，定义溢出策略。

### 案例三：电池管理系统累计电量

**需求：** 累计值高频变化，不能因 Flash 写入阻塞采样控制环。

**架构：** RAM 保存实时累计值，每 10 秒或累计变化超过阈值时提交；使用双副本和 CRC。对关键计量值增加超级电容保持时间，确保提交窗口完成。

**设计要点：** 根据允许丢失的最大能量量化提交周期；例如每次最多允许丢失 0.1 Ah，则由最大电流和采样周期反推提交频率，而不是随意设定定时器。

## 12. 高频问题深度答疑

### 1. 为什么有 CRC 还需要双副本？

CRC 只能判断一份数据是否符合校验，不能保证设备一定拥有最新数据。双副本通过序列号解决“新旧选择”，CRC 解决“内容损坏”。两者职责不同。

### 2. 擦除过程中掉电会怎样？

目标页可能处于不可用状态，不能假设擦除是原子的。因此新页必须先写完整并验证，旧页最后才擦除；启动时从多个页中选择状态合法、generation 最新的页。

### 3. 提交标志为什么必须最后写？

因为提交标志代表记录对恢复逻辑可见。先提交后写数据，掉电会产生“有效标志指向不完整数据”。最后写提交标志可把可见性推迟到数据完成之后。

### 4. 是否应该每条记录都回读？

对关键参数建议回读；对高吞吐日志可在页级完成后校验，但必须评估 Flash 控制器错误检测能力、数据价值和故障概率。安全相关参数通常不能省略验证。

### 5. RTOS 中是否可以关闭中断执行擦除？

不应简单关闭中断。擦除可能持续几十毫秒，会破坏通信、控制和看门狗时序。应使用存储任务、RAM 函数、双 Bank、后台时机调度，并测量最坏阻塞时间。

### 6. 为什么不能只用一个递增版本号？

版本号解决新旧顺序，不解决内容完整性、地址损坏、长度错误和随机位翻转。工业实现至少需要 Magic、长度、版本/序列号、CRC 和提交状态。

## 13. 课程核心总结

- EEPROM 模拟的核心不是“模拟 EEPROM API”，而是构造**可恢复的 Flash 日志系统**。
- **数据先写、完整性验证、提交后置**是掉电安全的基本原则。
- **双页追加日志**适合低频参数；**多页循环日志**适合事件和较高写入量；**FRAM**适合高频持久化。
- 性能瓶颈排序通常为：**页擦除延迟 > 垃圾回收搬迁 > 编程耗时 > 扫描耗时**。
- 寿命设计必须同时考虑擦除次数、写放大、热点 Key、温度和异常掉电。
- Flash NVM 驱动必须提供：错误码、超时、回读、CRC、版本迁移、并发保护和故障诊断。

## 16. 实践与进阶路径

### 梯度实战任务

1. **任务一：** 实现固定长度单页追加日志，加入 CRC 和回读校验。
2. **任务二：** 扩展为双页 GC，模拟掉电点覆盖所有写入阶段。
3. **任务三：** 加入序列号回绕、页 generation 和版本迁移。
4. **任务四：** 实现 RTOS 存储任务，测量业务任务最大阻塞时间。
5. **任务五：** 实现多页事件日志，支持按时间序列读取和最旧页覆盖。
6. **任务六：** 在真实硬件上进行 10 万次循环写入，统计错误率、擦除时间分布和温度影响。

### 性能测试方法

- 用 GPIO 在 Flash 编程、擦除前后打点，示波器测量真实时延。
- 通过电源 MOSFET 或可编程电源在每个写入阶段随机断电。
- 测试低压、低温、高温、最大总线负载和看门狗边界。
- 统计：启动扫描时间、GC 最坏延迟、写放大、有效恢复率、错误地址分布。
- 使用静态分析检查越界、整数溢出、未初始化 padding 和锁顺序。

### 进阶学习方向

- Flash Translation Layer（FTL）与日志结构文件系统。
- NOR Flash ECC、Cache、双 Bank 和读写并行机制。
- 安全存储：HMAC、AES-GCM、反回滚计数器和密钥隔离。
- OTA 升级中的配置迁移、断点续传和 A/B 回滚。
- 面向 IEC 61508、ISO 26262 的 NVM 完整性、诊断覆盖率和故障注入验证。
