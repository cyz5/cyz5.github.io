
## 1. 学习目标

### 理解

- 理解**硬件调试不是“换器件试错”，而是基于可观测证据、时序约束和故障假设逐层收敛的工程过程**。
- 理解硬件故障的主要边界：电源、时钟、复位、启动介质、总线、信号完整性、电源完整性、EMC、热和制造缺陷。
- 理解“现象、事实、推断、验证结论”之间的区别。
- 理解调试中最重要的三个问题：
    1. 系统是否真正上电。
    2. CPU 是否真正取指并执行。
    3. 故障发生在硬件、固件、接口还是测试方法本身。

### 掌握

- 掌握从现象到根因的分层排查流程。
- 掌握万用表、示波器、逻辑分析仪、JTAG/SWD、协议分析仪、电流探头、热像仪和电源分析仪的正确使用边界。
- 掌握电源、时钟、复位、启动、存储器和通信接口的调试方法。
- 掌握最小系统、二分法、替换法、隔离法、故障注入和对照实验。
- 掌握硬件调试数据记录、复现率统计和版本关联方法。

### 精通

- 能够根据波形、寄存器、总线事务和电流指纹推断故障阶段。
- 能够定位间歇性故障、温度相关故障、负载相关故障和制造偏差故障。
- 能够区分测量仪器引入的负载、探头伪影、JTAG 干扰和真实板级问题。
- 能够建立硬件、固件、测试、生产和供应链协同的故障闭环。

### 能够设计

- 能够设计具备测试点、调试接口、边界扫描、故障日志、可控启动和安全降级能力的产品。
- 能够制定硬件调试计划、故障树、证据矩阵和问题关闭标准。
- 能够为量产设计 ICT、FCT、老化、边界条件和自动化诊断方案。
- 能够把调试能力前移到原理图、PCB、BSP 和固件架构阶段。

## 3. 技术概述

### 3.1 硬件调试的目标

硬件调试的最终目标不是证明“某个器件坏了”，而是确定：

```
故障是否真实
→ 故障发生在哪个阶段
→ 故障边界是什么
→ 哪个变量改变会影响故障
→ 根因是否被独立实验验证
→ 修复是否引入新风险
```

### 3.2 故障分层模型

```
产品不工作
├─ 外部条件
│  ├─ 输入电压/极性
│  ├─ 负载/线缆
│  ├─ 温度/湿度
│  └─ 测试设备
│
├─ 能量层
│  ├─ 输入保护
│  ├─ DC/DC/LDO
│  ├─ 电源时序
│  └─ 过流/欠压
│
├─ 时基层
│  ├─ 晶振
│  ├─ PLL
│  ├─ 时钟树
│  └─ 复位释放
│
├─ 执行层
│  ├─ CPU 取指
│  ├─ SRAM/Flash
│  ├─ Cache/MPU
│  └─ 异常处理
│
├─ 互连层
│  ├─ SPI/I²C/UART
│  ├─ CAN/RS-485
│  ├─ USB/Ethernet
│  └─ DMA/中断
│
└─ 系统层
   ├─ 业务状态机
   ├─ 热与 EMC
   ├─ 制造偏差
   └─ 长期可靠性
```

### 3.3 典型调试阶段

|阶段|关键问题|主要工具|
|---|---|---|
|上电前|是否存在短路、反接和装配错误|目检、万用表、限流电源|
|上电瞬间|浪涌、时序、过流是否正常|示波器、电流探头|
|最小系统|CPU 是否运行|SWD/JTAG、GPIO、UART|
|启动阶段|取指、Flash、时钟、复位是否正常|调试器、逻辑分析仪|
|外设阶段|总线事务和电气电平是否正确|协议分析仪、示波器|
|满载阶段|PI、SI、热、EMC 是否越界|示波器、热像仪、频谱仪|
|量产阶段|是否可重复筛除边界样品|ICT、FCT、自动化测试|

## 4. 核心特性横向对比

### 4.1 调试工具对比

|工具|最擅长发现|不擅长发现|关键注意事项|
|---|---|---|---|
|万用表|直流电压、电阻、通断|纳秒级瞬态、时序|输入阻抗和测量参考点|
|示波器|电源、时钟、复位、时序|协议长期统计|探头、带宽、触发设置|
|逻辑分析仪|数字协议和长时间事件|模拟过冲、地弹|阈值设置可能掩盖问题|
|JTAG/SWD|CPU 状态、寄存器、内存|CPU 未上电或时钟失效|连接本身可能改变系统|
|协议分析仪|USB/Ethernet/CAN 事务|芯片端电气波形|不等于物理层合格|
|电流探头|启动、负载、异常电流|电压根因|带宽、零点和磁芯方向|
|热像仪|热点、局部发热、异常功耗|隐藏焊点、低功率故障|发射率和空间分辨率|
|频谱仪|EMI 峰值和频段|根因位置|需结合近场与共模测量|
|TDR/VNA|阻抗、反射、互连损耗|CPU 逻辑|连接器、夹具和校准|

### 4.2 调试策略对比

|策略|适用场景|优点|风险|
|---|---|---|---|
|分层隔离|不确定故障|逻辑清晰|需要可控接口|
|二分法|大系统、路径较长|收敛快|切分不合理会丢失故障|
|替换法|可疑器件或模块|验证速度快|可能掩盖系统性根因|
|对照法|好板/坏板比较|适合间歇故障|样品差异需控制|
|故障注入|边界和恢复验证|可重复|注入能量需受控|
|统计法|量产和低概率故障|可量化|需要足够样本量|

### 4.3 示波器测量方式对比

|方式|适用|优点|局限|
|---|---|---|---|
|单端探头|低频、共地信号|简便|地线电感、地环路|
|差分探头|浮地、开关节点|抑制共模|CMRR 随频率下降|
|有源探头|高速低负载|带宽高、寄生小|成本高、过压能力有限|
|同轴焊接|电源纹波和高速点|回路短、重复性好|需预留测试结构|
|电流探头|启动和动态负载|非侵入式|只能测电流，不能直接定位电压|

## 5. 底层原理与功能特性深度解析

### 5.1 证据驱动的调试闭环

每个问题都应建立记录：

```
现象：什么情况下失败
事实：仪器实际测到什么
假设：最可能的根因是什么
实验：只改变哪个变量
结果：故障是否变化
结论：排除/确认什么
后续：下一步验证什么
```

不要把“更换电容后恢复”直接等同于“电容是根因”。更换动作可能同时改变了：

- 机械应力。
- 焊点接触。
- 测试探头位置。
- 电源负载。
- 温度。
- 接地路径。

### 5.2 上电前安全检查

#### 目检项目

- 器件方向、极性和料号。
- BGA/QFN/LGA 焊接桥连和虚焊。
- 连接器、跳线和测试点。
- 电源域是否存在反向连接。
- 保护器件是否装反。
- 过孔、铜皮和螺丝是否造成短路。
- 未装器件是否导致悬空关键节点。

#### 无源检查

```
/* 测试程序中不应直接把未确认的电阻值作为硬编码结论。 */
typedef struct {
    uint32_t rail_id;
    uint32_t measured_mv;
    uint32_t expected_min_mv;
    uint32_t expected_max_mv;
    bool pass;
} rail_measurement_t;

bool rail_measurement_valid(const rail_measurement_t *m)
{
    if (m == NULL) {
        return false;
    }

    return (m->measured_mv >= m->expected_min_mv) &&
           (m->measured_mv <= m->expected_max_mv);
}
```

上电前应使用限流电源，从低电压开始逐步升压，监控：

- 输入电流。
- 各电源轨电压。
- 稳压器温度。
- 过流指示。
- 关键电容和芯片异常发热。

### 5.3 电源优先调试

电源调试顺序：

```
输入端
→ 保护后
→ 稳压器输入
→ 稳压器输出
→ 负载点
→ 芯片电源引脚
→ 负载阶跃下的动态波形
```

必须分别验证：

- 静态电压。
- 上电斜率。
- 电源时序。
- Power-Good。
- 纹波频谱。
- 负载瞬态。
- 欠压、过压和短路行为。

**只测稳压器输出，不测芯片电源引脚，是常见的错误。**

### 5.4 时钟调试

时钟异常可能导致：

- CPU 无法运行。
- SWD 连接失败。
- UART 波特率错误。
- USB/Ethernet 失步。
- ADC 采样频率错误。
- 看门狗异常。

#### 调试顺序

1. 检查晶振供电和地。
2. 检查晶振负载电容和布局。
3. 检查外部时钟输入幅度和占空比。
4. 检查 PLL 输入范围。
5. 读取时钟切换和失效标志。
6. 使用低频内部 RC 旁路外部晶振。
7. 分别验证 CPU、总线和外设时钟。

#### 时钟旁路代码

```
typedef enum {
    CLOCK_SOURCE_INTERNAL = 0,
    CLOCK_SOURCE_EXTERNAL,
    CLOCK_SOURCE_PLL
} clock_source_t;

bool clock_start_with_fallback(void)
{
    if (clock_enable_internal_rc()) {
        clock_select_source(CLOCK_SOURCE_INTERNAL);

        if (clock_configure_safe_bus_dividers()) {
            return true;
        }
    }

    if (clock_enable_external_oscillator(100U)) {
        clock_select_source(CLOCK_SOURCE_EXTERNAL);
        return clock_configure_pll();
    }

    fault_log_stage_in_backup_ram(FAULT_CLOCK_STARTUP);
    return false;
}
```

启动故障时，先用内部 RC 建立可调试环境，可以区分“晶振路径问题”和“CPU/固件问题”。

### 5.5 复位调试

需要同时观察：

- POR/BOR 输出。
- 外部复位监控器输出。
- NRST 电压。
- 复位释放时间。
- 电源稳定时间。
- 看门狗复位。
- 软件主动复位。
- 调试器复位行为。

#### 复位原因必须最早保存

```
typedef struct {
    uint32_t raw_reset_flags;
    uint32_t boot_count;
    uint32_t crc32;
} reset_snapshot_t;

void capture_reset_reason_early(void)
{
    reset_snapshot_t snapshot;

    snapshot.raw_reset_flags = platform_read_reset_flags_raw();
    snapshot.boot_count =
        backup_register_read(BOOT_COUNT_REG) + 1U;
    snapshot.crc32 = crc32_compute(
        &snapshot,
        sizeof(snapshot) - sizeof(snapshot.crc32));

    backup_sram_write(&snapshot, sizeof(snapshot));
    backup_register_write(BOOT_COUNT_REG,
                          snapshot.boot_count);

    /* 读取后再清除，禁止先清除后分析。 */
    platform_clear_reset_flags();
}
```

### 5.6 CPU 是否真的运行

推荐设置多级可观测点：

```
复位释放
→ 启动 GPIO 翻转
→ C 运行时初始化完成
→ 时钟配置完成
→ 内存初始化完成
→ 外设初始化完成
→ 主循环心跳
→ 业务状态心跳
```

```
void debug_boot_stage(uint32_t stage)
{
    /*
     * 该函数必须尽量无依赖，可使用专用 GPIO、备份寄存器或 ITM。
     */
    platform_debug_gpio_write(stage & 0x0FU);
    backup_register_write(DEBUG_STAGE_REG, stage);
}

void system_boot(void)
{
    capture_reset_reason_early();
    debug_boot_stage(1U);

    if (!clock_start_with_fallback()) {
        debug_boot_stage(0xE1U);
        system_safe_halt();
    }
    debug_boot_stage(2U);

    if (!memory_init()) {
        debug_boot_stage(0xE2U);
        system_safe_halt();
    }
    debug_boot_stage(3U);

    if (!peripheral_init_minimal()) {
        debug_boot_stage(0xE3U);
        system_safe_halt();
    }
    debug_boot_stage(4U);
}
```

对启动早期代码，不应依赖：

- 尚未初始化的 UART。
- 尚未配置的 DMA。
- 可能异常的外部 Flash。
- 尚未稳定的 RTOS。
- 需要堆内存的日志系统。

### 5.7 JTAG/SWD 调试边界

调试器可以获取：

- PC、SP、LR 和通用寄存器。
- 异常状态寄存器。
- Fault 地址寄存器。
- 栈内容和调用链。
- 外设寄存器。
- 内存和 Flash 内容。

但连接失败不一定表示 MCU 损坏，可能是：

- 芯片未上电或电压不合格。
- SWDIO/SWCLK 被外设占用。
- 复位脚被拉住。
- 调试时钟过快。
- 安全启动或调试锁定。
- 目标地与调试器地存在电位差。
- 目标板被外部电路反向供电。
- 低功耗状态关闭调试域。

排查顺序：

```
目标电源
→ GND 连续性
→ VTref
→ nRESET
→ SWDIO/SWCLK 波形
→ 降低调试频率
→ Connect Under Reset
→ 读取 IDCODE
→ 检查安全配置
```

### 5.8 Fault 调试

Cortex-M 常见故障寄存器：

- HFSR。
- CFSR。
- MMFAR。
- BFAR。
- DFSR。
- AFSR。
- R0～R3、R12、LR、PC、xPSR。

#### HardFault 捕获框架

```
#include <stdint.h>

typedef struct {
    uint32_t r0;
    uint32_t r1;
    uint32_t r2;
    uint32_t r3;
    uint32_t r12;
    uint32_t lr;
    uint32_t pc;
    uint32_t xpsr;
    uint32_t cfsr;
    uint32_t hfsr;
    uint32_t mmfar;
    uint32_t bfar;
} fault_context_t;

__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile (
        "tst lr, #4                 \n"
        "ite eq                     \n"
        "mrseq r0, msp               \n"
        "mrsne r0, psp               \n"
        "b hardfault_capture        \n"
    );
}

void hardfault_capture(const uint32_t *stack)
{
    fault_context_t context;

    if (stack == NULL) {
        platform_system_reset();
    }

    context.r0 = stack[0];
    context.r1 = stack[1];
    context.r2 = stack[2];
    context.r3 = stack[3];
    context.r12 = stack[4];
    context.lr = stack[5];
    context.pc = stack[6];
    context.xpsr = stack[7];
    context.cfsr = platform_read_cfsr();
    context.hfsr = platform_read_hfsr();
    context.mmfar = platform_read_mmfar();
    context.bfar = platform_read_bfar();

    backup_sram_write(&context, sizeof(context));
    fault_log_stage_in_backup_ram(FAULT_HARDFAULT);

    platform_force_outputs_safe();
    platform_system_reset();

    for (;;) {
        /* 防止编译器优化掉故障停机路径。 */
    }
}
```

工程上应进一步验证：

- PC 是否落在合法代码区。
- LR 是否为合法返回地址。
- 栈指针是否对齐并落在有效 RAM。
- CFSR 中是 MemManage、BusFault 还是 UsageFault。
- 是否发生在中断上下文。
- 是否与电源、DMA、Cache 或 MPU 配置相关。

### 5.9 总线调试

#### I²C

检查：

- SDA/SCL 上拉阻值。
- 上升时间。
- 起始、停止和 ACK。
- 总线是否被从设备拉低。
- 电平是否匹配。
- 总线恢复时钟。

```
bool i2c_bus_recover(void)
{
    i2c_disable_peripheral();
    gpio_configure_open_drain(I2C_SCL_PIN);
    gpio_configure_open_drain(I2C_SDA_PIN);

    gpio_write(I2C_SDA_PIN, true);

    for (uint32_t i = 0U; i < 9U; ++i) {
        gpio_write(I2C_SCL_PIN, false);
        platform_delay_us(5U);
        gpio_write(I2C_SCL_PIN, true);
        platform_delay_us(5U);

        if (gpio_read(I2C_SDA_PIN)) {
            break;
        }
    }

    /* 产生 STOP 条件。 */
    gpio_write(I2C_SDA_PIN, false);
    platform_delay_us(5U);
    gpio_write(I2C_SCL_PIN, true);
    platform_delay_us(5U);
    gpio_write(I2C_SDA_PIN, true);

    i2c_enable_peripheral();
    return gpio_read(I2C_SDA_PIN) &&
           gpio_read(I2C_SCL_PIN);
}
```

#### SPI

检查：

- CPOL/CPHA。
- CS 建立和保持时间。
- CLK 边沿、过冲和串扰。
- MISO 是否被多个设备同时驱动。
- DMA 缓存一致性。
- 发送端和接收端实际采样点。

#### CAN/RS-485

检查：

- 收发器供电。
- 终端电阻位置。
- 共模范围。
- DE/RE 时序。
- 总线错误计数。
- 总线关闭恢复。
- 线缆屏蔽和接地。

### 5.10 测量方法自身的影响

典型测量错误：

- 用长鳄鱼夹测高速时钟或电源纹波。
- 示波器地夹接到不合理的远端地。
- 差分探头共模范围不足。
- 探头输入电容改变了被测节点。
- 逻辑分析仪阈值设置错误。
- 电流探头未消磁或零点漂移。
- 使用自动量程导致关键瞬态丢失。
- 示波器带宽限制掩盖真实尖峰。

每份调试记录至少包含：

```

```

## 6. 性能量化分析

### 6.1 示例平台

```
MCU：Cortex-M7，400 MHz
输入：24 VDC
电源轨：5 V、3.3 V、1.2 V
主时钟：25 MHz 晶振 + PLL
示波器：1 GHz，5 GSa/s
调试器：SWD，默认 4 MHz
通信：CAN FD、QSPI、Ethernet
环境：25°C，额定输入，最大业务负载
```

以下数据为典型工程示例，用于说明测试方法，不代表所有器件保证值。

### 6.2 调试阶段的观测指标

|指标|正常示例|异常示例|可能方向|
|---|---|---|---|
|上电浪涌|0.8 A，3 ms|3.5 A，持续|短路、时序、负载未限流|
|3.3 V 纹波|12 mVpp|85 mVpp|PDN、稳压环路、负载突变|
|1.2 V 瞬态跌落|28 mV|110 mV|去耦、路径阻抗、环路|
|NRST 低电平宽度|8 ms|反复 0.2 ms|电源、EMC、看门狗|
|晶振启动时间|2.5 ms|>100 ms|负载、电容、布局、器件|
|CPU 首个 GPIO 标记|4.1 ms|无|复位、时钟、启动介质|

|MCU 工作电流|180 mA|450 mA|外设异常、短路、振荡|

### 6.3 启动时间预算

启动总时间：

Tboot=Tpower+Tclock+Treset+Tmemory+Tdriver+TapplicationTboot​=Tpower​+Tclock​+Treset​+Tmemory​+Tdriver​+Tapplication​

例如：

```
电源稳定：       5 ms
晶振/PLL：        3 ms
复位释放：        2 ms
外部 Flash：      8 ms
驱动初始化：     12 ms
应用自检：        20 ms
```

Tboot=5+3+2+8+12+20=50msTboot​=5+3+2+8+12+20=50ms

若产品偶发启动超过 200 ms，应把时间分段打点，不能只测最终“是否启动”。

### 6.4 复现率统计

故障复现率：

Pfail=NfailNtotalPfail​=Ntotal​Nfail​​

例如 10,000 次启动失败 7 次：

Pfail=7×10−4Pfail​=7×10−4

若需要估算比例的不确定性，可使用二项分布置信区间；样本量较小时，不应以“测试 100 次没失败”宣称零故障。

### 6.5 温度加速与边界扫描

至少构造以下矩阵：

|维度|低边界|典型|高边界|
|---|---|---|---|
|输入电压|最小工作值|标称值|最大工作值|
|温度|最低温|室温|最高温|
|负载|空载|典型|最大负载|
|通信|空闲|常规|满负载|
|时钟|最低速|标准|最高速|
|线缆|短线|标准线|最长线|
|器件|不同批次|主批次|边界批次|

**必须测试组合边界，而不是只测试单变量边界。** 例如最低输入电压、高温、最大负载和最大通信流量往往同时出现。

### 6.6 调试接口性能

SWD/JTAG 连接失败时，可按以下量级逐步降低频率：

```
4 MHz → 2 MHz → 1 MHz → 400 kHz
```

这不是性能优化，而是为了判断：

- 走线反射。
- 调试线负载过大。
- 目标时钟不稳定。
- 复位期间无法响应。
- 调试器和目标板电平不匹配。

### 6.7 热定位量化

芯片结温近似：

TJ=TA+PθJATJ​=TA​+PθJA​

功耗可从电源测得：

P≈Vrail⋅IrailP≈Vrail​⋅Irail​

如果 1.2 V 核心电源从 0.8 A 增加到 1.4 A：

ΔP=1.2×(1.4−0.8)=0.72WΔP=1.2×(1.4−0.8)=0.72W

异常增量应进一步区分：

- 软件是否开启了错误外设。
- 电源是否振荡。
- 芯片是否发生内部短路。
- 负载是否被异常驱动。
- 测量是否包含其他电源域。

### 6.8 性能瓶颈与收益

|调试瓶颈|低效做法|优化方法|典型收益|
|---|---|---|---|
|无法复现|反复人工操作|自动化刺激和日志|复现周期从小时降至分钟|

|误判测量|长地线、错误阈值|标准化测量夹具|降低伪影和争议|

│

## 8. 工程最佳实践

### 8.1 调试原则

1. **先保护样品，再获取证据。**
2. **从电源、复位、时钟和最小系统开始，不要一上来追业务协议。**
3. **每次实验只改变一个主要变量。**
4. **优先使用无创测量，再使用拆件和飞线。**
5. **波形必须在正确位置、正确带宽和正确参考点测量。**
6. **好板和坏板必须在完全相同配置下对照。**
7. **临时飞线、探头和调试器都要记录，因为它们会改变系统。**
8. **所有间歇性故障都必须量化复现率。**
9. **修复后必须验证原始故障、边界条件和回归风险。**
10. **没有独立验证的推断不能作为根因关闭问题。**

### 8.2 调试设计决策矩阵

|设计能力|无|基础|工业级|
|---|---|---|---|
|电源测试点|少量板边测试点|各主要电源轨|负载点、Kelvin、动态测试位|
|调试接口|仅量产烧录口|SWD/JTAG|SWD/JTAG、UART、Trace、复位控制|
|启动观测|无|一个 LED|阶段 GPIO、备份寄存器、早期日志|
|故障记录|无|软件日志|早期复位、CRC、时间戳、持久化策略|
|外设自检|无|启动自检|运行时健康监控和故障注入|
|测试模式|无|固定测试固件|自动化可配置测试固件|
|量产诊断|人工目检|FCT|ICT/FCT/边界扫描/追溯|
|安全恢复|软件重启|看门狗|硬件关断、独立监控、故障锁存|

### 8.3 原理图与 PCB 调试友好性

- 每个电源域预留测量点。
- 关键电源支持串联 0 Ω 或电流测量位。
- 复位、时钟、启动模式和 Power-Good 预留观测点。
- 高速接口预留受控阻抗测试结构，避免长 Stub。

- 对危险输出预留硬件强制关闭点。
- 标记信号方向、电源域和测试点名称。

## 9. 常见错误与避坑指南

### 9.1 错误一：一上来就换芯片

#### 错误操作

```
现象：MCU 不启动
动作：立即更换 MCU
结果：新 MCU 仍不启动
```

#### 根因分析

没有先验证：

- 电源。
- 复位。
- 时钟。
- 启动模式。
- Flash 供电。
- SWD 连接。
- PCB 焊接。

#### 正确实现

```
输入电源
→ 各电源轨
→ NRST
→ 时钟
→ SWD IDCODE
→ 启动引脚
→ 芯片取指
→ 外部存储器
```

#### 风险影响

- 浪费器件和时间。
- 破坏原始故障证据。
- 把系统性设计问题误判为器件故障。

---

### 9.2 错误二：用逻辑分析仪代替示波器

#### 错误操作

```
逻辑分析仪显示 SPI 数据正确
结论：SPI 电气信号没有问题
```

#### 根因分析

逻辑分析仪通常只判断采样点是否越过阈值，可能无法发现：

- 过冲和下冲。
- 振铃造成的边沿重复。
- 接收端 Setup/Hold 裕量不足。
- 电源地弹。
- 临界温度下的模拟波形退化。

#### 正确实现

```
协议层：逻辑分析仪/协议分析仪
物理层：示波器/差分探头
电源层：电源探头/电流探头
系统层：CRC、超时、错误计数和压力测试
```

#### 风险影响

- 量产后出现偶发误码。
- 只能通过降速掩盖问题。
- 无法定位接收端实际波形。

---

### 9.3 错误三：示波器长地线测量高速节点

#### 错误代码或操作

```
探头尖端接 1.2 V 电源
10 cm 鳄鱼夹接远端 GND
观察到 200 mVpp 高频振铃
```

#### 根因分析

地线寄生电感与探头电容构成谐振回路，测得波形可能主要是探头伪影。

#### 正确实现

- 使用电源轨专用探头。
- 使用短地弹簧或同轴焊接。
- 在负载点测量。
- 同时记录带宽限制和全带宽结果。
- 让好板、坏板使用相同探头和位置。

#### 风险影响

- 对不存在的振铃进行错误整改。
- 修改补偿网络后导致真实不稳定。
- 好板和坏板结论失真。

---

### 9.4 错误四：无限重试掩盖硬件故障

#### 错误代码

```
void peripheral_init(void)
{
    while (!sensor_init()) {
        /* 错误：没有超时、计数和故障记录。 */
    }
}
```

#### 根因分析

- 总线被锁死时 CPU 永久阻塞。
- 失去故障发生位置。
- 看门狗可能被错误任务喂养。
- 系统无法进入可诊断状态。

#### 正确实现

```
#define SENSOR_INIT_RETRY_MAX  3U

bool sensor_init_bounded(void)
{
    for (uint32_t retry = 0U;
         retry < SENSOR_INIT_RETRY_MAX;
         ++retry) {
        if (sensor_init_with_timeout(20U)) {
            return true;
        }

        sensor_bus_recover();
        platform_delay_ms(2U);
    }

    fault_log_stage_in_backup_ram(FAULT_SENSOR_INIT);
    sensor_enter_safe_state();
    return false;
}
```

#### 风险影响

- 设备看似“卡死”。
- 现场无法自动恢复。
- 故障率统计失真。
- 安全输出状态不确定。

---

### 9.5 错误五：先清除复位标志再读取

#### 错误代码

```
void boot_init(void)
{
    platform_clear_reset_flags();
    uint32_t reason = platform_read_reset_flags();
    log_reset_reason(reason);
}
```

#### 根因分析

清除动作破坏了最关键的故障证据，导致 Brownout、看门狗和外部复位无法区分。

#### 正确实现

```
void boot_init_correct(void)
{
    uint32_t reason = platform_read_reset_flags_raw();

    backup_register_write(LAST_RESET_REASON, reason);
    platform_clear_reset_flags();

    log_reset_reason(reason);
}
```

#### 风险影响

- 间歇性复位无法定位。
- EMC 与软件故障混淆。
- 现场数据不足以支持根因分析。

---

### 9.6 错误六：只在常温和空载下验证

#### 错误操作

```
室温、额定电压、空载启动 100 次全部通过
结论：硬件可靠
```

#### 根因分析

很多故障只在以下组合出现：

- 最低输入电压。
- 最高温度。
- 最大负载。
- 最大通信流量。
- 长线缆和外部干扰。
- 不同器件批次。

#### 正确实现

建立自动化边界矩阵，并记录每次测试的：

- 电源波形。
- 电流。
- 温度。
- 复位原因。
- 通信错误。
- 启动时间。
- 软件和硬件版本。

#### 风险影响

- 现场才暴露边界缺陷。
- 量产批次差异导致低良率。
- 认证、老化或客户环境中失败。

---

### 10.2 分层自检框架

```
typedef enum {
    SELF_TEST_POWER = 0,
    SELF_TEST_CLOCK,
    SELF_TEST_MEMORY,
    SELF_TEST_GPIO,
    SELF_TEST_BUS,
    SELF_TEST_APPLICATION
} self_test_item_t;

typedef struct {
    uint32_t passed_bitmap;
    uint32_t failed_bitmap;
    uint32_t first_failed_item;
    uint32_t duration_ms;
} self_test_report_t;

bool run_self_test(self_test_report_t *report)
{
    if (report == NULL) {
        return false;
    }

    *report = (self_test_report_t){0};
    report->first_failed_item = UINT32_MAX;

    if (platform_power_rails_valid()) {
        report->passed_bitmap |= 1UL << SELF_TEST_POWER;
    } else {
        report->failed_bitmap |= 1UL << SELF_TEST_POWER;
        report->first_failed_item = SELF_TEST_POWER;
        return false;
    }

    if (platform_clock_frequency_valid()) {
        report->passed_bitmap |= 1UL << SELF_TEST_CLOCK;
    } else {
        report->failed_bitmap |= 1UL << SELF_TEST_CLOCK;
        report->first_failed_item = SELF_TEST_CLOCK;
        return false;
    }

    if (memory_quick_test()) {
        report->passed_bitmap |= 1UL << SELF_TEST_MEMORY;
    } else {
        report->failed_bitmap |= 1UL << SELF_TEST_MEMORY;
        report->first_failed_item = SELF_TEST_MEMORY;
        return false;
    }

    if (gpio_loopback_test()) {
        report->passed_bitmap |= 1UL << SELF_TEST_GPIO;
    } else {
        report->failed_bitmap |= 1UL << SELF_TEST_GPIO;
        report->first_failed_item = SELF_TEST_GPIO;
        return false;
    }

    if (communication_loopback_test()) {
        report->passed_bitmap |= 1UL << SELF_TEST_BUS;
    } else {
        report->failed_bitmap |= 1UL << SELF_TEST_BUS;
        report->first_failed_item = SELF_TEST_BUS;
        return false;
    }

    report->duration_ms = platform_get_tick_ms();
    return true;
}
```

### 10.3 外设诊断统一接口

```
typedef struct {
    bool (*init)(void);
    bool (*health_check)(void);
    bool (*recover)(void);
    uint32_t (*get_error_count)(void);
    void (*force_safe)(void);
} diagnostic_driver_t;

typedef struct {
    uint32_t check_count;
    uint32_t error_count;
    uint32_t recovery_count;
    bool online;
} diagnostic_state_t;

bool diagnostic_poll(const diagnostic_driver_t *driver,
                     diagnostic_state_t *state)
{
    if ((driver == NULL) || (state == NULL) ||
        (driver->health_check == NULL) ||
        (driver->recover == NULL) ||
        (driver->force_safe == NULL) ||
        (driver->get_error_count == NULL)) {
        return false;
    }

    state->check_count++;
    state->error_count = driver->get_error_count();

    if (driver->health_check()) {
        state->online = true;
        return true;
    }

    state->online = false;
    driver->force_safe();

    if (state->recovery_count < 3U && driver->recover()) {
        state->recovery_count++;
        state->online = true;
        return true;
    }

    fault_log_stage_in_backup_ram(FAULT_DIAGNOSTIC_FAILED);
    return false;
}
```

## 11. 工业级实际案例分析

### 11.1 案例一：首板无法通过启动，自研控制器无串口输出

#### 需求

- Cortex-M7。
- 外部 QSPI Flash 启动。
- 25 MHz 晶振。
- 1.2 V、1.8 V、3.3 V 多电源域。
- 需要支持 SWD 下载和量产启动。

#### 现象

- 3.3 V 电源存在。
- SWD 偶尔可连接。
- UART 无输出。
- 更换软件版本无改善。

#### 调试证据

1. 1.2 V 负载点只有 1.08 V。
2. 25 MHz 晶振无稳定振荡。
3. NRST 在上电后反复出现窄脉冲。
4. QSPI CLK 没有活动。
5. 降低 SWD 频率后可读到芯片 ID，但无法稳定运行。

#### 根因

- 1.2 V Buck 反馈分压焊接错误。
- 晶振负载电容与实际器件不匹配。
- 外部复位监控器门限设置错误，导致核心电源尚未稳定就反复复位。

#### 修复

- 修正反馈网络。
- 按晶振等效负载重新计算电容。
- 调整复位门限和延时。
- 使用内部 RC 先启动，再切换外部晶振。
- 增加电源、NRST、晶振和启动阶段测试点。

#### 结果

|指标|修复前|修复后|
|---|---|---|
|1.2 V 负载点|1.08 V|1.20 V|
|晶振启动|不稳定|2.7 ms 内稳定|
|NRST 反复脉冲|有|无|
|SWD 连接成功率|约 40%|100%|
|QSPI 启动成功率|0%|100%|

#### 设计要点

- “无串口”不能直接推断为 UART 驱动问题。
- QSPI 没有活动前，应先确认 CPU 已经执行到访问外部 Flash 的位置。
- 电源、时钟和复位必须同步测量。

### 11.2 案例二：高温满载下随机死机

#### 需求

- 400 MHz MCU。
- Ethernet 满负荷。
- SDRAM 和 QSPI 并行访问。
- 工作温度 -40°C～85°C。
- 24 小时稳定运行。

#### 现象

- 室温空载运行正常。
- 70°C 以上、Ethernet 满负荷时偶发死机。
- 日志有时显示 HardFault，有时显示看门狗复位。
- 降低 CPU 主频后故障明显减少。

#### 调试过程

1. 增加 HardFault 栈捕获，发现部分 PC 落在非法地址。
2. 测量 1.2 V 负载点，发现 DMA/Cache 同时活动时跌落 95 mV。
3. 观察 QSPI 接收端波形，发现高温下过冲和采样窗口缩小。
4. 检查 MPU 和 Cache，发现 DMA 缓冲区未做一致性维护。
5. 发现高温下稳压器有效输出电容降低，环路恢复变慢。

#### 根因

这是**电源完整性、信号完整性和软件 Cache 一致性共同造成的复合问题**，不能只归因于 HardFault。

#### 修复

- 优化 1.2 V 去耦和负载点供电路径。
- 调整 Buck 补偿并完成温度验证。
- QSPI 源端增加串联阻尼。
- 对 DMA 缓冲区执行 Cache Clean/Invalidate。
- 降低高温条件下的最高通信速率。
- 将 HardFault 上下文写入备份 SRAM。

#### 结果

|指标|修复前|修复后|
|---|---|---|
|70°C 满载 24 h 死机|5 次|0 次|
|1.2 V 最大跌落|95 mV|31 mV|
|QSPI CRC 错误|约 10⁻⁵|未观测到|
|HardFault 可定位率|约 30%|100%|
|高温最高稳定速率|40 MHz|80 MHz|

#### 设计要点

- 降频有效并不代表降频是根因修复。
- HardFault 可能是电源、总线或内存一致性问题的最终表现。
- 必须同步看电源波形、物理总线和 CPU 异常上下文。

### 11.3 案例三：量产板 CAN 偶发掉线，实验室无法复现

#### 需求

- 8 个 CAN FD 节点。
- 20 m 线缆。
- 工业电机环境。
- 需要自动恢复且不能误动作。

#### 现象

- 样机少量测试正常。
- 量产后约 0.2% 设备出现偶发掉线。
- 重启设备后恢复。
- 更换收发器不能完全解决。

#### 调试证据

- 坏板在 2 Mbit/s 数据段存在边沿畸变。
- 中间节点有一部分装配了错误的终端电阻。
- 某批 TVS 电容较高，降低了边沿速度。
- 软件在总线错误后没有记录 TEC/REC 和 Bus-Off 原因。
- 现场电机启动时共模电流明显增加。

#### 修复

硬件：

- 中间节点移除终端电阻。
- 更换低电容 TVS。
- 缩短支线。
- 优化屏蔽和机壳返回路径。

固件：

- 记录错误计数、最后错误类型和 Bus-Off 时间。
- 有限次数复位收发器。
- 恢复失败后进入降级通信模式。
- 危险输出不由通信恢复逻辑直接控制。

#### 结果

|指标|修复前|修复后|
|---|---|---|
|量产异常比例|0.2%|未观测到|
|错误原因可见率|低|100%|
|总线恢复时间|重启约 2 s|自动恢复约 30 ms|
|电机启动期间误动作|偶发|0 次|

#### 设计要点

- 量产低比例故障需要统计和样品对照，而不是依赖单块样板。
- 协议恢复必须建立在物理层合格基础上。
- 故障日志应包含时间、错误计数、电源和工作模式。

## 12. 高频问题深度答疑

### 12.1 SWD/JTAG 完全连接不上，是否说明芯片损坏？

不一定。先验证：

1. 目标电源和 VTref。
2. GND 连续性。
3. NRST 是否被拉低。
4. SWDIO/SWCLK 是否被外部器件强驱动。
5. 调试器频率是否过高。
6. 是否启用了安全锁定或低功耗。
7. 是否需要 Connect Under Reset。
8. 芯片是否被外部电路反向供电。

若仍无响应，再考虑焊接、时钟、供电损坏或芯片故障。

### 12.2 为什么“换板后正常”不能证明原板芯片坏了？

换板同时改变了很多变量：

- 焊接状态。
- 电源网络。
- 连接器接触。
- 机械应力。
- 器件批次。
- PCB 层间缺陷。
- 探头和线缆位置。

应使用交换实验：

```
好板芯片 → 坏板
坏板芯片 → 好板
好板外设 → 坏板
坏板外设 → 好板
```

并记录交换前后的故障迁移情况。

### 12.3 为什么必须先查电源？

因为电源异常会同时影响：

- CPU。
- 时钟。
- 复位。
- Flash。
- 收发器。
- ADC。
- 调试接口。

如果电源不满足条件，后续软件和协议现象都可能是假象。电源调试至少要覆盖负载点、启动和动态波形。

### 12.4 为什么逻辑分析仪显示正确，但系统仍然读错？

因为逻辑分析仪可能在一个与 MCU 不同的采样位置、阈值和时间点工作。真实 MCU 可能遭遇：

- Setup/Hold 不足。
- 接收端振铃。
- 门限移动。
- 电源地弹。
- DMA 缓存不一致。
- CS 时序边界错误。
- 温度和电压导致延迟变化。

必须同步使用示波器查看接收端物理波形，并检查软件缓存和时序配置。

### 12.5 如何调试偶发故障？

不能只“多跑几次”，应建立可统计、可触发、可保存的方案：

- 自动化重复测试。
- 硬件触发复位、错误线或电源跌落。
- 早期复位原因记录。
- 备份 SRAM 保存异常上下文。
- CRC、超时和错误计数。
- 记录输入电压、温度和业务模式。
- 好板/坏板同步采集。

### 12.6 什么时候应该使用飞线或临时电阻？

飞线适合验证假设，不适合直接作为最终修复。使用时必须记录：

- 飞线长度和位置。
- 参考地路径。
- 串联/并联阻值。
- 是否改变阻抗和回流。
- 是否影响热和 EMC。

若飞线使问题消失，应将其转换为可制造的原理图、PCB 和 BOM 修改，再做正式验证。

### 12.7 如何判断是硬件故障还是软件故障？

使用分层对照：

```
硬件最小测试固件正常？
├─ 否 → 优先查电源、时钟、复位、焊接和接口物理层
└─ 是 → 加载业务模块并逐层启用
   ├─ 某模块启用后失败 → 检查该模块及其负载
   └─ 满载才失败 → 查 PI、SI、热、EMC 和资源竞争
```

但二者经常耦合，例如 Cache 一致性、GPIO Slew、负载调度和电源瞬态都属于硬件—软件协同问题。

### 12.8 调试时为什么不能一直连接示波器和调试器？

仪器会改变系统：

- 探头增加电容。
- 地线增加回流路径。
- 调试器改变复位和启动状态。
- SWD 线引入串扰和负载。
- USB/串口线引入额外地连接。
- 示波器保护地改变浮地系统结构。

应进行：

```
无仪器运行
→ 仅接调试器
→ 仅接示波器
→ 同时连接
```

比较故障概率，识别测量装置是否成为变量。

## 13. 课程核心总结

### 核心要点

- **硬件调试的本质是建立证据链，而不是凭经验替换器件。**
- **电源、时钟、复位和最小系统是所有复杂调试的起点。**
- **调试器能看到 CPU 状态，但不能替代电源、时钟和物理层测量。**
- **协议正确不等于电气正确；逻辑分析仪不能替代示波器。**
- **间歇性问题必须自动化、统计化并关联温度、电压、负载和版本。**
- **复位原因和 Fault 上下文必须在启动早期保存。**
- **硬件测试点、隔离位、调试口和可控启动应在设计阶段加入。**
- **软件必须提供启动阶段标记、自检、超时、有限恢复和故障日志。**
- **安全输出不能依赖 CPU 在故障状态下及时执行。**
- **修复完成的判据是原故障消失、边界测试通过、回归风险受控且证据完整。**

### 性能排序

通用板级调试建议的优先级为：

```
输入与电源
> 复位
> 时钟
> CPU 取指与启动介质
> 内存与异常上下文
> 外设物理层
> 协议与驱动
> 满载 PI/SI/EMC
> 温度、电压和制造边界
> 量产统计与长期可靠性
```

### 通用选型结论

- 完全无响应：优先使用**限流电源、目检、热像和电源分段测量**。
- SWD 不通：优先确认**目标电源、VTref、NRST、GND、调试频率和安全配置**。
- 启动卡死：使用**阶段 GPIO、备份寄存器、内部 RC 旁路和最小启动固件**。
- 偶发复位：同步记录**复位源、电源波形、NRST、时钟和负载电流**。
- 总线异常：同时观察**协议事务和物理电气波形**。
- 低概率量产问题：使用**统计、好坏板对照、自动化边界矩阵和版本追溯**。
- 安全相关系统：采用**硬件关断、独立监控、故障锁存和受限软件恢复**。

## 16. 实践与进阶路径

### 16.1 梯度实战任务

#### 任务一：建立最小系统调试板

设计一块包含以下模块的实验板：

```
MCU
├─ 可切换内部/外部时钟
├─ 1 个可控复位监控器
├─ 2 路可测电源轨
├─ SWD/JTAG
├─ UART
├─ 4 个阶段 GPIO
├─ 1 个外部 SPI Flash
└─ 1 个可断开的传感器接口
```

要求：

- 上电前可测电阻。
- 每个电源轨有测试点。
- 关键接口有串联电阻位。
- 可使用跳线隔离外设。
- 可通过 GPIO 输出启动阶段编码。

#### 任务二：编写启动诊断固件

实现：

- 早期复位原因保存。
- 内部 RC 启动。
- 外部晶振切换。
- 电源轨 ADC 检查。
- SRAM 快速测试。
- 外部 Flash JEDEC ID 和 CRC。
- 阶段 GPIO 标记。
- HardFault 上下文保存。
- UART 诊断命令。

#### 任务三：故障注入

受控注入：

- 拉低 NRST。
- 延迟晶振启动。
- 降低输入电压。
- 增加电子负载。
- 断开外部 Flash。
- 改变 SPI CPHA。
- 注入 I²C SDA 卡低。
- 拉低 Power-Good。
- 产生通信错误。
- 模拟温度升高。

验证系统是否：

- 正确识别故障阶段。
- 保存首个故障证据。
- 进入安全状态。
- 有限次数恢复。
- 失败后稳定降级。

#### 任务四：搭建自动化边界测试

使用可编程电源、电子负载、温箱和仪器控制接口，自动扫描：

```
输入电压 × 温度 × 负载 × 通信速率 × 线缆长度 × 软件版本
```

每次保存：

- 样品 ID。
- PCB/BOM 版本。
- 固件版本。
- 测试参数。
- 电源轨数据。
- 电流波形。
- 复位原因。
- 错误计数。
- 通过/失败结果。

#### 任务五：好板/坏板差异分析

选择一块稳定板和一块故障板，建立统一测量模板：

- 相同输入电压。
- 相同负载。
- 相同探头。
- 相同测试点。
- 相同触发条件。
- 相同软件和配置。

依次比较：

```
电阻
→ 直流电压
→ 上电电流
→ 电源纹波
→ 时钟
→ 复位
→ 启动阶段
→ 总线波形
→ 热分布
```

#### 任务六：量产诊断设计

建立以下测试层级：

```
来料测试
├─ 关键器件参数
├─ 替代料一致性
└─ 供应商批次追溯

ICT
├─ 开短路
├─ 阻值和极性
├─ 电源静态
└─ 关键网络连通性

FCT
├─ 上电时序
├─ 启动自检
├─ 通信回环
├─ ADC/GPIO
└─ 负载与保护

老化与边界
├─ 温度循环
├─ 满载运行
├─ 通信压力
└─ 电源扰动
```

### 16.2 性能测试方法

|测试目标|方法|关键指标|
|---|---|---|
|启动可靠性|自动循环上电|成功率、启动时间、复位原因|
|电源稳定性|负载阶跃|跌落、恢复、纹波|
|时钟稳定性|频率测量、温漂|频率误差、启动时间|
|内存可靠性|March/CAT/CRC|错误率、地址定位|
|总线可靠性|回环和压力|BER、CRC、超时、重试|
|CPU 异常|Fault 注入|捕获完整率、恢复时间|
|热可靠性|温箱满载|结温、降频、死机|
|EMC 韧性|ESD/EFT/射频|复位、错误、恢复、安全状态|
|量产一致性|大样本统计|良率、分布、边界样品|

### 16.3 推荐故障定位流程

```
固定问题配置
→ 保存样品和版本信息
→ 确认测试设备未改变现象
→ 安全上电并记录输入电流
→ 验证电源轨和负载点
→ 验证复位和时钟
→ 判断 CPU 是否执行
→ 捕获启动阶段或 Fault 上下文
→ 隔离外设和负载
→ 同步测量协议与物理层
→ 进行好板/坏板对照
→ 单变量故障注入
→ 修复后重复原始测试
→ 执行全边界、回归和量产验证
```
