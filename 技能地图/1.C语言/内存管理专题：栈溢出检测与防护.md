
栈溢出不是单纯的“局部数组太大”。在嵌入式系统中，它可能来自深调用链、中断嵌套、FPU 上下文、递归、可变长数组、任务栈配置错误，或某个看似无关的库函数。溢出发生后，首先被覆盖的可能是返回地址、任务控制块、全局数据或其他任务的栈；故障往往在很久之后才暴露。

本课重点建立一套完整的工程方法：

- **静态估算栈上界**；
- **运行时监测栈余量**；
- **用 MPU、保护区和编译器工具捕获越界**；
- **正确计算 Cortex-M 异常栈与 RTOS 任务栈**；
- **在栈已经损坏时，仍尽可能保存故障现场**。

示例以 **C11、Cortex-M4/M4F、GNU Arm 工具链、FreeRTOS** 为主。不同芯片、RTOS 端口、ABI 和编译器版本会改变栈帧细节，需以目标构建产物和芯片手册为准。

**数据说明**：本课中的容量与周期计算是可复算的预算示例，不是未注明条件的实测数据。实际 WCET 和最大栈使用量必须在目标硬件与完整构建配置下验证。

## 3. 技术概述

### 3.1 什么是栈溢出

栈溢出是指栈使用超出其预留边界，导致访问或覆盖栈区域以外的内存。

典型增长方向：

```
高地址
┌─────────────────────┐
│ 栈顶初始位置         │
│ 已使用栈帧           │
│ 更深调用 / 更多嵌套   │
│                     │
│ 保护区               │
└─────────────────────┘
低地址
```

许多 Cortex-M 工程中的栈向低地址增长，但**不能把这一点当作所有架构或 ABI 的通用保证**。必须根据处理器、端口和链接布局确认方向。

### 3.2 栈溢出的主要来源

|来源|典型情况|
|---|---|
|大局部数组|函数内声明数 KiB 缓冲区|
|深调用链|多层函数、复杂库调用|
|递归|递归深度无上界|
|VLA|栈用量由输入长度决定|
|`alloca()`|运行期动态扩栈，难以静态分析|
|中断嵌套|多层 ISR 同时使用 MSP|
|浮点上下文|Cortex-M4F 扩展异常栈帧|
|RTOS 任务栈|任务栈配置小于调用需求|
|启动代码|早期栈太小或初始化顺序错误|
|优化变化|构建选项变化导致栈帧变化|
|库函数|格式化、解析、数学库或递归算法占用较大|

### 3.3 栈溢出的故障形态

- 覆盖相邻全局变量或其他栈。
- 破坏任务控制块，调度时才发生故障。
- 覆盖保存寄存器或返回地址。
- 触发 MemManage、BusFault 或 HardFault。
- 在异常入口压栈时失败，导致 `STKERR` 或 `MSTKERR`。
- 破坏 MSP 后，普通 C 语言 HardFault 处理器自己也无法可靠运行。

**栈溢出检测的关键不是“出错后能不能看到崩溃”，而是能否在越界接近边界时及时发现，并在现场尚可用时采取保护动作。**

## 5. 底层原理与功能特性深度解析

### 5.1 函数调用为什么使用栈

函数调用可能需要保存：

- 返回地址；
- 被调用者保存寄存器；
- 额外参数；
- 局部对象；
- 对齐填充；
- 编译器临时溢出槽；
- 调试构建中的额外对象。

但是，C 源码中的局部变量不一定都进入栈：

- 可能被放在寄存器；
- 可能被常量折叠；
- 可能完全消除；
- 可能内联到调用者；
- 优化可能改变栈帧形状。

因此：

**源码中局部变量的字节数不是实际栈占用的充分估计。**

### 5.2 编译器栈使用报告

GNU 编译器可使用：

```
-fstack-usage
```

它会为函数生成 `.su` 文件，常见记录包括：

- 函数名；
- 单函数栈字节数；
- `static`、`dynamic` 或 `dynamic,bounded` 等分类。

示例构建参数：

```
-O2
-g3
-fstack-usage
-Wall
-Wextra
-Wvla
```

查看 `.su` 文件：

```
cat *.su
```

限制：

- 报告通常是编译时函数级估计；
- 内联会改变函数边界；
- 汇编函数可能需要人工分析；
- 间接调用需补充目标集合；
- 递归需要已知深度上界；
- ISR 嵌套和硬件异常压栈需另外加入；
- LTO 可能改变最终代码，应对最终构建配置生成并检查结果。

### 5.3 调用图与栈上界

若函数调用图是一棵无递归路径的树，一个执行路径的栈深可近似为：

Spath=∑f∈pathSf+SABI alignment+Sruntime/exceptionSpath​=f∈path∑​Sf​+SABI alignment​+Sruntime/exception​

系统任务栈预算至少应考虑最深合法路径，而不是所有函数栈帧的总和。

举例：

```
task_entry       48 B
  └─ protocol    96 B
       └─ decode 160 B
            └─ parse 224 B
```

简单相加：

48+96+160+224=528 B48+96+160+224=528 B

再加：

- ABI 对齐；
- 被调用函数；
- RTOS 上下文；
- 异常入栈；
- 安全裕量。

如果 `parse()` 会递归，递归深度也要乘入；如果输入可控且递归深度没有上界，静态证明通常无法完成。

### 5.4 Cortex-M 异常压栈

Cortex-M 异常入口通常由硬件保存基本现场：

```
R0
R1
R2
R3
R12
LR
PC
xPSR
```

共：

8×4=32 B8×4=32 B

若 Cortex-M4F 执行扩展浮点上下文保存，硬件浮点栈帧还可能包含：

```
S0～S15、FPSCR 和保留字
```

常见扩展部分为：

18×4=72 B18×4=72 B

基本帧加扩展帧：

32+72=104 B32+72=104 B

还可能有：

- 对齐填充；
- ISR 软件保存寄存器；
- ISR 局部变量；
- ISR 调用函数的栈帧；
- RTOS 端口保存的上下文。

这只是异常现场的一部分。应以具体核心、FPU 配置、端口汇编和反汇编确认。

### 5.5 MSP 与 PSP 的关键关系

常见 Cortex-M RTOS 配置：

```
Thread mode：PSP，每个任务拥有自己的栈
Handler mode：MSP，异常处理使用公共栈
```

任务被中断时：

1. 若线程模式使用 PSP，硬件首先把被中断线程现场压入 **PSP 对应任务栈**。
2. 进入 Handler 模式后，ISR 的 C 代码通常使用 **MSP**。
3. 更高优先级中断嵌套时，还可能继续消耗 MSP。
4. RTOS 上下文切换代码可能额外保存寄存器到任务栈。

因此，至少要分别预算：

```
任务栈：任务调用链 + 异常压入 PSP 的现场 + 端口上下文
MSP 栈：启动路径 + ISR 调用链 + 中断嵌套 + 处理器上下文
```

**把全部 ISR 栈都算到 MSP，或把硬件异常帧全部算到 MSP，都可能是错的。关键是异常发生时处理器实际使用的栈指针。**

### 5.6 `EXC_RETURN` 与异常现场选择

异常处理器进入时，LR 通常保存特殊的 `EXC_RETURN` 值。它编码了返回模式和被中断上下文的栈选择。

对 Cortex-M 常见实现，可通过其位字段判断返回到 Thread 还是 Handler，以及返回上下文涉及 MSP 还是 PSP。精确解码应依据 ARM 架构文档和目标核心版本，不建议直接对所有内核使用未经校验的常量假设。

典型 HardFault 汇编入口的思想是：

```
/*
 * 汇编入口根据 EXC_RETURN 选择堆栈指针，
 * 再把堆栈帧指针传给 C 语言记录函数。
 * 具体汇编需按工具链、核心和 ABI 验证。
 */
```

不要在未知栈状态下仅凭普通 C 函数参数推断异常现场位置。

### 5.7 栈高水位检测

常见做法：

1. 初始化时用固定字节填充栈区。
2. 运行后扫描从栈底开始仍未被覆盖的区域。
3. 根据被覆盖边界估算历史最大使用量。

假设任务栈大小为 SS，扫描发现 FF 字节仍保持填充值，则估计使用量：

Uestimated=S−FUestimated​=S−F

这是**已写入区域估计**，不一定等于 SP 曾经移动到的最深位置。

例如，函数动态调整 SP 预留了大块区域，但没有写入其中大部分字节，水位扫描可能低估实际栈指针最深位置。

### 5.8 FreeRTOS 任务栈高水位

FreeRTOS 通常提供类似接口：

```
UBaseType_t uxTaskGetStackHighWaterMark(TaskHandle_t task);
```

某些端口还提供 `uxTaskGetStackHighWaterMark2()`。

注意：

- 返回单位可能是 `StackType_t` 个元素，而不一定是字节。
- 具体单位和实现由 FreeRTOS 版本、配置和端口决定。
- 高水位基于栈填充模式，属于历史写入估计。
- 任务必须至少运行到覆盖目标路径。
- 最大值和最小值的解释要区分：API 常返回“剩余最小栈空间”的水位。

转换为字节时，先核对端口和类型：

余量字节=返回元素数×sizeof(StackType_t)余量字节=返回元素数×sizeof(StackType_t)

### 5.9 软件 canary 与编译器栈保护

#### 软件 canary

在栈边界放置特征值，定期检查是否被覆盖。

优点：

- 成本低；
- 易于集成；
- 可在没有 MPU 的系统中提供一定检测。

缺点：

- 通常在覆盖后才发现；
- 若越界跳过 canary，可能漏检；
- 需要可靠的检查时机；
- canary 本身若位于错误位置或未受保护，仍可能被破坏。

#### 编译器栈保护

GCC 常见选项：

```
-fstack-protector
-fstack-protector-strong
-fstack-protector-all
```

编译器在部分函数序言中保存 guard 值，在函数返回前检查。

它主要检测**被保护函数的栈帧对象破坏**，不等同于：

- 栈空间不足检测；
- SP 越界检测；
- 中断栈保护；
- 任意栈溢出立即异常。

还要配置运行库的 `__stack_chk_guard` 和 `__stack_chk_fail()` 行为；嵌入式库和启动代码的细节依实现而定。

### 5.10 MPU guard region

MPU 可以把栈边界附近区域设为不可访问，以便溢出访问时触发 MemManage Fault。

典型思想：

```
栈可写区域
┌──────────────────┐
│ 当前栈使用区       │
│ 可扩展余量         │
├──────────────────┤
│ 不可访问 guard     │  ← 溢出到此触发异常
└──────────────────┘
```

限制：

- MPU 区域数量有限；
- 区域大小与对齐要求依核心而异；
- Cortex-M4 MPU 常要求区域大小为 2 的幂，并按大小对齐；
- 子区域禁用有特定最小区域粒度，不能任意保护任意字节；
- 任务切换时可能要重设 MPU 区域；
- 保护区需要消耗可用地址空间；
- 访问保护区时的异常处理仍需可靠栈。

Cortex-M33 等具备 `PSPLIM/MSPLIM` 的实现可提供更直接的栈限制寄存器，但不能把它推广到所有 Cortex-M。

### 5.11 大局部对象的处理

错误倾向：

```
void process_frame(void)
{
    uint8_t scratch[4096];
    /* ... */
}
```

如果此函数可被多个任务调用，或调用链较深，栈成本会被重复计入。

常见替代方案：

- 调用者提供工作区；
- 每任务静态工作区；
- 专用固定块池；
- 由模块独占的静态工作区；
- 分块处理算法；
- 受控动态分配，但不在硬实时路径。

不建议为图省事把所有局部对象都改成全局变量；这会引入重入性和并发问题。

### 5.12 VLA、`alloca()` 与递归

```
void parse(size_t length)
{
    uint8_t temporary[length]; /* VLA */
}
```

栈需求由 `length` 决定，若输入没有严格上界，栈预算也没有可证上界。

```
void *temporary = alloca(size);
```

`alloca()` 分配在当前调用栈中，通常不会自动检查是否有足够栈空间。

递归函数：

```
void recursive_parse(node_t *node)
{
    if (node == NULL) {
        return;
    }

    recursive_parse(node->child);
}
```

若树深度来自外部输入且没有限制，最大栈使用量无法确定。

高可靠嵌入式工程通常：

- 禁止 VLA 和 `alloca()`；
- 禁止无界递归；
- 对深度设置上限；
- 使用显式栈或迭代算法；
- 通过编译选项和代码审查落实规则。

## 6. 性能量化分析

### 6.1 任务栈预算公式

对一个任务：

Stask≥Sdeepest-call-chain+Sexception-on-PSP+SRTOS-port-extra+SmarginStask​≥Sdeepest-call-chain​+Sexception-on-PSP​+SRTOS-port-extra​+Smargin​

MSP：

SMSP≥Sstartup+max⁡legal interrupt nesting(Shardware frames+SISR software+SISR call chains)+SmarginSMSP​≥Sstartup​+legal interrupt nestingmax​(Shardware frames​+SISR software​+SISR call chains​)+Smargin​

计算时要确认哪些项会同时存在，避免简单把互斥执行路径全加在一起或漏掉嵌套。

### 6.2 预算示例：Cortex-M4F 任务栈

假设经过静态报告和调用图估算：

|项目|预算|
|---|---|
|任务最深普通调用链|640 B|
|一次异常压入任务 PSP 的扩展帧|104 B|
|RTOS 端口任务上下文额外空间|96 B|
|安全裕量|256 B|
|合计|1096 B|

据此可选择例如 1280 B 或更大且满足项目分配粒度的栈大小，再通过目标板压力测试验证。

**96 B 的端口额外空间只是示例参数，必须从具体端口汇编、上下文切换代码和构建结果核实。**

### 6.3 MSP 中断栈示例

假设允许两层 ISR 嵌套，预算如下：

|项目|每层或总量|
|---|---|
|两层异常基本帧|2×32=642×32=64 B|
|浮点扩展帧可能额外占用|最坏按实际路径另计|
|两层 ISR 软件保存及局部变量|320 B|
|ISR 调用链|256 B|
|启动阶段额外栈需求|256 B|
|安全裕量|512 B|

不含额外浮点帧时的示例总计：

64+320+256+256+512=1408 B64+320+256+256+512=1408 B

这不是普适 MSP 配置。真实计算还需考虑：

- 是否使用浮点；
- 浮点异常栈帧位于 PSP 还是 MSP；
- 惰性压栈；
- 高优先级中断是否允许嵌套；
- `NMI`、Fault 与普通中断的关系；
- 入口汇编和 C 函数实际栈帧。

### 6.4 安全裕量如何设置

不应以固定百分比替代分析。可按风险组成裕量：

Smargin=Stoolchain variation+Sfeature variation+Smeasurement uncertainty+Sfault pathSmargin​=Stoolchain variation​+Sfeature variation​+Smeasurement uncertainty​+Sfault path​

例如：

- 编译器升级；
- 新增日志；
- FPU 路径未覆盖；
- 格式化函数的深调用；
- 异常路径额外处理；
- 高水位扫描低估。

裕量应有理由、可审查、可复测。

### 6.5 测量报告要求

目标板至少记录：

```
芯片型号和修订
核心与 FPU 配置
编译器版本
优化与 LTO 配置
任务栈大小
MSP 保留大小
中断优先级和嵌套配置
测试路径
高水位结果
SP 最低值（若可记录）
故障与保护区触发情况
```

高水位应覆盖：

- 最大报文；
- 解析失败路径；
- 错误日志路径；
- 浮点调用路径；
- 中断最深嵌套；
- 看门狗和故障处理路径。

### 6.6 栈访问性能与防护成本

- 栈空间本身通常位于 SRAM，访问成本由存储器和总线决定。
- 高水位扫描成本与扫描字节数成正比。
- 软件 canary 检查成本通常很低，但检查频率决定发现延迟。
- MPU 检查通常由硬件执行，正常访问开销通常远小于软件扫描；具体影响要看核心实现和异常配置。
- `-fstack-protector` 会增加函数序言和返回路径指令。
- 不能仅凭估计声称某机制“无性能影响”，应对关键路径做目标板测量。

## 7. 应用场景选型指南

### 7.1 纯文本决策流程图

```
该执行上下文是否有独立栈？
├── 是：任务 PSP 栈
│   ├── 能否静态估算调用链？
│   │   ├── 否：先去除无界递归、VLA、alloca
│   │   └── 是：结合异常现场和端口上下文预算
│   ├── 是否需要越界立即捕获？
│   │   ├── 是：配置 MPU guard 或核心栈限制寄存器
│   │   └── 否：至少启用水位和任务栈检查
│   └── 压力测试关键路径并记录最低余量
└── 否：公共 MSP
    ├── 计算启动路径
    ├── 计算所有合法 ISR 嵌套
    ├── 计算 Fault/NMI 路径

├── 是
│   └── 静态分析 + MPU + 运行监测 + 安全故障处理
└── 否
    └── 编译器报告 + 水位监测 + 压力测试

├── 是
│   └── 设置硬上限或改用显式工作区
└── 否
    └── 继续验证最深合法路径
```

### 7.2 场景选型

|场景|建议方案|重点|
|---|---|---|
|普通 RTOS 任务|编译器报告 + 高水位 + 安全裕量|覆盖最深任务路径|
|高完整性任务|静态预算 + MPU guard|越界及时异常|
|共享 MSP 中断栈|嵌套分析 + MSP guard|估算最坏 ISR 组合|
|使用 FPU 的控制任务|扩展异常帧预算|惰性浮点压栈|
|复杂协议解析|禁止无界递归，限制输入|栈深可证明|
|Bootloader|复位早期 MSP 预算 + 链接断言|`main()` 前路径也要覆盖|
|故障处理程序|独立应急栈或汇编入口|避免依赖损坏栈|

## 8. 工程最佳实践

### 8.1 栈预算必须按上下文分开

至少形成三张表：

|预算对象|内容|
|---|---|
|每个任务栈|调用链、异常 PSP 帧、端口上下文|
|MSP 栈|启动代码、ISR 嵌套、Fault 路径|
|特殊栈|引导阶段、应急栈、协处理器或安全域栈|

不要把所有栈都压缩成一个“系统栈总量”数字。

### 8.2 编译规则

常见基线：

```
-fstack-usage
-Wvla
-Walloca
-Wframe-larger-than=<项目阈值>
-fstack-protector-strong
```

注意：

- GCC 对 `-Wframe-larger-than` 的计算和报告细节受版本影响。
- `-Wframe-larger-than` 不是栈上界证明。
- 生产配置启用栈保护前，要验证嵌入式运行库提供正确失败处理。
- 对关键模块，保留 `.su` 文件和 map 文件作为构建产物。
- 编译器、优化选项或 LTO 改变后，应重新审查栈预算。

### 8.3 代码规则

1. 默认禁止无界递归。
2. 默认禁止 VLA 和 `alloca()`。
3. 限制函数最大栈帧，超阈值必须评审。
4. 大数组使用显式工作区或专用池。
5. 高优先级 ISR 不调用高栈消耗格式化函数。
6. 限制 ISR 的调用层级和嵌套。
7. 对外部输入限制协议深度、元素数量和解析递归深度。
8. 线程入口中集中处理资源和错误，不在深层函数反复创建大临时对象。
9. 关键函数检查反汇编，而不只看源码。
10. 库函数调用栈也要纳入预算。

### 8.4 运行期监测

建议：

- 定期或在低负载时检查任务高水位；
- 对低余量任务记录告警；
- 统计历史最小栈余量；
- 监测 MSP 最低地址或哨兵；
- 触发阈值时保存任务名、任务句柄、SP 和故障状态；
- 避免水位检查本身在高优先级 ISR 中执行。

### 8.5 保护与故障处理分层

推荐组合：

```
编译期：栈帧报告、调用图和阈值检查
运行期：任务水位、MSP 哨兵
硬件层：MPU guard / 栈限制寄存器
故障后：汇编入口、独立记录区、受控复位
```

任何单层都可能漏检或无法恢复。

## 9. 常见错误与避坑指南

### 9.1 错误一：按局部变量总和配置栈

错误估算：

```
局部变量合计 300 B，所以任务栈配置 512 B。
```

根因：

- 未计入调用链；
- 未计入保存寄存器、参数和对齐；
- 未计入异常现场；
- 未计入 FPU 和 RTOS 上下文；
- 优化与库函数可能改变栈帧。

正确做法：

1. 生成 `.su` 报告。
2. 建立实际调用图。
3. 找每条合法执行路径的最大累计栈帧。
4. 加入异常和端口上下文。
5. 通过压力测试验证最低余量。
6. 为工具链和功能变化留出有依据的安全裕量。

风险影响：

- 调用深度稍增或增加一个日志路径就溢出；
- 故障仅在特定报文或中断时出现。

### 9.2 错误二：用高水位当作栈上界证明

错误推论：

```
水位还剩 100 B，因此不会溢出。
```

根因：

- 没覆盖最深路径；
- VLA 或 `alloca()` 尚未执行；
- 只移动 SP、不写入内存的区域未被填充检测覆盖；
- FPU 扩展栈帧尚未触发；
- ISR 嵌套状态不同。

正确做法：

```
静态分析上界
+ 目标板最坏路径高水位
+ SP/保护区监测
+ 安全裕量
```

风险影响：

- 测试通过但现场偶发 HardFault；
- 低频异常路径造成不可复现覆盖。

### 9.3 错误三：把所有中断栈只计入 MSP

错误估算：

```
MSP 加 104 B，所有异常现场都在这里。
```

根因：

- 异常进入时保存的线程上下文可能压入被中断线程使用的 PSP。
- Handler 模式下 ISR C 代码使用 MSP。
- 嵌套异常和任务上下文的栈归属不同。

正确做法：

- 根据当时 Thread/Handler 模式和当前 SP，逐条画栈流向。
- 分别预算任务栈和 MSP。
- 核对 `EXC_RETURN`、FreeRTOS PendSV 汇编和端口实现。
- 对有 FPU 的路径核查扩展帧位置和惰性压栈。

风险影响：

- 任务栈漏算异常帧；
- MSP 预算不足以承受嵌套 ISR。

### 9.4 错误四：以为 `-fstack-protector` 能防止一切栈溢出

错误假设：

```
打开了 -fstack-protector-strong，所以栈不会越界。
```

根因：

- 栈保护主要在受保护函数返回前检查 guard。
- 保护位置和覆盖函数由编译器策略决定。
- 不一定捕获栈指针越过整个栈区域。
- 故障可能早已破坏其他数据。
- 中断栈也不是自动由函数 canary 保护。

正确做法：

```
栈保护编译选项
+ MPU/栈边界
+ 高水位和哨兵
+ 任务栈静态预算
```

风险影响：

- 以为有保护而减少栈容量；
- 保护触发前已发生其他内存破坏。

### 9.5 错误五：栈溢出后在普通 C HardFault 中大量打印

错误代码：

```
void HardFault_Handler(void)
{
    printf("HardFault\n");
    dump_all_state();
}
```

根因：

- 当前 MSP 或 PSP 可能已损坏；
- `printf()` 可能使用大量栈；
- 可能触发锁、动态分配或 UART 中断；
- 故障处理再次异常。

正确策略：

- 使用最小汇编入口；
- 切换到独立应急栈，或只记录少量寄存器到静态保留区；
- 绝不在故障路径动态分配；
- 记录后复位或进入安全循环；
- 验证记录区域在当前复位类型下有效。

风险影响：

- 丢失原始现场；
- Fault 嵌套；
- 看门狗复位但没有诊断数据。

### 9.6 错误六：认为 FreeRTOS 高水位返回值就是字节

错误代码：

```
size_t remaining_bytes =
    uxTaskGetStackHighWaterMark(task);
```

根因：

- API 返回单位可能是 `StackType_t` 元素，不一定是字节。

正确处理：

```
UBaseType_t remaining_units =
    uxTaskGetStackHighWaterMark(task);

size_t remaining_bytes =
    (size_t)remaining_units * sizeof(StackType_t);
```

仍需核对项目版本、端口和接口文档。

风险影响：

- 余量估算错误一个倍数；
- 对 16 位或 32 位 `StackType_t` 的平台理解不一致。

## 10. 多机制组合使用方案

### 10.1 多层防护架构

```
编译期
├── -fstack-usage
├── VLA / alloca 禁止
├── 最大栈帧阈值
└── 调用图与递归审查

运行期
├── RTOS 任务高水位
├── MSP 边界哨兵
├── 栈最低地址监测
└── 低余量告警

硬件
├── MPU guard region
├── 可用时的 PSPLIM/MSPLIM
└── Fault 状态寄存器采集

异常恢复
├── 独立应急栈
├── 静态保留现场
├── 不分配、不格式化
└── 安全复位或故障锁定
```

### 10.2 任务栈低水位监测框架

FreeRTOS API 的具体单位依版本和端口核对。

```
#include <stddef.h>
#include <stdint.h>

#include "FreeRTOS.h"
#include "task.h"

typedef struct {
    const char *task_name;
    size_t remaining_bytes;
} task_stack_report_t;

bool task_stack_remaining_bytes(TaskHandle_t task,
                                task_stack_report_t *report)
{
    if ((task == NULL) || (report == NULL)) {
        return false;
    }

#if (INCLUDE_uxTaskGetStackHighWaterMark == 1)
    const UBaseType_t remaining_units =
        uxTaskGetStackHighWaterMark(task);

    report->task_name = pcTaskGetName(task);
    report->remaining_bytes =
        (size_t)remaining_units * sizeof(StackType_t);

    return true;
#else
    (void)task;
    (void)report;
    return false;
#endif
}
```

使用注意：

- `pcTaskGetName()` 是否可用取决于 FreeRTOS 配置。
- 该值代表水位估计，不是绝对上界。
- 由低优先级监控任务周期读取，避免 ISR 中扫描。
- 监测阈值应按任务栈预算分别设置，不应全系统统一使用一个数。

### 10.3 MSP 哨兵框架

可在 MSP 栈边界附近布置哨兵，并在安全时机检查。但必须保证：

- 哨兵地址不与真实栈使用区域重叠；
- 链接脚本为其保留空间；
- 检查函数不会依赖已溢出的 MSP；
- 栈方向和边界与芯片启动代码一致。

伪代码结构：

```
bool msp_guard_intact(void)
{
    for (size_t i = 0u; i < MSP_GUARD_WORDS; ++i) {
        if (g_msp_guard[i] != MSP_GUARD_PATTERN) {
            return false;
        }
    }

    return true;
}
```

如果要扫描的是异常处理当前正在使用的 MSP，必须考虑扫描函数自身也会消耗 MSP。实际实现更适合从安全的监控上下文检查，或使用 MPU 保护。

### 10.4 HardFault 现场记录

Cortex-M HardFault 处理器可尽量记录：

- `CFSR`；
- `HFSR`；
- `MMFAR`；
- `BFAR`；
- `EXC_RETURN`；
- 异常帧中的 PC、LR、xPSR；
- MSP、PSP；
- 当前任务标识。

但对栈错误尤其要谨慎：

- 如果 `CFSR` 中出现栈压入错误，异常帧可能不完整。
- 如果记录代码使用当前损坏栈，可能产生二次故障。
- `MMFAR/BFAR` 只有在对应有效位设置时才应信任。
- 记录区域应静态分配或放入适当保留区。
- 高级实现通常用汇编入口切换应急栈，再调用极简 C 函数。

### 10.5 MPU 保护布局示例

概念布局：

```
低地址
┌──────────────────────────┐
│ MPU 不可访问保护区        │
├──────────────────────────┤
│ 任务栈可访问区域           │
│                           │
│ PSP 初始栈顶               │
└──────────────────────────┘
高地址
```

实现时必须：

- 按 MPU 区域最小尺寸和对齐要求布局；
- 评估 `configENABLE_MPU` 与端口任务上下文切换；
- 避免保护区与其他对象共享同一 MPU 粒度区域；
- 确认任务切换时区域寄存器更新；
- 在故障处理器中识别 MemManage Fault；
- 在链接和初始化阶段断言栈边界不重叠。

## 11. 工业级实际案例分析

以下为常见工业场景的工程化分析，数值为预算示例，不代表特定项目实测。

### 11.1 案例一：协议解析任务偶发 HardFault

#### 需求

- 接收长度可变；
- 报文最大 2048 B；
- 解析器支持嵌套字段；
- 仅特定复杂报文触发故障。

#### 根因调查

先检查：

1. 是否使用 VLA 或 `alloca()`。
2. 解析是否递归。
3. 嵌套深度是否由输入控制。
4. 失败路径是否调用格式化日志。
5. 任务栈高水位是否覆盖最大报文。
6. 是否在报文处理中触发 FPU 或异常。

#### 方案

- 设定最大嵌套深度。
- 将递归解析改成显式节点栈或迭代状态机。
- 解析工作区由调用者提供。
- 对异常路径使用固定错误码，不进行深层格式化。
- 对解析任务配置 MPU guard。

核心代码示意：

```
#define MAX_PARSE_DEPTH 16u

typedef struct {
    const token_t *token;
    size_t child_index;
} parse_frame_t;

bool parse_iterative(const token_t *root,
                    parse_frame_t *frames,
                    size_t frame_capacity)
{
    if ((root == NULL) ||
        (frames == NULL) ||
        (frame_capacity < MAX_PARSE_DEPTH)) {
        return false;
    }

    size_t depth = 0u;
    frames[depth++] = (parse_frame_t) {
        .token = root,
        .child_index = 0u
    };

    while (depth > 0u) {
        parse_frame_t *frame = &frames[depth - 1u];

        if (frame_complete(frame)) {
            --depth;
            continue;
        }

        const token_t *child = next_child(frame);

        if (child == NULL) {
            continue;
        }

        if (depth >= MAX_PARSE_DEPTH) {
            return false;
        }

        frames[depth++] = (parse_frame_t) {
            .token = child,
            .child_index = 0u
        };
    }

    return true;
}
```

#### 设计要点

- `frame_capacity` 应与实际数组容量一致。
- 输入长度、节点数和深度都要独立限制。
- 显式工作区占用静态或调用者提供内存，而不是当前任务栈。
- 对工作区本身也要做边界检查。

### 11.2 案例二：Cortex-M4F 控制任务栈不足

#### 需求

- 控制任务运行浮点算法；
- 任务栈原配置 1024 B；
- 调试时偶发栈检查失败；
- 加入浮点异常路径后问题更频繁。

#### 分析

- 任务普通调用链累计约 520 B；
- 任务被中断时 PSP 需要容纳异常现场；
- FPU 扩展帧可能增加 72 B；
- RTOS 端口上下文保存另有开销；
- 日志和错误处理路径调用链较深。

预算示例：

520+104+128+256=1008 B520+104+128+256=1008 B

原栈 1024 B 几乎没有未计入变化的余量。

#### 设计调整

- 将控制任务栈提升到经过预算的容量；
- 日志移出控制任务；
- ISR 只提交轻量事件；
- 用高水位和压力测试验证；
- 若芯片支持，给任务栈配置 MPU guard；
- 审查 FPU 配置和 FreeRTOS FPU 上下文保存策略。

#### 设计要点

不能简单认为“异常帧总是 104 B”。需要确认：

- 该任务实际是否执行浮点；
- 惰性压栈配置；
- 异常发生时的线程栈；
- 端口是否额外保存浮点寄存器；
- 哪些调用路径会同时叠加。

### 11.3 案例三：MSP 栈在中断嵌套时被破坏

#### 需求

- 高优先级快速采样中断可抢占低优先级通信中断；
- 通信 ISR 调用多个驱动层函数；
- 故障只发生在总线压力大时。

#### 架构问题

```
通信 ISR
  └── 驱动层
      └── 数据校验
          └── 日志格式化
```

高优先级采样 ISR 在其间嵌套，MSP 同时承担：

- 外层 ISR 调用链；
- 高优先级 ISR 的异常现场；
- 高优先级 ISR 自身调用链；
- 可能的浮点或额外保存。

#### 方案

- ISR 中删除格式化和复杂校验。
- 采样 ISR 使用最小操作并写入固定缓冲区。
- 通信 ISR 仅复制必要寄存器状态，后续交由任务处理。
- 根据合法嵌套图计算 MSP 上界。
- MSP 下方设置 MPU guard 或静态哨兵。
- 故障处理使用独立应急栈。

## 12. 高频问题深度答疑

### 12.1 FreeRTOS 高水位显示余量很多，还会栈溢出吗？

会。

原因包括：

- 测试没有走到最深调用链；
- VLA 或 `alloca()` 尚未触发；
- 栈指针移动但未写入所有区域；
- FPU 扩展上下文路径未出现；
- MSP 中断栈与任务栈分开，测错了对象；
- 水位反映的是历史填充值覆盖边界，而非经形式证明的最大 SP 深度。

高水位是动态证据，不是上界证明。

### 12.2 `-fstack-protector-strong` 和 MPU guard 有什么不同？

- 栈保护通常在函数返回前检查局部栈对象附近的 guard。
- MPU guard 通过访问权限阻止进入保护区域，通常在越界访问时触发硬件异常。

前者更像软件 canary，后者更接近边界访问保护。两者保护范围不同，可组合使用。

### 12.3 是否应该把所有大局部数组改成全局变量？

不一定。

改为全局或静态对象会：

- 永久占用 RAM；
- 让函数变成不可重入或需要锁；
- 造成不同任务之间的共享竞态；
- 增加状态管理复杂度。

更好的做法是根据生命周期和并发模型选择：

- 每任务静态工作区；
- 调用者传入缓冲区；
- 固定池；
- 分块算法；
- 受控动态工作区。

### 12.4 任务栈和 MSP 是否可以共用一块空间？

通常不应按普通任务栈的方式混为一谈。Cortex-M Thread 与 Handler 模式可能选择不同栈指针；启动代码、异常和任务切换端口都有特定约定。

应遵循芯片启动代码和 RTOS 端口设计，为任务 PSP 栈和 MSP 分别预留和验证空间。

### 12.5 为什么 HardFault 中读取的 PC 不可信？

异常可能在压栈过程中失败：

- 堆栈帧没有完整写入；
- `STKERR` 或 `MSTKERR` 标志表明压栈错误；
- 栈地址越界或不可访问；
- 现场被进一步故障覆盖。

因此，在读取异常帧前应先检查 Fault 状态和栈地址范围。不能无条件解引用“SP 指向的八个字”。

### 12.6 中断优先级越高，对 MSP 栈越安全吗？

不一定。

更高优先级中断可能增加嵌套深度和同步复杂度。实际栈影响取决于：

- 哪些中断可互相抢占；
- 优先级屏蔽配置；
- ISR 调用链；
- 异常返回行为；
- 是否有尾链等处理器机制。

需要画出所有合法嵌套路径，而不是仅按中断数量相加。

## 13. 课程核心总结

### 核心要点

1. **栈容量要按最深合法执行路径预算，不能按局部变量总和估算。**
2. Cortex-M 任务 PSP 栈与异常 MSP 栈要分开分析。
3. Cortex-M4F 的浮点扩展异常栈帧可能显著增加占用。
4. 高水位只是运行覆盖证据，不是数学上界。
5. `-fstack-protector` 不等于栈边界保护。
6. MPU guard 可以更早捕获越界，但布局、粒度和异常处理都要验证。
7. VLA、`alloca()` 和无界递归会破坏栈预算的确定性。
8. 栈溢出后的故障处理不能依赖已损坏的栈、堆或日志系统。
9. 编译期报告、运行期监测、硬件保护和压力测试必须组合使用。
10. 工具链、优化选项、FPU 配置改变后，要重新审查栈预算。

### 性能与保护手段排序

按实现复杂度从低到高的常见趋势：

```
编译期栈报告
    ↓
填充高水位和哨兵
    ↓
编译器栈保护
    ↓
MPU guard / 核心栈限制寄存器
    ↓
独立应急栈与故障恢复架构
```

这不是保护能力的绝对排序。每种机制针对的问题不同。

### 通用选型结论

- 普通任务：静态预算、编译器报告、高水位。
- 关键任务：额外加入 MPU guard 或核心栈限制功能。
- MSP：显式分析 ISR 嵌套，不依赖任务栈水位推断。
- 深解析代码：限制输入深度，避免递归和 VLA。
- Fault 路径：无动态分配、无复杂格式化，必要时切换应急栈。

## 14. 快速参考速查表

### 检测与防护速查

|机制|何时用|常见误区|
|---|---|---|
|`-fstack-usage`|编译期建立函数栈帧表|把函数报告当成系统最大值|
|调用图分析|估算任务路径上界|漏掉函数指针或 ISR|
|FreeRTOS 高水位|运行后观察历史使用|把水位当作证明|
|`-fstack-protector-strong`|检查受保护函数的栈破坏|认为它防止所有栈溢出|
|MPU guard|需要越界访问时硬件捕获|忽略区域大小与对齐要求|
|栈哨兵|无 MPU 平台的轻量监测|发现得太晚或被跳过|
|独立应急栈|故障现场需要可靠记录|仍在 Fault 中调用复杂库|

### 栈预算项目表

|项目|任务栈|MSP|
|---|---|---|
|最深函数调用链|是|是|
|异常硬件帧|按异常发生时所用栈核算|按实际异常路径核算|
|RTOS 保存上下文|是|视端口而定|
|ISR 软件栈帧|通常不直接算进任务 C 调用链|是|
|FPU 扩展上下文|按具体栈指针和路径|按具体异常路径|
|安全裕量|是|是|
|启动代码|通常不属于任务栈|是|

### 关键构建检查

```
-fstack-usage
-Wvla
-Walloca
-Wframe-larger-than=<阈值>
-fstack-protector-strong
```

每个选项都要结合工具链版本和工程配置验证；它们不能替代调用图、运行测试和硬件保护。

## 16. 实践与进阶路径

### 第一阶段：生成栈报告

为完整工程增加：

```
-fstack-usage
-Wvla
-Walloca
-Wframe-larger-than=<项目阈值>
```

收集：

- `.su` 文件；
- map 文件；
- 任务栈配置；
- MSP 链接边界；
- ISR 函数列表。

对最大栈帧函数逐项评审。

### 第二阶段：建立任务调用图

对每个任务：

1. 找到任务入口。
2. 列出可达调用链。
3. 标记函数指针目标。
4. 标记递归、VLA、`alloca()`。
5. 找最深执行路径。
6. 计算任务栈预算。
7. 加入异常和 RTOS 端口上下文。

对 MSP：

1. 列出所有可嵌套 ISR。
2. 绘制合法抢占关系。
3. 计算最坏嵌套路径。
4. 叠加 ISR 调用链与浮点影响。
5. 单独核算启动和 Fault 处理路径。

### 第三阶段：运行期压力测试

测试至少覆盖：

- 最大尺寸报文；
- 最深解析嵌套；
- 错误和超时路径；
- FPU 使用路径；
- 最大 ISR 嵌套；
- 高频任务抢占；
- 低内存日志路径；
- 看门狗和故障处理路径。

记录每个任务的水位、MSP 最低位置和触发保护次数。

### 第四阶段：硬件保护验证

若使用 MPU guard：

- 人为把栈指针或访问地址推进到保护区；
- 确认触发的 Fault 类型和状态寄存器；
- 确认 HardFault 不发生二次故障；
- 确认现场记录正确；
- 确认其他任务和中断栈不被误保护；
- 验证区域对齐和链接边界。

### 第五阶段：栈溢出故障演练

在开发板上构造受控过深调用或越界访问，验证：

1. 保护机制是否如预期触发。
2. Fault 处理器是否使用安全栈。
3. 记录的 PSP、MSP、PC 和状态寄存器是否可信。
4. 复位后记录是否可读。
5. 系统是否进入安全状态，而不是继续运行在已损坏状态。

### 进阶方向

- 调用图自动化和 WCET/栈深联合分析；
- MPU 按任务隔离与 RTOS 上下文切换；
- Cortex-M33 的 PSPLIM/MSPLIM 配置；
- 安全启动阶段的早期栈布局；
- 故障处理独立应急栈；
- 对编译器 LTO 和内联变化进行栈回归分析；
- 将栈预算阈值、最高水位和 MPU 测试纳入持续集成。

最终工程交付应包含：**每任务栈预算表、MSP 嵌套分析、构建报告、运行水位、硬件保护验证结果，以及栈溢出后的恢复与取证方案。**
