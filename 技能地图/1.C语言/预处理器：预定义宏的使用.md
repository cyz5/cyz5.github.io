
**预定义宏是编译环境提供给源代码的编译期信息接口。** 它们可以描述源文件位置、语言标准、编译器、目标架构和 ABI，也可以揭示部分语言或运行环境能力。

工业级使用的关键，在于明确每个宏能够证明什么：

- `__STDC_VERSION__` 表示语言标准模式，不能独立证明工具链完整支持该标准。
- `__GNUC__` 表示 GCC 或某种 GCC 兼容环境，不能独立证明编译器就是 GCC。
- `__ARM_FP` 表示相应目标浮点能力信息，不能独立证明当前使用硬浮点参数传递 ABI。
- `__STDC_HOSTED__ == 0` 表示独立式实现，不能推导出“没有标准库”。
- `__FILE__`、`__LINE__` 能定位编译时源位置，不能保证固件构建可复现。
- `__DATE__`、`__TIME__` 能提供翻译时间信息，不能作为可靠的发布版本标识。

本课以 **C11/C17 为主要基线**，单独标注 C23 和编译器扩展。涉及性能数据时，区分标准保证、计算示例和目标实测；没有目标板与工具链产物的部分，不虚构实测结果。

## 1. 学习目标

### 1.1 理解

- 理解标准预定义宏、条件性标准宏、编译器扩展宏和项目配置宏的边界。
- 理解预定义宏在预处理阶段的展开行为。
- 理解宏描述的是编译环境，不一定是设备运行现场。
- 理解编译器身份、语法能力、目标能力、ABI 和运行库能力之间的区别。

### 1.2 掌握

- 使用 `__FILE__`、`__LINE__` 构建日志、断言与故障记录接口。
- 使用 `__STDC_VERSION__` 建立最低语言标准约束。
- 使用编译器与目标宏选择适配实现。
- 通过工具链宏快照确认真实构建环境。
- 避免路径泄漏、时间戳污染和保留标识符冲突。

### 1.3 精通

- 识别 C/C++、GCC/Clang 和不同 Arm ABI 的检测陷阱。
- 正确区分“宏未定义”“明确不支持”和“需要进一步探测”。
- 设计可复现构建中的版本与源码位置策略。
- 定位不同翻译单元、不同编译选项造成的环境不一致。

### 1.4 能够设计

- 设计统一的编译器与平台适配层。
- 设计支持属性检测、标准检查和目标检查的公共基础头。
- 设计带构建标识、源位置和故障状态的诊断体系。
- 建立预定义宏快照、ABI 检查和构建产物归档流程。

## 2. 前置要求

### 2.1 知识要求

- 宏替换、字符串化、记号拼接和条件编译。
- 头文件保护与声明、定义分离。
- C 翻译阶段与翻译单元。
- 基础 ABI：指针宽度、字节序、对齐和调用约定。
- 裸机、RTOS 与宿主测试环境的区别。
- 编译、链接和运行库选择之间的关系。

### 2.2 技能要求

- 能查看完整编译命令。
- 能查看预处理输出与宏定义列表。
- 能阅读 map、ELF 属性和反汇编。
- 能为产品配置建立独立构建目录。
- 能区分目标交叉编译器与构建主机编译器。

GCC/Clang 的常用检查入口：

```
-E          只运行预处理
-dM         配合 -E，输出宏定义列表
-Wundef     诊断条件表达式中未定义的宏
-Wdate-time 诊断可能影响可复现构建的日期时间宏
```

这些选项不是 ISO C 接口，具体支持情况应结合工具链版本确认。

## 3. 技术概述

### 3.1 四类宏必须分开管理

|类别|示例|定义者|主要用途|
|---|---|---|---|
|标准预定义宏|`__FILE__`、`__LINE__`、`__STDC__`|C 实现|源位置、实现信息|
|条件性标准宏|`__STDC_VERSION__`、`__STDC_NO_ATOMICS__`|满足相应条件的实现|标准版本与可选能力信息|
|编译器或目标扩展宏|`__GNUC__`、`__clang__`、`__ARM_ARCH`|工具链|编译器和目标适配|
|项目或库控制宏|`NDEBUG`、`CONFIG_LOG`、`APP_BUILD_ID`|构建系统、用户或库协议|产品配置|

**`NDEBUG` 不是 C 标准要求编译器自动提供的预定义宏。** 它是标准 `assert` 接口使用的控制宏。

类似地：

- `_POSIX_C_SOURCE` 是特性选择宏。
- `DEBUG` 是常见项目约定。
- `CONFIG_USE_RTOS` 是项目配置。
- `__cplusplus` 是 C++ 语言环境提供的宏，在兼容头文件中经常需要检测。

### 3.2 编译环境信息存在不同层次

```
语言模式
  └─ 当前按哪个 C/C++ 标准编译

编译器实现
  └─ 哪个前端、哪个版本、哪些扩展

目标代码生成
  └─ 架构、指令集、浮点能力

ABI
  └─ 参数传递、类型尺寸、对齐

运行支持
  └─ 标准库、原子辅助函数、线程支持

产品现场
  └─ 实际芯片、时钟配置、外设状态、RTOS 初始化
```

**上层信息不能自动替代下层验证。**

例如，编译器可以生成浮点指令，不代表系统启动代码已经启用 FPU，也不代表 RTOS 已正确保存浮点上下文。

## 4. 核心特性横向对比

### 4.1 常用标准宏与相关标识符

|名称|类别|典型含义|重要限制|
|---|---|---|---|
|`__FILE__`|标准预定义宏|当前推定源文件名的字符串字面量|可能含路径，可受 `#line` 影响|
|`__LINE__`|标准预定义宏|当前推定源行号的整数常量|可受 `#line` 影响|
|`__DATE__`|标准预定义宏|翻译日期字符串|增加构建不确定性|
|`__TIME__`|标准预定义宏|翻译时间字符串|不适合发布版本或安全时间|
|`__STDC__`|标准预定义宏|符合相应标准要求的实现中为 `1`|不能描述所有扩展与完整能力|
|`__STDC_VERSION__`|标准版本宏|C 标准版本值|需考虑旧语言模式与实现差异|
|`__STDC_HOSTED__`|标准预定义宏|`1` 宿主式，`0` 独立式|不直接说明具体库函数是否可用|
|`__STDC_NO_ATOMICS__`|C11/C17 条件性宏|定义为 `1` 表示不支持相应原子能力|未定义不证明操作一定无锁|
|`__STDC_NO_THREADS__`|C11/C17 条件性宏|定义为 `1` 表示不支持相应标准线程能力|RTOS 与标准线程库是不同接口|
|`__STDC_NO_VLA__`|条件性宏|描述相应版本下的可变长度相关支持|C23 语义边界有变化|
|`__func__`|**预定义标识符，不是宏**|当前函数名称|不能用于 `#if` 或宏记号拼接|

### 4.2 身份检测、能力检测与构建探测

|方法|示例|能证明什么|适用边界|
|---|---|---|---|
|编译器身份检测|`defined(__clang__)`|编译环境声明的身份|不能证明全部扩展可用|
|版本检测|`__GNUC__ >= 12`|声明的兼容版本|厂商回移补丁会改变实际能力|
|能力查询|`__has_attribute(...)`|对应属性是否被前端识别|不一定证明运行效果|
|编译探测|编译一个最小片段|当前选项下代码可编译|不证明库已链接|
|链接探测|链接一个最小程序|符号和链接依赖可满足|不证明现场行为|
|目标运行测试|在目标设备执行|当前环境下的实际行为|仍需覆盖负载与边界|

**推荐顺序：先明确所需能力，再选择能验证它的最低充分手段。**

## 5. 底层原理与功能特性深度解析

### 5.1 `__FILE__` 与 `__LINE__`：展开位置决定结果

```
#define APP_HERE_FILE __FILE__
#define APP_HERE_LINE __LINE__
```

使用：

```
const char *file = APP_HERE_FILE;
int line = APP_HERE_LINE;
```

它们在宏被展开的位置产生对应信息，不会在 `#define` 出现时永久固定。

这使日志包装宏能够记录调用位置：

```
void app_log_write(const char *file,
                   int line,
                   const char *format,
                   ...);

#define APP_LOG(...) \
    app_log_write(__FILE__, __LINE__, __VA_ARGS__)
```

调用：

```
APP_LOG("sensor initialization failed");
```

格式串放入 `...`，兼容 C99/C11/C17，避免固定格式参数后省略尾参的逗号问题。

#### 不能直接用普通包装函数代替位置宏

```
static inline void app_report_failure(void)
{
    app_log_write(__FILE__, __LINE__, "failure");
}
```

这里记录的是包装函数定义所在的位置。

需要调用方位置时，应通过宏传入，或要求调用方显式提供位置对象。

### 5.2 两层字符串化与行号

```
#define APP_STRINGIZE_RAW(x_) #x_
#define APP_STRINGIZE(x_) APP_STRINGIZE_RAW(x_)

#define APP_SOURCE_TEXT \
    __FILE__ ":" APP_STRINGIZE(__LINE__)
```

使用：

```
const char *location = APP_SOURCE_TEXT;
```

展开后相邻字符串字面量由 C 翻译过程连接，效果类似：

```
const char *location = "sensor.c" ":" "123";
```

最终形成一个字符串字面量。

错误方式：

```
#define APP_BAD_LINE_TEXT APP_STRINGIZE_RAW(__LINE__)
```

结果是：

```
"__LINE__"
```

因为直接字符串化抑制了该参数的预展开。

### 5.3 `#line` 会改变推定文件名与行号

```
#line 500 "generated_protocol.c"
```

紧接着下一源行的推定行号变成 `500`，文件名变成指定名称。

用途包括：

- 代码生成器映射到原始描述文件。
- 生成解析器的诊断定位。
- 自动化测试构造位置场景。

工程影响：

- `__FILE__` 不必等于磁盘真实路径。
- `__LINE__` 不必等于编辑器显示的物理行号。
- 编译器诊断和调试信息可能体现这些映射。

**源位置是诊断信息，不是可信身份或访问控制依据。**

### 5.4 `__func__` 不是宏

C99 起，函数内部的 `__func__` 表现得如同存在一个静态字符数组，保存当前函数名称。

```
#include <stdio.h>

static void app_sensor_start(void)
{
    (void)printf("function=%s\n", __func__);
}
```

不能：

```
#if defined(__func__)
/* 这不是检测 __func__ 是否可用的正确方式。 */
#endif
```

也不能依赖相邻字符串字面量连接：

```
/* 错误：__func__ 不是字符串字面量宏。 */
const char *text = "function=" __func__;
```

正确方式是作为运行期函数参数传递：

```
app_log_write(__FILE__, __LINE__, "%s: ready", __func__);
```

GCC/Clang 的 `__FUNCTION__`、`__PRETTY_FUNCTION__` 属于扩展，应避免不必要地替代标准 `__func__`。

### 5.5 `__STDC_VERSION__`：版本门槛与能力门槛分开

常见正式值：

|版本|值|
|---|---|
|C95|`199409L`|
|C99|`199901L`|
|C11|`201112L`|
|C17|`201710L`|
|C23|`202311L`|

要求 C11 的纯 C 模块：

```
#if !defined(__STDC_VERSION__)
#error "This module requires C11 or later"
#elif __STDC_VERSION__ < 201112L
#error "This module requires C11 or later"
#endif
```

但头文件需要兼容 C++ 时，不应直接套用：

```
#if defined(__cplusplus)

# if __cplusplus < 201103L
#  error "C++11 or later is required"
# endif

#else

# if !defined(__STDC_VERSION__)
#  error "C11 or later is required"
# elif __STDC_VERSION__ < 201112L
#  error "C11 or later is required"
# endif

#endif
```

部分工具链对 `__cplusplus` 的历史行为依赖选项，因此兼容清单还需要实际编译测试。

**不要从 C11 模式直接推导标准线程库、原子操作后端和全部可选特性均可用于当前工程。**

### 5.6 `__STDC_HOSTED__`：描述实现环境，不描述整个固件

```
#if __STDC_HOSTED__ == 1
#define APP_C_ENV_HOSTED 1
#else
#define APP_C_ENV_HOSTED 0
#endif
```

独立式环境常见于裸机和部分 RTOS 工程，但这不意味着：

- 一定没有 `malloc`。
- 一定没有 `printf`。
- 一定不能链接 libc。
- 一定不存在文件接口。

反过来，宿主式模式也不能证明：

- 输出后端连接成功。
- `stdout` 可在 ISR 使用。
- 动态分配具有确定的最坏时间。
- 所有系统调用桩已正确接入。

需要某个库功能时，用构建配置和链接验证明确表达：

```
#ifndef APP_HAVE_VSNPRINTF
#error "APP_HAVE_VSNPRINTF must be provided by the build configuration"
#endif

#if !APP_HAVE_VSNPRINTF
#error "Text formatting backend requires vsnprintf"
#endif
```

### 5.7 可选能力宏：原子、线程与 VLA

C11/C17 原子能力检查：

```
#if defined(__STDC_NO_ATOMICS__) && (__STDC_NO_ATOMICS__ == 1)
#error "This module requires C atomic support"
#endif

#include <stdatomic.h>
```

这只是第一步。

还需要区分：

```
原子语法可用
  ↓
原子类型和操作可编译
  ↓
所需运行库可链接
  ↓
具体对象上的操作是否无锁
  ↓
是否适合目标 ISR 和实时性要求
```

可用 `atomic_is_lock_free()` 查询具体对象：

```
#include <stdatomic.h>
#include <stdbool.h>

static atomic_uint app_event_count;

bool app_event_counter_is_lock_free(void)
{
    return atomic_is_lock_free(&app_event_count);
}
```

但这个返回值也不证明：

- 当前中断优先级使用合法。
- 特定操作延迟符合预算。
- 所有目标核心行为一致。
- 设备内存适合执行该原子操作。

`__STDC_NO_THREADS__` 不能用来判断 RTOS 是否存在。FreeRTOS 任务接口与 C 标准 `<threads.h>` 不是同一套能力。

对于 VLA：

- C11/C17 中相关支持是可选的。
- C23 调整了变长修改类型等支持要求，`__STDC_NO_VLA__` 的解释需要按对应标准版本处理。
- 工业项目如果禁止 VLA，应通过编码规则和编译器诊断执行，而不是只看一个宏。

### 5.8 编译器身份检测：注意兼容宏重叠

```
#if defined(__clang__)
#define APP_COMPILER_CLANG 1
#define APP_COMPILER_GCC   0

#elif defined(__GNUC__)
#define APP_COMPILER_CLANG 0
#define APP_COMPILER_GCC   1

#else
#define APP_COMPILER_CLANG 0
#define APP_COMPILER_GCC   0
#endif
```

Clang 常定义 GCC 兼容宏，因此顺序重要。

但即便这个分类正确，以下推理仍不可靠：

```
#if APP_COMPILER_GCC
/* Assume any desired GCC extension exists. */
#endif
```

对具体属性，应优先使用能力查询：

```
#if defined(__has_attribute)
# if __has_attribute(format)
#  define APP_PRINTF_FORMAT(fmt_index_, first_arg_) \
       __attribute__((format(printf, fmt_index_, first_arg_)))
# endif
#endif

#ifndef APP_PRINTF_FORMAT
#define APP_PRINTF_FORMAT(fmt_index_, first_arg_)
#endif
```

对于不提供查询机制的受支持工具链，可在专门的适配文件中，根据已验证版本补充实现。

### 5.9 目标宏、浮点能力与 ABI

常见目标扩展：

|宏|常见工具链语境|用途|
|---|---|---|
|`__arm__`|GCC/Clang 等|Arm 目标识别|
|`__thumb__`|GCC/Clang 等|Thumb 代码生成模式|
|`__ARM_ARCH`|Arm 相关工具链|架构级别|
|`__ARM_FP`|支持相应 Arm 约定的工具链|浮点指令能力信息|
|`__ARM_PCS_VFP`|相应 Arm ABI 环境|VFP 参数传递相关 ABI|
|`__riscv`|RISC-V 工具链|RISC-V 目标识别|
|`__riscv_xlen`|RISC-V 工具链|整数寄存器宽度|
|`__BYTE_ORDER__`|GCC/Clang 常见扩展|目标字节序|

Arm 的关键区分：

```
硬件具有 FPU
≠ 当前选项允许生成浮点指令
≠ 当前采用硬浮点参数传递 ABI
≠ 启动代码已启用 FPU
≠ RTOS 已正确管理浮点上下文
```

示例构建契约：

```
#if defined(__arm__) && defined(APP_REQUIRE_HARD_FLOAT_ABI)

# if APP_REQUIRE_HARD_FLOAT_ABI
#  if !defined(__ARM_PCS_VFP)
#   error "This build requires the validated VFP calling convention"
#  endif
# endif

#endif
```

该检查必须限制在已经确认宏语义的工具链范围内。预编译库还要检查 ELF 属性和链接器兼容性诊断。

### 5.10 `__DATE__` 与 `__TIME__`：时间字符串不是版本系统

典型形式：

```
static const char app_translation_time[] =
    __DATE__ " " __TIME__;
```

通常日期格式类似：

```
Jul  8 2026
```

时间格式类似：

```
14:35:07
```

需要注意：

- 不是统一的 ISO 8601 表达。
- 不包含标准化时区信息。
- 不同翻译单元可能在不同时间翻译。
- 增量构建可能混合旧对象和新对象。
- 相同源码可能产生不同二进制。

推荐用构建系统提供：

```
/* Generated header: app_build_config.h */
#define APP_RELEASE_VERSION "2.4.1"
#define APP_BUILD_ID        "release-2.4.1-ci-1842"
#define APP_SOURCE_REVISION "0123456789abcdef"
#define APP_CONFIG_ID       "controller-a-prod"
```

这些项目宏的值应来自受控构建流程。

**源码版本也不等于完整构建身份。** 还应记录配置、工具链和关键构建输入。

### 5.11 `__COUNTER__`、`__BASE_FILE__`、`__FILE_NAME__`

这些是部分编译器提供的扩展。

- `__COUNTER__`：每次展开递增，适合生成局部唯一名称。
- `__BASE_FILE__`：某些工具链提供主输入文件信息。
- `__FILE_NAME__`：某些工具链提供文件名部分。

风险：

- 不属于通用 C11/C17 保证。
- 预编译头和包含顺序会影响 `__COUNTER__` 的使用边界。
- 文件名可能重名。
- 不能把计数值当成跨构建稳定的协议 ID。

局部唯一名称示例：

```
#define APP_CAT_RAW(a_, b_) a_##b_
#define APP_CAT(a_, b_) APP_CAT_RAW(a_, b_)

/* Only in a validated toolchain environment. */
#define APP_UNIQUE_NAME(prefix_) APP_CAT(prefix_, __COUNTER__)
```

**不要在公共 ABI、持久化格式或跨翻译单元编号中依赖 `__COUNTER__`。**

## 6. 性能量化分析

### 6.1 宏展开本身没有运行期查询

```
const char *file = __FILE__;
int line = __LINE__;
```

不需要运行时询问编译器“当前在哪一行”。

成本来自展开后的代码和数据：

- 文件路径字符串。
- 日志调用。
- 参数传递。
- 格式化。
- 故障记录结构体。
- 链接保留的辅助库。

### 6.2 源位置字符串的存储计算

假设：

- 100 个源文件的路径均被保留。
- 每条路径平均 72 字节，不含终止零。
- 每个路径只保留一份。

计算：

```
路径存储 = 100 × (72 + 1)
         = 7300 字节
```

如果缩短为平均 18 字节：

```
缩短后 = 100 × (18 + 1)
       = 1900 字节

计算差值 = 7300 − 1900
         = 5400 字节
```

这是模型值，最终差异取决于：

- 字符串合并。
- 各调用点是否共享路径。
- LTO。
- 段垃圾回收。
- 对齐。
- 某些源文件是否完全未保留。

特别注意：

```
"module.c:10"
"module.c:20"
```

与“一个共享文件名 + 两个整数行号”的存储模型不同。

大量使用 `APP_SOURCE_TEXT` 可能生成许多不同的位置字符串，必须检查最终 `.rodata`。

### 6.3 故障记录结构体尺寸

假设 32 位 ABI 下指针和 `uint32_t` 都为 4 字节，且相关对齐为 4：

```
typedef struct {
    const char *file;
    const char *function;
    uint32_t line;
    uint32_t fault_code;
} app_fault_record_t;
```

常见尺寸：

```
2 × 4 + 2 × 4 = 16 字节
```

在 64 位宿主上，常见尺寸可能为 24 字节。应以实际目标 `sizeof` 为准。

如果跨复位保存或跨设备传输，不能直接保存这种含指针的本机结构体：

- 指针在其他镜像或地址空间中没有意义。
- 布局可能变化。
- 字节序可能变化。
- 固件升级后地址可能改变。

持久化记录更适合保存：

```
构建 ID + 模块 ID + 行号 + 故障码
```

### 6.4 版本比较没有运行期分支

```
#if __STDC_VERSION__ >= 201112L
/* implementation A */
#else
/* implementation B */
#endif
```

未选分支在预处理阶段被丢弃。

但选择了哪种实现，可能显著影响性能。例如：

- 原子指令与运行库锁。
- 内建位操作与循环实现。
- 硬件浮点与软件浮点。
- 主机替身与真实 MMIO。

因此性能分析应面向**所选实现**，不能只报告宏本身没有开销。

### 6.5 可复现构建的量化验证

同一份源码执行两次独立构建：

```
输入相同
配置相同
工具链相同
构建路径不同
构建时间不同
```

比较：

1. 最终固件哈希。
2. ELF 的可分配段。
3. 调试信息。
4. 字符串表。
5. 构建元数据。

如果目标是整个 ELF 逐字节一致，仅移除 `__TIME__` 还不够，还要控制：

- 源码路径。
- 调试路径。
- 归档元数据。
- 链接器生成标识的策略。
- 生成文件顺序。
- 工具链版本。
- 签名或打包过程中的时间字段。

### 6.6 实测平台与验证方法

当前未提供目标平台，因此没有可声明为本课实测的 Flash、周期和栈数据。

建议选择实际项目平台，记录：

|项目|必填信息|
|---|---|
|处理器|MCU 型号、架构、频率|
|内存|缓存、Flash 等待周期|
|工具链|编译器、汇编器、链接器版本|
|编译|优化级别、LTO、目标 ABI|
|日志|同步、队列、DMA 或事件编码|
|测量|map、反汇编、周期计数器、栈统计|

测试组：

- 不携带源位置。
- 文件名加行号。
- 文件名、行号加函数名。
- 模块 ID 加行号。
- 完整文本格式化日志。

**只在其他条件固定时，才能把尺寸和时间变化归因于源位置方案。**

## 7. 应用场景选型指南

### 7.1 纯文本决策流程图

```
需要哪类信息？
├─ 调用位置
│  ├─ 开发定位 → __FILE__ + __LINE__ + __func__
│  └─ 量产事件 → 构建 ID + 模块 ID + 行号
├─ 语言标准
│  ├─ C → __STDC_VERSION__
│  └─ C++ → __cplusplus，并验证工具链选项
├─ 编译器扩展
│  ├─ 有能力查询 → __has_attribute / __has_builtin 等
│  └─ 无能力查询 → 已验证工具链适配 + 编译探测
├─ 目标架构或 ABI
│  └─ 工具链目标宏 + ELF/链接检查
├─ 运行库能力
│  └─ 编译与链接探测 + 项目能力宏
└─ 固件版本
   └─ 构建系统生成版本、配置、源码和工具链标识
```

### 7.2 典型需求选型

|需求|方案|理由|
|---|---|---|
|调试断言定位|`__FILE__`、`__LINE__`、`__func__`|直接保留调用上下文|
|最低 C 标准|`__STDC_VERSION__` 检查|尽早拒绝不支持的语言模式|
|格式串检查|属性能力检测|检查的是具体能力|
|原子 ISR 计数|原子支持检查、无锁检查、目标验证|单一宏不足以证明适用性|
|固件发布追踪|生成构建信息|稳定关联源码与配置|
|发布镜像路径清理|前缀映射 + 产物检查|控制路径信息|
|Arm 浮点 ABI|目标宏与 ELF 属性|区分指令能力和调用约定|
|本地唯一变量|受控使用 `__COUNTER__`|只在局部生成范围内使用|

## 8. 工程最佳实践

### 8.1 建立适配层，不在业务代码中散布厂商宏

建议结构：

```
app_compiler.h       编译器属性与能力封装
app_target.h         架构与 ABI 检查
app_build_info.h     构建信息接口
app_source_loc.h     源位置类型与宏
app_config.h         产品策略
```

业务代码使用：

```
APP_WARN_UNUSED_RESULT
int app_storage_commit(void);
```

而不是到处写：

```
#if defined(__GNUC__)
__attribute__((warn_unused_result))
#endif
```

### 8.2 不定义、取消定义或伪造实现保留宏

错误：

```
#define __GNUC__ 12
#define __STDC_VERSION__ 201112L
#undef __ARM_PCS_VFP
```

这些操作不会升级编译器能力，反而会误导：

- 标准库头。
- 编译器适配层。
- 第三方库。
- ABI 选择逻辑。

需要模拟测试时，建立项目自己的可注入能力层，不篡改实现身份。

### 8.3 原始宏保留原义，产品策略另起名字

```
#define APP_ALLOW_FLOAT_FORMATTING 0
#define APP_REQUIRE_LOCK_FREE_ISR_COUNTER 1
```

它们是产品要求，不应伪装成：

```
#define __HAS_FLOAT_PRINTF__ 0
```

统一使用项目命名前缀，避免保留标识符。

### 8.4 版本检测只用于明确的版本问题

适合：

- 某已知编译器版本的确定缺陷。
- 某扩展在特定版本正式加入。
- 某 ABI 行为在版本间发生变动。

不适合：

- 用版本号猜测 libc 配置。
- 用前端版本猜测硬件能力。
- 用 GCC 兼容版本猜测 Clang 的完整特性。

版本规避应包含：

```
问题说明
受影响范围
最小复现
替代路径
解除条件
```

### 8.5 路径映射必须覆盖相应产物

GCC/Clang 的部分版本支持以下选项：

```
-fmacro-prefix-map=old=new
-fdebug-prefix-map=old=new
-ffile-prefix-map=old=new
```

作用范围和支持情况以工具链文档为准。

不能仅仅在运行时截取 basename：

```
const char *short_name = find_basename(__FILE__);
```

就断言完整路径已经从固件删除。

运行时返回后缀地址不保证原始完整字符串不会留在镜像中。

### 8.6 选型决策矩阵

|设计目标|优先选择|避免|
|---|---|---|
|标准可移植|标准宏、编译探测|无必要的厂商扩展|
|可复现构建|受控生成元数据|默认嵌入当前日期时间|
|量产故障追踪|构建 ID + 稳定事件编码|只保存函数地址|
|编译器兼容|能力检测|单看厂商名字|
|ABI 一致性|编译选项、目标宏、ELF 验证|单一宏推断全部 ABI|
|小镜像|模块 ID、共享字符串|每处完整位置字符串|
|跨语言公共头|C/C++ 分别检测|用 C 宏判断 C++ 版本|

## 9. 常见错误与避坑指南

### 9.1 错误一：把 `__func__` 当宏或字符串字面量

**错误代码：**

```
#define APP_FUNCTION_TEXT "function=" __func__
```

**根因：** `__func__` 是函数内预定义标识符，不是字符串字面量宏。

**正确实现：**

```
APP_LOG("function=%s", __func__);
```

**风险影响：**

- 编译失败。
- 通过 `defined(__func__)` 得到错误的能力判断。

---

### 9.2 错误二：GCC 检测抢先匹配 Clang

**错误代码：**

```
#if defined(__GNUC__)
#define APP_COMPILER_NAME "GCC"
#elif defined(__clang__)
#define APP_COMPILER_NAME "Clang"
#endif
```

**根因：** Clang 常定义 GCC 兼容宏。

**正确实现：**

```
#if defined(__clang__)
#define APP_COMPILER_NAME "Clang"
#elif defined(__GNUC__)
#define APP_COMPILER_NAME "GCC-compatible"
#else
#define APP_COMPILER_NAME "Other"
#endif
```

身份识别之外，具体能力单独检测。

**风险影响：**

- 进入错误的缺陷规避分支。
- 使用不适用的诊断 pragma 或扩展。

---

### 9.3 错误三：用日期时间代替版本标识

**错误代码：**

```
const char app_firmware_version[] = __DATE__ " " __TIME__;
```

**根因：** 翻译时间没有覆盖源码、配置和工具链身份。

**正确实现：**

```
#include "app_build_config.h"

const char app_firmware_version[] = APP_RELEASE_VERSION;
const char app_build_id[] = APP_BUILD_ID;
```

**风险影响：**

- 同一源码产生不同镜像。
- 不同源码可能有相同或混淆的时间字符串。
- 增量构建的元数据不能反映完整镜像。

---

### 9.4 错误四：用 C11 模式证明原子操作适合 ISR

**错误代码：**

```
#if __STDC_VERSION__ >= 201112L
#define APP_ISR_ATOMIC_SAFE 1
#endif
```

**根因：** 混淆语言版本、原子库支持、无锁实现和 ISR 约束。

**正确实现：**

```
#if !defined(__STDC_VERSION__) || \
    (__STDC_VERSION__ < 201112L)
#error "C11 or later is required"
#endif

#if defined(__STDC_NO_ATOMICS__) && (__STDC_NO_ATOMICS__ == 1)
#error "Atomic support is required"
#endif
```

随后验证无锁性、运行库、反汇编和目标时序。

**风险影响：**

- ISR 中调用隐含锁或不可用的运行库。
- 实时性不满足要求。
- 中断与任务竞争时出现无法接受的行为。

---

### 9.5 错误五：在普通函数中获取调用方位置

**错误代码：**

```
void app_fail(void)
{
    app_fault_record(__FILE__, __LINE__);
}
```

所有调用都记录相同包装函数位置。

**正确实现：**

```
void app_fail_at(const char *file, int line);

#define APP_FAIL() app_fail_at(__FILE__, __LINE__)
```

**风险影响：**

- 多个故障点被合并。
- 现场记录无法定位实际调用处。

---

### 9.6 错误六：认为独立式环境没有 libc

**错误代码：**

```
#if __STDC_HOSTED__ == 0
#define APP_HAVE_MEMCPY 0
#endif
```

**根因：** 独立式实现分类不等于具体项目库函数清单。

**正确实现：**

```
#ifndef APP_HAVE_MEMCPY
#error "Library capabilities must be supplied by the build"
#endif
```

通过实际工具链与链接配置确定能力。

**风险影响：**

- 无端禁用可用实现。
- 引入不必要的自制替代函数。
- 不同构建模式选择错误后端。

---

### 9.7 错误七：用 `__LINE__` 生成同一行上的唯一符号

**错误代码：**

```
#define APP_CAT_RAW(a_, b_) a_##b_
#define APP_CAT(a_, b_) APP_CAT_RAW(a_, b_)

#define APP_TEMP_NAME APP_CAT(app_temp_, __LINE__)
```

同一物理或推定行多次展开时，可能生成同名标识符。

**根因：** 行号是位置，不是全局唯一编号。

**正确实现：**

- 优先使用局部作用域和普通变量。
- 在受控工具链中，可使用 `__COUNTER__`。
- 需要持久稳定编号时，显式分配 ID。

**风险影响：**

- 重定义。
- 宏组合后意外名称冲突。
- 依赖包含顺序的编号变化。

## 10. 多机制组合使用方案

下面设计一个完整的诊断接口，组合：

- 源位置。
- 格式串属性检查。
- C11 可变参数宏。
- 有界格式化。
- 错误状态。
- 构建标识。
- 明确的并发与 ISR 限制。

### 10.1 公共头文件

```
/* app_diag.h */
#ifndef APP_DIAG_H_INCLUDED
#define APP_DIAG_H_INCLUDED

#include <stddef.h>
#include <stdint.h>

#if defined(__has_attribute)
# if __has_attribute(format)
#  define APP_DIAG_PRINTF_FORMAT(fmt_index_, first_arg_) \
       __attribute__((format(printf, fmt_index_, first_arg_)))
# endif
#endif

#ifndef APP_DIAG_PRINTF_FORMAT
#define APP_DIAG_PRINTF_FORMAT(fmt_index_, first_arg_)
#endif

#ifdef __cplusplus
extern "C" {
#endif

typedef struct {
    const char *file;
    const char *function;
    uintmax_t line;
} app_source_loc_t;

typedef enum {
    APP_DIAG_OK = 0,
    APP_DIAG_TRUNCATED,
    APP_DIAG_INVALID,
    APP_DIAG_FORMAT_ERROR,
    APP_DIAG_BACKEND_ERROR
} app_diag_status_t;

/*
 * Task-context only.
 * Formatting and backend must be safe for the configured runtime.
 *
 * Backend must not retain the supplied message pointer.
 * Concurrent callers require backend/runtime support or serialization.
 *
 * format must be a trusted format string.
 */
app_diag_status_t app_diag_emit_at(
    const char *file,
    uintmax_t line,
    const char *function,
    const char *format,
    ...) APP_DIAG_PRINTF_FORMAT(4, 5);

#ifdef __cplusplus
}
#endif

#define APP_DIAG(...) \
    app_diag_emit_at(__FILE__, \
                     (uintmax_t)__LINE__, \
                     __func__, \
                     __VA_ARGS__)

#endif
```

格式属性位置解释：

```
参数 4：格式串
参数 5：第一个格式化实参
```

这个宏应在函数内部调用，因为它使用 `__func__`。

### 10.2 实现文件

```
/* app_diag.c */
#include "app_diag.h"

#include <stdarg.h>
#include <stdio.h>

#define APP_DIAG_BUFFER_SIZE 128u

/*
 * Platform hook.
 *
 * The implementation must consume/copy message before returning.
 * Returns zero on success, nonzero on failure.
 */
extern int app_diag_backend_write(
    const app_source_loc_t *location,
    const char *message,
    size_t length);

app_diag_status_t app_diag_emit_at(
    const char *file,
    uintmax_t line,
    const char *function,
    const char *format,
    ...)
{
    char buffer[APP_DIAG_BUFFER_SIZE];
    app_source_loc_t location;
    va_list args;
    int required;
    size_t written;
    app_diag_status_t status;

    if ((file == NULL) ||
        (function == NULL) ||
        (format == NULL)) {
        return APP_DIAG_INVALID;
    }

    va_start(args, format);
    required = vsnprintf(buffer, sizeof(buffer), format, args);
    va_end(args);

    if (required < 0) {
        return APP_DIAG_FORMAT_ERROR;
    }

    if ((size_t)required >= sizeof(buffer)) {
        written = sizeof(buffer) - 1u;
        status = APP_DIAG_TRUNCATED;
    } else {
        written = (size_t)required;
        status = APP_DIAG_OK;
    }

    location.file = file;
    location.function = function;
    location.line = line;

    if (app_diag_backend_write(&location, buffer, written) != 0) {
        return APP_DIAG_BACKEND_ERROR;
    }

    return status;
}
```

### 10.3 工程边界

该框架具备：

- 固定大小格式化缓冲区。
- 截断检测。
- `va_end` 配对。
- 明确后端失败。
- 调用方位置记录。
- 可用时的格式参数检查。

还需要平台层保证：

- `vsnprintf` 的实际实现满足项目需求。
- 不在 ISR 调用。
- 后端不会保留栈上 `buffer` 和 `location` 的地址。
- 多任务并发行为明确。
- 日志不承担业务副作用。
- 生产版本不会把不可信输入直接作为格式串。

**128 字节只是局部字符数组大小，不是整个调用路径的栈峰值。** 格式化库和后端会继续使用栈。

### 10.4 构建信息单一定义

```
/* app_build_info.h */
#ifndef APP_BUILD_INFO_H_INCLUDED
#define APP_BUILD_INFO_H_INCLUDED

typedef struct {
    const char *release_version;
    const char *build_id;
    const char *source_revision;
    const char *config_id;
} app_build_info_t;

extern const app_build_info_t app_build_info;

#endif
```

```
/* app_build_info.c */
#include "app_build_info.h"
#include "app_build_config.h"

const app_build_info_t app_build_info = {
    APP_RELEASE_VERSION,
    APP_BUILD_ID,
    APP_SOURCE_REVISION,
    APP_CONFIG_ID
};
```

将构建字符串集中在一个实现文件，避免每个翻译单元各自生成元数据对象。

### 10.5 协同架构

```
构建系统
  ├─ 生成构建身份
  ├─ 固定目标与 ABI
  └─ 归档宏快照
          ↓
基础适配层
  ├─ 语言检查
  ├─ 属性检测
  └─ 目标契约检查
          ↓
诊断入口宏
  └─ 捕获文件、行号、函数
          ↓
有界格式化 / 固定事件记录
          ↓
平台后端
          ↓
现场记录 + 对应版本符号与源码
```

## 11. 工业级实际案例分析

以下是工业领域中的典型工程场景，不将示例描述为未经证实的具体企业项目。

### 11.1 案例一：工业控制器的现场故障回溯

#### 需求

设备在客户现场运行，故障后只能读取少量非易失记录，要求能定位到对应固件和调用位置。

#### 架构设计

- 固件包含稳定构建 ID。
- 模块具有显式分配的稳定 ID。
- 故障记录保存数值字段。
- 服务端使用构建 ID 找到对应源码和符号。
- 不直接持久化 `__FILE__` 指针。

#### 核心代码

```
#include <stdint.h>

typedef struct {
    uint32_t format_version;
    uint32_t module_id;
    uint32_t line;
    uint32_t fault_code;
} app_fault_payload_t;

/*
 * The implementation adds build identity, sequence, integrity data,
 * and performs explicit serialization.
 */
extern int app_fault_store(const app_fault_payload_t *payload);

#define APP_MODULE_MOTOR_CONTROL UINT32_C(17)

#define APP_STORE_FAULT(code_)                                  \
    do {                                                       \
        const app_fault_payload_t app_fault_local_ = {          \
            UINT32_C(1),                                       \
            APP_MODULE_MOTOR_CONTROL,                          \
            (uint32_t)__LINE__,                                \
            (uint32_t)(code_)                                  \
        };                                                     \
        (void)app_fault_store(&app_fault_local_);                \
    } while (0)
```

#### 设计要点

- 这里忽略返回值仅适用于上层明确接受“尽力记录”的路径；正常故障管理应监控记录失败。
- 行号必须与构建 ID 配对。
- 模块 ID 不从 `__COUNTER__` 自动生成。
- Flash 写入不能随意放进中断或异常处理路径。
- 掉电一致性、磨损和故障上下文可执行性需要专门设计。

---

### 11.2 案例二：同一固件的可复现发布

#### 需求

相同源码与配置，在两个受控环境构建，要求最终发布载荷一致。

#### 原始问题

```
const char app_build_stamp[] = __DATE__ " " __TIME__;
```

开发机路径又通过 `__FILE__` 进入镜像：

```
/home/alice/work/controller/src/motor.c
/build/ci/job-1842/src/motor.c
```

即便机器码逻辑相同，镜像也不同。

#### 架构设计

- 发布版本来自版本控制和 CI。
- 日期字段如确有需求，由统一构建元数据策略生成。
- 映射源码与调试路径。
- 固定生成文件顺序。
- 检查最终发布载荷，而不是只比较 `.text`。
- 签名和封装阶段单独定义可复现目标。

#### 核心代码

```
#include "app_build_config.h"

const char app_release[] = APP_RELEASE_VERSION;
const char app_revision[] = APP_SOURCE_REVISION;
const char app_configuration[] = APP_CONFIG_ID;
```

#### 设计要点

- GCC 等工具链支持的 `SOURCE_DATE_EPOCH` 可用于相关时间处理，但它不是 ISO C 规则。
- 不应假定所有工具和所有打包步骤都遵循该环境变量。
- 发布档案保留源码、配置、工具链、链接脚本和生成器版本。
- 路径映射是否覆盖宏与调试信息，需要分别验证。

### 11.3 案例三：Cortex-M 浮点库集成故障

#### 需求

应用、DSP 库和 RTOS 端口必须采用兼容的浮点 ABI，并正确管理浮点上下文。

#### 典型误判

```
#ifdef __ARM_FP
/* Assume hard-float ABI and correct RTOS integration. */
#endif
```

#### 架构设计

分别检查：

1. CPU 型号与 FPU 能力。
2. 编译器 `-mcpu/-mfpu/-mfloat-abi` 等实际选项。
3. 工具链目标宏。
4. 静态库 ELF 属性。
5. 启动代码。
6. RTOS 浮点上下文管理。
7. 实机任务切换测试。

#### 核心检查

```
#if defined(APP_REQUIRE_HARD_FLOAT_ABI) && \
    APP_REQUIRE_HARD_FLOAT_ABI

# if !defined(__ARM_PCS_VFP)
#  error "Expected validated hard-float calling convention"
# endif

#endif
```

#### 设计要点

- 该检查只适用于已验证会提供该宏的工具链。
- 不能用一条预处理检查替代库兼容性检查。
- 链接成功也不能证明启动阶段已启用 FPU。
- 实机测试应包含浮点任务切换、嵌套中断和异常路径。

## 12. 高频问题深度答疑

### 12.1 `__FILE__` 是绝对路径还是相对路径？

标准不要求统一为某一种路径形式。

实际结果受以下因素影响：

- 编译命令中的输入路径。
- 构建工具工作目录。
- `#include` 使用方式。
- 编译器路径映射选项。
- `#line`。

如果产品需要固定形式，应通过构建策略保证，并检查预处理输出和最终镜像。

### 12.2 可以通过 `__GNUC__` 判断所有 GCC 内建函数吗？

不能。

原因包括：

- 其他编译器定义兼容宏。
- 内建函数可能依赖版本和目标。
- 某些内建会展开成运行库调用。
- 编译器识别并不等于目标能够无辅助实现。

例如，一个原子内建可能需要额外运行库。验证应包含编译、链接和必要的反汇编检查。

### 12.3 `__STDC_NO_ATOMICS__` 没定义，是不是一定支持无锁原子？

不是。

它与无锁性是不同问题。

无锁性还受：

- 原子类型。
- 对象尺寸。
- 对齐。
- 目标指令集。
- 工具链实现。
- 当前编译选项。

影响。

对于 ISR，除了无锁性，还要验证中断语义和最坏执行时间。

### 12.4 为什么日志里有文件名和行号，还需要构建 ID？

因为同一行号会随源码修改而改变。

```
版本 A：motor.c:180 是电流限幅
版本 B：motor.c:180 是状态切换
```

现场只记录 `motor.c:180`，无法唯一定位。

构建 ID 将记录绑定到：

- 对应源码。
- 产品配置。
- 工具链。
- 符号文件。
- 必要的生成文件。

### 12.5 能否用编译时间实现过期机制或防回滚？

不应把 `__DATE__`、`__TIME__` 当作安全依据。

问题包括：

- 构建机器时间不可信。
- 没有标准化时区。
- 可通过构建环境改变。
- 与签名版本策略没有必然联系。
- 增量构建可能保留旧字段。

防回滚应基于经过验证的版本计数、签名策略和可信持久化状态。预定义时间宏只适合作为受限诊断信息。

### 12.6 为什么宏快照必须使用目标编译选项？

因为预定义宏取决于编译选项。

```
同一编译器
  + 不同 -mcpu
  + 不同浮点 ABI
  + 不同语言标准
  + 不同 -ffreestanding 设置
```

可能产生不同的宏集合。

不带真实选项生成的快照，只能说明默认环境，不能证明某个固件的构建环境。

## 13. 课程核心总结

### 13.1 核心要点

- **先区分标准宏、扩展宏与项目配置宏。**
- **`__func__` 是预定义标识符，不是预处理宏。**
- **`__FILE__`、`__LINE__` 适合诊断，不适合作为可信身份。**
- **标准版本、编译器身份、具体能力、ABI 和运行支持必须分别验证。**
- **不要修改实现保留宏来伪造环境。**
- **日期时间宏不等于发布版本，也不等于可信时间。**
- **现场位置记录必须关联构建身份。**
- **预定义宏快照需要携带真实目标选项。**

### 13.2 性能排序

不存在通用的“某个预定义宏更快”。

从诊断数据体积看，在明确设计假设下通常是：

```
稳定模块 ID + 数值行号
    数据较紧凑

共享文件名 + 数值行号
    可读性和空间折中

每调用点完整位置字符串
    可能产生更多不同字符串

完整文本格式化
    还增加格式化与输出成本
```

最终以目标 map、反汇编和实际测量为准。

### 13.3 通用选型结论

|目标|结论|
|---|---|
|开发定位|标准源位置宏与 `__func__`|
|产品追踪|受控构建元数据|
|能力选择|能力查询与构建探测|
|ABI 保证|编译选项、目标宏、ELF 和库检查|
|可复现构建|控制时间、路径和生成输入|
|实时诊断|数值事件，延迟格式化|
|长期维护|适配层集中封装|

### 14.1 场景选型表

|需求|推荐接口|
|---|---|
|当前推定文件名|`__FILE__`|
|当前推定行号|`__LINE__`|

|原子 ISR 适用性|支持、无锁、平台和时序验证|

### 14.2 特性对比表

|信息|是否标准 C 宏|能否直接证明运行行为|
|---|---|---|
|`__FILE__`|是|否|
|`__LINE__`|是|否|
|`__DATE__` / `__TIME__`|是|否|
|`__STDC_VERSION__`|是，按版本条件提供|否|
|`__STDC_HOSTED__`|是|否|
|`__func__`|不是宏，是标准标识符|仅提供函数名称|
|`__GNUC__`|否|否|
|`__ARM_FP`|非 ISO C，属于目标约定|否|
|`__COUNTER__`|C11/C17 中属于扩展|否|
|`NDEBUG`|标准接口控制宏，非自动预定义|控制 `assert` 展开|
|`APP_BUILD_ID`|项目宏|依赖构建流程保证|

### 14.3 宏环境导出示例

GCC 类 Arm 工具链示例，选项应替换为真实项目值：

```
arm-none-eabi-gcc \
  -std=c11 \
  -mcpu=cortex-m4 \
  -mthumb \
  -mfpu=fpv4-sp-d16 \
  -mfloat-abi=hard \
  -dM -E -x c \
  /dev/null
```

该例使用 POSIX 的 `/dev/null`。其他环境可以提供一个空的 `.c` 文件。

分别保留：

- 仅工具链与目标选项的基础快照。
- 包含产品配置后的项目宏快照。

两者用途不同，不能混为一份环境证明。

## 16. 实践与进阶路径

### 16.1 第一阶段：建立宏分类实验

创建一个最小文件，观察：

- `__FILE__`。
- `__LINE__`。
- `__DATE__`。
- `__TIME__`。
- `__STDC_VERSION__`。
- `__STDC_HOSTED__`。
- 编译器身份宏。
- 目标架构宏。

分别切换：

- C11 与 C17。
- 宿主编译器与交叉编译器。
- 默认模式与独立式选项。
- 不同 CPU 与浮点 ABI。

**验收：每个宏都能说明定义者、含义和不能证明的事项。**

### 16.2 第二阶段：实现源位置诊断接口

实现本课的 `APP_DIAG`：

- 有界格式化。
- 格式串检查。
- 截断状态。
- 后端失败。
- 文件、函数和行号。
- 明确调用上下文。

添加有意义的验证：

- 普通日志正确记录调用行。
- 长字符串正确截断。
- 后端失败能够返回。
- 空格式串指针被拒绝。
- 支持格式检查的工具链能诊断参数类型错误。

### 16.3 第三阶段：验证路径和尺寸

构建三种版本：

|版本|源位置信息|
|---|---|
|A|完整路径、函数、行号|
|B|映射路径、函数、行号|
|C|模块 ID、行号|

比较：

- `.rodata`。
- `.text`。
- 总 Flash。
- 单次调用栈。
- 日志传输长度。
- 现场定位能力。

**验收：用产物证明空间变化，不按源码表面长度估计。**

### 16.4 第四阶段：可复现构建实验

在两个不同构建目录执行相同构建：

1. 初始保留 `__DATE__`、`__TIME__`。
2. 检查镜像差异。
3. 移除翻译时间依赖。
4. 统一源码与调试路径。
5. 固定生成输入。
6. 再次比较发布载荷和 ELF。

**验收：明确哪些产物要求逐字节一致，哪些外层签名或封装字段采用独立策略。**

### 16.5 第五阶段：目标能力验证

选择一个真实平台能力，例如原子计数或浮点 DSP：

```
预定义宏检查
  ↓
最小编译
  ↓
最小链接
  ↓
ELF 属性与反汇编
  ↓
目标运行
  ↓
负载和边界测试
```

原子计数重点测试：

- 所需类型。
- 对齐。
- 无锁性。
- 中断和任务竞争。
- 最坏延迟。

浮点重点测试：

- 库 ABI。
- 启动使能。
- 任务切换。
- 中断上下文。
- 栈峰值。

### 16.6 进阶方向

- 编译器内建函数与运行库辅助调用。
- Arm ACLE、RISC-V 扩展与目标特性检测。
- C23 特性与工具链实现差异。
- 可复现构建和供应链元数据追踪。
- 源位置压缩与离线日志解码。
- 统一故障事件字典和构建 ID 服务。
- 多核系统中的原子实现与内存模型。
- 预编译头、模块化构建与宏环境一致性。
