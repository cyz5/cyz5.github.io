
## 1. 学习目标

### 理解

- 理解联合体中所有成员共享同一段存储空间，但具有不同成员类型和访问语义。
- 理解联合体大小、对齐和成员偏移受实现及 ABI 影响。
- 理解联合体本身不记录当前有效成员，类型判别必须由外部状态或协议提供。
- 理解“写入一个成员、读取另一个成员”与结构体成员访问、类型转换及严格别名规则的区别。

### 掌握

- 能设计带枚举标签的安全联合体。
- 能使用联合体表达互斥状态、变体消息、资源复用和硬件寄存器视图。
- 能正确初始化联合体、管理活动成员，并处理对象生命周期和错误路径。
- 能区分 union type-punning、`memcpy`、指针强转及显式序列化的适用范围。

### 精通

- 能分析联合体在 ABI、编译器优化、有效类型、陷阱表示、字节序和未对齐访问方面的风险。
- 能设计跨模块、跨任务、跨核使用联合体时的同步和所有权规则。
- 能审查 union 与位域、packed、DMA、寄存器映射、持久化格式之间的组合风险。
- 能根据目标编译器和 MCU 的真实行为制定测试与静态验证策略。

### 能够设计

- 能为协议解析器设计版本化、带标签的变体消息结构。
- 能为状态机和驱动实例设计内存占用可控、状态明确的联合体模型。
- 能设计可审计的 union API，明确标签、有效成员、生命周期、并发访问和错误状态。
- 能在需要兼容硬件布局时通过 ABI 文档、编译期断言和目标板验证建立布局契约。

### 知识要求

- 熟悉结构体、枚举、指针、数组、存储期和类型限定符。
- 理解对象表示、字节序、对齐和结构体填充。

- 能使用调试器或反汇编工具确认联合体访问的实际代码生成。

## 3. 技术概述

### 3.1 联合体的定义

联合体是一种复合类型，其所有非位域成员**共享同一块存储区域**：

```
union value_t {
    uint32_t u32;
    float    f32;
    uint8_t  bytes[4];
};
```

同一个联合体对象可以按不同成员类型解释这块存储。联合体至少需要足够的空间容纳其最大成员，并满足所有成员所需的对齐。

通常：

```
sizeof(union) >= 所有成员 sizeof 的最大值
alignof(union) >= 所有成员对齐要求的最大值
```

具体大小、对齐和成员偏移还可能受 ABI 与编译器扩展影响。

### 3.2 共享存储不等于自动判型

```
union payload_t {
    uint32_t command;
    float    measurement;
};
```

`payload_t` 对象本身不包含“当前存的是 `command` 还是 `measurement`”这个标签。程序必须通过其他机制知道当前成员，例如：

- 配套枚举标签；
- 状态机状态；
- 协议字段；
- 外部硬件状态；
- API 契约。

**不带标签的联合体只是共享存储，不是自描述变体类型。**

### 3.3 技术价值

- **内存复用**：不同时间或不同状态下只需要一种成员存储。
- **状态建模**：表示“多个互斥状态之一”。
- **协议或消息载荷**：在统一外壳中承载不同类型的内容。
- **硬件寄存器视图**：某些目标上的寄存器视图或厂商接口会使用联合体。
- **低成本类型选择**：比所有候选字段同时存储更节省空间。

### 3.4 主流应用分支

|应用分支|常见形式|主要约束|
|---|---|---|
|带标签变体|`enum tag + union payload`|标签必须与活动成员一致|
|消息载荷|固定最大载荷联合体|需定义编码和边界|
|状态互斥资源|多种状态共享缓存区|状态切换需清理资源和更新状态|
|寄存器视图|`union` 配位域或掩码|依赖芯片与编译器布局|
|位模式观察|数值类型与字节数组共用存储|端序、表示和标准规则限制|
|内存池槽位|多种对象共用固定尺寸槽|对齐和对象生命周期必须正确|

## 4. 核心特性横向对比

### 4.1 联合体与结构体对比

|特性|`struct`|`union`|
|---|---|---|
|成员是否各自拥有存储|是|否，共享存储|
|总大小|成员大小加填充|至少容纳最大成员，再按实现对齐|
|成员能否同时保存独立值|能|不能保证；写一个成员会覆盖共享区域|
|成员偏移|按声明顺序递增，可能有填充|所有成员从对象起始处开始，但具体标准细节依实现|
|典型语义|同时存在的字段|互斥的变体或共享表示|
|需不需要标签|视业务而定|通常需要外部标签|
|典型错误|误解 padding、越界|读取错误活动成员、标签不一致|

### 4.2 联合体的不同建模方式

|方案|数据结构|优点|风险|
|---|---|---|---|
|裸联合体|`union payload`|最省空间、简单|无活动成员信息，调用契约脆弱|
|标签 + 联合体|`struct { enum tag; union payload; }`|状态明确，可校验|标签和成员仍需维护一致|
|结构体并集字段|`struct { fields...; }`|可同时保存全部值|内存占用较大|
|`void *` 加类型标签|标签和通用指针|可指向外部对象|生命周期、对齐、强转风险更复杂|
|显式编码字节数组|`uint8_t bytes[N]`|格式可控、跨平台|编解码代码更多|

### 4.3 联合体操作的安全性比较

|操作|可移植性|主要说明|
|---|---|---|
|写入成员后读取同一成员|高|常规用法|
|读取另一成员以“看位模式”|受实现规则约束|不能假设所有平台和类型都可移植|
|用 `memcpy` 复制对象表示|更适合做位模式复制|仍需考虑大小、表示和目标类型有效性|
|将缓冲区强转为联合体指针|风险高|对齐、对象类型、生命周期和长度均可能不满足|
|对联合体原始字节做网络发送|不可移植|端序、填充、表示和协议版本问题|
|带标签联合体并通过 `switch` 访问|推荐|标签与成员需要不变量保护|

## 5. 底层原理与功能特性深度解析

### 5.1 联合体的对象布局

```
#include <stdint.h>

union sample_t {
    uint8_t  byte;
    uint32_t word;
    uint8_t  raw[7];
};
```

这个联合体至少要容纳 7 字节，并满足 `uint32_t` 的对齐要求。常见 ABI 下可能是：

```
sizeof(union sample_t)  == 8
_Alignof(union sample_t) == 4
```

但具体数值必须查询目标实现：

```
#include <stddef.h>
#include <stdint.h>

_Static_assert(sizeof(union sample_t) >= 7U,
               "union cannot hold raw member");
_Static_assert(_Alignof(union sample_t) >= _Alignof(uint32_t),
               "union alignment is insufficient");
```

联合体大小可能大于最大成员大小，原因包括整体对齐和尾部尺寸规则。不要把 `sizeof(union)` 直接等同于最大成员的 `sizeof`，除非目标 ABI 已明确保证并经断言验证。

### 5.2 成员地址与共享存储

联合体成员都从同一存储区域开始：

```
union data_t {
    uint32_t number;
    uint8_t bytes[4];
};

union data_t data;

&data.number;
&data.bytes[0];
```

这两个地址通常数值相同，但类型不同：

```
&data.number   类型为 uint32_t *
&data.bytes[0] 类型为 uint8_t *
```

联合体的目的不是让两个值同时存在，而是让同一存储区域在不同语义下复用。

### 5.3 初始化联合体

未指定成员名的初始化，默认初始化第一个成员：

```
union value_t {
    uint32_t integer;
    float real;
};

union value_t value = { 42U };
```

指定成员的初始化：

```
union value_t value = {
    .real = 1.25f
};
```

在 C99 及之后版本中，指定初始化器使意图清晰。对于带标签联合体，应在同一初始化器中同时设置标签和对应成员：

```
#include <stdint.h>

typedef enum {
    VALUE_KIND_INTEGER,
    VALUE_KIND_REAL
} value_kind_t;

typedef struct {
    value_kind_t kind;
    union {
        uint32_t integer;
        float real;
    } data;
} value_t;

static const value_t initial_value = {
    .kind = VALUE_KIND_REAL,
    .data = {
        .real = 1.25f
    }
};
```

### 5.4 带标签联合体：推荐的通用模式

```
#include <stdint.h>

typedef enum {
    MESSAGE_KIND_STATUS,
    MESSAGE_KIND_SAMPLE,
    MESSAGE_KIND_ERROR
} message_kind_t;

typedef struct {
    uint32_t uptime_ms;
    uint8_t flags;
} status_message_t;

typedef struct {
    int32_t value;
    uint16_t channel;
} sample_message_t;

typedef struct {
    uint16_t code;
    uint32_t detail;
} error_message_t;

typedef struct {
    message_kind_t kind;
    union {
        status_message_t status;
        sample_message_t sample;
        error_message_t error;
    } payload;
} message_t;
```

访问时先检查标签：

```
#include <stddef.h>

static int message_validate(const message_t *message)
{
    if (message == NULL) {
        return -1;
    }

    switch (message->kind) {
    case MESSAGE_KIND_STATUS:
        return 0;

    case MESSAGE_KIND_SAMPLE:
        return 0;

    case MESSAGE_KIND_ERROR:
        return 0;

    default:
        return -2;
    }
}
```

处理逻辑：

```
static int message_handle(const message_t *message)
{
    if (message_validate(message) != 0) {
        return -1;
    }

    switch (message->kind) {
    case MESSAGE_KIND_STATUS:
        /* 只访问 payload.status */
        return 0;

    case MESSAGE_KIND_SAMPLE:
        /* 只访问 payload.sample */
        return 0;

    case MESSAGE_KIND_ERROR:
        /* 只访问 payload.error */
        return 0;

    default:
        return -1;
    }
}
```

该模式建立了一个关键不变量：

```
kind == MESSAGE_KIND_SAMPLE
    => 当前有效成员是 payload.sample
```

需要保证所有构造和更新路径都维持这个不变量。不能只修改标签而忘记写入对应成员，也不能只写成员而留下旧标签。

### 5.5 安全构造和更新 API

将成员写入和标签更新封装起来，可减少不一致：

```
#include <stdint.h>

static int message_set_sample(message_t *message,
                              int32_t value,
                              uint16_t channel)
{
    if (message == NULL) {
        return -1;
    }

    message->payload.sample.value = value;
    message->payload.sample.channel = channel;

    /* 最后更新 tag，避免在构造中间态被观察到。 */
    message->kind = MESSAGE_KIND_SAMPLE;
    return 0;
}

static int message_set_error(message_t *message,
                             uint16_t code,
                             uint32_t detail)
{
    if (message == NULL) {
        return -1;
    }

    message->payload.error.code = code;
    message->payload.error.detail = detail;
    message->kind = MESSAGE_KIND_ERROR;
    return 0;
}
```

如果对象由多个任务或 ISR 并发访问，上述“最后写标签”仍然不足以保证原子切换。需要锁、临界区、双缓冲、消息队列或版本计数等同步机制。

### 5.6 有效成员与读取另一成员

常规安全规则是：

> **写入哪个成员，就读取哪个成员；需要解释其他编码时，使用明确的编码/解码方式。**

以下写法在一些编译器中常被用于观察浮点位模式：

```
union float_bits_t {
    float f;
    uint32_t u;
};

union float_bits_t value = { .f = 1.0f };
uint32_t bits = value.u;
```

这种 union type-punning 是实现敏感的用法。GCC/Clang 对其有特定支持规则，但可移植性需要查目标编译器文档，且仍需确认：

- `float` 和 `uint32_t` 大小是否相同；
- 浮点格式是否符合预期；
- 字节序和表示是否符合协议；
- 目标类型是否存在相应的有效位模式。

更通用的位模式复制方式：

```
#include <stdint.h>
#include <string.h>

static int float_to_bits(float input, uint32_t *output)
{
    if (output == NULL) {
        return -1;
    }

    if (sizeof(input) != sizeof(*output)) {
        return -2;
    }

    memcpy(output, &input, sizeof(*output));
    return 0;
}
```

`memcpy` 避免通过不兼容指针类型进行访问，但它不会让两个类型的表示自动相同。`sizeof` 相等也不代表浮点格式、NaN 编码或字节序相同。

### 5.7 `memcpy` 与 union type-punning 的区别

```
float f = 1.0f;
uint32_t u;

memcpy(&u, &f, sizeof(u));
```

与：

```
union {
    float f;
    uint32_t u;
} value;

value.f = 1.0f;
u = value.u;
```

两种方式的适用规则不同：

- `memcpy` 复制对象表示字节，不通过不兼容类型的左值访问源对象。
- union 读取另一个成员属于实现相关或由实现定义行为范畴，具体规则需看标准版本和实现。
- 两种方式都不解决端序问题。
- 两种方式都不能保证特定浮点表示。
- 对协议而言，仍应按明确的编码格式逐字段处理。

### 5.8 柔性数组、动态对象与联合体

联合体通常不能直接包含柔性数组成员作为普通变体成员；柔性数组成员只能出现在符合标准要求的结构体末尾。需要变长载荷时，常用固定最大载荷、单独指针或尾随字节区。

固定容量载荷：

```
enum {
    PAYLOAD_CAPACITY = 64U
};

typedef struct {
    uint16_t length;
    uint8_t data[PAYLOAD_CAPACITY];
} byte_payload_t;
```

动态载荷则应将指针和长度明确放在变体成员中：

```
typedef struct {
    uint8_t *data;
    size_t length;
} dynamic_payload_t;

typedef struct {
    unsigned kind;
    union {
        uint32_t scalar;
        dynamic_payload_t bytes;
    } value;
} dynamic_value_t;
```

此时必须另外定义：

- 当前联合体成员的标签；
- `data` 的所有权；
- 释放责任；
- 异步使用期限；
- 错误回滚行为；
- 是否允许 `data == NULL && length == 0`。

### 5.9 联合体与硬件寄存器

某些芯片定义或旧式驱动会用 union 表示寄存器的整体值和分字段视图：

```
typedef union {
    uint32_t word;
    struct {
        uint32_t enable : 1;
        uint32_t mode   : 2;
        uint32_t reserved : 29;
    } bits;
} control_register_t;
```

这种写法有较强的平台依赖：

- 位域分配顺序由实现决定；
- 位域存储单元大小和布局实现相关；
- 访问可能生成读改写；
- `volatile` 不提供原子性；
- 寄存器可能具有写一清零、读清零或写保护语义；
- 编译器可能使用与芯片期望不同的位序。

通常更稳健的方式是掩码操作：

```
#include <stdint.h>

#define CTRL_ENABLE_MASK (1UL << 0)
#define CTRL_MODE_MASK   (3UL << 1)

static uint32_t control_set_mode(uint32_t old_value, uint32_t mode)
{
    return (old_value & ~CTRL_MODE_MASK) |
           ((mode << 1) & CTRL_MODE_MASK);
}
```

但寄存器本身的访问方式必须以芯片手册为准。有些寄存器不能安全地读改写，应使用专用置位/清位寄存器。

### 5.10 内存池槽位和最大对齐

用联合体为不同类型提供共享槽位时，必须保证最大尺寸和最大对齐：

```
#include <stdint.h>

typedef union {
    uint8_t bytes[64];
    uint32_t words[16];
    double floating_value;
    void *pointer;
} storage_slot_t;
```

联合体通常会自然满足其成员中最大对齐要求。但若包含的类型还不足以覆盖某对象的对齐要求，不能认为槽位自动满足该对象对齐。

不要用普通 `uint8_t buffer[N]` 强行承载任意对象：

```
uint8_t buffer[64];
struct object_t *obj = (struct object_t *)buffer; /* 可能未对齐 */
```

应使用正确对齐的联合体、`_Alignas` 或实现提供的对齐分配器，并正确处理对象生命周期和有效类型。

## 6. 性能量化分析

### 6.1 量化口径

联合体自身通常不会增加访问层级；它主要影响：

- 对象大小；
- 对齐；
- 活动成员访问方式；
- 类型切换时的数据复制；
- 编译器可进行的优化；
- 并发和 Cache 行为。

以下示例假设：

- 32 位 MCU；
- `uint32_t` 4 字节、对齐 4；
- `uint8_t` 1 字节；
- 目标 ABI 使用常见自然对齐；
- 联合体成员不需要额外扩展对齐。

具体结果应由目标编译器实测。

### 6.2 内存占用公式

若联合体成员大小分别为：

```
S1, S2, ..., Sn
```

则联合体至少需要：

```
max(S1, S2, ..., Sn)
```

最终 `sizeof(union)` 还要考虑 ABI 对齐和整体尺寸规则。

带标签联合体：

```
struct {
    enum tag tag;
    union payload payload;
};
```

总大小约为：

```
align_up(sizeof(tag) + sizeof(union payload), struct_alignment)
```

这只是布局估算。成员间可能存在填充，枚举大小也依 ABI 或编译选项而定。

### 6.3 联合体相对结构体的节省

```
struct all_values_t {
    uint32_t integer;
    float real;
    uint8_t bytes[16];
};

union one_value_t {
    uint32_t integer;
    float real;
    uint8_t bytes[16];
};
```

若：

```
sizeof(uint32_t) = 4
sizeof(float) = 4
sizeof(bytes) = 16
```

常见情况下：

```
sizeof(struct all_values_t) ≈ 24 字节
sizeof(union one_value_t)   ≈ 16 字节
```

带标签后如果标签为 4 字节且整体按 4 字节对齐：

```
带标签联合体通常约 20 字节
```

若有 1000 个对象，比较 24 字节结构体和 20 字节带标签联合体：

```
1000 * (24 - 20) = 4000 字节
```

实际大小需在目标 ABI 上确认。

### 6.4 时间开销

- 读取当前活动成员通常与普通结构体成员访问类似。
- `switch(tag)` 会有分支成本；分支表或预测效果取决于编译器和目标。
- 切换活动成员可能需要初始化、清零、释放资源或复制载荷，这些往往比成员访问本身更贵。
- 使用 packed union 或把未对齐数据强转为 union 指针，可能引入额外访问成本或故障。
- 对多核共享的 union，锁、临界区和 Cache 同步往往是主要开销。

因此应分别测量：

1. 单次活动成员读取；
2. 带标签分发；
3. 成员切换；
4. 变体对象数组遍历；
5. 并发同步路径；
6. 目标存储区与 Cache 状态。

### 6.5 瓶颈和优化手段

|瓶颈|识别方式|优化手段|
|---|---|---|
|最大成员过大导致所有对象膨胀|`sizeof`、map 文件和实例数量|将大载荷移出 union，改为指针或外部池|
|标签分支热点|周期计数、性能剖析|按状态分组处理，避免每元素重复复杂分派|
|成员切换伴随大量清零|汇编和数据流分析|只初始化实际需要成员，确保无旧数据泄露|
|动态成员所有权复杂|静态分析、资源跟踪|统一构造/销毁 API，限制所有权转移|
|packed union 访问未对齐|汇编、异常和周期测量|解码到对齐内部对象|
|多核共享 union 状态竞争|并发压力测试|单一所有者、队列传递或双缓冲|

## 7. 应用场景选型指南

```
同一对象是否在不同状态下只需要保存一种数据？
|
+-- 否
|   +-- 使用 struct，各成员独立保存
|
+-- 是
    |
    +-- 使用者能否可靠知道当前变体？
    |   |
    |   +-- 否
    |   |   +-- 设计 tag + union
    |   |
    |   +-- 是
    |       +-- 裸 union 可用于严格局部、短生命周期场景
    |
    +-- 是否要和外部二进制格式逐字节一致？
        |
        +-- 是
        |   +-- 优先显式序列化/反序列化
        |   +-- 只有硬件规范要求时才使用 packed union
        |
        +-- 否
            +-- 自然对齐 union，检查大小和所有权
```

### 典型场景

|场景需求|推荐方案|原因|
|---|---|---|
|命令消息有多种互斥载荷|`enum + union`|标签明确，最大载荷共用存储|
|状态机不同状态保存不同上下文|带标签联合体|避免同时保留无关字段|
|临时解析多种数值类型|局部 union 或 `memcpy` 位模式|生命周期短，边界可控|
|网络协议格式|显式字节编码|不依赖本机 ABI 和端序|
|芯片寄存器整体与字段视图|芯片定义或掩码操作|必须匹配硬件和编译器规则|
|内存池复用不同对象类型|最大尺寸且正确对齐的 union|降低固定池槽位浪费|
|跨任务传输变体数据|带标签消息队列对象|明确状态和所有权|

## 8. 工程最佳实践

### 8.1 设计原则

- **可长期存活的变体对象通常使用 `tag + union`。**
- **标签与成员更新应封装在构造、切换和销毁函数中。**
- **用 `switch` 覆盖所有标签，并为非法标签提供明确错误路径。**
- **不要依赖联合体内部的旧字节内容。**
- **不需要共享存储时使用 `struct`，不要为了“灵活”滥用 union。**
- **协议数据应显式编码，避免直接发送联合体对象表示。**
- **联合体成员含指针时，明确谁拥有所指向对象。**
- **涉及并发时，把标签、载荷和同步视为一个整体状态。**
- **寄存器位域只有在芯片和编译器规范明确保证时才使用。**

### 8.2 选型决策矩阵

|需求|选择|关键校验|
|---|---|---|
|所有字段同时有效|`struct`|评估成员布局|
|多种互斥值之一|`tag + union`|tag 与成员一致|
|只在局部临时重解释表示|`memcpy` 或受控 union 技术|大小、表示和端序|
|外部协议载荷|字节数组 + 编解码函数|长度、端序、版本|
|最大内存槽位复用|union 槽位|最大尺寸和最大对齐|
|硬件寄存器映射|手册定义的结构和访问机制|编译器布局与访问代码|
|多核共享变体|单一所有者或同步封装|原子性、屏障、Cache|

### 8.3 工业级编码规范

```
typedef enum {
    VALUE_KIND_U32,
    VALUE_KIND_BYTES
} value_kind_t;

typedef struct {
    value_kind_t kind;
    union {
        uint32_t u32;
        struct {
            const uint8_t *data;
            size_t length;
        } bytes;
    } value;
} value_t;
```

- 标签名和成员名保持一一对应、语义明确。
- 变体构造函数应校验指针和长度。
- 更新函数先完成载荷写入，再提交标签；并发情况下还需同步。
- 若某成员拥有资源，销毁函数必须依据标签释放正确资源。
- 未知标签必须返回错误，不应默认解释成某个成员。
- 对外 ABI 中固定大小、偏移和对齐时，使用静态断言。
- 不以 `memset` 清零作为所有成员均被合法初始化的替代方案。
- 记录哪些联合体成员可以包含拥有型指针、借用指针或 DMA 地址。

## 9. 常见错误与避坑指南

### 错误一：写入一个成员后，无条件读取另一个成员

错误代码：

```
union value_t {
    uint32_t integer;
    float real;
};

union value_t value = {
    .integer = 0x3F800000U
};

float result = value.real;
```

根因：这种 type-punning 的可移植性和结果依赖实现、对象表示及浮点格式。

正确做法：若目的是浮点转换，使用数值转换：

```
uint32_t integer = 1U;
float result = (float)integer;
```

若目的是复制位模式，使用 `memcpy` 并验证大小和目标表示：

```
uint32_t bits = 0x3F800000U;
float result;

if (sizeof(result) == sizeof(bits)) {
    memcpy(&result, &bits, sizeof(result));
}
```

风险影响：编译器优化后行为变化，目标浮点格式或端序不同导致错误值。

### 错误二：带标签联合体的标签与活动成员不一致

错误代码：

```
message.payload.sample.value = 100;
message.kind = MESSAGE_KIND_ERROR;

/* 后续代码读取 payload.error */
```

根因：修改载荷和标签时没有维护状态不变量。

正确实现：通过一个封装函数更新：

```
static int message_set_sample(message_t *message,
                              int32_t value,
                              uint16_t channel)
{
    if (message == NULL) {
        return -1;
    }

    message->payload.sample.value = value;
    message->payload.sample.channel = channel;
    message->kind = MESSAGE_KIND_SAMPLE;
    return 0;
}
```

风险影响：读取错误成员，触发错误分支、资源错误释放或数据损坏。

### 错误三：用 union 内存镜像作为网络协议

错误代码：

```
send(socket_fd, &message, sizeof(message), 0);
```

根因：

- 联合体和结构体有 padding；
- 字节序依赖主机；
- 枚举宽度和表示可能不同；
- 变体标签与 payload 可能存在布局差异；
- 版本升级无法安全兼容。

正确实现：定义显式 wire format，逐字段编码并执行长度检查。

风险影响：跨平台互操作失败、版本兼容破坏、可能泄露填充字节。

### 错误四：对联合体的所有成员同时保留有效值

错误代码：

```
union measurement_t {
    uint32_t raw;
    float value;
};

union measurement_t measurement;
measurement.raw = 100U;
measurement.value = 23.5f;
/* 不能期待 raw 和 value 同时保存原先的值 */
```

根因：成员共享存储，第二次写入覆盖同一存储区域。

正确做法：若两个值都要同时保留，使用结构体：

```
struct measurement_t {
    uint32_t raw;
    float value;
};
```

风险影响：逻辑数据丢失，状态分析困难。

### 错误五：联合体中的指针没有所有权规则

错误代码：

```
union payload_t {
    uint8_t *buffer;
    uint32_t value;
};
```

之后无条件：

```
free(payload.buffer);
```

根因：无法知道当前成员是否是 `buffer`，也无法判断它是否由当前对象拥有。

正确做法：增加标签，并明确所有权：

```
typedef enum {
    PAYLOAD_VALUE,
    PAYLOAD_OWNED_BUFFER
} payload_kind_t;

typedef struct {
    payload_kind_t kind;
    union {
        uint32_t value;
        struct {
            uint8_t *data;
            size_t length;
        } buffer;
    } payload;
} payload_t;
```

销毁函数按 `kind` 释放，且只释放由对象拥有的资源。

风险影响：非法释放、重复释放、泄漏和悬空指针。

### 错误六：把任意字节缓冲区强转为 union 指针

错误代码：

```
uint8_t bytes[16];
union payload_t *payload = (union payload_t *)bytes;
```

根因：`bytes` 可能不满足 union 的对齐要求，缓冲区长度也未必够，且对象类型和有效类型规则可能不满足。

正确做法：先验证长度，再使用 `memcpy` 复制到正确类型的对齐对象，或通过字段解码函数解析。

风险影响：未对齐访问、越界读取、违反类型访问规则。

### 错误七：把 union 位域当作跨平台寄存器定义

错误代码：

```
union reg_t {
    uint32_t word;
    struct {
        uint32_t a : 1;
        uint32_t b : 3;
        uint32_t reserved : 28;
    } bits;
};
```

根因：位域顺序、分配方式和读改写行为实现相关。

正确做法：优先按芯片文档使用明确掩码和寄存器操作；若厂商 SDK 明确依赖此布局，锁定工具链并测试反汇编。

风险影响：字段映射错误、错误清除状态位、编译器升级后寄存器行为改变。

## 10. 多机制组合使用方案

### 10.1 带标签、容量约束和所有权清晰的消息载荷

下面的模式将：

- 枚举标签；
- 联合体；
- 固定容量数组；
- 明确长度；
- 构造和校验 API；

组合在一起，适用于不需要动态分配的消息系统。

```
#include <stddef.h>
#include <stdint.h>
#include <string.h>

enum {
    MESSAGE_TEXT_CAPACITY = 48U
};

typedef enum {
    APP_MESSAGE_SCALAR,
    APP_MESSAGE_TEXT
} app_message_kind_t;

typedef struct {
    app_message_kind_t kind;
    union {
        int32_t scalar;
        struct {
            uint8_t length;
            char data[MESSAGE_TEXT_CAPACITY];
        } text;
    } payload;
} app_message_t;

static int app_message_set_scalar(app_message_t *message,
                                  int32_t value)
{
    if (message == NULL) {
        return -1;
    }

    message->payload.scalar = value;
    message->kind = APP_MESSAGE_SCALAR;
    return 0;
}

static int app_message_set_text(app_message_t *message,
                                const char *text,
                                size_t length)
{
    if ((message == NULL) ||
        (text == NULL && length != 0U)) {
        return -1;
    }

    if (length > MESSAGE_TEXT_CAPACITY) {
        return -2;
    }

    if (length != 0U) {
        memcpy(message->payload.text.data, text, length);
    }

    message->payload.text.length = (uint8_t)length;
    message->kind = APP_MESSAGE_TEXT;
    return 0;
}

static int app_message_validate(const app_message_t *message)
{
    if (message == NULL) {
        return -1;
    }

    switch (message->kind) {
    case APP_MESSAGE_SCALAR:
        return 0;

    case APP_MESSAGE_TEXT:
        if (message->payload.text.length >
            MESSAGE_TEXT_CAPACITY) {
            return -2;
        }
        return 0;

    default:
        return -3;
    }
}
```

### 10.2 重要工程约束

- 该消息对象拥有自己的文本数组，不存在外部字符串生命周期问题。
- `length` 表示文本字节数，不隐含结尾 `'\0'`；若需要 C 字符串语义，应为终止符预留容量并定义编码。
- 标签更新函数应是对象唯一的变体切换入口。
- 如果消息要跨任务传递，应按值复制整个对象或通过队列传递所有权。
- 如果对象会被 ISR 和任务同时访问，应使用同步机制；单独 `volatile` 不够。
- 如果需要持久化或网络传输，仍要显式序列化，不能直接写出 `app_message_t` 的内存镜像。

## 11. 工业级实际案例分析

### 案例一：协议命令消息的变体载荷

#### 需求

一个控制协议支持查询、写参数和诊断三种消息。各类消息的载荷完全互斥，最大载荷大小不同，要求内存固定、无动态分配。

#### 架构设计

```
message_kind_t
      |
      +-- QUERY      -> query_payload
      +-- WRITE      -> write_payload
      +-- DIAGNOSTIC -> diagnostic_payload
```

定义带标签联合体，每个分支有固定宽度字段和显式长度。接收路径先验证外部帧长度，再解析标签和字段，最后构造内部消息对象。

#### 设计要点

- 外部字节流与内部 union 分离。
- 未知命令返回协议错误，不猜测成员。
- 所有变体的最大长度用编译期常量限制。
- 只有解析成功后才发布完整消息，避免消费者看到半构造对象。
- 消息队列传递完整对象时，确认对象大小与队列存储预算匹配。

### 案例二：驱动状态机的互斥上下文

#### 需求

传感器驱动在 `IDLE`、`CALIBRATING` 和 `STREAMING` 状态下保存不同数据。各状态上下文互斥，MCU RAM 受限。

#### 架构设计

```
typedef enum {
    SENSOR_IDLE,
    SENSOR_CALIBRATING,
    SENSOR_STREAMING
} sensor_state_t;

typedef struct {
    uint32_t requested_samples;
    uint32_t collected_samples;
} calibration_context_t;

typedef struct {
    uint16_t period_ms;
    uint8_t channel_mask;
} streaming_context_t;

typedef struct {
    sensor_state_t state;
    union {
        calibration_context_t calibration;
        streaming_context_t streaming;
    } context;
} sensor_driver_t;
```

状态迁移通过单一函数完成，函数负责停止旧状态硬件、释放旧状态资源、初始化新状态上下文，最后提交新状态。

#### 设计要点

- 状态字段本身是 union 标签。
- 迁移函数统一维护硬件状态和软件状态。
- 不在多个任务中直接改 `state` 或 `context`。
- 如果不同状态需要独立持久化，应使用独立结构体而非 union。
- 状态切换过程若可被中断观察，应增加临界区或状态迁移中间态。

### 案例三：内存池复用多类固定大小工作对象

#### 需求

系统有多种短生命周期任务对象，最大对象为 64 字节，不能使用堆，所有对象来自固定池。

#### 架构设计

用联合体定义槽位，保证尺寸和对齐至少覆盖所有工作对象。池的元数据单独存储，记录槽位当前类型和占用状态。

```
#include <stdint.h>

typedef struct {
    uint32_t address;
    uint16_t length;
    uint16_t flags;
} tx_job_t;

typedef struct {
    uint8_t source;
    uint8_t destination;
    uint8_t payload[32];
} parse_job_t;

typedef union {
    tx_job_t tx;
    parse_job_t parse;
    uint8_t raw[64];
    uint32_t alignment_member;
} job_storage_t;

typedef enum {
    JOB_SLOT_FREE,
    JOB_SLOT_TX,
    JOB_SLOT_PARSE
} job_kind_t;

typedef struct {
    job_kind_t kind;
    uint8_t in_use;
    job_storage_t storage;
} job_slot_t;
```

#### 设计要点

- `raw[64]` 确保存储容量至少 64 字节，但若某对象对齐大于 `uint32_t`，需要加入更严格对齐成员或使用 `_Alignas`。
- 每个槽位有标签，释放时只执行对应类型的清理逻辑。
- 分配和释放路径需要处理重复释放、错误类型释放和池耗尽。
- 如果槽位在任务间传递，需定义唯一所有者或使用队列保护。
- 固定池比每种对象分别静态分配更节省空间，但增加了状态管理复杂度。

## 12. 高频问题深度答疑

### 1. union 中同时能不能有多个成员有效？

从存储角度看，所有成员覆盖同一存储区域。写入某个成员后，不能假设其他成员仍保留先前的独立值。某些标准规则对共同初始序列、字符类型访问等有特殊规定，但一般业务代码应把 union 当成互斥成员使用。

### 2. union 会不会自动记录当前成员？

不会。编译器通常不会为普通 union 自动加入标签字段。标签必须由程序自己保存，通常使用 `enum` 与 union 放在同一个结构体里。

### 3. 为什么推荐 `enum + union`，而不是裸 union？

标签让程序能验证当前变体，并能在 `switch` 中明确处理每一种情况。裸 union 只适合标签已由其他严格上下文提供的局部场景；在模块边界、队列和长期对象中，裸 union 容易让调用方误读成员。

### 4. 读取非最后写入成员是否总是未定义行为？

不能用一句“永远未定义”概括所有 C 标准版本和编译器实现。C 对 union 成员重新解释有相关规则，结果可能依赖实现；编译器也可能文档化支持特定 type-punning。可移植工程不应依赖未记录行为。需要解释位模式时，使用受控的 `memcpy` 并验证表示假设。

### 5. union 是否适合做网络协议结构体？

通常不适合直接映射网络字节。union 可用于内部表示解析后的变体载荷，但网络输入应先按字节解析、验证长度和端序，再构造内部带标签联合体。

### 6. union 是否一定比 struct 节省内存？

若成员互斥，通常会节省；但还需加标签、对齐和尾部填充。若最大成员比其余成员大很多，整个对象都按最大成员大小分配；有时把大型数据改为独立池或指针会更省。但指针方案增加生命周期、碎片和所有权复杂度。

### 7. union 可以包含指针吗？

可以，但指针成员会引入所有权与生命周期问题。标签必须说明当前指针成员是否有效、是否拥有目标对象、何时释放、是否允许为空。销毁函数应按标签执行正确清理。

### 8. union 与 `void *` 哪个更适合变体数据？

若候选类型是有限且已知的，`enum + union` 更安全，因为类型集合显式、存储可以内嵌、无需外部分配。`void *` 适合通用回调或外部对象引用，但需要额外管理对齐、类型恢复和生命周期。

### 9. 对 union 做 `memset` 清零是否等价于初始化所有成员？

不是。`memset` 将对象表示字节设置为零，不保证每一种成员类型的零值表示都一定是全零位模式，也不意味着所有成员同时成为有效值。对整数和常见 MCU 类型通常可工作，但应依据类型和实现；更好的做法是使用指定初始化器或构造函数初始化当前成员。

### 10. 带标签联合体的状态切换是否可以无锁？

不能仅凭“标签最后写入”就认为无锁安全。其他线程可能同时读取标签和载荷，读到新标签但旧载荷，或读到旧标签但新载荷。需要互斥、原子发布协议、双缓冲、消息队列或版本序列锁，并确保内存顺序正确。

## 13. 课程核心总结

- **union 的成员共享存储，不能把它当作多个字段同时有效的结构体。**
- 联合体不记录活动成员；长期对象和模块接口优先使用 `tag + union`。
- 标签和活动成员必须由统一 API 维护一致。
- 联合体大小和对齐受 ABI 与实现影响；固定布局要用断言验证。
- union type-punning 的可移植性受标准和编译器规则影响；需要稳定解释位模式时优先用 `memcpy` 并明确表示假设。
- 协议、文件和持久化格式使用显式序列化，不直接发送或保存 union 对象内存。
- union 中的指针成员必须定义所有权、生命周期和释放规则。
- 硬件寄存器位域、packed union 和跨核共享需要按芯片与编译器文档单独审查。

### 通用选型结论

- 字段同时有效：使用 `struct`。
- 多个变体互斥：使用 `enum + union`。
- 外部字节格式：使用字节缓冲区和显式编解码。
- 内存池槽位：使用满足最大尺寸和最大对齐的 union，并用元数据记录当前类型。
- 寄存器访问：优先遵循芯片厂商接口和掩码操作，谨慎依赖位域布局。

## 14. 快速参考速查表

### 14.1 声明和大小

|声明|语义|
|---|---|
|`union value { int i; float f; };`|两个成员共享存储|
|`struct value { int i; float f; };`|两个成员独立存储|
|`sizeof(union T)`|至少能容纳最大成员，并满足实现对齐|
|`_Alignof(union T)`|联合体对象对齐要求|
|`offsetof(union T, member)`|联合体成员偏移检查工具；通常为 0，但依标准及实现约束处理|

### 14.2 使用规则

|场景|建议|
|---|---|
|写入并读取同一个成员|正常使用|
|表示多种互斥消息|`enum + union`|
|解释数值位模式|优先 `memcpy`，验证表示和大小|
|访问协议字段|显式字节解码|
|union 中保存指针|标签、所有权和析构路径必须明确|
|并发修改 tag 和 payload|用同步协议保护整体变体|
|寄存器映射|依据芯片手册、编译器规则和汇编验证|

### 14.3 带标签联合体模板

```
typedef enum {
    KIND_A,
    KIND_B
} kind_t;

typedef struct {
    kind_t kind;
    union {
        type_a_t a;
        type_b_t b;
    } value;
} variant_t;
```

访问规则：

```
先验证 kind
再访问对应 union 成员
未知 kind 走错误路径
```

## 16. 实践与进阶路径

### 16.1 梯度实战任务

1. **布局验证**：定义含 `uint8_t`、`uint32_t` 和数组成员的 union，用 `sizeof`、`_Alignof` 和断言验证目标布局。
2. **变体消息**：实现 4 种消息载荷的 `enum + union`，覆盖未知标签、构造失败和复制传递。
3. **资源型变体**：让一个成员持有动态内存，编写构造、替换、销毁函数，测试重复释放和失败回滚。
4. **协议编解码**：把带标签联合体编码为固定 wire format，再解码为内部对象；加入端序、长度和版本校验。
5. **位模式实验**：比较 union type-punning 与 `memcpy`，查看不同编译器和优化等级下的汇编与结果。
6. **内存池槽位**：实现静态对象池，union 存储不同类型对象，增加类型检查、占用状态和重复归还检测。
7. **并发状态切换**：用 RTOS 队列或临界区保护 tag 与 payload，做压力测试和竞态审查。

### 16.2 性能测试方法

- 固定编译器、目标 ABI、优化等级和 LTO 配置。
- 测量裸成员访问、标签分支、变体切换和 union 数组遍历。
- 比较 `struct` 全量存储、带标签 union 和指针变体三种方案的 RAM、代码大小和周期数。
- 在目标板上使用 DWT、PMU 或平台计时器，排除计时器开销和中断干扰。
- 查看反汇编，确认成员访问是否为自然宽度、是否发生字节拆分。
- 对多核或 DMA 场景同时测量同步、Cache 维护和总线竞争成本。
- 报告编译器版本、芯片型号、主频、存储区域、优化选项、对象数量和统计分布。

### 16.3 进阶学习方向

- C 标准中的 union 成员访问、对象表示和有效类型规则。
- 严格别名与编译器对 union type-punning 的扩展约定。
- 目标 ABI 中的 union 对齐、参数传递和返回规则。
- 位域布局、寄存器读改写及硬件副作用。
- tagged union、状态机和代数数据类型的 C 语言建模。
- 固定对象池、placement 生命周期管理和无堆架构。
- 跨核共享内存中的原子发布、内存屏障和 Cache 一致性。
- 网络协议与持久化数据的版本化序列化设计。
