
> 本课聚焦 C 预处理器中字符串化、记号拼接和可变参数宏的高级用法、标准差异与工程风险。示例以 **C11/C17** 为主要兼容基线，并单独标注 GNU 扩展和 C23 能力。  
> 宏在预处理阶段展开，不是函数调用；宏参数替换、重新扫描和记号拼接的规则决定了它的行为。理解这些规则，是安全使用宏的前提。

## 3. 技术概述

### 3.1 宏是什么

宏是预处理器根据指令对预处理记号执行替换的机制。它发生在 C 编译器进行语法和类型分析之前。

例如：

```
#define UART_BASE 0x40000000u
```

在预处理阶段，源文件中的 `UART_BASE` 会被替换为对应记号。它不是变量，也没有运行期存储空间或函数调用开销。

宏的主要价值包括：

- 条件编译和平台适配。
- 常量、属性、寄存器字段等编译期表达。
- 生成重复代码，如枚举、表、序列化映射。
- 构造日志、断言和测试辅助接口。
- 在不依赖 C++ 模板的 C 工程中进行有限的代码生成。

但宏没有类型系统、作用域语义和参数求值规则，错误往往在预处理输出或调用点才显现。

### 3.2 三个关键操作符

|操作符|名称|主要作用|典型用途|
|---|---|---|---|
|`#`|字符串化运算符|将宏形参对应的预处理记号转换成字符串字面量|断言输出表达式文本、生成配置名|
|`##`|记号拼接运算符|将左右相邻记号合并为一个预处理记号|拼接寄存器名、生成标识符、X-macro|
|`...` / `__VA_ARGS__`|可变参数宏|接收零个或多个额外参数|日志格式化、断言诊断、测试框架|

### 3.3 重要边界

- `#` 和 `##` 只对**宏替换列表中的形参**产生特殊作用，不能作为普通运行期字符串或运算符使用。
- 预处理器处理的是记号，不具备 C 类型系统。
- 宏参数可能被替换、展开多次；参数本身若含副作用表达式，可能导致重复求值。
- 宏不能替代函数、`static inline` 函数或类型安全抽象的所有用途。
- 宏中的 `#` 与 `##` 都不等同于运行期的字符串拼接或整数运算。

## 4. 核心特性横向对比

|特性|`#` 字符串化|`##` 记号拼接|C99/C11 可变参数|GNU `, ##__VA_ARGS__`|C23 `__VA_OPT__`|
|---|---|---|---|---|---|
|主要目的|生成字符串字面量|生成一个新记号|接收可变参数|在特定空参数情形下移除逗号|根据可变参数是否存在，条件性输出记号|
|标准属性|C 标准|C 标准|C99 起标准|GNU 扩展|C23 标准|
|参数预展开|字符串化参数自身不先展开|与 `##` 相邻的参数不先展开|进入替换列表后按规则展开|依赖扩展规则|按标准规则判断可变参数是否含预处理记号|
|空参数能力|可字符串化为空字符串|空参数与拼接行为需要特别处理|C99/C11 对省略可变参数有约束|可处理 GNU 特定场景|明确支持条件性输出|
|主要风险|字符串内容与直觉不一致|生成非法或非预期记号|调用形式与标准模式不兼容|可移植性差|老工具链不支持|
|推荐场景|诊断文本、静态标识|生成标识符、表格字段|通用格式参数接口|明确限定 GNU 工程|新标准项目中的可选尾参宏|

**推荐原则：** 跨工具链 C11/C17 项目优先避免依赖 GNU 逗号吞并扩展；能使用 C23 的项目优先考虑 `__VA_OPT__`，但必须通过目标编译器验证。

## 5. 底层原理与功能特性深度解析

### 5.1 宏展开的关键模型

对于函数式宏，工程上可以按以下简化模型理解：

1. 识别宏调用和实参边界。
2. 将实参绑定到形参。
3. 将实参替换进替换列表。
4. 对替换结果中的适用部分进行宏展开和重新扫描。
5. 处理字符串化 `#` 和拼接 `##` 的特殊规则。
6. 继续扫描替换结果中的宏名，但受宏展开抑制规则约束。

这个模型是理解行为的工具，不应将其机械化为“全局文本替换”。宏的行为基于预处理记号和标准规定的替换过程。

### 5.2 字符串化 `#`

#### 基础用法

```
#define STR_RAW(x) #x

const char *s = STR_RAW(hello);
```

展开结果：

```
const char *s = "hello";
```

字符串化时：

- 形参对应的原始记号序列被转换为字符串字面量。
- 参数内部的连续空白会规整成单个空格。
- 字符串字面量内部的 `"` 和 `\` 会按规则进行转义。
- 参数不会先按普通宏替换规则展开。

#### 先展开再字符串化

若需要先展开参数，再得到展开后的文本，使用两层宏：

```
#define STR_RAW(x) #x
#define STR_EXPAND(x) STR_RAW(x)

#define CHIP_REV B

const char *raw = STR_RAW(CHIP_REV);
const char *expanded = STR_EXPAND(CHIP_REV);
```

概念结果：

```
const char *raw = "CHIP_REV";
const char *expanded = "B";
```

第一层 `STR_EXPAND` 的实参会先按普通规则展开，然后传给 `STR_RAW`；`STR_RAW` 才执行字符串化。

#### 工程示例：断言表达式文本

```
#include <stdio.h>
#include <stdlib.h>

#define APP_ASSERT(expr)                                                   \
    do {                                                                   \
        if (!(expr)) {                                                     \
            (void)fprintf(stderr,                                          \
                           "assertion failed: %s (%s:%d)\n",               \
                           #expr, __FILE__, __LINE__);                     \
            abort();                                                       \
        }                                                                  \
    } while (0)
```

使用：

```
APP_ASSERT(queue_count <= queue_capacity);
```

失败信息可包含：

```
assertion failed: queue_count <= queue_capacity (queue.c:123)
```

注意：这里 `expr` 在运行期只出现一次，避免了常见的重复求值问题。实际产品中，是否调用 `fprintf`、`abort` 应按故障处理策略替换为安全日志、故障记录或复位路径。

### 5.3 记号拼接 `##`

#### 基础用法

```
#define REG_NAME(prefix, index) prefix##index

#define UART_REG(index) REG_NAME(UART, index)

UART_REG(3)
```

如果 `UART_REG(3)` 先把 `UART` 和 `3` 传入 `REG_NAME`，则拼接生成：

```
UART3
```

若不需要先展开参数，可以直接使用 `##`。但当参数是另一个宏名时，结果常常不符合预期。

#### `##` 抑制相邻参数的预展开

```
#define CAT_RAW(a, b) a##b
#define CAT(a, b) CAT_RAW(a, b)

#define PORT 2

CAT_RAW(UART, PORT)
CAT(UART, PORT)
```

概念结果：

```
UARTPORT
UART2
```

原因：

- `CAT_RAW` 中，`a` 和 `b` 都与 `##` 相邻，直接参与拼接，不先展开 `PORT`。
- `CAT` 中的参数在传给内层 `CAT_RAW` 前，先经历普通宏展开，所以 `PORT` 变为 `2`。

**常用两层拼接模板：**

```
#define PP_CAT_RAW(a, b) a##b
#define PP_CAT(a, b) PP_CAT_RAW(a, b)
```

#### 拼接结果必须是合法预处理记号

下列拼接只有在拼接结果能构成单个合法预处理记号时才有意义：

```
#define MAKE_FIELD(type, field) type##_##field

MAKE_FIELD(uart, status)
```

结果为：

```
uart_status
```

不要把 `##` 当作任意字符串拼接。它不能可靠地合并任意文本，也不能用于运行期数据。

### 5.4 可变参数宏

#### C99/C11/C17 常规形式

```
#define LOGF(level, fmt, ...) \
    log_write((level), (fmt), __VA_ARGS__)
```

调用时通常必须给出至少一个可变参数：

```
LOGF(LOG_LEVEL_INFO, "rx=%u", rx_count);
```

调用：

```
LOGF(LOG_LEVEL_INFO, "ready");
```

会在固定参数后没有可变参数。对于传统 C99/C11/C17 写法，这会导致实参列表不符合相应约束或触发严格模式诊断；不要假定所有编译器都会以相同方式接受。

#### GNU `, ##__VA_ARGS__` 扩展

```
#define LOGF_GNU(fmt, ...) \
    log_write((fmt), ##__VA_ARGS__)
```

在 GNU 方言中，当可变参数被省略时，编译器可移除逗号，从而允许：

```
LOGF_GNU("ready");
LOGF_GNU("rx=%u", rx_count);
```

这是 **GNU 扩展**，不是可移植的 C11/C17 写法。不同编译器、标准模式与兼容选项下行为可能不同。必须将此类用法明确标记为工具链依赖。

#### C23 `__VA_OPT__`

C23 引入 `__VA_OPT__(tokens)`：可变参数存在时输出其中记号；为空时不输出。

```
#define LOGF_C23(fmt, ...) \
    log_write((fmt) __VA_OPT__(,) __VA_ARGS__)
```

当可变参数非空时，概念展开为：

```
log_write((fmt), arg1, arg2)
```

当可变参数为空时，概念展开为：

```
log_write((fmt))
```

该能力依赖支持 C23 的编译器。还需要注意：预处理器标准模式、编译器版本和告警策略会共同影响实际可用性。

### 5.5 工程可复用代码：可移植日志接口

对于 C11/C17，为避免空可变参数的逗号问题，可以将格式串也放入可变部分：

```
#include <stdarg.h>
#include <stdio.h>

typedef enum {
    LOG_LEVEL_ERROR = 0,
    LOG_LEVEL_WARN  = 1,
    LOG_LEVEL_INFO  = 2,
    LOG_LEVEL_DEBUG = 3
} log_level_t;

static void log_vwrite(log_level_t level,
                       const char *file,
                       int line,
                       const char *fmt,
                       va_list ap)
{
    static const char *const names[] = {
        "ERROR", "WARN", "INFO", "DEBUG"
    };

    if ((unsigned)level >= (sizeof(names) / sizeof(names[0])) ||
        file == NULL ||
        fmt == NULL) {
        return;
    }

    (void)fprintf(stderr, "[%s] %s:%d: ",
                  names[level], file, line);
    (void)vfprintf(stderr, fmt, ap);
    (void)fputc('\n', stderr);
}

static void log_write(log_level_t level,
                      const char *file,
                      int line,
                      const char *fmt,
                      ...)
{
    va_list ap;

    if (fmt == NULL) {
        return;
    }

    va_start(ap, fmt);
    log_vwrite(level, file, line, fmt, ap);
    va_end(ap);
}

/* C99 起：所有格式参数都位于可变参数部分，不需要逗号吞并扩展。 */
#define LOG_INFO(...) \
    log_write(LOG_LEVEL_INFO, __FILE__, __LINE__, __VA_ARGS__)

#define LOG_ERROR(...) \
    log_write(LOG_LEVEL_ERROR, __FILE__, __LINE__, __VA_ARGS__)
```

调用：

```
LOG_INFO("system ready");
LOG_INFO("rx=%u, err=%d", rx_count, error_code);
```

工程注意事项：

- `va_list` 必须通过 `va_start` 初始化，并通过 `va_end` 清理。
- 不能把格式串和参数类型不匹配当作宏能解决的问题；启用编译器格式化属性可增强检查。
- `stdio` 可能不适合中断上下文或硬实时任务，应替换为经过设计的异步日志队列。
- 日志后端应定义并发、缓冲区溢出、阻塞、丢弃策略与故障行为。
- 不应在 ISR 中调用可能阻塞或不可重入的格式化接口。

### 5.6 X-macro：一份定义，多处生成

```
#define SENSOR_TABLE(X)                        \
    X(TEMP,  "temperature",  0x01u)             \
    X(PRESS, "pressure",     0x02u)             \
    X(HUM,   "humidity",     0x03u)

typedef enum {
#define SENSOR_ENUM(name, text, id) SENSOR_##name = (id),
    SENSOR_TABLE(SENSOR_ENUM)
#undef SENSOR_ENUM
} sensor_id_t;

static const char *const sensor_names[] = {
#define SENSOR_NAME(name, text, id) [id] = (text),
    SENSOR_TABLE(SENSOR_NAME)
#undef SENSOR_NAME
};
```

价值：

- 枚举、字符串表、协议映射等信息可以保持单一来源。
- 避免手工维护多份重复清单。

风险与约束：

- 定义表要有稳定的参数顺序和清晰命名。
- 展开产生的数组下标必须合法、无重复。
- 宏生成的代码仍然要经过编译器类型检查和单元测试。
- 复杂 X-macro 会增加阅读和调试成本，应限制其使用范围。

## 6. 性能量化分析

### 6.1 运行期成本

`#`、`##` 和可变参数宏本身都在预处理阶段处理。它们不会在运行期生成“宏调用开销”。

但宏展开出的代码会像普通 C 代码一样参与优化，因此运行期成本取决于展开结果，而不是宏的语法形式。

|项目|运行期成本|说明|
|---|---|---|
|单纯 `#` 生成字符串字面量|通常 0 次运行期计算|字符串字面量可能占用只读存储空间|
|`##` 生成标识符|0 次运行期计算|仅影响编译期名称|
|`LOG_INFO(...)` 展开成函数调用|与被调用函数相同|宏自身不额外产生函数调用|
|被编译期删除的日志宏|通常无调用指令|仍可能增加预处理/编译工作|
|展开成重复表达式的宏|可能产生多次运行期计算|例如宏形参在替换列表中出现多次|

### 6.2 可量化公式

宏机制的运行期成本可以按最终生成代码估算：

```
宏运行期成本 = 宏展开后的 C 语句所生成的机器码成本
```

若形参在展开代码中使用 `k` 次，表达式的副作用可能被执行 `k` 次：

```
#define SQUARE(x) ((x) * (x))

int y = SQUARE(read_counter());
```

`read_counter()` 可能被调用两次。这里的代价不是预处理器计算，而是展开后的两个函数调用。

日志接口若保留格式化调用：

```
单次日志成本 ≈ 门控判断 + 参数准备 + 格式化成本 + 后端提交成本
```

异步日志中的总响应时间还包含：

```
写入响应时间 = 生产者侧格式化/入队时间 + 队列等待时间 + 后端发送时间
```

### 6.3 实测数据与可复现基准

宏替换属于编译期行为，不能给出脱离处理器、编译器版本、优化选项和后端实现的通用运行期“实测数据”。下面给出可复现实测设计，而不虚构平台数据。

**测试平台记录项：**

- MCU 型号、时钟频率、Flash wait state、缓存配置。
- 编译器名称与版本、目标架构、标准模式。
- 编译选项：优化级别、LTO、调试信息、链接脚本。
- 日志后端：轮询 UART、DMA、RTOS 队列或主机仿真。
- 测量方法：DWT 周期计数器、GPIO 示波器测量或 CPU 性能计数器。

**建议测试组：**

1. 无日志代码基线。
2. 日志宏编译期关闭。
3. 日志宏打开但运行期级别过滤。
4. 只入队、不格式化。
5. 任务上下文完整格式化并输出。
6. ISR 中执行日志路径的负向测试，验证是否被禁止。

**测量指标：**

- 代码尺寸：链接 map 中 `.text`、`.rodata`、日志缓冲区大小。
- 单次调用周期：读取 DWT 前后计数差，重复多次取中位数和高分位数。
- 栈峰值：编译器栈使用报告、栈填充扫描或 RTOS 高水位统计。
- 日志丢失率：发送计数与实际输出计数对比。
- 实时干扰：日志开启前后任务响应时间与截止期违约数。

### 6.4 瓶颈与优化收益

常见瓶颈通常不在宏本身，而在：

- `printf` 类格式化的 CPU 时间和栈使用。
- 串口发送带宽、同步等待和临界区占用。
- 多线程共享日志后端导致的锁竞争。
- 日志字符串与格式化库带来的 Flash 占用。
- 编译期宏展开过度导致的编译时间、诊断可读性和调试体验下降。

优化手段：

- 在预处理阶段关闭不需要的日志级别。
- 采用 ISR 安全的定长事件记录，延迟到任务上下文格式化。
- 给日志队列制定明确的满队列策略：丢弃低优先级、覆盖最旧项或计数告警。
- 使用限长格式化缓冲区，并处理截断。
- 用编译器的格式化检查属性检查格式与参数类型。
- 用构建产物与目标测量确认收益，不根据源代码行数判断成本。

## 7. 应用场景选型指南

### 7.1 纯文本决策流程图

```
需要在编译期生成名称或文本吗？
├─ 需要生成诊断字符串
│  ├─ 只需当前参数的字面记号 → 使用单层 #x
│  └─ 需先展开宏再生成字符串 → 使用 STR_RAW / STR 两层宏
├─ 需要生成标识符
│  ├─ 输入参数本身是字面记号 → 可直接 ##，但先验证拼接结果
│  └─ 输入参数需要先展开 → 使用 CAT_RAW / CAT 两层宏
└─ 需要接收可变参数
   ├─ 可将格式串纳入 ... → C99/C11/C17 通用接口，优先采用
   ├─ 项目已启用 C23 且工具链确认支持 → 使用 __VA_OPT__
   └─ 必须支持 GNU 特定调用形式 → 可使用 , ##__VA_ARGS__，并标记扩展依赖
```

### 7.2 典型场景

|场景|需求|方案|理由|
|---|---|---|---|
|断言诊断|输出失败表达式|`#expr`|直接保留调用端表达式文本|
|寄存器/字段名生成|形成编译期标识符|两层 `CAT`|处理形参宏展开顺序|
|兼容 C11 的日志接口|格式串可独立使用|`LOG(...)`，将格式串放入 `...`|避免空尾参逗号兼容问题|
|C23 日志接口|固定参数后允许空尾参|`__VA_OPT__(,)`|标准化条件性输出|
|固件协议映射|多处重复维护同一清单|X-macro|单一数据源生成枚举与映射|
|高实时 ISR 事件记录|低延迟记录事件|固定长度结构体入队|宏只负责接口糖，后端保证实时性|

## 8. 工程最佳实践

### 8.1 设计原则

1. **能用函数表达的运行期逻辑，优先用函数或 `static inline`。**
2. 宏参数在替换列表中出现多次时，要确认没有副作用；必要时改成函数。
3. 多语句宏使用 `do { ... } while (0)`，并确保调用者以分号结束。
4. 表达式宏整体加括号，参数也要适当加括号。
5. `#` 与 `##` 需要预展开时，使用明确命名的两层包装宏。
6. GNU 扩展要在项目编码规范中登记，并通过编译选项和 CI 固定工具链行为。
7. 日志宏应明确线程安全、ISR 使用限制、缓冲区大小和满队列策略。
8. 宏的命名宜体现用途和范围，如 `PP_CAT`、`LOG_ERROR`、`CONFIG_ASSERT`。
9. 对复杂宏保留展开样例，避免后续修改造成静默语义变化。
10. 宏参数不要包含带逗号的复合表达式，除非调用方式显式分组且能通过预处理器边界规则。

### 8.2 选型决策矩阵

|方案|可移植性|类型安全|调试性|代码生成能力|适用结论|
|---|---|---|---|---|---|
|普通函数|高|高|高|低|默认选择|
|`static inline`|高|高|高|低|小型热路径和头文件接口|
|对象式宏|高|低|中|低|编译期常量、条件配置|
|`#` / `##` 宏|中高|低|中低|高|字符串化、标识符生成|
|C99 可变参数宏|高（支持 C99 以上）|低|中|中|可移植日志/断言包装|
|GNU 逗号吞并扩展|低|低|中低|中|工具链明确固定的 GNU 工程|
|C23 `__VA_OPT__`|取决于 C23 工具链支持|低|中|中|新标准项目|

### 8.3 工业级编码规范建议

- 严格模式编译，并把非标准扩展告警纳入 CI。
- 至少对宏头文件运行预处理回归测试。
- 对宏参数包含 `++`、函数调用、volatile 读取、I/O 访问等表达式开展副作用审查。
- 为宏定义编写最小化正向和负向测试。
- 对日志宏和断言宏建立特殊规则：ISR 中禁止调用、敏感数据禁止输出、格式字符串不可来自不可信输入。
- 对生成标识符的宏验证所有输入组合是否形成合法且唯一的名称。

## 9. 常见错误与避坑指南

### 错误一：字符串化时误以为参数先展开

错误代码：

```
#define STR(x) #x
#define MODE fast

const char *p = STR(MODE);
```

根因：

- `#` 直接处理形参对应的原始记号；不先将 `MODE` 展开。

正确实现：

```
#define STR_RAW(x) #x
#define STR(x) STR_RAW(x)

#define MODE fast

const char *p = STR(MODE);  /* "fast" */
```

风险影响：

- 配置标签、诊断文本与预期不一致。
- 可能导致生成字符串无法匹配协议或测试脚本。

---

### 错误二：拼接时误以为参数先展开

错误代码：

```
#define CAT(a, b) a##b
#define INDEX 4

int value = register_INDEX;
```

若试图通过 `CAT(register_, INDEX)` 生成 `register_4`，直接拼接不会按直觉先展开 `INDEX`。

正确实现：

```
#define CAT_RAW(a, b) a##b
#define CAT(a, b) CAT_RAW(a, b)

#define INDEX 4
#define REG_NAME(i) CAT(register_, i)

int value = REG_NAME(INDEX);  /* register_4 */
```

根因与风险：

- `##` 相邻形参不先进行普通宏展开。
- 结果可能生成不存在的标识符或无效记号，导致编译失败。

---

### 错误三：用 GNU 扩展却宣称标准 C11 可移植

错误代码：

```
#define LOG(fmt, ...) printf((fmt), ##__VA_ARGS__)
```

根因：

- `, ##__VA_ARGS__` 的逗号吞并行为属于 GNU 扩展，不应当作为 C11/C17 的通用保证。

正确实现：C99/C11/C17 通用接口

```
#define LOG(...) log_write(__FILE__, __LINE__, __VA_ARGS__)

LOG("boot");
LOG("value=%u", value);
```

风险影响：

- 在严格标准模式、不同编译器或不同扩展选项下报错或行为不一致。
- 构建环境升级后出现回归。

---

### 错误四：宏参数被重复求值

错误代码：

```
#define MIN(a, b) ((a) < (b) ? (a) : (b))

int result = MIN(read_sensor(), fallback_value);
```

根因：

- `a` 可能在比较和条件结果处被求值多次。

正确实现：

```
static inline int min_int(int a, int b)
{
    return (a < b) ? a : b;
}

int result = min_int(read_sensor(), fallback_value);
```

风险影响：

- 重复读取硬件寄存器、重复执行函数、重复自增或产生不一致结果。
- 在 MMIO 场景中，重复读取可能具有副作用。

---

### 错误五：多语句宏破坏调用点语法

错误代码：

```
#define UPDATE_AND_CLEAR(x) \
    x = 1;                  \
    x = 0

if (ready)
    UPDATE_AND_CLEAR(flag);
else
    recover();
```

根因：

- 宏展开后多个语句不再构成一个语法单元，`else` 可能无法匹配预期 `if`。

正确实现：

```
#define UPDATE_AND_CLEAR(x) \
    do {                    \
        (x) = 1;            \
        (x) = 0;            \
    } while (0)
```

风险影响：

- 编译错误，或更危险的控制流与审阅者理解不一致。

---

### 错误六：拼接得到非法记号

错误代码：

```
#define BAD_JOIN(a, b) a##b

int x = BAD_JOIN(12, abc);
```

根因：

- 拼接结果未必是合法的单个预处理记号。
- `##` 不是任意字符连接器。

正确做法：

- 将拼接输入约束为可形成合法标识符或合法记号的组件。
- 对所有实际参数组合运行预处理测试。
- 若目标是生成字符串，使用字符串化机制，而不是 `##`。

风险影响：

- 编译器诊断不直观，跨工具链行为差异增大。

---

## 10. 多机制组合使用方案

### 10.1 架构目标

组合使用：

- 编译期级别过滤。
- `__FILE__`、`__LINE__` 元信息。
- 可变参数格式接口。
- 运行期安全的日志后端。
- 明确的 ISR 使用策略。

### 10.2 C11/C17 代码框架

```
#include <stdarg.h>
#include <stddef.h>
#include <stdio.h>

typedef enum {
    LOG_LVL_ERROR = 0,
    LOG_LVL_WARN  = 1,
    LOG_LVL_INFO  = 2,
    LOG_LVL_DEBUG = 3
} log_level_t;

/*
 * 生产项目应将后端替换为固定大小队列、DMA 或专用日志任务。
 * 该示例仅演示宏接口与 va_list 的正确边界。
 */
static void log_backend(log_level_t level,
                        const char *file,
                        int line,
                        const char *fmt,
                        va_list ap)
{
    static const char *const level_name[] = {
        "ERROR", "WARN", "INFO", "DEBUG"
    };

    if ((unsigned)level >=
        (sizeof(level_name) / sizeof(level_name[0])) ||
        file == NULL ||
        fmt == NULL) {
        return;
    }

    (void)fprintf(stderr, "[%s] %s:%d: ",
                  level_name[level], file, line);
    (void)vfprintf(stderr, fmt, ap);
    (void)fputc('\n', stderr);
}

static void log_emit(log_level_t level,
                     const char *file,
                     int line,
                     const char *fmt,
                     ...)
{
    va_list ap;

    if (fmt == NULL) {
        return;
    }

    va_start(ap, fmt);
    log_backend(level, file, line, fmt, ap);
    va_end(ap);
}

#ifndef APP_LOG_COMPILED_LEVEL
#define APP_LOG_COMPILED_LEVEL LOG_LVL_INFO
#endif

#define APP_LOG_ERROR(...)                                             \
    do {                                                               \
        if (APP_LOG_COMPILED_LEVEL >= LOG_LVL_ERROR) {                 \
            log_emit(LOG_LVL_ERROR, __FILE__, __LINE__, __VA_ARGS__); \
        }                                                              \
    } while (0)

#define APP_LOG_WARN(...)                                              \
    do {                                                               \
        if (APP_LOG_COMPILED_LEVEL >= LOG_LVL_WARN) {                  \
            log_emit(LOG_LVL_WARN, __FILE__, __LINE__, __VA_ARGS__);  \
        }                                                              \
    } while (0)

#define APP_LOG_INFO(...)                                              \
    do {                                                               \
        if (APP_LOG_COMPILED_LEVEL >= LOG_LVL_INFO) {                  \
            log_emit(LOG_LVL_INFO, __FILE__, __LINE__, __VA_ARGS__);  \
        }                                                              \
    } while (0)

#define APP_LOG_DEBUG(...)                                             \
    do {                                                               \
        if (APP_LOG_COMPILED_LEVEL >= LOG_LVL_DEBUG) {                 \
            log_emit(LOG_LVL_DEBUG, __FILE__, __LINE__, __VA_ARGS__); \
        }                                                              \
    } while (0)
```

注意：

- `APP_LOG_COMPILED_LEVEL` 的预处理器比较必须是整型常量表达式；实际使用时建议统一管理级别宏。
- 示例后端使用 `stdio`，不代表它适用于生产 MCU 的中断上下文。
- 若要让关闭级别的宏完全不生成调用，建议用 `#if` 进行条件编译，而不是仅依赖优化器删除常量分支。
- 若参数表达式本身有副作用，被编译期删除后其副作用也会消失。因此日志参数应避免承担程序状态更新。

### 10.3 组合设计模式

```
调用点
  ↓
日志宏：提供级别、文件、行号和可变参数
  ↓
编译期门控：删除不需要的日志级别
  ↓
轻量记录接口：ISR 只写固定长度事件（若系统允许）
  ↓
任务上下文格式化：消费队列记录
  ↓
后端：UART DMA / RTT / 文件 / 网络传输
```

宏负责接口便利性，不负责线程安全、队列容量、实时性或丢包语义；这些必须由后端架构保证。

## 11. 工业级实际案例分析

### 案例一：多型号 MCU 寄存器名映射

#### 需求

- 同一驱动适配多个 SoC 型号。
- 不同型号存在寄存器实例名差异。
- 希望编译期生成目标寄存器标识符，避免运行期查表。

#### 架构设计

- 用平台配置选择 SoC 实例编号。
- 用两层 `CAT` 让配置宏先展开。
- 驱动代码只依赖统一的寄存器访问包装函数。
- 通过每个目标配置的独立编译测试验证生成标识符存在。

#### 核心代码

```
#define PP_CAT_RAW(a, b) a##b
#define PP_CAT(a, b) PP_CAT_RAW(a, b)

#define SOC_UART_INSTANCE 2
#define SOC_UART_REG(name) \
    PP_CAT(UART, PP_CAT(SOC_UART_INSTANCE, _##name))

/*
 * 复杂嵌套拼接在不同编译器上更难维护。
 * 实际项目通常拆成两个明确阶段或由平台头文件提供显式映射。
 */
```

更推荐显式映射，降低预处理器复杂度：

```
#define SOC_UART_BASE UART2_BASE
#define SOC_UART_STATUS_REG UART2_STATUS_REG

static inline unsigned int soc_uart_read_status(void)
{
    return *SOC_UART_STATUS_REG;
}
```

#### 设计要点

- 若映射关系少且型号有限，显式配置宏通常比复杂拼接更可靠。
- 拼接只在确实需要从规律化命名空间生成符号时使用。
- CI 应分别构建每种型号，防止某一型号的符号拼接遗漏。

---

### 案例二：协议字段清单生成枚举、字符串和校验表

#### 需求

- 协议字段同时需要枚举值、字段名称和校验属性。
- 多处复制清单容易出现编号错位。
- 工程使用 C11，需保证工具链可移植。

#### 架构设计

- 通过 X-macro 维护单一字段清单。
- 每个生成目标定义一个展开宏。
- 字段编号固定，明确检查范围与重复项。
- 对生成结果做单元测试和静态断言。

#### 核心代码

```
#define PROTOCOL_FIELDS(X)                                      \
    X(MSG_ID,      0x01u, 1u)                                    \
    X(PAYLOAD_LEN, 0x02u, 2u)                                    \
    X(CHECKSUM,    0x03u, 2u)

typedef enum {
#define FIELD_ENUM(name, id, width) FIELD_##name = (id),
    PROTOCOL_FIELDS(FIELD_ENUM)
#undef FIELD_ENUM
} protocol_field_id_t;

typedef struct {
    protocol_field_id_t id;
    unsigned int width;
    const char *name;
} protocol_field_desc_t;

static const protocol_field_desc_t protocol_fields[] = {
#define FIELD_DESC(name, id, width) \
    { FIELD_##name, (width), #name },
    PROTOCOL_FIELDS(FIELD_DESC)
#undef FIELD_DESC
};
```

#### 设计要点

- `#name` 生成字段标识字符串，不应依赖运行期字符串拼接。
- 表中字段宽度、编号必须做边界和重复检查。
- X-macro 应保持简单、参数语义明确；过度嵌套会让故障定位困难。

---

### 案例三：嵌入式系统日志级别与实时性隔离

#### 需求

- 正常版本关闭 DEBUG 日志。
- ERROR/WARN 保留。
- ISR 中不允许调用阻塞式格式化。
- 任务上下文支持格式化日志。

#### 架构设计

- 用编译期宏过滤不必要级别。
- 任务上下文日志允许格式化后提交队列。
- ISR 仅记录固定大小事件码和少量参数，且必须验证队列操作的 ISR 安全性。
- 后端任务统一输出，定义队列满策略、最大等待时间和丢弃计数。

#### 核心接口示意

```
typedef struct {
    unsigned int event_id;
    unsigned int arg0;
    unsigned int timestamp;
} isr_event_t;

/* 由 RTOS/平台层实现，必须明确 ISR 安全及失败语义。 */
extern int event_queue_send_from_isr(const isr_event_t *event);

#define ISR_EVENT(event, a0, ts)             \
    do {                                     \
        const isr_event_t e_ = {              \
            (unsigned int)(event),            \
            (unsigned int)(a0),                \
            (unsigned int)(ts)                \
        };                                   \
        (void)event_queue_send_from_isr(&e_); \
    } while (0)
```

#### 设计要点

- 不应在 ISR 宏里调用 `printf`、动态内存分配或可能阻塞的锁。
- 需要确认 `event_queue_send_from_isr` 的队列满处理、内存屏障和中断优先级约束。
- 事件参数转换为固定宽度类型前，应审查有符号转换、范围截断和 ABI。
- 宏只提供语法便利，实时性来自队列实现和系统调度设计。

## 12. 高频问题深度答疑

### 问题 1：`#` 为什么不自动展开参数？

因为字符串化需要保留调用点传入的记号表示。若直接先展开，原始宏名信息就不可见。标准提供两层宏模式，使调用者显式选择“保留原始形式”或“先展开再字符串化”。

### 问题 2：为什么 `##` 两侧参数不先展开？

`##` 的语义是把相邻记号组成一个新记号。如果先展开，拼接的输入边界和结果可能变化，因此标准规定与 `##` 相邻的形参有特殊处理。需要先展开时，用外层宏接收并展开参数，再交给内层拼接宏。

### 问题 3：可变参数宏为什么经常出现逗号问题？

逗号是预处理器识别宏调用实参分隔符的重要记号。固定参数后若省略 `...`，替换列表中的逗号仍可能保留，造成语法错误。GNU 扩展以非标准方式吞掉特定逗号；C23 的 `__VA_OPT__` 则提供标准化的条件输出机制。

### 问题 4：C11/C17 项目如何安全支持“只传格式串”的日志调用？

把格式串也放入可变参数部分：

```
#define LOG(...) log_write(__FILE__, __LINE__, __VA_ARGS__)
```

这样调用 `LOG("ready")` 时，可变部分并非省略，而是包含一个格式串参数，不需要处理固定参数后的空尾参逗号。

### 问题 5：宏能否替代函数以获得更高性能？

不能仅凭“宏没有函数调用”就得出更快结论。优化器通常能内联小函数；宏可能造成重复求值、代码膨胀和更差的调试能力。应比较最终汇编、代码尺寸、执行周期和栈用量。默认优先考虑类型安全的 `static inline` 函数。

### 问题 6：日志宏关闭后，调用参数还会不会求值？

若使用 `#if` 在预处理阶段删除整段代码，参数不会进入编译单元，因此不会被求值。若宏展开成 `if (0) { log(...); }`，通常会由优化器删除，但不应依赖未优化构建的行为；某些副作用表达式还会引起误解。日志参数不应承担业务副作用。

## 13. 课程核心总结

### 核心要点

- `#` 用于字符串化；直接字符串化时，参数不会按普通规则预展开。
- `##` 用于记号拼接；与其相邻的参数不会先普通展开。
- 两层宏是解决“先展开，再字符串化/拼接”的标准工程模式。
- `...` 与 `__VA_ARGS__` 可用于可变参数宏；空尾参处理必须考虑标准版本。
- `, ##__VA_ARGS__` 是 GNU 扩展；C23 的 `__VA_OPT__` 是标准方案。
- 宏不具备类型安全和函数式参数求值语义，必须防止重复求值和语法结构破坏。
- 性能应看展开后的代码，而不是根据宏或函数的名称进行判断。

### 性能排序结论

不存在适用于所有平台的“宏一定比函数快”的排序。对同一最终机器码，运行期成本相同；对不同展开结果，应以目标平台测量为准。工程上通常优先采用：

```
普通函数 / static inline（类型安全、易调试）
    > 简单宏（常量、条件编译、必要代码生成）
    > 复杂宏（高维护风险，必须以实际收益证明其必要性）
```

此排序是维护性和安全性优先级，不是机器周期排名。

### 通用选型结论

- 运行期逻辑：优先函数或 `static inline`。
- 诊断字符串：使用 `#`，需要宏展开时使用两层写法。
- 标识符生成：使用 `##`，需要预展开时使用两层写法。
- C11/C17 可变参数接口：优先让格式串也成为 `...` 的一部分。
- C23 项目：工具链确认支持后使用 `__VA_OPT__`。
- GNU 扩展：仅在明确固定工具链的项目中使用，并写入兼容性声明。
- 实时日志：宏只做入口，实时性由后端、队列和调度架构保证。

## 14. 快速参考速查表

### 14.1 场景选型表

|需求|推荐写法|
|---|---|
|获取参数原始拼写|`#x`|
|获取参数宏展开后的文本|`STR_RAW` + `STR` 两层宏|
|拼接字面记号|`a##b`|
|先展开后拼接|`CAT_RAW` + `CAT` 两层宏|
|C11/C17 允许只传格式串|`#define LOG(...) log(..., __VA_ARGS__)`|
|C23 固定参数后允许空尾参|`__VA_OPT__(,)`|
|GNU 项目兼容省略尾参|可考虑 `, ##__VA_ARGS__`，注明扩展依赖|
|重复生成枚举、字符串、表项|X-macro|
|运行期计算或副作用表达式|函数或 `static inline`|

### 14.2 特性对比表

|写法|是否标准|参数是否预展开|典型用途|主要风险|
|---|---|---|---|---|
|`#x`|标准|否|诊断文本|得到的是宏名而非展开值|
|`STR_RAW(x)` / `STR(x)`|标准|外层先展开|展开后的文本|层次多，命名应清楚|
|`a##b`|标准|相邻参数不先展开|标识符生成|拼接结果必须合法|
|`CAT_RAW` / `CAT`|标准|外层先展开|宏参数拼接|复杂嵌套难读|
|`__VA_ARGS__`|C99 起标准|按常规替换规则|格式化接口|空尾参和逗号边界|
|`, ##__VA_ARGS__`|GNU 扩展|依扩展规则|可选尾参|可移植性差|
|`__VA_OPT__`|C23|依标准规则|可选尾参|老工具链不支持|

## 15. 学习效果自检

完成本课后，应能独立回答并验证：

- 能解释 `STR_RAW(MACRO)` 与 `STR(MACRO)` 的结果差异。
- 能解释 `CAT_RAW(prefix, MACRO)` 为什么可能没有得到展开值。
- 能写出两层字符串化和两层记号拼接宏。
- 能区分 C99/C11 可变参数宏、GNU `, ##__VA_ARGS__` 和 C23 `__VA_OPT__`。
- 能设计一个 C11/C17 可调用 `LOG("ready")` 的接口，不依赖 GNU 扩展。
- 能找出会重复求值的宏，并改写为 `static inline` 函数。
- 能判断宏拼接结果是否合法。
- 能使用预处理输出验证宏行为。
- 能说明日志宏在 ISR 中的限制和后端责任边界。
- 能为目标工具链建立宏兼容性测试和构建告警策略。

## 16. 实践与进阶路径

### 阶段一：展开行为验证

建立独立测试文件，覆盖：

- 单层与双层字符串化。
- 单层与双层记号拼接。
- 参数为空、包含宏名、包含括号和复杂表达式等情况。
- C11/C17 严格模式与 GNU 方言的差异。

使用：

```
gcc -std=c11 -Wall -Wextra -Wpedantic -E macro_test.c
```

重点观察预处理结果，不只检查最终是否编译成功。

### 阶段二：构建日志宏

实现以下能力：

- `ERROR/WARN/INFO/DEBUG` 分级。
- 预处理期关闭指定级别。
- 文件、行号、任务标识和时间戳。
- 队列满时可观测的丢弃计数。
- 禁止 ISR 使用格式化日志，改为固定事件记录。
- 格式字符串与参数类型检查。

### 阶段三：X-macro 数据建模

选择一个协议字段或设备通道清单，生成：

- 枚举。
- 名称字符串表。
- 字段长度表。
- 访问权限表或测试用例表。

验证编号唯一性、数组边界及生成代码的可读性。

### 阶段四：性能与可靠性测试

- 用目标平台周期计数器测量日志调用和入队路径。
- 对比日志关闭、同步输出和异步输出的代码尺寸、栈使用和响应时间。
- 用压力测试统计队列峰值、丢弃率、最坏等待时间。
- 使用 `-E`、map 文件、反汇编和栈使用报告确认优化结果。
- 在 CI 中针对每个编译器和标准模式运行宏测试。

### 进阶方向

- 预处理器条件编译与跨平台配置体系。
- X-macro、代码生成脚本和自动生成头文件的边界设计。
- C23 预处理器新增能力及工具链成熟度。
- 日志与遥测的无锁环形缓冲区、内存序和 ISR 安全设计。
- 静态分析对宏展开代码的覆盖能力与限制。
- 编译时间、预处理产物规模与宏接口可维护性度量。
