
内存泄漏不只是“忘记调用 `free()`”。在嵌入式系统中，泄漏还包括：

- 对象仍被分配，但已经无法从任何有效所有者访问；
- 错误路径只释放了部分资源；
- 对象被长期引用，实际生命周期超出设计预期；
- 池块、DMA 缓冲区或队列对象被永久占用；
- `realloc()` 失败后丢失原指针；
- 计数器、引用计数或所有权转移协议失效。

长期运行设备中的泄漏往往不是一次耗尽几百 KB，而是每小时、每次重连或每个异常分支丢失几十字节。它可能在数天后才表现为分配失败、系统降级或复位。

本课重点建立一套完整能力：**定义所有权、在开发阶段发现泄漏、在运行阶段监测趋势、在产品设计中消除泄漏路径，并能在资源耗尽时安全降级。**

## 1. 学习目标

### 理解

- 理解泄漏、悬空引用、重复释放和逻辑滞留之间的差别。
- 理解 C 语言不会自动回收动态分配对象。
- 理解“可达”不等于“业务上仍然需要”。
- 理解泄漏可能发生在通用堆、固定池、队列、DMA 对象和第三方库内部。

### 掌握

- 按所有权规则审查 API 和错误路径。
- 使用主机动态分析工具、分配跟踪和运行时统计发现泄漏。
- 正确处理 `malloc()`、`free()`、`realloc()` 的失败与释放语义。
- 设计统一的销毁函数和部分初始化清理路径。
- 通过故障注入验证每个分配失败点。

### 精通

- 区分泄漏、碎片、缓存增长和正常高水位。
- 通过分配调用栈、对象计数和任务状态定位资源滞留。
- 设计受约束的运行时泄漏追踪器，避免追踪器自身递归分配。
- 将内存所有权与队列、引用计数、DMA 完成、中断同步结合。
- 设计长期运行系统的泄漏检测与恢复机制。

### 能够设计

- 设计覆盖模块边界的所有权契约。
- 设计可在开发版启用、产品版降级运行的跟踪机制。
- 建立泄漏测试、最大占用测试和故障注入的 CI 流程。
- 为无法完全消除动态分配的系统设计容量上限与安全降级。

## 3. 技术概述

### 3.1 什么是内存泄漏

在 C 语言中，分配对象通常具有分配存储期：对象从成功分配开始，一直存在到对应分配器释放它。

典型泄漏：

```
void bad_function(void)
{
    int *value = malloc(sizeof(*value));

    if (value == NULL) {
        return;
    }

    value = NULL; /* 丢失唯一指针，分配对象仍存在。 */
}
```

关键不是“指针变量离开作用域”，而是：

> **分配对象仍然占用资源，却失去了释放它所需的所有有效路径。**

### 3.2 嵌入式中的资源泄漏不止是 `malloc()`

|资源|泄漏或滞留形式|
|---|---|
|C 堆对象|分配后未释放，或丢失唯一所有权|
|固定池块|分配后没有归还|
|DMA 缓冲区|DMA 完成后未释放，或完成事件丢失|
|队列对象|发送成功后所有权不明确|
|RTOS 任务|删除任务后任务私有资源未释放|
|文件、套接字|没有关闭或连接状态异常退出|
|互斥锁/资源句柄|获取后未释放，造成永久阻塞|
|缓存对象|有界缓存被错误配置成无界增长|

### 3.3 泄漏与相邻概念

|现象|是否一定是泄漏|说明|
|---|---|---|
|当前堆使用量很高|否|可能是正常常驻对象|
|峰值后不下降|否|可能有缓存或对象池保留|
|总空闲大但大块申请失败|否|可能是碎片|
|对象仍可访问但业务不再需要|逻辑泄漏|资源仍被无用引用占住|
|指针丢失且对象仍分配|是|典型不可达泄漏|
|每次重连对象数持续增长|高度可疑|可能漏释放或缓存无上限|

**动态分析器报告“仍可达”的块，不代表这些块在业务上一定合理。**

## 5. 底层原理与功能特性深度解析

### 5.1 用所有权而不是“谁有指针”管理对象

裸指针只表示一个地址，不表达：

- 谁负责释放；
- 谁能修改；
- 是否可以跨任务保存；
- 是否被 DMA 使用；
- 是否允许复制引用；
- 何时对象失效。

推荐为每个资源定义一个所有权角色：

|角色|责任|
|---|---|
|创建者|成功分配并建立初始状态|
|所有者|负责释放，或明确转移所有权|
|借用者|仅在约定时间内访问，不释放、不保留|
|接收者|队列或回调成功后取得所有权|
|观察者|只读访问，不延长生命周期|

API 要说明失败时所有权归属：

```
/*
 * 成功：*out 获得对象所有权。
 * 失败：*out 为 NULL，内部临时资源已清理。
 */
bool session_create(session_t **out);

/*
 * 成功发送：函数把所有权转给队列消费者，并将 *owned 置 NULL。
 * 失败：所有权仍属于调用者。
 */
bool message_submit(message_t **owned);
```

### 5.2 统一销毁函数

结构体拥有多个资源时，应只有一个清理入口。

```
#include <stdlib.h>

typedef struct {
    uint8_t *rx_buffer;
    uint8_t *tx_buffer;
    int socket_handle;
} channel_t;

void channel_destroy(channel_t *channel)
{
    if (channel == NULL) {
        return;
    }

    free(channel->tx_buffer);
    free(channel->rx_buffer);

    if (channel->socket_handle >= 0) {
        socket_close(channel->socket_handle);
        channel->socket_handle = -1;
    }

    free(channel);
}
```

设计要求：

- 每个字段的“未持有资源”状态必须明确。
- 初始化时把指针设为 `NULL`，句柄设为无效值。
- 销毁函数应支持部分初始化对象。
- 释放顺序要符合资源依赖关系。
- 销毁函数不应失败后再次泄漏其他成员。

### 5.3 部分初始化失败的单出口清理

```
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>

typedef struct {
    uint8_t *rx;
    uint8_t *tx;
    parser_t *parser;
} link_t;

void link_destroy(link_t *link)
{
    if (link == NULL) {
        return;
    }

    parser_destroy(link->parser);
    free(link->tx);
    free(link->rx);
    free(link);
}

link_t *link_create(size_t rx_size, size_t tx_size)
{
    if ((rx_size == 0u) || (tx_size == 0u)) {
        return NULL;
    }

    link_t *link = malloc(sizeof(*link));

    if (link == NULL) {
        return NULL;
    }

    *link = (link_t) {
        .rx = NULL,
        .tx = NULL,
        .parser = NULL
    };

    link->rx = malloc(rx_size);

    if (link->rx == NULL) {
        goto fail;
    }

    link->tx = malloc(tx_size);

    if (link->tx == NULL) {
        goto fail;
    }

    link->parser = parser_create();

    if (link->parser == NULL) {
        goto fail;
    }

    return link;

fail:
    link_destroy(link);
    return NULL;
}
```

统一清理入口避免每个失败分支遗漏不同成员。

`goto fail` 在这种资源收尾场景中通常比复制多份释放代码更安全。

### 5.4 `realloc()` 泄漏与事务语义

错误写法：

```
buffer = realloc(buffer, new_size);

if (buffer == NULL) {
    return false;
}
```

非零尺寸重分配失败时，旧对象仍然有效；直接覆盖指针会丢失它。

正确写法：

```
void *temporary = realloc(buffer, new_size);

if (temporary == NULL) {
    return false; /* 旧 buffer 仍有效。 */
}

buffer = temporary;
```

更完整的封装：

```
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>

bool buffer_resize(void **buffer, size_t new_size)
{
    if (buffer == NULL) {
        return false;
    }

    if (new_size == 0u) {
        free(*buffer);
        *buffer = NULL;
        return true;
    }

    void *temporary = realloc(*buffer, new_size);

    if (temporary == NULL) {
        return false;
    }

    *buffer = temporary;
    return true;
}
```

调用端应传入真正的 `void *` 对象：

```
void *storage = NULL;

if (!buffer_resize(&storage, 256u)) {
    /* 处理失败。 */
}
```

不要把任意 `T **` 强制转换为 `void **`。C 的 `void *` 转换规则不能推导出 `void **` 与 `T **` 可互换。

### 5.5 指针泄漏与所有权转移

队列传递指针时，需要明确成功和失败语义：

```
#include <stdbool.h>

bool submit_owned(packet_t **owned)
{
    if ((owned == NULL) || (*owned == NULL)) {
        return false;
    }

    packet_t *packet = *owned;

    if (!queue_send(packet)) {
        /* 失败时所有权仍在调用方。 */
        return false;
    }

    /* 成功后由消费者负责释放。 */
    *owned = NULL;
    return true;
}
```

消费者：

```
void packet_consumer(void)
{
    packet_t *packet = NULL;

    while (queue_receive(&packet)) {
        process_packet(packet);
        packet_destroy(packet);
    }
}
```

关键约束：

- `queue_send()` 成功必须意味着消费者最终会处理或丢弃对象。
- 关闭队列、任务退出和系统重置时必须清理队列中的所有对象。
- 发送方不能在成功后继续通过其他别名访问对象。
- 若消费者启动 DMA，消费者应继续承担所有权，直至 DMA 完成。

### 5.6 引用计数可能缓解生命周期问题，也可能制造新问题

简单引用计数：

```
typedef struct {
    uint32_t references;
    payload_t payload;
} shared_object_t;
```

需要规定：

- 引用计数的初始值；
- 谁可以增加和减少；
- 增减是否原子；
- 引用计数为零时由谁析构；
- 是否可能存在循环引用；
- 引用计数溢出如何处理；
- ISR 是否参与引用操作。

**引用计数不是泄漏自动修复工具。**

错误增加一次会造成永久滞留；错误减少一次会导致过早释放。更重要的是，引用计数只能追踪已登记引用，无法自动追踪裸指针别名。

### 5.7 固定池的“泄漏”检测

固定池没有 `malloc/free`，仍然会泄漏：

```
acquire 成功 → 对象进入队列 → 消费者提前返回 → 未 release
```

池级检测应记录：

- 当前使用数量；
- 峰值使用数量；
- 分配失败次数；
- 非法归还次数；
- 每个块的状态；
- 可选的分配调用点或任务 ID。

如果池数量 32，运行多年后长期维持 32/32，而业务并发上限只有 8，优先怀疑对象滞留或归还路径遗漏。

### 5.8 运行期对象状态机

对异步对象，不要只记一个布尔 `busy`。可设计状态：

```
typedef enum {
    OBJ_FREE,
    OBJ_CPU_OWNED,
    OBJ_QUEUED,
    OBJ_DMA_OWNED,
    OBJ_COMPLETE
} object_state_t;
```

允许转移：

```
FREE → CPU_OWNED
CPU_OWNED → QUEUED
QUEUED → CPU_OWNED
CPU_OWNED → DMA_OWNED
DMA_OWNED → COMPLETE
COMPLETE → FREE
```

非法转移应记录错误，必要时进入安全故障处理。

### 5.9 泄漏检测必须避免追踪器自我递归

如下设计很危险：

```
malloc()
  → leak_tracker_record()
      → malloc()
          → leak_tracker_record()
              → ...
```

解决方向：

- 追踪表静态分配；
- 追踪器内部不使用被追踪分配器；
- 追踪元数据采用固定数组或静态环形缓冲区；
- 追踪代码明确重入保护；
- 记录调用点时避免动态格式化字符串。

## 6. 性能量化分析

### 6.1 泄漏增长速率

若单次事件泄漏 LL 字节，每单位时间发生 RR 次：

G=L×RG=L×R

若每次设备重连泄漏 96 B，每天重连 500 次：

G=96×500=48000 B/dayG=96×500=48000 B/day

约为：

46.875 KiB/day46.875 KiB/day

若可用动态资源 64 KiB，理论上约：

6446.875≈1.37 day46.87564​≈1.37 day

就可能耗尽。该计算忽略碎片、其他分配和峰值波动，通常只能用于风险估算。

### 6.2 目标设备运行监测指标

建议分开统计：

|指标|含义|
|---|---|
|当前已分配请求字节|业务请求总量|
|当前分配块数量|存活对象数|
|峰值已分配字节|历史高水位|
|峰值对象数|并发高水位|
|总空闲量|剩余总容量|
|最大连续空闲块|最大单次可申请容量|
|分配失败数|容量或碎片问题|
|分配/释放次数|长期配对检查|
|每模块对象数|资源归属诊断|

对固定池，重点记录：

```
pool_capacity
current_used
peak_used
allocation_failures
invalid_releases
```

### 6.3 不能把“当前使用量不回落”直接当作泄漏

可能的原因：

1. 合理的常驻对象。
2. 缓存策略保留内存。
3. 内存池保留容量但对象已经归还。
4. 高水位分配器不把内存归还系统。
5. 碎片导致可用大块减少。
6. 真实泄漏或逻辑滞留。

必须结合**对象数量、资源所有者、分配调用点和生命周期事件**判断。

### 6.4 跟踪表容量预算

假设静态跟踪表最多记录 256 个活跃对象。每条记录包含：

```
typedef struct {
    void *pointer;
    size_t requested_size;
    uint32_t callsite_id;
    uint16_t task_id;
    uint16_t flags;
} allocation_record_t;
```

在典型 32 位 ABI 下，每条记录可能约 16 B；实际必须用目标编译器测 `sizeof`。

若为 256 条：

256×16=4096 B256×16=4096 B

还需考虑：

- 对齐；
- 锁和统计字段；
- 记录表搜索开销；
- 记录表满策略。

这类追踪器适合开发版，产品版通常使用简化计数或更小采样表。

### 6.5 额外运行时成本

- 每次分配查找记录槽位：取决于线性搜索或哈希实现。
- 每次释放查找对象记录：同上。
- 记录调用栈：可能显著增加 RAM、代码和时间。
- 事件日志：可能触发阻塞或二次分配。
- 追踪锁：可能增加任务延迟和优先级反转。

因此建议分级启用：

```
开发版：完整记录和断言
集成测试版：调用点 + 统计
产品版：峰值、失败数、模块计数
```

## 7. 应用场景选型指南

### 7.1 纯文本决策流程图

```
对象是静态容量对象吗？
├── 是
│   └── 静态分配或固定池
│       ├── 增加峰值和失败计数
│       └── 检查所有状态转移均归还
└── 否
    ├── 对象生命周期是否跨异步边界？
    │   ├── 是
    │   │   ├── 定义唯一所有者和转移点
    │   │   └── 增加任务、队列、DMA 退出清理
    │   └── 否
    │       └── 优先用栈、调用者缓冲区或 arena
    └── 必须使用 malloc/free 吗？
        ├── 否：改为池或静态工作区
        └── 是
            ├── 是否所有分配器入口都统一？
            │   ├── 否：先统一资源域
            │   └── 是：增加跟踪、故障注入和运行监测

运行一段时间后占用不回落？
├── 是
│   ├── 当前对象数增长：疑似泄漏或无界缓存
│   ├── 对象数稳定但大块申请失败：疑似碎片
│   └── 对象数降低但堆水位不恢复：可能是分配器策略
└── 否
    └── 仍需检查稀有错误路径和长时间测试
```

### 7.2 场景选型

|场景|检测方式|重点|
|---|---|---|
|主机可复现模块|ASan、LeakSanitizer、Valgrind|越界、UAF、泄漏|
|MCU 长期运行|统计、事件计数、对象池水位|趋势和峰值|
|RTOS 消息系统|对象状态机、队列所有权核查|失败发送与任务退出|
|DMA 异步流程|DMA in-flight 计数和超时|完成丢失、过早释放|
|低内存错误路径|逐分配点故障注入|部分初始化回收|
|第三方库|包装器、库接口审计|私有堆和释放配对|
|现场偶发复位|静态故障记录|复位前资源和调用点|

## 8. 工程最佳实践

### 8.1 API 契约必须明确

每个资源 API 都回答：

1. 成功时谁拥有对象？
2. 失败时是否保留原对象？
3. 输入指针是借用还是转移？
4. 是否允许异步保存？
5. 哪个函数负责释放？
6. 销毁是否允许部分初始化对象？
7. 是否可从 ISR 调用？
8. 是否会阻塞？
9. 是否可能进行二次分配？

### 8.2 统一资源域

不同分配器不得交叉释放：

```
malloc       ↔ free
pvPortMalloc ↔ vPortFree
pool_alloc   ↔ pool_free
driver_alloc ↔ driver_release
```

即使底层偶然使用同一块 SRAM，也不能假定元数据兼容。

### 8.3 用状态结构聚合资源

比起多个全局裸指针，使用明确拥有资源的结构体：

```
typedef struct {
    parser_t *parser;
    uint8_t *workspace;
    message_pool_t *pool;
    bool started;
} service_t;
```

配套：

```
bool service_init(service_t *service);
void service_deinit(service_t *service);
```

`service_deinit()` 应对部分初始化状态安全。

### 8.4 代码审查规则

重点搜索：

```
malloc(
calloc(
realloc(
pvPortMalloc(
pool_alloc(
queue_send(
dma_start(
task_create(
```

对每处检查：

- 成功返回值；
- 失败分支；
- 对应释放点；
- 异步所有权；
- 错误路径清理；
- 重复调用和重连路径；
- 对象是否逃逸到静态变量、队列或回调。

### 8.5 工程规范

1. 禁止直接覆盖唯一持有指针的 `realloc()` 结果。
2. 禁止在接口没有所有权说明时传递拥有型裸指针。
3. 禁止错误路径通过动态分配记录错误。
4. 禁止 ISR 使用未明确支持的通用堆接口。
5. 任务删除前必须释放或转移任务拥有的资源。
6. 队列关闭和系统停机必须清理排队对象。
7. 缓存和对象池必须设置容量上限。
8. 对长周期设备执行至少覆盖多个典型业务周期的压力测试。
9. 关键模块报告当前值、峰值、失败次数。
10. 将静态分析、主机动态分析和目标板长期测试组合使用。

## 9. 常见错误与避坑指南

### 9.1 错误一：失败分支只释放部分成员

错误代码：

```
object_t *object = malloc(sizeof(*object));

if (object == NULL) {
    return NULL;
}

object->a = malloc(128u);
object->b = malloc(256u);

if ((object->a == NULL) || (object->b == NULL)) {
    free(object);
    return NULL;
}
```

根因：

- `a` 或 `b` 可能已成功分配；
- 只释放外层对象，内部块泄漏。

正确实现：

```
object_t *object = malloc(sizeof(*object));

if (object == NULL) {
    return NULL;
}

*object = (object_t) {
    .a = NULL,
    .b = NULL
};

object->a = malloc(128u);
object->b = malloc(256u);

if ((object->a == NULL) || (object->b == NULL)) {
    object_destroy(object);
    return NULL;
}
```

风险影响：

- 仅在低内存路径发生；
- 常规功能测试难以覆盖；
- 故障后资源持续减少。

### 9.2 错误二：`realloc()` 失败时丢失旧指针

错误代码：

```
data = realloc(data, new_size);

if (data == NULL) {
    return false;
}
```

根因：

- 非零重分配失败时旧对象依然有效；
- 直接覆盖导致内存不可释放。

正确实现：

```
void *replacement = realloc(data, new_size);

if (replacement == NULL) {
    return false;
}

data = replacement;
```

风险影响：

- 低内存时泄漏进一步加重；
- 原始数据恢复路径丢失。

### 9.3 错误三：队列发送失败后对象没有归还

错误代码：

```
packet_t *packet = packet_create();

if (packet == NULL) {
    return;
}

if (!queue_send(packet)) {
    return; /* packet 泄漏。 */
}
```

正确实现：

```
packet_t *packet = packet_create();

if (packet == NULL) {
    return;
}

if (!queue_send(packet)) {
    packet_destroy(packet);
    return;
}

/* 发送成功后由消费者负责销毁。 */
```

风险影响：

- 队列拥塞时泄漏速度最快；
- 正常负载不一定复现；
- 可能在网络突发时迅速耗尽池。

### 9.4 错误四：对象被缓存但没有上限

错误模式：

```
cache_insert(new_item); /* 无限制增长。 */
```

根因：

- 对象仍然可达，动态工具可能认为不是泄漏；
- 但缓存保留策略没有容量上限，属于逻辑资源泄漏风险。

正确设计：

```
缓存容量上限 = N
超过容量时：
├── 淘汰最旧条目
├── 拒绝插入
└── 降级为不缓存
```

风险影响：

- 长时间运行后内存随输入种类单调增长；
- 动态分析报告中不一定显示“丢失引用”。

### 9.5 错误五：任务退出时忽略私有资源

错误代码：

```
void worker_task(void *argument)
{
    worker_context_t *context = worker_context_create();

    if (context == NULL) {
        vTaskDelete(NULL);
    }

    do_work(context);

    vTaskDelete(NULL); /* 直接退出，未释放 context。 */
}
```

正确实现：

```
void worker_task(void *argument)
{
    worker_context_t *context = worker_context_create();

    if (context != NULL) {
        do_work(context);
        worker_context_destroy(context);
    }

    vTaskDelete(NULL);
}
```

还要检查：

- 删除任务时是否有异步 DMA 或回调仍引用 `context`；
- 任务栈和任务控制块使用静态还是动态分配；
- RTOS 版本与任务删除语义；
- 任务自删除时是否允许调用统一清理路径。

### 9.6 错误六：把 `volatile` 当作生命周期管理

错误想法：

```
volatile object_t *shared;
```

`volatile` 不会：

- 释放对象；
- 管理引用；
- 阻止悬空指针；
- 提供互斥；
- 确保 DMA 完成。

应使用所有权协议、队列、锁、原子操作和 DMA 状态机解决相应问题。

### 10.2 固定容量分配跟踪器框架

目标板通常不能直接使用宿主机的 LeakSanitizer。可增加一个静态分配的跟踪表，记录统一包装器管理的分配对象。

**使用约束：**

- 所有相关分配必须经过包装器。
- 跟踪表静态分配，不得调用被跟踪的分配函数。
- 下方示例的锁 hook 必须由平台实现。
- 统计记录的是请求尺寸，不等于底层实际块占用。
- `realloc()` 对已被其他线程同时操作的同一指针不安全；调用方必须自行同步。
- 跟踪表满时示例采取“释放新块并返回失败”的保守策略，可按系统需求调整。

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdlib.h>

#define LEAK_TRACK_MAX 128u

#ifndef LEAK_TRACK_LOCK
#define LEAK_TRACK_LOCK()   platform_leak_track_lock()
#define LEAK_TRACK_UNLOCK() platform_leak_track_unlock()
#endif

typedef struct {
    void *pointer;
    size_t size;
    uint32_t site_id;
    bool active;
} leak_record_t;

typedef struct {
    size_t live_blocks;
    size_t live_bytes;
    size_t peak_blocks;
    size_t peak_bytes;
    size_t alloc_failures;
    size_t table_overflows;
    size_t unknown_frees;
} leak_stats_t;

static leak_record_t g_records[LEAK_TRACK_MAX];
static leak_stats_t g_stats;

static size_t find_free_record_locked(void)
{
    for (size_t i = 0u; i < LEAK_TRACK_MAX; ++i) {
        if (!g_records[i].active) {
            return i;
        }
    }

    return LEAK_TRACK_MAX;
}

static size_t find_pointer_record_locked(const void *pointer)
{
    for (size_t i = 0u; i < LEAK_TRACK_MAX; ++i) {
        if (g_records[i].active &&
            (g_records[i].pointer == pointer)) {
            return i;
        }
    }

    return LEAK_TRACK_MAX;
}

static void increment_saturated(size_t *value)
{
    if (*value != SIZE_MAX) {
        ++(*value);
    }
}

void *tracked_malloc(size_t size, uint32_t site_id)
{
    if (size == 0u) {
        return NULL;
    }

    void *pointer = malloc(size);

    if (pointer == NULL) {
        LEAK_TRACK_LOCK();
        increment_saturated(&g_stats.alloc_failures);
        LEAK_TRACK_UNLOCK();
        return NULL;
    }

    LEAK_TRACK_LOCK();

    const size_t slot = find_free_record_locked();

    if (slot == LEAK_TRACK_MAX) {
        increment_saturated(&g_stats.table_overflows);
        LEAK_TRACK_UNLOCK();

        /*
         * 跟踪表满时拒绝未跟踪对象，避免统计出现静默缺口。
         */
        free(pointer);
        return NULL;
    }

    g_records[slot] = (leak_record_t) {
        .pointer = pointer,
        .size = size,
        .site_id = site_id,
        .active = true
    };

    ++g_stats.live_blocks;

    if (size <= SIZE_MAX - g_stats.live_bytes) {
        g_stats.live_bytes += size;
    } else {
        g_stats.live_bytes = SIZE_MAX;
    }

    if (g_stats.live_blocks > g_stats.peak_blocks) {
        g_stats.peak_blocks = g_stats.live_blocks;
    }

    if (g_stats.live_bytes > g_stats.peak_bytes) {
        g_stats.peak_bytes = g_stats.live_bytes;
    }

    LEAK_TRACK_UNLOCK();

    return pointer;
}

void tracked_free(void *pointer)
{
    if (pointer == NULL) {
        return;
    }

    LEAK_TRACK_LOCK();

    const size_t slot = find_pointer_record_locked(pointer);

    if (slot == LEAK_TRACK_MAX) {
        increment_saturated(&g_stats.unknown_frees);
        LEAK_TRACK_UNLOCK();

        /*
         * 工程策略可选：
         * 1. 不调用 free，避免错误释放导致堆破坏；
         * 2. 触发诊断故障。
         */
        return;
    }

    const size_t size = g_records[slot].size;

    g_records[slot] = (leak_record_t) { 0 };

    if (g_stats.live_blocks > 0u) {
        --g_stats.live_blocks;
    }

    if (g_stats.live_bytes >= size) {
        g_stats.live_bytes -= size;
    } else {
        g_stats.live_bytes = 0u;
    }

    LEAK_TRACK_UNLOCK();

    free(pointer);
}

void *tracked_realloc(void *pointer,
                      size_t new_size,
                      uint32_t site_id)
{
    if (pointer == NULL) {
        return tracked_malloc(new_size, site_id);
    }

    if (new_size == 0u) {
        tracked_free(pointer);
        return NULL;
    }

    LEAK_TRACK_LOCK();

    const size_t old_slot =
        find_pointer_record_locked(pointer);

    if (old_slot == LEAK_TRACK_MAX) {
        increment_saturated(&g_stats.unknown_frees);
        LEAK_TRACK_UNLOCK();
        return NULL;
    }

    const size_t old_size = g_records[old_slot].size;

    LEAK_TRACK_UNLOCK();

    void *replacement = realloc(pointer, new_size);

    if (replacement == NULL) {
        LEAK_TRACK_LOCK();
        increment_saturated(&g_stats.alloc_failures);
        LEAK_TRACK_UNLOCK();

        /* 原对象仍然有效，跟踪记录不变。 */
        return NULL;
    }

    LEAK_TRACK_LOCK();

    /*
     * 同一个 pointer 不得与其他线程并发 realloc/free。
     * 在该约束下，旧记录仍存在且槽位不会被其他分配复用。
     */
    const size_t current_old_slot =
        find_pointer_record_locked(pointer);

    if (current_old_slot == LEAK_TRACK_MAX) {
        LEAK_TRACK_UNLOCK();

        /*
         * 这是跟踪器内部一致性故障。
         * replacement 已经有效，不能在此简单返回 NULL，
         * 否则会泄漏 replacement。
         */
        free(replacement);
        return NULL;
    }

    g_records[current_old_slot] = (leak_record_t) {
        .pointer = replacement,
        .size = new_size,
        .site_id = site_id,
        .active = true
    };

    if (new_size >= old_size) {
        const size_t increase = new_size - old_size;

        if (increase <= SIZE_MAX - g_stats.live_bytes) {
            g_stats.live_bytes += increase;
        } else {
            g_stats.live_bytes = SIZE_MAX;
        }
    } else {
        const size_t decrease = old_size - new_size;

        if (g_stats.live_bytes >= decrease) {
            g_stats.live_bytes -= decrease;
        } else {
            g_stats.live_bytes = 0u;
        }
    }

    if (g_stats.live_bytes > g_stats.peak_bytes) {
        g_stats.peak_bytes = g_stats.live_bytes;
    }

    LEAK_TRACK_UNLOCK();

    return replacement;
}

leak_stats_t tracked_memory_stats(void)
{
    leak_stats_t result;

    LEAK_TRACK_LOCK();
    result = g_stats;
    LEAK_TRACK_UNLOCK();

    return result;
}
```

### 10.3 追踪器的工程审查

这类跟踪器适合定位问题，但不能取代所有权设计。

还需注意：

- `site_id` 应由静态常量产生，避免每次动态构造字符串。
- 若使用 `__FILE__` 字符串，可能增加固件常量区；可用编译期哈希或事件映射表。
- 追踪器查找采用线性扫描，最多检查 128 条记录。
- 锁实现不能在高优先级 ISR 中错误地阻塞。
- 对未知指针，示例不调用 `free()`，防止进一步破坏堆；产品策略需明确是继续运行、告警还是复位。
- 若启用多任务并发，不能让同一对象被一个任务 `free()`、另一个任务 `realloc()`。
- 跟踪器只能覆盖经过包装器的分配。第三方库私有分配器需独立监测。

### 10.4 调用点包装

```
#include <stdint.h>

#define TRACKED_ALLOC(size_) \
    tracked_malloc((size_), allocation_site_id(__FILE__, __LINE__))

#define TRACKED_REALLOC(ptr_, size_) \
    tracked_realloc((ptr_), (size_), \
                    allocation_site_id(__FILE__, __LINE__))
```

宏的 `site_id` 生成函数应无动态分配，例如对文件名和行号计算 32 位哈希。哈希冲突需要接受或同时记录更多字段。

## 11. 工业级实际案例分析

以下为工业常见问题的工程化案例。数据用于说明分析方法，不代表特定产品实测报告。

### 11.1 案例一：通信重连导致堆逐步耗尽

#### 需求与现象

- 网关持续运行；
- 网络掉线后自动重连；
- 每次重连后空闲内存略少；
- 经过多次重连后连接创建失败。

#### 可能路径

```
连接对象创建
├── 分配连接状态
├── 分配接收缓冲区
├── 创建解析器
└── 注册回调

断连
├── 关闭 socket
├── 取消回调
├── 停止 DMA
└── 销毁连接对象
```

常见遗漏：

- 注册失败后解析器未销毁；
- socket 关闭，但接收缓冲区没有释放；
- 延迟回调仍保留旧对象，导致销毁路径跳过；
- 重连前旧连接没有完成 DMA 取消。

#### 设计要点

- 使用单一 `connection_destroy()`。
- 销毁前先禁止新的回调进入。
- 等待或取消异步 I/O。
- 追踪每次连接创建和销毁对象数。
- 运行 10,000 次重连测试，检查稳态对象数是否回到基线。
- 将重连失败路径逐步故障注入。

#### 预期监测

```
active_connections
live_rx_buffers
live_parsers
pending_callbacks
dma_in_flight
allocation_failures
```

如果 `active_connections` 回到 0，但 `live_rx_buffers` 每次增加 1，泄漏位置已明显缩小。

### 11.2 案例二：队列满时消息对象泄漏

#### 需求

- 生产任务创建事件对象；
- 通过 FreeRTOS 队列传给消费者；
- 高负载时消费者处理速度下降；
- 运行一段时间后事件池耗尽。

#### 架构设计

```
生产者：
acquire → 填写 → queue send
                   ├── 成功：所有权转移
                   └── 失败：生产者归还

消费者：
queue receive → 处理 → release
```

#### 核心代码

```
bool event_publish(event_t **owned)
{
    if ((owned == NULL) || (*owned == NULL)) {
        return false;
    }

    event_t *event = *owned;

    if (xQueueSend(g_event_queue, &event, 0u) != pdPASS) {
        /* 发送失败，生产者仍持有对象。 */
        return false;
    }

    /* 发送成功，消费者负责释放。 */
    *owned = NULL;
    return true;
}

void event_producer(void)
{
    event_t *event = event_pool_acquire();

    if (event == NULL) {
        event_drop_counter_increment();
        return;
    }

    fill_event(event);

    if (!event_publish(&event)) {
        event_pool_release(event);
        event = NULL;
    }
}
```

#### 设计要点

- `event_publish()` 只在队列成功后转移所有权。
- 如果消费者被删除或队列被清空，队列中的每个对象必须逐一归还。
- 池峰值与队列峰值一起监测。
- 队列深度 16、消费者持有 1 个、生产者临时持有 2 个时，池至少要覆盖这些数量和安全余量，而不是简单设置为 16。

### 11.3 案例三：低内存错误路径本身再次分配

#### 现象

设备在堆接近耗尽时分配失败，错误处理开始格式化日志；日志格式化再次分配，继而触发递归失败或系统卡死。

#### 风险链

```
业务 malloc 失败
  ↓
动态格式化错误日志
  ↓
日志内部 malloc 失败
  ↓
日志错误处理再次分配
  ↓
递归、栈耗尽或锁死
```

#### 架构改造

- 低内存路径使用静态错误码和固定长度记录。
- 采用静态环形缓冲区。
- 错误计数器使用饱和计数。
- 日志任务在资源恢复后再格式化输出。
- 故障路径禁止调用可能分配的字符串格式化接口。

```
typedef struct {
    uint32_t event_id;
    uint32_t argument0;
    uint32_t argument1;
} compact_error_record_t;

static compact_error_record_t g_emergency_log[8];
static volatile uint32_t g_emergency_log_write;

void record_allocation_failure(uint32_t module_id,
                               uint32_t requested_size)
{
    const uint32_t index = g_emergency_log_write % 8u;

    g_emergency_log[index] = (compact_error_record_t) {
        .event_id = module_id,
        .argument0 = requested_size,
        .argument1 = 0u
    };

    ++g_emergency_log_write;
}
```

#### 设计要点

- 环形缓冲区并发访问时需使用适当同步。
- 记录操作不能调用动态分配。
- 丢弃旧记录还是覆盖新记录必须明确。
- 若在异常处理程序使用，需要分析当前栈是否可靠。

## 12. 高频问题深度答疑

### 12.1 ASan 没报泄漏，能否证明没有泄漏？

不能。

可能原因：

- 测试路径未覆盖泄漏分支；
- 对象仍由全局指针或缓存引用，属于逻辑泄漏；
- 第三方库使用独立分配器；
- 目标板行为与主机模拟路径不同；
- 资源是固定池块、RTOS 对象或 DMA 描述符，不在 ASan 管理范围内。

ASan 是强工具，但不是系统资源完整性证明。

### 12.2 为什么 ASan 报告“仍可达”的对象？

泄漏工具通常根据程序结束时对象是否能从根集合到达来分类。

全局缓存、静态指针、任务控制结构可能仍引用对象。工具会认为它们可达，但业务上对象可能已经无用。

应结合业务语义判断：

- 缓存是否有上限？
- 会话是否已经结束？
- 回调表是否还保留指针？
- 对象引用计数是否归零？

### 12.3 堆水位降低，但没有泄漏报告，可能是什么？

可能是：

- 分配器不把空闲区归还给系统；
- 空闲空间碎片化；
- 跟踪工具没覆盖某个分配域；
- 统计的是剩余最大块而不是总剩余；
- 某个分配器扩展了静态保留区域；
- 代码内存池和 C 堆被混合统计。

应同时采集总空闲、最大连续空闲、活动块数和分配域来源。

### 12.4 引用计数能解决异步对象泄漏吗？

它能帮助管理多方共享对象，但前提是每个引用都被严格登记和释放。

常见问题：

- 某条路径忘记减计数，形成滞留；
- 重复减计数，导致提前释放；
- 计数器不是原子的；
- 循环引用使计数永不归零；
- 任务取消时漏掉引用释放。

对于简单异步流，单一所有权加队列转移通常更容易验证。

### 12.5 固定池没有内存泄漏，为什么还是会耗尽？

对象可能仍然被某个有效指针持有，但业务已经不需要它。例如：

- 队列对象无人消费；
- DMA 完成事件丢失；
- 任务提前退出但没有归还对象；
- 缓存没有上限；
- 某个状态机永远停留在 `BUSY`。

这是资源滞留或逻辑泄漏。应记录每块状态和持有者，而不只记录池总水位。

### 12.6 运行期遇到泄漏能不能自动回收？

C 没有自动垃圾回收机制。除非架构使用追踪式 GC，否则无法安全猜测哪些裸指针不再使用。

更现实的恢复策略：

- 限制无界资源增长；
- 停止非关键服务；
- 清理可重建缓存；
- 重建单个子系统；
- 进入安全状态并复位；
- 通过复位后日志保留诊断数据。

**不要把“扫描 RAM 看起来像指针的值”作为可靠回收方案。**

## 13. 课程核心总结

### 核心要点

1. **泄漏根因通常是所有权不清，而不是缺少一行 `free()`。**
2. 动态分析工具可以发现实际执行路径的问题，不能代替架构和长期运行验证。
3. `realloc()` 必须采用临时指针，失败时保留旧对象。
4. 部分初始化必须有统一、可重复调用的清理路径。
5. 队列发送失败、任务退出、DMA 完成丢失都是高发泄漏点。
6. 固定池也可能发生逻辑泄漏。
7. 堆当前使用量不下降，不一定就是泄漏；要区分保留策略、碎片和真实对象增长。
8. 低内存错误路径不能依赖新的动态分配。
9. 跟踪器本身不能递归使用被跟踪分配器。
10. 目标产品需要运行期峰值、失败次数和对象数量监测。

### 性能和可靠性排序

按“发现根因的直接性”通常可概括为：

```
所有权清晰 + 故障注入
    ↓
ASan/LeakSanitizer 动态分析
    ↓
分配调用点跟踪
    ↓
池与堆水位趋势监控
    ↓
仅观察系统是否复位
```

不同方法解决不同问题，不能互相替代。

### 通用预防结论

- 能不动态分配就不在运行期动态分配。
- 必须动态分配时，统一分配域、定义所有权、限制容量。
- 异步共享时用明确的所有权转移，而不是隐含的裸指针约定。
- 用故障注入验证低内存路径。
- 将开发期强检测与产品期轻量遥测组合起来。

## 14. 快速参考速查表

### 泄漏排查表

|现象|优先检查|
|---|---|
|每次重连占用递增|连接销毁、回调注销、DMA 取消|
|队列满后池耗尽|发送失败分支是否归还|
|任务删除后占用不降|任务私有对象、任务栈和 TCB 策略|
|运行很久后大块申请失败|最大空闲块、碎片、长寿命对象混排|
|只在低内存时故障|错误日志、清理路径和重试递归|
|释放时崩溃|越界、重复释放、跨分配器释放|
|统计对象数增长但字节稳定|小对象泄漏或固定池块滞留|
|字节增长但对象数稳定|单个无界缓冲区或 `realloc()` 容量无上限|

### 资源释放配对表

|获取方式|对应释放|
|---|---|
|`malloc/calloc/realloc`|`free`|
|`pvPortMalloc`|`vPortFree`|
|固定池 `acquire`|同一池 `release`|
|文件打开|对应关闭接口|
|socket 创建|close/shutdown 约定|
|DMA 提交|完成或取消后归还缓冲区|
|任务创建|依 RTOS 分配模式处理 TCB、任务栈及私有资源|

### 代码审查清单

- [ ]  每次成功获取都有所有者。
- [ ]  每个失败分支都清理已成功获取的资源。
- [ ]  异步调用是否保存了指针？
- [ ]  队列发送成功是否明确转移所有权？
- [ ]  队列发送失败是否仍由调用方释放？
- [ ]  任务退出或删除是否清理资源？
- [ ]  `realloc()` 是否使用临时指针？
- [ ]  缓存是否有容量上限？
- [ ]  错误处理路径是否会再次分配？
- [ ]  第三方库是否使用独立分配器？

## 16. 实践与进阶路径

### 第一阶段：代码审计

对一个实际模块执行：

1. 搜索所有动态分配和资源获取点。
2. 为每个对象标注创建者、所有者、释放者。
3. 列出所有提前返回、错误跳转和超时分支。
4. 检查队列、回调、DMA 和全局表中的指针逃逸。
5. 统一到对象级销毁函数。

产出：

```
对象所有权表
分配器配对表
失败路径清单
异步引用清单
```

### 第二阶段：主机动态分析

将可移植模块编译到主机：

```
-g
-fsanitize=address,undefined
-fno-omit-frame-pointer
```

测试：

- 正常创建和销毁；
- 解析失败；
- 重复连接和断开；
- 超时；
- 部分初始化失败；
- 消费者取消；
- 队列满。

在支持的环境中运行 LeakSanitizer 或 Valgrind，并把报告纳入 CI。

### 第三阶段：分配失败注入

包装分配器，使第 kk 次分配失败：

```
第 1 次失败
第 2 次失败
……
第 K 次失败
全部成功
```

每次结束后核对：

live_blocksafter=live_blocksbeforelive_blocksafter​=live_blocksbefore​

并确认：

- 旧对象状态仍有效；
- 输出参数契约一致；
- 没有部分提交；
- 不发生重复释放；
- 后续重试仍可成功。

### 第四阶段：长时间运行验证

固定场景循环：

- 重连；
- 任务创建与销毁；
- 队列拥塞；
- DMA 超时；
- 配置更新；
- 大小边界输入。

周期性记录：

```
当前分配块数
当前请求字节
峰值
分配失败数
池使用峰值
最大连续空闲块
关键任务堆栈水位
```

测试时长应覆盖目标产品的典型长周期行为；对于长期无人值守设备，短时间稳定不代表长期无泄漏。

### 第五阶段：目标板故障取证

建立无需动态分配的故障记录：

- 复位原因；
- 分配失败计数；
- 最后一次分配调用点 ID；
- 当前模块对象数；
- 池使用峰值；
- 最近的资源获取和释放事件；
- 关键任务栈余量。

故障记录区应明确处理掉电、看门狗复位和 SRAM 保留行为。

### 进阶方向

- C 静态分析工具的所有权与路径分析规则；
- 线性类型、借用检查与 C API 设计；
- 句柄表与代数，检测陈旧引用；
- 无锁固定池及 ABA 问题；
- RTOS 多核内存追踪；
- 低内存安全状态与功能降级；
- 资源生命周期的状态机建模和形式化验证。

本课的工程验收标准不是“测试没看到泄漏”，而是能够说明：**谁创建每个对象、谁在什么条件下释放、所有失败路径如何回收、异步引用何时结束、资源耗尽时系统如何保持安全。**
