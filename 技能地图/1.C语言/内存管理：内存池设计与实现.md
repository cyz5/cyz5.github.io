
内存池不是“把 `malloc()` 换成数组”。一个可用于工业系统的内存池，至少要回答：

- 池里的对象尺寸和数量上限是什么？
- 分配与释放的最坏执行时间如何约束？
- 如何检测越界、重复释放和非法指针？
- 任务、中断和 DMA 如何共享对象？
- 池耗尽时系统如何退化？
- 对象的所有权何时转移，何时归还？
- 统计数据能否用于证明容量足够？

本课以**固定大小内存池**为主，讨论嵌入式系统中常见的静态容量对象管理；再介绍分级池、句柄池、并发同步和调试增强。平台示例采用 **C11、32 位 MCU、FreeRTOS**。并发原语和中断优先级规则必须按具体 RTOS 端口调整。

**数据说明**：本课给出可复算的容量公式和测量方法。没有真实目标板采样的数据会标记为理论预算或测量目标，不伪装成实测结果。

## 3. 技术概述

### 3.1 什么是内存池

内存池预先管理一段固定容量的存储空间，并按照确定的策略提供对象。

固定块池：

```
池存储
┌────────┬────────┬────────┬────────┬────────┐
│ block0 │ block1 │ block2 │ block3 │ block4 │
└────────┴────────┴────────┴────────┴────────┘
```

分配和释放通常只操作池元数据，不向系统申请新内存。

### 3.2 池的主要类型

|类型|分配对象|典型特征|
|---|---|---|
|固定块池|同尺寸块|简单、容量确定、无池内外部碎片|
|分级池|若干尺寸类别|尺寸灵活，可能有类别内部浪费|
|typed object pool|某一种 C 类型|接口类型安全、适合固定业务对象|
|句柄池|索引或句柄|避免长期保存裸指针，便于检测陈旧引用|
|arena|连续增长的临时对象|适合阶段性分配，通常批量释放|
|slab/cache|固定类型对象或尺寸类|常见于操作系统和高并发运行时|

### 3.3 内存池解决什么，不解决什么

内存池通常可以解决或改善：

- 通用堆外部碎片；
- 分配失败难以预测；
- 动态分配时延长尾；
- 小对象块头开销过大；
- 运行期内存来源不透明。

内存池不能自动解决：

- 池容量不足；
- 对象越界写；
- 重复释放；
- 悬空指针；
- 多任务数据竞争；
- DMA 与 CPU 同时访问；
- 错误的对象所有权。

**固定池提供容量边界，不提供对象使用正确性。**

### 空闲链表与位图的工程取舍

|维度|空闲链表|位图|
|---|---|---|
|常见分配操作|取链表头，O(1)|找空闲位，O(字数)|
|释放操作|写入 next 指针|计算索引并清位|
|用户块是否被用作元数据|常见会|不需要|
|越界写影响|可能破坏空闲链|可能破坏块内容，但通常不直接改空闲链|
|重复释放检测|需要额外状态或魔数|可检测对应位已空闲|
|时间上界|较容易|由池容量上界决定|
|额外 RAM|小|每块约 1 bit，另有对齐|

若要求严格、可审计的时间上界，可限制池容量并采用固定次数扫描，或使用字位扫描后明确推导最坏字数。

## 5. 底层原理与功能特性深度解析

### 5.1 容量与占用公式

定义：

- NN：池块数量；
- SS：每块存储跨度，已包含对齐后的块大小；
- AA：元数据对齐后大小；
- MM：位图字节数。

池的静态 RAM 近似为：

Mpool=N×S+M+A+MstatsMpool​=N×S+M+A+Mstats​

位图使用 32 位字时：

M=⌈N32⌉×4M=⌈32N​⌉×4

例如，64 个块，每块 272 B：

Mblocks=64×272=17408 BMblocks​=64×272=17408 B

位图：

M=⌈6432⌉×4=8 BM=⌈3264​⌉×4=8 B

还需要加入统计字段、临界区状态和结构体对齐。

### 5.2 对齐与块跨度

假设对象类型要求对齐 aa，对象有效尺寸为 uu，则块跨度：

S=align_up⁡(u,a)S=align_up(u,a)

若块内还有状态字或调试保护区，必须先计算完整布局，再按最大对齐要求对齐。

```
[ 前保护区 ][ 用户对象区 ][ 尾保护区 ][ 对齐填充 ]
```

池的每个块起始地址必须满足对象类型的对齐要求。仅仅“数组首地址对齐”还不够，**块跨度也必须是对齐的整数倍**。

### 5.3 位图池：数据结构与不变量

位图约定：

```
bit = 1：对象已分配
bit = 0：对象空闲
```

核心不变量：

allocated_count=∑i=0N−1bitmap[i]allocated_count=i=0∑N−1​bitmap[i]

每个释放请求必须满足：

1. 指针非空；
2. 指针位于池存储范围；
3. 指针恰好指向块起始位置；
4. 对应位当前为 1；
5. 释放不会导致统计下溢。

### 5.4 可复用的位图池实现

以下代码提供：

- 静态存储；
- 32 位位图；
- 边界和块边界检查；
- 重复释放检测；
- 容量与峰值统计；
- 临界区 hook；
- 失败统计。

**并发约束**：必须为目标平台实现 `POOL_CRITICAL_ENTER/EXIT`。如果只由单一任务调用，可使用无操作 hook；多个任务共享时必须使用正确的临界区或锁。ISR 是否允许调用，要依据具体端口另行实现，不能直接假设任务临界区适用于 ISR。

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <string.h>

/*
 * 必须由平台层提供。
 * 要求：保护 begin 到 end 内的元数据读改写。
 * ISR 版本应另设接口，避免误用任务级同步。
 */
#ifndef POOL_CRITICAL_ENTER
#define POOL_CRITICAL_ENTER() platform_pool_lock()
#define POOL_CRITICAL_EXIT()  platform_pool_unlock()
#endif

#define POOL_MAX_BLOCKS 64u
#define POOL_WORD_BITS  32u
#define POOL_WORD_COUNT ((POOL_MAX_BLOCKS + POOL_WORD_BITS - 1u) / \
                         POOL_WORD_BITS)

typedef struct {
    uint8_t *storage;
    size_t block_size;
    size_t block_count;

    uint32_t allocated[POOL_WORD_COUNT];

    size_t current_used;
    size_t peak_used;
    size_t allocation_failures;
    size_t invalid_frees;
} fixed_pool_t;

static uint32_t trailing_zero_count_nonzero(uint32_t value)
{
#if defined(__GNUC__) || defined(__clang__)
    return (uint32_t)__builtin_ctz(value);
#else
    uint32_t count = 0u;

    while ((value & 1u) == 0u) {
        value >>= 1u;
        ++count;
    }

    return count;
#endif
}

bool fixed_pool_init(fixed_pool_t *pool,
                     void *storage,
                     size_t block_size,
                     size_t block_count)
{
    if ((pool == NULL) ||
        (storage == NULL) ||
        (block_size == 0u) ||
        (block_count == 0u) ||
        (block_count > POOL_MAX_BLOCKS)) {
        return false;
    }

    if (((uintptr_t)storage % _Alignof(max_align_t)) != 0u) {
        return false;
    }

    if ((block_size % _Alignof(max_align_t)) != 0u) {
        return false;
    }

    if (block_count > SIZE_MAX / block_size) {
        return false;
    }

    *pool = (fixed_pool_t) {
        .storage = storage,
        .block_size = block_size,
        .block_count = block_count
    };

    memset(pool->allocated, 0, sizeof(pool->allocated));
    return true;
}

void *fixed_pool_alloc(fixed_pool_t *pool)
{
    if ((pool == NULL) ||
        (pool->storage == NULL) ||
        (pool->block_size == 0u) ||
        (pool->block_count == 0u)) {
        return NULL;
    }

    void *result = NULL;

    POOL_CRITICAL_ENTER();

    const size_t word_count =
        (pool->block_count + POOL_WORD_BITS - 1u) / POOL_WORD_BITS;

    for (size_t word_index = 0u;
         word_index < word_count;
         ++word_index) {
        const size_t base = word_index * POOL_WORD_BITS;
        const size_t remaining = pool->block_count - base;
        const uint32_t valid_bits =
            (remaining >= POOL_WORD_BITS)
                ? UINT32_MAX
                : ((1u << remaining) - 1u);

        const uint32_t free_bits =
            ~pool->allocated[word_index] & valid_bits;

        if (free_bits == 0u) {
            continue;
        }

        const uint32_t bit =
            trailing_zero_count_nonzero(free_bits);
        const size_t block_index =
            base + (size_t)bit;

        pool->allocated[word_index] |= (1u << bit);
        ++pool->current_used;

        if (pool->current_used > pool->peak_used) {
            pool->peak_used = pool->current_used;
        }

        result = pool->storage +
                 block_index * pool->block_size;
        break;
    }

    if (result == NULL) {
        if (pool->allocation_failures != SIZE_MAX) {
            ++pool->allocation_failures;
        }
    }

    POOL_CRITICAL_EXIT();

    return result;
}

bool fixed_pool_free(fixed_pool_t *pool, void *pointer)
{
    if ((pool == NULL) ||
        (pointer == NULL) ||
        (pool->storage == NULL) ||
        (pool->block_size == 0u) ||
        (pool->block_count == 0u)) {
        return false;
    }

    const uintptr_t base = (uintptr_t)pool->storage;
    const uintptr_t address = (uintptr_t)pointer;

    if (pool->block_count > SIZE_MAX / pool->block_size) {
        return false;
    }

    const size_t total_size =
        pool->block_count * pool->block_size;

    if ((address < base) ||
        ((address - base) >= total_size)) {
        POOL_CRITICAL_ENTER();

        if (pool->invalid_frees != SIZE_MAX) {
            ++pool->invalid_frees;
        }

        POOL_CRITICAL_EXIT();
        return false;
    }

    const size_t offset = (size_t)(address - base);

    if ((offset % pool->block_size) != 0u) {
        POOL_CRITICAL_ENTER();

        if (pool->invalid_frees != SIZE_MAX) {
            ++pool->invalid_frees;
        }

        POOL_CRITICAL_EXIT();
        return false;
    }

    const size_t block_index = offset / pool->block_size;
    const size_t word_index = block_index / POOL_WORD_BITS;
    const uint32_t bit_index =
        (uint32_t)(block_index % POOL_WORD_BITS);
    const uint32_t mask = 1u << bit_index;

    bool released = false;

    POOL_CRITICAL_ENTER();

    if ((pool->allocated[word_index] & mask) != 0u) {
        pool->allocated[word_index] &= ~mask;

        if (pool->current_used > 0u) {
            --pool->current_used;
            released = true;
        }
    }

    if (!released && (pool->invalid_frees != SIZE_MAX)) {
        ++pool->invalid_frees;
    }

    POOL_CRITICAL_EXIT();

    return released;
}

bool fixed_pool_get_stats(const fixed_pool_t *pool,
                          size_t *current,
                          size_t *peak,
                          size_t *failures,
                          size_t *invalid_frees)
{
    if ((pool == NULL) ||
        (current == NULL) ||
        (peak == NULL) ||
        (failures == NULL) ||
        (invalid_frees == NULL)) {
        return false;
    }

    POOL_CRITICAL_ENTER();

    *current = pool->current_used;
    *peak = pool->peak_used;
    *failures = pool->allocation_failures;
    *invalid_frees = pool->invalid_frees;

    POOL_CRITICAL_EXIT();

    return true;
}
```

### 5.5 实现代码的边界与安全审查

上面的代码是适合进一步工程集成的框架，但仍有明确边界：

- 它使用 `_Alignof(max_align_t)`，需要 C11 编译模式。
- `block_size` 必须已经按目标对象最大对齐要求调整。
- 池内并发访问必须由 hook 正确串行化。
- 如果 `block_count` 小于 32，`1u << remaining` 的 `remaining` 范围有效；`remaining` 不会超过 32。对于 `remaining == 32`，代码单独使用 `UINT32_MAX`，避免移位 32 位。
- 指针转整数与地址算术依赖目标 ABI；这是嵌入式实现代码，不是纯抽象算法证明。
- 元数据损坏仍可能导致错误行为；高完整性系统可增加 CRC、保护区和状态码。
- 池对象本身应具有静态或足够长的生命周期，不能让 `pool` 结构先于 `storage` 失效。

### 5.6 典型的静态 typed pool

通用 `void *` 池便于复用，但不提供类型安全。业务对象可以使用 typed wrapper：

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

typedef struct {
    uint32_t id;
    uint16_t length;
    uint16_t type;
    uint8_t payload[128];
} message_t;

#define MESSAGE_POOL_COUNT 16u

typedef union {
    max_align_t alignment;
    message_t object;
} message_slot_t;

static message_slot_t g_message_slots[MESSAGE_POOL_COUNT];
static uint32_t g_message_bitmap[1];

message_t *message_acquire(void)
{
    void *slot = fixed_pool_alloc(&g_message_pool);

    if (slot == NULL) {
        return NULL;
    }

    message_t *message = slot;

    *message = (message_t) {
        .id = 0u,
        .length = 0u,
        .type = 0u
    };

    return message;
}

bool message_release(message_t *message)
{
    return fixed_pool_free(&g_message_pool, message);
}
```

实际工程中，`g_message_pool` 应用静态存储，并在系统初始化阶段绑定 `g_message_slots`。若使用上述通用池实现，槽位跨度需确保为 `max_align_t` 的整数倍；typed wrapper 也可直接自实现位图以减少无关抽象。

**类型化接口可减少把错误类型归还给池的风险，但不能阻止调用者保存悬空别名。**

### 5.7 空闲链表池的关键原理

空闲块本身保存链表链接：

```
typedef struct free_node {
    struct free_node *next;
} free_node_t;
```

分配：

```
head = head->next
return old_head
```

释放：

```
block->next = head
head = block
```

优点是通常 O(1)。主要问题：

- 用户越界写可能覆盖 `next`；
- 重复释放可能形成环；
- 释放任意地址会使链表指向非法位置；
- 释放后的对象前几个字节承担分配器元数据职责；
- 并发更新需要正确同步。

空闲链表适合性能敏感且对象来源可信的系统。对外部输入影响的对象池，位图或带状态的句柄池通常更容易审计。

### 5.8 任务栈池与动态对象池不同

RTOS 任务栈可以从静态数组池获得，但其特殊要求包括：

- 目标 ABI 对齐；
- 足够容量；
- 栈填充与水位监控；
- 删除任务时的释放时机；
- 不能把正在运行的任务栈归还；
- 任务控制块与栈可能具有不同生命周期。

因此，**不能仅因为任务栈使用固定块池，就按普通报文池的规则释放它。**

## 6. 性能量化分析

### 6.1 时间复杂度与可证明上界

对位图池，分配最多扫描：

W=⌈N32⌉W=⌈32N​⌉

个位图字。

若 N=64N=64，最多检查 2 个字；若 N=256N=256，最多检查 8 个字。

这给出算法层面的上界，不包括：

- 临界区等待；
- 中断抢占；
- 总线争用；
- 编译器生成代码差异；
- 原子操作或锁实现成本。

位图分配的扫描次数由池容量静态确定，适合做 WCET 评估。

### 6.2 固定池容量推导

某个对象池的数量应从业务并发模型推导：

Nrequired=Nproducer-held+Nqueue+Nconsumer-held+NDMA-in-flight+Nretry+NmarginNrequired​=Nproducer-held​+Nqueue​+Nconsumer-held​+NDMA-in-flight​+Nretry​+Nmargin​

例如：

|状态|最大数量|
|---|---|
|生产者正在构造|2|
|队列中等待|8|
|消费者正在处理|2|
|DMA 正在使用|2|
|重试暂存|1|
|安全余量|3|
|总计|18|

应配置至少 18 个对象，再根据失效模式和系统级安全裕度决定是否增加。

**“测试时没耗尽”不是容量推导方法。**

### 6.3 RAM 与内部浪费示例

假设报文有效载荷最多 250 B，结构体和字段共计请求 258 B；按 8 B 对齐得到每块 264 B。若池容量 18：

Mblocks=18×264=4752 BMblocks​=18×264=4752 B

位图：

Mbitmap=⌈1832⌉×4=4 BMbitmap​=⌈3218​⌉×4=4 B

再加入控制结构和对齐，约略为 4.7 KiB。

若常见实际报文只有 60 B，单块的空闲部分不会自动提供给其他对象。这是池的**尺寸类别内部浪费**。

解决方式可以是：

- 分成小报文池和大报文池；
- 用变长块链表，但增加复杂度；
- 使用多段报文，不要求每条报文占一个大块；
- 在非实时路径使用受控堆。

### 6.4 位图和空闲链表的空间成本

N 个块、32 位位图：

Mbitmap=4×⌈N32⌉Mbitmap​=4×⌈32N​⌉

每个块一个指针的链表元数据，假设 32 位地址：

Mlist-link=4NMlist-link​=4N

但空闲链表常将链接字段放在块内部，不一定额外增加总占用；代价是空闲块不能保留原有内容，且越界破坏风险更高。

### 6.5 测量方法

使用 DWT 或目标平台计时器分别测：

- 空闲池分配；
- 池满时分配失败；
- 正常释放；
- 非法释放拒绝；
- 临界区等待；
- 最差扫描次数；
- 真实中断干扰下的分布。

结果至少报告：

```
最低值
中位数
P99
最大观测值
测试池容量
编译器版本和选项
中断配置
是否存在并发竞争
```

如果测量 64 块池只使用 1 块，不能据此声称其最坏分配时延已测出。

## 8. 工程最佳实践

### 8.1 先建立池容量模型

对每种对象分别估算：

- 最大生产速度；
- 消费最坏延迟；
- 最大队列深度；
- 最大并行 DMA 数；
- 重试和异常保留数；
- 安全余量；
- 池耗尽时的业务策略。

若生产速率为 RpRp​，处理服务速率为 RcRc​，且 Rp>RcRp​>Rc​，那么池最终必然耗尽。增大池只能延迟耗尽，不会修复服务能力不足。

### 8.2 池耗尽策略必须是业务决策

常见策略：

|策略|适用场景|风险|
|---|---|---|
|丢弃新对象|遥测、低优先级日志|数据丢失|
|覆盖最旧对象|最新状态优先|事件历史丢失|
|降级功能|可选诊断、非关键服务|逻辑复杂|
|阻塞等待|任务上下文，且允许阻塞|死锁、优先级影响|
|返回错误|同步 API|调用方必须处理|
|触发安全状态|安全关键资源耗尽|影响可用性|

### 8.3 同步策略

|使用方式|可选同步|注意事项|
|---|---|---|
|单任务独占|无锁|必须证明没有其他访问者|
|多任务共享|mutex 或临界区|分析锁持有时间和优先级反转|
|ISR 与任务共享|专用 ISR API、原子或短临界区|按中断优先级规则设计|
|多核共享|原子操作或跨核锁|本核关中断通常不够|
|DMA 与 CPU 共享|不能只靠软件锁|还需 DMA 状态、缓存与所有权协议|

### 8.4 统计字段

建议每个池至少记录：

```
capacity
current_used
peak_used
allocation_failures
invalid_frees
double_free_attempts
largest_free_run（若为连续位图池）
```

计数器溢出策略要明确。对于诊断计数，常见策略是饱和到 `SIZE_MAX`，而不是回绕后误报低值。

### 8.5 错误处理规则

- 池初始化失败时，不启动依赖该池的任务。
- 分配失败返回错误，不返回未初始化块。
- 释放失败不得静默忽略。
- ISR 不允许等待池可用。
- 关键池的耗尽应有速率受限的告警。
- 故障处理路径不能依赖同一个已经耗尽的池。

### 8.6 map 文件与链接期约束

检查：

- 池存储处于正确 SRAM；
- DMA 池不在 DMA 不可达区域；
- 多池合计没有覆盖任务栈或 `.noinit`；
- 自定义 section 有正确对齐；
- 池实际大小与预算一致。

```
arm-none-eabi-size firmware.elf
arm-none-eabi-nm -S --size-sort firmware.elf
arm-none-eabi-objdump -h firmware.elf
```

在 CI 中可对关键池尺寸设置阈值，超限即失败。

## 9. 常见错误与避坑指南

### 9.1 错误一：假设池块天然满足类型对齐

错误代码：

```
static unsigned char storage[10 * 12];

struct dma_desc *desc =
    (struct dma_desc *)(storage + index * 12);
```

根因：

- 数组起点和块跨度都可能不满足 `struct dma_desc` 对齐。
- 非对齐访问可能导致异常、性能退化或未定义行为。

正确实现：

```
typedef struct {
    _Alignas(struct dma_desc)
    unsigned char bytes[
        POOL_COUNT * POOL_BLOCK_STRIDE
    ];
} aligned_storage_t;
```

`POOL_BLOCK_STRIDE` 必须是 `sizeof(struct dma_desc)` 按 `_Alignof(struct dma_desc)` 向上对齐后的值。

### 9.2 错误二：释放池内偏移地址

错误代码：

```
unsigned char *payload = pool_alloc(&pool);
pool_free(&pool, payload + 4u);
```

根因：

- 池要求原始块首地址；
- 偏移地址不是池分配接口返回的块地址。

正确实现：

```
unsigned char *block = pool_alloc(&pool);
unsigned char *payload = block + HEADER_SIZE;

/* 使用 payload，但释放原始 block。 */
pool_free(&pool, block);
```

更好的 API 是返回包含头部和载荷的 typed object，避免业务代码自己偏移和回溯。

### 9.3 错误三：重复释放同一块

错误代码：

```
pool_free(&pool, block);
pool_free(&pool, block);
```

根因：

- 第二次释放可能把同一块再次加入空闲链；
- 两个调用者随后获得同一块，造成并发覆盖。

正确做法：

```
if (!pool_free(&pool, block)) {
    report_pool_invariant_fault();
}
```

业务层还应清除所有权变量：

```
pool_free(&pool, owned_block);
owned_block = NULL;
```

清空一个指针不能消除别名，但可以减少同一所有者误用。

### 9.4 错误四：把池块交给通用 `free()`

错误代码：

```
void *block = fixed_pool_alloc(&pool);
free(block);
```

根因：

- 块不一定来自 C 库分配器；
- `free()` 会把池地址当作堆块头解析。

正确做法：

```
fixed_pool_free(&pool, block);
```

分配与释放必须通过同一资源域。

### 9.5 错误五：ISR 中等待池可用

错误代码：

```
void USART_IRQHandler(void)
{
    event_t *event = pool_alloc_wait(&event_pool, WAIT_FOREVER);
    /* ... */
}
```

根因：

- ISR 不能阻塞等待任务释放对象；
- 可能死锁或破坏调度器状态；
- 中断延迟无界。

正确实现：

```
void USART_IRQHandler(void)
{
    event_t *event = event_pool_try_alloc_from_isr();

    if (event == NULL) {
        event_overflow_counter_increment_from_isr();
        clear_or_drain_hardware_status();
        return;
    }

    fill_event_from_registers(event);

    if (!event_queue_send_from_isr(event)) {
        event_pool_free_from_isr(event);
        event_overflow_counter_increment_from_isr();
    }
}
```

ISR 版本必须由平台和 RTOS 明确支持，不能直接复用任务锁。

### 9.6 错误六：DMA 完成前归还池块

错误代码：

```
event_t *event = pool_alloc(&pool);
dma_start(event, sizeof(*event));
pool_free(&pool, event);
```

根因：

- DMA 仍持有对象地址；
- 池可能立即把相同块分配给其他任务。

正确实现：

```
FREE → CPU_OWNED → DMA_OWNED → COMPLETE → FREE
```

释放动作必须发生在确认 DMA 不再访问该块之后。

### 9.7 错误七：只按平均负载配置池容量

错误思路：

```
平均同时使用 3 个对象，所以池配 4 个即可。
```

根因：

- 峰值并发由最坏处理延迟、突发输入和重试决定；
- 平均值不能覆盖瞬态积压。

正确容量依据：

Npool≥Nqueued+Nin-flight+Nheld+NmarginNpool​≥Nqueued​+Nin-flight​+Nheld​+Nmargin​

风险影响：

- 偶发池耗尽；
- 故障集中发生于启动、重连、总线拥塞等高负载阶段。

## 10. 多机制组合使用方案

### 10.1 固定池 + 队列 + 所有权转移

典型架构：

```
FREE_POOL
   │ acquire
   ▼
PRODUCER_OWNED
   │ queue send succeeds
   ▼
READY_QUEUE
   │ queue receive
   ▼
CONSUMER_OWNED
   │ process complete
   ▼
FREE_POOL
```

所有权规则：

- 申请成功后，生产者拥有对象。
- 队列发送失败，生产者仍拥有对象，必须归还。
- 队列发送成功，所有权转移给接收方。
- 接收方处理期间不得由生产者修改。
- 若启动 DMA，接收方必须等 DMA 完成后再归还。

### 10.2 FreeRTOS 风格代码框架

以下示例使用固定块池接口；队列传递指针。它依赖平台提供正确的池锁和 FreeRTOS 静态队列支持。

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

#include "FreeRTOS.h"
#include "queue.h"

#define EVENT_POOL_COUNT  16u
#define EVENT_QUEUE_DEPTH 16u
#define EVENT_DATA_SIZE   128u

typedef struct {
    uint16_t type;
    uint16_t length;
    uint32_t timestamp;
    uint8_t data[EVENT_DATA_SIZE];
} event_t;

typedef struct {
    _Alignas(max_align_t)
    uint8_t storage[
        EVENT_POOL_COUNT *
        ((sizeof(event_t) + _Alignof(max_align_t) - 1u) /
         _Alignof(max_align_t) *
         _Alignof(max_align_t))
    ];
} event_storage_t;

static event_storage_t g_event_storage;
static fixed_pool_t g_event_pool;

static StaticQueue_t g_event_queue_control;
static uint8_t g_event_queue_storage[
    EVENT_QUEUE_DEPTH * sizeof(event_t *)
];
static QueueHandle_t g_event_queue;

bool event_system_init(void)
{
    const size_t stride =
        ((sizeof(event_t) + _Alignof(max_align_t) - 1u) /
         _Alignof(max_align_t)) *
        _Alignof(max_align_t);

    if (!fixed_pool_init(&g_event_pool,
                         g_event_storage.storage,
                         stride,
                         EVENT_POOL_COUNT)) {
        return false;
    }

    g_event_queue = xQueueCreateStatic(
        EVENT_QUEUE_DEPTH,
        sizeof(event_t *),
        g_event_queue_storage,
        &g_event_queue_control);

    return g_event_queue != NULL;
}

event_t *event_acquire(void)
{
    event_t *event = fixed_pool_alloc(&g_event_pool);

    if (event == NULL) {
        return NULL;
    }

    *event = (event_t) {
        .type = 0u,
        .length = 0u,
        .timestamp = 0u
    };

    return event;
}

/*
 * 调用约束：
 * 成功发送后，调用方不得继续访问 event。
 * 失败时，调用方仍拥有 event。
 */
bool event_submit(event_t *event, TickType_t wait)
{
    if ((event == NULL) ||
        (event->length > EVENT_DATA_SIZE)) {
        return false;
    }

    return xQueueSend(g_event_queue,
                      &event,
                      wait) == pdPASS;
}

void event_consumer_task(void *argument)
{
    (void)argument;

    for (;;) {
        event_t *event = NULL;

        if (xQueueReceive(g_event_queue,
                          &event,
                          portMAX_DELAY) != pdPASS) {
            continue;
        }

        process_event(event);

        if (!fixed_pool_free(&g_event_pool, event)) {
            report_pool_invariant_fault();
        }
    }
}
```

### 10.3 代码需要进一步补齐的工程约束

上面示例展示组合模式，不是完整业务模块，还应加入：

- `event_submit()` 成功后由 API 层清除调用者所有权变量，或用二级指针表达转移；
- 队列满时的统一释放责任；
- 对非法或非本池指针的成员资格校验；
- ISR 专用提交函数；
- 事件时间戳来源和原子性；
- 初始化失败后的启动策略；
- 队列深度与池块数量一致性的配置断言；
- DMA 事件的延迟释放逻辑；
- FreeRTOS 队列静态存储的对齐和端口要求。

更明确的所有权接口：

```
bool event_submit_owned(event_t **owned, TickType_t wait)
{
    if ((owned == NULL) || (*owned == NULL)) {
        return false;
    }

    event_t *event = *owned;

    if (!event_submit(event, wait)) {
        return false;
    }

    *owned = NULL;
    return true;
}
```

失败时指针保留，成功时置空。调用者仍需遵守不保留其他别名的约定。

### 10.4 多尺寸池协同

常见设计：

```
small pool: 64 B × 32
medium pool: 256 B × 16
large pool: 1536 B × 4
```

选择规则：

```
请求 ≤ 64 B    → small
请求 ≤ 256 B   → medium
请求 ≤ 1536 B  → large
否则           → 失败或专用大缓冲区
```

这降低了小对象占用大块的浪费，但引入了：

- 各池独立耗尽；
- 池间不能自动借用容量；
- 需要明确升级、降级和回退规则；
- 不同池可能具有不同 DMA 和缓存属性。

## 11. 工业级实际案例分析

以下为常见工业系统的设计场景与容量推演，参数为示例，不代表特定产品实测。

### 11.1 案例一：CAN/CAN FD 接收事件池

#### 需求

- 多个接收中断源；
- 接收事件异步送入高优先级任务；
- ISR 不能阻塞；
- 队列满时不能覆盖已提交事件。

#### 容量推导

假设：

- 消费队列最大 24 个事件；
- ISR 暂存或刚取出事件最多 2 个；
- 消费者当前持有 1 个；
- 安全余量 5 个。

N=24+2+1+5=32N=24+2+1+5=32

#### 架构

```
ISR
├── 非阻塞申请事件
├── 读取硬件帧
├── 送入静态队列
└── 失败时丢弃并累计计数

通信任务
├── 取出事件
├── 校验与路由
└── 归还池块
```

#### 设计要点

- ISR 分配失败时必须及时清除或排空硬件状态。
- 不能在 ISR 内格式化日志。
- 丢弃计数应使用目标平台支持的原子或短临界区。
- 队列和池容量需要一起核算。
- 若高优先级中断不能被 RTOS 临界区屏蔽，应将池元数据操作限制在更低优先级，或采用专门的无锁设计并进行充分验证。

### 11.2 案例二：UDP 报文分级池

#### 需求

- 小控制报文常见；
- 大诊断报文偶尔出现；
- 通信任务具有短时突发；
- 不允许大量小报文占据大块池。

#### 方案

```
descriptor pool: 32 B × 32
small payload:   128 B × 24
large payload:   1536 B × 8
```

报文描述符包含：

```
typedef struct {
    uint16_t length;
    uint16_t flags;
    uint8_t *payload;
    uint8_t pool_class;
} packet_desc_t;
```

生命周期：

```
申请描述符
  ↓
按长度选载荷池
  ↓
接收数据
  ↓
队列转移所有权
  ↓
处理结束后先归还载荷，再归还描述符
```

#### 风险控制

- 如果载荷分配成功、描述符分配失败，必须归还载荷。
- 如果描述符发布失败，发布者仍负责归还全部资源。
- `pool_class` 应是受校验枚举，不应直接作为未校验数组索引。
- 不能仅按单包上限核算，还要按连接数、队列深度和重传缓存核算。

### 11.3 案例三：运动控制系统的控制事件池

#### 需求

- 10 kHz 控制循环；
- 控制回调不允许阻塞；
- 后台诊断产生可丢弃事件；
- 故障事件需要高于普通诊断事件的保留优先级。

#### 方案

```
critical pool: 4 个故障事件
normal pool:   24 个诊断事件
control path:  静态状态结构，不使用池
```

#### 设计要点

- 控制状态本身不通过通用事件池分配。
- 故障池与普通池分开，避免普通日志耗尽关键事件。
- 池满时普通事件丢弃，关键故障采用专用静态槽位或覆盖式最新状态记录。
- 若事件需要 DMA 输出，保持对象直到 DMA 完成。
- 通过 DWT 测量控制循环在池竞争和无竞争条件下的延迟差异。

## 12. 高频问题深度答疑

### 12.1 内存池是否能彻底消除碎片？

固定块池消除的是**池内部的跨块外部碎片**：一个空闲块不会被分割成多段后无法使用。

它仍有：

- 块内部尺寸浪费；
- 多尺寸池之间的空闲容量不均；
- 池容量长期保留；
- 如果每个池支持变长分配，仍可能有碎片。

### 12.2 空闲链表池一定比位图快吗？

不一定。

空闲链表常见操作数量少，但仍有：

- 临界区成本；
- 指针加载的内存延迟；
- 锁争用；
- 内存破坏检查；
- 实际编译器代码差异。

位图池扫描上界明确。小容量池的位图操作可能非常快，也更易检测重复释放。

必须在目标平台测量，不要仅凭 O(1) 与 O(N) 的符号比较。

### 12.3 池块释放后要不要清零？

取决于安全和性能要求。

清零优点：

- 减少旧数据残留；
- 降低部分未初始化使用问题；
- 可能满足敏感数据处理要求。

代价：

- 释放时延与块大小成正比；
- 临界区内清零会延长中断或锁延迟；
- 增加总线带宽占用。

更好的做法通常是：

1. 在离开临界区后清零；
2. 仅在下一次分配时清理业务字段；
3. 对密钥等敏感对象使用专门安全清零；
4. 不把普通 `memset()` 当成不可优化的安全擦除保证。

### 12.4 池满时等待还是失败？

- ISR：只能非阻塞失败。
- 有严格实时期限的任务：通常返回失败或降级。
- 后台任务：可短时间等待，但必须验证不会造成死锁。
- 等待者不能同时持有会阻止释放对象的锁。
- 若生产速度长期超过消费速度，等待只会把压力转移到上游队列。

### 12.5 是否可以在池块开头存放 `next` 指针？

可以，但需要注意：

- 空闲时块内容被用于链表元数据；
- 释放时原对象内容失效；
- 越界写可能破坏链表；
- 最小块大小必须至少容纳节点结构；
- 对齐要满足指针要求；
- 并发更新要正确同步。

这是高性能实现常见模式，但要配合成员资格、状态和完整性校验。

### 12.6 为什么释放指针的范围检查可能不够？

范围检查只能证明地址数值位于池区间，不能证明：

- 指针是当前对象的有效来源；
- 块当前处于已分配状态；
- 调用者没有越权；
- 指针没有来自另一池但地址区间碰巧重叠。

位图池还能检查块边界和分配位，但无法识别所有逻辑错误。高完整性场景可使用带池 ID 和代数的句柄。

### 12.7 内存池和对象缓存有什么不同？

概念有重叠：

- 内存池管理固定块或尺寸类别；
- 对象缓存常针对同一类型，可能在释放时执行构造/析构、初始化或回收；
- OS slab allocator 往往同时包含每 CPU 缓存、批量分配和同步策略。

在 C 中通常没有语言级构造函数，typed object pool 可提供 `init/reset/destroy` 回调来建立对象不变量。

## 13. 课程核心总结

### 核心要点

1. **内存池的首要价值是容量和生命周期可控，不只是速度。**
2. 固定块池适合固定尺寸、高频率、可推导并发上限的对象。
3. 空闲链表通常操作少，但元数据易受越界破坏。
4. 位图便于检测重复释放，时间上界可由池容量推导。
5. 池块跨度必须同时满足对象尺寸和对齐要求。
6. 池满处理是业务策略，不是分配器内部细节。
7. 跨任务传递应以队列和明确所有权协议为边界。
8. DMA 使用中的对象不能在硬件访问结束前释放。
9. 多尺寸池减少块内浪费，但增加各池独立耗尽风险。
10. 水位统计和峰值测试不能替代容量推导。

### 性能排序

常见操作管理成本趋势：

```
静态对象
    ≈ 固定池空闲链表
    ≤ 小型位图池
    < 需要搜索或合并的通用堆
```

此排序不是所有实现的严格结论。实际性能受锁、中断、总线和实现影响。

### 通用选型结论

- 尺寸、数量可推导：固定池。
- 多种固定尺寸：分级池。
- 高性能且来源可信：空闲链表池。
- 更重视诊断与非法释放检测：位图池或句柄池。
- 生命周期成批结束：arena。
- 尺寸高度变化且非实时：受控通用堆。
- 硬实时路径：预分配或证明分配操作和同步均有上界。

## 14. 快速参考速查表

### 池型选型表

|需求|推荐|
|---|---|
|固定尺寸、高频对象|固定块池|
|需要检测重复释放|位图池|
|极短且可证明的分配路径|空闲链表池|
|多种常见尺寸|分级池|
|生命周期批量结束|arena|
|长期保存、引用复杂|句柄池|
|DMA 专用对象|专用区域池|
|ISR 使用|无等待、明确支持 ISR 的池接口|

### 关键不变量表

|不变量|检查方式|
|---|---|
|当前使用数不超过容量|分配和释放时断言|
|每个块最多一个所有者|状态机、句柄或调试状态|
|释放地址必须是块首地址|范围和跨度检查|
|空闲块与已用块互斥|位图或显式状态|
|队列对象总数受池容量约束|容量公式与运行监测|
|DMA 使用期间对象不可释放|所有权状态机|
|统计不回绕|饱和计数或更宽类型|

### 每个池的最低监测集

|指标|用途|
|---|---|
|容量|静态配置|
|当前使用数|即时负载|
|峰值使用数|容量验证|
|分配失败次数|发现容量不足|
|非法释放次数|发现调用契约问题|
|最大连续空闲块|仅适用于变长或连续池|
|分配和释放周期|时延评估|
|调用来源|定位异常增长|

## 16. 实践与进阶路径

### 第一阶段：实现单线程位图池

实现：

- 32 个固定块；
- 分配和释放；
- 非法指针检查；
- 重复释放检测；
- 当前和峰值统计。

测试：

- 全部分配后失败；
- 全部释放后重新分配；
- 乱序释放；
- 空指针释放；
- 池外指针释放；
- 块内偏移指针释放；
- 重复释放。

### 第二阶段：加入并发保护

分别实现：

- 单任务无锁版本；
- 多任务互斥版本；
- ISR 非阻塞版本。

验证：

- 多任务并行申请和释放；
- 高优先级任务对低优先级持锁任务的影响；
- ISR 优先级与 RTOS 临界区规则；
- 临界区最大长度。

### 第三阶段：实现 typed pool 和队列所有权转移

对象应经过：

```
FREE → PRODUCER → QUEUED → CONSUMER → FREE
```

每个状态转移都设置断言，并测试：

- 队列满；
- 消费者异常退出；
- 提交失败；
- 重复归还；
- DMA 延迟完成。

### 第四阶段：构造压力负载

记录：

- 当前使用数；
- 峰值使用数；
- 失败次数；
- 分配和释放周期；
- 队列深度；
- 丢弃率。

负载至少覆盖：

- 稳态；
- 最大输入突发；
- 消费者阻塞；
- 连接重试；
- DMA 延迟；
- 低内存异常路径。

### 第五阶段：故障注入与代码审查

在每个分配点注入失败，检查：

- 池使用数恢复到基线；
- 对象状态不被部分提交；
- 失败路径不递归分配；
- 所有权回到明确的模块；
- 关键系统进入预期降级状态。

### 进阶方向

- TLSF 或 buddy allocator 的源码与 WCET 分析；
- 带代数的索引句柄，检测陈旧引用；
- per-task/per-core cache 与跨核回收；
- DMA 缓存一致性和非缓存区域设计；
- MPU 保护区与池边界防护；
- 形式化状态机验证；
- 将池容量、峰值和分配失败纳入 CI 与现场遥测。
