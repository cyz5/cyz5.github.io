
嵌入式系统中的“栈、堆、全局区、常量区、代码段”，实际上涉及三个不同层面：

- **C 语言层面**：对象的存储期、作用域、链接属性、生命周期与可修改性。
- **编译链接层面**：目标文件的 section、符号、重定位，以及链接后的地址分配。
- **硬件运行层面**：Flash、SRAM、TCM、外部 RAM 的物理特性，以及启动代码、DMA、MPU 对这些区域的使用规则。

**高级工程师必须能够把这三个层面连成一条可验证的链：一行 C 声明 → ELF 中的符号与段 → 链接地址 → 启动行为 → 运行时访问路径 → 故障与性能表现。**

本课以 **GNU Arm Embedded 工具链、ELF、STM32F407VG、Cortex-M4F、裸机/FreeRTOS** 为主要分析环境，同时说明结论在其他平台上的适用边界。

**数据说明**：本课给出明确的平台参数、可复算的容量与周期计算、可执行的测量方法。没有实际硬件采样的项目明确标注为“预算示例”或“理论下界”，不将其表述为实测结果。实际周期数必须绑定芯片配置、编译选项、链接位置和测试条件。

- 建立栈、堆、静态区的运行监测与故障取证机制。

### 能够设计

- 设计具有容量上界的工业控制器内存布局。
- 设计启动期分配、运行期无动态分配的内存策略。
- 设计面向 DMA、多任务和异常恢复的内存所有权协议。
- 设计链接期、启动期、运行期三层内存约束与验证体系。

## 3. 技术概述

### 3.1 “五大内存分区”是一种工程抽象

常见描述如下：

```
代码区：机器指令
常量区：只读数据
全局区：全局变量和静态变量
堆：动态分配对象
栈：函数调用和局部临时状态
```

这个描述便于入门，但不足以指导工业设计。

更准确的模型是：

|层面|关注点|典型概念|
|---|---|---|
|C 语言|对象何时存在、能否修改、在哪里可见|自动存储期、静态存储期、分配存储期|
|目标文件|编译器如何组织代码和数据|`.text`、`.rodata`、`.data`、`.bss`|
|链接布局|对象最终放在哪里|Flash、SRAM、CCM、外部 RAM|
|启动初始化|运行前如何建立初始状态|复制 `.data`、清零 `.bss`|
|运行机制|对象由谁管理|调用栈、分配器、固定块池|
|硬件保护|什么主体能进行什么访问|MPU、总线矩阵、DMA 可达性|

**栈和堆通常不是由 C 标准规定的物理分区；它们是实现自动存储期和动态分配的一类常见机制。**

例如，优化后的自动变量可能完全保存在寄存器中，甚至被消除。

### 3.2 C 对象的存储期

C11/C17 讨论四种存储期：

|存储期|典型对象|生命周期|
|---|---|---|
|自动存储期|普通块作用域局部对象|通常从进入所在块到离开该块|
|静态存储期|文件作用域对象、`static` 局部对象|整个程序执行期|
|线程存储期|`_Thread_local` 对象|对应线程执行期|
|分配存储期|`malloc()` 等分配得到的对象|从分配成功到释放|

对于变长数组，生命周期规则还与其声明执行有关。

**作用域回答“名字在哪里可见”，存储期回答“对象什么时候存在”，链接属性回答“多个声明是否指向同一个实体”。三者不能混用。**

### 3.3 MCU 上的典型物理布局

以 STM32F407VG 为例：

|存储器|地址范围概念|容量|主要特点|
|---|---|---|---|
|主 Flash|从 `0x08000000` 开始|1 MiB|保存程序和只读数据|
|SRAM1 + SRAM2|从 `0x20000000` 开始|合计 128 KiB|通用数据、栈、DMA 缓冲区|
|CCM RAM|从 `0x10000000` 开始|64 KiB|CPU 数据访问，普通 DMA 不可达|

典型布局：

```
Flash
├── 异常向量表
├── .text
├── .rodata
├── 异常展开表等只读元数据
└── .data 的初始值副本

SRAM
├── .data
├── .bss
├── .noinit
├── 固定块池 / 通信缓冲区
├── 可选堆区域
├── 未分配空间
└── MSP 栈区域

CCM RAM
├── 可选任务栈
├── CPU 私有工作区
└── 算法中间数据
```

这只是一个设计方案。**物理布局由链接脚本和运行时实现共同决定，不存在通用且固定的“堆一定向上、栈一定紧邻堆向下”的规则。**

## 4. 核心特性横向对比

### 4.1 五类区域对比

|维度|栈|堆|全局/静态数据|常量数据|代码|
|---|---|---|---|---|---|
|典型内容|调用现场、溢出寄存器、局部数组|动态对象|全局变量、静态局部变量|查找表、字面量|指令|
|常见 ELF 表达|不一定有对应实体 section|不一定有对应实体 section|`.data`、`.bss`|`.rodata` 等|`.text` 等|
|生命周期|与调用或任务相关|由分配/释放控制|整个程序执行期|通常整个程序执行期|程序执行期|
|管理者|ABI、编译器、RTOS|分配器|链接器、启动代码|编译器、链接器|编译器、链接器|
|容量确定性|需要调用深度分析|取决于分配模型|链接期可确定|链接期可确定|链接期可确定|
|碎片问题|通常无外部碎片|可能有|无运行期碎片|无运行期碎片|无运行期碎片|
|常见风险|溢出、悬空指针|泄漏、碎片、重复释放|并发访问、静态占用过大|非法修改、位置误判|错误执行权限、重定位遗漏|
|常见位置|SRAM/TCM|SRAM/外部 RAM|SRAM/保留 RAM|Flash/SRAM|Flash/可执行 RAM|

### 4.2 相同 C 类型，不同内存行为

```
#include <stdint.h>

uint32_t g_zero;                    /* 常见：.bss */
uint32_t g_nonzero = 0x12345678u;    /* 常见：.data */
static uint32_t s_counter;          /* 常见：.bss，内部链接 */
const uint32_t g_limit = 1000u;     /* 常见：.rodata */

void example(void)
{
    uint32_t local = 10u;           /* 可能在寄存器，也可能在栈 */
    static uint32_t calls;          /* 静态存储期，常见：.bss */
    const uint32_t threshold = 20u; /* 自动存储期，不保证在 Flash */

    calls += local + threshold;
}
```

上面的 section 归属是常见工具链行为。优化、LTO、自定义 section、链接脚本都可能改变最终结果。

**最终证据是 ELF、map 和反汇编，不是源代码中的关键字。**

## 5. 底层原理与功能特性深度解析

### 5.1 从 C 声明到物理地址

处理链如下：

```
源文件
  ↓ 编译
目标文件：符号 + 输入 section + 重定位记录
  ↓ 链接
ELF：输出 section + 最终符号地址 + 装载信息
  ↓ 下载/烧录
Flash 中的代码和初始化数据
  ↓ 复位启动
复制数据、清零零初始化区域、建立运行环境
  ↓
进入 main()
```

推荐编译选项：

```
-O2
-g3
-ffunction-sections
-fdata-sections
-fstack-usage
-Wall
-Wextra
-Wformat=2
-Werror=return-type
```

链接时：

```
-Wl,--gc-sections
-Wl,-Map=firmware.map,--cref
```

注意：

- `-ffunction-sections` 通常使每个函数进入独立输入 section。
- `--gc-sections` 会回收不可达 section。
- 中断向量、注册表等通过特殊方式引用的数据，可能需要链接脚本 `KEEP()` 保留。
- `__attribute__((used))` 主要影响编译器是否发出实体，**不能一概替代链接器的保留策略**。

检查命令：

```
arm-none-eabi-readelf -S firmware.elf
arm-none-eabi-readelf -l firmware.elf
arm-none-eabi-nm -n -S firmware.elf
arm-none-eabi-objdump -h firmware.elf
arm-none-eabi-objdump -d firmware.elf
```

`readelf -S` 看 section，`readelf -l` 看装载视图。二者用途不同。

### 5.2 `.data`：一个运行副本，一个初始值来源

考虑：

```
#include <stdint.h>

uint32_t g_boot_mode = 3u;
```

如果该变量运行时位于 SRAM：

- 它的 **VMA** 是 SRAM 地址。
- 初始值 `3` 通常存储在 Flash，对应 **LMA**。
- 复位后，启动代码把初始值复制到 SRAM。

因此，典型 `.data` 同时消耗：

1. Flash 中的初始值存储空间；
2. SRAM 中的运行空间。

```
Flash 中初始值
0x00000003
    │ 启动复制
    ▼
SRAM 中 g_boot_mode
0x00000003
```

这也解释了为什么把大型可变数组从零初始化改成非零初始化，可能同时增大固件镜像和启动时间。

### 5.3 `.bss`：启动时建立零值

```
#include <stdint.h>

uint8_t g_rx_buffer[4096];
uint32_t g_error_count = 0u;
```

常见 GCC/ELF 实现会将这些对象放入 `.bss`。

`.bss` 通常采用 `SHT_NOBITS`：

- 记录所需运行空间；
- 不在 ELF 文件中保存同等长度的全零内容；
- 启动代码负责清零。

**`.bss` 不消耗等量固件文件空间，不代表它不消耗 RAM，也不代表它没有启动时间成本。**

显式初始化为零的对象也常放入 `.bss`，并非一定进入 `.data`。

### 5.4 链接脚本中的 VMA、LMA 和容量约束

以下是 **GNU ld 语法片段**，用于说明布局规则；应合并到芯片厂商提供的完整链接脚本中，保留其向量表、异常展开、构造函数数组等必要定义。

```
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
    CCM   (rw)  : ORIGIN = 0x10000000, LENGTH = 64K
}

__msp_size = 8K;

SECTIONS
{
    .data :
    {
        . = ALIGN(4);
        __data_start__ = .;
        *(.data .data.*)
        . = ALIGN(4);
        __data_end__ = .;
    } > RAM AT > FLASH

    __data_load__ = LOADADDR(.data);

    .bss (NOLOAD) :
    {
        . = ALIGN(8);
        __bss_start__ = .;
        *(.bss .bss.*)
        *(COMMON)
        . = ALIGN(8);
        __bss_end__ = .;
    } > RAM

    .noinit (NOLOAD) :
    {
        . = ALIGN(8);
        __noinit_start__ = .;
        KEEP(*(.noinit .noinit.*))
        . = ALIGN(8);
        __noinit_end__ = .;
    } > RAM

    __static_ram_end__ = .;

    .msp_stack ORIGIN(RAM) + LENGTH(RAM) - __msp_size (NOLOAD) :
    {
        __msp_limit__ = .;
        . += __msp_size;
        __msp_top__ = .;
    } > RAM

    ASSERT(__static_ram_end__ <= __msp_limit__,
           "Static RAM overlaps MSP stack")
}
```

关键点：

- `> RAM AT > FLASH`：运行于 RAM，初始内容保存在 Flash。
- `NOLOAD`：该 section 不需要以普通初始化内容装载。
- **`NOLOAD` 不等于“掉电保持”** 。
- `ASSERT()` 把容量问题提前变成链接错误。
- 此片段未建立通用堆；使用 `malloc()` 时还必须配置库分配器和 `_sbrk()` 等接口。
- `MEMORY` 中的 `rwx` 属性**不等于已经配置 MPU**。

### 5.5 启动代码如何建立 C 运行环境

以下函数应由复位汇编在建立有效 MSP 后调用，并在依赖 `.data/.bss` 的普通 C 代码运行之前完成。

```
#include <stdint.h>

extern uint32_t __data_load__[];
extern uint32_t __data_start__[];
extern uint32_t __data_end__[];

extern uint32_t __bss_start__[];
extern uint32_t __bss_end__[];

void runtime_init_memory(void)
{
    uintptr_t src = (uintptr_t)__data_load__;
    uintptr_t dst = (uintptr_t)__data_start__;
    const uintptr_t data_end = (uintptr_t)__data_end__;

    while (dst < data_end) {
        *(volatile uint32_t *)dst =
            *(const volatile uint32_t *)src;

        dst += sizeof(uint32_t);
        src += sizeof(uint32_t);
    }

    dst = (uintptr_t)__bss_start__;
    const uintptr_t bss_end = (uintptr_t)__bss_end__;

    while (dst < bss_end) {
        *(volatile uint32_t *)dst = 0u;
        dst += sizeof(uint32_t);
    }
}
```

工程约束：

- 链接脚本保证起止地址和长度为 4 字节对齐。
- 这是面向指定 ABI 和链接器的底层代码，整数地址转换依赖实现。
- 启动模块应检查反汇编，确认没有意外调用尚不可用的运行库。
- 该函数不能依赖已初始化的全局变量。
- 若存在 `.ramfunc`、`.ccm_data`、外部 RAM 数据区，应增加对应复制表或清零表。
- 外部 SDRAM 中的数据必须在 SDRAM 控制器初始化完成后处理。
- 厂商 `SystemInit()` 的调用顺序必须核对；某些早期硬件初始化会先于数据段初始化执行。

### 5.6 `.noinit`：跳过初始化，不等于数据可信

```
#include <stdint.h>

#define BOOT_RECORD_MAGIC 0x42544F4Bu

typedef struct {
    uint32_t magic;
    uint32_t reset_count;
    uint32_t reset_count_inv;
} boot_record_t;

__attribute__((section(".noinit.boot"), aligned(8)))
static volatile boot_record_t g_boot_record;

void boot_record_update(void)
{
    uint32_t count = g_boot_record.reset_count;

    const int valid =
        (g_boot_record.magic == BOOT_RECORD_MAGIC) &&
        (g_boot_record.reset_count_inv == ~count);

    if (!valid) {
        count = 0u;
    }

    ++count; /* 无符号回绕在此被接受。 */

    /* 最后写 magic，减少中途复位留下“已提交”外观的概率。 */
    g_boot_record.magic = 0u;
    g_boot_record.reset_count = count;
    g_boot_record.reset_count_inv = ~count;
    g_boot_record.magic = BOOT_RECORD_MAGIC;
}
```

此示例适合简单诊断，不是完整事务存储。

必须理解：

- SRAM 是否在某类复位后保留，由芯片复位域决定。
- 上电、掉电、欠压后内容可能无效。
- 反码只能检测部分损坏，不能替代 CRC 或完整事务协议。
- 若要求应对任意写入时刻复位，应使用双槽、序号、CRC 和提交标记。
- `volatile` 不提供掉电原子性，也不构成跨核或 DMA 一致性协议。

### 5.7 栈：ABI 与异常机制共同管理的运行区

典型函数：

```
#include <stddef.h>
#include <stdint.h>

uint32_t sum_u16(const uint16_t *data, size_t count)
{
    if ((data == NULL) && (count != 0u)) {
        return 0u;
    }

    uint32_t sum = 0u;

    for (size_t i = 0u; i < count; ++i) {
        sum += data[i];
    }

    return sum;
}
```

在优化构建中，参数、循环变量、累加值可能全部位于寄存器。这个函数可能没有明显栈帧。

栈通常用于：

- 保存返回地址和被调用者保存寄存器；
- 保存无法全部放入寄存器的局部对象；
- 为被调用函数传递额外参数；
- 保存异常现场；
- 保存 RTOS 切换上下文。

AAPCS32 的重要约束：

- 通常要求 SP 至少保持 4 字节对齐；
- **公共调用接口要求 8 字节对齐**；
- 异常进入时可能增加对齐填充；
- 手写汇编必须遵守 ABI。

Cortex-M4 的硬件基本异常栈帧：

```
R0、R1、R2、R3、R12、LR、PC、xPSR
共 8 × 4 = 32 字节
```

浮点扩展上下文还可能增加：

```
S0～S15、FPSCR、保留字
共 18 × 4 = 72 字节
```

所以完整硬件扩展帧可达到：

32+72=104 字节32+72=104 字节

此外还要计算：

- 对齐填充；
- ISR 的软件保存寄存器；
- ISR 局部变量与调用链；
- RTOS 端口保存的上下文；
- 浮点任务的其他寄存器保存。

**启用惰性浮点压栈后，空间预留与实际写入时机可能不同，不能仅根据一次采样低估栈上界。**

### 5.8 Cortex-M 的 MSP、PSP 与 RTOS 任务栈

常见 RTOS 设计：

```
任务线程模式 → PSP → 各自任务栈
异常处理模式 → MSP → 公共中断栈
```

当运行于 PSP 的线程被中断：

1. 硬件先把线程异常现场压入 **PSP 对应任务栈**；
2. 进入 Handler 模式后，ISR 使用 **MSP**；
3. 更高优先级中断嵌套时，其异常现场通常压入 MSP。

因此：

**任务栈预算不能漏掉首次异常入栈，MSP 预算不能漏掉中断嵌套。**

FreeRTOS 中常见的 `StaticTask_t`、任务栈数组虽然具有静态存储期，但其中保存的是任务运行栈。这说明：

> **C 对象的存储期与该内存区域承担的运行用途是两个维度。**

### 5.9 堆：区域与分配器是两回事

堆分配器通常需要维护：

```
块头
├── 块大小
├── 分配状态
└── 空闲链表或索引信息

有效载荷
└── 返回给调用者的内存
```

对请求 nn 字节，若头部大小为 hh、对齐要求为 aa，常见占用模型为：

B(n)=align_up⁡(n+h,a)B(n)=align_up(n+h,a)

假设：

- 请求 13 字节；
- 块头 8 字节；
- 对齐 8 字节；

则：

B(13)=align_up⁡(21,8)=24 字节B(13)=align_up(21,8)=24 字节

有效载荷利用率：

η=1324≈54.2%η=2413​≈54.2%

这是**假设分配器格式下的计算示例**。具体分配器可能采用不同头部和舍入规则。

常见 FreeRTOS 分配策略：

|实现|特点|主要限制|
|---|---|---|
|`heap_1`|只分配，不回收|不适合反复创建销毁对象|
|`heap_2`|支持释放，不合并相邻空闲块|易形成外部碎片|
|`heap_3`|包装 C 库 `malloc/free`|行为依赖 C 库及其集成|
|`heap_4`|单区域，支持相邻空闲块合并|遍历开销随空闲链表状态变化|
|`heap_5`|多区域，合并规则类似 `heap_4`|必须正确描述区域并管理属性差异|

**`pvPortMalloc()` 与 C 库 `malloc()` 不一定使用同一个堆。**

### 5.10 常量区：`const`、字符串与指针自身

```
#include <stdint.h>

const uint8_t g_table[] = { 1u, 2u, 3u, 4u };

const char *g_name = "motor";
char * const g_fixed_ptr = 0;
const char * const g_fixed_name = "motor";
```

分别分析：

|声明|对象含义|常见位置|
|---|---|---|
|`g_table`|不可修改数组|`.rodata`|
|`g_name`|可修改的指针，指向不可经该类型修改的字符|指针在 `.data`，字面量在只读区|
|`g_fixed_ptr`|不可修改的指针，指向可修改字符|指针常在只读区|
|`g_fixed_name`|不可修改的指针，指向只读字符|指针和字面量常在只读区|

这里的“只读区”仍由工具链和链接布局决定。

特别注意：

```
void function(void)
{
    const uint32_t limit = 100u;
}
```

`limit` 具有自动存储期，可能：

- 被折叠成立即数；
- 存在寄存器；
- 存在栈中；
- 完全被优化掉。

**`const` 规定访问语义，不直接承诺物理存储位置。**

### 5.11 代码段：Flash 执行与 RAM 执行

将特定函数放到输入 section：

```
#include <stdint.h>

__attribute__((section(".ramfunc"), noinline))
uint32_t crc32_step(uint32_t crc, uint8_t value)
{
    crc ^= value;

    for (uint32_t bit = 0u; bit < 8u; ++bit) {
        const uint32_t mask = 0u - (crc & 1u);
        crc = (crc >> 1) ^ (0xEDB88320u & mask);
    }

    return crc;
}
```

要让它真正从 RAM 执行，还必须：

1. 链接脚本把 `.ramfunc` 的 VMA 放入可执行 RAM；
2. 把其 LMA 放入 Flash；
3. 启动时复制；
4. 确保所有调用目标、跳板、常量池和数据依赖都可用；
5. 在带指令缓存的平台上执行必要的一致性维护；
6. 配置正确的 MPU 执行权限。

在 STM32F407 上：

- 普通 SRAM 可用于适当配置下的 RAM 代码执行；
- **CCM RAM 不应当作普通可执行代码区使用**；
- Flash 擦写期间能否执行其他 Flash 内容，要依据该芯片的 Flash 组织和读写限制判断。

把一个函数标记为 `.ramfunc`，并不自动保证整个调用链脱离 Flash。

### 6.3 `.data/.bss` 对启动时间的影响

以本例：

- `.data`：6 KiB；
- `.bss`：20 KiB；
- 32 位循环。

迭代次数：

- Cc=4Cc​=4 cycles；

- 暂忽略固定开销；

Tbudget≈128 μsTbudget​≈128 μs

优化方向：

|手段|预期收益|代价|
|---|---|---|
|减少大型可变初始化表|减少 Flash、RAM 与启动复制|可能需要调整算法|
|真正保留区放 `.noinit`|减少清零量|必须增加有效性验证|
|只读表放 Flash|减少 SRAM 占用|读取延迟与总线争用可能增加|
|优化复制清零例程|减少启动周期|必须验证对齐和运行库依赖|

### 6.5 DWT 周期计数器测量

以下代码依赖 CMSIS 设备头文件。

```
#include <stdbool.h>
#include <stdint.h>

/* 使用对应 STM32F4 设备头文件提供 CoreDebug、DWT、__DSB、__ISB。 */

bool cycle_counter_init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;

    if ((DWT->CTRL & DWT_CTRL_NOCYCCNT_Msk) != 0u) {
        return false;
    }

    DWT->CYCCNT = 0u;
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;

    __DSB();
    __ISB();

    return (DWT->CTRL & DWT_CTRL_CYCCNTENA_Msk) != 0u;
}

static inline uint32_t cycle_begin(void)
{
    __asm volatile ("" ::: "memory");
    __DSB();
    __ISB();

    return DWT->CYCCNT;
}

static inline uint32_t cycle_end(uint32_t begin)
{
    __DSB();
    __ISB();
    __asm volatile ("" ::: "memory");

    return DWT->CYCCNT - begin;
}
```

测量示例：

```
#include <stdint.h>

static volatile uint32_t g_benchmark_sink;

uint32_t benchmark_crc(uint32_t seed, uint8_t value)
{
    const uint32_t start = cycle_begin();

    const uint32_t result = crc32_step(seed, value);

    const uint32_t elapsed = cycle_end(start);

    g_benchmark_sink = result;
    return elapsed;
}
```

注意：

- 测量空区间以估算屏障和读取计数器的开销。
- 确认反汇编中目标操作没有被常量折叠。
- 在 168 MHz 下，32 位计数器约 **25.6 秒回绕一次**。
- 无符号减法适用于测量区间小于一次完整回绕的情况。
- 开中断测试反映系统干扰；关中断测试用于隔离本体成本，两者都需要。
- 若短操作接近测量开销，应批量执行后计算平均值，同时保留单次抖动测试。

### 6.6 为什么不能给出统一的“栈比堆快多少”

需要区分：

1. **分配与释放成本**；
2. **对象访问成本**。

栈对象和堆对象若最终都在相同 SRAM，地址、对齐和访问模式相同，则读取一个字的硬件成本并不会因为“来自堆”就天然更高。

差异主要来自：

- 栈帧调整与分配器遍历成本；
- 对齐和对象布局；
- 数据局部性；
- 所在物理存储器；
- 缓存与总线竞争；
- 编译器是否能把对象放进寄存器。

**存储策略影响管理成本，物理位置和访问模式决定大部分访存成本。**

## 8. 工程最佳实践

### 8.1 先建立内存所有权，再选择区域

每个跨模块对象至少定义：

|属性|必须回答的问题|
|---|---|
|所有者|哪个模块负责创建和释放？|
|生命周期|什么时候有效，什么时候失效？|
|借用规则|调用返回后，接收方是否还能保留指针？|
|并发规则|哪些任务、ISR、DMA 可以同时访问？|
|位置约束|是否必须位于特定 SRAM、对齐到特定边界？|
|失败策略|容量耗尽时丢弃、降级、重试还是复位？|

**内存区域不能替代所有权协议。把对象改成全局变量只能延长生命周期，不能解决并发问题。**

### 8.2 选型决策矩阵

评分：5 最有利，1 最不利；仅比较管理策略，假设对象位于同类 RAM。

|指标|栈|静态对象|固定块池|通用堆|
|---|---|---|---|---|
|分配时延可预测性|5|5|5|2～4|
|容量静态可证明性|3|5|5|2|
|支持异步生命周期|1|5|5|5|
|对尺寸变化的适应性|2|1|3|5|
|无外部碎片|5|5|5|1～4|
|运行期容量调整|1|1|2|5|

其中栈的“容量可证明性”受递归、函数指针、库函数和中断路径影响。

### 8.3 工业级编码规范

1. **默认禁止 VLA、`alloca()` 和无界递归。**
2. 大型临时数组必须经过栈预算评审。
3. ISR 默认不调用通用堆分配器。
4. 分配失败必须进入明确的业务分支。
5. 分配尺寸乘法必须检查溢出。
6. 指针跨异步边界时必须声明所有权。
7. DMA 缓冲区必须有专门位置约束。
8. 地址和长度使用合适类型：地址用 `uintptr_t`，尺寸用 `size_t`。
9. `volatile` 仅用于确实需要的访问语义，不作为锁使用。
10. 对结构大小、对齐、池容量使用 `_Static_assert`。
11. 建议使用 `-fno-common`，避免旧式公共符号行为掩盖重复定义。
12. map 文件和关键 section 大小纳入 CI。

安全计算分配尺寸：

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

bool size_mul_checked(size_t count, size_t elem_size, size_t *result)
{
    if (result == NULL) {
        return false;
    }

    if ((elem_size != 0u) && (count > SIZE_MAX / elem_size)) {
        return false;
    }

    *result = count * elem_size;
    return true;
}
```

在支持 C11 且具有完整 `uintptr_t` 的目标平台上，上述代码可复用。

### 8.4 链接期与运行期双重防线

链接期：

- SRAM 不得与 MSP 保留区重叠；
- DMA 区不得进入不可达 RAM；
- Bootloader 和应用 Flash 区不得交叉；
- 关键 section 不得被垃圾回收；
- 栈顶地址必须满足 ABI 对齐。

运行期：

- 记录分配失败次数；
- 监测池使用峰值；
- 检测任务栈余量；
- 对关键区域设置 MPU 权限；
- 保存可定位的故障记录。

MPU 的典型目标：

```
代码：只读、可执行
普通数据：可读写、不可执行
只读表：只读、不可执行
栈底保护区：不可访问
设备寄存器：设备属性、不可执行
```

STM32F407 的 Cortex-M4 MPU 不提供 Cortex-M33 那样的专用栈限制寄存器；应结合 MPU、软件检查和布局设计。

## 9. 常见错误与避坑指南

### 9.1 错误一：返回自动对象地址

错误代码：

```
#include <stdint.h>

uint8_t *get_frame(void)
{
    uint8_t frame[64] = { 0u };
    return frame;
}
```

根因：

- `frame` 在函数返回后生命周期结束。
- 指针值可能看起来没有变化，但不再指向有效对象。

正确实现：

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

bool build_frame(uint8_t *out, size_t capacity, size_t *written)
{
    if (written == NULL) {
        return false;
    }

    *written = 0u;

    if ((out == NULL) || (capacity < 4u)) {
        return false;
    }

    out[0] = 0xAAu;
    out[1] = 0x55u;
    out[2] = 0x01u;
    out[3] = 0x00u;

    *written = 4u;
    return true;
}
```

风险影响：

- 偶现协议损坏；
- 返回地址或其他栈对象被误写；
- 故障对日志和编译优化高度敏感。

### 9.2 错误二：异步 DMA 使用栈缓冲区

错误代码：

```
void send_status(void)
{
    uint8_t frame[32] = { 0u };

    /* 假设该接口只保存地址，DMA 在函数返回后继续读取。 */
    uart_dma_start(frame, sizeof(frame));
}
```

根因：

- DMA 生命周期超过了栈对象生命周期。
- 下一个函数可能覆盖原地址。

正确实现要引入持久缓冲区和忙状态：

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

/*
 * 调用约束：
 * 1. send_status() 仅由同一个控制任务调用；
 * 2. 完成中断必须经过同步协议通知该任务；
 * 3. 此处用任务内 busy 表示状态，不允许 ISR 直接并发访问。
 */

static uint8_t g_tx_buffer[32];
static bool g_tx_busy;

bool send_status(void)
{
    if (g_tx_busy) {
        return false;
    }

    for (size_t i = 0u; i < sizeof(g_tx_buffer); ++i) {
        g_tx_buffer[i] = 0u;
    }

    g_tx_busy = true;

    if (!uart_dma_start(g_tx_buffer, sizeof(g_tx_buffer))) {
        g_tx_busy = false;
        return false;
    }

    return true;
}

/* 由控制任务在收到 DMA 完成事件后调用。 */
void send_status_complete(void)
{
    g_tx_busy = false;
}
```

风险影响：

- 发送内容被改写；
- 错误只在高负载时出现；
- 引入难以复现的数据一致性问题。

还需考虑 DMA 启动失败是否可能部分启动；底层驱动必须定义“返回失败后不再访问缓冲区”的契约。

### 9.3 错误三：修改字符串字面量

错误代码：

```
void bad_text(void)
{
    char *name = "motor";
    name[0] = 'M';
}
```

根因：

- C 中字符串字面量通常具有字符数组类型，但修改它属于**未定义行为**。
- 在 MCU 上可能尝试写 Flash，导致异常或无效写入。

正确实现：

```
void editable_text(void)
{
    char name[] = "motor";
    name[0] = 'M';
}
```

只读使用：

```
const char *get_device_name(void)
{
    return "motor";
}
```

风险影响：

- HardFault；
- 行为依赖链接位置；
- 字面量合并后影响其他使用者。

### 9.4 错误四：大数组和 VLA 导致栈失控

错误代码：

```
#include <stddef.h>
#include <stdint.h>

void decode(size_t input_size)
{
    uint8_t scratch[input_size];
    /* ... */
}
```

根因：

- 栈占用由外部输入决定；
- 无法仅从链接大小看出；
- 栈扩展通常没有像操作系统进程那样的自动增长保护。

正确实现：

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

#define DECODE_MAX_INPUT 1024u

bool decode(const uint8_t *input,
            size_t input_size,
            uint8_t *workspace,
            size_t workspace_size)
{
    if ((input == NULL) || (workspace == NULL)) {
        return false;
    }

    if ((input_size > DECODE_MAX_INPUT) ||
        (workspace_size < input_size)) {
        return false;
    }

    for (size_t i = 0u; i < input_size; ++i) {
        workspace[i] = input[i];
    }

    return true;
}
```

风险影响：

- 覆盖其他数据；
- 破坏任务控制块；
- 在稍后调度时才出现故障。

### 9.5 错误五：错误释放和分配器混用

错误代码：

```
void bad_release(void)
{
    void *p = pvPortMalloc(128u);
    free(p); /* 除非集成明确支持，否则属于错误配对。 */
}
```

正确实现：

```
#include <stdbool.h>
#include <stddef.h>

bool process_dynamic_buffer(void)
{
    void *buffer = pvPortMalloc(128u);

    if (buffer == NULL) {
        return false;
    }

    const bool ok = process_buffer(buffer, 128u);

    vPortFree(buffer);
    return ok;
}
```

根因：

- 分配器元数据格式不同；
- 可能管理完全不同的地址范围。

风险影响：

- 空闲链表破坏；
- 后续任意分配时崩溃；
- 重复释放后产生可利用的内存破坏。

### 9.6 错误六：认为全局变量天然线程安全

错误代码：

```
#include <stdint.h>

volatile uint32_t g_count;

void task_a(void)
{
    ++g_count;
}
```

根因：

- `++` 是读、改、写，不是一个抽象的原子操作；
- `volatile` 不防止丢失更新；
- 即使单次 32 位访问在硬件上不可分割，也不代表整个表达式不可分割。

任务上下文下的正确实现：

```
#include <stdint.h>
#include "FreeRTOS.h"
#include "task.h"

static uint32_t g_count;

void count_increment(void)
{
    taskENTER_CRITICAL();
    ++g_count;
    taskEXIT_CRITICAL();
}

uint32_t count_get(void)
{
    uint32_t value;

    taskENTER_CRITICAL();
    value = g_count;
    taskEXIT_CRITICAL();

    return value;
}
```

约束：

- 这是任务上下文版本。
- ISR 应使用对应端口支持的 ISR 临界区接口。
- 高于 FreeRTOS 可屏蔽范围的中断不能随意参与该共享协议。
- SMP 系统需要重新评估本地关中断是否足够。

## 10. 多机制组合使用方案

### 10.1 组合架构：静态容量 + 固定池 + 队列传递所有权

适用于：

- 采集报文；
- 通信收发；
- 控制命令；
- 事件记录。

架构：

```
Flash
└── 只读配置与代码

静态 SRAM
├── 固定报文池
├── 空闲对象队列
├── 就绪对象队列
├── 任务控制块
└── 任务栈

生产者任务
  ↓ 申请一个固定对象
填写对象
  ↓ 发布成功后移交所有权
消费者任务
  ↓ 处理完成
归还固定对象
```

关键不变量：

Nfree+Nready+Nproducer-owned+Nconsumer-owned=NtotalNfree​+Nready​+Nproducer-owned​+Nconsumer-owned​=Ntotal​

下面使用 FreeRTOS 静态队列实现完整模块框架。要求：

- `configSUPPORT_STATIC_ALLOCATION == 1`；
- 初始化必须在任何访问前完成；
- 对象池 API 仅用于任务上下文；
- 每个对象同一时刻只有一个所有者；
- 指针只能来自该池。

```
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

#include "FreeRTOS.h"
#include "queue.h"

#define FRAME_COUNT       8u
#define FRAME_PAYLOAD_MAX 256u

typedef struct {
    uint16_t length;
    uint16_t type;
    uint8_t payload[FRAME_PAYLOAD_MAX];
} frame_t;

typedef struct {
    frame_t frames[FRAME_COUNT];

    StaticQueue_t free_queue_control;
    StaticQueue_t ready_queue_control;

    uint8_t free_queue_storage[FRAME_COUNT * sizeof(frame_t *)];
    uint8_t ready_queue_storage[FRAME_COUNT * sizeof(frame_t *)];

    QueueHandle_t free_queue;
    QueueHandle_t ready_queue;

    bool initialized;
} frame_channel_t;

_Static_assert(FRAME_PAYLOAD_MAX <= UINT16_MAX,
               "Frame length field is too small");

static frame_channel_t g_channel;

static bool frame_belongs_to_channel(const frame_t *frame)
{
    if (frame == NULL) {
        return false;
    }

    for (size_t i = 0u; i < FRAME_COUNT; ++i) {
        if (frame == &g_channel.frames[i]) {
            return true;
        }
    }

    return false;
}

bool frame_channel_init(void)
{
    if (g_channel.initialized) {
        return true;
    }

    g_channel.free_queue = xQueueCreateStatic(
        FRAME_COUNT,
        sizeof(frame_t *),
        g_channel.free_queue_storage,
        &g_channel.free_queue_control);

    g_channel.ready_queue = xQueueCreateStatic(
        FRAME_COUNT,
        sizeof(frame_t *),
        g_channel.ready_queue_storage,
        &g_channel.ready_queue_control);

    if ((g_channel.free_queue == NULL) ||
        (g_channel.ready_queue == NULL)) {
        g_channel.free_queue = NULL;
        g_channel.ready_queue = NULL;
        return false;
    }

    for (size_t i = 0u; i < FRAME_COUNT; ++i) {
        frame_t *frame = &g_channel.frames[i];

        if (xQueueSend(g_channel.free_queue, &frame, 0u) != pdPASS) {
            /*
             * 静态队列和对象数配置一致时不应发生。
             * 初始化失败后禁止启动依赖该模块的任务。
             */
            return false;
        }
    }

    g_channel.initialized = true;
    return true;
}

bool frame_acquire(frame_t **out, TickType_t timeout)
{
    if (out == NULL) {
        return false;
    }

    *out = NULL;

    if (!g_channel.initialized) {
        return false;
    }

    frame_t *frame = NULL;

    if (xQueueReceive(g_channel.free_queue,
                      &frame,
                      timeout) != pdPASS) {
        return false;
    }

    frame->length = 0u;
    frame->type = 0u;
    *out = frame;
    return true;
}

bool frame_publish(frame_t **owned, TickType_t timeout)
{
    if ((owned == NULL) ||
        !g_channel.initialized ||
        !frame_belongs_to_channel(*owned)) {
        return false;
    }

    frame_t *frame = *owned;

    if (frame->length > FRAME_PAYLOAD_MAX) {
        return false;
    }

    if (xQueueSend(g_channel.ready_queue,
                   &frame,
                   timeout) != pdPASS) {
        /* 发送失败，所有权仍属于调用方。 */
        return false;
    }

    /* 发送成功，调用方不得继续访问对象。 */
    *owned = NULL;
    return true;
}

bool frame_receive(frame_t **out, TickType_t timeout)
{
    if (out == NULL) {
        return false;
    }

    *out = NULL;

    if (!g_channel.initialized) {
        return false;
    }

    return xQueueReceive(g_channel.ready_queue,
                         out,
                         timeout) == pdPASS;
}

bool frame_release(frame_t **owned)
{
    if ((owned == NULL) ||
        !g_channel.initialized ||
        !frame_belongs_to_channel(*owned)) {
        return false;
    }

    frame_t *frame = *owned;

    if (xQueueSend(g_channel.free_queue, &frame, 0u) != pdPASS) {
        /*
         * 正确所有权协议下不应出现。
         * 失败常提示重复归还、状态破坏或错误调用。
         */
        return false;
    }

    *owned = NULL;
    return true;
}
```

生产者使用：

```
#include <string.h>

bool submit_payload(const uint8_t *data,
                    size_t length,
                    TickType_t timeout)
{
    if (((data == NULL) && (length != 0u)) ||
        (length > FRAME_PAYLOAD_MAX)) {
        return false;
    }

    frame_t *frame = NULL;

    if (!frame_acquire(&frame, timeout)) {
        return false;
    }

    if (length != 0u) {
        memcpy(frame->payload, data, length);
    }

    frame->length = (uint16_t)length;

    if (!frame_publish(&frame, timeout)) {
        const bool released = frame_release(&frame);

        if (!released) {
            /*
             * 系统集成点：记录不可恢复的不变量破坏，
             * 进入安全状态或执行受控复位。
             */
            application_memory_invariant_fault();
        }

        return false;
    }

    return true;
}
```

消费者：

```
void consumer_task(void *argument)
{
    (void)argument;

    for (;;) {
        frame_t *frame = NULL;

        if (!frame_receive(&frame, portMAX_DELAY)) {
            continue;
        }

        /*
         * process_frame() 必须在返回前结束对 frame 的访问。
         * 若它启动异步 DMA，释放必须推迟到完成事件之后。
         */
        process_frame(frame->payload, frame->length);

        if (!frame_release(&frame)) {
            application_memory_invariant_fault();
        }
    }
}
```

该框架的工程价值：

- 对象数量固定；
- 不存在通用堆外部碎片；
- 队列提供任务间同步；
- 通过二级指针把“成功后失去所有权”体现在 API 中；
- 失败时所有权仍清晰；
- 不需要删除静态队列或释放静态对象。

边界：

- 指针置空不能阻止调用者保存别名。
- 成员资格检查不能完整检测所有重复发布/重复归还。
- 更高完整性要求下，应增加状态表或**索引 + 代数**句柄，检测陈旧引用和非法状态转换。
- 模块不支持运行期并发重初始化；失败恢复应在系统初始化阶段完成。

## 11. 工业级实际案例分析

以下为真实工业应用类型的工程化案例，参数用于设计推演，不代表对特定厂商项目的实测报告。

### 11.1 案例一：伺服控制器的 20 kHz 电流环

#### 需求

- 控制周期：50 μs；
- 控制环目标预算：15 μs；
- ADC 通过 DMA 更新采样；
- 控制计算使用浮点；
- 后台同时进行通信和日志处理。

在 168 MHz 下：

50 μs×168 MHz=8400 cycles50 μs×168 MHz=8400 cycles

控制算法预算：

15 μs×168 MHz=2520 cycles15 μs×168 MHz=2520 cycles

#### 架构设计

|对象|位置|
|---|---|
|ADC DMA 缓冲区|DMA 可达 SRAM|
|PI 控制器状态|SRAM 或 CCM|
|电机只读参数|Flash|
|控制 ISR 局部对象|MSP 栈|
|通信报文|独立固定池|

核心原则：

**采样缓冲区必须先满足 DMA 可达性，不能因为 CCM 对 CPU 访问有利就放入 CCM。**

核心代码：

```
#include <stdint.h>

#define ADC_CHANNELS 4u

__attribute__((section(".dma_buffer"), aligned(4)))
static volatile uint16_t g_adc_samples[2][ADC_CHANNELS];

typedef struct {
    float kp;
    float ki;
    float integral;
    float min_output;
    float max_output;
} pi_controller_t;

__attribute__((section(".ccm_bss"), aligned(8)))
static pi_controller_t g_current_pi;

static float clamp_float(float value, float low, float high)
{
    if (value < low) {
        return low;
    }

    if (value > high) {
        return high;
    }

    return value;
}

float current_pi_step(float error, float dt)
{
    const float candidate =
        g_current_pi.integral + g_current_pi.ki * error * dt;

    const float raw =
        g_current_pi.kp * error + candidate;

    const float output = clamp_float(
        raw,
        g_current_pi.min_output,
        g_current_pi.max_output);

    /* 简化的条件积分抗饱和。 */
    if ((raw == output) ||
        ((raw > output) && (error < 0.0f)) ||
        ((raw < output) && (error > 0.0f))) {
        g_current_pi.integral = candidate;
    }

    return output;
}
```

设计要点：

- `.ccm_bss` 必须加入启动清零表。
- PI 参数在使能控制中断前初始化，并验证范围与有限值。
- DMA 半缓冲所有权必须根据半传输/全传输事件确定。
- `volatile` 只保证 CPU 实际读取缓冲区，不负责避免 DMA 与 CPU 同时访问同一半区。
- 测量必须包含 FPU 上下文和通信 DMA 干扰。
- 高优先级控制中断不应调用不允许的 FreeRTOS API。

### 11.2 案例二：工业网关长期运行后“大块分配失败”

#### 需求

- 连续运行数月；
- 存在小型控制消息和大型升级块；
- 网络断连、重连频繁；
- 日志显示总剩余堆仍有 12 KiB，但申请 4 KiB 失败。

#### 根因分析

可能的空闲分布：

```
空闲 2 KiB | 已用 | 空闲 2 KiB | 已用 | 空闲 3 KiB | 已用 | 空闲 5 KiB
```

这个具体分布能满足 4 KiB，因此不能用它解释失败。

真正符合失败条件的例子是：

```
空闲 3 KiB | 已用 | 空闲 3 KiB | 已用 | 空闲 3 KiB | 已用 | 空闲 3 KiB
```

总空闲：

Ftotal=12 KiBFtotal​=12 KiB

最大连续空闲：

Flargest=3 KiBFlargest​=3 KiB

4 KiB 连续申请失败。

可定义诊断指标：

ϕ=1−FlargestFtotalϕ=1−Ftotal​Flargest​​

此时：

ϕ=1−312=75%ϕ=1−123​=75%

这个指标是**碎片分散程度的诊断量**，不是所有分配器通用的正式性能指标。

#### 架构调整

```
长期配置对象 → 启动期分配，运行期不释放
控制报文     → 256 B 固定池
网络数据块   → 1536 B 固定池
升级工作区   → 独占静态 8 KiB 缓冲区
临时管理对象 → 单独受控堆
```

核心代码：

```
#include <stdbool.h>
#include <stdint.h>

#define UPGRADE_WORKSPACE_SIZE 8192u

static uint8_t g_upgrade_workspace[UPGRADE_WORKSPACE_SIZE];
static bool g_upgrade_active;

/* 仅由升级管理任务调用。 */
bool upgrade_begin(void)
{
    if (g_upgrade_active) {
        return false;
    }

    g_upgrade_active = true;

    if (!upgrade_engine_start(g_upgrade_workspace,
                              sizeof(g_upgrade_workspace))) {
        g_upgrade_active = false;
        return false;
    }

    return true;
}

/* 必须在引擎已经停止访问工作区后调用。 */
void upgrade_end(void)
{
    g_upgrade_active = false;
}
```

设计要点：

- 静态工作区提高容量确定性，但增加常驻 RAM。
- 升级引擎不能在返回“启动失败”后继续异步访问工作区。
- 若工作区与其他模式复用，必须有互斥状态机。
- 监测总空闲量、最大空闲块和最小历史空闲量，三者不能互相替代。
- 固件升级不能破坏控制路径的内存预算和实时性。

### 11.3 案例三：故障记录在看门狗复位后丢失

#### 需求

- 记录 HardFault 的 PC、LR 和故障状态；
- 看门狗复位后导出；
- 故障处理不能依赖堆；
- 避免使用已经损坏的业务栈。

#### 架构设计

```
HardFault 汇编入口
  ↓ 根据 EXC_RETURN 识别原始栈
提取现场
  ↓ 写入专属保留记录
执行必要的写入完成屏障
  ↓ 受控复位 / 等待看门狗
下次启动
  ↓ 校验记录并导出
```

核心记录结构：

```
#include <stdint.h>

#define CRASH_MAGIC 0x43525348u

typedef struct {
    uint32_t magic;
    uint32_t version;
    uint32_t exc_return;
    uint32_t stacked_pc;
    uint32_t stacked_lr;
    uint32_t cfsr;
    uint32_t hfsr;
    uint32_t checksum;
} crash_record_t;

__attribute__((section(".noinit.crash"), aligned(8)))
static volatile crash_record_t g_crash_record;

static uint32_t crash_checksum(const crash_record_t *record)
{
    return record->version ^
           record->exc_return ^
           record->stacked_pc ^
           record->stacked_lr ^
           record->cfsr ^
           record->hfsr ^
           0xA5A55A5Au;
}

void crash_record_commit(uint32_t exc_return,
                         uint32_t pc,
                         uint32_t lr,
                         uint32_t cfsr,
                         uint32_t hfsr)
{
    const crash_record_t record = {
        .magic = 0u,
        .version = 1u,
        .exc_return = exc_return,
        .stacked_pc = pc,
        .stacked_lr = lr,
        .cfsr = cfsr,
        .hfsr = hfsr,
        .checksum = 0u
    };

    g_crash_record.magic = 0u;
    g_crash_record.version = record.version;
    g_crash_record.exc_return = record.exc_return;
    g_crash_record.stacked_pc = record.stacked_pc;
    g_crash_record.stacked_lr = record.stacked_lr;
    g_crash_record.cfsr = record.cfsr;
    g_crash_record.hfsr = record.hfsr;
    g_crash_record.checksum = crash_checksum(&record);

    __DMB();
    g_crash_record.magic = CRASH_MAGIC;
    __DSB();
}
```

设计要点：

- 这是记录提交函数，不是完整 HardFault 入口。
- 读取堆栈前必须检查地址范围、对齐和压栈错误状态。
- 若为扩展浮点栈帧，基础寄存器所在偏移不同。
- 若 `CFSR` 指示压栈失败，不能盲信堆栈中的 PC。
- 如果 MSP 已损坏，普通 C 函数本身也可能无法可靠运行；高可靠实现需预留应急栈并设计汇编入口。
- XOR 校验仅适合轻量诊断；要求更强损坏检测时应使用 CRC。
- Cortex-M7 等带 D-cache 的平台还必须处理记录写回，屏障不能代替缓存清理。
- SRAM 保留性需结合具体复位源验证。

## 12. 高频问题深度答疑

### 12.1 为什么 `static` 局部变量不在栈上？

因为 `static` 改变其存储期。

```
void count_call(void)
{
    static unsigned count;
    ++count;
}
```

`count` 的名字只在函数块内可见，但对象在整个程序运行期存在，常见位置是 `.bss`。

它不会在每次调用时重新创建，也不会在函数返回时销毁。

代价是：

- 函数不再天然可重入；
- 多任务调用需要同步；
- 单元测试之间可能残留状态。

### 12.2 为什么 Flash 剩余很多，RAM 却溢出了？

因为 Flash 与 SRAM 是独立资源。

典型原因：

- 大型 `.bss` 数组；
- 可变查找表被放进 `.data`；
- 任务栈总量过大；
- 多套分配器分别保留堆；
- 网络协议栈拥有独立缓冲池。

应分别检查：

FusedFused​Rstatic+RreservedRstatic​+Rreserved​

而不是只看一个“程序总大小”。

此外，传统 `size` 输出中的 `text/data/bss` 是工具统计分类，不能机械等同于某一块芯片存储器。

### 12.3 栈水位正常，为什么仍然发生栈破坏？

填充扫描只能说明“哪些填充值被改写”。

可能漏检：

- 大栈帧只移动 SP，却没有写满；
- 越界跨过了检测边界；
- 未覆盖某条深调用链；
- 中断嵌套压力不足；
- FPU 惰性压栈情形未出现；
- 观测对象不是实际发生故障的 MSP/PSP。

可靠方法应组合：

- `-fstack-usage`；
- 调用图分析；
- 高水位监测；
- SP 最低值记录；
- MPU 保护；
- 中断与异常压力测试。

**水位是证据之一，不是完整证明。**

### 12.4 `const` 放 Flash 后一定更慢吗？

不一定。

影响因素包括：

- 常量是否被编译为立即数；
- Flash 预取或加速器是否命中；
- CPU 指令和数据是否争用同一资源；
- SRAM 是否同时被 DMA 大量访问；
- 平台是否具有缓存；
- 访问是否顺序、随机或跨边界。

对小常量，可能根本没有内存读取。

对大型查找表，必须在真实代码和真实总线负载下比较 Flash、SRAM、TCM。

### 12.5 RTOS 任务栈来自堆，它到底属于栈还是堆？

两个说法可以同时成立：

- **来源**：任务创建时通过堆分配获得；
- **用途**：被 PSP 用作任务运行栈。

同理：

```
static StackType_t task_stack[512];
```

这个对象：

- C 层面具有静态存储期；
- 链接层面常位于 `.bss`；
- 运行层面承担任务栈功能。

这正是不能把“五大区”当作互斥语言分类的原因。

### 12.6 为什么仅靠 `_sbrk()` 比较当前 SP 不能保证堆安全？

在简单裸机中，有些实现用当前 SP 阻止堆向栈增长。

RTOS 下问题包括：

- 当前 SP 可能是 PSP，只代表某个任务；
- MSP 位于另一片区域；
- 其他任务栈也许由同一个堆分配；
- 中断栈尚未达到最深嵌套；
- 存在多个不连续内存区域。

正确做法是：

- 给堆设置明确边界；
- 栈、堆和静态区域分别预算；
- 根据链接符号和分配器配置实施边界检查；
- 不把当前 SP 当成全系统安全边界。

## 13. 课程核心总结

### 13.1 核心要点

1. **C 语言不规定一个通用的“五区物理布局”。**
2. **存储期、作用域、链接属性、section、物理存储器必须分开分析。**
3. `.data` 常同时消耗 Flash 初始值空间和 SRAM 运行空间。
4. `.bss` 常不保存等量文件内容，但消耗 RAM 和启动清零时间。
5. `.noinit` 只表示跳过初始化，其有效性和保留性必须另行保证。
6. 栈预算必须覆盖调用链、异常、FPU、RTOS 上下文和裕量。
7. 堆故障不仅是“剩余空间不足”，还包括连续空间、碎片、元数据破坏和时延失控。
8. DMA 缓冲区必须同时满足可达性、对齐、生命周期和所有权要求。
9. `const`、`static`、`volatile` 分别解决不同问题，不能互相替代。
10. **最终布局看 ELF，启动行为看复位代码，运行正确性看所有权与硬件规则。**

### 13.2 性能排序的适用边界

对于“获得临时存储的管理成本”，常见趋势为：

```
已存在的静态工作区
    ≈ 简单栈帧调整
    ≈ 简单固定块池
    < 需要搜索、合并或同步的通用堆
```

这不是跨平台严格排序：

- 静态区可能仍需锁；
- 固定池可能包含队列唤醒；
- 栈函数可能有较多寄存器保存；
- 通用分配器也可能具有有界算法。

对于“读取一个对象”，**不存在普遍成立的栈、堆、全局访问速度排序**。

### 13.3 通用选型结论

- 小型、同步、短生命周期对象：优先自动对象。
- 大型工作区：优先调用者提供或专属受控工作区。
- 全生命周期对象：静态分配。
- 高频动态对象：优先固定池。
- 尺寸高度变化对象：使用受控堆并验证失败路径。
- 硬实时核心路径：尽量避免不可界定的动态分配。
- DMA 与持久化对象：先满足硬件和生命周期约束，再讨论访问速度。

|---|---|---|

|Flash 操作支持代码|可执行 RAM|完整调用链和常量依赖|

### 14.2 特性对比表

|对象/区域|典型初始化动作|典型 Flash 成本|典型 RAM 成本|
|---|---|---|---|
|`.text`|通常直接执行|代码大小|通常无|
|`.rodata`|通常直接读取|数据大小|通常无|
|`.data`|从 LMA 复制到 VMA|初始值大小|对象大小|
|`.bss`|清零|无等量零内容|对象大小|
|`.noinit`|跳过初始化|通常无初始化内容|对象大小|
|RAM 代码|启动复制|代码初始副本|运行代码大小|
|静态任务栈|按 RTOS 初始化|通常无等量初值|栈数组大小|
|通用堆|初始化分配器|分配器代码等|预留区及元数据|

### 14.3 关键字与语义速查

|写法|能保证什么|不能保证什么|
|---|---|---|
|`static` 局部对象|静态存储期、块作用域|可重入、线程安全|
|文件作用域 `static`|内部链接|特定物理地址|
|`const`|不可经该限定访问路径修改；定义为 const 的对象不可合法修改|一定在 Flash|
|`volatile`|实现规定下的可观察访问|原子性、互斥、缓存一致性|
|自定义 section 属性|指定输入 section|最终内存位置正确|
|`aligned(N)`|请求至少指定对齐，受实现限制|DMA 可达、缓存一致|
|`NOLOAD`|链接装载属性|掉电保持、内容有效|
