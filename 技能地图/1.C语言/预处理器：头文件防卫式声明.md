
**头文件防卫式声明，是让接口在重复包含、独立包含、跨模块编译、跨语言调用和版本演进时，仍然保持确定性与一致性的一组设计方法。**

它不仅包括常见的 `#ifndef` 头文件保护，还包括：

- 头文件能够独立编译，不依赖偶然的包含顺序。
- 声明与定义严格分离，避免重复符号和每个翻译单元各存一份数据。
- 接口明确表达指针、长度、所有权、生命周期和并发约束。
- 配置变化不能悄悄破坏公共数据布局。
- 不透明类型、静态断言、编译器属性共同形成防线。
- C/C++、不同工具链和预编译库之间的边界可验证。

本课以 **C11/C17 为主要基线**，对 C++ 兼容和编译器扩展单独说明。代码示例假设平台提供 `uint8_t` 等所使用的精确宽度整数类型；涉及动态分配的示例仅适用于允许使用堆的运行环境。

## 1. 学习目标

### 1.1 理解

- 理解头文件包含本质上是预处理阶段的记号引入。
- 理解头文件保护作用于**单个翻译单元**，不能解决所有链接冲突。
- 理解声明、定义、不完整类型和链接属性之间的关系。
- 理解头文件既是编译接口，也是模块边界和 ABI 契约。

### 1.2 掌握

- 编写具有唯一保护宏、依赖完整、包含顺序无关的头文件。
- 正确声明函数、常量、全局对象和不透明类型。
- 正确使用 `static inline`，避免 C 内联链接语义陷阱。
- 为 C/C++ 混合工程编写兼容头文件。
- 使用 `_Static_assert`、错误码和编译器属性表达接口约束。

### 1.3 精通

- 定位头文件保护宏冲突、循环包含和类型不完整错误。
- 识别由配置、打包指令、枚举宽度和工具链选项引起的 ABI 不一致。
- 区分编译期防护、链接期防护和运行期参数校验。
- 评估头文件对编译依赖、代码尺寸、RAM 和维护成本的影响。

### 1.4 能够设计

- 设计面向驱动、协议栈、中间件和 SDK 的公共头文件规范。
- 设计具有稳定边界的 C 接口，支持模块内部实现演进。
- 建立头文件独立编译、重复包含、C/C++ 兼容和符号检查流程。
- 根据实时性、内存分配方式和 ABI 要求选择对象公开方式。

## 3. 技术概述

### 3.1 头文件实际上如何工作

假设：

```
/* app.c */
#include "sensor.h"
#include "sensor.h"
```

预处理器不会天然把 `sensor.h` 当作只能引入一次的模块。没有保护机制时，其内容会被再次处理。

重复函数原型通常合法：

```
int sensor_start(void);
int sensor_start(void);
```

但重复定义结构体通常不合法：

```
struct sensor_state {
    unsigned int flags;
};

struct sensor_state {
    unsigned int flags;
};
```

头文件保护的直接目的，是避免同一个翻译单元重复处理不应重复出现的内容。

### 3.2 四层防卫模型

|防卫层|主要机制|解决的问题|
|---|---|---|
|预处理层|保护宏、依赖隔离、宏清理|重复包含、配置污染|
|编译层|完整原型、不透明类型、静态断言|类型误用、布局假设错误|
|链接层|定义唯一性、符号前缀、ABI 管理|重复定义、符号冲突|
|运行层|参数检查、状态检查、生命周期契约|空指针、越界、释放后使用|

**头文件保护只能覆盖第一层的一部分。**

例如，下面的头文件即使有保护宏，仍然可能导致链接错误：

```
#ifndef ACME_COUNTER_H_INCLUDED
#define ACME_COUNTER_H_INCLUDED

int acme_counter = 0;

#endif
```

原因是每个包含它的源文件，都会各自产生一个外部对象定义。

### 3.3 常见技术分支

- 标准保护宏：`#ifndef` / `#define` / `#endif`。
- 工具链扩展：`#pragma once`。
- 自包含头文件：直接包含接口声明所需要的依赖。
- 不透明对象：只暴露结构体前置声明。
- 固定公开布局：公开结构体并管理版本和 ABI。
- 头文件实现：`static inline` 或显式受控的生成机制。
- 跨语言声明：C++ 下使用 `extern "C"`。
- 契约增强：静态断言、属性、所有权和并发说明。

## 4. 核心特性横向对比

### 4.1 防重复包含方案

|方案|ISO C 可移植性|判断依据|主要风险|推荐用途|
|---|---|---|---|---|
|保护宏|高|宏是否已定义|宏名冲突、保护范围错误|通用库、长期维护代码|
|`#pragma once`|非 ISO C 标准机制|编译器识别文件身份|依赖工具链和文件身份处理|工具链固定且验证过的项目|
|两者同时使用|取决于 pragma 支持策略|两套机制|冗余、不能消除保护宏冲突|团队已有明确规范时|
|无保护|不适合普通声明头|每次都重新处理|重复类型定义等|有意多次展开的 `.def` 清单|

**不要把“支持 `#pragma once`”和“任何文件系统布局下都不会遇到身份识别问题”等同起来。** 符号链接、复制文件和生成目录的具体行为由工具链实现决定。

### 4.2 对象接口方案

|方案|尺寸/布局可见|栈上直接创建|ABI 隔离能力|内存控制|主要代价|
|---|---|---|---|---|---|
|公开完整结构体|是|能|低|强|内部布局成为公共契约|
|不透明类型 + 动态创建|否|不能直接创建对象本体|高|依赖分配器|分配失败、生命周期管理|
|不透明类型 + 静态对象池|否|不能直接创建对象本体|高|可确定|池容量、并发和句柄管理|
|调用方提供存储|通常只公开尺寸/对齐需求|可实现|中|强|对齐、有效类型和版本管理复杂|
|固定公开句柄|否|可保存句柄|高|可确定|句柄校验、代际管理|

### 4.3 函数与对象声明

|写法|本质|放头文件是否合适|
|---|---|---|
|`int app_open(void);`|外部函数声明|合适|
|`extern unsigned int app_count;`|外部对象声明|语法合适，架构上需审查|
|`unsigned int app_count;`|文件作用域暂定定义|不应放普通公共头|
|`const unsigned int app_limit = 16u;`|C 中通常是外部对象定义|不应在多个翻译单元重复|
|`static unsigned int app_count;`|每个翻译单元一个内部对象|容易产生意外副本|
|`static inline int app_get(void) { ... }`|内部链接函数定义|适合小型、稳定辅助函数|
|`int app_get(void) { ... }`|外部函数定义|不应直接放普通公共头|

## 5. 底层原理与功能特性深度解析

### 5.1 标准保护宏：作用域是翻译单元

推荐模板：

```
#ifndef ACME_DRIVER_UART_H_INCLUDED
#define ACME_DRIVER_UART_H_INCLUDED

#include <stddef.h>
#include <stdint.h>

int acme_uart_write(const uint8_t *data, size_t length);

#endif /* ACME_DRIVER_UART_H_INCLUDED */
```

第一次包含：

1. 保护宏未定义。
2. 定义保护宏。
3. 处理接口内容。

第二次包含：

1. 保护宏已定义。
2. 跳过受保护内容。

但编译另一个 `.c` 文件时，通常开始一个新的预处理环境，保护宏会再次由该翻译单元建立。

因此：

> **保护宏避免同一翻译单元重复处理头文件，不会让整个工程只产生一份对象定义。**

#### 命名要求

推荐：

```
ACME_PROTOCOL_PACKET_H_INCLUDED
ACME_PLATFORM_TIMER_H_INCLUDED
```

避免：

```
__PACKET_H__
_PACKET_H
```

以下标识符涉及 C 的保留命名规则：

- 以双下划线开头。
- 以下划线加大写字母开头。
- 其他以下划线开头的名字在特定作用域也有保留限制。

统一使用项目、模块和文件名组成前缀，最容易规避问题。

### 5.2 保护宏冲突会静默吞掉接口

假设两个头文件复制了相同保护宏：

```
/* uart.h */
#ifndef ACME_DRIVER_H_INCLUDED
#define ACME_DRIVER_H_INCLUDED

int acme_uart_init(void);

#endif
```

```
/* spi.h */
#ifndef ACME_DRIVER_H_INCLUDED
#define ACME_DRIVER_H_INCLUDED

int acme_spi_init(void);

#endif
```

先包含 `uart.h` 后，`spi.h` 的内容会被跳过。

这不是“重复定义”，而是**声明缺失**，有时直到远处的调用点才报错。

防护措施：

- 保护宏与路径保持可识别对应关系。
- 自动检查保护宏唯一性。
- 每个公共头独立编译。
- 不把多个公开头错误地共用一个保护宏。

### 5.3 自包含头文件：自己包含自己需要的类型

错误设计：

```
#ifndef ACME_BUFFER_H_INCLUDED
#define ACME_BUFFER_H_INCLUDED

int acme_buffer_write(const uint8_t *data, size_t length);

#endif
```

它假设调用者已经包含 `<stdint.h>` 和 `<stddef.h>`。

正确设计：

```
#ifndef ACME_BUFFER_H_INCLUDED
#define ACME_BUFFER_H_INCLUDED

#include <stddef.h>
#include <stdint.h>

int acme_buffer_write(const uint8_t *data, size_t length);

#endif
```

判断标准非常直接：

```
#include "acme_buffer.h"

int main(void)
{
    return 0;
}
```

只包含这个头文件就应能编译。

不要手工前置声明标准库类型：

```
/* 不要自行猜测 size_t 的定义。 */
typedef unsigned int size_t;
```

这可能与目标 ABI 不一致。

### 5.4 实现文件首先包含自己的头文件

推荐：

```
/* acme_buffer.c */
#include "acme_buffer.h"

#include <string.h>
```

这样能尽早发现：

- 头文件缺少必要包含。
- 实现与声明参数类型不一致。
- 实现函数漏掉公共原型。
- 接口错误地依赖其他头先出现。

它不是完全验证，但成本低、收益明确。

### 5.5 前置声明：降低依赖，但必须尊重不完整类型规则

可以：

```
struct acme_bus;

int acme_sensor_attach(struct acme_bus *bus);
```

因为声明一个结构体指针，不需要知道结构体大小。

不可以：

```
struct acme_bus;

struct acme_sensor {
    struct acme_bus bus;
};
```

按值嵌入成员需要完整类型。

同样不可以：

```
struct acme_bus;

_Static_assert(sizeof(struct acme_bus) > 0u,
               "Incomplete type");
```

常见可用操作与限制：

|操作|不完整结构体是否允许|
|---|---|
|声明指针|允许|
|声明接收该指针的函数|允许|
|比较兼容指针、传递指针|允许|
|访问成员|不允许|
|`sizeof` 该结构体|不允许|
|按值定义对象|不允许|

**标准库内部类型、第三方未承诺稳定的标签名，不应自行前置声明。**

### 5.6 循环包含：保护宏只能止住递归，不能补全类型

假设：

```
/* a.h */
#include "b.h"

struct a {
    struct b peer;
};
```

```
/* b.h */
#include "a.h"

struct b {
    struct a owner;
};
```

即使添加保护宏，这个设计仍然不可能成立：两个结构体互相按值包含，尺寸没有有限解。

若关系本质是引用，改成指针：

```
/* a.h */
#ifndef ACME_A_H_INCLUDED
#define ACME_A_H_INCLUDED

struct b;

struct a {
    struct b *peer;
};

#endif
```

```
/* b.h */
#ifndef ACME_B_H_INCLUDED
#define ACME_B_H_INCLUDED

struct a;

struct b {
    struct a *owner;
};

#endif
```

随后必须补充生命周期规则：

- 谁创建对象。
- 谁拥有对象。
- 哪个对象先销毁。
- 指针能否为空。
- 解绑是否需要同步。

消除编译依赖并不自动解决运行期所有权。

### 5.7 函数声明必须是完整原型

C11/C17 中：

```
int acme_start();
```

表示没有提供参数类型信息，不等于明确声明“没有参数”。

推荐：

```
int acme_start(void);
```

有参数时完整写出：

```
int acme_read(unsigned int channel,
              uint8_t *destination,
              size_t capacity,
              size_t *actual);
```

不要依赖旧式声明让错误参数“先编译过去”。

C23 对空参数列表规则有变化，但 C11/C17 兼容工程仍应使用 `(void)`。

### 5.8 声明与定义分离：`extern` 的边界

头文件：

```
#ifndef ACME_BUILD_INFO_H_INCLUDED
#define ACME_BUILD_INFO_H_INCLUDED

#include <stdint.h>

extern const uint32_t acme_build_version;

#endif
```

实现文件：

```
#include "acme_build_info.h"

const uint32_t acme_build_version = UINT32_C(0x00010002);
```

注意：

```
extern const uint32_t acme_build_version = UINT32_C(1);
```

带初始化器的这个写法仍然是定义。**添加 `extern` 不会把一个带初始化器的对象自动变成纯声明。**

对于可变全局对象，建议先评估是否能封装：

```
uint32_t acme_get_error_count(void);
```

封装的实际价值包括：

- 可调整内部存储。
- 可加入同步。
- 可改变计数策略。
- 不暴露可写全局状态。

### 5.9 `const` 在 C 中不意味着内部链接

错误假设：

```
/* constants.h */
const unsigned int acme_retry_limit = 3u;
```

在 C 中，这通常定义具有外部链接的对象。多个翻译单元包含后可能产生重复定义。

可选方案：

```
#define ACME_RETRY_LIMIT 3u
```

或者：

```
enum {
    ACME_RETRY_LIMIT = 3
};
```

或者：

```
extern const unsigned int acme_retry_limit;
```

选择依据：

|需求|方案|
|---|---|
|预处理条件中使用|数值宏|
|C 整数常量表达式，值适合枚举|枚举|
|需要对象地址或导出符号|`extern const` + 单一定义|
|每个翻译单元允许独立副本|`static const`，审查尺寸和地址语义|

再次强调：**枚举可用于 C 常量表达式，不能直接作为 `#if` 的数值来源。**

### 5.10 `static inline`：适合小函数，不等于保证内联

```
#ifndef ACME_BITS_H_INCLUDED
#define ACME_BITS_H_INCLUDED

#include <stdint.h>

static inline uint32_t acme_clear_bits_u32(uint32_t value,
                                           uint32_t mask)
{
    return value & ~mask;
}

#endif
```

这个方案有两个特性：

- `static` 赋予内部链接，避免跨翻译单元外部定义冲突。
- `inline` 为实现提供内联建议和相关语言语义，**不保证最终没有调用指令**。

需要注意：

- 函数地址在不同翻译单元中不应被假设为同一地址。
- 未内联时可能每个翻译单元保留一份代码。
- 大函数放入头文件会扩大编译依赖。
- 内部静态状态可能形成每个翻译单元独立的副本。

不要随意把它简化成：

```
inline uint32_t acme_clear_bits_u32(uint32_t value,
                                    uint32_t mask)
{
    return value & ~mask;
}
```

C99/C11 的外部内联规则与 GNU89 模式不同。需要一个共享外部函数时，优先在 `.c` 中提供普通定义。

### 5.11 C/C++ 兼容：`extern "C"` 只处理语言链接

```
#ifndef ACME_TIMER_H_INCLUDED
#define ACME_TIMER_H_INCLUDED

#include <stdint.h>

#ifdef __cplusplus
extern "C" {
#endif

int acme_timer_start(uint32_t period_us);
void acme_timer_stop(void);

#ifdef __cplusplus
}
#endif

#endif
```

`extern "C"` 的主要作用是指定语言链接，避免 C++ 名字修饰等差异。

它不能自动解决：

- C++ 不接受的 C 语法。
- C 与 C++ 对某些类型和限定符的不同规则。
- 结构体布局和打包差异。
- 不同编译器的 ABI 差异。
- 异常跨 C 边界传播。
- 对象生命周期和并发问题。

公共 C/C++ 头文件应避免暴露：

- C 专属、C++ 不兼容的数组参数语法。
- 未封装的 `restrict`。
- 依赖特定语言布局的复杂类型。
- C++ 模板或标准库对象作为 C ABI 参数。

标准头文件通常放在 `extern "C"` 块外，减少无意改变第三方声明环境的风险。

### 5.12 静态断言：验证真实需要的假设

跨 C11/C++11 的小型兼容封装：

```
#ifndef ACME_COMPILE_ASSERT_H_INCLUDED
#define ACME_COMPILE_ASSERT_H_INCLUDED

#ifdef __cplusplus
#define ACME_STATIC_ASSERT(condition_, message_) \
    static_assert((condition_), message_)
#else
#define ACME_STATIC_ASSERT(condition_, message_) \
    _Static_assert((condition_), message_)
#endif

#endif
```

使用：

```
#include <limits.h>
#include <stdint.h>
#include "acme_compile_assert.h"

ACME_STATIC_ASSERT(CHAR_BIT == 8,
                   "This protocol requires eight-bit bytes");

ACME_STATIC_ASSERT(sizeof(uint32_t) == 4u,
                   "This interface requires four-byte uint32_t");
```

应避免没有必要地锁死：

```
_Static_assert(sizeof(void *) == 4u, "Requires 32-bit pointers");
```

只有接口确实依赖这个条件时才断言，否则会无端破坏主机测试和未来迁移。

**静态断言应验证设计前提，不能替代对设计前提本身的审查。**

### 5.13 编译器属性：增强检查，保留兼容退路

```
#ifndef ACME_ATTRIBUTES_H_INCLUDED
#define ACME_ATTRIBUTES_H_INCLUDED

#if defined(__has_attribute)
# if __has_attribute(warn_unused_result)
#  define ACME_WARN_UNUSED_RESULT \
       __attribute__((warn_unused_result))
# endif
#endif

#ifndef ACME_WARN_UNUSED_RESULT
#define ACME_WARN_UNUSED_RESULT
#endif

#endif
```

使用：

```
ACME_WARN_UNUSED_RESULT
int acme_storage_commit(void);
```

适合标记：

- Flash 写入。
- 持久化提交。
- 资源创建。
- 安全校验。
- 队列提交。

不要随便添加 `nonnull`：

```
/* 如果接口允许 data == NULL 且 length == 0，这个属性可能不合适。 */
```

某些属性不仅影响告警，也会影响优化器假设。**属性必须与运行期契约一致。**

## 6. 性能量化分析

### 6.1 头文件防护本身的运行期开销

保护宏、前置声明、函数原型等本身不生成运行期指令：

```
保护宏运行期成本 = 0
普通函数声明运行期成本 = 0
结构体前置声明运行期成本 = 0
静态断言通过后的运行期成本 = 0
```

但头文件中的定义、内联函数和数据副本可能产生实际开销。

### 6.2 头文件数据副本的空间模型

假设一个头文件包含：

```
static uint8_t acme_scratch[256];
```

有 12 个翻译单元使用各自副本，并且这些副本最终都被保留：

```
静态 RAM = 12 × 256 = 3072 字节
```

如果设计上只需要一个共享对象：

```
单实例 RAM = 256 字节

多余 RAM = 3072 − 256 = 2816 字节
```

这是**明确假设下的计算值**，最终结果还要检查：

- 是否真正被引用。
- 编译器是否删除未使用对象。
- 链接垃圾回收。
- 段对齐。
- LTO。

对于 `static const` 查表，可能出现只读存储副本；常量合并是否发生不能作为接口设计保证。

### 6.3 公开结构体与指针接口的尺寸

假设特定目标 ABI：

- 指针为 4 字节。
- `uint32_t` 为 4 字节。
- 指针对齐为 4 字节。

```
typedef struct {
    uint32_t flags;
    uint32_t count;
    void *backend;
} acme_public_context_t;
```

在上述 ABI 下，常见结果为：

```
sizeof(acme_public_context_t) = 12 字节
```

但不能据此推断所有目标都是 12 字节。应在目标构建中验证：

```
_Static_assert(sizeof(acme_public_context_t) == 12u,
               "Unexpected ABI layout");
```

该断言只应出现在确实承诺这种布局的 ABI 场景中。

### 6.4 不透明类型是否必然变慢

不必然。

以下接口：

```
int acme_device_read(acme_device_t *device,
                     uint8_t *data,
                     size_t length);
```

并不天然增加一次函数指针跳转。对象不透明与是否使用虚表、函数表是不同问题。

可能的成本来自：

- 不能在调用方直接展开内部操作。
- 跨库优化受限。
- 为访问字段增加函数调用。
- 动态分配或对象池管理。

可能的收益包括：

- 降低全工程重编译范围。
- 避免错误直接访问。
- 保持 ABI 稳定。
- 允许实现内部优化。

对高频路径，可以采用“稳定外部接口 + 少量公开值类型 + 局部内联辅助函数”的组合。

### 6.5 编译时间模型

可用以下近似模型分析：

```
总前端处理成本 ≈
Σ 每个翻译单元实际处理的头文件成本
```

假设：

- 80 个源文件包含某公共头。
- 该头又引入大型协议、RTOS 和驱动头。
- 修改其中一个公开依赖导致 80 个对象失效。

将依赖移入 `.c` 后，可能只重编译少量实现文件。

但不能直接按头文件行数给出固定毫秒收益，因为还取决于：

- 文件系统缓存。
- 编译器。
- 宏展开复杂度。
- 调试信息。
- 并行构建。
- 预编译头。
- 编译缓存。

### 6.6 实测要求与结果边界

当前没有目标板和构建产物，本课不提供虚构的实测周期或编译时间。

建议实测平台至少记录：

|项目|记录内容|
|---|---|
|目标|MCU、主频、缓存、Flash 等待周期|
|编译器|名称、版本、C 标准模式|
|优化|`-O0/-O2/-Os`、LTO|
|链接|段垃圾回收、链接脚本|
|代码|翻译单元数、头文件依赖关系|
|构建|干净构建与增量构建分别测量|
|产物|`.text`、`.rodata`、`.data`、`.bss`|
|调用|实际反汇编和周期统计|

**头文件优化的收益应同时报告构建成本和目标产物变化。**

## 7. 应用场景选型指南

### 7.1 纯文本决策流程图

```
这个文件是否用于重复生成代码？
├─ 是
│  ├─ X-macro 清单 → 明确允许多次包含，使用 .def/.inc 等约定
│  └─ 普通接口头 → 重新审查设计
└─ 否
   └─ 添加唯一头文件保护

接口是否需要知道某个结构体内部布局？
├─ 否
│  └─ 前置声明 / 不透明类型
└─ 是
   ├─ 只是输入输出数据载体 → 公开稳定值类型
   └─ 是内部运行状态 → 评估是否应隐藏

对象是否必须由调用者直接放在栈上？
├─ 是
│  ├─ 可接受布局公开 → 公开结构体
│  └─ 必须隐藏布局 → 专门设计存储与对齐协议
└─ 否
   ├─ 允许动态分配 → create/destroy
   └─ 禁止动态分配 → 静态对象池 / 句柄

接口是否跨 C/C++ 或预编译库边界？
├─ 是 → 语言链接 + ABI 约束 + 兼容性验证
└─ 否 → 仍保持完整原型和一致配置
```

### 7.2 场景选型表

|场景|推荐方案|理由|
|---|---|---|
|通用驱动 SDK|保护宏、自包含、不透明句柄|降低集成成本和实现耦合|
|ISR 小型位运算|`static inline`|类型安全，适合局部优化|
|协议字段值对象|明确宽度的公开结构体|数据语义简单，可审查|
|网络报文直接映射|通常用字节解析函数|避免对齐、字节序和布局假设|
|大型查找表|头文件 `extern const`，源文件定义|避免副本与重复定义|
|无堆安全关键系统|静态对象池或公开受控对象|内存行为确定|
|多团队预编译库|不透明类型、版本查询|控制 ABI 演进|
|X-macro 数据清单|有意重复包含的清单文件|与普通接口头区别处理|

## 8. 工程最佳实践

### 8.1 头文件只暴露使用者真正需要的内容

公共头中通常可以出现：

- 类型声明。
- 稳定值类型。
- 函数原型。
- 必要常量。
- 小型 `static inline`。
- 与接口直接相关的编译期检查。

通常不应出现：

- 私有 RTOS 控制块。
- 驱动内部寄存器操作序列。
- 大型数据定义。
- 私有分配器状态。
- 业务内部全局变量。
- 无关平台配置。

### 8.2 明确每个指针的契约

一个生产接口至少应说明：

```
/*
 * data:
 *   May be NULL only when length is zero.
 *
 * length:
 *   Number of readable bytes at data.
 *
 * Ownership:
 *   Caller retains ownership.
 *
 * Lifetime:
 *   Implementation does not retain data after return.
 *
 * Concurrency:
 *   Caller must serialize operations on the same object.
 */
```

`const uint8_t *` 只限制通过该指针修改所指对象，不能表达：

- 指针一定有效。
- 缓冲区足够长。
- 内存不会被 DMA 改写。
- 另一个线程不会并发修改。
- 对象一定处于有效生命周期。

### 8.3 长度与缓冲区一起设计

推荐：

```
int acme_read(uint8_t *destination,
              size_t capacity,
              size_t *actual);
```

不推荐：

```
int acme_read(uint8_t *destination);
```

除非目标大小由一个严格且可验证的接口契约固定。

输出参数还要规定：

- 失败时是否修改。
- 是否保证写零。
- 是否允许为空。
- 部分成功如何表达。

### 8.4 避免公共头泄漏打包状态

工具链扩展示例：

```
#pragma pack(push, 1)

typedef struct {
    uint8_t kind;
    uint32_t value;
} acme_packed_record_t;

#pragma pack(pop)
```

这里必须成对恢复状态，但仍存在：

- 非标准扩展。
- 非对齐访问。
- 字节序。
- ABI 和代码生成变化。

**公共协议通常优先使用显式序列化，而不是依赖 packed 结构体。**

更不能在头文件开头写一个 `#pragma pack(1)`，然后忘记恢复，影响调用方后续所有结构体。

### 8.5 避免命名空间污染

C 没有模块命名空间，因此统一前缀尤其重要：

```
acme_uart_open
acme_uart_status_t
ACME_UART_MAX_FRAME
```

避免公开：

```
read
ERROR
MIN
VERSION
```

枚举成员也处于普通标识符命名空间，不能因为它写在枚举内部就假设不会冲突。

### 8.6 不随意修改调用方宏环境

危险做法：

```
#undef assert
#define malloc app_malloc
#define DEBUG 1
```

公共头不应悄悄接管调用者的通用宏。

X-macro 等局部辅助宏应在使用后清理：

```
#define ACME_ENTRY(name_) /* expansion */
/* use */
#undef ACME_ENTRY
```

公开配置宏则按文档保持，不要无规则地定义和取消。

### 8.7 选型决策矩阵

|设计目标|优先方案|需要特别审查|
|---|---|---|
|最大可移植性|标准保护宏、标准类型|厂商 pragma|
|减少依赖|前置声明、不透明类型|按值嵌入|
|稳定 ABI|不透明对象、固定边界类型|条件字段、裸枚举 ABI|
|确定内存|静态池、调用方受控分配|通用堆|
|热路径性能|小型 `static inline`|大函数头文件化|
|减少共享状态|对象实例、访问函数|公开可写全局|
|跨语言|简单 C ABI|C++ 类型、异常跨边界|

### 8.8 头文件发布前检查

- 能否单独作为第一个头文件包含。
- 能否重复包含。
- 与其他公共头交换顺序后是否仍可编译。
- 是否引入意外对象定义。
- 是否改变调用方打包、诊断或宏状态。
- 是否依赖某个源文件先定义配置。
- 是否暴露不必要的内部类型。
- 是否明确并发和所有权。
- 是否能在所有受支持语言模式下编译。

## 9. 常见错误与避坑指南

### 9.1 错误一：保护宏重名

**错误代码：**

```
/* Both uart.h and spi.h use this. */
#ifndef ACME_DRIVER_H
#define ACME_DRIVER_H

/* declarations */

#endif
```

**根因：** 复制模板后没有修改保护宏。

**正确实现：**

```
#ifndef ACME_DRIVER_UART_H_INCLUDED
#define ACME_DRIVER_UART_H_INCLUDED

/* UART declarations */

#endif
```

**风险影响：**

- 声明被静默屏蔽。
- 故障与包含顺序有关。
- 错误位置远离根因。

---

### 9.2 错误二：在头文件定义全局变量

**错误代码：**

```
#ifndef ACME_STATS_H_INCLUDED
#define ACME_STATS_H_INCLUDED

unsigned int acme_error_count = 0u;

#endif
```

**根因：** 每个翻译单元都产生外部定义。

**正确实现：**

```
/* acme_stats.h */
extern unsigned int acme_error_count;
```

```
/* acme_stats.c */
#include "acme_stats.h"

unsigned int acme_error_count = 0u;
```

更好的封装通常是访问函数。

**风险影响：**

- 重复定义链接失败。
- 为“修复”而改成 `static` 后，变成多份独立状态。
- 若计数被 ISR 与任务同时访问，还存在并发问题。

---

### 9.3 错误三：依赖传递包含

**错误代码：**

```
/* acme_packet.h */
int acme_packet_send(const uint8_t *data, size_t length);
```

项目恰好先包含另一个头，因此暂时不报错。

**根因：** 把偶然的包含关系当成接口保证。

**正确实现：**

```
#include <stddef.h>
#include <stdint.h>

int acme_packet_send(const uint8_t *data, size_t length);
```

**风险影响：**

- 重排包含顺序后失败。
- 上游库清理依赖后，下游突然无法编译。
- SDK 使用者必须猜测隐含前提。

---

### 9.4 错误四：用 `static` 隐藏重复定义问题

**错误代码：**

```
/* acme_counter.h */
static unsigned int acme_counter;

static inline void acme_counter_increment(void)
{
    ++acme_counter;
}
```

**根因：** 每个翻译单元拥有自己的计数器。

**正确实现：**

```
/* acme_counter.h */
void acme_counter_increment(void);
unsigned int acme_counter_get(void);
```

在一个实现文件中保存状态，并根据调用上下文实现同步。

**风险影响：**

- 模块 A 增加计数，模块 B 读取却为零。
- RAM 副本增加。
- 调试器看到多个同名局部符号，定位困难。

---

### 9.5 错误五：公共结构体字段受配置控制

**错误代码：**

```
typedef struct {
    uint32_t state;

#if CONFIG_ENABLE_STATS
    uint32_t dropped;
#endif

    uint32_t errors;
} acme_device_t;
```

**根因：** 不同模块可能以不同布局解释同一对象。

**正确实现：**

```
typedef struct acme_device acme_device_t;

int acme_device_get_errors(const acme_device_t *device,
                           uint32_t *errors);
```

或者明确固定公开布局，并统一所有构建配置。

**风险影响：**

- 错误字段访问。
- 越界读写。
- 预编译库与应用不兼容但链接仍成功。

---

### 9.6 错误六：函数声明未提供参数原型

**错误代码：**

```
int acme_device_open();
```

**根因：** 在 C11/C17 中，它没有明确约束参数列表。

**正确实现：**

```
int acme_device_open(void);
```

或者：

```
int acme_device_open(unsigned int instance);
```

**风险影响：**

- 参数错误更难被及时发现。
- 混用旧代码、不同调用约定时风险增大。

---

### 9.7 错误七：把声明属性当成实际校验

**错误代码：**

```
int acme_write(const uint8_t *data, size_t length)
    __attribute__((nonnull(1)));
```

同时文档却允许零长度时传空指针。

**根因：** 属性契约与实际接口约定冲突。

**正确实现：**

```
int acme_write(const uint8_t *data, size_t length);
```

实现中：

```
if ((data == NULL) && (length != 0u)) {
    return -1;
}
```

**风险影响：**

- 编译器基于属性做出与接口预期不同的优化。
- 调用方收到矛盾诊断。
- 运行期检查不能可靠补救错误的编译期假设。

---

## 10. 多机制组合使用方案

下面实现一个**不透明字节缓冲区模块**，组合使用：

- 唯一保护宏。
- 自包含头文件。
- C/C++ 兼容。
- 不透明对象。
- 明确长度和所有权。
- 参数检查。
- 有界资源。
- 失败清理。
- 状态返回。

示例是**单上下文或外部串行化使用的 FIFO**，不提供内部线程同步，也不适用于 ISR 调用创建和销毁接口。

### 10.1 公共头文件

```
/* acme_byte_fifo.h */
#ifndef ACME_BYTE_FIFO_H_INCLUDED
#define ACME_BYTE_FIFO_H_INCLUDED

#include <stddef.h>
#include <stdint.h>

#ifdef __cplusplus
extern "C" {
#endif

typedef struct acme_byte_fifo acme_byte_fifo_t;

typedef enum {
    ACME_FIFO_OK = 0,
    ACME_FIFO_INVALID,
    ACME_FIFO_NO_MEMORY,
    ACME_FIFO_NO_SPACE,
    ACME_FIFO_NO_DATA
} acme_fifo_status_t;

/*
 * capacity must be greater than zero.
 *
 * On failure, *out_fifo is set to NULL when out_fifo is valid.
 * The caller owns the returned object.
 *
 * This interface uses dynamic allocation.
 */
acme_fifo_status_t acme_byte_fifo_create(
    size_t capacity,
    acme_byte_fifo_t **out_fifo);

/*
 * Accepts NULL.
 * Caller must ensure no concurrent operations are active.
 * Other aliases to the object become invalid.
 */
void acme_byte_fifo_destroy(acme_byte_fifo_t *fifo);

/*
 * All-or-nothing write.
 * data may be NULL only when length is zero.
 * Source memory must not overlap internal FIFO storage.
 * The implementation retains no reference to data.
 *
 * Calls on the same FIFO require external serialization.
 */
acme_fifo_status_t acme_byte_fifo_write(
    acme_byte_fifo_t *fifo,
    const uint8_t *data,
    size_t length);

/*
 * All-or-nothing read.
 * destination may be NULL only when length is zero.
 * Destination memory must not overlap internal FIFO storage.
 *
 * On insufficient data, destination is unchanged.
 */
acme_fifo_status_t acme_byte_fifo_read(
    acme_byte_fifo_t *fifo,
    uint8_t *destination,
    size_t length);

#ifdef __cplusplus
}
#endif

#endif /* ACME_BYTE_FIFO_H_INCLUDED */
```

这里的状态枚举适合同一受控 C 工具链体系。若跨不同枚举 ABI 的预编译边界，应统一 ABI 编译选项，或改用固定宽度状态类型与数值常量。

### 10.2 实现文件

```
/* acme_byte_fifo.c */
#include "acme_byte_fifo.h"

#include <limits.h>
#include <stdlib.h>
#include <string.h>

_Static_assert(CHAR_BIT == 8,
               "Byte FIFO requires eight-bit bytes");

struct acme_byte_fifo {
    uint8_t *storage;
    size_t capacity;
    size_t read_index;
    size_t write_index;
    size_t used;
};

/*
 * Preconditions:
 *   index < capacity
 *   amount <= capacity
 *
 * Avoids index + amount overflow.
 */
static size_t acme_fifo_advance(size_t index,
                               size_t amount,
                               size_t capacity)
{
    const size_t to_end = capacity - index;

    if (amount < to_end) {
        return index + amount;
    }

    return amount - to_end;
}

acme_fifo_status_t acme_byte_fifo_create(
    size_t capacity,
    acme_byte_fifo_t **out_fifo)
{
    acme_byte_fifo_t *fifo;

    if (out_fifo == NULL) {
        return ACME_FIFO_INVALID;
    }

    *out_fifo = NULL;

    if (capacity == 0u) {
        return ACME_FIFO_INVALID;
    }

    fifo = malloc(sizeof(*fifo));
    if (fifo == NULL) {
        return ACME_FIFO_NO_MEMORY;
    }

    fifo->storage = malloc(capacity);
    if (fifo->storage == NULL) {
        free(fifo);
        return ACME_FIFO_NO_MEMORY;
    }

    fifo->capacity = capacity;
    fifo->read_index = 0u;
    fifo->write_index = 0u;
    fifo->used = 0u;

    *out_fifo = fifo;
    return ACME_FIFO_OK;
}

void acme_byte_fifo_destroy(acme_byte_fifo_t *fifo)
{
    if (fifo == NULL) {
        return;
    }

    free(fifo->storage);
    free(fifo);
}

acme_fifo_status_t acme_byte_fifo_write(
    acme_byte_fifo_t *fifo,
    const uint8_t *data,
    size_t length)
{
    size_t first;

    if (fifo == NULL) {
        return ACME_FIFO_INVALID;
    }

    if ((data == NULL) && (length != 0u)) {
        return ACME_FIFO_INVALID;
    }

    if (length > (fifo->capacity - fifo->used)) {
        return ACME_FIFO_NO_SPACE;
    }

    if (length == 0u) {
        return ACME_FIFO_OK;
    }

    first = fifo->capacity - fifo->write_index;
    if (first > length) {
        first = length;
    }

    (void)memcpy(fifo->storage + fifo->write_index,
                 data,
                 first);

    if (length > first) {
        (void)memcpy(fifo->storage,
                     data + first,
                     length - first);
    }

    fifo->write_index = acme_fifo_advance(
        fifo->write_index, length, fifo->capacity);
    fifo->used += length;

    return ACME_FIFO_OK;
}

acme_fifo_status_t acme_byte_fifo_read(
    acme_byte_fifo_t *fifo,
    uint8_t *destination,
    size_t length)
{
    size_t first;

    if (fifo == NULL) {
        return ACME_FIFO_INVALID;
    }

    if ((destination == NULL) && (length != 0u)) {
        return ACME_FIFO_INVALID;
    }

    if (length > fifo->used) {
        return ACME_FIFO_NO_DATA;
    }

    if (length == 0u) {
        return ACME_FIFO_OK;
    }

    first = fifo->capacity - fifo->read_index;
    if (first > length) {
        first = length;
    }

    (void)memcpy(destination,
                 fifo->storage + fifo->read_index,
                 first);

    if (length > first) {
        (void)memcpy(destination + first,
                     fifo->storage,
                     length - first);
    }

    fifo->read_index = acme_fifo_advance(
        fifo->read_index, length, fifo->capacity);
    fifo->used -= length;

    return ACME_FIFO_OK;
}
```

### 10.3 防卫点分析

|防卫点|实现位置|作用|
|---|---|---|
|重复包含|保护宏|避免重复类型定义|
|缺失依赖|标准头直接包含|保证自包含|
|内部字段误用|不透明结构体|调用方无法直接修改索引|
|空指针|每个入口校验|防止明显无效调用|
|零长度空指针|显式提前返回|不把空指针交给 `memcpy`|
|分配失败|两阶段清理|避免泄漏|
|容量不足|写前检查|保证全写或不写|
|数据不足|读前检查|保证输出不被部分修改|
|索引加法溢出|差值推进算法|避免直接计算大和|
|并发误用|明确外部串行化契约|不把普通 FIFO 宣称为线程安全|

这个接口不能检测任意悬空指针。`destroy()` 后再次使用旧别名仍然是调用错误。

**C 中的防卫式接口可以降低误用概率，不能把任意无效地址安全地“校验成有效对象”。**

### 10.4 无堆系统的替代设计

若禁止动态分配，可以采用：

```
typedef uint32_t acme_fifo_handle_t;

acme_fifo_status_t acme_fifo_pool_acquire(
    acme_fifo_handle_t *handle);

acme_fifo_status_t acme_fifo_pool_release(
    acme_fifo_handle_t handle);
```

内部静态池需要进一步处理：

- 固定容量。
- 对象占用状态。
- 句柄索引。
- 代际编号。
- 释放后旧句柄。
- 并发访问。
- 初始化时序。

不应简单把任意 `uint8_t storage[N]` 强转为私有结构体后就声称解决了静态内存问题。还要审查**对齐、有效类型、对象生命周期和容量版本**。

## 11. 工业级实际案例分析

以下是工业领域中的典型场景设计，不将示例描述为未经验证的具体企业项目。

### 11.1 案例一：多 RTOS 驱动 SDK 的公共头依赖失控

#### 需求

同一传感器驱动支持：

- 裸机。
- FreeRTOS。
- 另一套商业 RTOS。

原始公共头直接包含 RTOS 头：

```
#include "FreeRTOS.h"
#include "semphr.h"
```

导致裸机用户无法使用，SDK 更新还会传播 RTOS 配置变化。

#### 架构设计

- 公共头只暴露驱动接口。
- 同步对象保留在私有实现。
- RTOS 适配放在平台源文件。
- 明确驱动调用上下文。

#### 核心代码

```
#ifndef ACME_SENSOR_H_INCLUDED
#define ACME_SENSOR_H_INCLUDED

#include <stdint.h>

typedef struct acme_sensor acme_sensor_t;

typedef struct {
    int32_t temperature_milli_c;
    uint32_t timestamp_us;
} acme_sensor_sample_t;

/*
 * Task-context synchronous call.
 * Not callable from ISR.
 * Output is unchanged on failure.
 */
int acme_sensor_read(acme_sensor_t *sensor,
                     acme_sensor_sample_t *sample);

#endif
```

#### 设计要点

- `acme_sensor_t` 内部可以保存不同 RTOS 的锁。
- 公共数据不暴露 RTOS 类型。
- 时间戳宽度、回绕语义和单位必须明确。
- 不透明类型不自动带来线程安全；同步语义仍需单独设计。

### 11.2 案例二：工业协议栈使用打包结构体直接映射报文

#### 需求

网络报文含：

- 1 字节消息类型。
- 2 字节长度。
- 4 字节序号。

原始实现通过 packed 结构体和指针强转访问。

问题包括：

- 字节序错误。
- 非对齐访问。
- 头文件泄漏打包状态。
- 输入长度不足。
- 结构体访问和实际对象类型不匹配。

#### 架构设计

公开逻辑值类型，报文解析通过字节读取完成。

#### 核心代码

```
#include <stddef.h>
#include <stdint.h>

typedef struct {
    uint8_t kind;
    uint16_t payload_length;
    uint32_t sequence;
} acme_message_header_t;

static inline uint16_t acme_load_be16(const uint8_t *data)
{
    return (uint16_t)(
        ((uint16_t)data[0] << 8) |
        (uint16_t)data[1]);
}

static inline uint32_t acme_load_be32(const uint8_t *data)
{
    return ((uint32_t)data[0] << 24) |
           ((uint32_t)data[1] << 16) |
           ((uint32_t)data[2] << 8) |
           (uint32_t)data[3];
}

int acme_parse_message_header(const uint8_t *data,
                              size_t length,
                              acme_message_header_t *out)
{
    acme_message_header_t result;

    if ((data == NULL) || (out == NULL)) {
        return -1;
    }

    if (length < 7u) {
        return -1;
    }

    result.kind = data[0];
    result.payload_length = acme_load_be16(data + 1u);
    result.sequence = acme_load_be32(data + 3u);

    *out = result;
    return 0;
}
```

实际模块中将类型和函数原型放头文件，解析实现放 `.c`。字节加载辅助函数可以保留为模块私有函数。

#### 设计要点

- 线格式大小是 **7 字节**，不依赖 `sizeof(acme_message_header_t)`。
- 输出结构体只是逻辑表示，不要求与报文字节布局一致。
- 出错前不修改输出。
- 是否需要检查完整 payload 长度，由解析接口职责决定。
- 需要校验类型值和协议版本时，在完整解析层追加检查。

### 11.3 案例三：设备厂商向第三方提供预编译升级库

#### 需求

升级库被多个团队集成，希望后续版本增加内部状态时不强制改动调用方。

原始接口：

```
typedef struct {
    uint32_t state;
    uint32_t image_size;
    uint32_t offset;
} acme_updater_t;
```

新版增加校验上下文后，对象大小变化，旧应用仍按旧大小分配。

#### 架构设计

- 升级上下文不透明。
- 输入参数使用稳定值类型。
- 公开版本和能力查询。
- 创建、销毁与调用约定由库负责。
- 升级镜像的实际 Flash 分区由平台接口约束。

#### 核心声明

```
#ifndef ACME_UPDATER_H_INCLUDED
#define ACME_UPDATER_H_INCLUDED

#include <stddef.h>
#include <stdint.h>

typedef struct acme_updater acme_updater_t;

typedef struct {
    uint32_t abi_version;
    uint32_t capability_bits;
} acme_updater_info_t;

int acme_updater_get_info(acme_updater_info_t *info);

int acme_updater_begin(acme_updater_t *updater,
                       uint32_t image_size);

int acme_updater_feed(acme_updater_t *updater,
                      const uint8_t *data,
                      size_t length);

int acme_updater_finish(acme_updater_t *updater);

#endif
```

#### 设计要点

- 上述只是核心操作接口；对象获得方式需由库另行提供。
- `feed()` 是否复制数据、何时完成写入，必须明确。
- `finish()` 不能在验证失败时伪装成功。
- 动态库或不同运行库边界中，分配和释放应由同一模块配对。
- 不透明类型只能隔离私有布局，不能掩盖 CPU/FPU ABI、调用约定和标准库不一致。

## 12. 高频问题深度答疑

### 12.1 有了 `#pragma once`，还需要保护宏吗？

如果团队明确只支持经过验证的工具链，使用 `#pragma once` 可以满足需求。

但面向长期维护、多编译器或第三方 SDK，保护宏更容易表达标准可移植性。

二者一起使用不会让接口天然更安全：

- 保护宏冲突仍然存在。
- 头文件中错误的全局定义仍然存在。
- ABI 不一致仍然存在。

选择一种明确规范并验证，比无规则叠加更有价值。

### 12.2 为什么不建议所有依赖都放到一个公共“大头文件”里？

因为它会掩盖真实依赖：

```
#include "everything.h"
```

短期内不容易缺类型，长期会造成：

- 修改一个底层头，大量源文件重编译。
- 模块无法单独复用。
- 平台专属类型污染通用接口。
- 循环依赖不易察觉。
- 使用者不知道某个声明来自哪里。

预编译头可以作为构建优化，但不能替代头文件自包含和直接依赖管理。

### 12.3 不透明类型与禁止动态内存是否冲突？

不冲突。

可以使用：

- 静态对象池。
- 模块级单实例。
- 句柄表。
- 受控专用分配器。
- 经严格设计的调用方存储协议。

真正的权衡是：

- 是否要求调用方直接知道对象尺寸。
- 是否需要任意数量实例。
- 是否允许构建时确定容量。
- 是否需要跨版本二进制兼容。

不透明类型是一种封装机制，不是一种分配策略。

### 12.4 为什么不在头文件里声明所有全局变量，方便访问？

因为公开可写全局会把同步与状态约束扩散到所有调用方。

例如：

```
extern volatile uint32_t acme_error_count;
```

`volatile` 不能保证：

- 自增是原子的。
- 多字段状态一致。
- 任务与 ISR 不丢更新。
- 多核缓存一致性。

访问函数可以集中实施同步和约束。真正需要共享 MMIO 或平台状态时，也应限制可见范围。

### 12.5 `const` 指针、`restrict`、数组参数能否保证安全？

不能独立保证。

```
int acme_copy(uint8_t *destination,
              const uint8_t *source,
              size_t length);
```

仍然需要保证：

- 源和目标至少有 `length` 字节。
- 生命周期有效。
- 若实现使用 `memcpy`，相关区域不重叠。

C 的数组参数：

```
void acme_process(uint8_t data[16]);
```

作为函数参数会调整为指针，不能自动验证调用方确实提供了 16 字节。

C99 的：

```
void acme_process(uint8_t data[static 16]);
```

表达更强的调用前提，但不是运行期边界检查，并且不适合直接放进要求 C++ 兼容的公共接口。

### 12.6 为什么推荐实现文件先包含自己的头，而不是先包含系统头？

因为先包含系统头可能掩盖自身头文件缺少依赖。

同时，先包含自己的头能让编译器尽早比较声明与定义。

但仍需独立头文件测试，因为：

- 某些构建会强制包含全局头。
- 预编译头可能已经提供类型。
- 编译命令可能预定义宏。
- 当前源文件未必覆盖所有条件分支。

**“自己的头先包含”是日常约束，独立编译是验证手段。**

## 13. 课程核心总结

### 13.1 核心要点

- **保护宏解决单个翻译单元的重复处理问题。**
- **声明与定义分离，才是避免跨翻译单元重复符号的关键。**
- **头文件必须直接包含自身声明需要的依赖。**
- **前置声明用于降低依赖，不完整类型的限制必须遵守。**
- **不透明类型能隔离内部布局，不能自动解决分配、并发和 ABI 的全部问题。**
- **`static inline` 适合小型辅助函数，不保证内联，也不保证全工程只有一份实体。**
- **C/C++ 兼容需要语言链接和语法、类型、ABI 的共同兼容。**
- **指针、长度、所有权、生命周期与并发约束是接口的一部分。**

### 13.2 性能排序与边界

运行期方面：

```
纯声明 / 保护宏 / 静态断言：
    本身不产生运行期指令

static inline：
    可能内联，也可能形成局部调用或多份代码

普通外部函数：
    成本取决于调用、优化、LTO 和具体实现

不透明接口：
    不天然增加间接调用，但可能限制调用方可见优化
```

工程上应优先优化：

1. 意外数据副本。
2. 热路径中的真实调用成本。
3. 大型头文件带来的编译依赖。
4. 公开布局导致的 ABI 与重构成本。

### 13.3 通用选型结论

|目标|推荐|
|---|---|
|普通公共头|唯一保护宏、自包含|
|小型纯计算辅助函数|`static inline`|
|大型表|`extern const` + `.c` 定义|
|模块内部状态|不透明类型|
|简单输入输出数据|稳定公开值类型|
|无堆多实例|静态池或句柄|
|跨语言|简单 C ABI + `extern "C"`|
|跨版本预编译库|不透明对象 + ABI 管理|
|协议解析|字节级编解码，避免直接结构体映射|

## 16. 实践与进阶路径

### 16.1 初阶：头文件独立性检查

为每个公共头建立最小文件：

```
#include "acme_module.h"

int main(void)
{
    return 0;
}
```

再建立重复包含文件：

```
#include "acme_module.h"
#include "acme_module.h"

int main(void)
{
    return 0;
}
```

对每个受支持产品配置编译。

**验收标准：不依赖预编译头、强制包含文件或其他公共头就能通过。**

### 16.2 中阶：构造声明与定义实验

分别把以下内容放入头文件，再让两个 `.c` 文件包含：

```
int acme_a;
```

```
int acme_b = 0;
```

```
static int acme_c;
```

```
const int acme_d = 1;
```

```
extern const int acme_e;
```

观察：

- 编译是否成功。
- 链接是否成功。
- 符号是全局还是局部。
- 是否出现多个副本。

GCC 可额外比较 `-fcommon` 与 `-fno-common` 对暂定定义的影响。不能把某种模式下“能链接”当成正确的模块设计。

### 16.3 工程任务：公开对象改为不透明对象

选取一个驱动上下文：

1. 列出调用方真正需要的操作。
2. 将内部结构体移入 `.c`。
3. 提供创建/初始化和销毁/释放路径。
4. 明确分配策略。
5. 清除调用方直接字段访问。
6. 为查询、修改和错误处理建立接口。
7. 比较重构前后的依赖与增量构建范围。

**验收标准：修改私有字段时，公共头无需变化。**

### 16.4 性能测试方法

测试两种设计：

- 公共头包含大型依赖并定义查找表。
- 精简公共头，查找表放源文件。

记录：

- 干净构建时间。
- 修改私有实现后的增量构建时间。
- 修改公共接口后的增量构建时间。
- `.text`、`.rodata`、`.data`、`.bss`。
- 符号数量和副本。
- 热路径反汇编。
- 目标周期和栈使用。

固定工具链、优化和构建并行度，并区分冷缓存与热缓存。

### 16.5 CI 验证任务

建议建立以下检查：

```
公共头枚举
  ↓
保护宏唯一性检查
  ↓
每个头单独包含
  ↓
每个头重复包含
  ↓
关键头交换包含顺序
  ↓
C / C++ 兼容编译
  ↓
受支持配置矩阵编译
  ↓
符号与存储尺寸检查
  ↓
ABI 与预编译库兼容检查
```

负向检查也很重要：

- 不完整类型按值使用应失败。
- 缺少必要配置应失败。
- 意外重复外部定义应失败。
- 不支持的 ABI 组合应被拒绝。
- 必须处理的错误结果应触发项目规定的诊断。

### 16.6 进阶方向

- C99/C11 内联语义与 GNU89 内联差异。
- 公共 ABI 版本化和共享库符号管理。
- 对齐、有效类型与调用方存储对象的合法构造。
- 句柄代际编号和释放后使用防护。
- 编译器属性与静态分析契约。
- 生成式头文件、配置指纹和可复现构建。
- 头文件依赖图治理与增量构建优化。
- 安全关键编码规范中的接口、全局状态与头文件规则。
