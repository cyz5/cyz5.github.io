
条件编译的核心任务，是在**编译前确定产品能力、硬件依赖、软件依赖与接口契约**，让非法配置尽早失败，让合法配置生成可预测、可验证的固件。

对于工业嵌入式工程，条件编译的难点通常不在 `#if` 的语法，而在以下问题：

- 配置来自构建系统、板级头文件和命令行时，谁拥有最终解释权？
- 关闭某个功能后，调用参数是否仍有副作用？
- 某个宏在不同源文件中取值不一致，是否会破坏结构体布局和库 ABI？
- 仿真、量产、诊断、安全版本是否真正构建并验证过？
- 软件认为关闭的功能，是否仍通过链接脚本、预编译库或启动代码进入镜像？
- 编译器能识别某个关键字，是否意味着目标硬件和运行库也支持对应能力？

本课以 **C11/C17 为主要工程基线**，单独说明 C23 和常见编译器扩展。代码默认使用符合标准的 C；涉及构建系统、链接器和平台后端的位置，会明确标出边界。

## 1. 学习目标

### 1.1 理解

- 理解条件编译所处的翻译阶段，以及它与运行期分支、优化器死代码删除的区别。
- 理解 `#if`、`#ifdef`、`#ifndef`、`#elif`、`#else`、`#endif` 的精确语义。
- 理解预处理整数表达式与 C 语言整数常量表达式的差异。
- 理解“宏是否存在”和“宏值是否启用”是两个不同维度。
- 理解配置如何影响代码、数据、依赖、ABI 和测试空间。

### 1.2 掌握

- 掌握布尔配置、枚举配置、数值配置、能力宏的命名和校验方式。
- 掌握统一配置入口、默认值、覆盖顺序和非法组合检查。
- 掌握跨编译器、跨操作系统、跨 MCU 的能力检测方式。
- 掌握功能关闭时的接口设计、副作用约束和构建验证方法。

### 1.3 精通

- 能定位由于未定义宏、枚举常量、头文件顺序和翻译单元配置不一致引发的缺陷。
- 能识别配置导致的结构体布局、调用约定和预编译库兼容性风险。
- 能建立配置矩阵、预处理检查、符号检查和镜像差异分析流程。
- 能判断一个差异应该通过条件编译、运行期参数、函数表还是独立源文件解决。

### 1.4 能够设计

- 设计面向多产品、多板卡、多工具链的配置架构。
- 设计具有依赖校验、资源校验和版本追踪能力的产品配置系统。
- 设计可裁剪模块，使其关闭后行为明确、接口稳定、残留可检查。
- 设计与启动代码、链接脚本、运行库和 RTOS 配置一致的构建契约。

- 能阅读预处理输出和编译器诊断。

## 3. 技术概述

### 3.1 条件编译发生在哪里

可以用以下简化过程理解：

```
源文件
  ↓
字符处理、续行、形成预处理记号、注释处理
  ↓
执行 #include、宏展开、条件包含
  ↓
生成保留分支的记号序列
  ↓
C 语法分析、类型检查、优化
  ↓
汇编、链接
```

这里的关键边界是：

> **不保留的条件分支通常不进入 C 语法与类型检查，但源文件仍然必须满足前期词法处理和条件指令配对的要求。**

例如：

```
#if 0
this is not valid C syntax;
#endif
```

通常可以通过预处理，因为这些记号被丢弃。

但不能因此在禁用分支中放入未闭合注释、未终止字符串等词法错误。

### 3.2 条件编译的三种核心价值

|价值|解决的问题|典型用途|
|---|---|---|
|依赖隔离|某平台没有相关头文件、寄存器或运行库|裸机与 RTOS、不同 MCU 驱动|
|产品裁剪|镜像不能包含某项代码或数据|关闭浮点格式化、关闭诊断协议|
|契约验证|配置组合不合法|安全启动依赖密码库、DMA 依赖资源分配|

### 3.3 条件编译和运行期分支的根本区别

```
#if CONFIG_TRACE
trace_emit();
#endif
```

当条件为假时，`trace_emit()` 不进入后续 C 编译。

```
if (CONFIG_TRACE) {
    trace_emit();
}
```

即使 `CONFIG_TRACE` 为零，保留的代码仍需通过语法和语义检查。优化器可能删除分支，但它不能让不存在的平台类型、寄存器声明和头文件依赖自动变得合法。

因此：

- **依赖不存在：使用条件编译或分离源文件。**
- **依赖存在，只是运行时行为不同：优先考虑普通控制流。**

## 4. 核心特性横向对比

### 4.1 各类机制对比

|机制|生效阶段|未选择代码是否类型检查|能否隔离平台头文件|能否运行期切换|主要风险|
|---|---|---|---|---|---|
|`#if` / `#ifdef`|预处理|通常否|能|不能|分支长期不构建、配置不一致|
|普通 `if`|运行期语义，可能被优化|是|不能|能|分支成本、非法依赖仍参与编译|
|`static inline` + 常量参数|编译优化|是|通常不能|视参数而定|依赖优化结果|
|函数指针表|运行期|是|结合源文件隔离|能|间接调用、初始化和生命周期|
|构建系统选择源文件|构建阶段|仅编译选中文件|能|不能|源文件选择与配置头不一致|
|链接垃圾回收|链接阶段|已完成编译|不能|不能|保留规则、段粒度、引用关系|
|弱符号替换|链接阶段|是|有限|通常不能|意外选中默认实现、工具链差异|

**推荐组合：构建系统负责选择实现，配置头负责声明与验证，模块接口负责保持稳定。**

### 4.2 `#if` 与 `#ifdef` 对比

|写法|判断对象|宏定义为 `0` 时|宏未定义时|推荐用途|
|---|---|---|---|---|
|`#ifdef X`|是否定义|真|假|头文件保护、存在性协议|
|`#ifndef X`|是否未定义|假|真|默认值、缺失检查|
|`#if X`|展开后的整数值|假|通常按零处理|规范化的数值配置|
|`#if defined(X)`|是否定义|真|假|与 `#ifdef` 等价，可组合|
|`#if defined(X) && X`|是否定义且非零|假|假|兼容外部可选宏|
|`#if X == VALUE`|配置值比较|按比较结果|可能静默误判|枚举型配置，需先校验存在性|

**项目内部布尔配置建议统一定义为 `0` 或 `1`，并用 `#if CONFIG_X`。**

## 5. 底层原理与功能特性深度解析

### 5.1 `#if` 不是 C 表达式解释器

预处理器可以处理整数运算、比较、逻辑运算、位运算和条件运算，但不能查询 C 类型系统。

可以：

```
#define CONFIG_CHANNELS 4
#define CONFIG_BYTES_PER_CHANNEL 32

#if (CONFIG_CHANNELS * CONFIG_BYTES_PER_CHANNEL) > 256
#error "Configured channel storage exceeds budget"
#endif
```

不能：

```
#if sizeof(unsigned int) == 4
/* 非法：预处理器不理解 sizeof。 */
#endif
```

也不能：

```
#if ((unsigned int)1) != 0
/* 非法：#if 不支持 C 类型转换。 */
#endif
```

需要类型信息时，改用编译期静态断言：

```
#include <stdint.h>

_Static_assert(sizeof(uint32_t) == 4u,
               "This module requires four-byte uint32_t");
```

注意：`uint32_t` 本身是可选的精确宽度类型。目标平台未提供它时，模块就不满足该接口前提。

### 5.2 未定义标识符会变成零

对 `#if` 表达式完成适用的宏替换后，剩余标识符通常按 `0` 处理。

```
#define CONFIG_UART_DMA 1

#if CONFIG_UART_DAM
/* 拼写错误，可能静默关闭。 */
#endif
```

这就是 `-Wundef` 的工程价值。

正确模式：

```
#ifndef CONFIG_UART_DMA
#error "CONFIG_UART_DMA must be defined"
#endif

#if (CONFIG_UART_DMA != 0) && (CONFIG_UART_DMA != 1)
#error "CONFIG_UART_DMA must be 0 or 1"
#endif

#if CONFIG_UART_DMA
/* DMA implementation. */
#endif
```

**边界说明：** 如果把宏错误地写成标识符，例如 `#define CONFIG_UART_DMA enabled`，预处理器可能把 `enabled` 当成零。因此，数值校验还需要与 **`-Wundef`、构建配置类型检查**配合使用。

### 5.3 枚举常量不能直接作为预处理配置值

这是嵌入式工程中非常隐蔽的错误。

```
enum {
    LOG_LEVEL_ERROR = 0,
    LOG_LEVEL_DEBUG = 3
};

#define CONFIG_LOG_LEVEL LOG_LEVEL_DEBUG

#if CONFIG_LOG_LEVEL >= LOG_LEVEL_DEBUG
/* 实际预处理比较可能成为 0 >= 0。 */
#endif
```

预处理器不知道枚举常量。两个名字都可能被替换为零，导致条件意外为真。

正确做法是用数值宏表达预处理域中的值：

```
#define APP_LOG_ERROR 0
#define APP_LOG_WARN  1
#define APP_LOG_INFO  2
#define APP_LOG_DEBUG 3

#ifndef CONFIG_LOG_LEVEL
#define CONFIG_LOG_LEVEL APP_LOG_INFO
#endif

#if (CONFIG_LOG_LEVEL < APP_LOG_ERROR) || \
    (CONFIG_LOG_LEVEL > APP_LOG_DEBUG)
#error "Invalid CONFIG_LOG_LEVEL"
#endif
```

如果 C 接口还需要枚举类型，可以另行映射：

```
typedef enum {
    APP_LOG_LEVEL_ERROR = APP_LOG_ERROR,
    APP_LOG_LEVEL_WARN  = APP_LOG_WARN,
    APP_LOG_LEVEL_INFO  = APP_LOG_INFO,
    APP_LOG_LEVEL_DEBUG = APP_LOG_DEBUG
} app_log_level_t;
```

这里分成两个命名空间：

- `APP_LOG_*`：预处理整数值。
- `APP_LOG_LEVEL_*`：C 枚举成员。

**这也修正了上一课需要特别注意的一点：枚举成员能参与 C 常量表达式，不能作为 `#if` 中的数值定义使用。**

### 5.4 整数运算与短路规则

`#if` 中支持逻辑短路：

```
#define CONFIG_SAMPLE_RATE 1000
#define CONFIG_TICK_RATE   100

#if (CONFIG_TICK_RATE == 0) || \
    ((CONFIG_SAMPLE_RATE % CONFIG_TICK_RATE) != 0)
#error "Sample rate must be an integer multiple of tick rate"
#endif
```

但**逻辑短路不意味着右侧任意预处理语法都可以不合法**。

不推荐：

```
#if defined(__has_include) && __has_include("vendor_feature.h")
#include "vendor_feature.h"
#endif
```

不支持 `__has_include` 的预处理器仍可能无法正确解析整个表达式。

更稳妥的兼容写法：

```
#if defined(__has_include)
# if __has_include("vendor_feature.h")
#  include "vendor_feature.h"
#  define APP_HAVE_VENDOR_FEATURE_HEADER 1
# else
#  define APP_HAVE_VENDOR_FEATURE_HEADER 0
# endif
#else
# define APP_HAVE_VENDOR_FEATURE_HEADER 0
#endif
```

同时要注意：

> **头文件存在，只能证明头文件可被找到，不能证明对应库已链接、硬件已存在或产品允许启用该能力。**

### 5.5 预处理整数宽度与符号问题

预处理条件表达式的整数计算不能简单理解为目标 MCU 的 `int` 宽度。标准在该上下文中按 `intmax_t`、`uintmax_t` 所对应的表示规则处理有符号和无符号整数类型。

因此以下两类表达式都不适合作为随意的配置运算：

```
#if -1 < 1U
/* 涉及无符号转换，不应按数学直觉推断。 */
#endif
```

```
#if (1 << CONFIG_IRQ_BITS) != 0
/* 位移范围、符号和位宽边界都需要约束。 */
#endif
```

工程建议：

- 配置尽量使用非负、范围受控的十进制整数。
- 先校验范围，再进行移位、乘法或除法。
- 目标对象尺寸与布局用 `_Static_assert` 校验。
- 不用复杂 `#if` 算术代替配置生成器。

示例：

```
#ifndef CONFIG_CHANNEL_COUNT
#error "CONFIG_CHANNEL_COUNT is required"
#endif

#if (CONFIG_CHANNEL_COUNT < 1) || (CONFIG_CHANNEL_COUNT > 16)
#error "CONFIG_CHANNEL_COUNT must be in [1, 16]"
#endif
```

### 5.6 `defined` 应直接写在条件指令中

推荐：

```
#if defined(CONFIG_BACKEND_UART) && defined(CONFIG_BACKEND_RTT)
#error "Choose one backend"
#endif
```

避免：

```
#define APP_IS_DEFINED(x) defined(x)

#if APP_IS_DEFINED(CONFIG_BACKEND_UART)
/* 宏展开生成 defined 的行为不具备所需的可移植性保证。 */
#endif
```

**不要用宏包装 `defined` 操作符。** 某些编译器接受这种形式，不代表它适合作为标准 C 项目的基础设施。

### 5.7 配置层次：值、能力与策略分离

建议分成三类：

```
/* 硬件能力：芯片/板级层拥有。 */
#define SOC_HAS_UART_DMA 1

/* 软件能力：构建系统或库配置拥有。 */
#define BUILD_HAS_DMA_DRIVER 1

/* 产品策略：产品配置拥有。 */
#define CONFIG_UART_USE_DMA 1
```

然后验证：

```
#if CONFIG_UART_USE_DMA && !SOC_HAS_UART_DMA
#error "Selected SoC does not support UART DMA"
#endif

#if CONFIG_UART_USE_DMA && !BUILD_HAS_DMA_DRIVER
#error "UART DMA requires DMA driver"
#endif
```

这样可以区分：

- 硬件是否支持。
- 软件实现是否被构建。
- 产品是否选择使用。

把三者混成 `USE_DMA`，通常会导致驱动、构建脚本和产品配置互相覆盖。

### 5.8 头文件保护与 `#pragma once`

可移植保护：

```
#ifndef ACME_APP_CONFIG_H_INCLUDED
#define ACME_APP_CONFIG_H_INCLUDED

/* Declarations and configuration. */

#endif /* ACME_APP_CONFIG_H_INCLUDED */
```

注意：

- 不使用 `__APP_CONFIG_H__`、`_APP_CONFIG_H` 等保留标识符形式。
- 不同头文件不能复制同一个保护宏。
- 保护宏只防止同一翻译单元重复包含，**不能防止不同源文件获得不同配置**。

`#pragma once` 被主流工具链广泛支持，但不属于 ISO C 的统一可移植接口。是否使用，应由工具链支持清单决定。

### 5.9 C 版本检测与 C23 条件指令

```
#if defined(__STDC_VERSION__)
# if __STDC_VERSION__ >= 202311L
#  define APP_C23_OR_LATER 1
# else
#  define APP_C23_OR_LATER 0
# endif
#else
# define APP_C23_OR_LATER 0
#endif
```

常见正式标准值：

|标准|`__STDC_VERSION__`|
|---|---|
|C99|`199901L`|
|C11|`201112L`|
|C17|`201710L`|
|C23|`202311L`|

C23 增加了 `#elifdef`、`#elifndef` 等便利形式，例如：

```
#if defined(APP_BOARD_A)
/* A */
#elifdef APP_BOARD_B
/* B */
#endif
```

对于以 C11/C17 为基线的工程，继续使用：

```
#elif defined(APP_BOARD_B)
```

**标准版本宏不是全部能力的唯一证明。** 工具链可能提前实现某些扩展，也可能对标准的部分功能支持不完整；关键能力仍需编译探测。

## 6. 性能量化分析

### 6.1 条件编译本身的运行期开销

**条件指令本身产生的运行期指令数为 0。**

但是否减少 Flash、RAM、栈和执行时间，取决于被删除的代码、数据及其引用关系。

对同一平台和构建选项：

```
Flash 节省量 = 启用镜像的 Flash 占用 − 关闭镜像的 Flash 占用

RAM 节省量 = 启用镜像的静态 RAM 占用 − 关闭镜像的静态 RAM 占用

周期节省量 = 启用路径周期 − 关闭路径周期
```

需要把 `.text`、`.rodata`、初始化数据的 Flash 装载空间和对齐填充分开分析，避免重复计数。

### 6.2 可核算的存储空间示例

以下是**明确假设下的计算值，不是目标板实测结果**。

假设某诊断模块包含：

- 64 条固定长度字符串，每条 48 字节。
- 256 条事件槽，每条固定为 16 字节。
- 字符串存入只读区。
- 事件缓冲区存入 `.bss`。
- 不计对齐、索引表和格式化库。

则：

```
字符串 Flash = 64 × 48 = 3072 字节

事件 RAM = 256 × 16 = 4096 字节
```

如果条件编译真正删除这两项定义：

```
直接 Flash 减少 = 3072 字节
直接静态 RAM 减少 = 4096 字节
```

最终镜像变化还可能包含：

- 日志函数及其依赖的减少。
- 格式化库是否仍被其他模块使用。
- 链接段对齐引入的差值。
- 字符串合并和 LTO 的影响。

**不能把源文件中一个数组的大小直接当成最终固件的整体节省量。**

### 6.3 串口输出对实时性的量化影响

假设：

- UART 波特率：115200。
- 帧格式：8N1，每字节共 10 bit。
- 一条日志：80 字节。

线路占用时间：

```
T = 80 × 10 / 115200
  ≈ 0.006944 秒
  ≈ 6.94 ms
```

对于 1 ms 控制周期：

```
6.94 ms / 1 ms ≈ 6.94 个控制周期
```

这说明同步日志可能显著破坏实时性。

但必须区分：

- **线路占用时间：约 6.94 ms。**
- **CPU 阻塞时间：取决于轮询、中断、DMA 和队列实现。**

DMA 可以降低 CPU 占用，不能改变线路带宽。

### 6.4 条件编译与常量分支的对比

|场景|`#if 0`|`if (0)`|
|---|---|---|
|不存在的类型、寄存器引用|可被隔离|仍可能报错|
|被包围的 `#include`|可不执行|不受普通 `if` 控制|
|调用参数的副作用|被删除|不执行|
|调用语句类型检查|不进行|进行|
|最终机器码|被包围内容不进入 C 编译|通常可删除，检查实际产物|
|字符串是否完全消失|若无其他引用通常消失|受编译和链接策略影响|

需要纠正一个容易混淆的认识：

> `if (0) { f(x++); }` 中，`x++` 在 C 语义上就不会执行，并不是靠优化器才避免执行。优化器影响的是代码和数据残留，不改变这个分支不执行的语义。

### 6.5 实测平台与结果记录要求

当前没有目标板、工具链和构建产物，因此不能提供可声称为“本课实测”的周期、Flash 或栈数据。正式工程报告应至少记录：

|维度|必填内容|
|---|---|
|硬件|MCU 完整型号、频率、缓存、Flash 等待周期|
|工具链|编译器与链接器版本|
|编译|优化级别、LTO、段拆分选项|
|链接|链接脚本、垃圾回收、保留规则|
|配置|产品配置标识、规范化配置文件哈希|
|测量|周期计数器、GPIO、栈高水位、map 文件|
|统计|样本数、中位数、最大值、测试负载|

不要把不同优化级别、不同链接脚本的两个镜像归因于单个配置宏。

### 6.6 配置空间也是性能与成本问题

若有 `n` 个独立布尔配置：

```
理论组合数 = 2^n
```

例如：

```
10 个布尔开关：1024 种
20 个布尔开关：1,048,576 种
```

这会直接影响构建时间和验证成本。

优化方向：

- 将互斥布尔量改成单一枚举配置。
- 用依赖约束提前排除非法组合。
- 定义有限、受支持的产品配置。
- 对非关键组合采用成对覆盖或约束覆盖。
- 对安全启动、Flash 擦写、OTA 等关键组合进行明确的专项验证。

**成对覆盖不能替代高风险多条件组合的测试。**

## 7. 应用场景选型指南

### 7.1 决策流程图

```
这个差异是否必须在构建时确定？
├─ 否
│  ├─ 运行期仅有少量参数不同 → 配置结构体 / 普通 if
│  └─ 实现需要动态选择 → 稳定接口 + 函数表
└─ 是
   ├─ 是否涉及不同平台依赖或大段实现？
   │  ├─ 是 → 独立源文件，由构建系统选择
   │  └─ 否 → 小范围条件编译
   ├─ 是否必须从发布镜像中删除？
   │  ├─ 是 → 条件编译 + 源文件选择 + 镜像检查
   │  └─ 否 → 可考虑常量分支或静态内联
   ├─ 是否影响公共结构体或调用约定？
   │  ├─ 是 → 建立 ABI 契约，优先重新设计接口
   │  └─ 否 → 保持差异在模块内部
   └─ 是否存在配置依赖或资源冲突？
      ├─ 是 → 配置生成阶段校验，并在 C 层补充断言
      └─ 否 → 纳入受支持配置矩阵
```

### 7.2 场景、方案与理由

|场景|方案|理由|
|---|---|---|
|MCU A/B 寄存器布局不同|不同驱动源文件|避免业务代码充斥芯片分支|
|裸机和 RTOS 时间接口不同|平台时间接口 + 两种实现|上层保持统一|
|发布版关闭调试字符串|条件编译 + 字符串检查|明确删除路径并验证镜像|
|同一固件支持多种传感器|运行期探测与驱动注册|不必为每个设备重建固件|
|DMA/中断模式互斥|单一模式宏|避免非法组合|
|浮点格式化依赖可选库|构建系统选择库 + 配置校验|宏本身不能控制库实现|
|MCU ISR 原子操作支持|工具链探测 + 硬件与实现验证|标准版本不等于 ISR 实时保证|
|预编译通信库有不同 ABI|固定公开接口或明确 ABI 版本|防止应用和库解释布局不同|

## 8. 工程最佳实践

### 8.1 统一配置入口

推荐结构：

```
config/
  app_config_values.h
  app_config.h
  app_config_validate.h

products/
  product_a.h
  product_b.h

generated/
  product_config.h

platform/
  app_platform.h
  app_platform_baremetal.c
  app_platform_rtos.c
```

职责：

- `app_config_values.h`：定义合法枚举值。
- `product_config.h`：当前构建选定的产品值。
- `app_config.h`：唯一公共入口，补默认值并执行检查。
- `app_config_validate.h`：依赖和范围检查。
- 构建系统：确保产品配置与源文件集合匹配。

**同一个配置项只允许一个权威来源。**

对于生成式配置体系，禁止某个源文件自行写：

```
#define CONFIG_UART_MODE 2
#include "app_config.h"
```

否则同一固件不同翻译单元可能获得不同视图。

### 8.2 默认值要区分风险级别

适合默认：

```
#ifndef CONFIG_DIAG
#define CONFIG_DIAG 0
#endif
```

不适合静默默认：

```
#ifndef CONFIG_FLASH_ERASE_SIZE
#error "Flash erase geometry must be explicitly configured"
#endif
```

推荐策略：

|配置|默认策略|
|---|---|
|普通诊断开关|可默认关闭|
|日志级别|可默认低级别|
|硬件地址、Flash 几何|必须明确指定或由芯片定义提供|
|安全启动策略|必须明确指定|
|RTOS 端口、CPU/FPU ABI|由构建配置明确选择|
|DMA 通道分配|由资源配置明确指定并校验|

### 8.3 互斥模式优先单值枚举

不推荐：

```
#define CONFIG_UART_POLL 1
#define CONFIG_UART_IRQ  1
#define CONFIG_UART_DMA  0
```

推荐：

```
#define APP_UART_MODE_POLL 0
#define APP_UART_MODE_IRQ  1
#define APP_UART_MODE_DMA  2

#define CONFIG_UART_MODE APP_UART_MODE_IRQ
```

校验：

```
#if (CONFIG_UART_MODE != APP_UART_MODE_POLL) && \
    (CONFIG_UART_MODE != APP_UART_MODE_IRQ) && \
    (CONFIG_UART_MODE != APP_UART_MODE_DMA)
#error "Unsupported UART mode"
#endif
```

三个布尔量有 `2³ = 8` 种组合，而三选一只需要三个有效状态。

### 8.4 条件编译靠近边界，远离业务流程

不推荐：

```
void control_step(void)
{
#if CONFIG_USE_RTOS
    /* lock */
#endif

    /* business logic */

#if CONFIG_BOARD_A
    /* board-specific IO */
#else
    /* another IO */
#endif

#if CONFIG_USE_RTOS
    /* unlock */
#endif
}
```

优先改成：

```
#include "app_platform.h"

void control_step(void)
{
    app_platform_enter();
    /* Business logic uses stable platform interfaces. */
    app_platform_set_output(1u);
    app_platform_leave();
}
```

平台差异放入独立实现。`enter/leave` 的互斥、中断和可重入语义必须由接口契约明确，不能仅仅把一段条件代码换成模糊函数名。

### 8.5 能力检测优先于厂商名称推断

不推荐：

```
#ifdef __GNUC__
/* Assume every desired GCC extension exists. */
#endif
```

原因：

- Clang 也定义部分 GCC 兼容宏。
- 不同 GCC 版本支持能力不同。
- 相同前端可能面向不同目标和 ABI。

对属性可以使用能力探测：

```
#if defined(__has_attribute)
# if __has_attribute(warn_unused_result)
#  define APP_NODISCARD __attribute__((warn_unused_result))
# endif
#endif

#ifndef APP_NODISCARD
#define APP_NODISCARD
#endif
```

关键能力不能静默退化时，改为构建失败：

```
#ifndef APP_HAVE_REQUIRED_ATOMIC_BACKEND
#error "Required atomic backend has not been selected"
#endif
```

**原子 API 可用，不等于原子操作无锁；无锁也不等于已满足具体 ISR 延迟预算。**

### 8.6 选型决策矩阵

|设计问题|首选方案|避免方案|
|---|---|---|
|两种板级实现|独立 `.c` 文件|业务函数中层层 `#if`|
|一个局部寄存器差异|局部条件编译|为一行差异复制整个驱动|
|公共数据布局差异|固定布局或不透明类型|随功能宏改变公开结构体|
|功能关闭|明确的空操作或不支持状态|各调用点自行判断宏|
|必需平台实现缺失|编译/链接失败|默认弱符号静默成功|
|运行期设备发现|驱动表、配置对象|为所有现场组合生成固件|
|功能发布控制|配置约束 + 产物检查|只依赖一个 `DEBUG` 宏|

### 8.7 条件编译不替代安全边界

编译期关闭调试命令可以减少攻击面，但不是授权机制。

不能仅靠：

```
#if CONFIG_FACTORY_COMMANDS
/* privileged command handlers */
#endif
```

就认为生产系统不需要权限验证、生命周期控制和安全启动。

是否需要这些机制由实际威胁模型决定；条件编译只负责构建选择。

## 9. 常见错误与避坑指南

### 9.1 错误一：把零值宏当作未定义

**错误代码：**

```
#define CONFIG_WATCHDOG 0

#ifdef CONFIG_WATCHDOG
watchdog_init();
#endif
```

**根因：** `#ifdef` 只检查定义状态。

**正确实现：**

```
#if CONFIG_WATCHDOG
watchdog_init();
#endif
```

配置入口保证该宏始终定义为 `0` 或 `1`。

**风险影响：**

- 产品声明关闭的功能实际启用。
- 看门狗、日志、诊断接口等行为与产品配置不一致。

---

### 9.2 错误二：未定义宏静默变成零

**错误代码：**

```
#if CONFIG_SECURE_BOOOT
secure_boot_verify();
#endif
```

**根因：** 拼写错误被解释为零。

**正确实现：**

```
#ifndef CONFIG_SECURE_BOOT
#error "CONFIG_SECURE_BOOT must be defined"
#endif

#if CONFIG_SECURE_BOOT
secure_boot_verify();
#endif
```

同时启用 `-Wundef`，对自有代码提升为错误。

**风险影响：**

- 关键功能静默缺失。
- 功能测试不覆盖对应路径时，缺陷可能进入发布版本。

---

### 9.3 错误三：在 `#if` 中使用枚举常量

**错误代码：**

```
enum {
    BACKEND_POLL = 0,
    BACKEND_DMA = 2
};

#define CONFIG_BACKEND BACKEND_DMA

#if CONFIG_BACKEND == BACKEND_POLL
/* 可能实际成为 0 == 0。 */
#endif
```

**根因：** 预处理器不读取枚举声明。

**正确实现：**

```
#define APP_BACKEND_POLL 0
#define APP_BACKEND_DMA  2

#define CONFIG_BACKEND APP_BACKEND_DMA

#if CONFIG_BACKEND == APP_BACKEND_POLL
/* Poll implementation. */
#endif
```

**风险影响：**

- 编译完全成功，但进入错误实现。
- 比直接编译失败更难定位。

---

### 9.4 错误四：不同翻译单元使用不同配置

**错误代码：**

```
/* public_device.h */
typedef struct {
    unsigned int state;

#if CONFIG_DEVICE_STATS
    unsigned int dropped;
#endif

    unsigned int errors;
} device_t;
```

假设通常的四字节 `unsigned int` 且无额外填充：

- 库启用统计：`errors` 位于偏移 8。
- 应用关闭统计：`errors` 位于偏移 4。

两边都能成功编译，链接器通常不能发现这个布局差异。

**正确实现：**

```
/* Public header. */
typedef struct app_device app_device_t;

int app_device_get_errors(const app_device_t *device,
                          unsigned int *errors);
```

结构体定义保留在实现文件内部。

或者保持公开布局固定，并建立明确 ABI 版本。

**根因：** 宏改变了跨模块二进制契约。

**风险影响：**

- 越界读写、错误状态解释、堆栈损坏。
- 只在特定预编译库或产品组合中出现。

---

### 9.5 错误五：关闭日志后业务副作用消失

**错误代码：**

```
#if CONFIG_DIAG
#define APP_LOG_VALUE(v) app_log_value(v)
#else
#define APP_LOG_VALUE(v) ((void)0)
#endif

APP_LOG_VALUE(++packet_count);
```

**根因：** 业务状态更新藏在可删除的诊断参数中。

**正确实现：**

```
++packet_count;
APP_LOG_VALUE(packet_count);
```

**风险影响：**

- 调试版与发布版业务行为不同。
- 关闭日志后计数、状态机或超时计算异常。

---

### 9.6 错误六：普通 `if` 不能隔离缺失的平台依赖

**错误代码：**

```
if (CONFIG_UART_DMA) {
    DMA1_Channel1->CCR = 1u;
}
```

目标平台即使关闭 DMA，也可能没有 `DMA1_Channel1` 声明。

**正确实现：**

```
#if CONFIG_UART_DMA
DMA1_Channel1->CCR = 1u;
#endif
```

当实现较大时，选择单独源文件。

**根因：** 混淆运行期控制流和预处理依赖隔离。

**风险影响：**

- 关闭功能的目标仍编译失败。
- 为了绕过编译错误引入伪寄存器定义，进一步隐藏问题。

---

### 9.7 错误七：认为 `#if 0` 可以容纳任意文本

**错误代码：**

```
#if 0
/* An unfinished comment
#endif
```

**根因：** 注释处理早于条件分支丢弃，`#endif` 被吞进注释。

**正确实现：**

```
#if 0
/* Complete comment. */
old_function();
#endif
```

更好的长期做法是删除失效代码，让版本控制保存历史。

**风险影响：**

- 预处理失败。
- 编辑器显示和实际编译边界不一致。
- 大片代码意外被注释或条件屏蔽。

---

### 9.8 错误八：依赖头文件包含顺序改变配置

**错误代码：**

```
/* module_a.h */
#ifndef CONFIG_RING_SIZE
#define CONFIG_RING_SIZE 64
#endif
```

```
/* module_b.h */
#ifndef CONFIG_RING_SIZE
#define CONFIG_RING_SIZE 128
#endif
```

**根因：** 公共配置没有唯一入口，先包含的头文件决定最终值。

**正确实现：**

```
/* Both headers include the same authoritative configuration. */
#include "app_config.h"
```

默认值仅在配置入口定义。

**风险影响：**

- 重排 `#include` 就改变程序。
- 增量构建与干净构建行为不同。
- 跨模块缓冲区大小不一致。

---

## 10. 多机制组合使用方案

下面设计一个完整的、可裁剪的诊断事件模块，组合使用：

1. 统一配置入口。
2. 数值范围检查。
3. 跨功能依赖检查。
4. `_Static_assert`。
5. 条件编译与稳定接口。
6. 有界缓冲区与明确的溢出行为。

### 10.1 配置值定义

`app_config_values.h`：

```
#ifndef ACME_APP_CONFIG_VALUES_H_INCLUDED
#define ACME_APP_CONFIG_VALUES_H_INCLUDED

#define APP_UART_MODE_POLL 0
#define APP_UART_MODE_IRQ  1
#define APP_UART_MODE_DMA  2

#endif
```

### 10.2 产品配置

`product_config.h` 由构建系统生成或选择，不允许源文件自行覆盖：

```
#ifndef ACME_PRODUCT_CONFIG_H_INCLUDED
#define ACME_PRODUCT_CONFIG_H_INCLUDED

#define CONFIG_USE_RTOS          0
#define CONFIG_DIAG              1
#define CONFIG_DIAG_CAPACITY     64
#define CONFIG_UART_MODE         APP_UART_MODE_IRQ

#define SOC_HAS_UART_DMA         1
#define BUILD_HAS_DMA_DRIVER     0

#endif
```

本例采用**产品配置头作为唯一权威来源**。如果工程允许 `-D` 覆盖，应另外定义统一、可审计的覆盖协议，不能与此方案混用而不说明优先级。

### 10.3 统一入口与校验

`app_config.h`：

```
#ifndef ACME_APP_CONFIG_H_INCLUDED
#define ACME_APP_CONFIG_H_INCLUDED

#include "app_config_values.h"
#include "product_config.h"

#ifndef CONFIG_USE_RTOS
#error "CONFIG_USE_RTOS is required"
#endif

#ifndef CONFIG_DIAG
#error "CONFIG_DIAG is required"
#endif

#ifndef CONFIG_UART_MODE
#error "CONFIG_UART_MODE is required"
#endif

#ifndef SOC_HAS_UART_DMA
#error "SOC_HAS_UART_DMA is required"
#endif

#ifndef BUILD_HAS_DMA_DRIVER
#error "BUILD_HAS_DMA_DRIVER is required"
#endif

#if (CONFIG_USE_RTOS != 0) && (CONFIG_USE_RTOS != 1)
#error "CONFIG_USE_RTOS must be 0 or 1"
#endif

#if (CONFIG_DIAG != 0) && (CONFIG_DIAG != 1)
#error "CONFIG_DIAG must be 0 or 1"
#endif

#if (SOC_HAS_UART_DMA != 0) && (SOC_HAS_UART_DMA != 1)
#error "SOC_HAS_UART_DMA must be 0 or 1"
#endif

#if (BUILD_HAS_DMA_DRIVER != 0) && (BUILD_HAS_DMA_DRIVER != 1)
#error "BUILD_HAS_DMA_DRIVER must be 0 or 1"
#endif

#if (CONFIG_UART_MODE != APP_UART_MODE_POLL) && \
    (CONFIG_UART_MODE != APP_UART_MODE_IRQ) && \
    (CONFIG_UART_MODE != APP_UART_MODE_DMA)
#error "Unsupported UART mode"
#endif

#if CONFIG_UART_MODE == APP_UART_MODE_DMA

# if !SOC_HAS_UART_DMA
#  error "Selected SoC has no UART DMA capability"
# endif

# if !BUILD_HAS_DMA_DRIVER
#  error "UART DMA mode requires the DMA driver"
# endif

#endif

#if CONFIG_DIAG

# ifndef CONFIG_DIAG_CAPACITY
#  error "CONFIG_DIAG_CAPACITY is required when diagnostics are enabled"
# endif

# if (CONFIG_DIAG_CAPACITY < 2) || (CONFIG_DIAG_CAPACITY > 1024)
#  error "Diagnostic capacity must be in [2, 1024]"
# endif

# if (CONFIG_DIAG_CAPACITY & (CONFIG_DIAG_CAPACITY - 1)) != 0
#  error "Diagnostic capacity must be a power of two"
# endif

#endif

#endif
```

这里使用二次幂容量，是为了让后端环形索引可以采用掩码；**不是所有环形队列都必须要求二次幂容量**。

### 10.4 稳定接口

`app_diag.h`：

```
#ifndef ACME_APP_DIAG_H_INCLUDED
#define ACME_APP_DIAG_H_INCLUDED

#include <stdint.h>
#include "app_config.h"

typedef struct {
    uint32_t event_id;
    uint32_t argument;
    uint32_t timestamp;
} app_diag_event_t;

typedef enum {
    APP_DIAG_OK = 0,
    APP_DIAG_DISABLED,
    APP_DIAG_FULL,
    APP_DIAG_EMPTY,
    APP_DIAG_INVALID
} app_diag_status_t;

#if CONFIG_DIAG

app_diag_status_t app_diag_push(const app_diag_event_t *event);
app_diag_status_t app_diag_pop(app_diag_event_t *event);

#else

static inline app_diag_status_t
app_diag_push(const app_diag_event_t *event)
{
    (void)event;
    return APP_DIAG_DISABLED;
}

static inline app_diag_status_t
app_diag_pop(app_diag_event_t *event)
{
    (void)event;
    return APP_DIAG_DISABLED;
}

#endif

#endif
```

关闭功能后的行为明确：

- 调用接口仍然存在。
- 参数仍按普通函数调用规则求值。
- 返回“不支持/已关闭”状态。
- 不会让调用方输出对象处于“假装成功但未写入”的状态。

### 10.5 单执行上下文的有界队列实现

`app_diag.c`：

```
#include <stddef.h>
#include "app_diag.h"

#if CONFIG_DIAG

/*
 * Contract:
 * - push/pop execute in one serialized context.
 * - Concurrent task/ISR access is NOT supported by this implementation.
 * - No dynamic allocation.
 * - No reset API: avoids accidental concurrent reinitialization.
 */
typedef struct {
    app_diag_event_t events[CONFIG_DIAG_CAPACITY];
    unsigned int read_index;
    unsigned int write_index;
    unsigned int count;
} app_diag_queue_t;

_Static_assert(
    (sizeof(app_diag_event_t) * CONFIG_DIAG_CAPACITY) <= 16384u,
    "Diagnostic event storage exceeds the configured RAM budget");

static app_diag_queue_t app_diag_queue;

static unsigned int app_diag_next(unsigned int index)
{
    return (index + 1u) &
           ((unsigned int)CONFIG_DIAG_CAPACITY - 1u);
}

app_diag_status_t app_diag_push(const app_diag_event_t *event)
{
    if (event == NULL) {
        return APP_DIAG_INVALID;
    }

    if (app_diag_queue.count ==
        (unsigned int)CONFIG_DIAG_CAPACITY) {
        return APP_DIAG_FULL;
    }

    app_diag_queue.events[app_diag_queue.write_index] = *event;
    app_diag_queue.write_index =
        app_diag_next(app_diag_queue.write_index);
    ++app_diag_queue.count;

    return APP_DIAG_OK;
}

app_diag_status_t app_diag_pop(app_diag_event_t *event)
{
    if (event == NULL) {
        return APP_DIAG_INVALID;
    }

    if (app_diag_queue.count == 0u) {
        return APP_DIAG_EMPTY;
    }

    *event = app_diag_queue.events[app_diag_queue.read_index];
    app_diag_queue.read_index =
        app_diag_next(app_diag_queue.read_index);
    --app_diag_queue.count;

    return APP_DIAG_OK;
}

#endif
```

这是一个**调用上下文明确受限的可复用实现**，不能直接宣称为 ISR 安全或线程安全。

若用于任务与 ISR 并发：

- 选择符合中断优先级规则的 RTOS 队列。
- 或实现经过验证的 SPSC 队列。
- 明确原子性、内存序、缓存一致性和队列满策略。
- 不通过添加 `volatile` 来替代同步设计。

### 10.6 关闭后完全不求值的可选入口

若诊断参数准备成本较高，并且约定可以完全删除：

```
#if CONFIG_DIAG

#define APP_DIAG_RECORD(id_, arg_, ts_)                         \
    do {                                                       \
        const app_diag_event_t app_diag_local_event_ = {        \
            (uint32_t)(id_),                                    \
            (uint32_t)(arg_),                                   \
            (uint32_t)(ts_)                                     \
        };                                                     \
        (void)app_diag_push(&app_diag_local_event_);             \
    } while (0)

#else

#define APP_DIAG_RECORD(id_, arg_, ts_) ((void)0)

#endif
```

这里的临时名称仍有宏名称冲突风险；应采用项目命名前缀，并限制这类宏的使用范围。需要处理队列满、输入范围或返回状态的调用方，应直接调用函数接口。

两种入口的语义要明确区分：

|入口|关闭后参数是否求值|适用目的|
|---|---|---|
|`app_diag_push(...)`|是|稳定函数接口|
|`APP_DIAG_RECORD(...)`|否|可完全裁剪的诊断点|

## 11. 工业级实际案例分析

以下选取三个真实工业领域中的典型需求模式，给出可落地设计；不将示例包装为未经提供证据的具体企业项目。

### 11.1 案例一：工业网关的量产、维护与开发镜像

#### 需求

同一硬件提供：

- 开发镜像：详细日志、诊断命令、测试接口。
- 维护镜像：受控维护能力。
- 量产镜像：关闭测试接口，保留必要故障记录。

仅用一个 `DEBUG` 宏不够，因为“日志级别”“维护能力”“安全策略”不是同一维度。

#### 架构设计

- 产品配置明确选择镜像类型。
- 安全相关功能逐项配置。
- 配置阶段检查非法组合。
- 发布阶段检查 ELF、map 和最终镜像。
- 维护授权由运行期安全机制承担。

#### 核心代码

```
#define APP_IMAGE_DEVELOPMENT 0
#define APP_IMAGE_SERVICE     1
#define APP_IMAGE_PRODUCTION  2

#define CONFIG_IMAGE_KIND          APP_IMAGE_PRODUCTION
#define CONFIG_TEST_COMMANDS       0
#define CONFIG_MANUFACTURING_HOOKS 0
#define CONFIG_SECURE_BOOT         1

#if (CONFIG_IMAGE_KIND != APP_IMAGE_DEVELOPMENT) && \
    (CONFIG_IMAGE_KIND != APP_IMAGE_SERVICE) && \
    (CONFIG_IMAGE_KIND != APP_IMAGE_PRODUCTION)
#error "Invalid image kind"
#endif

#if CONFIG_IMAGE_KIND == APP_IMAGE_PRODUCTION

# if CONFIG_TEST_COMMANDS
#  error "Production image must not contain test commands"
# endif

# if CONFIG_MANUFACTURING_HOOKS
#  error "Production image must not contain manufacturing hooks"
# endif

# if !CONFIG_SECURE_BOOT
#  error "This product requires secure boot in production"
# endif

#endif
```

#### 设计要点

- `NDEBUG` 只控制标准 `assert` 的行为，不应该自动代表完整量产策略。
- 禁止测试接口还要检查它是否从其他静态库进入镜像。
- 在最终二进制中搜索字符串只能提供辅助证据；更可靠的检查还包括符号、段和链接依赖。
- 自定义段可能被 `KEEP` 保留，不能假设 `--gc-sections` 会删除。

---

### 11.2 案例二：电机控制器的轮询、中断与 DMA 后端

#### 需求

- 低成本型号使用中断收发。
- 高性能型号使用 DMA。
- 控制算法代码保持一致。
- DMA 不得与 ADC 采样通道冲突。
- ISR 延迟必须满足控制周期预算。

#### 架构设计

```
控制算法
  ↓
稳定通信接口
  ↓
构建系统选择一个实现
  ├─ uart_irq.c
  └─ uart_dma.c
```

配置校验：

```
#define APP_UART_MODE_IRQ 1
#define APP_UART_MODE_DMA 2

#define CONFIG_UART_MODE      APP_UART_MODE_DMA
#define CONFIG_UART_DMA_CH    3
#define CONFIG_ADC_DMA_CH     1

#if CONFIG_UART_MODE == APP_UART_MODE_DMA

# if CONFIG_UART_DMA_CH == CONFIG_ADC_DMA_CH
#  error "UART and ADC DMA channels conflict"
# endif

#endif
```

#### 核心接口

```
#include <stddef.h>
#include <stdint.h>

typedef enum {
    APP_UART_OK = 0,
    APP_UART_BUSY,
    APP_UART_INVALID,
    APP_UART_IO_ERROR
} app_uart_status_t;

/*
 * Synchronous contract:
 * On success, the backend no longer references data.
 * Timeout and blocking bounds are defined by the platform implementation.
 */
app_uart_status_t app_uart_write(const uint8_t *data,
                                size_t length);
```

两个后端必须实现相同的缓冲区生命周期语义。不能让中断实现同步完成、DMA 实现立即返回却继续引用缓冲区，而接口文档完全不变。

#### 设计要点

- 如果 DMA 控制器支持请求复用，同一通道编号检查未必足够，需要按真实硬件路由建模。
- DMA 能力还依赖可访问内存、缓存维护和对齐约束。
- FPU、CPU 架构、中断向量等构建选项必须与启动文件和 RTOS 端口一致。
- 条件编译解决实现选择，不能证明 ISR 最坏延迟已达标。

### 11.3 案例三：带预编译协议库的医疗或工业设备

#### 需求

应用与协议库由不同团队构建，需要避免：

- 一个使用打包结构体，另一个使用默认对齐。
- 一个启用扩展字段，另一个未启用。
- 一个使用短枚举 ABI，另一个未使用。
- API 版本一致但配置 ABI 不一致。

#### 架构设计

- 公开数据结构固定布局或采用不透明句柄。
- 接口使用明确宽度的整数。
- 不跨库边界暴露受配置影响的内部对象。
- 提供版本与配置兼容性查询。
- 构建时记录 ABI 相关编译选项。

#### 核心代码

```
#include <stdint.h>

#define APP_PROTOCOL_ABI_VERSION UINT32_C(3)

typedef struct {
    uint32_t abi_version;
    uint32_t feature_bits;
    uint32_t max_payload;
} app_protocol_info_t;

/*
 * Library implementation writes its own build information.
 * Returns 0 on success; nonzero on invalid argument or other failure.
 */
int app_protocol_get_info(app_protocol_info_t *info);
```

应用启动检查：

```
typedef enum {
    APP_PROTOCOL_CHECK_OK = 0,
    APP_PROTOCOL_CHECK_QUERY_FAILED,
    APP_PROTOCOL_CHECK_ABI_MISMATCH
} app_protocol_check_t;

app_protocol_check_t app_protocol_check_compatibility(void)
{
    app_protocol_info_t info = { 0u, 0u, 0u };

    if (app_protocol_get_info(&info) != 0) {
        return APP_PROTOCOL_CHECK_QUERY_FAILED;
    }

    if (info.abi_version != APP_PROTOCOL_ABI_VERSION) {
        return APP_PROTOCOL_CHECK_ABI_MISMATCH;
    }

    return APP_PROTOCOL_CHECK_OK;
}
```

#### 设计要点

- 查询结构自身必须具有稳定 ABI。
- 查询通过不能修复调用约定、CPU ABI 或浮点 ABI 不一致；这些必须由构建和链接策略保证。
- 配置哈希应覆盖真正影响 ABI 的项目，不能只哈希几个功能宏。
- 必须在访问配置相关对象之前完成兼容性检查。
- 若使用链接期配置标记，必须确保真实符号引用能保留，避免被优化和段垃圾回收删除。

## 12. 高频问题深度答疑

### 12.1 为什么项目内部推荐“总是定义为 0/1”，而不是“定义即启用”？

因为它减少了语义歧义：

```
#define CONFIG_DIAG 0
```

始终明确表达“存在这个配置项，当前关闭”。

如果采用存在性约定：

```
/* No definition means disabled. */
```

则“产品有意关闭”和“配置生成遗漏”难以区分。

但外部库可能规定：

```
#ifdef LIB_ENABLE_FEATURE
```

此时定义为零仍会启用。应在适配层转换：

```
#if CONFIG_LIBRARY_FEATURE
#define LIB_ENABLE_FEATURE
#endif
```

转换必须发生在第三方头文件首次包含之前。

**不要把项目内部约定强行套到第三方库。**

### 12.2 关闭功能时，应该删除接口还是保留空实现？

取决于接口语义。

适合保留：

- 可选诊断。
- 可选性能统计。
- 上层允许“功能不可用”的查询接口。

适合让编译失败：

- 某产品根本不允许使用该功能。
- 没有该功能时，调用方无法正确工作。
- 安全关键路径不允许静默退化。

对于“读取数据”的接口，关闭后不能返回成功却不填写输出参数。

```
static inline int app_optional_read(unsigned int *value)
{
    (void)value;
    return -1;
}
```

这里返回失败比伪造数据更清晰；实际工程应使用项目统一错误码。

### 12.3 条件编译能否保证代码绝对不进入固件？

只对受该条件控制的源码路径提供保证。

还要考虑：

- 同名实现来自其他静态库。
- 启动文件和汇编中存在直接引用。
- 链接脚本 `KEEP` 保留自注册段。
- 全局构造、初始化表或函数指针表创建引用。
- 数据通过生成文件或二进制资源进入镜像。

因此，重要裁剪项应验证：

```
配置选择
  ↓
源文件列表
  ↓
预处理结果
  ↓
链接引用
  ↓
最终镜像
```

### 12.4 为什么改一个宏，有时必须重新编译所有模块？

因为宏可以改变：

- 公共结构体布局。
- 内联函数实现。
- 数组大小。
- 常量取值。
- 函数声明。
- 条件包含的头文件。
- 库依赖和 ABI。

正确的构建系统应追踪头文件依赖，并确保生成配置变化能使相关对象失效。

常见措施：

- 编译器依赖文件，如 `-MMD -MP`。
- 不同产品使用不同构建目录。
- 编译缓存正确考虑命令行和头文件。
- 发布构建执行可复现的干净构建。

`-MMD` 不会自动把所有外部构建输入变成依赖；生成脚本、链接脚本和配置数据库仍需构建系统管理。

### 12.5 `#if` 嵌套多少层开始需要重构？

标准没有工程层面的“最佳层数”。

可把以下情况作为重构信号：

- 同一平台条件在多个模块重复出现。
- 一个函数同时区分板卡、RTOS、日志和通信模式。
- 修改一个功能需要理解多个独立宏的交叉关系。
- 某个分支长期不构建。
- 宏改变公开类型布局。
- 很难回答当前产品到底会编译哪段实现。

团队可以把 **两到三层嵌套**作为代码审查提示阈值，但它不是语言限制或普适性能界限。

### 12.6 配置矩阵太大，怎样保证有效验证？

分层处理：

1. **语法合法性**：配置生成器检查类型、范围和依赖。
2. **编译合法性**：受支持配置全部构建。
3. **边界覆盖**：最小值、最大值、关闭值和互斥选项。
4. **高风险覆盖**：OTA、安全启动、Flash 擦写、DMA/缓存组合。
5. **目标测试**：仿真通过不能替代寄存器、时序和并发验证。
6. **发布追踪**：固件与配置、工具链、链接脚本一一对应。

测试对象应是明确的受支持产品配置，而不是无限制地承诺任意宏组合都能工作。

## 13. 课程核心总结

### 13.1 核心要点

- **`#ifdef` 判断存在性，`#if` 判断数值。**
- **未定义标识符在 `#if` 中可能变成零，必须重视 `-Wundef`。**
- **枚举、`sizeof` 和类型转换不属于预处理器的类型计算能力。**
- **条件编译应围绕模块和平台边界组织，避免渗入业务流程。**
- **配置是跨模块契约，可能影响 ABI、资源分配和镜像内容。**
- **能力、构建依赖和产品策略需要分开表达。**
- **关闭功能后的求值行为和错误语义必须写进接口契约。**
- **最终镜像检查比“源代码里写了 `#if`”更能说明裁剪是否生效。**

### 13.2 性能排序

对于关闭功能的本地调用路径：

```
预处理删除：相关调用和参数不进入 C 编译
常量假分支：运行期不执行，产物残留需检查
空函数/空内联：实参仍求值，调用是否残留取决于实现和优化
运行期禁用：至少保留相应状态与控制逻辑，具体成本需测量
```

这不是对所有项目的绝对机器周期排名。若最终生成相同机器码，则运行期成本相同。

### 13.3 通用选型结论

|问题|通用结论|
|---|---|
|小范围编译期差异|使用条件编译|
|大范围平台实现差异|选择不同源文件|
|运行期变化|使用配置对象和普通控制流|
|发布裁剪要求|条件编译与产物检查结合|
|公共布局变化|优先不透明类型或固定 ABI|
|非法配置|越早失败越好，不能静默回退|
|必需能力缺失|明确构建失败|
|可选能力缺失|定义可预测的降级行为|

## 16. 实践与进阶路径

### 16.1 基础任务：构造条件编译行为实验

编写一个测试文件，覆盖：

1. 宏未定义。
2. 宏定义为零。
3. 宏定义为一。
4. 宏定义为枚举名。
5. 宏定义为错误标识符。
6. 普通 `if (0)` 内的不存在函数或类型。
7. `#if 0` 内的合法记号但非法 C 语法。
8. 第三方“存在即启用”配置。

分别观察：

- 预处理输出。
- `-Wundef` 诊断。
- C 语义检查结果。
- 最终符号和字符串残留。

**验收要求：能解释每个结果对应的阶段。**

### 16.2 工程任务：实现统一配置体系

为一个小型固件建立：

- 两种板卡。
- 裸机和 RTOS 两种执行环境。
- 三种 UART 模式。
- 诊断开关和容量。
- 固定的量产配置。

加入：

- 必需项检查。
- 布尔值检查。
- 模式合法性检查。
- DMA 能力与资源冲突检查。
- RAM 预算静态断言。
- 产品配置标识。

**验收要求：非法组合必须在明确位置失败，并给出可读错误。**

### 16.3 架构任务：重构一个宏污染模块

选择一个存在大量 `#if` 的驱动：

1. 列出所有配置轴。
2. 区分产品策略、平台能力和运行期参数。
3. 抽取稳定接口。
4. 将主要平台实现拆成独立源文件。
5. 将局部寄存器差异保留在最小范围。
6. 去除公共结构体中的配置相关字段。

**验收要求：上层业务代码不再直接依赖 MCU 型号宏。**

### 16.4 性能测试任务

在实际目标板上构建四个版本：

|版本|配置|
|---|---|
|A|无诊断基线|
|B|诊断源代码存在，但条件编译关闭|
|C|诊断启用，运行期关闭|
|D|诊断启用并持续输出|

记录：

- Flash 总占用与各段变化。
- 静态 RAM。
- 最大栈使用。
- 控制任务响应时间。
- 日志线路占用。
- 队列峰值和丢弃数量。
- 是否出现截止期违约。

**比较时保持工具链、链接脚本、优化选项和测试负载一致。**

### 16.5 CI 任务：建立配置验证闭环

```
规范化产品配置
  ↓
配置类型、范围、依赖检查
  ↓
生成配置头及构建清单
  ↓
选择源文件和库
  ↓
严格编译
  ↓
链接与存储预算检查
  ↓
发布镜像内容检查
  ↓
目标功能与时序测试
  ↓
归档配置、工具链、map、ELF 与固件
```

增加负向构建测试：

- 必需宏缺失应失败。
- 拼写错误应失败。
- DMA 资源冲突应失败。
- 发布版启用测试命令应失败。
- 配置容量超预算应失败。
- 应用与预编译库 ABI 不一致应被拒绝。

**验收要求：不仅证明合法配置能构建，还要证明非法配置无法悄悄通过。**
